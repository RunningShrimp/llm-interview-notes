## 1.1 网络与协议

### 1.1.1 HTTP 协议演进：1.0 → 1.1 → 2 → 3

**是什么（通俗类比）：**

HTTP 版本演进就是「修路」的历史：1.0 是每次出门都重新叫车；1.1 是司机留下来等你（Keep-Alive）；2 是一辆车装多份货分格配送（多路复用）；3 是干脆换了套不怕堵的私人路网（QUIC）。

**演进对比表：**

| 版本 | 核心机制 | 解决了什么 | 遗留问题 |
|------|---------|-----------|---------|
| HTTP/1.0 | 一请求一 TCP 连接 | — | 每次都三次握手，开销大 |
| HTTP/1.1 | Keep-Alive 持久连接、管道化、Chunked、Host 头 | 连接复用省握手 | 队头阻塞：响应必须按序返回 |
| HTTP/2 | 二进制分帧、多路复用、HPACK 头压缩、服务器推送 | 应用层队头阻塞（一个连接并行多个流） | TCP 层队头阻塞：丢一个包全体等重传 |
| HTTP/3 | QUIC（基于 UDP） | 0-RTT 建连、连接迁移、彻底解决传输层队头阻塞 | 中间设备对 UDP 不友好，普及度 |

**几个高频细节（资深经验要能脱口而出）：**

- **Keep-Alive ≠ TCP KeepAlive**：前者是 HTTP 层「连接复用」，后者是 TCP 层「保活探测」，完全两回事
- **Chunked Transfer**：响应体长度未知时，把数据切成一块块发，每块前标注十六进制长度，`0\r\n` 结尾——**它就是 SSE 能「边生成边推」的协议基础**
- **TLS**：非对称加密（ECDHE）交换密钥 → 对称加密（AES）传数据，安全与性能兼得；TLS 1.3 握手降为 1-RTT，会话恢复支持 0-RTT
- **HTTP/2 对 SSE 是利好**：HTTP/1.1 下浏览器对同域名最多 6 个 TCP 连接，开多个 SSE 会占满；HTTP/2 多路复用让多个 SSE 流跑在同一连接上

### 1.1.2 经典题：一个 HTTP 请求的完整旅程

**怎么答（按这个顺序讲，每步都能展开一层）：**

```text
浏览器                          网关/负载均衡               服务端                存储
  │                                │                        │                    │
  │ ① URL 解析、DNS 解析            │                        │                    │
  │   （本地缓存→递归查询→权威DNS）  │                        │                    │
  │ ② TCP 三次握手 ──────────────────────────────────────▶ │                    │
  │ ③ TLS 握手（若 HTTPS，1~2-RTT）──────────────────────▶ │ 证书验证/ECDHE 协商 │
  │ ④ 发送 HTTP 请求（请求行/头/体）│                        │                    │
  │ ───────────────────────────▶ ⑤ LVS/Nginx 四层/七层转发 ─▶ ⑥ 路由→中间件      │
  │                                │   （负载均衡/限流/WAF） │   鉴权/参数校验     │
  │                                │                        │ ⑦ 业务逻辑          │
  │                                │                        │   查缓存 ──────────▶ Redis
  │                                │                        │   未命中回源 ──────▶ MySQL
  │                                │                        │ ⑧ 组装响应（可能    │
  │                                │                        │   Chunked 流式）    │
  │ ⑨ 接收响应、解析渲染 ◀─────────────── 原路返回 ──────────────────────────── │
  │ ⑩ Keep-Alive 复用连接 或 四次挥手                          │                    │
```

**拉开差距的讲法（每步带一个「可能出问题的点」）：**

- DNS：本地缓存污染 / TTL 过长导致扩容不生效
- TCP/TLS：握手 RTT 是移动端首屏延迟大头 → HTTP/3 或 TLS 1.3 优化
- 网关层：连接数上限、限流误伤、`proxy_buffering` 导致流式失效（见 1.1.4）
- 服务端：线程池打满、下游超时向上传递
- 传输层：TCP 队头阻塞、慢启动对短请求的影响

> 面试官问这道题，考的不是流程背诵，而是你**脑子里有没有整条链路的容量模型和故障模型**。

### 1.1.3 SSE vs WebSocket：LLM 流式为什么首选 SSE（★本章最高频）

**是什么（通俗类比）：**

SSE 是「收音机」——你打开它听广播，单向的，电台说啥你听啥；WebSocket 是「电话」——双向实时通话，谁都能先开口。LLM 流式输出恰好是「服务端单向吐 token」的收音机场景，拿电话协议干收音机的活，纯属浪费。

**对比表（背熟）：**

| 维度 | SSE | WebSocket |
|------|-----|-----------|
| 通信方向 | 单向（服务端→客户端） | 全双工 |
| 协议 | 纯 HTTP（`Content-Type: text/event-stream`） | 独立协议（HTTP Upgrade 握手后变成 ws://） |
| 数据格式 | 文本 | 文本 + 二进制 |
| 断线重连 | **浏览器 EventSource 原生自动重连**，带 `Last-Event-ID` 断点续传 | 需要自己实现心跳 + 重连逻辑 |
| 网关/代理/CDN 友好度 | 高——就是普通 HTTP 响应 | 低——需要网关专门支持 Upgrade |
| 认证 | 复用 HTTP 头（Cookie/Token） | 握手后要自己传 |
| 连接数限制 | HTTP/1.1 下浏览器同域 6 个（HTTP/2 无此问题） | 无此限制 |
| 适用场景 | LLM 流式、监控大盘推送、通知 | 聊天室、协同编辑、游戏、双向指令 |

**为什么 LLM 流式首选 SSE（答这四条）：**

1. **业务模型匹配**：LLM 对话本质是「一问一答 + 答案流式吐出」，用户在生成期间不发数据——单向足够
2. **基础设施零改造**：SSE 走纯 HTTP，网关、LB、CDN、鉴权、埋点全部复用现有体系；WebSocket 要过 Upgrade，中间任何一环不支持就挂
3. **断线恢复便宜**：EventSource 自动重连 + `Last-Event-ID`，配合服务端按 conversation_id 续传已生成 token，天然抗弱网
4. **HTTP/2 加持**：多路复用解决了浏览器连接数上限，SSE 的最后一块短板已补齐

**SSE 数据流（白板能画）：**

```text
客户端                             服务端                        LLM API
  │  POST /chat  Accept: text/event-stream                        │
  │ ────────────────────────────▶ │                              │
  │                               │  发起 LLM 流式请求             │
  │                               │ ───────────────────────────▶ │
  │ ◀── 响应头 200                 │                              │
  │     Content-Type: text/event-stream                           │
  │     Cache-Control: no-cache                                   │
  │                               │ ◀── data: {"delta":"你"}      │
  │ ◀── data: {"delta":"你"}       │ ◀── data: {"delta":"好"}      │
  │ ◀── data: {"delta":"好"}       │      （逐 token 透传）         │
  │     ...                       │                              │
  │ ◀── event: done / data: [DONE] │                              │
  ▼ 断线时 EventSource 自动重连，携 Last-Event-ID，服务端从断点续发
```

**SSE 报文长什么样（认得出）：**

```text
id: 41            ← 事件序号：断点续传的依据
data: {"delta": "你好"}

event: done       ← 自定义事件类型
data: [DONE]

retry: 3000       ← 告诉客户端断线后 3 秒重连
```

### 1.1.4 Nginx 的 SSE 缓冲陷阱（线上实战必考）

**是什么：**

Nginx 默认开启 `proxy_buffering`——把上游响应攒到缓冲区再发给客户端。SSE 的 token 被攒在缓冲区里，**用户盯着空白屏幕半天，突然一次性蹦出一大段**——这就是「假流式」，接 LLM 网关时最经典的翻车现场。

**为什么：**
- 代理默认假设「响应攒齐了再转发更高效」，但流式的意义恰恰是「来一个发一个」
- `gzip` 压缩也会攒数据成块；默认 `proxy_read_timeout 60s` 会让长回答中途断连

**怎么做（生产配置片段）：**

```nginx
location /v1/chat/stream {
    proxy_pass http://llm_gateway;
    proxy_http_version 1.1;
    proxy_set_header Connection "";

    proxy_buffering off;          # ← 核心：关掉响应缓冲
    proxy_cache off;              # 别缓存流式响应
    gzip off;                     # gzip 会攒数据，破坏流式

    proxy_read_timeout 300s;      # 长回答，默认 60s 会中途掐断
    proxy_send_timeout 300s;
    # 应用侧也可主动声明：add_header X-Accel-Buffering no;
}
```

**排查口诀**：客户端「卡一下再一次性出字」→ 查链路上所有中间层的 buffering；`curl -N` 直连服务端是流式、过 Nginx 不是 → 锁定代理层。

### 🎤 面试这样答：为什么你们 LLM 应用用 SSE 而不是 WebSocket？

> "因为 LLM 对话的通信模型天然是单向的——用户提问后就是服务端持续吐 token，中间用户不发数据，SSE 的服务端单向推送正好匹配，WebSocket 的全双工能力在这里是浪费。更关键的工程理由有三点：第一，SSE 就是纯 HTTP 响应，Content-Type 是 text/event-stream，网关、负载均衡、CDN、鉴权、监控全部复用现有 HTTP 体系，而 WebSocket 要走 Upgrade 握手，中间任何一环不配合就出问题；第二，浏览器 EventSource 原生支持断线自动重连，还能带 Last-Event-ID 做断点续传，我们服务端按会话 ID 记录已生成位置，弱网恢复体验很好；第三，HTTP/2 多路复用解决了浏览器连接数限制，SSE 的短板已经补齐。唯一要踩的坑是 Nginx 默认 proxy_buffering 会把 token 攒起来造成'假流式'，必须关缓冲、关 gzip、调大 read_timeout，我们上线前用 curl -N 全链路验证过。"（约 280 字）

**追问：**

1. **如果要做语音实时对话（边说边识别边回）呢？**
   答：那就是双向实时场景了——麦克风音频流上行 + 回复下行，这时候 WebSocket（或 WebRTC）才是对的。选型跟着通信模型走，不是跟潮流走。
2. **SSE 只能 GET 吗？对话要带很长的上下文怎么办？**
   答：标准 EventSource 只支持 GET，参数放 URL 有长度和安全问题。生产做法是 `fetch` + `ReadableStream` 自己解析 SSE 流（可以 POST），或者先 POST 拿 conversation_id 再 GET 订阅。
3. **假流式怎么快速定位是哪一层的问题？**
   答：分段验证：`curl -N` 直连应用是流式 → 问题在代理；直连也卡 → 查应用是不是攒完再返回。逐层看 proxy_buffering、gzip、以及应用框架的响应缓冲设置。
4. **HTTP/3 对你们的流式场景有帮助吗？**
   答：有帮助。QUIC 解决 TCP 队头阻塞，切换网络（WiFi→5G）时连接不断（连接迁移），对移动端弱网下的长流式连接是实打实的收益；但要先确认中间链路对 UDP 的支持度。

## 1.2 数据库（MySQL / PostgreSQL）

### 1.2.1 为什么是 B+Tree（对比 B 树 / 哈希 / 红黑树）

**是什么（通俗类比）：**

B+ 树是一本「多层目录」：非叶子节点是目录的目录，叶子节点才是真正挨着放数据的书页。查任何一条数据，走的都是同样浅的几层目录——对磁盘这种「翻一页很贵」的存储来说，**矮，就是快**。

**为什么（四个对比，面试标准打法）：**

| 结构 | 问题 | B+ 树怎么赢 |
|------|------|------------|
| 哈希表 | 等值查询 O(1) 很快，但**不支持范围查询、排序、最左前缀** | 叶子层有序 + 双向链表，`BETWEEN / ORDER BY / LIKE 'a%'` 全覆盖 |
| B 树 | 非叶子节点也存数据 → 单页放的键少 → 扇出小 → 树更高 | 非叶子只存键，扇出极大（一页几百个键），3~4 层撑千万级数据 |
| 红黑树/跳表 | 二叉结构太高瘦，千万数据约 23 层，每层一次磁盘 IO | 矮胖：树高 ≈ 磁盘 IO 次数，千万数据 3 层 ≈ 3 次 IO |
| 有序数组 | 范围扫描快，但插入要整体挪动 | 叶子链表插入只动局部 |

**结构图（白板能画）：**

```text
                  ┌──────────┐
                  │ 15 | 56  │  ← 非叶子节点：只存"路标"（键），不存数据
                  └────┬─────┘    → 单页可放几百个键 → 扇出大 → 树极矮
          ┌───────────┴─────────────┐
          ▼                         ▼
    ┌───────────┐             ┌───────────┐
    │ 15|20|49  │             │ 56|72|90  │
    └─┬──┬──┬───┘             └─┬──┬──┬───┘
      ▼  ▼  ▼  ◀═══ 叶子层双向链表 ═══▶  ▼  ▼  ▼
   [3~15][15~20][20~49]      [56~72][72~90][90~97]   ← 叶子：存整行（聚簇）
        ⇆        ⇆              ⇆        ⇆             或主键值（二级索引）
   范围查询：二分定位起点 → 沿链表顺序扫，不用回到树顶
```

**一句话总结**：B+ 树是为**磁盘 / SSD 按页读取**特性量身定做的结构——把「随机 IO 次数」压到最低，把「范围扫描」变成顺序读。

### 1.2.2 索引实战：聚簇 / 二级 / 联合 / 覆盖 / ICP

**核心概念链（按因果链记，别背散点）：**

```text
聚簇索引（主键 B+ 树，叶子 = 整行数据）
   │ 二级索引的叶子里放的是主键 → 查完还要拿主键回聚簇树再查一次 = "回表"
   ▼
二级索引（叶子 = 索引列 + 主键）
   │ 多列共建一棵树：整体按 (a,b,c) 排序 → a 定了才轮到 b → "最左匹配"
   ▼
联合索引 + 最左匹配
   │ 查询需要的列如果全在索引里 → 根本不用回表
   ▼
覆盖索引（select 的列全在索引里，EXPLAIN 显示 Using index）
   │ where 里的条件列如果在索引中，存储引擎层先过滤再回表，减少回表次数
   ▼
ICP（Index Condition Pushdown，索引条件下推，5.6+）
```

**高频细节：**

- **最左匹配的坑**：`(a,b,c)` 索引下，`where a=1 and c=3` 只用到 a；`where b=2` 完全用不上；**范围查询右侧列失效**（`a>1 and b=2` 只用到 a）
- **索引失效清单（能报出一串）**：列上用函数 / 运算、隐式类型转换（varchar 列用数字查）、前导模糊 `like '%xx'`、`or` 两侧有非索引列、不满足最左前缀
- **为什么推荐自增主键**：插入即追加，页写满开新页；随机主键（UUID）导致页分裂、碎片、写放大

### 1.2.3 事务、MVCC 与锁

**Redo / Undo / Binlog / WAL（先分清谁是谁）：**

| 日志 | 层面 | 作用 | 写法 |
|------|------|------|------|
| Redo Log | InnoDB 引擎层 | **崩溃恢复**：已提交事务不丢（crash-safe） | 循环写、固定大小 |
| Undo Log | InnoDB 引擎层 | **回滚** + MVCC 版本链 | 随事务产生 |
| Binlog | Server 层 | **主从复制、数据恢复** | 追加写 |
| WAL | 通用思想 | 先写日志再刷数据页——MySQL / PG / Kafka / ES 全是这个套路 | — |

**两阶段提交（redo 与 binlog 的一致性）：**

```text
update 执行流程：① 写 undo log（记旧值）
              ② 内存中修改数据页（脏页）
              ③ 写 redo log（prepare 状态）
              ④ 写 binlog
              ⑤ redo log 置为 commit
崩溃恢复规则：redo 处于 prepare → 检查 binlog 是否完整
   完整 → 提交；不完整 → 回滚（两份日志要么都算数，要么都不算）
```

**MVCC 是什么（通俗类比）：**

多人协作文档的「历史版本」——每个人读的是自己打开时刻的快照，别人后来的编辑不打扰你。实现靠 **undo log 版本链 + ReadView（可见性判断）**。

- **RC（读已提交）**：每条 select 都生成新 ReadView → 能看到别人最新提交 → 不可重复读
- **RR（可重复读，MySQL 默认）**：事务内第一条 select 生成 ReadView 并复用 → 整个事务看到同一快照
- PG 默认 RC；MySQL 默认 RR（历史原因：早期 statement 格式 binlog 要求主从语句重放顺序一致）

**四种隔离级别速查：**

| 隔离级别 | 脏读 | 不可重复读 | 幻读 | 实现要点 |
|---------|------|-----------|------|---------|
| Read Uncommitted | 有 | 有 | 有 | 基本不用 |
| Read Committed | 无 | 有 | 有 | 每次 select 新建 ReadView |
| Repeatable Read（MySQL 默认） | 无 | 无 | 基本无 | 复用 ReadView + **Next-Key Lock** 锁区间 |
| Serializable | 无 | 无 | 无 | 读也加锁，吞吐骤降 |

**锁家族一句话**：行锁（Record Lock）锁一行；间隙锁（Gap Lock）锁一个区间防插入；**Next-Key Lock = 行锁 + 间隙锁**，RR 级别下防幻读的主角。代价：不等值查询下锁范围可能放大，是**死锁高发区**——线上要开死锁日志、按固定顺序更新。

### 1.2.4 慢查询优化与分库分表

**慢查询排查固定流程：**

```text
① 慢日志定位 SQL（long_query_time）
② EXPLAIN 看四要素：type（至少 range，ALL 全表扫描要警惕）/ key / rows / Extra
③ 常见病：没索引或索引失效 → 回表太多（改覆盖索引）
   → filesort / temporary（排序分组没走索引）
④ 动刀顺序：改 SQL/索引 > 改表结构 > 读写分离 > 分库分表（最后才动）
```

**分库分表（什么时候、怎么做、代价）：**

- **垂直拆**：按业务拆库拆表（订单库 / 用户库）；**水平拆**：单表行数过大（经验值单表 2000 万内、单库 2TB 内先忍）
- **分片键选择**：用最高频的查询维度（订单用 user_id），避免广播查询
- **扩容**：range 分段好扩但冷热不均；hash 均匀但扩容要数据迁移（双写迁移 / 一致性哈希）
- **代价清单（必答）**：跨分片 join / 深分页难（业务层聚合或冗余宽表）、分布式 ID（雪花 Snowflake：时间戳+机器号+序列）、跨分片事务（→ 1.5.7 消息最终一致）

### 🎤 面试这样答：MVCC 到底解决什么问题？

> "MVCC 解决的是'读写互不阻塞'——让查询读快照、不排队等写锁，这是高并发下数据库吞吐的根基。实现依赖两个东西：undo log 版本链，每行改动都留旧版本；ReadView，事务的'可见性快照'，按事务 ID 和创建时间判断版本链上哪个版本对自己可见。RC 和 RR 的本质区别就在 ReadView 的生成时机：RC 每次 select 都新建，所以能看到别人新提交的数据，造成不可重复读；RR 在事务第一条查询时生成并一直复用，整个事务看到同一份快照。要注意 RR 的快照读防不住写入场景的幻读——当前读（for update）要靠 Next-Key Lock 锁区间。落到实践，我们排查过一类问题：长事务持有旧 ReadView 导致 undo 链膨胀、purge 滞后，表空间涨得飞快——所以监控里专门加了长事务告警。"（约 270 字）

**追问：**

1. **为什么 MySQL 默认 RR 而 PG 默认 RC？**
   答：历史原因——MySQL 早期 statement 格式 binlog 按语句重放，RC 下主从会出现不一致，RR + 间隙锁能保住语句执行环境一致；PG 用逻辑复制没有这个包袱，RC 并发度更好。
2. **事务提交了，数据落盘了吗？**
   答：没有。提交只保证 redo log 落盘（WAL），数据页还是脏页，由后台线程异步刷。崩溃后靠 redo 前滚恢复——这就是 crash-safe 的含义。
3. **update 没走索引会怎样？**
   答：扫全表时对所有行加行锁，效果近似锁表；RR 下还会放大间隙锁范围，极易死锁。线上大表 update 必须先确认索引。
4. **为什么覆盖索引能提速？**
   答：二级索引查到主键后回聚簇树是随机 IO；覆盖索引让查询在二级索引里就地解决，避免回表——高频查询建议按「覆盖索引」设计联合索引的列。

## 1.3 Redis

### 1.3.1 数据结构选型

| 结构 | 典型场景 | 一句话理由 |
|------|---------|-----------|
| String | 缓存 JSON、计数器（INCR） | 原子自增，做配额 / 限流的地基 |
| Hash | 对象字段级读写 | 改一个字段不用整存整取 |
| List | 简单队列、最新动态 | 双端操作；但做 MQ 不专业（无 ack） |
| Set | 去重、标签、共同关注 | 交并差集合运算 |
| ZSet | 排行榜、延迟队列 | 按 score 排序，跳表实现 |
| Bitmap | 签到、活跃标记 | 1 亿用户约 12MB |
| HyperLogLog | UV 统计 | 0.81% 误差换 12KB 空间 |
| Stream | 消息队列（ack、消费组） | List 队列的专业版 |

**追问级细节**：ZSet 底层是**跳表 + 哈希表**（跳表管排序和范围、哈希管 O(1) 查成员分值）；dict 扩容用**渐进式 rehash**（避免一次性迁移阻塞单线程）；大 key 扫描时留意迁移中的双写。

### 1.3.2 缓存三件套：穿透 / 击穿 / 雪崩

**是什么（一张图分清三种病）：**

```text
                    请求洪流
                       │
              ┌────────▼────────┐
              │      Redis      │
              └────┬───────┬────┘
             命中→返回  │       │ 未命中
                       │       ▼
                       │   ┌────────────────────────────────────┐
                       │   │ 病因不同，药方完全不同：             │
                       │   │ ① 穿透：查的数据根本不存在           │
                       │   │    （恶意 id / 脏请求直通 DB）       │
                       │   │ ② 击穿：某个热点 key 过期的一瞬间    │
                       │   │    （百万 QPS 同时打向 DB）          │
                       │   │ ③ 雪崩：大批 key 同时过期            │
                       │   │    或 Redis 整个宕机               │
                       │   └────────────────────────────────────┘
                       ▼
```

**工程解法对照表（背熟）：**

| 问题 | 解法 | 细节 |
|------|------|------|
| 穿透 | ① 缓存空值 | TTL 设短（30s~60s），防恶意 key 撑爆缓存 |
| | ② 布隆过滤器 | 「说没有就一定没有」，适合 key 集合稳定；误判率与空间权衡 |
| | ③ 入口校验 | id 格式 / 合法性先挡一层 |
| 击穿 | ① 互斥锁重建 | SETNX 抢到的人查库回填，其他人自旋或返回旧值 |
| | ② 逻辑过期 | 不设 TTL，value 里带过期时间，发现过期异步刷新、先返回旧值 |
| | ③ 热点永不过期 | 确定性热点 + 后台定时刷新 |
| 雪崩 | ① TTL 加随机抖动 | `ttl + random(0,300)`，错峰过期 |
| | ② 高可用集群 | 哨兵 / Cluster 防单点 |
| | ③ 多级缓存 + 限流降级 | 本地缓存挡一层；DB 前挂限流，宁可慢不能死 |

### 1.3.3 热 Key 与大 Key

- **热 Key 发现**：客户端采样统计 / `redis-cli --hotkeys` / monitor（生产慎用）；**解法**：本地缓存（Caffeine / 本地 LRU）挡读、key 拆多副本随机路由（`key_1..key_n`）
- **大 Key 发现**：`--bigkeys`、RDB 离线分析；**警惕线**：String > 10KB、集合元素 > 5000
- **大 Key 危害**：慢查询阻塞单线程、网卡打满、集群数据倾斜、迁移卡死
- **解法**：Hash 分桶拆分（大 JSON 按字段拆）、压缩、删除用 `UNLINK`（异步）别用 `DEL`（同步阻塞）

### 1.3.4 分布式锁：SETNX → RedLock 争议

**演进链（按这个顺序讲，体现工程成熟度）：**

```text
v1  SETNX key value              → 持锁者挂了没人删 → 死锁
v2  SETNX + EXPIRE（两条命令）    → 非原子，中间崩了照样死锁
v3  SET key value NX EX 10        → 原子了，但会误删别人的锁
    （业务跑了 15s，锁 10s 已过期，B 拿到锁，A 回来把 B 的锁删了）
v4  唯一 value（UUID）+ Lua「比对再删」→ 解决误删
v5  看门狗续期（Redisson）        → 业务没跑完自动续，宕机/跑完停止续
v6  RedLock（多个独立实例多数派）  → 理论更强，但争议巨大
```

**RedLock 争议（能讲出双方观点是加分项）：**

- **主张**：单实例锁会因主从切换丢锁；向 N 个独立节点加锁、多数成功才算持有，更稳
- **反方（Martin Kleppmann）**：依赖各节点时钟稳定——**GC 停顿 / 时钟跳变后，锁可能已被别人持有而你浑然不觉**；它提供的是「效率」保证而非「正确性」保证
- **工程结论（面试就这么答）**：绝大多数场景「单实例 + 看门狗 + 唯一 value」足够（锁只是防重复劳动）；**正确性要求极高（钱）的场景别用 Redis 锁**，用数据库乐观锁 / 唯一约束，或 etcd / ZK 基于共识的锁

### 1.3.5 缓存一致性（Cache Aside 正确姿势）

- **标准模式**：读——先缓存后库，miss 则回填；写——**先更新 DB，再删缓存**
- **为什么是「删」不是「改」**：并发写时改缓存容易把旧值写回；删除让下次读触发回源，天然收敛
- **为什么不能「先删缓存再更新 DB」**：删完到更新完成的窗口里，读请求把**旧值**回填进缓存，脏数据长期驻留 → 补救：**延迟双删**（更新后 sleep 几百 ms 再删一次）
- **更强的方案**：订阅 binlog（Canal）异步删缓存——业务代码零侵入、不丢事件，代价是多一条链路
- **底线认知**：Cache Aside 是**最终一致**；要强一致就别上缓存，或读写穿透（Read/Write Through）+ 分布式锁，性能代价自负

### 🎤 面试这样答：100 万用户同时请求同一个热点数据，怎么保护 Redis 和 MySQL？

> "这是典型的热 key + 击穿复合场景，我会分三层防御。第一层，热 key 前置：应用本地缓存一份短 TTL（比如 1~5 秒）的副本，100 万 QPS 里 99% 在本地内存就消化了，根本不出发。第二层，防击穿：这个 key 不设自然过期，改为逻辑过期——value 里带刷新时间，后台线程定时或发现过期后异步重建，重建期间读请求拿旧值先应答，DB 永远只被一个线程打。第三层，兜底：DB 前挂限流（令牌桶），MySQL 侧该查走覆盖索引，宁可部分请求变慢也不能把库打挂。如果热点不可预知，就上热 key 探测（客户端采样统计），发现后动态推本地缓存。最后用回放真实流量压测验证本地缓存命中率和 DB QPS 降幅，这套组合拳下来 DB 压力一般能降两个数量级。"（约 270 字）

**追问：**

1. **本地缓存和 Redis 数据不一致怎么办？**
   答：接受短暂不一致——本地 TTL 就是误差上限；变更频繁且一致性敏感的数据不上本地缓存，或走 pub/sub 广播失效。
2. **布隆过滤器为什么能防穿透？数据删了怎么办？**
   答：它「说不存在就真不存在」，把必然 miss 的 key 挡在缓存外；但标准布隆不支持删除，要用计数布隆或定期重建。
3. **互斥锁重建击穿方案，抢不到锁的请求怎么办？**
   答：短暂自旋等待（几 ms 到几十 ms）后拿刚回填的新值；等不到返回降级内容或旧值，不能把等待堆积成超时雪崩。
4. **看门狗续期，进程假死怎么办？**
   答：看门狗线程也死了就不续，锁自然过期释放——看门狗只解决「业务慢」，不解决「进程挂」，进程挂靠过期时间兜底。

## 1.4 消息队列

### 1.4.1 Kafka 为什么高吞吐

**五个关键词（每个都能展开一句）：**

```text
① 顺序写磁盘 + 页缓存     → 顺序写 SSD 上百 MB/s；数据先落 page cache，读也命中缓存
② 零拷贝（sendfile）      → 磁盘→网卡不经过用户态，省 2 次拷贝 + 2 次上下文切换
③ 批量 + 压缩            → producer 攒一批（按大小/时间触发）压缩后发送
④ 分区并行               → 吞吐 = 单分区 × 分区数，水平扩展无上限
⑤ 批量拉取 + 稀疏索引     → 消费顺序读；offset 索引 + 位置索引快速定位
```

**副本机制（ISR）图（白板能画）：**

```text
            Topic: doc-events（3 分区 · 3 副本 · 生产者只写 Leader）
   Partition-0         Partition-1         Partition-2
 ┌────────────┐      ┌────────────┐      ┌────────────┐
 │ Leader     │      │ Leader     │      │ Leader     │
 │ (Broker-1) │      │ (Broker-2) │      │ (Broker-3) │
 └─────▲──────┘      └─────▲──────┘      └─────▲──────┘
       │ 拉取同步           │ 拉取同步          │ 拉取同步
 ┌─────┴──────┐      ┌─────┴──────┐      ┌─────┴──────┐
 │ Follower   │      │ Follower   │      │ Follower   │
 │  (ISR 内)  │      │  (ISR 内)  │      │  (ISR 内)  │
 └────────────┘      └────────────┘      └────────────┘
 ISR = 跟得上 Leader 的副本集合；落后太多被踢出
 Leader 宕机 → 从 ISR 中选新 Leader；acks=all = 等 ISR 全部落盘才应答
```

### 1.4.2 投递语义：为什么 Exactly Once 工程上难

| 语义 | 含义 | 风险 | 实现方式 |
|------|------|------|---------|
| At Most Once | 最多一次 | **可能丢**（先提交 offset 再处理，处理前挂了） | 发送不重试 / 消费先提交 |
| At Least Once | 至少一次 | **可能重**（先处理再提交 offset，提交前挂了，重启再消费一遍） | acks=all + 重试 + 手动提交 |
| Exactly Once | 恰好一次 | 理想态 | 幂等生产者 + 事务（跨分区原子写 + 消费-处理-提交绑定） |

**为什么难（标准答法）：**

一次投递横跨**三个环节**：生产者→Broker（重试就可能重，不重试就可能丢）、Broker 持久化与副本切换、消费者处理与 offset 提交（处理了没提交，重启就重消费）。Kafka 内部可以用「幂等生产者（broker 去重）+ 事务（消费-处理-提交绑定成原子操作）」做到 **Kafka 链路内**的 Exactly Once；但只要**副作用越过 Kafka**——写了 MySQL、调了第三方 API、调了一次 LLM——事务就罩不住了：LLM 调用烧掉的钱，不会因为你回滚 offset 而退回来。

> **工程共识：At Least Once + 消费端幂等 = 事实上的 Exactly Once。** 别指望链路本身，把去重放在消费端。

### 1.4.3 消息不丢 / 不重 / 不积压 + 死信队列

**不丢（三段各自设防）：**

```text
生产端：acks=all + retries 调大 + 幂等 producer（enable.idempotence）
Broker：副本数 ≥3 + min.insync.replicas ≥2（acks=all 才有意义）
消费端：先处理成功，再手动提交 offset
        （自动提交 = 「处理一半就提交」的丢消息之源）
```

**不重 = 消费端幂等（四种武器）：**

1. 唯一业务键 + 数据库唯一索引（重复插入直接冲突丢弃）
2. 去重表 / Redis SETNX 记录已处理 message_id（带 TTL）
3. 状态机校验（订单已是「已支付」，再收到支付消息直接 ack 跳过）
4. 乐观锁版本号（`update ... where version=n`）

**不积压（发现→处理）：**

- 发现：消费 lag 告警（consumer group 的消费延迟是 MQ 核心监控指标）
- 处理：**扩消费者**（上限 = 分区数，超了没用 → 先扩分区）、批量消费、可丢弃的堆积直接跳过或转储（日志类）、紧急走「堆积转存 + 离线补处理」

**顺序消息**：Kafka 只保证**分区内有序**——把要保序的消息用同一个 key（同一订单 id、同一文档 id）路由到同一分区。

**死信队列（DLQ）**：消费重试 N 次（如 3 次，指数退避）仍失败 → 转入 DLQ → 告警 + 人工介入 / 定时补偿。**价值：毒丸消息不阻塞主流程**——一条格式错误的消息永远重试失败，没有 DLQ 就会卡死整个分区的消费。

### 🎤 面试这样答：设计一条文档向量化入库流水线

> "场景是用户上传文档后要解析、切块、向量化、入库，整条链路几秒到几分钟，必须异步化。我的设计：上传接口只做接收、落对象存储，随即发一条 MQ 消息（带文件指纹做幂等键）就返回，用户侧轮询或 SSE 收进度。消费侧按阶段拆消费者：解析（PDF/OCR）→ 切块 → 调 embedding 模型批量向量化 → 写向量库和元数据库 → 质量校验、更新状态。选 Kafka 类 MQ 的理由：削峰（批量上传不打爆 embedding 配额）、失败重试、消费位置可追溯回放。三个工程要点：第一，embedding API 有 RPM/TPM 限制，消费端要按 token 预算限速、攒批量请求，失败指数退避；第二，幂等靠文件指纹 + 去重表，重复消息直接跳过，避免重复入库；第三，重试三次仍失败进死信队列，告警人工处理，状态机把文档标为失败、可手动重跑。积压靠消费 lag 监控，扩消费者上限受分区数约束，容量规划时预留分区余量。"（约 290 字）

**追问：**

1. **向量化入库和元数据写库是两个系统，一致性怎么办？**
   答：本地消息表 / outbox 思路：元数据状态先行（PENDING），向量入库成功后回调改 DONE，定时任务扫描超时 PENDING 的做补偿重试或标记失败——最终一致。
2. **文档更新了怎么办？**
   答：文件指纹（hash）判重，内容变了走增量：新版本切块入库后原子切换版本指针，再异步删除旧版本向量——检索永远只看到有效版本。
3. **为什么不用 Redis List / Stream 直接当队列？**
   答：小规模可以，但这个场景要持久化、重试、死信、消费者组横向扩展、回溯重放——这些是 Kafka 类 MQ 的主场；Redis Stream 的持久化与运维成熟度弱一档。
4. **如果 embedding 服务整体挂了怎么办？**
   答：消费端熔断暂停拉取——消息留在 MQ 里本身就是最好的缓冲，恢复后从 offset 继续；长时间故障则降级排队 + 上游限流上传入口，保护整体可用性。

### 🔗 AI 场景映射（1.4）

- **文档向量化入库流水线**：上面这道题本身——AI 数据工程的标准异步化范式（切块与元数据细节在 L4 展开）
- **Agent 异步任务编排**：长任务（深度研究、批量报告）走「提交-回调」：任务队列 + 状态机 + 完成通知（SSE/推送）；同步 HTTP 里跑几分钟的 LLM 任务是反模式
- **事件驱动 Multi-Agent**：Agent 间协作用消息解耦（上游 Agent 产出事件、下游订阅），天然支持重试与多订阅者
- **Token 消耗事件流**：每次调用发 token 用量事件到 MQ → 下游聚合计费 / 配额 / 成本报表——计费与主链路解耦

## 1.5 并发与分布式

### 1.5.1 进程 / 线程 / 协程

| 概念 | 是什么 | 切换成本 | 典型 |
|------|--------|---------|------|
| 进程 | 资源分配的基本单位 | 最高（地址空间、页表全套） | 容器隔离、多服务部署 |
| 线程 | CPU 调度的基本单位 | 中（上下文 + 内核态切换） | Java 线程池 |
| 协程 | 用户态轻量执行流 | 极低（寄存器级，不进内核） | Go goroutine / Python asyncio |

- **Go GMP**：G（goroutine）M（内核线程）P（调度上下文）；goroutine 阻塞在系统调用时，P 会带着运行队列挂到另一个 M 上——**几十万协程是常态**
- **Python asyncio**：单线程事件循环，**await 是协作式让出**——一个 CPU 密集任务不让出就卡死全场（与 Go 抢占式调度最大的差别），所以 Python 里 CPU 密集要丢进程池
- **三个 ≠**：**并发 ≠ 并行**（逻辑任务数 vs 物理核同时执行）；**异步 ≠ 多线程**（事件循环 vs 线程池，前者适合 IO 密集）；**协程 ≠ 线程**（用户态 vs 内核态）

### 1.5.2 I/O 多路复用：select / poll / epoll

**是什么（通俗类比）**：一个服务员看着整排餐桌，谁举手就服务谁——而不是每桌配一个服务员干等。

| 机制 | 原理 | 瓶颈 |
|------|------|------|
| select | 每次把 fd 集合拷进内核，线性扫描 | 上限 1024，O(n) |
| poll | 链表存 fd，仍线性扫描 | 无硬上限，O(n) |
| epoll | 内核红黑树注册 fd + 就绪链表回调 | O(1) 取就绪，支撑百万连接 |

**为什么重要**：Redis、Nginx、Netty、asyncio、推理框架的请求调度——所有「少线程扛海量连接」的系统底层都是它。一句金句：**IO 密集型系统的瓶颈通常不是计算，而是「等」——多路复用 + 事件驱动，把「等」的时间拿去服务别人。**

### 1.5.3 限流：四种算法

| 算法 | 原理 | 优点 | 缺点 |
|------|------|------|------|
| 固定窗口计数 | 每分钟一个计数器，超了拒绝 | 最简单 | **临界突刺**：59s 和 61s 各打满额度，2 秒内双倍流量 |
| 滑动窗口 | 细分小格滚动统计 | 抹平临界问题 | 实现稍复杂，精度与格子数权衡 |
| 漏桶 | 恒定速率流出 | 绝对平滑，保护脆弱下游 | 无法应对合理突发 |
| 令牌桶 | 恒速发令牌，桶可囤积 | **允许突发**（囤的令牌一次用掉） | 参数需调优 |

- 分布式限流：计数放 Redis + **Lua 保证原子性**（读-判断-扣减三步不能拆开）
- 生产常见双层限流：本地令牌桶先挡一层 + 集群 Redis 精确一层（本地挡量、集群保准）

### 1.5.4 熔断与降级

```text
              失败率超阈值（如 10s 内 50%）
   ┌──────────┐ ─────────────────────▶ ┌──────────┐
   │  Closed  │                        │   Open   │
   │ 正常放行  │ ◀──── 探测成功 ────── │ 快速失败  │
   └──────────┘                       └────┬─────┘
        ▲                                  │ 冷却期（如 30s）到
        │            ┌─────────────────────┘
        └────────────┤        ▼
                 ┌───────────┐
                 │ Half-Open │  放少量真实请求探测：
                 └───────────┘  恢复则闭合，仍失败则继续 Open
```

- **熔断**是自动的（指标驱动）；**降级**是预案（有损服务：返回缓存 / 默认值 / 简化逻辑）；**隔离（Bulkhead）**是止损（线程池 / 信号量按下游分组，一处故障不拖垮全局）
- 黄金法则：**超时必须层层设置且上游 < 下游总和**；重试要有上限 + 指数退避 + 抖动——**重试风暴比故障本身更致命**

### 1.5.5 CAP / BASE

- **CAP**：网络分区（P）必然发生，只能在 C（线性一致）与 A（可用）之间二选一——不是「三选二」的选择题，而是 **P 发生时的应对策略**
- 例：ZK / etcd 偏 CP（分区时少数派不可用）；Eureka 偏 AP（注册中心宁可返回陈旧地址）
- **BASE**：基本可用 + 软状态 + 最终一致——大规模互联网系统的现实主义宣言；**跨库 / 跨服务场景默认放弃强一致，用补偿和对账收敛**

### 1.5.6 幂等设计（高频实战题）

**是什么**：同一操作执行一次和执行 N 次，结果相同。重试是分布式系统的生存方式，幂等是重试的安全前提。

**四种实现（按成本从低到高记）：**

```text
① 天然幂等：select、delete by id、set x=v（覆盖写）
② 唯一约束：业务唯一键 + DB 唯一索引，重复插入直接冲突
③ 去重表 / Redis：request_id 先 SETNX，已存在直接返回上次的结果
④ 状态机 + 乐观锁：update orders set status='PAID'
                      where id=? and status='UNPAID'
   —— 影响行数 = 0 说明已处理过（LLM 工具重试防重复扣款的标准解法）
```

**支付 API 幂等示范（经典题）**：客户端生成 `Idempotency-Key`（UUID），服务端用它做唯一键——第一次请求处理并**存下响应结果**；重试带同一 key 直接返回存储的结果，而不是再执行一遍。顺带说清：**POST 不幂等、PUT 幂等（同值覆盖）**，所以支付这类敏感 POST 必须显式做幂等键。

### 1.5.7 分布式事务：Saga / TCC（概念级即可）

| 方案 | 一致性 | 侵入性 | 适用 |
|------|--------|--------|------|
| 2PC / XA | 强 | 低（数据库层） | 同步短事务；协调者单点 + 阻塞，互联网少用 |
| TCC | 最终 | 高（每方实现 Try/Confirm/Cancel 三接口） | 资金类核心链路 |
| Saga | 最终 | 中（长流程拆本地事务 + **补偿**） | 跨服务长流程（下单→扣库存→发券→通知） |
| 本地消息表 / 事务消息（RocketMQ 半消息） | 最终 | 低 | 「主库成功必须发消息」的最常用解 |
| 最大努力通知 | 弱 | 低 | 跨企业通知（支付回调重试） |

**TCC vs Saga 一句话**：TCC 是「先冻结再确认」（Try 预留资源、Confirm 提交、Cancel 释放——把两阶段做在业务层）；Saga 是「一路做下去，错了逐个补偿」（没有冻结，补偿逻辑要处理已生效的副作用）。

### 🎤 面试这样答：LLM 网关的限流和降级怎么做？

> "LLM 网关和传统网关最大的差别是限流维度：传统按 QPS，LLM 必须按 RPM 加 TPM 双维度——一次 10 万 token 的深度推理请求和一个 50 token 的补全，资源占用差三个数量级。实现上用 Redis + Lua 的令牌桶变体：请求前先估 token（按字符数近似），先扣 RPM 再扣 TPM 配额，不足则排队或拒绝。降级是级联的：主模型超时或错误率超阈值触发熔断，切备用模型——注意保持上下文兼容，messages 格式是通用事实标准，切换对用户无感；备用也不行就走小模型或规则兜底，简单任务用小模型质量差距很小。另外推理是长耗时任务，网关要做排队 + 优先级调度：VIP 请求插队、低优先级 batch 化、超时请求主动丢弃防止占着连接。熔断指标除了错误率还要盯 TTFT——TTFT 恶化往往是供应商过载的前兆，比错误率更早亮红灯。"（约 290 字）

**追问：**

1. **为什么用令牌桶不用漏桶？**
   答：对话流量天然突发（早上集中提问），漏桶强行平滑会把合理突发排成长队；令牌桶允许囤积令牌吸收突发，保护后端同时不牺牲体感。
2. **token 数没法提前精确知道，怎么限流？**
   答：输入侧按字符数近似可估，输出侧按 max_tokens 预扣、完成后按实际用量对账回补——先粗后细，宁可小幅超卖再对账。
3. **模型切换时上下文怎么保持一致？**
   答：messages 数组是事实标准，网关只透传；但各模型 system 角色遵从度、工具调用 schema 兼容性有差异，切模型前后要过回归测试集。
4. **排队怎么设计用户体验？**
   答：返回排队位置和预估时间，SSE 先推一条「排队中」事件保持连接；超时给明确失败而不是无限等待，附重试建议。

### 🔗 AI 场景映射（1.5）

- **Token 维度限流**：RPM + TPM 双桶、预扣 + 对账——传统限流算法换了个计量单位
- **推理请求队列**：LLM 是计算密集 + 长耗时，QPS 思维完全失灵；优先级调度（付费用户优先）、batch 聚合、超时丢弃是推理侧队列三件套
- **模型网关熔断降级**：熔断对象从「下游服务」变成「模型供应商」；级联降级 大模型→小模型→规则/缓存；还多了新指标维度（TTFT、幻觉率）
- **幂等**：Agent 的工具重试（LLM 可能重复发起扣款调用）——Stripe 式 Idempotency-Key 直接平移过来
- **协程 / 异步**：AI 应用的 IO 密集特征（等 LLM 响应、等检索、等工具）天然适合 asyncio / goroutine；一个 Agent 服务并发几百个会话靠的就是事件循环

## 1.6 系统设计思维框架：八维度

**是什么**：所有设计题（含 AI 设计题）用固定顺序展开，保证不漏关键权衡：

```text
① 数据量 ──▶ ② 并发量 ──▶ ③ 延迟 ──▶ ④ 一致性
                                            │
⑧ 可观测 ◀── ⑦ 成本 ◀── ⑥ 容灾 ◀── ⑤ 可用性
```

**每个维度的传统形态 vs AI 形态（这张表是全场面试的万能钥匙）：**

| 维度 | 传统系统问什么 | AI 系统问什么 |
|------|--------------|--------------|
| ① 数据量 | 表行数、存储 TB | 文档数、向量数、日增会话量、**语料质量** |
| ② 并发量 | QPS、连接数 | RPM / TPM、**并发推理路数**、GPU 利用率 |
| ③ 延迟 | P99 接口耗时 | **TTFT**、tokens/s、检索延迟、rerank 延迟 |
| ④ 一致性 | 主从延迟、跨库事务 | 向量库与源库同步、**模型/Prompt 版本一致性** |
| ⑤ 可用性 | 99.9%、多活 | **多模型供应商容灾**、降级链路完整性 |
| ⑥ 容灾 | 备份、演练 | 供应商限流 / 停服预案、回滚（模型 + Prompt 双维度） |
| ⑦ 成本 | 服务器、带宽 | **Token 成本**、embedding / rerack 调用费、自建 vs API |
| ⑧ 可观测 | Trace / 日志 / 指标 | + Token 用量、**幻觉率抽检**、Prompt 版本追踪 |

**用法示范（30 秒破题）**：拿到「设计企业知识库问答」，先反问澄清：多少文档（①）、多少用户什么并发（②）、能接受多快的首字（③）——容量和架构完全不同：10 万文档 pgvector 单机就够，1000 万就要 Milvus 集群 + 分层检索。**先问规模再画图，是 Senior 的肌肉记忆。**

---

### 🎤 面试这样答：为什么你强调先澄清规模再设计？

> "因为架构方案没有绝对对错，只有和规模是否匹配。10 万文档的知识库，pgvector 加好元数据索引和权限过滤，单实例就能跑得很好，硬上 Milvus 分布式集群是给自己找运维麻烦；但 1000 万文档、日增十万、多租户，就要考虑分区、冷热分层、读写分离和检索分层。所以我习惯先澄清八个维度：数据量、并发量、延迟要求、一致性要求、可用性目标、容灾预案、成本约束、可观测性——AI 系统里这套维度还要换算：QPS 变成 RPM 和 TPM，延迟变成 TTFT，成本里多了一项按 token 计费的推理开销，一致性多了向量库和源库的同步问题。澄清完这些，方案自然浮出来，而且是带容量计算和 trade-off 的方案，不是抄一张通用架构图。这也让面试官看到我在用生产思维做设计，而不是画盒子。"（约 270 字）

**追问：**

1. **面试官不给你澄清机会，直接要方案怎么办？**
   答：自己分段假设——「假设 10 万文档、百级并发，我会这么设计；如果放大到千万级，这三处要换」——用假设链展示思维，而不是干等输入。
2. **八个维度里 AI 系统最容易漏的是哪个？**
   答：成本和效果可观测。传统系统服务器成本相对固定，AI 系统 token 成本和流量线性相关且贵；另外幻觉率抽检这类「效果监控」是 AI 特有维度，多数候选人只画数据流不讲这个。

### 🔗 AI 场景映射（1.6）

本节本身就是映射框架——八维度表就是「传统→AI」的换算器。三个直接应用：

- **答任何 AI 设计题的骨架**：企业知识库 / 智能客服 / Agent 平台（L9 的四类压轴题），开场全部用八维度澄清，答完用八维度收尾自查是否漏项
- **容量评估换算**：QPS → RPM/TPM（一次对话 ≈ 数千 token，10 倍流量 = 10 倍推理成本，线性无折扣——与传统服务「加机器就摊薄」的成本模型完全不同）

### A. 二层追问链：面试官连环深挖

阅读方式：每条链都是真实面试的追问节奏。**第一层答对只是入场券，第二层答稳才有信任，第三层带数字才有区分度。**

#### A.1 B+ 树与主键策略（对应 1.2）

**第一层追问：为什么自增主键插入比随机主键快？**

> **答：** InnoDB 是聚簇索引，数据按主键顺序物理组织。自增主键永远追加到最右叶子页——顺序写、页写满才分裂，且分裂是「右伸」型（新页拿走一半空间，原页记录不搬移），缓存友好、磁盘顺序 IO。随机主键要插进已有页的中间，触发页分裂 + 页内记录搬移 + 碎片化，写放大明显。

**追问：那什么时候反而该用「不单调递增」的主键？**

> **答：** 分布式写入防热点。自增主键意味着所有写入集中在 B+ 树最右侧叶子页——单机感知不明显，但在分布式数据库（TiDB 等）里，尾部页就是写入热点，所以 TiDB 提供 `SHARD_ROW_ID_BITS` 把行 ID 打散。同理，分库分表时用「趋势递增但不集中于单库」的雪花 ID，而不是每库各自自增（否则全局 ID 冲突）。

**再追问：UUID 直接做主键，代价能量化吗？**

> **答：** 三个数字：
> 1. **空间**：UUID v4 存 VARCHAR(36) 是 36 字节，BIGINT 是 8 字节——大 4 倍多；且 InnoDB 每个二级索引叶子都冗余一份主键，全库索引膨胀 2~3 倍
> 2. **页分裂**：随机插入的页分裂与页内搬移频率远高于顺序插入，buffer pool 命中率下降、IO 放大
> 3. **比较成本**：字符串比较发生在树查找每一层，比整型慢
>
> 共识：主键用趋势递增的 BIGINT 或雪花 ID；UUID/ULID 留给需要全局唯一但不做聚簇主键的业务字段。

#### A.2 MVCC 与长事务（对应 1.2）

**第一层追问：ReadView 到底什么时候生成？**

> **答：** 不是 BEGIN 时，而是事务里**第一条快照读执行时**生成。它记录四要素：m_ids（当时活跃事务 ID 集合）、min_trx_id（m_ids 最小值）、next_trx_id（下一个将分配的事务 ID）、creator_trx_id（自己）。

**追问：RC 和 RR 差异的真正原因？**

> **答：** 一句话：**ReadView 生成时机不同**。RC 每条快照读都重新生成（所以能看到别人新提交的数据 → 不可重复读）；RR 只在第一条快照读生成并全程复用（整个事务一个快照 → 可重复读）。差异不在锁，在快照新旧。

```text
ReadView 可见性判断（沿 undo 版本链从新到旧回溯）：

  版本链（undo log）                当前 ReadView：m_ids=[100,200]  next=300
  ┌─────────────┐
  │ row 当前值   │ trx_id=200 → 200 ∈ m_ids？是（还活跃）→ 不可见，回溯 ↓
  └──────┬──────┘
  ┌──────▼──────┐
  │ undo 版本1   │ trx_id=150 → 150 ∈ m_ids？是（快照时活跃）→ 不可见，回溯 ↓
  └──────┬──────┘
  ┌──────▼──────┐
  │ undo 版本2   │ trx_id=50  → 50 < min(m_ids)=100（快照前已提交）→ ✅ 可见
  └─────────────┘
  规则速记：== creator（自己改的）→ 可见 | >= next（快照后开的）→ 不可见
            ∈ m_ids（快照时活跃）→ 不可见 | 其余（快照前已提交）→ 可见
```

**再追问：长事务为什么危险？**

> **答：** 三个放大效应：
> 1. **Undo 链膨胀**：RR 的 ReadView 全程有效 → 比它新的所有 undo 版本都不能清除，版本链越拖越长，undo 表空间膨胀、快照回溯变慢
> 2. **锁窗口放大**：行锁/间隙锁持有到提交，长事务 = 长锁窗口，并发 update 同范围必然锁等待、死锁
> 3. **主从延迟放大**：大事务 binlog 到从库要单事务连续回放，秒级大事务能造分钟级延迟
>
> 治理：`information_schema.innodb_trx` 里盯 `trx_started`，超 60s 告警；代码红线——事务内禁止调外部 RPC / 发消息。

#### A.3 Redis 渐进式 rehash 与大 key 删除（对应 1.3）

**第一层追问：渐进式 rehash 期间，两个字典怎么读写？**

> **答：** dict 里 ht[0]（旧表）和 ht[1]（新表）并存。rehash 期间的规则：
> - **新增**：只写 ht[1]，保证旧表只减不增
> - **查 / 改 / 删**：先查 ht[0]，没命中再查 ht[1]
> - **渐进推进**：每次增删改查顺手把 ht[0] 中 rehashidx 指向的一个桶搬到 ht[1]，另有定时任务兜底搬运；搬完释放旧表
>
> 为什么渐进：一次性 rehash 百万级 key 是 O(n) 阻塞操作，单线程的 Redis 会卡死；渐进把成本摊进每次操作。

**追问：rehash 有什么隐性代价？**

> **答：** rehash 期间两张表并存 → **哈希表内存瞬时接近双倍**；每次读写多一次表判断。所以大内存实例的 `maxmemory` 必须给 rehash 留余量，否则扩容中途触发淘汰甚至 OOM——这也是「数据量贴着内存上限跑」的 Redis 最脆弱的时刻。

**再追问：大 key 删除为什么阻塞？UNLINK 怎么解决的？**

> **答：** `DEL` 是同步释放：一个 100 万元素的 hash 要逐元素 free，单线程里就是几百 ms 到秒级卡顿，期间所有请求排队。`UNLINK` 把两步拆开——「引用摘除」O(1) 立刻返回，「内存释放」交给后台 lazyfree 线程异步做。配套还有 `lazyfree-lazy-expire` / `lazyfree-lazy-eviction` 开关把过期删除和内存淘汰也异步化。注意：判断「能否异步」本身要检查对象引用，小对象异步反而更慢，Redis 内部有个阈值（默认 64）以下仍然同步删。

#### A.4 Kafka ISR 与消息丢失（对应 1.4）

**第一层追问：ISR 是什么？和副本数什么关系？**

> **答：** ISR = In-Sync Replicas，与 leader 保持同步的副本集合（含 leader）。同步的判据不是绝对一致，而是 `replica.lag.time.max.ms`（默认 10s，旧版 30s）内有 fetch 跟上；落后超时被踢出，追上再拉回。**acks=all 只要求 ISR 内副本确认，而 ISR 可能收缩到只剩 leader**——所以 acks=all ≠ 绝对不丢，必须配 `min.insync.replicas=2` 才有约束力（ISR 不足时写入直接报错而不是降级成功）。

**追问：LEO 和 HW 是怎么同步推进的？**

> **答：** LEO = 每个副本日志的下一条 offset；HW（高水位）= 消费者可见边界 = min(所有 ISR 副本的 LEO)。follower 发 Fetch 时上报自己的 LEO，leader 更新「远端副本 LEO」并算出新 HW，随 Fetch 响应发回给 follower。

```text
LEO/HW 推进图（leader LEO=6）：

   leader:    [0][1][2][3][4][5]  LEO=6
                                ▲
                Fetch(LEO=4) ───┤ 更新 remoteA=4
   followerA: [0][1][2][3]   LEO=4
   followerB: [0][1][2]      LEO=3   Fetch(LEO=3) → 更新 remoteB=3

   HW = min(leader 6, remoteA 4, remoteB 3) = 3
        └─ 消费者只能读 offset ≤ HW-1（0~2 可见；3~5 已写入但不可见）

   followerB 追平后 remoteB=6 → HW = min(6,6,4) = 4 → 逐步推进到 6
   （HW 推进有一轮 Fetch 往返延迟，这就是「消费可见性滞后」的来源）

   丢消息点：acks=1 时 leader 在 HW 推进前宕机、消息未同步 → 新 leader
   上任后旧消息被截断，生产端却已收到 ack —— 消息真丢。
```

**再追问：丢消息的经典错误配置组合是什么？**

> **答：** 三段叠加的经典事故组合：**生产端 `acks=1`**（leader 落盘即成功，同步前宕机就丢）+ **消费端 `enable.auto.commit=true`**（poll 到就提交 offset，处理没落库就崩溃/重平衡，这批消息永不重投）+ **消费组频繁重平衡**（放大上一条的暴露窗口）。加固三段论：
> 1. 生产端：acks=all + min.insync.replicas=2 + retries（配幂等生产者防重）
> 2. 消费端：关自动提交，处理完成（落库）后手动提交 offset + 消费幂等
> 3. 兜底：关键链路对账任务（T+1 比对生产与消费两侧）
>
> 心法：Kafka 层做到 At Least Once，业务层用幂等把它变成事实上的 Exactly Once。

#### A.5 epoll LT/ET 与惊群（对应 1.5 / 1.1）

**第一层追问：LT 和 ET 的区别？**

> **答：** LT（水平触发）：接收缓冲区只要还有数据，epoll_wait 每次都返回该 fd——不怕漏读，允许阻塞 IO，是默认模式。ET（边沿触发）：只在状态跳变（无数据→有数据）时通知一次——必须一次把数据读完，否则剩余数据不会再有通知（除非新数据再次到达触发新跳变）。

**追问：ET 为什么必须配非阻塞 IO？**

> **答：** 「一次读完」的标准写法是循环 read 直到返回 EAGAIN。若 fd 是阻塞的，最后一次 read（缓冲区已空）会把整个线程挂起——单线程事件循环直接卡死，等价于宕机。所以 ET 的姿势是固定的：fd 设 `O_NONBLOCK`，循环读到 EAGAIN 才停，把 EAGAIN 当「读干净了」的完成信号。nginx / Redis 的事件驱动都是这套。

**再追问：惊群问题是什么？怎么解的？**

> **答：** 多个 worker 进程同时阻塞在 accept / epoll_wait 同一个 fd 上，新连接到来全被唤醒，只有一个抢到，其余空跑——白白付出上下文切换。演进三代：
> 1. `accept_mutex`：先抢用户态锁再 accept，串行化避免惊群，但锁竞争本身有开销（Nginx 早期默认）
> 2. `EPOLLEXCLUSIVE`（内核 4.5+）：同一 fd 只唤醒一个等待的 epoll
> 3. `SO_REUSEPORT`：每个 worker 各自 bind 同一端口，内核按四元组哈希把连接分发到不同 socket 的 accept 队列——彻底消除竞争，还顺带做了连接级负载均衡，Nginx 的 `reuseport` 即此，已是现代标配

#### A.6 一致性哈希与数据倾斜（对应 1.5 / 1.6）

**第一层追问：虚拟节点解决什么问题？**

> **答：** 裸一致性哈希（物理节点直接映射到环上）有两个病：节点少时环上位置不均（倾斜），节点增减时相邻节点承接负载差异巨大。虚拟节点把每个物理节点复制成成百上千个 vnode 撒到环上，用统计均匀替代几何均匀，还支持权重（性能好的机器多撒几个）。Redis Cluster 的 16384 个 slot 就是 vnode 思想的工程化变体。

**追问：数据倾斜怎么算？**

> **答：** vnode 均匀假设下，单节点负载期望 = 总量 / N，波动随 vnode 数增大而收敛。经验：每节点 100+ 个 vnode，倾斜可压到 ±10% 以内。但要区分「环倾斜」和「数据倾斜」——后者来自数据本身（大 V、爆款商品集中在少数 key），解法是热点 key 加随机后缀打散（用读放大换均衡），或本地缓存挡热点读。

**再追问：和普通取模比，扩容一台的迁移量差多少？**

> **答：** 取模 `hash(key) % N` 扩到 N+1：N 与 N+1 互质，几乎 **100%** 的 key 映射改变（10 台扩到 11 台，10/11 ≈ 91% 的 key 要搬）。一致性哈希扩一台，只有环上落入新节点区间的 key 需要迁移，理论 **1/(N+1)**（10 台扩 1 台 ≈ 9%）。91% vs 9%——就是「全量停机搬迁」和「滚动在线搬迁」的差别，直接决定扩容能不能在不停止服务的情况下做。

### B. 生产事故复盘：STAR-L × 3

> 高级岗面试的杀手锏不是背更多八股，而是**讲得出有数字、有决策、有后续的事故**。以下三个 case 为虚构叙事但数字自洽，可当作你真实事故的「结构模板」——把你的故障按这个骨架重讲一遍。

#### B.1 缓存雪崩引发的全站故障（S 级，持续 35 分钟）

**背景（S/T）：** 电商平台，商品详情页读 6 万 QPS，Redis 集群扛 5.8 万，MySQL 一主两从常态 3 千 QPS。大促前一天运营批量预热 80 万个商品缓存，脚本统一设置 TTL = 24h，**无随机抖动**。

**故障时间线：**

```text
19:59   大促开抢前 1 分钟，缓存命中率 99.2%，一切正常
20:00   80 万 key 同一秒集中过期 → 6 万 QPS 全部穿透到 MySQL
20:00:40 两个从库连接池打满（max_connections=2000），回源查询大量报错
20:02   主库 CPU 100%，连带同实例上另外 3 个业务的库一起变慢（连锁）
20:05   网关线程池触发拒绝，商品页 5xx 率 40%，下单链路开始超时
20:10   决策：商品页降级为静态兜底页（上次快照 + 暂不展示实时价格）
20:18   DBA kill 全部回源查询，主从逐步恢复
20:25   离线脚本按 500 QPS 限速重新预热（错峰 30 分钟铺完）
20:35   全量恢复，5xx 归零
```

**应急（A）：** 三板斧——降级（静态页保住下单主链路）、限流（回源查询限 500 QPS）、错峰预热。复盘时承认：应急不算失败，**35 分钟里 25 分钟花在「确认是雪崩而不是被攻击」**——可观测性不足是故障时长的放大器。

**根因（R）：** ① TTL 无随机抖动（直接原因）；② 无多级缓存，Redis 是单点防线；③ 回源无合并（同一商品被上千请求同时回源）；④ 缓存与 DB 之间没有容量联动的自动降级。

**长期改进（L）：** 1) TTL 强制 `base + random(0, 1800s)`，封装进公共库无法绕过；2) 本地缓存 Caffeine 二级（TTL 10s）挡瞬时穿透；3) 回源合并 singleflight，同 key 并发只放行一个请求；4) 预热必须走错峰预热平台并限速；5) 缓存命中率跌破 95% 自动告警 + 预案卡片推送值班群。

#### B.2 慢查询引发的主从延迟雪崩（S 级，持续 2 小时）

**背景（S/T）：** 订单库一主一从，90% 读流量在从库。周五晚 21:00 上线新报表功能，一条 `SELECT ... GROUP BY user_id ORDER BY ...` 漏建索引，全表扫描 2000 万行，单次 40s，且被「每小时定时任务 + 用户手动刷新」双重触发。

**故障时间线：**

```text
21:00   报表功能上线，SQL 跑在从库
21:10   从库回放线程被大查询压制，Seconds_Behind_Master 开始上涨
21:30   延迟 300s 且线性上涨；业务现象：用户支付成功后订单列表查不到
        → 客服被打爆 → 300+ 用户重复下单
22:00   通过 slow log + show processlist 定位到该 SQL
22:15   kill 查询，但积压的 binlog 仍需时间回放
23:00   延迟归零，全程 2 小时
```

**应急（A）：** kill 慢 SQL；「我的订单」页面临时切换读主（同步在网关限流保护主库）；前端对延迟窗口内订单展示「处理中」状态缓解重复下单。

**根因（R）：** 上线流程没有强制 EXPLAIN 评审；报表类重查询与在线业务共库共从库；依赖人工发现延迟（无告警）。

**长期改进（L）：** 1) SQL 工单卡口：自动 EXPLAIN，`type=ALL 且 rows>10 万` 直接拦截；2) 报表迁移到专用只读实例 / 数仓；3) 开启并行复制（MTS）降低单事务回放影响；4) 主从延迟 >60s 自动告警（此前靠人肉巡检）。

#### B.3 消息积压 800 万条的应急与根因（P1 级，积压 8 小时）

**背景（S/T）：** 订单履约消息 topic 8 分区，8 个消费者实例正常消费 5000 TPS，下游是积分系统 HTTP 接口（P99 正常 50ms）。周四 14:00 下游发布新版本引入慢逻辑。

**故障时间线与应急：**

```text
14:00   下游接口 P99 从 50ms 涨到 3s，超时率 30%
        消费 TPS 5000 → 800（消费线程全部阻塞在下游调用上）
14:00~22:00  lag 从 0 线性涨到 800 万，Kafka 磁盘水位 85%
22:00   值班发现（lag 告警阈值设的是 100 万——形同虚设）

应急三步：
① 止血：下游回滚版本（但积压不会自己消失）
② 搬运：原 topic 只有 8 分区，消费者数已到上限 → 写一个只搬运不处理的
   转储程序，把消息快速搬到 32 分区的新 topic（吞吐 5 万/s）
③ 并行消费：新 topic 上 32 个消费者实例，非核心逻辑（通知/积分明细）
   临时降级跳过，消费 TPS 拉到 4 万/s
00:30   积压清零，总恢复时长 2.5 小时
```

**根因（R）：** 下游是弱依赖却没有熔断降级（超时率 30% 还在硬打）；消费线程池与业务调用无隔离，下游慢直接拖死消费能力；lag 告警用绝对值阈值且阈值过大。

**长期改进（L）：** 1) 弱依赖统一接熔断（错误率 >10% 自动熔断走兜底）；2) 消费线程与下游调用线程池隔离 + 超时收紧到 500ms；3) lag 告警改为**增长速率**触发（5 分钟涨 10 万即报警）；4) 每季度做一次消费能力压测并登记容量水位。

### 🎤 面试这样答：讲一个你处理过的最难的线上事故

**骨架（90 秒版）：** 一句话背景（规模 + 正常态基线）→ 时间线三四个关键节点（带数字）→ 你做的关键决策（选 A 不选 B 的理由）→ 根因 → 编号列表的长期改进 → 一句反思。

**三个加分细节：** ① 有具体数字（QPS / 延迟 / 持续时长 / 影响单量）；② 讲清「当时有两个选项，我选了保守的那个，因为……」体现判断力而不只是操作力；③ 主动说「后来我们把这类问题做成了自动告警 / 平台能力」——**把事故讲成资产**。

**面试官追问预判：**
- 「为什么不用 X 方案？」→ 提前想好被否掉的备选及其代价
- 「这事最终归因给谁？」→ 高级岗忌讳甩锅到个人，归因到流程与机制缺失
- 「怎么保证不再发生？」→ 讲进上线卡口 / 监控 / 演练，而不是「我们更小心了」

### C. 容量与性能估算：30 秒口算演示

> 现场推演题考的不是数字精确，是**方法正确 + 量级不差**。每题给口算步骤，面试时边写边念出来。

#### C.1 MySQL 单表 2000 万经验阈值是怎么算的

30 秒口算：
1. InnoDB 页 16KB，假设行宽 1KB → 每叶子页约 **16 行**
2. 非叶子节点条目 = 主键 8B + 页指针 6B = 14B → 每非叶子页约 16KB / 14B ≈ **1170 个条目**（扇出）
3. 3 层 B+ 树容量 = 1170 × 1170 × 16 ≈ **2190 万 ≈ 2000 万**

```text
[根：1170 条目] → [1170 个二层页 × 1170 条目] → [约 137 万叶子页 × 16 行]
                                             = 2190 万行
```

4. 含义：2000 万行内一次主键点查最多 3 次页 IO；根与二层常驻 buffer pool，实际磁盘 IO ≈ 1 次
5. 边界：行宽 200B 时每页 80 行，3 层能装 1 亿+——**2000 万是「1KB 行宽」下的经验值而非硬限制**，真正的信号是 buffer pool 命中率随数据量增长出现拐点、树高从 3 变 4

### 🎤 面试这样答：MySQL 为什么 2000 万就要分表？

> 「先纠正前提：2000 万不是硬阈值，是可以推导的经验值——非叶子页扇出约 1170，1KB 行宽下 3 层 B+ 树恰好约 2190 万行。超过后树长到 4 层，多一次 IO 事小，**叶子页装不进 buffer pool 导致命中率下滑**才是性能拐点。我们实际是盯命中率曲线决策的：读写都热的表 3000 万就该拆，冷数据归档后单表 5000 万照样跑。而且拆之前先试读写分离和归档——分库分表是不可逆的复杂度，能晚拆就晚拆。」
>
> **追问「那你们什么时候拆的、怎么选拆分键？」** → 用真实数字回答：行宽、QPS、命中率拐点、按 user_id 哈希分 16 库 64 表、非拆分键查询走冗余表 / 异构索引。

#### C.2 Redis 内存估算：100 万 key × 平均 1KB

30 秒口算：
1. 数据本体：100 万 × 1KB = **1 GB**
2. 每 key 固定开销约 100B：redisObject 16B + SDS 头与 key 字符串 ~20B + dictEntry 24B + 哈希桶指针 ~8B（负载因子 ≤1 时）
3. 开销合计：100 万 × 100B ≈ 100 MB
4. 再乘碎片系数与 rehash 双桶余量 ×1.2~1.5
→ **实际 RSS 约 1.4~1.5 GB；报容量按「数据大小 × 1.5」申请**

追问延伸：同样数据改用 100 个 hash、每个 1 万 field——小 hash 用 ziplist/listpack 紧凑编码，内存省 20%+，但失去单 key 级过期。**数据结构选型就是内存与灵活性的交换**。

#### C.3 Kafka 集群吞吐估算

30 秒口算：
1. 单分区吞吐经验值（顺序写 + 批量 + 压缩）：**10~30 MB/s**
2. 集群吞吐 ≈ min(分区数 × 单分区吞吐, 磁盘顺序写 / 网卡上限)
3. 例：日志平台日增 2 TB，峰均比 10 倍 → 峰值 ≈ 2TB / 86400s × 10 ≈ **240 MB/s**
4. 所需分区数 = 240 / 30 = 8 → 留 100% 余量取 **16 分区**
5. 别忘副本写放大：3 副本 → 磁盘按 6 TB/天规划；消费端按每实例 30 MB/s 配 8+ 个消费者（与分区数对齐）

注意反向约束：分区不是越多越好——更多分区意味着更长的 leader 选举 / 重平衡时间、更多文件句柄与端到端延迟。

#### C.4 连接数 vs 线程数：C10K 估算

30 秒口算：
1. 线程模型：1 万连接 × 1MB 线程栈 = **10 GB 虚拟内存**；每次上下文切换 1~10 μs，1 万线程的时间片轮转本身吃掉数个核 → 不可行
2. epoll 事件驱动：单线程管 1 万 fd，内存 = 每连接收发 buffer 4~8KB × 1 万 ≈ **80 MB** → 轻松
3. 推到 C1M：100 万 × 8KB ≈ 8 GB，单机内存仍可行，瓶颈转移到内核协议栈、网卡中断、内存带宽 → 需要 RSS 多队列 + SO_REUSEPORT 多进程分摊
→ 结论：**C10K 的本质是「线程数 ≠ 连接数」，用事件驱动解耦**。AI 网关的 SSE 长连接就是这个模型的延伸——几十万挂机连接上持续转发 token 流，靠的正是 epoll + 非阻塞 + 少量事件循环线程。

### D. 高级岗专属视野

#### D.1 「资深 vs 初级」答法差异对比

| 问题 | 初级典型答法 | 资深应该答到 |
|------|-------------|-------------|
| B+ 树为什么快 | 「矮胖，IO 少」 | 扇出 → 3 层 2000 万推导 → buffer pool 命中率 → 什么场景哈希反而优 |
| 慢 SQL 优化 | 「加个索引」 | 先 EXPLAIN 分辨「缺索引」还是「优化器选错」→ 统计信息 / 索引 hint / 语句改写 → 用 rows/Extra 量化前后 |
| 缓存一致性 | 「延迟双删」 | 不一致窗口成因与时长上界 → binlog 订阅最终一致 → 业务能接受多久不一致、为什么 |
| 消息不丢 | 「acks=all」 | 三段各自的丢法与配置组合 → min.insync.replicas 的坑 → 幂等 + 对账兜底 |
| 分布式锁 | 「setnx + 过期时间」 | 续约、fencing token、RedLock 争议双方 → 低频强一致场景宁可用 DB 锁 |
| 分库分表 | 「2000 万就拆」 | 先问读写分离 / 归档是否够 → 拆分键与查询模式兼容代价 → 不可逆，晚拆优于早拆 |
| 限流方案 | 「Redis 令牌桶」 | 先定保护对象与阈值来源（压测）→ 单机 vs 集群 → 被限流后用户体验（排队 / 降级 / 报错） |

差异的本质：初级答「**怎么做**」，资深答「**为什么、什么时候不这么做、代价是什么**」。

#### D.2 技术选型叙事：什么时候引入组件是过度设计（YAGNI）

判据表（满足左侧信号，才考虑右侧组件）：

| 信号（右列的引入前提） | 才考虑引入 |
|------|-----------|
| 单表超 5000 万且读写分离 + 归档后仍顶不住 | 分库分表 |
| 日消息量千万级以上、需要持久化与回放 | Kafka（低量级 RabbitMQ 甚至本地队列够） |
| 团队 >5 人、单体部署发布互相阻塞 | 微服务化 |
| 真有第二机房 / 合规要求 | 多活 / 单元化 |
| 出现第二个以上数据消费者 | CDC / 事件总线 |

引入组件的真实成本 = 显性（开发迁移）+ 隐性（**运维、监控告警、故障面扩大、招人门槛、文档沉淀**）。资深的选型叙事长这样：「我们 QPS 500 时用 Redis 单机 + RDB 就够；涨到 5 万、写入成为瓶颈才上集群——**每次升级都有指标触发，而不是技术焦虑驱动**。」反例一句话讲透：「日活 1 万的应用上了 Kafka + 微服务 + K8s，三个月后迭代速度反而变慢——复杂度本身也是一种故障来源。」

#### D.3 面试官心理：深挖题在筛什么

- **筛「真做过」还是「背过」**：用过的人有颗粒度——知道 UNLINK 之外还有 lazyfree 开关、知道 ISR 收缩到 1 时 acks=all 也会丢。**细节密度是亲历的化石**
- **筛「边界感」**：答到自己知识边界时是否诚实。三层全对不必然，「这块我没深入到源码，我的理解是 X，我会用 Y 去验证」是加分项，硬编是减分项
- **筛「事故记忆」**：真扛过故障的人讲时间线会带数字甚至情绪（「那个周五晚上」），编造的故事缺少细节摩擦力
- **筛「共事感」**：资深岗意味着要做方案评审、给取舍拍板——回答里有没有「我们当时怎么权衡、谁反对、后来怎么验证」的叙事，比结论本身更暴露层级

深挖题的本质不是筛知识，是筛**「这个人遇到未知问题时的反应模式」**：慌着编、稳着推、还是诚实标记未知再给出验证路径。
