## 2.1 核心概念（模型的"规格书"）

### 2.1.1 Token：LLM 世界的计量单位

**是什么（通俗类比）：**

Token 是模型眼里"文字的最小零件"。模型不认识汉字也不认识单词，只认识 Token：英文常见词通常 1 词 = 1 Token，生僻词被拆成几块；中文一个汉字往往是 1 个甚至多个 Token（取决于词表）。负责"文本 ↔ 数字序列"互转的程序就叫 **tokenizer（分词器）**。

```text
用户看到的：    "今天的天气怎么样？"
tokenizer 拆成：["今","天","的","天","气","怎么","样","？"]   ← 8 个 Token
模型看到的：    [4521, 889, 203, 4521, 6107, 12433, 2091, 30]
                （每个数字查一张几十万行的"密码本" = 词表）
```

**为什么中文 Token 更贵：**

- 训练语料英文占比高，tokenizer 词表对英文覆盖好（常见词整存整取），对中文覆盖差（很多词要拆成单字甚至字节碎片）
- 同样信息量，中文消耗的 Token 往往是英文的 1.5~2 倍 → **同样按 Token 计费/限流，中文业务成本天然更高**（新一代多语言 tokenizer 已在改善，选型要看实测）
- 经验值：1 Token ≈ 0.7 个英文单词；1 个汉字 ≈ 0.6~1.5 Token（不同模型差异很大）

**工程影响（模型即组件视角）：**

- 计费按 Token：输入/输出分开计价，输出通常贵数倍
- 限流按 TPM：容量评估的计量单位（见 2.2.3）
- 上下文按 Token：窗口预算管理（见 2.1.2）
- 实操：上线前用官方 tokenizer / count_tokens 接口拿真实中文语料实测，别拿英文经验拍脑袋

### 2.1.2 Context Window：模型的"内存"

**是什么（通俗类比）：**

Context Window（上下文窗口）= 模型一次推理能"看得见"的全部 Token 上限，类似函数的栈内存：**输入 Prompt + 输出 Completion 共享这一块**。宣传里的 8K/128K/1M 指的都是 Token 数，不是字数。

**超窗口会发生什么（三种行为，按厂商/接口不同）：**

1. **直接报错**：API 返回 400（context_length_exceeded）——最常见，请求整体失败
2. **服务端静默截断**：对话类接口悄悄丢掉最早的消息只留最近的——不报错，但模型"失忆"
3. **客户端自行截断**：你自己组装 Prompt 时就该预算好，别把决定权交给服务端

**怎么做（后端纪律）：**

```text
窗口预算 = 系统指令 + 检索知识 + 对话历史 + 用户输入 + 输出预留(Max Tokens)
                                                    ↑
                        常见坑：不给输出留空间 → 生成到一半被掐断
                        （finish_reason=length，JSON 截断下游解析必炸）
```

- 组装 Prompt 前先估算 Token，超预算就裁剪/摘要（优先级与压缩策略见 L3 Context 工程）
- 长对话场景监控"窗口使用率"指标，持续 >80% 说明该上压缩或换长窗口模型

### 2.1.3 采样参数：Temperature / Top-P / Max Tokens

**是什么（通俗类比）：**

模型每一步输出的是"全词表上的概率分布"，采样参数决定"怎么从这个分布里抽一个词"：

- **Temperature**：分布的"尖锐度旋钮"。→0 时几乎总选最高概率词（保守稳定）；越高分布越平（发散、有创意）
- **Top-P（核采样）**：先把"累积概率凑不够 P 的陪跑候选"踢出抽奖箱，再抽。Top-P=0.1 只留少数高分词
- **Max Tokens**：输出长度上限，防跑飞的"保险丝"

**Temperature vs Top-P 对比：**

| 维度 | Temperature | Top-P |
|------|-------------|-------|
| 调什么 | 整个概率分布的尖锐/平坦 | 候选词集合的截断比例 |
| 类比 | 音量旋钮 | 先筛掉陪跑者再抽奖 |
| 极端行为 | →0 近似贪心取最优；调高→天马行空 | →0 只留 Top1；=1 全词表参与 |
| 生产建议 | 分类/抽取/工具调用 0~0.3；文案创作 0.7+ | 通常保持默认，与 Temperature 二选一调，别同时猛调 |

**工程影响（拉开差距的点）：**

- **Temperature=0 也不保证严格可复现**：浮点并行归约顺序、动态批处理、MoE 路由抖动都会引入微小随机性，几百步自回归连乘后放大——所以确定性不能押在采样参数上，要靠输出校验（L3）
- 参数随"任务类型"而不是"心情"配置：同一系统里意图识别 0.1、营销文案 0.8，做成配置化管理
- Max Tokens 是成本保险丝；Reasoning 模型的思考过程也在消耗它（见 2.1.5）

### 解码与采样：生产参数怎么配（2.1.3 的工程深挖）

**为什么应用工程师要管解码：**

线上很多"模型不稳定 / 胡说 / 跑题 / 格式崩"，根因不是模型能力不够，而是**解码策略与约束没配对**——同一个模型，采样参数配错就能把 90 分的答案打成 60 分；反过来，一套配对的"采样 + 约束"方案能白捡一大截稳定性。2.1.3 讲了参数"是什么"，这一节讲"生产上怎么配"。

**先建立直觉：每个 Token 落地前发生了什么**

```text
全词表 logits ─▶ softmax 概率分布 ─▶ 截断候选集 ─▶ 抽样/贪心选 1 个 ─▶ 下一个 step
                      │                  │
              Temperature 在这里"整形"    Top-k 按名次砍 / Top-p 按累积概率砍
                                         （惩罚项在这之前把已出现过的词降权）

同一个分布，两种温度下手感完全不同：
  低温：▇▇▇▂▁▁▁▁▁▁   头部极高 → 几乎总选第一名（稳定但呆板）
  高温：▃▃▄▃▂▃▂▂▂▂   摊平     → 尾部词也有机会（多样但易跑飞）
```

**四参数直觉对比表：**

| 参数 | 直觉一句话 | 往高调 | 往低调 | 生产定位 |
|------|-----------|--------|--------|---------|
| Temperature | 分布尖锐度的总旋钮 | 发散、有创意、易胡说 | 保守稳定、易重复卡壳 | 主旋钮，按任务类型配置化管理 |
| Top-p（核采样） | 只从累积概率 P 内的头部候选里抽 | 候选多、多样性升 | 候选少、趋近贪心 | 通常保持默认，与温度二选一微调 |
| Top-k | 只让概率前 k 名进抽奖箱 | k 大≈不设限 | k=1 即贪心 | 兜底防长尾怪词，偶见 50~100 |
| 惩罚项（repetition/frequency/presence） | 把已出现过的词降权 | 抑制复读机；过高则用词破碎 | 放任重复绕圈 | 文案类才需要动，事实类别碰 |

（纪律沿袭 2.1.3：Temperature 与 Top-P 二选一当主旋钮，别同时猛调；Top-k 与 Top-p 作用同向，双设时取更严者生效。）

**生产场景选型表（背这张去面试）：**

| 场景 | 推荐配置 | 理由 |
|------|---------|------|
| 事实问答 / RAG 问答 | **低温 0~0.3 + 引用约束**（"仅根据给定资料回答，无证据就拒答"） | 要忠实不要发挥；RAG 最大的错误放大器就是高温改写检索内容 |
| 意图识别 / 分类 / 抽取 | 温度 0 + 结构化输出 | 枚举任务只要第一名，任何随机性都是噪声 |
| 创意写作 / 营销文案 | 温度 0.7~1.0（或 Top-p 0.9）+ 惩罚项防复读 | 要的就是多样性 |
| 结构化输出（JSON/表单） | **JSON Schema / 函数调用优先于祈祷** | 约束解码让非法 Token 根本采不出来；prompt 里写"请输出 JSON"是赌运气 |
| Reasoning 模型 | 少动采样参数，重心放问题定义 | 思考链自带发散，外加热温度反而劣化（见 2.1.5） |

**调参顺序（从零配一个新任务）：**

1. 先定任务类型（事实 / 创意 / 枚举），直接套上面的选型表拿基线——而不是从默认值开始凭手感乱拧
2. 主旋钮只动一个：事实类先把温度压到位；创意类先调温度、再考虑 Top-p
3. 按症状微调：输出呆板重复 → 略升温或加惩罚项；跑题胡说 → 降温/收紧 Top-p，同时回头查 prompt 与上下文（很多"采样病"其实是"上下文病"）
4. 每次只动一个参数 + 用固定评测集对比前后——采样参数同样要"可回归"，不是拍脑袋

**两个常被遗忘的配角：** Stop sequences（命中即截断，防止模型越界续写废话）和 Max Tokens（成本与总时长的硬顶）不算"采样"，但属于同一张解码配置单——结构化输出场景 Stop sequences 配好能省掉一大截垃圾尾 Token。

**落地形态（参数配置化，不是散落在代码里）：**

```text
sampling_profile:
  rag_qa:       { temperature: 0.1, top_p: 1.0, max_tokens: 1024, schema: "answer_with_citation" }
  intent_class: { temperature: 0,   schema: "intent_enum" }
  copywriting:  { temperature: 0.9, frequency_penalty: 0.4 }
# 按任务类型挂 profile；参数变更走评审 + 回归评测，与改代码同权重
```

**常见坑（翻车高发区）：**

- **温度高 →"合理但不真实"**：输出流畅、自信、细节丰富，但事实是编的——高温放大的正是长尾里的幻觉词，用户体感是"模型变聪明了，也变能编了"
- **解析失败 → 二次调用成本飙升**：靠正则/截取解析自然语言输出，5% 失败率意味着 5% 的请求要走重试甚至人工兜底，P99 延迟和成本全被尾部拖垮——解法是 Schema 约束 + 失败降级路径，不是降温祈祷
- **长上下文 + 高温 → 跑题加速**：上下文过长注意力被稀释、分布本就更散，高温再推一把（长上下文排布见进阶篇 A.2）
- **全站一套默认参数**：意图识别和营销文案共用一个温度，是采样参数没做配置化管理的信号（2.1.3 的纪律）

**推测解码一段（与 2.3.5 呼应）：**

Speculative Decoding 是**服务端加速手段，对调用方透明**：小模型先一口气草拟 N 个 Token，大模型一次并行验证，猜对的整段采纳、猜错从错点重算——输出分布不变、质量无损。应用工程师要的不是"会配它"，而是知道它解释了两个现象：为什么有些厂商的流式输出"一段一段蹦"（一批猜测被整体验证通过）；以及自部署时它是 vLLM 类引擎降延迟的选项之一。机制详见 2.3.5。

**🎤 口述模板：线上 RAG 问答"不稳定、偶尔胡说"，怎么从解码角度排查？**

> "我先把锅从模型能力上摘下来：很多不稳定根因是解码策略。第一步查温度：RAG 问答必须 0 到 0.3 的低温，高温等于允许模型改写检索资料，把忠实性问题放大成幻觉。第二步查约束：光降温不够，prompt 要加引用约束——仅根据给定资料回答、无证据就拒答；输出走 Schema 结构化校验，因为解析失败引发的二次调用会让成本和延迟飙升。第三步查惩罚项：事实类任务别动它，乱加会把术语拆得破碎。最后确认参数按任务类型做配置化管理，而不是全站一个默认值。这些查完还不稳，才回头查检索质量和模型能力——排查顺序本身就是工程判断。"（约 240 字）

**追问：**

1. **Top-k 和 Top-p 同时设会怎样？**
   答：两个都在砍候选集，同时设时效果取更严的（既进前 k、又在累积概率 P 内）。工程上主用一个，别叠加调，否则连消融实验都做不干净。
2. **为什么结构化输出优先 Schema 而不是 prompt 约束？**
   答：prompt 是软约束，模型可能听也可能不听，失败率随字段复杂度上升；Schema/函数调用走约束解码，非法 Token 在采样阶段就被排除，再加校验兜底——概率级兜底和事后补救的差别。
3. **低温 + 引用约束都配了还是偶尔胡说，下一步查什么？**
   答：解码层查完，往下一层查检索质量（证据块是否真命中、排布是否首尾高价值）和模型本身的幻觉评测；解码策略只能保证"不出力"，保证不了"证据链完整"。

### 2.1.4 Embedding 与相似度（概念级）

**是什么（通俗类比）：**

Embedding 把一段文本压成一个固定长度的向量（如 1024 维），语义相近的文本在向量空间里"住得近"。它是 RAG 检索、语义缓存、Few-Shot 动态选取的地基——把"意思像不像"变成"距离近不近"的几何问题。

**三种相似度（概念级）：**

| 度量 | 比什么 | 通俗理解 | 工程用法 |
|------|--------|---------|---------|
| 余弦相似度 | 方向夹角 | 两句话"方向"是否一致，不管长短 | 文本语义检索的默认选择 |
| 点积（内积） | 方向 + 模长 | 向量归一化后与余弦等价 | 向量库先归一化，再用点积冒充余弦——更快 |
| 欧氏距离 | 绝对距离 | 空间中两点的直线距离 | 关注量级差异的场景，部分非归一化模型用 |

**工程要点：**
- 同一个索引里必须用**同一个 Embedding 模型**生成的向量，混用等于鸡同鸭讲
- 换 Embedding 模型 = 全量向量重建（大动作，选型慎重，见 L4/L5）
- 相似度阈值（如 0.75+ 判"相关"）没有万能值，要拿业务数据校准

### 2.1.5 模型类型演进：Base → Instruction → Chat → Reasoning

**是什么（通俗类比）：**

四代模型像员工的四个成长阶段：Base 是"博览群书但不会干活"的实习生——你给它前缀它就往后续写；Instruction 是"教过怎么执行指令"的员工；Chat 是"会多轮沟通、懂角色、会用工具"的熟手；Reasoning 是"接任务先打草稿再交付"的专家——草稿（思考 Token）也计费、也要时间。

**四代对比表：**

| 维度 | Base | Instruction | Chat | Reasoning(o1/R1 类) |
|------|------|-------------|------|---------------------|
| 核心能力 | 文本续写 | 听懂单轮指令 | 多轮对话 + 角色系统 + 工具调用 | 长链推理后再回答 |
| 给它什么 | 一段前缀文本 | 一条指令 | messages 数组(system/user/assistant) | 简洁的问题定义 + 验收标准 |
| 典型坑 | 给它提问，它续写出十个新提问 | 没有对话状态 | 依赖好的 chat 模板 | 延迟高数倍、思考 Token 计费 |
| 工程定位 | 微调底座，应用层少直接用 | 已基本被 Chat 取代 | **应用绝对主力** | 按需路由的"难题专家"（级联见 L8） |

**Reasoning 模型对工程的三冲击（2025 高频）：**

1. **思考 Token**：推理过程也消耗 Token → 计费、Max Tokens、TPM 配额全被放大；部分厂商思考过程不可见（只给结论），DeepSeek 风格则通过 `reasoning_content` 增量返回思考过程
2. **延迟**：TTFT 可能到几十秒，超时、前端"思考中"状态、排队体验全要重做
3. **Prompt 方式不同**：别写"一步一步想"、少给 Few-Shot，重心移到"把问题定义清楚 + 验收标准"（详见 L3.4）

### 2.1.6 训练名词级理解（各解决什么问题）

**一句话总纲：预训练造脑子，SFT 教做事，RLHF/DPO 对齐品味，LoRA/量化是省钱手段。**

| 名词 | 解决什么问题 | 一句话原理 | 你何时需要关心 |
|------|-------------|-----------|---------------|
| 预训练 Pretraining | 造出懂语言的 Base 模型 | 海量文本"预测下一个词"式自监督学习 | 不做；但要知道知识有截止日期、领域深浅从这里来 |
| SFT 监督微调 | 让 Base"听话" | 用"指令→标准回答"对做示范教学 | 需要定制输出风格/固定格式/领域话术时 |
| RLHF | 对齐人类偏好 | 人工排序答案→训练奖励模型→强化学习优化 | 名词级；知道效果最好但贵、流程重 |
| DPO | RLHF 的简化平替 | 跳过奖励模型，直接从偏好对学习 | 名词级；比 RLHF 简单稳定，开源社区主流 |
| LoRA | 降低微调成本 | 冻结原权重，只训练很小的增量矩阵 | 低成本微调首选；消费级显卡可跑 |
| 量化(AWQ/GPTQ) | 降低部署成本 | 权重从 FP16 压到 INT8/INT4：显存省、速度快、精度微降 | 自部署推理时（vLLM 加载量化版） |

**决策口诀（面试常考"什么时候微调"）：**
- 知识问题 → RAG（更新快、可溯源），不是微调
- 风格/格式/领域术语问题 → SFT/LoRA 打补丁
- 业界惯例 **RAG-First**（四维度对比详见 L5.3）

#### 对齐与偏好优化（进阶补丁）

> 定位声明：应用岗面试对 RLHF/DPO 家族**点到为止**——不考公式推导，考你能不能讲清「工程上关心什么」：数据质量、可回滚、行为漂移、评估闭环。2.1.6 给了名词级一句话，这里升到工程决策级。

**这一层在对齐什么（与 2.1.6 的递进关系）：**

SFT 教模型"做事"——示范数据只能告诉它"好答案长什么样"；对齐教的是"品味"——A 回答比 B 好在哪里、什么时候宁可不答。这种"相对好坏"的判断没法用标准答案表达，只能用偏好数据教。偏好本身是个三角：**有用性 / 无害性 / 可控性**，三者天然打架（越听话越容易被诱导滥用），对齐就是在三者之间找业务可接受的平衡点。

**你什么时候真的会遇到它（应用岗的三个真实触点）：**

1. **自托管开源模型做领域定制**：裸 SFT 后格式对了但"品味"不对（啰嗦 / 不拒答 / 过度承诺），补一轮 DPO 偏好优化是标配动作
2. **用评估模型（judge）给输出打分**：你消费的正是别人对齐好的判断力——judge 的漂移会直接污染你的评测结论，judge 版本要锁定
3. **分析线上 badcase**：先分诊是"能力不足"还是"偏好不符"——前者换模型 / 加知识，后者调偏好数据 / 系统指令，方向判断错了全是白忙

**三家主流方法对比（机制 / 成本 / 稳定性）：**

| 方法 | 机制一句话 | 成本 | 稳定性 | 工程观感 |
|------|-----------|------|--------|---------|
| RLHF（PPO 路线） | 人工偏好排序 → 训奖励模型 → 强化学习优化策略 | 最贵：人工标注 + 奖励模型训练 + RL 基建 | 最难调：reward hacking、训练易崩 | 效果天花板最高，头部厂商旗舰模型的主流路线 |
| RLAIF | 用评估模型代替人工打偏好标签 | 标注成本大降 | 新风险：judge 的漂移和偏见会被蒸馏进模型 | 规模化偏好数据的性价比路线 |
| DPO | 跳过奖励模型和 RL，直接在偏好对上优化策略 | 轻：偏好对 + 常规训练栈 | 稳：损失温和、好复现 | 开源社区事实主流，应用团队自托管微调的首选 |

**一句话带过的两个新名字（被问到不愣住即可）：**

- **KTO**：连"成对偏好"都不需要，用好/坏单标签即可优化——标注门槛更低
- **Constitutional AI**：先给模型立一部"宪法"（原则清单），让它自我批评再修订答案，配合 AI 反馈减少人工

**工程落地点三条（讲得出这三条就有"工程味"）：**

1. **偏好数据要覆盖"拒答边界"**：只教"怎么答好"、不教"什么时候不答"，上线必出行为漂移——安全策略、拒答话术、结构化格式都要有负例样本
2. **回归集（golden set）+ 版本化**：模型 / 训练数据 / 偏好规则三者可追溯，任何一次对齐改动先跑回归集再上线——与 2.2.4 的契约测试同一个思想：防"静默变坏"
3. **高风险领域别指望对齐一次解决所有风险**：优先做"拒答策略 + 引用机制 + 审核流程"的组合拳，对齐只是纵深防御中的一层（安全话题详见 L5/L7）

**两个高频追问的答法（备着）：**

1. **"DPO 为什么比 RLHF 稳？"**
   答：没有奖励模型这个中间层，就没有"钻空子"的对象——RLHF 的策略会 hack 奖励模型的漏洞（reward hacking），DPO 直接在偏好对上算损失，损失面温和、没有 RL 探索带来的训练崩坏，所以普通训练栈就能跑。
2. **"偏好数据从哪来？"**
   答：三个来源——线上 badcase 整理成对（修复前 vs 修复后）、人工撰写正负例、强模型生成候选再人工挑选。质量比数量重要，几千对高质量数据就能带来明显的行为改变。

**一句收束：** 被问到对齐，先说"工程上我关心数据质量、可回滚、行为漂移"这个视角，再展开方法对比——顺序反过来就变成背名词了。

### 2.1.7 微调工程实践：LoRA/QLoRA 与防翻车清单

> 2.1.6 回答"什么时候微调"，这一节回答"真要微调时怎么不翻车"。应用岗不需要亲手训过，但要能对着清单说出每个决策点的取舍。

```text
微调项目全流程（每一步都埋着防翻车点）：
  需求分诊(微调 vs RAG) ─▶ 数据准备(三要点) ─▶ 训练(LoRA/QLoRA + 关键参数)
        │                    │                   │
     停：RAG-First        停：数据不过关不训     停：小 rank 保守起步
        ▼                    ▼                   ▼
  领域测试集 ──不达标──▶ 回改数据/调参 ──达标──▶ 通用回归集(防漂移) ─▶ 灰度上线 ─▶ 行为漂移监控
```

**第一步还是决策：微调 vs RAG 速查（2.1.6 口诀的展开版）：**

| 判断维度 | 倾向 RAG | 倾向微调 |
|---------|---------|---------|
| 知识形态 | 变动频繁（政策/产品/FAQ），要可溯源引用 | 相对稳定，核心是风格/格式/术语 |
| 失败代价 | 答错要追责 → 必须给得出处 | 格式不统一难看但不致命 |
| 成本结构 | 知识更新 = 改文档，分钟级生效 | 知识更新 = 重训 + 重评测，天级 |
| 延迟/成本诉求 | — | 小模型微调后替代大模型在线推理，降本降延迟 |
| 典型任务 | 知识问答、文档摘要 | 统一报告格式、领域话术、固定 JSON 输出 |

（业界惯例 RAG-First：先 RAG 跑通，微调解决 RAG 解决不了的"行为问题"；四维度对比详见 L5.3。）

**LoRA 一图流（为什么便宜）：**

```text
LoRA：冻结基座权重，旁挂低秩增量
  x ──▶ [W（冻结）] ──────▶ ＋ ──▶ h      W: d×d 原权重，不参与训练
        └─▶ [A: d×r] ▶ [B: r×d] ──┘      r ≪ d（如 8/16/32），只训 A、B
  等效改动 ΔW = B·A：可训参数量从 d² 降到 2×d×r，低秩 = 天然正则

QLoRA：把冻结的 W 先压成 4bit 存显存（计算时反量化），A/B 仍全精度训练
```

**LoRA vs QLoRA 选型表（PEFT 两条主流路线）：**

| 维度 | LoRA | QLoRA |
|------|------|-------|
| 做法 | FP16/BF16 基座冻结 + 低秩增量 | 基座先 4bit 量化 + 低秩增量 |
| 显存 | 中等（7B 级别也要 20G+ 的卡） | 最省（7B 级单张消费级卡可跑） |
| 流程复杂度 | 简单，主流训练框架一等公民 | 略复杂：量化配置 + 精度对齐，多一层调参 |
| 训练速度 | 快 | 慢一些（反量化的计算开销） |
| 质量上限 | 基线 | 多数场景与 LoRA 打平，极少数精细任务略降 |
| 怎么选 | 显存充足、要流程稳、要复现一致 | 显存紧张、单机单卡、实验迭代期 |

**数据准备三要点（数据质量决定微调上限）：**

1. **去重与清洗**：重复样本等于隐性加权，模型会过拟合到高频模板；脏数据（错误答案、错乱格式）会被一丝不苟地学走——"垃圾进、垃圾出"在微调里是字面意义
2. **指令格式统一**：训练样本的 instruction/input/output 模板，与推理时的 chat 模板**严格一致**——训练一个格式、推理用另一个格式，等于白训
3. **任务多样化防模板化**：清一色同句式数据，模型学到的是"套路"不是"能力"；混入多种任务与指令风格，通用能力也更不容易掉

```text
一条合格训练样本（格式与推理时 chat 模板严格一致）：
  {"instruction": "把下面的客服对话整理成工单",
   "input": "……原始对话原文……",
   "output": "{\"类别\": \"物流\", \"紧急度\": \"P2\", \"摘要\": \"……\"}"}
  ↑ 正例教格式，负例教边界：不该受理的请求 → 标准拒答话术；超出知识范围 → "无法确定"
```

**关键参数速查表（被追问时的及格线）：**

| 参数 | 是什么 | 经验范围 | 调过头的风险 |
|------|--------|---------|-------------|
| rank（r） | 低秩矩阵的秩 = 补丁容量 | 8~64 常用 | 过拟合 + 显存涨；风格/格式类任务 8~16 足够 |
| α（alpha） | 增量的缩放系数，等效强度 ≈ α/r | 常取 r 的 1~2 倍 | 与学习率强耦合，乱调等于学习率乱调 |
| dropout | 增量矩阵上的正则 | 0.05~0.1 | 太大欠拟合，学不动领域风格 |
| 学习率 | 比 full finetune 大约一个量级 | 1e-4 ~ 3e-4 量级 | 太大 → 灾难遗忘/过拟合；太小 → 学不动 |
| batch size × 梯度累积 | 有效批量 | 显存不够就用累积凑 | 有效批量过小，训练曲线不稳 |

**防灾难遗忘两招 + 评估两线（翻过车的人必聊这段）：**

- **防灾难遗忘两招：**
  1. **混合通用数据**：领域数据里掺 10~30% 原始通用指令数据，提醒模型"别忘老本行"
  2. **正则化约束**：LoRA 低秩本身是天然正则（能改的参数就少）；再配 dropout、早停、小学习率，把改动锁死在"补丁"范围
- **评估两线（上线前后都要有）：**
  1. **领域测试集**：目标任务的专用评测集 + 人工抽检，证明"该学的学会了"
  2. **行为漂移监控**：留一套通用能力回归集（拒答边界、指令遵循、格式稳定性）定期跑，证明"没学的没忘掉"——上线后继续盯，这是微调版模型独有的运维项

**上线后行为漂移的三个典型信号（监控项就这么定）：**

- 拒答率突变：学过头 → 什么都不敢答；混进坏样本 → 什么都敢答
- 通用指令合格率下降：JSON 格式、指令遵循这些"老手艺"回流到旧问题
- 领域外问题质量下降：用户拿它当通用助手用的场景开始翻车

**防翻车总清单（上线前过一遍）：**

- [ ] 决策复核：这个问题 RAG/prompt 真的解决不了吗（RAG-First）
- [ ] 数据：已去重、格式与推理模板一致、任务多样化、负例与拒答样本在列
- [ ] 参数：rank/α/dropout/学习率有记录，从保守值起步
- [ ] 防遗忘：混入通用数据比例明确
- [ ] 评估：领域测试集达标 + 通用回归集无漂移
- [ ] 回滚：模型版本、数据版本、评测报告三者绑定，可一键回退

> 微调的落地决策框架（ROI 核算、组织时机、与 RAG/长提示词的替代方案对比），见 [L9 · 热点与 AI 系统设计](../4-面试冲刺/09_L9_热点与AI系统设计.md) 的 Fine-tuning 决策一节。

### 🎤 面试这样答：为什么 Temperature 设成 0，两次结果还是不一样？

> "因为采样参数只控制'从概率分布里怎么抽'，Temperature=0 只是近似贪心地取最高概率词，但模型推理本身就不是严格确定性的：GPU 浮点并行计算的归约顺序不固定；服务端为了吞吐会做动态批处理，同一请求在不同批次里的数值路径可能不同；MoE 架构的路由也有抖动。而自回归生成是几百步的连乘，每步的微小差异会逐步放大。所以 Temperature=0 能显著收敛行为，但不能把'确定性'押在它上面。工程上真正要确定性的地方我用三层保障：能枚举的用结构化输出加 Schema 校验；关键决策不靠单次采样，用投票或规则复核；下游永远按'概率系统'设防，不盲信任何单次输出。本质上，我是把'输出有随机性'当成这个组件的既定特性来设计系统，而不是试图消灭它。"（约 270 字）

**追问：**

1. **那怎么让用户每次提问得到一样的答案（比如测试场景）？**
   答：固定种子（seed 参数，部分厂商支持）+ Temperature=0 + 固定 Prompt 版本，能大幅提高一致性，但仍非合同级保证；测试断言用结构/语义校验而非全等。
2. **中文业务选模型，tokenizer 会影响你的决策吗？**
   答：会。同样 128K 窗口，中文有效容量可能只有英文的一半；计费和 TPM 也按 Token 算，中文更贵。选型时拿真实中文语料实测 tokens/字，再算容量和成本账。
3. **Base 模型现在还有什么用？**
   答：主要是继续预训练/微调的底座，以及纯续写类任务（补全代码、续写文档）。应用层直接用 Chat 模型——messages 接口、工具调用这些形态都是为它设计的。
4. **LoRA 微调比全参微调效果差很多吗？**
   答：大多数风格、格式、领域适配场景差距很小，而成本差一个数量级；深度能力改造才需要全参。先 LoRA 跑通评测，不够再升级。

## 2.2 LLM API 工程化（后端主场）

### 2.2.1 调用地基：鉴权、超时、重试、幂等

**鉴权（API Key 管理，全是事故来源）：**

- 形态：HTTP 头携带密钥（`Authorization: Bearer` / `x-api-key`），本质就是调外部服务的 API Key
- 纪律：
  - Key 进密管系统/KMS 或至少环境变量，**绝不硬编码、绝不进 Git、绝不下发前端**
  - 后端统一持钥代理调用，前端只见你自己的业务鉴权
  - 按业务线/环境分 Key：配额隔离 + 泄漏时爆炸半径小 + 审计清晰
  - 支持轮换 + 异常用量告警（key 泄漏的典型信号）

**超时设置策略（LLM 特有的变形）：**

| 超时项 | 常规后端 | LLM API 的变形 | 建议值思路 |
|--------|---------|---------------|-----------|
| 连接超时 | 1~3s | 不变，快速失败 | 秒级 |
| 读超时（非流式） | 覆盖整个响应 | 生成可能要几十秒甚至几分钟 | P99 生成时长 + buffer（60~180s） |
| 读超时（流式） | 同上 | 退化成 **idle 超时**：两个 chunk 之间的最大间隔 | 10~30s（收到 chunk 就续命） |
| 总预算超时 | — | 流式也要封顶，防"涓涓细流永不结束" | 按 SLA 定，如 120s |

- 分层超时：上游（网关）超时必须 > 下游（模型）超时，否则下游还在干活、上游已经 504
- 交互场景用 **TTFT 定 SLA**：首字 3 秒出不来，就要 loading 动效或降级小模型（依据见 2.3）

**重试：指数退避 + 抖动（jitter）：**

```text
时间线（base=1s，max_retries=3）：

 请求① ──失败(429/5xx/超时)
        ├─ 退避 1s + jitter(0~1s)
 请求② ──失败
        ├─ 退避 2s + jitter
 请求③ ──失败
        ├─ 退避 4s + jitter
 请求④ ──成功 ✔   （仍失败 → 降级备用模型 / 进队列延后 / 返回兜底话术）

 为什么指数：早期快重试抢瞬时抖动，后期慢重试等容量恢复
 为什么加抖动：同批失败实例若同频重试 → 齐刷刷打过去（惊群）→ 服务端再次被打挂
```

- **只重试值得重试的错误**：429、5xx、网络超时/重置 → 可重试；400（参数错）、401（鉴权错）、内容政策拒绝 → 重试一万次也一样，立刻修代码或改 Prompt
- 优先尊重响应头 `Retry-After`（厂商已告诉你等多久）
- 重试封顶（2~4 次）+ 重试预算（防止重试流量把故障放大成雪崩）

**幂等（LLM 场景的三层含义，比常规后端更细）：**

1. LLM 生成本身无副作用 → 生成类调用**重试安全**
2. 但**计费有副作用**：盲目重试 = 双倍烧钱 → 重试封顶 + 成本监控
3. Agent 场景里 LLM 输出会触发**工具副作用**（扣款/发邮件）→ 重试危险区：工具调用带幂等键、先查后做、不可逆操作加 Dry-run（详见 L6.2）

### 2.2.2 流式响应 SSE 深入

**SSE 是什么（通俗类比）：**

SSE（Server-Sent Events）= "服务器单向广播的 HTTP 长连接"。基于普通 HTTP，响应头声明 `text/event-stream`，之后服务端持续写 `data: xxx` 格式的事件块。相比 WebSocket：生成本来就是单向下发（单向够用）、走标准 HTTP 端口和网关、协议是纯文本好调试——所以 LLM 流式首选 SSE。

**数据流格式示例（OpenAI 风格，各家大体同构）：**

```text
HTTP/1.1 200 OK
Content-Type: text/event-stream        ← 客户端据此进入流模式
Cache-Control: no-cache

data: {"choices":[{"delta":{"role":"assistant","content":"今"}}]}     ← 事件1
                                                                      （空行 = 事件结束）
data: {"choices":[{"delta":{"content":"天"}}]}                        ← 事件2：增量

data: {"choices":[{"delta":{"content":"怎么样"},"finish_reason":null}]}

data: {"choices":[{"delta":{},"finish_reason":"stop"}]}               ← 收尾：停止原因
data: [DONE]                                                          ← 流结束标记
                                            （部分厂商在最后 chunk 带 usage 计量，需显式请求）
```

**chunk 解析的工程要点：**

- 每个 `data:` 后是**一行完整 JSON**（内部不能有裸换行），事件以**空行（\n\n）分隔**——按行读、按事件切，别按固定字节切
- 内容在 `delta` 里是**增量**，业务侧自己拼接：`full += delta.content`
- DeepSeek 风格 Reasoning 模型：思考过程走 `delta.reasoning_content`，正文走 `delta.content`——前端可做"思考中…/作答中…"两段式渲染
- **`[DONE]` 是正常结束的唯一标志**：没收到 [DONE] 连接就断 = 异常中断
- 计量：`usage`（prompt/completion tokens）用于扣配额和成本记账（可观测详见 L8）

**异常中断处理与"断点续传"：**

```text
正常：chunk → chunk → … → finish_reason → [DONE] → 连接关闭
异常：chunk → chunk → ✂ （网络断 / 服务端中途 error 事件 / idle 超时） ← 没有 [DONE]！

处理策略（成本从低到高）：
 ① 检测：没收到 [DONE] 就断流 → 标记"生成中断"，给用户重试入口
 ② 保底：已收到的部分内容不丢（先渲染 + 存草稿），别整段清空
 ③ 续传：把"已生成内容"作为 assistant 消息前缀回填 → 再请求"继续写"
        （服务端配合：会话级缓存已生成前缀，重连后从断点续发）
 ④ 重生成：最简单但双倍成本，短文本可接受
```

- 前端渐进渲染：逐 chunk append + Markdown 增量渲染 + 节流（避免每个 chunk 都触发整段重排）
- **网关陷阱（高频事故）**：Nginx 默认缓冲响应，攒够一批才下发 → 用户看到"卡 10 秒然后蹦出一大段"的**假流式**。必须 `proxy_buffering off;`（或让后端回 `X-Accel-Buffering: no` 头）

**流式 vs 非流式对比：**

| 维度 | 非流式 | 流式 SSE |
|------|--------|---------|
| 用户看到首字 | 全部生成完（可能 30s+） | TTFT 后立即可见 |
| 感知延迟 | 高 | 低（体感快数倍） |
| 总成本/总耗时 | 基线 | **完全一样**（见 2.3.2） |
| 读超时语义 | 覆盖全程 | chunk 间隔（idle）超时 |
| 客户端复杂度 | 一次 JSON 解析 | 增量拼接 + [DONE] + 中断处理 |
| 基础设施要求 | 常规 | 网关关缓冲、避开整段压缩/缓存 |

### 2.2.3 配额管理：RPM/TPM、429、批量、embedding 限流

**是什么（通俗类比）：**

厂商限流的两把尺子：**RPM**（每分钟请求数，像 QPS 限制）和 **TPM**（每分钟 Token 数，LLM 特有的"流量体积"限制）。LLM 业务的真正天花板几乎总是 **TPM**——单请求就是几千 Token，"请求数不多但体积巨大"。

**429（Too Many Requests）处理：**

- 读响应头/体：`Retry-After`（等多久）+ 确认是 RPM 还是 TPM 超限
- 立即动作：该请求进入指数退避重试（2.2.1），而不是硬打
- 根治动作（客户端主动限速，别等 429 来教育你）：

```text
客户端配额治理三件套：
 ① 并发信号量：全局限制在途请求数（防 RPM）
 ② Token 令牌桶：按"预估 tokens/请求"预扣，速率 = 配额的 80%（防 TPM，留 buffer）
 ③ 排队削峰：超限请求进本地队列延后消化，向上游只呈现平滑流量
```

- 结构性扩容：多 Key 池轮转（注意厂商条款）、申请提额、离线任务走 Batch 错峰、超出自建推理（L8）

**容量评估示例（面试可能让你现场算）：**

```text
业务目标：峰值 10 QPS，平均每次 Prompt 2K + 输出 0.5K = 2.5K tokens
TPM 需求 = 10 × 60 × 2.5K = 150 万 TPM
结论：远超常见配额（通常几万~几十万量级）
     → 必须组合拳：语义缓存砍重复流量 + 模型级联砍单价 + Batch 错峰 + 提额/自部署
```

**Batch API（异步批量）：**

- 不进实时链路：攒一批请求一次性提交，厂商数小时内返回（常有约 5 折折扣）
- 适合：文档总结、离线标注、评测集跑分——**成本敏感、延迟不敏感**的任务全走它

**Embedding 接口限流三板斧（高频实战题）：**

1. **批量请求**：embedding 接口支持一次传多条文本（数组入参），吞吐高、RPM 占用少——入库流水线必须用批量
2. **缓存**：`hash(文本 + 模型版本) → 向量` 落 Redis/DB；文档入库天然幂等（重复段落直接命中），高频常见问题命中率很可观
3. **本地模型兜底**：BGE 等开源模型 ONNX/CPU 部署，云端限流打满或故障时降级切换（接受少量精度差异，按业务分级开关）

### 2.2.4 多模型适配层设计

**是什么（通俗类比）：**

各家模型 API 就像不同数据库的方言：大思路一致，字段名、事件格式、错误码全是细节差异。适配层 = 给 LLM 做一层"统一 SQL 方言 + 连接池"——业务代码只写一次，底下随便换厂商。

**各家 API 差异维度表（记维度，别背细节；以官方文档为准）：**

| 差异维度 | 典型分歧点 |
|---------|-----------|
| 鉴权 | Bearer Token vs x-api-key + 版本号头 |
| 消息结构 | system 独立顶层字段 vs 塞进 messages 数组 |
| 流式事件 | data:[DONE] 风格 vs event:type 多事件类型风格 |
| 思考内容 | 完全隐藏 vs reasoning_content 增量可见 |
| 工具调用 | 参数命名、工具结果怎么回填，各家不同 |
| 错误码/限流头 | 429 响应体结构、Retry-After 头格式 |
| 计费口径 | 缓存折扣、思考 Token 是否计费各不相同 |

（OpenAI 系已是事实标准：GLM/DeepSeek 等大多提供 OpenAI 兼容模式，切换成本低；Claude 这类原生协议不同的厂商是适配成本大头。）

**统一抽象层架构（白板图）：**

```text
              业务代码（只依赖统一接口，不知道底下是谁）
                            │
            ┌───────────────▼────────────────┐
            │          统一抽象层             │
            │  统一模型：ChatRequest /        │
            │  ChatResponse / StreamEvent /  │
            │  ToolCall                      │
            │  消息结构转换 · 流式事件规范化   │
            │  工具调用协议互转 · 错误码归一化 │
            └───┬─────────┬─────────┬────────┘
                │         │         │
           ┌────▼───┐ ┌───▼────┐ ┌──▼─────┐ ┌────────┐
           │ OpenAI │ │ Claude │ │  GLM   │ │DeepSeek│
           │ Adapter│ │ Adapter│ │ Adapter│ │ Adapter│
           └────────┘ └────────┘ └────────┘ └────────┘
 横切能力（在抽象层统一收口）：
 路由选型(按任务/成本/延迟) · 故障转移 · 多 Key 配额池
 重试退避 · 熔断降级 · 成本记账 · 统一监控埋点
```

**设计要点：**
- 抽象"最小完备"：chat / embed / 流式事件 / 工具调用四大件；某家特有参数走 extensions 字段透传，**别让厂商特例污染统一接口**（抽象泄漏是适配层最大的坑）
- 路由策略放网关层：任务分类 → 简单任务便宜小模型、难题 Reasoning 模型（模型级联详见 L8）
- 故障转移保持上下文一致：切厂商时把已有 messages 原样带给新模型，注意各家窗口与格式兼容
- 成本记账按"模型 × 业务线"打点，月底能回答"每个功能的 AI 成本"——这是 L8 成本治理的数据地基

### 🎤 面试这样答：线上大量 429，怎么治理？

> "429 是结果，治理分'止血'和'根治'。止血：客户端读 Retry-After 进入指数退避重试，同时用并发信号量把在途请求压住，避免重试雪崩；已溢出的请求进本地队列延后消化，交互场景给排队提示而不是报错。根治先做容量核算：按'峰值 QPS × 60 × 单次平均 Token'换算成 TPM 需求，和配额对比确认缺口——LLM 业务的瓶颈几乎总在 TPM 而不是 RPM，因为单请求就是几千 Token。然后按性价比上手段：语义缓存砍掉重复问题的流量；模型级联让简单任务走小模型；离线任务全走 Batch API 拿折扣错峰；再不够就申请提额或多 Key 池轮转。同时把 429 率、各 Key 的 TPM 使用率做成监控，打到 80% 就预警，而不是等用户报障。整套限流会做进网关的横切层，业务方无感。"（约 280 字）

**追问：**

1. **为什么 TPM 比 RPM 更容易成瓶颈？**
   答：单请求动辄几千 Token，请求数不高但"流量体积"巨大：10 QPS × 2.5K Token 就是 150 万 TPM。所以限流器要以 Token 为单位预扣，而不是只数请求数。
2. **语义缓存会不会答非所问？**
   答：会，这是命中率与风险的权衡。做法：设较高相似度阈值、只缓存确定性知识类问答、命中后标注"参考回答"、加 TTL；生成类/个性化内容不进缓存（详见 L8.2）。
3. **流式响应连到一半断了，用户看到一半内容，怎么办？**
   答：前端以 [DONE] 为正常结束标志，没收到就是中断；已收内容保留并给重试入口；要续传就把已生成部分作为 assistant 前缀回填再请求"继续"；服务端可用会话缓存支持断点续发；小文本直接重生成也可接受。
4. **适配层最大的坑是什么？**
   答：抽象泄漏——为用某家独有功能把它的参数塞进统一接口，其他厂商实现不了。原则：统一接口最小完备，厂商特有参数走 extensions 透传，差异终结在 Adapter，业务层零感知。

## 2.3 推理性能概念（懂原理才能定超时和容量）

### 2.3.1 一次生成的两阶段：Prefill → Decode

**是什么（通俗类比）：**

模型生成 = "先通读题（Prefill），再一字一字写答案（Decode）"。通读是可以并行的高速阅读；写答案因为每个字都依赖上一个字，只能串行——这就是**为什么生成是逐 Token 的**：第 N+1 个 Token 的概率分布，要等第 N 个 Token 落定才能算。

```text
以"Prompt 1000 Token，生成 200 Token"为例：

  Prompt: [t1 t2 t3 ··· t1000]
     │
     ▼  ① Prefill 预填充：一次性并行处理整个 Prompt（读题）
  ┌────────────────────────────────────┐
  │ 计算密集，耗时与 Prompt 长度成正比        │
  │ 副产品：KV Cache（题目要点的"便签"）      │
  │ 决定指标：TTFT（首 Token 延迟）           │
  └────────────────────────────────────┘
     │ 吐出第 1 个 Token（用户开始看到字）
     ▼  ② Decode 解码：一个一个往外蹦（写答案）
  [t1001]→[t1002]→[t1003]→ ··· →[t1200]
   串行、访存密集：每个新 Token 要"回看"全部前文（查 KV Cache）
   决定指标：tokens-per-sec（生成速度）

  端到端延迟 ≈ TTFT（Prefill 决定）+ 生成 Token 数 ÷ 生成速度（Decode 决定）
```

**为什么 Prompt 越长越慢：** Prefill 计算量与 Prompt 长度成正比 → TTFT 变长；同时每步 Decode 要回看更多前文，生成速度也略降。所以 128K 长上下文请求的首字延迟远高于 1K 请求——**超时和 SLA 必须按 Prompt 长度分档设定**。

**对系统设计的意义（贯穿主线落地）：**
- 定超时：TTFT 分布 → 定 idle 超时；总时长 = TTFT + Token 数 ÷ 速度 → 定总预算（呼应 2.2.1）
- 定体验：TTFT 高的场景（长上下文/Reasoning）前端要有"思考中"状态设计
- 定优化方向：砍 Prompt 长度（L3 压缩）直接降 TTFT；限制 Max Tokens 直接封顶总时长

### 2.3.2 流式为什么改善体验但不降成本

**结论先行：** 流式只是把"全部生成完再给"改成"边生成边给"，**总计算量一个 Token 都没少**——成本不变、总时长不变，变的是**感知延迟**：用户从"白屏 20 秒"变成"1 秒看到第一个字，内容渐次出现"。人对响应的手感几乎全由 TTFT 决定。

| 优化手段 | 降感知延迟 | 降真实成本 |
|---------|:--:|:--:|
| 流式输出 | ✔ | ✘ |
| 缩短 Prompt（压缩/裁剪） | ✔（TTFT 降） | ✔ |
| 限制 Max Tokens | ✔ | ✔ |
| 模型级联（简单任务小模型） | ✔ | ✔ |
| Prompt Caching | ✔（TTFT 降） | ✔（折扣） |

（面试易错点：答"流式省成本"是常见减分项——省的是用户耐心，不是钱。）

### 2.3.3 KV Cache 与 PagedAttention（vLLM）

**KV Cache 是什么（通俗类比）：**

Decode 每生成一个新 Token，都要"回看"前面所有 Token 的注意力中间结果（Key/Value）。如果每步都重算全部前文，代价不可接受——所以把算过的存起来复用，这就是 **KV Cache**：Prefill 阶段顺手把整份 Prompt 的 K/V 算好存进显存，之后每步只算增量。

**它的问题：** KV Cache 按请求长度线性吃显存，且各请求长度不一 → 传统"连续大块分配"产生大量碎片，显存利用率低、并发上不去。

**PagedAttention（vLLM 的核心创新，概念级）：** 借操作系统"分页管理内存"的思路管理 KV Cache——切成固定小块按需分配、逻辑连续物理离散。效果：碎片大幅减少、同卡并发（吞吐）显著提升，还能让多请求共享相同前缀的缓存块。**面试一句话：vLLM 用分页思路管 KV Cache 显存，把推理吞吐提了一个档次——这是自部署选它的核心理由。**

### 2.3.4 Prompt Caching（前缀缓存）

**是什么（通俗类比）：**

Prompt Caching = "通读过的题不再重读"。如果请求每次都以**相同的固定前缀**开头（system prompt + 工具定义 + Few-Shot），厂商可以把这段前缀的 KV Cache 保留复用：下次命中前缀，Prefill 只需算"变化的后缀"。

**好处（两重）：**
1. **计费折扣**：命中缓存的输入 Token 按折扣价计费（常见 5 折甚至更低，各厂商不同）——固定前缀占比越高省得越多
2. **TTFT 下降**：Prefill 计算量变小，首字更快

**工程做法（把 Prompt 设计成"缓存友好"）：**

```text
缓存友好：[固定：system + 工具定义 + Few-Shot] + [变化：检索结果 + 历史 + 用户输入]
             ↑ 前缀一字不改，稳定命中                 ↑ 动态内容全放后面

缓存杀手：把时间戳/随机 ID/个性化字段混进前缀 → 每次全量 miss
```

- 注意各厂商的命中门槛（最小前缀长度，如 1024 Token 起）与缓存 TTL（闲置过期）
- 与 Few-Shot 动态选取有天然矛盾（示例一变前缀就变）——高命中场景宁可固定示例集（L3 的权衡题）
- 自部署场景对应 vLLM 的 prefix caching，思路同源

### 2.3.5 Speculative Decoding（一句话）

**投机采样，一句话：** 小模型先"一口气猜"出后面 N 个 Token，大模型一次并行验证，猜对整段采纳、猜错从错点重算——不改变输出质量的前提下，Decode 阶段一次吐多个 Token，显著提速。

### 🎤 面试这样答：LLM 调用的超时怎么定？和普通 RPC 有什么不同？

> "最大的不同是延迟结构。普通 RPC 延迟毫秒级、近似常量，一个读超时就够；LLM 调用的延迟由两段构成：TTFT 由 Prefill 决定，主要受 Prompt 长度影响；之后是 Decode 逐 Token 生成，受输出长度和生成速度影响，从秒级到分钟级方差极大。所以我分层设置：连接超时秒级快速失败；非流式读超时按 Prompt 长度分档，参考线上 P99 生成时长加 buffer——常规对话 60 秒，长上下文或 Reasoning 模型单独放宽；流式则把读超时退化成 idle 超时，只约束两个 chunk 之间的间隔，同时设总时长预算防涓涓细流。另外上游网关超时必须大于下游，否则下游还在生成、上游已经超时报错。这套认知也直接决定容量评估：按单请求 Token 体量算 TPM，而不是 QPS 思维。本质上，是先把'模型即组件'的延迟模型搞清楚，超时和容量才有的放矢。"（约 300 字）

**追问：**

1. **用户抱怨回答慢，你怎么排查？**
   答：先拆延迟三段：网关耗时、TTFT、生成速度 =（总时长 − TTFT）÷ Token 数。TTFT 高 → 看 Prompt 长度、前缀缓存命中率、服务端负载；生成速度低 → 换更快模型档位或限制输出长度；都不高 → 查链路上的排队和串行调用。
2. **Prompt Caching 怎么设计才能真省钱？**
   答：结构上"固定前缀 + 动态后缀"：system、工具定义、固定示例集放最前且一字不改；检索结果、历史、用户输入放后面。严防时间戳、随机数、个性化字段掺进前缀导致全量 miss。上线后监控缓存命中率，作为成本优化核心指标。
3. **KV Cache 和 Prompt Caching 是一回事吗？**
   答：不是。KV Cache 是推理引擎内部机制，服务单次请求的 Decode 阶段；Prompt Caching 是跨请求复用固定前缀的 KV，是产品化能力，带计费折扣。自部署时 vLLM 的 prefix caching 提供类似能力。
4. **为什么说流式不省成本？那还值不值得做？**
   答：总计算量不变，省的是感知延迟——用户 1 秒看到首字，体感快数倍，交互产品几乎必做；但降账单要靠缓存、级联、压缩、Batch 这些手段。

## 进阶篇：高级岗深挖区（把"会用 API"和"懂组件"分开的地方）

```text

第一层  "Token 是什么？"                       ──▶ 淘汰没入门的
第二层  "7B 模型 32K 上下文 KV Cache 占多少？" ──▶ 淘汰只会调 API 的
第三层  "所以长上下文为什么贵？怎么压？"        ──▶ 淘汰没算过账的

```

#### A.1 二层追问链：Tokenizer 与 BPE

> **追问：** "你说 Token 是最小零件，tokenizer 是怎么把文字拆成 Token 的？"
>
> **答：** 主流方案是 BPE（Byte Pair Encoding，字节对编码），概念级三步：① 把语料拆到最碎（单字符甚至单字节）；② 统计哪两个**相邻碎片最常一起出现**（比如 "th"+"e" 出现了 900 万次），把它们合并成一个新 Token 记进词表；③ 重复②几千轮，词表就从"字母级"长成"常用词整存、生僻词碎片拼"的形态。推理分词就是拿这张练好的词表做贪心最长匹配。

> **再追问：** "那不同模型的 tokenizer 为什么不可比？"
>
> **答：** 因为**词表是各家自己训练的**：语料配比、合并轮数、词表大小（3 万 / 12 万 / 25 万）全不同。同一句中文，A 模型拆 40 个 Token、B 模型可能拆到 90——**差 2 倍很常见**。Token 数不是文本的物理属性，是"文本 × 特定词表"的属性，换词表就换读数。

> **再追问：** "这对成本估算和上下文预算意味着什么？"
>
> **答：** 一切按目标模型实测：① 成本不能拿 A 模型的 token 数套 B 模型单价；② 窗口预算同理，"这句中文多少 Token"跨模型没有统一答案；③ 换模型 = 重测 tokens/字 这个基础系数，容量、成本、限流三本账全部重算。落地做法：选型阶段用真实业务语料跑 count_tokens，把"每千字 Token 数"当硬性选型输入，不看宣传页拍脑袋。

#### A.2 二层追问链：上下文窗口与 lost in the middle

> **追问：** "窗口 128K，是不是塞到 100K 也没问题？"
>
> **答：** 不是。有个经典现象叫 **lost in the middle**：长上下文里模型的信息召回呈"U 形"——开头和结尾召回好，**中间部分明显差**。多文档 QA 实验里，同一个关键事实放开头能答对、挪到中间准确率能掉 20 个点。模型"看得见"全部 Token，但注意力分配不均——窗口是内存，注意力才是真正的读取带宽。

> **再追问：** "这对 RAG 的上下文排布有什么实际影响？"
>
> **答：** 排布原则变成**两头放最重要的，中间放可牺牲的**：system 指令和关键约束放开头；高置信检索块放开头或结尾；低置信、兜底块放中间；用户问题这类要被反复参照的内容，惯例"开头一次、结尾再一次"（首尾夹击）。同时 top-k 不是越大越好——塞 20 个块把关键块挤到中间，不如精排后塞 8 个。

> **再追问：** "所以 128K 窗口为什么不能当 128K 用？"
>
> **答：** 标称窗口 ≠ 有效窗口，中间隔着四个折扣：① **召回折扣**——U 形衰减，中间内容约等于半失效；② **成本折扣**——输入按 Token 线性计费，多数问题 10K 检索质量已饱和，多塞的 90K 是花钱买噪声；③ **延迟折扣**——Prefill 随长度线性涨，100K 输入 TTFT 可能十几秒；④ **稳定性折扣**——超长输入下指令遵循和格式稳定性劣化。工程上的有效窗口 = min(标称窗口， 检索质量饱和点， 成本预算， SLA 允许的 TTFT)，多数 RAG 场景工作点定在 8K~32K。

#### A.3 二层追问链：Temperature=0 与确定性工程

> **追问：** "Temperature 到底在控制什么？"
>
> **答：** 概念级三步：模型每步给全词表每个 Token 打原始分（logits）→ 经 softmax 变成概率分布（Temperature 在这一步起作用：调低高分更突出、调高分布更平）→ 按分布**抽样**一个 Token 作为输出。Temp=0 退化成"近似总选最高分"。

> **再追问：** "那 Temp=0 为什么还不可复现？"
>
> **答：** 三个来源：① **浮点非结合性**——GPU 并行归约的加法分组顺序不固定，(a+b)+c ≠ a+(b+c) 的浮点误差让 logits 有微小抖动，两个 Token 并列第一时谁胜出就可能翻转；② **动态批处理**——服务端把你的请求和别人的拼批跑，批次构成不同、数值路径不同；③ **MoE 路由抖动**——专家路由的并行竞争在边界上可能选不同专家。自回归是几百步连乘，每步亿分之一的扰动都会放大成完全不同的输出。

> **再追问：** "业务就是要确定性，工程上怎么解？"
>
> **答：** 不跟采样参数较劲，三层保障：① **锁可控变量**——seed（支持的厂商）+ Temp=0 + 固定 Prompt 模板版本，一致性提到 99%+ 但不当合同；② **输出校验**——结构化输出 + Schema 校验，不合格带退避重试、次数封顶；③ **架构去依赖**——关键决策不押单次采样：规则复核、多路投票、或把这段逻辑从 LLM 挪回确定性代码。一句话：**确定性是系统属性，不是参数属性**。

#### A.4 二层追问链：KV Cache 显存账

> **追问：** "为什么需要 KV Cache？"
>
> **答：** Attention 的机制是"每个新 Token 要和**全部历史** Token 算相关性"。生成第 1000 个 Token 时要回看前 999 个——如果不缓存，每步都全量重算前文的 Key/Value 投影，总计算量是平方级。KV Cache 把每层算过的 K/V 存进显存复用，每步只算新 Token 的增量——**用显存换计算**。

> **再追问：** "显存占用怎么算？7B 模型 32K 上下文占多少？"
>
> **答：** 一条乘法 + 一个数字示例：

```text
KV Cache 显存 = 2(K和V) × 层数 × KV头数 × 每头维度 × 序列长度 × 每元素字节

以经典 7B（Llama-2-7B 结构：32 层 / 32 KV 头 / head_dim 128 / FP16=2 字节）：

  每 Token   ：2 × 32 × 32 × 128 × 2B ──────────────▶  512 KB
  32K 上下文 ：512KB × 32768 ──────────────────────▶   16 GB

  ┌──────────────── 单张 24GB 卡的账 ─────────────────┐
  │ 模型权重 7B × 2B ──────────────  14 GB            │
  │ KV Cache（32K × 1 个请求）─────  16 GB            │
  │ 合计 30 GB ✗ 放不下（还没算激活值和第二个请求）      │
  └───────────────────────────────────────────────────┘

  同结构上 GQA（KV 头 32→8，Llama-3 风格）：512KB → 128KB / Token
  32K 上下文只占 4GB ✔ —— 这就是长上下文模型必配 GQA 的原因
```

> **再追问：** "这笔账解释了什么？"
>
> **答：** 三个解释：① **长上下文为什么贵**——成本不只是计算，KV Cache 显存随上下文线性涨，32K 单请求就能吃掉一张卡，供应商的长输入溢价里有真实显存成本；② **并发为什么受限**——卡上显存 = 权重 + 所有在途请求的 KV Cache，cache 越大、并发越少、吞吐越低；③ **PagedAttention 省在哪**——它不省"每 Token 512KB"的物理账，省的是**分配方式**：传统按最大长度预留连续大块，碎片浪费 60~80%；vLLM 学操作系统分页，小块按需分配，浪费压到 <4%，同卡并发翻倍以上——这是自部署默认选 vLLM 的核心理由。

#### A.5 二层追问链：429 与限流参数

> **追问：** "服务端为什么要限我？"
>
> **答：** 因为 GPU 是**共享池**。推理集群每张卡同时服务成百上千个请求（连续批处理），你的配额本质是"在共享池里买下的显存+算力份额"。按 Token 限比按请求数限更"按资源说话"——10K Token 的请求占用的 Prefill 计算和 KV 显存就是 1K 请求的 10 倍。限流保护的是池子里所有人，不只是防你一家。

> **再追问：** "客户端三件套（信号量/令牌桶/排队）参数怎么定？按 RPM 还是 TPM？"
>
> **答：** **按更紧的那把尺子**：分别按 RPM 和 TPM 算出各自意义上的容量上限，取小者做总闸。信号量（并发上限）≈ 更紧上限 ÷ 60 × 平均请求时长；令牌桶按配额的 80% 速率回填（留 buffer 给重试和突发）；队列容量按"可接受的排队延迟 × 排队速率"倒推，满了快速失败别硬排。另外单请求维度要单独设闸：一个 100K Token 的请求能瞬间打穿令牌桶，超长请求走独立通道。

> **再追问：** "多 Key 池轮转的风险呢？"
>
> **答：** 三个：① **条款风险**——多数厂商禁止同主体多账号规避限流，轻则封 Key 重则封主体；上量先走官方提额，多 Key 定位为故障转移而不是容量翻倍器；② **数据一致性**——不同 Key 可能路由到不同版本/区域，同一会话中途换 Key 行为会突变，轮转粒度按"会话"不按"请求"；③ **可观测性稀释**——用量和错误率散在多个 Key 上，监控必须按池聚合，否则 429 前兆被平均掉。

### B. 生产级 Case Study ×2（STAR-L，含数字）

> 高级岗面试的杀手锏不是背方案，是**讲自己翻过的车**。以下两个故事模板，替换成你项目里的真实数字即可使用。
>
> STAR-L 讲述要点：Situation/Task 各一句话带过，把时间留给 Action 里的决策与数字，Result 必须量化，Learning 必须是"如果重来会怎么做"级别的沉淀。每个数字都要经得起"这个数怎么测出来的"的追问。

#### B.1 Case：一次大促活动的 LLM 容量保障

- **Situation：** 电商大促（类双 11），AI 导购客服预计流量为日常峰值的 5 倍（日常峰值 20 QPS）。
- **Task：** 大促全程（含 0 点峰值小时）AI 链路零事故，TTFT P95 < 5s。
- **Action：**
  1. **容量预估（先算账再谈方案）：** 峰值预估 100 QPS；单请求 = system+RAG 上下文约 3K in + 0.5K out ≈ 3.5K Token → TPM 需求 = 100 × 60 × 3.5K = **2100 万**；可用配额（主 Key 200 万 + 备用 3×100 万）= 500 万——**缺口 4 倍**，注定走组合拳而不是硬扛。
  2. **压测（提前两周，用线上真实 Token 分布回放）发现三个没预料到的问题：**
     - **embedding 接口先打挂**：每次问答都实时做 query embedding（RAG 检索），embedding QPS ≈ LLM QPS。压到 40 QPS 时 embedding 429 率冲到 30%——它的配额口径比 LLM 紧得多，且是最早饱和的一环。修复：问题向量缓存（精确 hash + 语义双层）、批量接口、本地 BGE 兜底，把云端 embedding 调用量压掉 60%。
     - **SSE 长连接占用**：100 QPS × 平均 30s 生成时长 = **3000 条并发长连接**，网关连接池上限 4096，叠加普通 API 流量几乎打满。修复：连接池扩到 8192 + 收紧 Max Tokens 把平均生成压到 20s（并发降到 2000）+ 前置排队削峰（队列 500 上限，满则快速失败走兜底话术）。
     - **TTFT 劣化**：自己配额没打满，但高并发下服务端排队，TTFT 从 1.2s 涨到 8s——**超时和 SLA 不能只按自家配额推算**，要按"共享池饱和"建模。
  3. **多级预案（按指标阈值自动触发，不靠人盯）：**

     | 级别 | 触发条件 | 动作 |
     |------|---------|------|
     | L1 缓存 | 大促规则/价格类高频问题 | 预热 2000 条高频问答语义缓存，目标命中 20%+ |
     | L2 降级 | TPM 使用率 >80% 或队列深度 >300 | 切小模型档位 + top-k 8→4 + 关闭深度推理 |
     | L3 扩容 | 429 率 >1% 持续 5 分钟 | Key 池 4→8 故障转移 + 停全部离线 Batch 让路 |

- **Result：** 实际峰值 82 QPS；语义缓存命中 22%；429 率 0.3%；TTFT P95 2.8s；零事故；总成本比线性外推预估低 18%（缓存 + 级联红利）。
- **Learning：** ① 容量评估要算**整条链路**的配额（LLM + embedding + rerank），embedding 是最常被漏掉的暗坑；② SSE 场景的第二本容量账是 **并发 = QPS × 平均生成时长**，和 TPM 一样会先打满；③ 压测必须用真实 Token 分布——拿短样本压出来的容量是虚的。

#### B.2 Case：多模型网关迁移事故

- **Situation：** 从单供应商迁移到多模型网关（动机：成本 + 供应商可用性风险），涉及 3 家模型，灰度切流 5%→20%→100%。
- **Task：** 业务代码零改动完成迁移，灰度期问题不外溢到用户。

```text
                     业务代码（只依赖统一 ChatRequest / StreamEvent）
                                       │
                       ┌───────────────▼────────────────┐
                       │            模型网关             │
                       │  灰度路由：user_id hash 5%→20%  │
                       │  双跑比对：计量/延迟/错误率       │
                       └──┬──────────┬──────────┬───────┘
                  ┌───────▼──┐ ┌─────▼────┐ ┌───▼──────┐
                  │ Adapter A│ │ Adapter B│ │ Adapter C│
                  │(OpenAI系)│ │(原生协议) │ │(兼容模式) │
                  └─────┬────┘ └────┬─────┘ └───┬──────┘
                        │ 归一化：finish_reason 枚举 / usage / 流结束标志
                        ▼
          ┌────────────────────────────┐   ┌────────────────────┐
          │ 契约测试（CI 门禁）          │   │ 回放用例库          │
          │ 标准请求 → 真实响应回放      │◀──│ 每家录制+脱敏        │
          │ → 断言统一结构与计量完整性    │   │ 新供应商接入必过     │
          └────────────────────────────┘   └────────────────────┘
```

- **Action（灰度期踩的三个坑，全是"静默错"——不报错、只错数据）：**
  1. **JSON 字段差异**：三家 finish_reason 枚举不同（"stop" / "end_turn" / "maxlength"），上游只 switch 了 "stop" 和 "length"——B 家正常收尾被误判"异常中断"，触发无意义重试，灰度组成本虚高 15%。另有一家流式 usage 要显式传 stream_options 才返回，没传 → 计量缺失，成本报表漏记约 30%。
  2. **思考 Token 不可见**：B 家 reasoning 模型不返回 reasoning_content，前端"思考中"状态等一个永远不来的字段，一直不消失；且思考 Token 计费混在 completion_tokens 里 → 成本归因把"思考"记成"正文"，模型间成本对比失真。
  3. **SSE 格式差异**：B 家不用 `data: [DONE]` 而用 `event: done` 事件类型收尾；中间某代理层吃掉事件间空行，导致事件粘连解析错乱。
- **修复：** 适配层统一三件事——枚举归一化（end_turn→stop、maxlength→length 映射表）、计量兜底（usage 缺失时本地 tokenizer 估算并打"估算"标记）、流结束统一为内部 EndOfStream 事件（[DONE] 与 event:done 都映射过来）。
- **防回归（契约测试）：** 每家 Adapter 过一组**回放用例**——标准请求打真实服务，原始响应录制脱敏入库；CI 回放这些响应，断言归一化后的统一结构：字段齐全、枚举合法、结束标志存在、usage 完整。新供应商接入 = 先录契约集再放行；厂商 API 变更 = 契约集一跑即知。
- **Result：** 全量后解析类故障归零；新供应商接入周期从 2 周缩到 3 天；灰度期双跑比对把计量差异定位到天级。
- **Learning：** 适配层的 bug 几乎都是**静默错**，契约测试是把静默错变成显性失败的低成本手段；"灰度期双跑比对计量"是发现成本归因问题的唯一途径——不上线对比，永远发现不了。

### C. 成本与容量口算题（30 秒口算演示）

高级岗面试官爱出"现场算一下"。三道真实高频题，每题给 30 秒口算路径。**口算的意义不是精确，是量级正确**——量级错，方案就错。

#### C.1 月成本与缓存命中率

**题：** 日均 10 万次调用，平均 in 800 / out 400 Token，单价 $3 / $15 每百万 Token，月成本多少？语义缓存命中 30% 后实际多少？

```text
30 秒口算：
① 日 Token 量：in  10万 × 800 = 8000 万；out 10万 × 400 = 4000 万
② 日成本    ：in  80M × $3/M = $240；out 40M × $15/M = $600 → $840/日
③ 月成本    ：$840 × 30 ≈ $25,200
④ 命中 30%（命中部分完全不调模型）→ × 0.7 ≈ $17,640，月省 $7,560
记忆点：日均 10 万次 × 1.2K Token = 1.2 亿 Token/日 ≈ 单价($/M) × 120/日
```

**追问预备：** 命中部分为什么按 0 算？语义缓存命中直接返回存量答案，不发生模型调用——注意与 Prompt Caching 的"折扣"区分：后者仍调用、只打折（见 C.3）。

#### C.2 TPM 配额 → QPS 上限与 headroom

**题：** 配额 100 万 TPM，平均单请求 1200 Token，理论上限 QPS 多少？该按多少规划容量？

```text
30 秒口算：
① 每分钟请求数：100万 ÷ 1200 ≈ 833 RPM
② 换算 QPS  ：833 ÷ 60 ≈ 13.9 QPS（理论上限）
③ 留 headroom：× 0.8 → 11 QPS 作为容量红线
④ 长尾修正：平均值会被长请求打穿——若 P99 单请求 5K Token 且占比不低，
   保守上限按 P99 算：100万 ÷ 60 ÷ 5000 ≈ 3.3 QPS
口诀：配额 ÷ 单耗 ÷ 60 = 上限；上限 × 0.8 = 红线
```

**追问预备：** 为什么留 20%？重试流量、突发毛刺、多环境共享配额都要吃 buffer——headroom 不足时，一次重试风暴就能把系统推进雪崩。

#### C.3 Prompt Caching 收益估算

**题：** system prompt 固定 3K Token，日 10 万次调用，缓存命中价为原价 10%，月省多少？

```text
30 秒口算：
① 前缀日 Token：3000 × 10万 = 3 亿 Token/日（固定前缀，全部可命中）
② 不缓存成本 ：3 亿 = 300 个"百万" × $3 = $900/日
③ 缓存价 1 折 ：$90/日
④ 月省       ：(900 − 90) × 30 ≈ $24,300
记忆点：3K 固定前缀 × 10 万次/日 ≈ 每天 $900 的"纯前缀税"，缓存砍掉九成
```

**追问预备：** ① 实际命中不是 100%——有最小前缀门槛（常见 1024 Token 起）和 TTL 闲置过期，估算按 80~90% 命中再打折；② 检索结果、用户输入等动态后缀不在缓存范围，本题只算前缀部分。

### D. 高级视野

#### D.1 同题异答：API 调用者 vs 组件理解者

同一个问题，两种人的回答对照（左列及格，右列资深）：

| 面试官的问题 | API 调用者（及格线） | 组件理解者（资深线） |
|------------|-------------------|---------------------|
| 超时为什么要分档？ | "生成慢，超时设长点" | "延迟 = TTFT（随 Prompt 长线性涨）+ N÷速度，分布长尾——按 Prompt 分档 + 流式 idle 超时" |
| 为什么会 429？ | "调太快了，加退避" | "GPU 是共享池，TPM 是买下的资源份额——先算缺口，再组合拳：缓存/级联/Batch/提额" |
| 账单为什么比预估高？ | "Token 比想的多吧" | "查三处：tokenizer 实测系数、思考 Token 是否计费、重试放大（重试预算失控=翻倍）" |
| 换模型要注意什么？ | "改 base_url 和 key" | "词表差异→重测 token 系数；行为差异→回归评测集；格式差异→契约测试+灰度双跑" |
| 128K 窗口香不香？ | "香，能塞好多文档" | "有效窗口 < 标称：U 形召回衰减 + 成本线性涨 + TTFT 变长，工作点定在质量饱和处" |

区别的本质：**调用者的答案主语是"API"，理解者的答案主语是"系统里的资源与机制"**。

#### D.2 供应商锁定：什么时候抽象值得，什么时候是浪费

"只有一家供应商就别建适配层"（YAGNI）——**对一半**。正确姿势是**建轻的**：

- **值得（轻抽象）：** 接口对齐 OpenAI 风格（messages / 流式事件 / 工具调用已是事实标准），业务代码只面向这套形态写。成本极低（多数厂商本就有兼容模式），却锁住了"随时能换"的期权。
- **浪费（重抽象）：** 只有一家时就把全功能网关建齐——路由/级联/多 Key 池/计量归一提前全上。维护成本超过期权价值，而且**没被第二家供应商检验过的抽象，大概率是错的抽象**（你在抽象想象中的差异）。
- **升级触发信号：** 第二家供应商真实出现（成本/可用性/能力诉求）→ 再把网关做重，并用契约测试保迁移（B.2 的路径）。
- 一句话：**第一家企业就按事实标准写代码（轻），第二家出现才建重网关——抽象深度跟着供应商数量走。**

#### D.3 面试官心理：深挖 API 细节在筛什么

面试官连环追问词表、KV Cache 显存、限流参数，不是刁难，是在做一次低成本的区分：**这人有没有真上过生产**。

- 只看过文档的人，答案是"文档语言"：参数是什么、建议值是什么——干净，但没有数字、没有事故、没有取舍；
- 上过生产的人，答案自带"生产指纹"：说超时会带自己线上的 P99；说限流会带自己算过的 TPM 缺口；说不可复现会讲自己怎么被测试环境偶发失败坑过一周；
- 深挖链的价值在于**无法临时编造**：第二层（数字）和第三层（取舍）只能来自真实经历，背题者第一层之后就会露馅。

所以被深挖时最好的策略不是防守，是主动给数字、给翻车故事、给"如果重来"——每个数字都在告诉面试官：这道题我是在生产环境学的，不是在文档里。

### 🎤 面试这样答：128K 窗口为什么不能当 128K 用？

> "因为标称窗口和有效窗口之间隔着四层折扣。第一，召回衰减：lost in the middle 现象——长上下文的信息召回呈 U 形，中间部分明显差，关键内容放中间约等于半失效，所以 RAG 排布要首尾放高价值内容。第二，成本：输入按 Token 线性计费，多数问题 10K 检索质量就饱和了，多塞的 90K 是花钱买噪声。第三，延迟：Prefill 计算量随长度线性涨，100K 输入的 TTFT 可能十几秒，交互场景不可接受。第四，稳定性：超长输入下指令遵循和格式稳定性都会劣化。所以我把有效窗口当工程量来定：取标称窗口、检索质量饱和点、成本预算、SLA 允许的 TTFT 四者的最小值——实际多数 RAG 场景工作点定在 8K 到 32K，128K 只留给真正需要整篇长文档理解的任务，而且要先跑过长上下文召回评测才敢上。"（约 310 字）

**追问：**

1. **lost in the middle 怎么发现、怎么缓解？**
   答：发现靠"关键事实位置翻转"评测——同一组多文档 QA，把关键块分别放开头/中间/结尾跑对比，准确率差 20 个点就是中招。缓解：精排后控 top-k、关键内容首尾放置、超长输入改 map-reduce 分段摘要再汇总。
2. **你们线上工作点定在多少、怎么定的？**
   答：按检索质量饱和曲线定的——top-k 从 4 加到 12，回答质量在 8 附近饱和，结合成本与 TTFT 预算定在约 16K 输入；这个数随模型升级每季度重测一次。

### 🎤 面试这样答：7B 模型 32K 上下文，KV Cache 占多少显存？

> "可以口算：KV Cache 等于 2 乘层数乘 KV 头数乘每头维度乘序列长度乘每元素字节。经典 7B 结构 32 层、32 个 KV 头、head_dim 128、FP16 两字节——先算每 Token：2×32×32×128×2 字节，正好 512KB；32K 上下文就是 512KB×32768，约 16GB。也就是说光 KV Cache 就超过了模型权重本身（7B×2 字节 = 14GB），一张 24GB 卡连权重加一个 32K 请求都放不下。这笔账解释三件事：长上下文为什么贵——显存是真实成本；并发为什么受限——显存要分给所有在途请求；GQA 为什么是长上下文标配——KV 头从 32 砍到 8，每 Token 从 512KB 降到 128KB，32K 只占 4GB。至于 PagedAttention，它省的是另一笔账：不改变每 Token 的物理占用，改变分配方式——分页管理把碎片浪费从六七成压到个位数，同卡并发翻倍，这是自部署选 vLLM 的核心理由。"（约 330 字）

**追问：**

1. **KV Cache 量化（FP16→INT8）呢？**
   答：每元素 2 字节→1 字节，占用直接减半，代价微小精度损失；与 GQA 是乘法关系——一个砍头数、一个砍位宽，长上下文场景常叠加使用。
2. **为什么说 PagedAttention 提的是吞吐不是延迟？**
   答：它解决"多请求分显存"的碎片问题，同卡塞下更多并发 → 吞吐涨；单请求该算的一步不少，TTFT 与生成速度基本不变（跨请求共享前缀块时另说）。
