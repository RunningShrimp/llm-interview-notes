## 4.1 文档解析管线

### 4.1.1 知识库全景流程

**是什么（通俗类比）：**

知识库建设是一条"数据加工流水线"：原材料（PDF/Word/Markdown/网页）进厂，经解析、清洗、切块、贴标（元数据）、向量化，最终变成可检索的"标准件"入库。本质上就是一条 ETL 管道——Extract（解析）→ Transform（清洗/切块/元数据）→ Load（向量化入库）。

**全景流程图（白板必画）：**

```text
┌──────────┐  ┌─────────┐  ┌──────────┐  ┌──────────┐  ┌──────────┐
│ Raw Data │─▶│ Parsing │─▶│ Cleaning │─▶│ Chunking │─▶│ Metadata │
└──────────┘  └─────────┘  └──────────┘  └──────────┘  └──────────┘
 PDF/Word/     解析器选型     去重(指纹/    四种策略       来源/时间/
 Markdown/     版面分析      SimHash)     size+overlap   权限/版本/
 HTML/DB/      表格·多栏     PII 脱敏     Parent-Child   实体/分类
 Wiki/代码     统一转 MD     保留溯源                    标签注入
                                 │
                                 ▼
                        ┌────────────┐  ┌──────────┐
                        │ Embedding  │▶ │  Index   │
                        │ (批量/限流) │  │ 向量库+   │
                        └────────────┘  │ 标量索引  │
                                        └──────────┘
```

**为什么这条链子重要：**

错误会**向后放大**——解析把表格串了行，切块必然切碎语义，向量必然偏移；而入库后发现问题的修复成本是入库前的十倍（全链路重刷）。所以质量校验要前置到每个环节，而不是入库后才发现。

### 4.1.2 解析器选型矩阵

**是什么（通俗类比）：**

解析器选型像"翻译工具分级"：日常文本用快译（PyMuPDF），学术论文请专业译者（Marker/MinerU），模糊扫描件靠 OCR 老师傅（PaddleOCR），看不懂的图表只能请顶级专家（多模态大模型）。没有全能选手，只有**按文档类型动态路由**。

**怎么做（选型矩阵）：**

| 维度 | PyMuPDF | Marker / MinerU | OCR（PaddleOCR） | 多模态大模型（GPT-4o / Qwen-VL） |
|------|---------|-----------------|------------------|--------------------------------|
| 速度 | 极快（毫秒级/页） | 中（秒级/页，需 GPU） | 中慢（CPU 更慢） | 慢（数秒/页） |
| 精度 | 数字原生 PDF 近乎无损 | 高（版面分析+表格还原） | 依赖图像质量 | 最高（理解语义与图表） |
| 成本 | 免费（本地库） | 本地 GPU 可控 | 本地可跑 | 按 token/页计费，**贵** |
| 表格 | 弱（结构基本丢失） | **强**（转 Markdown 表格） | 弱（需表格专项识别） | 强（能还原合并单元格语义） |
| 公式/学术 | 弱 | **强**（这是主场） | 弱 | 中强 |
| 适用 | 数字原生 PDF、纯文本 | 论文、报告、结构化 PDF | 扫描件、图片型 PDF | 复杂版式、图文混排、图表推理 |
| 失效场景 | 扫描件（无文本层） | 极复杂跨页表格 | 手写、模糊、透视畸变 | 预算受限、超大规模批处理 |

**生产三原则：**

1. **先探测、后路由**：判断有无文本层（每页字符数 < 阈值 → 扫描件走 OCR）、是否含表格/公式（版面分析探测）——动态选择解析器，而不是一把梭
2. **Markdown 作统一中间表示**：所有解析器输出统一转 Markdown（标题层级、表格、代码块都带语义标记），下游切块只需面对一种格式
3. **成本分层**：90% 简单文档走 PyMuPDF（快且免费），10% 难文档走 MinerU/多模态——与"动态模型路由"同款思想

**解析器决策树：**

```text
                    收到一份文档
                         │
             有文本层？(提取字符数/页 > 阈值)
                ┌────────┴────────┐
               是                 否（扫描件/图片型）
                │                  │
        版面复杂？         图像清晰、版式规整？
       ┌───────┴───────┐      ┌────┴─────┐
     简单             复杂   是           否（手写/复杂图表）
       │               │      │            │
    PyMuPDF        Marker/ PaddleOCR   多模态大模型
  （毫秒级）       MinerU  （本地批量） （贵而准，限量）
       │               │      │            │
       └───────┬───────┴──────┴────────────┘
               ▼
    统一输出：Markdown + 页码/坐标（溯源用）
             进入 Cleaning 阶段
```

### 4.1.3 难点专题：表格、多栏、图片、页眉页脚、扫描件

**为什么难（一句话讲透本质）：**

PDF 不是结构化文档，而是"打印指令的集合"——它只知道**这页哪个坐标画了什么字符**，不知道"这是一个表格""这是两栏正文"。所有难点都归结为一件事：**从二维坐标还原语义结构**。

| 难点 | 典型症状 | 处理方案 |
|------|---------|---------|
| 表格 | 行列串成一行、合并单元格丢失、跨页断裂 | 版面分析定位表格区域 → 表格识别模型 → 转 Markdown/HTML 表格；跨页表格按表头相似度自动拼接 |
| 多栏排版 | 左右栏文字交叉穿插，语义顺序错乱 | 版面分析先分栏 → 各栏独立读取 → 栏间按坐标重排（同栏 y 递增，跨栏 x 分组） |
| 图片 | 图内文字丢失；装饰图变噪声 | 图内文字走 OCR；关键图表（流程图/数据图）送多模态模型生成文字描述，随原文入索引 |
| 页眉页脚 | 每页重复的页码/公司名混进正文，切块后全是噪声 | 坐标过滤（页面上下固定区域）+ 跨页重复模式检测（出现 ≥N 页的相同行判定为页眉页脚） |
| 扫描件 | 无文本层，直接解析为空 | OCR 管线：去畸变/二值化 → 版面分析 → 识别 → 坐标级重排 |

**核心技术组合拳：版面分析 + OCR + 坐标级切分：**

```text
 PDF / 图片
     │
     ▼
┌──────────────┐  输出每个区域的「类型 + 坐标 + 内容」
│ 版面分析模型  │  如 title(…) / text(…) / table(…) / figure(…)
└──────┬───────┘
       ▼
┌──────────────┐  按区域类型分流：
│  分区域处理   │  text → 直接提取；table → 表格识别；
└──────┬───────┘  figure → OCR / 多模态生成描述
       ▼
┌──────────────┐  按「阅读顺序」重排：先分栏、栏内
│  坐标级重排   │  自上而下，再栏间从左到右；
└──────┬───────┘  附上页码 + 区域坐标（溯源用）
       ▼
  结构完整的 Markdown
```

一句话总结：**先分区（版面分析），再分治（文本/表格/图片各走各的），最后按阅读顺序重排（坐标排序）**。

### 4.1.4 清洗与去重

**是什么（通俗类比）：**

洗菜——泥沙（乱码）、烂叶（页眉页脚残留）、Duplicate（同一文件传了三遍）都得先处理，不然一锅汤全毁。清洗是所有环节里最不起眼、但最容易翻车的一环。

**怎么做：**

**清洗清单（正则 + 规则为主，便宜且可控）：**
- 格式归一化：全角/半角统一、Unicode NFKC 规范化、连续空白折叠、控制字符（\x00 类）剔除
- 噪声剔除：页眉页脚残留、目录页、水印文字、"点击下载"类 boilerplate、超长无意义字符串（爬虫伪文本）

**去重三层（概念级，不抠数学）：**

| 层级 | 技术 | 一句话原理 | 适用 |
|------|------|-----------|------|
| 文件级 | 文件指纹（MD5/SHA256） | 内容 hash 一致 = 同一文件 | 重复上传判重、幂等入库 |
| 文档级 | SimHash | 整篇压成一个指纹，**海明距离越小越相似**（局部敏感：小改动只翻转少数位） | 同一文档多版本/转载的近似判重 |
| chunk 级 | MinHash + LSH | 用最小 hash 值集合近似重合比例（Jaccard），LSH 分桶免去两两比较 | 海量段落找重复（模板文、法务条款） |

记忆锚点：**文件指纹查"是不是同一个文件"，SimHash 查"整篇像不像"，MinHash 查"重合比例多大"**。

### 4.1.5 PII 脱敏

**是什么（通俗类比）：**

入库前的"安检门"——身份证号、手机号、病历这些敏感信息一旦变成向量进了库，就会随检索结果泄露给任何能查询的人，而且**向量不可逆，事后无法精准删除**。

**怎么做：**
- **检测**：正则（身份证/手机号/银行卡有固定模式）+ NER 模型（Presidio / 专用识别器）双路并行，取并集
- **处理**：掩码（`张*丰`）、泛化（具体日期→年份）、假名化（张三→PERSON_001，映射表存受控库，审计可反查）
- **顺序红线**：脱敏必须发生在**切块和向量化之前**——先进库就晚了，只能整条删除重灌

### 4.1.6 保留溯源信息（页码/段落号）

**为什么（引用与合规的地基）：**
- 企业级 RAG 答案必须带引用（"依据《员工手册》P12 第 3 段"），没有溯源 = 黑箱 = 不可用
- 出错时能定位到原文修复——溯源是数据质量"可运维"的前提
- 金融/法务场景的合规审计，要求答案可回溯到原始文件的确切位置

**怎么做：**

解析阶段就记录 `doc_id + page_no + para_no`（可选 bbox 坐标），每个 chunk 全程携带：

```text
chunk = {
  "text": "差旅报销需在费用发生后 30 天内提交…",
  "meta": {
    "doc_id": "handbook_v3",       # 来源文件
    "page":   12,                  # 页码
    "para":   3,                   # 段落号
    "bbox":   [100, 200, 500, 260] # 原文区域(前端高亮用,可选)
  }
}
```

前端展示引用时，用 meta 直接定位原文位置并高亮——这也是产品侧"答案可信度"的抓手。

### 🎤 面试这样答：PDF 里的表格解析怎么处理？

> "我会先把问题定性：PDF 是打印指令的集合，解析表格的本质是从二维坐标还原结构，所以不能靠单一解析器硬扛，要分层。第一层是路由：先判断有没有文本层——每页字符数低于阈值的按扫描件走 OCR 管线；有文本层再看版面复杂度，简单文档用 PyMuPDF 毫秒级出结果，复杂文档交给 Marker 或 MinerU 这类带版面分析的解析器。第二层是处理：版面分析模型先定位表格区域并拿到坐标，表格识别模型把它转成 Markdown 表格，跨页表格按表头相似度自动拼接，行列语义在这一步保住。第三层是兜底：解析结果做结构校验，比如列数一致性、空单元格比例，异常的进死信队列，高价值文档降级用多模态大模型重新解析。最后所有输出统一转 Markdown 中间格式，附上页码和坐标做溯源。核心思想一句话：按文档类型动态路由、分而治之、永远有兜底。"（约 320 字）

**追问：**

1. **怎么判断一个 PDF 是扫描件？**
   答：提取每页文本字符数，低于阈值（如 10 字/页）即判定无文本层；也可抽样看是否整页只有一张大图。扫描件路由到 OCR 管线。
2. **表格解析错了怎么办？**
   答：自动校验（列数漂移、空格率、乱码率）→ 异常进 DLQ；高价值文档降级多模态大模型重解析；线上配合引用溯源，让用户能点回原文核对。
3. **为什么要统一转 Markdown？**
   答：解析器五花八门，下游切块只应面对一种格式；Markdown 天然带标题层级/表格/代码块语义标记，正好支撑结构感知切块。
4. **多栏 PDF 直接用 PyMuPDF 提取会发生什么？**
   答：按内部字符流顺序输出，左右栏交叉成"乱码"，语义顺序错乱——必须先版面分析分栏，再按坐标重排阅读顺序。

## 4.2 切块（Chunking）

### 4.2.1 四种切块策略对比

**是什么（通俗类比）：**

切蛋糕——固定长度是"闭眼按尺子切"；递归分割是"先沿蛋糕上画好的线切，不够密再补刀"；语义切块是"盯着看哪里是天然断点再下刀"；结构感知是"按蛋糕本来的分层切"。

**怎么做（对比表）：**

| 维度 | 固定长度 | 递归分割 | 语义切块 | 结构感知 |
|------|---------|---------|---------|---------|
| 原理 | 每 N token 一刀 | 依次尝试分隔符：`\n\n` → `\n` → `。` → 空格 | 相邻句子算 embedding，相似度骤降处断开 | 按 Markdown 标题层级 / 代码块 / HTML 标签切 |
| 优点 | 最简单、块均匀 | 兼顾语义边界与 size 控制，**零模型成本** | 最尊重语义边界，召回率约 **+9%** | 块语义最完整，天然带层级上下文 |
| 缺点 | 无情切断句子/表格 | 仍可能切在语义中间 | 每句都算向量，**贵且慢** | 依赖解析质量；块大小不均匀 |
| 成本 | 无 | 无 | 高（N 倍 embedding 调用） | 低 |
| 适用 | 快速原型/粗糙兜底 | **生产默认**（LangChain RecursiveCharacterTextSplitter） | 高价值场景、精度压倒成本 | Markdown/HTML/代码类文档 |

**选型经验公式：有结构用结构，没结构递归兜底，语义切块按 ROI 加码。**
文档有标题层级/代码块 → 结构感知优先；杂乱纯文本 → 递归分割；检索质量就是业务命脉（客服、法律）→ 上语义切块，且通常只对高频/高价值文档子集开启。

### 4.2.2 chunk size 与 overlap 的权衡

**高频题正面回答：为什么 chunk 不能越大越好？太小又有什么问题？**

| | 太小（如 50 token） | 太大（如 4000 token） |
|---|---|---|
| 检索侧 | 单块语义稀薄；"指代悬空"（"该方法"找不到先行词），向量表达不出完整意思 | 一个向量稀释了多个主题，怎么查都不够像，检索精度下降 |
| 生成侧 | 命中后上下文不足，模型"只看到半句话" | 命中即带入大量无关内容，噪声干扰 + token 成本飙升 |
| 索引侧 | chunk 数量爆炸，索引膨胀、检索变慢 | 单块过大，rerank 与 LLM 处理成本高 |

**工程要点：**
- 常用区间：**300-800 token**（中文约 500-1000 字）；overlap 取 **10%-20%**
- **按 token 计量，不按字符数**：embedding 模型按 token 截断和计费，中文一个字 1-2 token，"800 字"和"800 token"差近一倍——不按 token 计量会对不齐模型截断上限，块被悄悄截断
- overlap 的作用：缓解边界效应——关键句跨块时，至少在某一块里是完整的
- **overlap 过大的代价**：索引膨胀（存储与检索成本线性上涨）+ Top-K 里出现同一段的不同偏移副本（重复上下文浪费预算）
- 认知升级：overlap 只是"创可贴"，治本靠 Parent-Child 或块级上下文补全（见 4.2.3 / 4.2.4）

### 4.2.3 Parent-Child（Small-to-Big）索引

**是什么（通俗类比）：**

图书馆的索引卡。卡片（child）上只有一小段摘要和书架号，用来**精准找到**；找到后去书架把整本书（parent）借出来**完整阅读**。检索用小，阅读用大。

**为什么：**

检索和生成的最优粒度天然矛盾——检索要"小块精准匹配"（块越大向量主题越稀释），生成要"大块完整上下文"（半句话看不懂）。Parent-Child 把两个阶段拆开，**各自用最优粒度**：child（约 100-200 token）建索引做检索；命中后取 parent（约 1000-2000 token）进 LLM 上下文。

**怎么做（结构图）：**

```text
      检索阶段:用 child(小块,精准)        生成阶段:用 parent(大块,完整)
             │                                  ▲
             ▼                                  │ parent_id 回表
  ┌───────────────────────┐        ┌────────────┴─────────────┐
  │ child_1 "报销时限30天" │───────▶│ parent_A: 《报销制度》    │
  │ child_2 "发票抬头要求" │───────▶│   完整章节 ~2000 token   │
  │ child_3 "超标审批流程" │───────▶│  (背景+条款+例外齐全)    │
  └───────────────────────┘        └──────────────────────────┘
             ▲                                  ▲
     只有 child 建向量索引              parent 不建向量索引
     (向量存储省一大半)                 (按 id 直取,可加缓存)
```

**关键设计：只对 child 向量化，parent 只存不索引**——这是控制索引膨胀的第一原则。

**存储方案对比（嵌套 vs 外键）：**

| 维度 | 嵌套存储（parent 内嵌 children 数组） | 外键关联（child 带 parent_id） |
|------|-----------------------------------|------------------------------|
| 结构 | parent 文档里嵌 chunk 数组 | child 独立平铺记录 + 外键 |
| 检索 child | 需从 parent 展开（或双向冗余） | 天然平铺，直接查向量库 |
| 回溯取 parent | 读一个文档即得 | 查到 child 后按 id 批量 get（两次查询，可加缓存） |
| 增量更新 | 改一个 chunk 要重写整个 parent | 单 chunk 独立更新 |
| 规模适应性 | 小规模、文档型存储（MongoDB 风格） | **大规模生产推荐**（向量库 + KV 分层） |

生产推荐外键式：向量库只存 child 向量 + parent_id 标量字段；parent 原文放 MySQL/对象存储，热 parent 加 LRU 缓存；命中后批量 mget，延迟可控。

**索引膨胀控制三招：**
1. 只向量化 child，parent 不进向量索引（省最大头）
2. 同一 parent 的 children 入库前去重（顺带省一份向量）
3. 检索 Top-K 后**按 parent_id 聚合去重**——10 个 child 命中同一 parent 只取一次，上下文不重复，腾出的名额补充其他主题

### 4.2.4 大纲外补充：块级上下文补全（Contextual Retrieval）

**问题：** child 脱离原文后"身份不明"——"该公司营收增长 15%"，向量里根本没有"哪家公司、哪一年"的信息，检索时极易失配。

**方案（Anthropic Contextual Retrieval 思路）：** 入库时用 LLM 给每个 chunk 生成一句上下文前缀（所属文档/章节/主语补全），拼接后再嵌入：

```text
入库时(一次性成本):
  chunk: "该公司营收增长15%"
    + LLM 生成前缀: "《XX集团2024年报》· 财务章节 · 主语:XX集团"
    → 拼接后整体 embedding → 入库
```

**本质：用入库时的一次性算力，换检索时的匹配精度**（官方报告检索失配率可降约 35%+，叠加 BM25 与 rerank 更低）。与 Parent-Child 互补——一个解决"上下文完整"，一个解决"向量身份完整"。

---

### 🎤 面试这样答：切块策略怎么选？chunk size 怎么定？

> "我的默认答案不是某个算法，而是一个决策顺序。第一步看文档有没有结构：Markdown、HTML、代码这类自带标题层级和代码块的，直接结构感知切块，语义最完整；第二步，没有结构的杂文本用递归分割兜底——它是 LangChain 的默认不是没有道理的，零模型成本、优先沿段落边界切，性价比最高；第三步，如果检索质量直接决定业务，比如法律、客服，再评估语义切块，它靠 embedding 找语义突变点，召回率能提 9 个点左右，但每个句子都要算向量，成本高，我通常只对高价值文档子集开启。size 方面，我按 token 不按字符计量——中文一字一到两个 token，按字符会对不齐模型截断上限——常规 300 到 800 token，overlap 取 10% 到 20%，保证跨块句子至少在一块里完整。最后我会补一句：size 调优不是终点，小而准和大而全的矛盾，我会用 Parent-Child 索引拆解——小块检索、大块生成，两个阶段各用最优粒度。"（约 340 字）

**追问：**

1. **overlap 为什么不设大点，比如 50%？**
   答：索引近乎翻倍（存储+检索成本线性涨），且 Top-K 会出现同一段的多个偏移副本，上下文预算被重复内容浪费。overlap 是创可贴，10-20% 够用，治本靠 Parent-Child。
2. **Parent-Child 下 Top-K 全命中同一个 parent 怎么办？**
   答：按 parent_id 聚合去重，一个 parent 只取一次，腾出的名额补充其他 parent——兼顾上下文完整性与结果多样性。
3. **语义切块到底值不值得上？**
   答：算账：多出的成本 = 全量句子级 embedding 调用；收益 = 召回率约 +9%。高价值、更新频率低的文档值得；高频变更的流水文档不值得。
4. **中文和英文在 size 设定上有什么差异？**
   答：中文一字约 1-2 token、信息密度高，同等 token 数承载更多信息；切分边界符也不同（句号/分号/顿号），必须用目标 tokenizer 实测校准，不能照抄英文默认值。

## 4.3 元数据工程与入库流水线

### 4.3.1 Metadata 设计

**是什么（通俗类比）：**

Metadata 就是知识库的"数据库索引设计"——**查询时有哪些 where 条件，就设计哪些索引列**。没有 metadata 的向量库，等于一张只能全表扫描的表。

**怎么做（六类字段）：**

| 字段类 | 示例 | 用途 |
|-------|------|------|
| 来源 | doc_id / file_path / source_system | 引用溯源、按文档粒度删除/重建 |
| 时间 | publish_time / ingest_time / expire_time | 时效过滤：新版本优先、过期知识剔除 |
| 版本 | version / is_latest | 版本管理，防止新旧知识"打架" |
| 权限 | tenant_id / acl_roles / confidentiality | 权限过滤、租户隔离（安全红线） |
| 实体 | 抽取的产品/人名/部门标签 | 实体命中增强检索 |
| 分类 | doc_type / department / topic | 范围过滤提精度 |

**设计方法论：从检索查询反推 schema。** 先收集线上查询会带哪些过滤条件（权限？部门？时效？），再定字段；不设计"以防万一"的冗余字段——标量索引同样有写入成本，和数据库索引一样不是越多越好。

### 4.3.2 Pre-filtering 前置过滤

**是什么：** 先按 metadata 过滤缩小候选集，再在子集内做 ANN 检索——对应数据库里"索引命中缩小扫描范围，再排序"。

**为什么：**
- **权限是红线不是排序问题**：无权限的文档绝不能进上下文，"检索出来再靠排序压下去"不可接受
- 精度与速度双升：候选集小，HNSW 图搜索又快又准

**注意（体现深度）：** 极端选择性过滤（如命中率 0.01%）会让 HNSW 图上候选过于稀疏而性能退化——工程上可退化为"先检索后过滤 + 补偿捞取"，或直接靠分区/collection 设计缓解。

### 4.3.3 动态元数据注入

**怎么做：** 查询时按用户身份动态拼过滤条件，而非把权限写死在数据里：

```text
filter = {
  tenant_id:   当前用户.tenant,         # 服务端强制注入
  acl_roles:   { $in: 当前用户.roles },  # 权限交集
  is_latest:   true,                    # 版本收敛
  expire_time: { $gt: now }             # 时效过滤
}
```

**为什么动态注入而不是入库时按权限物化：** 权限会变。写死在数据里，权限一调整就要全量重刷；查询时注入则权限变更零成本——把 ACL 当"查询计划"而不是"数据副本"。

### 4.3.4 异步向量化入库流水线（完整设计）

**是什么（后端视角）：** 这就是一条标准 ETL 数据管道——后端练过的 MQ 削峰、幂等、状态机、失败补偿、定时对账，在这里全部复用。

```text
┌──────┐ 上传,立即返回 ┌──────────┐  ┌─────────┐    ┌──────────┐
│前端/ │────────────▶│ 上传服务  │─▶│  MQ     │───▶│ 解析      │
│API   │  task_id    │·对象存储  │  │(按优先级│    │ Worker   │
└──────┘  (异步)     │·文件指纹  │  │ 分队列) │    │·动态路由  │
    ▲                 │·状态机落库 │  └─────────┘    │·统一转MD  │
    │ SSE/轮询进度     └──────────┘       │          └────┬─────┘
    │                                    ▼               ▼
┌───┴────────┐                   ┌─────────┐    ┌──────────────┐
│ 质量校验    │◀──── MQ ─────────│ 入库    │◀───│ 向量化        │
│·抽样人审    │                   │(向量库+ │    │ Worker       │
│·规则校验    │─通过─▶状态:done   │ 标量索引)│   │·批量(64-256) │
└────┬───────┘                   └─────────┘    │·令牌桶限流   │
     │ 不通过                                   │·指数退避     │
     ▼                                         └──────────────┘
┌──────────┐  失败补偿: 重试超限 → DLQ → 人工介入
│ DLQ      │  定时对账: 源文件表 vs 向量库逐条比对
└──────────┘            缺失→补偿重灌   多余→清理删除
```

**六个设计要点（每条都是后端老本事）：**

1. **上传即返回**：接口只做存储 + 记录 + 发 MQ，立即返回 task_id；前端轮询或 SSE 收进度——慢操作永不占用同步链路
2. **MQ 削峰 + 分级**：百万文档批量导入不能打爆解析服务；按文件大小/来源优先级分队列（大文件单独低速队列），消费端按容量拉取
3. **全链路幂等**：以文件指纹为幂等键，重复上传直接返回已完成状态；每个阶段处理前先查状态机，避免 MQ 重投导致重复切块/入库
4. **状态机推进**：`uploaded → parsed → chunked → embedded → indexed → verified`，每步落库；失败从断点重试，不从头重灌
5. **向量化批量 + 限流**：embedding API 有 RPM/TPM 配额——令牌桶限流 + 批量请求（一次 64-256 条）+ 指数退避重试；这是整条流水线最常见的瓶颈
6. **质量校验前置**：自动规则（chunk 数合理性、空块率、乱码率、溯源字段完整性、向量非零）+ 抽样人审；不过关自动打回重解析，不带病入库

### 4.3.5 增量更新与一致性

**三件事：**

1. **判重（幂等）**：上传时查文件指纹——命中且已入库则跳过，同一文件传 N 次只处理一次
2. **版本管理**：同一文档新版入库 → version+1、打 is_latest=true，旧版置 false（软删，可回滚）；检索默认 `is_latest=true`——否则旧版"退款 7 天"和新版"退款 30 天"同时被召回，是经典事故
3. **删除同步（双写一致性）**：源库删除 → 发删除事件 → 按 doc_id 删向量库；顺序是**先源库后向量库**；兜底靠定时对账（比对两侧 doc_id 集合，多的删、少的补）——和"缓存一致性"完全同款的解法

### 4.3.6 海量文档：分区与冷热分层

- **分区/分 collection**：按 tenant / 部门 / 文档类型 / 时间切分——每个维度都等于天然的 pre-filter（检索只扫一个分区），且爆炸半径可控（重建单分区不影响全局）
- **冷热分层**：常被检索的热文档放内存/SSD collection；归档冷数据转磁盘索引或廉价存储；按访问统计定期迁移
- **数字感觉**：100 万文档 × 平均 50 chunks = 5000 万向量，全塞一个 collection 的 HNSW 内存压力巨大——分区不是优化项，是必选项

### 4.3.7 多租户隔离

| 方案 | 做法 | 隔离强度 | 成本 |
|------|------|---------|------|
| 共库 + tenant_id 过滤 | 单 collection，检索必带 tenant_id | 弱（依赖过滤不出 bug） | 最省 |
| 共库分 collection | 每租户独立 collection | 中 | 中（collection 数量管理成本） |
| 独立实例/集群 | 大客户独立部署 | 强（物理隔离） | 贵 |

- 策略：中小租户共享 + 过滤，KA 客户独立——与 SaaS 数据库多租户方案一模一样
- **红线**：tenant_id 由服务端强制注入，绝不信任客户端传参；用"跨租户检索必须返回空"的测试用例固化防线

---

### 🎤 面试这样答：100 万文档要入库，流水线怎么设计？

> "我会把它当一条标准的 ETL 数据管道来设计，后端的成熟套路全部复用。接入层异步化：上传接口只做对象存储、文件指纹落库、发 MQ，立即返回 task_id 让前端轮询进度，慢操作绝不占用同步链路。消费层用 MQ 削峰并按优先级分队列，解析 worker 动态路由解析器，切块后进入向量化 worker——这一步是瓶颈，因为 embedding API 有配额，所以批量请求加令牌桶限流加指数退避。可靠性靠三件事：以文件指纹做全链路幂等；阶段状态机落库，失败从断点重试而不是从头重灌；重试超限进死信队列人工介入，另配定时对账任务比对源文件表和向量库条数，缺的补偿重灌、多的清理。质量上入库前有自动校验——空块率、乱码率、溯源字段完整性，不过关自动打回。容量上按租户和文档类型分 collection，检索天然缩小范围。这套设计的本质是：把'不靠谱的解析和向量化'包进'靠谱的管道语义'里。"（约 350 字）

**追问：**

1. **embedding API 被限流，流水线积压怎么办？**
   答：令牌桶限速 + 批量提效是常态；突发限流靠 MQ 天然缓冲积压、消费端降速；长期不够用则申请配额，或自部署 embedding 模型（BGE）分流非核心文档。
2. **入到一半服务挂了，怎么保证不丢不重？**
   答：状态机落库 + 幂等键：每阶段完成才推进状态，重启后按状态从断点继续；MQ 重投靠文件指纹和 chunk 唯一键去重；最终一致性靠对账任务兜底。
3. **embedding 模型要换版，怎么平滑切换？**
   答：向量不可混用（不同模型的向量空间不兼容）。方案：新 collection 按需迁移或双写、查询侧双读灰度比对、指标达标后切流、旧库保留回滚窗口——本质是数据库"双写迁移"的翻版。
 4. **源文件删了，向量库没删干净怎么办？**
   答：删除走事件驱动（先源后向量），漏删靠定时对账兜底：比对两侧 doc_id 集合，多的清掉；对账频率按合规要求定（如小时级）。

## 进阶篇：高级岗深挖区（数据工程决定 RAG 上限）

> 基础篇回答"是什么、怎么做"；进阶篇回答"数字是多少、什么时候不用、翻过什么车"。高级岗面试官靠这一层区分"用过"和"管过"。

### A. 二层追问链（面试官的深挖套路）

高级岗面试的经典节奏：你答出概念（第一层）→ 面试官追问数字/边界（第二层）→ 再追成本/取舍（第三层）。以下四条链是真实高频深挖路径，对话体演练。

```text
深挖节奏（每一层都在淘汰人）:
第一层  "你怎么做 X？"          ──▶ 淘汰没做过的（背概念者也在此现形）
第二层  "有数字吗？为什么？"    ──▶ 淘汰只看博客没落地过的
第三层  "成本多少？何时不用？"  ──▶ 淘汰没做过取舍决策的
剩下能答满三层的，就是"管过"而不只是"用过"的人
```

#### A.1 二层追问链：Contextual Retrieval

> **追问：** "你提过块级上下文补全，完整方案展开讲讲？"
>
> **答：** Anthropic 的 Contextual Retrieval。入库时对每个 chunk 单独调一次 LLM， Prompt 大意是"该片段出自以下文档，请为其生成一两句简短的上下文说明，说明它在整篇中的位置和主语"，把生成的前缀拼在 chunk 前面，然后**同时进两个索引**：拼接文本做 embedding 入向量库，拼接文本也入 BM25 索引——因为前缀补全了"哪家公司、哪个年度"这类关键词，关键词检索同样受益。检索时两路融合，可选再叠 rerank。

```text
入库时(一次性成本,可摊销):
┌────────┐   ┌─────────────┐   ┌──────────────────────┐
│ chunk  │──▶│ LLM 生成     │──▶│ "《XX集团2024年报》   │
│ 原文    │   │ 上下文前缀   │   │  财务章·主语XX集团:   │
└────────┘   └─────────────┘   │ 该公司营收增长15%"    │
                               └──────────┬───────────┘
                     ┌────────────────────┼────────────────┐
                     ▼                                     ▼
             ┌──────────────┐                     ┌──────────────┐
             │ 向量索引      │                     │ BM25 索引    │
             │ (语义身份完整) │                     │ (关键词补全)  │
             └──────────────┘                     └──────────────┘
                     └────────── 检索时 RRF 融合 ──────────┘
```

> **再追问：** "收益有数字吗？"
>
> **答：** Anthropic 官方报告：仅 contextual embedding 使检索失败率（top-20 未命中）**降 35%**；叠加 contextual BM25 双索引**降 49%**；再叠 rerank **降 67%**。三个组件收益可乘性叠加，这正是"数据侧优化"的诱人之处——不动检索模型，只把数据喂得更"有身份"。

> **再追问：** "5000 万 chunk 的库，前置生成成本怎么算？什么时候不值得？"
>
> **答：** 算账三步：
> 1. **token 量估算**：单次调用 ≈ 文档摘要（~1500 token）+ chunk（~300 token）+ 前缀输出（~80 token）；5000 万 chunk ≈ **约 1000 亿 token** 级别输入
> 2. **模型选择决定量级**：用 Haiku 级小模型 + Prompt Caching（文档摘要作为共享前缀可缓存，缓存命中的输入约 1/10 价格），量级可压到数千美元；用旗舰模型则贵一个数量级
> 3. **摊销逻辑**：这是一次性入库成本，收益作用于之后**每一次检索**——更新频率越低、查询量越大的库，摊销越划算
>
> **不值得的场景**：① 小库（<10 万 chunk，总检索 bad case 本来就少，直接 rerank 兜底更便宜）；② 高频变更库（文档每天重灌，前置生成成本变成持续开销，摊销失效）；③ chunk 上下文本来就自含的库（每块主语明确、独立成文，如 FAQ 对，生不生成前缀没区别）。一句话：**它治"chunk 脱离原文后身份不明"，不治所有检索病。**

#### A.2 二层追问链：Embedding 换版蓝绿切流

> **追问：** "你一句'双写迁移'带过了，完整方案展开？"
>
> **答：** 本质是数据库蓝绿切换，四阶段：
> 1. **建绿索引**：新版 embedding 模型对全量 chunk 重嵌入，写入新 collection（影子库，不接流量）
> 2. **增量双写**：绿库就绪后，入库流水线切双写——新 chunk 同时进旧（蓝）新（绿）两库，保证绿库不落后
> 3. **灰度切流**：查询侧按百分比把检索流量从蓝切绿（1%→10%→50%→100%），双读灰度期间新旧结果并存，对比召回质量指标（用黄金评测集）确认无退化再放量
> 4. **蓝库下线**：全量后保留蓝库一个回滚窗口（如 2 周），到期归档下线

```text
时间 ─────────────────────────────────────────────────────▶
      ┌─────┬──────────────┬─────────────────┬────────────┐
写入  │ 只有│   双写        │     双写        │   只有      │
      │ 蓝库│  (蓝+绿)      │    (蓝+绿)      │   绿库      │
      └─────┴──────────────┴─────────────────┴────────────┘
            ▲              ▲                 ▲            ▲
读取        │  100%蓝      │  1%→10%→50%     │  100%绿    │  蓝库归档
            │  (绿库建设)  │  双读比对        │            │  (下线)
            └── 全量重嵌 ───┘  质量门禁放量   └────────────┘
                 (影子库)
```

> **再追问：** "双写期的一致性问题呢？"
>
> **答：** 三个坑：
> 1. **写一半失败**：双写不是一个事务，绿库写失败要记"不一致清单"，靠补偿任务重试；不能静默吞掉，否则切流后绿库缺数据
> 2. **删除同步双份**：删除事件必须同时删两库，只删一边 = 一边有幽灵数据；对账任务在双写期要跑**两份**
> 3. **写放大**：embedding 调用翻倍，注意限流配额——好在双写期通常短，且可只对新增/变更文档双写，存量靠一次性重嵌

> **再追问：** "灰度期间指标掉了，回滚怎么做？"
>
> **答：** 因为蓝库一直在双写、从未下线，回滚 = 把读流量切回蓝库，**秒级完成、零数据丢失**——这正是蓝绿方案贵（双份资源）但稳的核心价值。回滚后不是直接放弃，而是抽样 diff 新旧库的召回结果，定位是模型适配问题（如中文 tokenizer 变化）还是数据问题（重嵌批次污染），修复后重新灰度。

#### A.3 二层追问链：Parent-Child 索引膨胀

> **追问：** "Parent-Child 说'只向量化 child 控膨胀'，数字级算一下？"
>
> **答：** 设父子比 1:5（1 个 parent 平均拆 5 个 child），全量 100 万 parent：
>
> | 项目 | 纯平铺方案 | Parent-Child 方案 | 增量 |
> |------|-----------|------------------|------|
> | 向量数（建索引） | 100 万 | 500 万（仅 child） | **+400%** |
> | 原文存储 | 100 万份大块 | 500 万份小块 + 100 万份大块 | 约 +25%（小块有 overlap 冗余时更多） |
> | 检索延迟 | 单次 ANN | ANN + 回表 mget parent | +一次批量 get（缓存后可忽略） |
>
> 结论：Parent-Child 的膨胀在**向量索引侧（4 倍+）**，不在存储侧。HNSW 内存近似随向量数线性涨，500 万向量 × 1024 维 fp32 ≈ 20GB 级索引内存——这就是为什么大规模库必须配分区。

> **再追问：** "什么时候该放弃 Parent-Child，改用句级窗口（Sentence Window）？"
>
> **答：** 三个信号：
> 1. **父块几乎不提供额外上下文**（如 FAQ、条款类"每条独立"的文档）——parent 只是 child 的拼接，白付 4 倍索引
> 2. **回表命中率低**：大量 child 命中的 parent 互相重复（Top-10 聚合后只剩 2-3 个 parent），上下文多样性反而不如平铺
> 3. **内存已到瓶颈且分区不可行**
>
> 句级窗口是 Parent-Child 的轻量退化版：按句切小块检索，命中后**运行时**向前向后拼窗口（不存 parent、不建外键），零额外索引、零回表，代价是"完整上下文"依赖拼窗逻辑、不感知文档结构。**一句话：文档结构性强、父块信息浓 → Parent-Child；句子级自足 → 句级窗口。**

#### A.4 二层追问链：HNSW 极端 pre-filter 退化

> **追问：** "你说极端过滤下 HNSW 会退化，原理是什么？"
>
> **答：** HNSW 是一张多层近邻图，检索是贪心游走——每步跳向"既离 query 近、又能继续往下走"的邻居。pre-filter 先把 99.99% 的点标记为"不可见"，图上就出现大量"断头路"：贪心路径走到被过滤的节点只能绕路甚至死胡同，算法被迫回退到近似暴力扫描。**过滤选择性越极端（命中率越低），图越不连通，退化越猛**——从毫秒级掉到秒级都有可能。

> **再追问：** "'先检索后过滤+补偿'的参数怎么调？"
>
> **答：** 三个旋钮：
> 1. **over-fetch 倍数**：不放大数据集，而是放大检索量——取 `top_k × N`（N 按 1/预估命中率放大，如权限过滤后预计剩 10% 就取 10 倍），过滤后截取 top_k。N 上限要封顶（如 50 倍），否则等价暴力扫
> 2. **ef 放大**：搜索时把 ef 参数（候选队列长度）调大，弥补图被过滤后的绕路损失；通常 ef ≥ 4×top_k 起步，压测调优
> 3. **切换开关**：按过滤选择性的实测拐点做策略路由——命中率 >5% 走 pre-filter（图还连通），<5% 切 post-filter + over-fetch，极端场景（<0.1% 且数据有分区键）直接下推到分区 collection
>
> 落地关键是**压测出自己数据分布下的拐点**，不要抄别人数字——图结构、维度、过滤字段分布不同，拐点差很远。

### B. 生产级 Case Study ×2（STAR-L，含数字）

> 高级岗面试的杀手锏不是背方案，是**讲自己翻过的车**。以下两个故事模板，替换成你项目里的真实数字即可使用。
>
> STAR-L 讲述要点：Situation/Task 各一句话带过，**把时间留给 Action 里的决策对比和 Result 里的数字**，Learning 必须是"如果重来会怎么做"级别的沉淀，不是空话。每个数字都要经得起"这个数怎么测出来的"的追问。

#### B.1 Case：10 万 → 800 万文档的知识库演进

- **Situation：** 企业知识库从 10 万文档（试点）涨到 800 万（全公司接入），检索 QPS 从 5 涨到 120。
- **Task：** 负责向量存储架构演进，P99 延迟红线 500ms，全程不停服。
- **Action（三阶段决策链，每阶段用数字说话）：**

| 阶段 | 规模 | 瓶颈（实测数字） | 决策 | 决策依据 |
|------|------|-----------------|------|---------|
| ① pgvector 单机 | 10 万 doc / 50 万向量 | QPS 30 时 P99 从 80ms 涨到 1.8s；HNSW 索引 2GB | 短期够用，加只读副本 | 已有 PG 团队运维，迁移成本 > 优化收益 |
| ② pgvector 分区 | 200 万 doc / 1000 万向量 | 单表索引 20GB+，写入时 autovacuum 拖垮读延迟；副本同步延迟 5s+ | 按 tenant/文档类型分 16 个区 + 冷热表分离 | 分区后单区索引 <2GB，P99 回到 300ms；但写入侧到顶了 |
| ③ 迁移 Milvus | 800 万 doc / 4000 万向量 | PG 方案预估需 64 分区 + 8 副本，运维复杂度爆炸 | 迁移 Milvus 集群（存算分离 + IVF_SQ8 量化） | 4000 万向量量化后内存可控，QPS 500+ 水平扩展 |

- **不停服迁移方案：** 就是进阶篇 A.2 的蓝绿切流——Milvus 建绿库 → 全量重嵌 + 增量双写（pgvector + Milvus）→ 按租户灰度切读 → 全量后 PG 保留两周下线。**踩的坑：** ① 重嵌用的 embedding 模型和原库不一致，灰度期新旧召回质量指标抖动，排查一周才发现是模型版本差异，重刷；② Milvus 的 IVF nprobe 初始照抄默认值 8，召回率只有 0.72，压测调到 32 才回到 0.9+（换来 P99 +40ms，可接受）。
- **Result：** 800 万文档稳定支撑，P99 480ms，QPS 峰值 300，检索成本每千次下降 60%。
- **Learning：** 每个阶段的"够用边界"要提前算（向量数 × 内存系数 / 写入吞吐天花板），**演进是被数字推着走的，不是追新**——如果 PG 分区能扛到明年，就不该迁。

#### B.2 Case：解析质量翻车事故

- **Situation：** 为提升表格解析效果，把一批财务 PDF 从 PyMuPDF 切换到新版解析器，直接上线。
- **Task：** 事故复盘与防回归体系搭建。
- **Action：** 三步走——
  1. **发现（靠监控不靠用户）：** 上线 3 天后，数据质量看板的"表格坏块率"从 0.5% 涨到 7.8%（阈值告警 >3%），同时黄金评测集上**检索召回率跌 12%**——新版解析器对合并单元格处理有 bug，表格行列错位，切块后变成语义噪声
  2. **修复：** 受影响 doc_id 清单从溯源元数据反查（这就是 4.1.6 溯源的价值）；这批文档回退旧解析器重灌，4 小时恢复；向解析器仓库提 issue + 补测试用例
  3. **防回归：** 建**解析质量门禁进 CI**——新增/变更解析器必须过一组"金标 PDF 集"（人工标注的 200 个含表格/多栏/公式的样本），表格结构保真度、乱码率不达标自动阻断发布
- **Result：** 后续两次解析器升级均在门禁阶段拦截问题，再未发生线上解析事故。
- **Learning：** 解析器是"静默失败"组件——不报错、只输出错的数据，**没有质量度量体系的解析管线等于裸奔**；溯源元数据让"回滚一批坏数据"从事后全量重刷变成精准定向修复。

### C. 数据质量度量体系（系统化）

基础篇零散提过质量校验，这里给出完整体系：**四层指标 + 阈值 + 采集方式 + 门禁分级**。核心思想：数据质量不是"感觉"，是**可采集、可告警、可阻断**的指标体系。

| 层 | 指标 | 定义 | 阈值参考 | 采集方式 |
|----|------|------|---------|---------|
| 解析层 | 乱码率 | 非常规字符占全文比例 | >2% 告警 | 解析后正则统计 |
| | 表格结构保真度 | 金标样本上表格行列还原正确率 | <95% 阻断（金标集） | CI 门禁比对 |
| | 页眉页脚残留率 | 跨页重复模式行占正文比 | >1% 告警 | 重复模式检测 |
| 切块层 | 空块率 | text 为空/过短（<10 字）的块占比 | >0.5% 告警 | 入库前统计 |
| | 超长块率 | 超 embedding 截断上限的块占比 | >1% 告警 | 入库前按 token 计量 |
| | 语义截断率 | 块首/尾句不完整（无终止符）比例 | >15% 告警 | 规则抽检 |
| 嵌入层 | 向量分布漂移 | 新批次向量均值/方差 vs 历史基线偏移 | 偏离 3σ 告警 | 入库后批量抽样统计 |
| | 零向量率 | embedding 返回全零/NaN 比例 | >0.01% 阻断 | 入库后校验 |
| 检索层 | 抽样召回抽检 | 黄金问题集 top-k 命中率 | 环比跌 >5% 告警 | 每日定时跑评测集 |
| | 引用点击率 | 用户点开引用原文的比例（间接质量信号） | 持续下降告警 | 线上埋点 |

**门禁分级（阻断 vs 告警）：**

```text
入库流水线中的质量关卡:
解析 ──▶ [P0 阻断: 零向量/表格保真度不达标] ──▶ 拒收,进 DLQ 人工处理
切块 ──▶ [P1 告警: 空块率/超长块率超标] ─────▶ 过滤坏块后继续,记录指标
嵌入 ──▶ [P1 告警: 分布漂移] ────────────────▶ 继续入库,触发排查工单
检索 ──▶ [P2 观测: 召回率环比下滑] ───────────▶ 汇入周报,定位到批次/来源
分级原则: 错误数据进得来(阻断) vs 质量波动可观测(告警)分开对待
```

**分级原则一句话：** 会污染索引、事后无法自动修复的（零向量、结构错乱表格）→ **P0 阻断**；不致命但反映趋势的（比率波动、分布漂移）→ **P1 告警继续**，靠人/工单跟进；只能事后观测的线上质量信号 → **P2 观测**。

**落地路径（别想一步到位）：**

```text
第 1 周   采集先行:在现有流水线埋点,先把四层指标"看见"(只有看板,无门禁)
第 2-3 周 告警接入:P1 类指标接告警(空块率/乱码率/超长块率),摸清自家数据的正常基线
第 4 周   基线固化:基线不是拍脑袋,是两周实际分布的分位数(P99 不是 0)
第 5 周+  门禁上线:金标集攒够 100+ 样本后,把 P0 阻断接入 CI;检索层评测集从 20 题起步
持续      坏样本回灌:线上每个 bad case 都可能变成金标集的一条新样本
```

常见误区：① 阈值照抄别人（数据分布不同，正常空块率可能差一个数量级）；② 一上来全门禁（阈值没校准就阻断，流水线天天停摆，团队很快学会绕过门禁）；③ 只建不审（指标没人看 = 没建）。**先看见，再告警，后阻断**——顺序反了会翻车。

### D. 高级视野

#### D.1 工时占比：数据工程占 RAG 项目 60-70%

业界共识：RAG 项目中**约 60-70% 的工时花在数据侧**（解析、清洗、切块、元数据、质量监控），模型/检索侧只占三成。面试怎么用这个数字：

> ❌ 背数字："业界说数据工程占 60-70%。"
> ✅ 展示成熟度："我们的 RAG 项目复盘，数据管线占了大约三分之二的工时——所以我把解析质量门禁、四层质量指标这些'一次投入持续收益'的建设放在了优先级最高的位置。**知道数字只是知道，围绕数字重新分配了自己的工时才是工程成熟度。**"

这个数字同时是回答"为什么 RAG 项目容易烂尾"的钥匙：团队按 Demo 的预期排期（以为大头是调模型），实际工时倒挂，数据侧欠债爆炸。

> 配套回答模板（追问"那你们项目呢"时用）："我们复盘过工时分布，数据管线约占三分之二——解析门禁与质量看板占了我前两个月的几乎全部精力，但正是这两块让后来的检索调优只花了一周就达标。"

#### D.2 多模态文档处理路线图

| 文档类型 | 当前可用方案 | 成熟度 | 备注 |
|---------|------------|--------|------|
| 图文混排 | 版面分析 + 图内 OCR + 图注关联 | ✅ 生产可用 | 主流管线标配 |
| 数据图表（柱状图/折线图） | 多模态 LLM 生成图表描述文本 | ⚠️ 可用但需人审 | 描述质量决定检索价值 |
| 数学公式 | MinerU/Marker 转 LaTeX | ✅ 基本可用 | LaTeX 进索引可被公式检索 |
| 复杂跨页表格 | 解析器 + 跨页拼接规则 | ⚠️ 案例依赖 | 兜底多模态 LLM |
| 手写/潦草扫描件 | OCR 置信度低 | ❌ 等成熟 | 置信度低的人工通道 |

**决策框架：能转文本的先转文本**（嵌入检索生态最成熟）；转不好且高价值的用多模态 LLM 生成描述入索引；两者都不行的走"图片原样存 + 多模态检索"的远期路线——当前多模态嵌入的检索精度和成本还不理想，**别为 5% 的极端文档提前建设 100% 的复杂度**。

#### D.3 对比表：Demo 级 vs 生产级知识库（十维）

| # | 维度 | Demo 级 | 生产级 |
|---|------|---------|--------|
| 1 | 解析 | 单一解析器一把梭 | 按文档类型动态路由 + 校验兜底 |
| 2 | 切块 | 固定长度默认参数 | 策略选型 + Parent-Child + 按文档类型定制 |
| 3 | 元数据 | 只有 text | 六类字段 + pre-filter + 动态权限注入 |
| 4 | 入库 | 同步脚本跑一次 | 异步流水线：MQ/幂等/状态机/DLQ/对账 |
| 5 | 溯源 | 无 | 页码/段落号全程携带，引用可点击 |
| 6 | 增量 | 删库重灌 | 指纹判重 + 版本管理 + 删除事件同步 |
| 7 | 质量 | 肉眼抽查 | 四层指标 + 分级门禁 + 金标回归集 |
| 8 | 换模型 | 全量重刷 | 蓝绿双写 + 灰度切流 + 秒级回滚 |
| 9 | 多租户 | 单租户 | 隔离分级 + tenant_id 服务端强制 |
| 10 | 成本 | 不看账单 | 向量化批量限流 + 冷热分层 + 索引压缩 |

**这张表的用法：** 面试自查时逐行打勾——你所在项目每一维处在哪一列？说不清的维度就是会被深挖的软肋；反过来说，能在十个维度上都讲出"我们从左列走到右列的过程和代价"，就是最有说服力的资深叙事。

### 🎤 面试这样答：Contextual Retrieval 值得上吗？成本怎么算？

> "我会先算三笔账再回答值不值。第一笔收益账：Anthropic 官方数字，contextual embedding 让检索失败率降 35%，叠 BM25 双索引降 49%，再叠 rerank 降 67%——这些收益不依赖换检索模型，纯粹是把每个 chunk 喂得'更有身份'。第二笔成本账：每个 chunk 要过一次 LLM 生成上下文前缀，按 5000 万 chunk 估算约千亿级输入 token，但有两处可压：用小模型生成、把文档摘要做 Prompt Caching 共享前缀（缓存命中输入约十分之一价格），量级能压到可接受。第三笔摊销账：这是一次性入库成本，收益作用于之后每一次查询——所以更新频率越低、查询量越大的库越划算。反过来，三种情况我明确不上：小库直接 rerank 兜底更便宜；每天重灌的高频变更库摊销失效；chunk 本来就自含主语的 FAQ 类库没病可治。所以我的结论是：它是'更新少查询多'场景的高 ROI 优化，不是无脑全量铺开的标配。"（约 330 字）

**追问：**

1. **前缀生成本身错了怎么办（LLM 幻觉污染 chunk）？**
   答：Prompt 约束"只用原文信息，不添加事实" + 抽样人审前缀质量；前缀只是增强信号，检索后用户看到的仍是原文（溯源保证），错误前缀的代价是漏召回而非错误答案。
2. **BM25 索引也要重建吗？**
   答：是，且是好处：前缀补全了"哪家公司哪个年度"这类关键词，BM25 同步受益；重建成本远低于向量侧重嵌，性价比高。
3. **为什么不干脆把整个文档摘要塞进每个 chunk？**
   答：Token 膨胀——每块带 1500 token 摘要，embedding 成本翻数倍且稀释块内语义；LLM 定制生成的一两句前缀是"摘要的浓缩定向版"，单位 token 信息密度最高。

### 🎤 面试这样答：你的知识库数据质量怎么管？

> "我把质量当指标体系管，不是当感觉管，分四层。解析层盯乱码率和表格结构保真度——后者靠 200 个人工标注的金标 PDF 集在 CI 里做门禁，解析器升级不过门禁不能发布，这是我们翻过车之后建起来的。切块层盯空块率、超长块率、语义截断率，入库前统计，异常块直接过滤。嵌入层做向量分布漂移检测，新批次和历史基线偏移超三个标准差就告警，防的是换模型或上游数据变化导致的静默劣化。检索层每天跑黄金评测集，召回率环比跌超五个百分点自动开工单。然后是分级：零向量、表格结构错乱这类会污染索引、事后无法自动修复的，P0 直接阻断进死信队列；比率波动、分布漂移这类不致命但反映趋势的，P1 告警继续入库靠人跟进。这套体系的核心是让'数据变坏'从用户投诉变成看板告警——我们的解析事故从'用户发现'变成了'上线前拦截'。"（约 320 字）

**追问：**

1. **金标集怎么维护、会不会过拟合？**
   答：从线上 bad case 持续回灌（坏样本沉淀），覆盖表格/多栏/公式/扫描件各类型；金标只做门禁不做训练，不存在传统意义的过拟合，但要防止"只测历史翻车类型"——定期补新文档形态的样本。
2. **质量指标和业务指标（召回率）怎么关联归因？**
   答：按入库批次打标签，召回率下跌时先看是不是某批次数据质量指标同时异常——元数据让"检索变差"能下钻到"哪批数据变坏"。
3. **向量分布漂移具体怎么算？**
   答：抽样新批次向量的逐维均值/方差与历史基线比对，偏离超 3σ 触发；更简单的做法是抽样算与基线中心的平均余弦距离。它防的是"上游悄悄换了 tokenizer/模型/数据源"这类静默事故。
