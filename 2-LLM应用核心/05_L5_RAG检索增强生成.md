## 5.1 基础架构（必须白板能画）

### 5.1.1 完整管线：一张图打天下

**是什么（通俗类比）：**

RAG 就是给 LLM 办的一场"开卷考试"：检索层负责"翻书翻得对"（找到相关页码），生成层负责"抄得对、不瞎编"（只根据翻到的内容作答）。整条管线就是这场考试的标准化流程。

**为什么：**
- LLM 的参数化知识是"训练截止日就冻结的教科书"，无法回答私有知识、实时知识
- 直接问 LLM 私有问题 = 闭卷考没学过的内容 → 必然编造（幻觉）
- 把知识外挂到检索库，模型只做"阅读理解"，知识更新只需换文档，不用重训模型

**怎么做（生产级完整管线）：**

```text
                        用户 Query
                            │
                            ▼
                 ┌─────────────────────┐
                 │ ① 查询改写层         │  多轮指代消解 / HyDE /
                 │                     │  多查询扩展 / 子问题分解
                 └──────────┬──────────┘
                            ▼
        ┌───────────────────────────────────────────┐
        │ ② 双路召回（宽召回，各取 top 50）           │
        │  ┌─────────────────┐  ┌─────────────────┐ │
        │  │  向量检索        │  │  BM25 关键词检索 │ │
        │  │  (语义泛化能力)  │  │  (精确匹配能力)  │ │
        │  │  + 元数据过滤    │  │                 │ │
        │  └────────┬────────┘  └────────┬────────┘ │
        └───────────┼────────────────────┼──────────┘
                    ▼                    ▼
                 ┌─────────────────────────┐
                 │ ③ RRF 融合排序           │  按排名倒数融合，
                 │                         │  免疫两路分数量纲差异
                 └────────────┬────────────┘
                              ▼
                 ┌─────────────────────────┐
                 │ ④ Rerank 精排            │  Cross-Encoder 对融合后
                 │                         │  top-N 逐对精细打分
                 └────────────┬────────────┘
                              ▼
                 ┌─────────────────────────┐
                 │ ⑤ Top-K 上下文组装       │  截断 / 去重 /
                 │                         │  相关度排序 / 预算控制
                 └────────────┬────────────┘
                              ▼
                 ┌─────────────────────────┐
                 │ ⑥ LLM 生成（带引用）     │  约束："仅基于上下文回答，
                 │                         │  无依据就说不知道"
                 └────────────┬────────────┘
                              ▼
                    答案 + [1][2] 引用溯源
```

每一环都是"可优化的独立模块"——这就是面试讲架构的叙事框架：**检索前优化（①）、检索中优化（②③）、检索后优化（④⑤）、生成端约束（⑥）**。

### 5.1.2 Naive RAG → Advanced RAG → Agentic RAG 演进叙事

**是什么（通俗类比）：**

三代 RAG 就像客服中心的进化：Naive 是"给实习生一本手册让他自己翻"；Advanced 是"给一套标准 SOP：先问清问题、翻两本手册、按可信度排序再回答"；Agentic 是"雇了个资深工程师，他自己判断要不要查、查哪本、查完够不够、要不要再查"。

**为什么（Naive RAG 的三大痛点倒逼演进）：**
- **检索质量差**：原句直接检索（多轮指代没消解）、单一向量检索（专有名词搜不中）、无精排（相关内容排在 top50 之外）
- **上下文组装粗暴**：top-K 直接拼接，噪声块稀释注意力，关键块被截断
- **生成失控**：没有"无依据就说不知道"的约束，没有引用溯源，幻觉无兜底

**怎么做（三代对比表）：**

| 维度 | Naive RAG | Advanced RAG | Agentic RAG |
|------|-----------|--------------|-------------|
| 核心思想 | 检索一次 → 生成一次 | 检索前/中/后全链路优化 | RAG 降级为 Agent 的一个**工具** |
| 查询处理 | 原句直接检索 | 改写 / HyDE / 多查询扩展 | Agent 自主决定查不查、怎么查 |
| 检索方式 | 单路向量 top-K | 混合检索 + 元数据过滤 | 按需选择数据源、参数、次数 |
| 精排 | 无 | Rerank 精排 + 上下文压缩 | 结果充分性自主评估，可二次检索 |
| 流程性质 | 固定直线 | 固定管线（更精细） | **动态循环**（决策驱动） |
| 成本/延迟 | 低 | 中 | 高（多轮 LLM 决策） |
| 适用场景 | Demo / 简单 FAQ | 绝大多数生产场景 | 复杂多跳问题 / 开放研究型任务 |

**演进一句话**：Naive 把 RAG 当"功能"，Advanced 把 RAG 当"管线"来优化，Agentic 把 RAG 当"工具"来调度。

---

### 🎤 面试这样答：「白板画一下你们的 RAG 架构，讲讲为什么这么设计」

> "我按数据流讲。用户 Query 进来先过**查询改写**：多轮对话里'它/这个'必须先消解，否则检索直接废掉。然后是**双路召回**：向量检索管语义泛化，BM25 管专有名词和型号这类精确匹配——单路向量在错误码、产品型号上经常搜不中，这是踩过坑的。两路结果用 **RRF 融合**，好处是只用排名不用原始分数，天然免疫两路分数量纲不一致的问题。融合后 top50 进 **Rerank 精排**——embedding 是双塔结构，query 和文档没有交互，排序精度有天花板，Cross-Encoder 精排能把真正相关的块顶到前面。之后**组装 Top-K 上下文**，做好去重和预算控制。最后 LLM 生成时**强制带引用**，Prompt 里写死'仅基于上下文回答，无依据就说不知道'。这样设计的原则是：**每一层只解决一类问题，且都可以独立评测、独立优化**——检索层看 recall@k，排序层看 MRR，生成层看 faithfulness，出了问题能精确定位到层。"（约 320 字）

**追问：**

1. **为什么不直接向量检索 top-K 就完事？**
   答：三处损失——单路召回漏精确匹配、无精排相关块沉底、无引用约束幻觉没兜底。管线每一环都是在补一类特定的损失。
2. **管线这么长，延迟怎么控？**
   答：改写用小模型、双路召回并行、Rerank 只精排 top20~50、流式输出先出首字；P95 预算按环节分配（检索+精排 ~300ms，LLM 首字 ~1s）。
3. **哪一环对最终效果影响最大？**
   答：召回是上限——gold chunk 没进 top-K，后面全白搭。所以排查和优化都优先砸在检索层，其次才是生成层。

## 5.2 检索核心

### 5.2.1 Embedding 选型

**是什么（通俗类比）：**

Embedding 模型是"语义 GPS 定位器"——把每段文本映射成高维空间里的一个坐标，语义越近坐标越近。检索的本质就是"找坐标最近的邻居"。

**为什么：**
- 检索质量的上限由 embedding 对你领域的**适配度**决定：通用模型在黑话、术语、内部缩写上语义会"飘"
- 换 embedding = 全量向量重算 + 索引重建，成本高，所以选型要一次想清楚

**怎么做（选型表）：**

| 模型 | 特点 | 适用场景 |
|------|------|---------|
| **BGE**（智源） | 中文第一梯队；bge-m3 一个模型同时支持稠密/稀疏/多向量三种检索 | **中文知识库默认首选** |
| **GTE**（阿里） | 中文强，通义生态整合好 | 中文 / 电商领域 |
| **E5** | 多语言强；注意输入要加 `query:` / `passage:` 前缀约定 | 多语言混合语料 |
| **Jina Embedding** | 支持超长文本（8K token 级） | 长文档整段嵌入 |
| **OpenAI text-embedding-3** | 效果稳、API 免运维 | 海外业务 / 快速原型；数据需出境是硬伤 |

**维度与成本的 trade-off：**
- 维度越高表达力上限越高，但存储、内存、计算成本线性涨；1024 维是中文场景常见的平衡点
- 领域适配 > 榜单排名：内部黑话多的语料，用领域数据微调一个开源模型，往往比换更大的通用模型收益更高

**Matryoshka（一句话）：** 像"俄罗斯套娃"向量——训练时让向量的**前缀子段也有效**，一套 1024 维向量可以截断成 512/256 维直接用，粗排用短的省算力、精排用全长保精度。

**多语言一句话：** 语料以中文为主就选中文强模型（BGE/GTE），不要迷信"多语言通用模型"——广度是拿深度换的。

### 5.2.2 向量库选型

**是什么（通俗类比）：**

向量库就是"为相似度查询特化的存储引擎"。选型逻辑和当年选 MySQL / ES / ClickHouse 一样：**按查询语义和数据规模选，不按名气选**。

**为什么：**
- 核心诉求是 ANN（近似最近邻）检索 + 元数据过滤，传统 B+ 树解决不了"找语义最近的"
- 选错代价大：数据迁移、管线改造、团队学习成本

**怎么做（对比表 + 场景结论）：**

| 维度 | Milvus | Qdrant | pgvector | Elasticsearch(8.x) |
|------|--------|--------|----------|--------------------|
| 定位 | 大规模分布式向量库 | 轻量高性能（Rust） | PG 的向量扩展 | 全文检索巨头加 kNN |
| 规模上限 | 十亿级，水平扩展 | 千万级，单机为主 | 百万级舒适区 | 千万级（依赖集群） |
| 运维成本 | 高（组件多，要专人） | 低（单二进制） | 极低（复用现有 PG） | 中（复用现有 ES 团队） |
| 事务/一致性 | 弱 | 弱 | **强（ACID）** | 弱 |
| 混合检索 | 向量+标量过滤 | 向量+payload 过滤 | SQL where 过滤 | **BM25+向量原生融合** |
| 何时选 | 1000 万级以上、要弹性扩缩 | 中小规模、要独立轻量部署 | **已有 PG + 中小规模 + 要事务** | **已有 ES 团队 + 要全文混合** |

**按场景给结论（面试直接背）：**
- 数据量 < 几百万、已有 PostgreSQL → **pgvector**，不引入新组件就是最大的工程收益
- 已有 ES 团队、且 BM25 混合检索是刚需 → **ES 8.x**，团队熟就是快
- 中小规模、独立部署、追求省心 → **Qdrant**
- 上千万/上亿文档、要分布式和弹性 → **Milvus**

### 5.2.3 索引原理：HNSW / IVF / PQ

**是什么（通俗类比）：**
- **HNSW**：像"高速公路 + 乡村公路"的多层路网——上层稀疏（跨省高速），下层稠密（市内街道），从顶层快速定位到目标附近再逐层下沉精确逼近
- **IVF**：像"图书馆分区"——先把所有书聚类到 N 个书架（nlist 个桶），查询时只扫离得最近的几个书架（nprobe 个桶）
- **PQ**：像"有损压缩图片"——把长向量切段、每段用最接近的"代表值"代替，内存大降但精度有损

**为什么（精确检索不可行）：**
- 一千万文档两两算距离 = 全表扫描，延迟秒级起——所以必须用 ANN（近似最近邻）索引，用"放弃一点点召回"换"数量级级的加速"

**怎么做（HNSW vs IVF 对比 + 参数经验）：**

| 维度 | HNSW | IVF |
|------|------|-----|
| 原理 | 多层近邻图，贪心逐层下沉 | 聚类分桶，查询扫部分桶 |
| 资源特征 | **内存换时间**（图全在内存） | **省内存**（只存桶心+分桶） |
| 召回质量 | 高且稳定 | 依赖 nprobe，边界数据易漏 |
| 建索引耗时 | 慢（构图贵） | 快（一次聚类） |
| 适用规模 | 中小规模（百万级舒适） | 大规模 |
| 关键参数 | M / ef_construction / **ef_search** | nlist / **nprobe** |

**参数怎么调（讲"经验"就够）：**
- `M`（每个节点的连接数）：默认 16~32；调大 → 召回↑ 内存↑
- `ef_construction`（建图时搜索宽度）：64~256；调大 → 图质量↑ 建库时间↑，**只在建索引时付出，值得给高**
- `ef_search`（查询时搜索宽度）：**运行时可调的"旋钮"**——线上召回不够就调大，延迟超了就调小，类比调数据库的 work_mem
- `nlist`（桶数）：通常取 `4 * sqrt(N)` 量级起步；`nprobe`（扫描桶数）：调大提召回、增延迟
- **调参方法论**：先跑默认值建立 baseline，用标注集测 recall@k，不够再加码——"调参前先有基准"这句话本身就是加分项

**PQ 一句话：** 常与 IVF 组合成 IVF-PQ，向量切段量化压缩，内存能降一个数量级，代价是精度损失，适合"数据量太大内存放不下"的场景。

**DiskANN 一句话：** 索引放 SSD、内存只放少量路由信息的磁盘向量索引，超大规模且成本敏感时的选择。

### 5.2.4 专题：混合检索（BM25 + 向量 + 融合）

**是什么（通俗类比）：**

向量检索像"懂意思的图书管理员"——你说"退货要多久"，他能找到"售后处理时效"的文档；BM25 像"较真的检索员"——你说"错误码 E-4502"，他一字不差地给你揪出来。混合检索就是两个一起雇。

**为什么（向量的天然短板）：**
- Embedding 把整段话压成一个向量，**专有名词、产品型号、错误码、代码函数名**这类"低频但关键"的 token 会被语义平均稀释——搜 "ERR_CONN_REFUSED"，向量空间里它和一堆"连接类错误"文档距离几乎一样近
- BM25 是词频统计检索（TF-IDF 的进化版），对精确 token 匹配天然强
- 用户查询天然分两类："语义模糊型"（向量强）和"精确指称型"（关键词强），单路召回必有盲区

**怎么做（双路召回 + RRF 融合架构）：**

```text
                  Query（改写后）
                       │
         ┌─────────────┴─────────────┐
         ▼                           ▼
 ┌───────────────┐           ┌───────────────┐
 │  向量检索      │           │  BM25 检索    │
 │  (语义泛化)    │           │  (精确匹配)   │
 │  top 50       │           │  top 50      │
 │  +元数据过滤   │           │              │
 └───────┬───────┘           └───────┬───────┘
         │ 排名列表 A                │ 排名列表 B
         └─────────────┬─────────────┘
                       ▼
             ┌───────────────────┐
             │  RRF 倒数排名融合   │
             │  概念：每路只看排名，│
             │  分数 = Σ 1/(k+排名) │
             │  （k 常取 60）      │
             └─────────┬─────────┘
                       ▼
              融合后 top 50 → 进 Rerank
```

**RRF vs 加权融合（必考对比）：**

| 维度 | RRF（倒数排名融合） | 加权线性融合 |
|------|------------------|-------------|
| 公式概念 | 每路只看**排名**，文档总分 = 各路 1/(k+排名) 之和 | score = α·向量分 + (1-α)·BM25 分 |
| 分数量纲 | **天然免疫**（只用排名，不看原始分） | 必须先归一化，否则一路压死另一路 |
| 参数 | 一个 k，不敏感好调 | α 权重要调参，且随数据分布漂移 |
| 丢失的信息 | 分数绝对值（置信度）丢了 | 保留分数信息 |
| 工程建议 | **默认首选** | 两路分数可比且稳定时才用 |

**分数归一化问题（加权融合的坑）：** 余弦相似度挤在 [0,1] 的高段（好文档 0.85、一般的 0.80），BM25 分数无上界（5.2、8.9 都可能），直接加权 = BM25 单方面说了算。要做 min-max / z-score 归一化，但归一化参数随数据分布漂移——这就是 RRF 成为工程默认的原因。

**稀疏向量一句话（第三路召回）：** SPLADE / BGE-M3 的稀疏表示 = "模型学出来的加权词袋"，哪些 token 重要、哪些同义词该激活都由模型学，是 BM25 的学习增强版；用 BGE-M3 可一套模型同时产出稠密+稀疏两种向量，稀疏路可与前两路再 RRF。

---

### 5.2.5 专题：Rerank 精排

**是什么（通俗类比）：**

Bi-Encoder（双塔）像"只看档案相亲"——双方各自建档（算向量），匹配时只比对档案距离，快但粗；Cross-Encoder 像"面对面深聊"——把 query 和文档拼在一起喂进模型逐 token 交叉注意，慢但准。

**为什么：**
- 双塔为了文档向量可离线预计算，**query 和文档从未"见过面"**，token 级交互信息全丢——这是排序精度的天花板
- 召回阶段的任务是"别漏"（宽召回），精排任务是"top 几位必须准"——两个阶段目标不同，模型结构也该不同
- 这就是推荐系统"召回→精排"两阶段思想在 RAG 的翻版

**怎么做（原理对比 + 延迟优化）：**

| 维度 | Bi-Encoder（双塔） | Cross-Encoder（交叉编码） |
|------|-------------------|--------------------------|
| 结构 | query、文档分别编码 → 算相似度 | query+文档拼接 → 单模型直接输出相关分 |
| 交互 | 无（各自独立，可预计算） | 逐 token 全交叉注意力 |
| 精度 | 中（天花板明显） | 高（精排标配） |
| 速度 | 快：文档向量离线算好 | 慢：每个 (query, doc) 对都要现算 |
| 角色 | 召回层（百万里挑 50） | 精排层（50 里挑 5） |

**延迟代价与优化（面试讲"优化手段"的关键）：**
1. **top-k 截取**：只对融合后 top 20~50 做 rerank，O(全库) 变 O(k)
2. **批处理**：候选对拼 batch 一次 GPU 推理，单对均摊成本大降
3. **模型选型/蒸馏**：BGE-Reranker（开源、中文强、可自部署可蒸馏）或 Cohere Rerank（API 效果稳）；延迟敏感场景用蒸馏出的轻量 reranker
4. **并行化**：rerank 与 LLM 首 token 前的准备工作重叠执行

### 5.2.6 查询改写与扩展

**是什么（通俗类比）：**

用户的问题经常是"没头没尾的省略句"（"那第二个呢？"）或"跟文档表述对不上的问法"。查询改写层就是检索前的"翻译官 + 扩音器"：把话补全、换种说法、拆开问。

**为什么：**
- 检索是"query 和文档的匹配游戏"，query 质量直接决定召回上限
- 多轮对话不改写，等于拿错误坐标找地址

**怎么做（五板斧对比表）：**

| 手法 | 做什么 | 收益 | 风险/代价 |
|------|--------|------|-----------|
| **Query Rewrite**（指代消解） | 小 LLM 把"它/第二个"补全成独立完整问题 | 多轮对话检索的前提，必配 | 改写跑偏 → 只用于检索 + 相似度护栏回退原文 |
| **HyDE**（假设答案检索） | 让 LLM 先编一个"假答案"，拿假答案的向量去检索 | 假答案往往比问题本身更接近真文档的语义（问答对齐） | 多一次 LLM 调用；假答案跑偏反而带偏检索 |
| **多查询扩展（RAG-Fusion）** | 一个问题改写成 N 个不同角度 query，各自检索后 RRF 融合 | 覆盖不同表述，召回率显著提升 | N 倍检索成本 + 一次 LLM 改写 |
| **子问题分解** | 复杂问题拆成多个可独立检索的子问题 | 多跳问题的必备手段 | 拆错方向全链路错；延迟叠加 |
| **Step-back** | 先问一个更抽象的"上位问题"（具体案例 → 概念原理） | 细节搜不到时用背景知识兜底 | 抽象过头召回泛化噪声 |

**选型经验一句话：** Rewrite 是刚需必配；HyDE / 多查询扩展按 bad case 数据决定要不要加；子问题分解是多跳场景的进阶手段（配合 5.3 的 Agentic RAG）。

---

### 🎤 面试这样答：「为什么检索要加 BM25？向量检索不够吗？」

> "不够，因为向量检索有结构性盲区。Embedding 把整段文本压成一个向量，本质是有损压缩，专有名词、产品型号、错误码、代码函数名这些低频 token 会被语义平均稀释——我们实测搜一个具体错误码，向量检索 top10 全是'同类错误'的泛化文档，真正含这个码的文档排在开外。BM25 是词频统计检索，对精确 token 匹配天然强，正好补这块。两路结果用 RRF 融合，只取排名不取原始分数，天然免疫两路分数量纲不一致的问题——余弦相似度挤在 0.8 附近而 BM25 分数无上界，直接加权等于 BM25 单方面说了算。上线后对比：纯向量 recall@10 约 0.78，混合检索到 0.89，多出的延迟只有 BM25 那一路十几毫秒，ES 上现成的。如果用 BGE-M3 还能加第三路稀疏向量——相当于学会加权的 BM25，三路融合再进 rerank。"（约 300 字）

**追问：**

1. **BM25 要分词，中文怎么办？**
   答：ik / jieba 分词 + 自定义词典把型号、黑话加进词库——分词切碎了 BM25 也搜不中。
2. **RRF 里的 k 是干什么的？**
   答：k≈60 是平滑常数，让第 1 名和第 2 名的贡献接近，避免"单路冠军独裁"；概念上理解即可——排名越靠前贡献越大，多路累加。
3. **稀疏向量和 BM25 都要吗？**
   答：二选一，都保留是冗余。已有 ES 用 BM25 最省；纯向量库方案用 BGE-M3 的稀疏字段。

---

### 🎤 面试这样答：「为什么要 Rerank？直接用向量相似度排序不行吗？」

> "不行，双塔结构有精度天花板。向量检索是 Bi-Encoder——文档向量离线预计算，查询时只算一次 query 向量比距离，快，但 query 和文档从头到尾没见过面，没有 token 级交互，做不到'top 几位都精确相关'。而最终喂给 LLM 的只有 top 3~5 块，这几位的排序质量直接决定答案质量。所以我在融合后 top50 上加 Cross-Encoder rerank——query 和每个候选拼在一起过模型，全交叉注意力，直接输出相关分。代价是每个候选对都要现算，所以必须控成本：只 rerank 融合后 top20~50、拼 batch 一次推理、用 BGE-Reranker 可自部署还能蒸馏小模型。实测 rerank 前后 MRR 从 0.62 到 0.81，多花 100~200ms 延迟，用 P95 预算换排序质量是划算的。本质上这是推荐系统'召回保广、精排保准'的两阶段思想，我把它搬到了 RAG。"（约 310 字）

**追问：**

1. **Rerank 这么准，为什么不全库 rerank？**
   答：全库交叉编码 = 千万次模型推理，延迟成本都不可接受。两阶段就是用便宜的召回把 O(N) 砍成 O(k)。
2. **Reranker 延迟超预算怎么办？**
   答：降候选数（top50→top20）、换蒸馏小模型、batch 推理；再不行业务降级——低价值 query 跳过 rerank 直接用 RRF 序。
3. **怎么衡量 rerank 的收益？**
   答：离线看 MRR、context precision@k 前后对比；线上看引用点击率和"答案无依据"负反馈占比。没有分层指标的 A/B 不上。

## 5.3 进阶架构（体现视野）

### 5.3.1 Agentic RAG：RAG 降级为 Agent 的工具（2025 高频新题）

**是什么（通俗类比）：**

传统 RAG 是"固定流水线"——不管问题难易都走同一套流程；Agentic RAG 是"资深研究员"——他自己判断：这题要不要查资料？查哪个库？查到的够不够？不够要不要换个关键词再查一次？

**为什么：**
- 固定管线对简单问题过度服务（延迟成本浪费），对复杂问题服务不足（一次检索不够用）
- 检索质量天然不确定，需要"评估-再行动"闭环，而不是一次性赌召回
- LLM 工具调用能力成熟后，"把检索封装成工具"是最自然的架构升级

**怎么做（决策循环图）：**

```text
            ┌────────────────────────────┐
            │    用户 Query 进入 Agent     │
            └─────────────┬──────────────┘
                          ▼
            ┌────────────────────────────┐
      ┌────▶│ ① 决策：需要检索吗？        │◀─────────────┐
      │     │ （闲聊/常识 → 直接回答）     │              │
      │     └─────────────┬──────────────┘              │
      │                   ▼ 需要检索                     │
      │     ┌────────────────────────────┐              │
      │     │ ② 决策：怎么检索？          │              │
      │     │  选库 / 改写 query / 拆子   │              │
      │     │  问题 / 定 top_k 和过滤条件  │              │
      │     └─────────────┬──────────────┘              │
      │                   ▼                             │
      │     ┌────────────────────────────┐              │
      │     │ ③ 调用检索工具（RAG 管线）   │              │
      │     └─────────────┬──────────────┘              │
      │                   ▼                             │
      │     ┌────────────────────────────┐              │
      │     │ ④ 评估：结果够回答吗？      │───不够────────┘
      │     │ （置信度/相关性/覆盖度）    │   换策略二次检索
      │     └─────────────┬──────────────┘
      │                   ▼ 够了
      │     ┌────────────────────────────┐
      │     │ ⑤ 生成答案（带引用）         │
      │     └────────────────────────────┘
      │                   │
      └── 循环上限 max_steps（如 3 次）
           超限 → 强制生成 + 声明信息不足 / 转人工
```

**工程要点（拉开差距的部分）：**
- **终止条件必须有**：最大步数 + 置信度阈值，否则 Agent 陷入"检索-不满意-再检索"死循环，token 烧穿
- **置信度评估**：让 LLM 对检索结果自评（相关性/覆盖度打分），或用 rerank 分数做代理指标
- **成本意识**：每轮循环 = LLM 决策调用 + 检索调用，延迟和成本数倍于固定管线——所以先用 5.3.2 的自适应路由分流，别让简单问题进循环

### 5.3.2 自适应 RAG：按查询类型路由

**是什么（通俗类比）：**

医院分诊台——感冒直接开药（直答），骨折拍片（精确检索），疑难杂症全院会诊（广度检索）。不是所有病人都走最贵的流程。

**为什么：**
- 查询难度是长尾分布：大部分简单、小部分复杂；统一走重管线 = 大部分请求为小部分需求买单
- 路由可以用便宜的分类器实现（小模型 / embedding 相似度 / 规则）

**怎么做（三路路由表）：**

| 查询类型 | 例子 | 路由策略 |
|---------|------|---------|
| 闲聊/通用常识 | "你好""水的沸点" | 直答不检索，零检索成本 |
| 事实型精确问题 | "E-4502 错误怎么处理" | 精确检索：小 top_k + 元数据过滤，快 |
| 开放/复杂问题 | "对比两个方案的优劣" | 广度检索：多查询扩展 + 大 top_k + rerank，甚至 Agentic 循环 |

**路由器实现（由轻到重）：** 规则/意图分类小模型 → embedding 相似度匹配 → LLM 分类。路由准确率要有监控——路由错了是"系统性体验下降"的隐蔽源头。

### 5.3.3 GraphRAG：知识图谱 + 向量

**是什么（通俗类比）：**

向量检索回答"A 像什么"，知识图谱回答"A 和 B 什么关系"。GraphRAG = 图书馆（向量）+ 一张关系网（图谱）：先在关系网上多跳定位相关实体，再取它们的文本详情。

**为什么：**
- "张三的导师的合作者研究过什么"这类**多跳推理**，向量检索天然做不了——每一跳的语义和整体问题差很远，直接检索全偏
- "整个知识库的主要主题是什么"这类**全局性问题**，靠 top-k 局部片段拼不出来

**怎么做（流程与成本账）：**

```text
离线构建：文档 → LLM 实体抽取 → 三元组(头,关系,尾) → 图谱
              → 社区检测（子图聚类）→ 分层社区摘要
在线查询：局部问题 → 向量检索 + 图邻居扩展（多跳）
          全局问题 → 遍历社区摘要做全局归纳
```

**成本账（面试必须主动讲）：**
- 构建成本：全量文档过 LLM 抽实体三元组，一次构建的 token 成本可能是普通入库的十倍量级
- 维护成本：文档更新要增量同步图谱，实体消歧、关系修正是长期脏活
- **LightRAG（一句话）**：去掉昂贵的社区检测与分层摘要，用"局部实体+全局关键词"双层检索保留多跳能力，构建维护成本大降——中小规模多跳需求的首选

**选型结论：** 关系密集领域（金融风控、医药、组织架构、供应链）+ 预算充足 → GraphRAG；偶尔多跳 → LightRAG 或 Agentic RAG 多次检索；纯事实问答 → 向量+混合检索足够。

### 5.3.4 专题：RAG vs 微调（几乎必问）

**是什么（通俗类比）：**

RAG 是"给员工发资料手册"——知识在外部，随时换手册，回答能翻给你看出处；微调是"送员工去培训"——知识烙进脑子里（参数），风格对反应快，但更新要重新培训，也没法溯源。

**为什么（决策的本质）：**

分界线是**要改的是"知识"还是"行为"**：
- 知识（事实、文档、实时数据）→ RAG：外挂、可更新、可溯源
- 行为（风格、格式、术语体系、输出套路）→ 微调：固化进参数，稳定且省 token

**怎么做（多维对比表）：**

| 维度 | RAG | 微调（SFT） |
|------|-----|------------|
| 知识更新 | 换文档即生效，分钟级 | 重训/继续训练，天~周级 |
| 成本 | 检索系统搭建 + 查询时延 | 训练算力 + 数据标注 + 基座升级要重做 |
| 可解释/溯源 | **强制引用，可定位出处** | 黑盒，无法溯源 |
| 幻觉控制 | 上下文约束 + 可拒答 | 无直接约束，靠数据质量间接影响 |
| 行为/风格改变 | 弱（Prompt 约束有限度） | **强**（格式/语气/领域套路固化） |
| 维护 | 文档管线 + 向量库运维 | 模型版本管理 + 全量回归评测 |
| 典型场景 | 企业知识库 / 文档问答 / 时效资讯 | 客服话术 / 固定输出格式 / 领域术语理解 |

**业界惯例（背下来）：RAG-First，微调打补丁。** 先用 RAG 解决知识和时效；当出现"Prompt 怎么写都不稳定遵守的格式/风格/黑话理解"时，用微调固化行为；两者不互斥——**微调改行为 + RAG 供知识**是常见组合（微调过的模型照样挂 RAG）。

---

### 🎤 面试这样答：「RAG 和微调怎么选？」

> "我的决策框架就一条：看要改的是**知识**还是**行为**。知识型需求——私有文档、实时数据、要溯源的合规要求——闭眼选 RAG：更新分钟级生效、答案带引用、幻觉可控；知识烙进参数就成了黑盒，更新要重训，出错没法定位，这些微调都给不了。行为型需求——固定输出格式、客服话术风格、领域黑话的稳定理解——Prompt 约束到极限也就那个样，微调把行为固化进参数，又稳又省 token。展开比四个维度：成本上 RAG 是检索系统一次性搭建加查询时延，微调是算力加标注且基座一升级就重做；时效上 RAG 换文档即生效，微调周级；可解释上 RAG 强制引用，微调黑盒；维护上 RAG 是文档管线，微调是模型版本管理加全量回归。所以我们惯例是 RAG-First、微调打补丁——90% 需求 RAG 覆盖，剩下格式风格稳定的硬需求用微调，而且两者不冲突，微调过的模型照样挂 RAG 供知识。"（约 330 字）

**追问：**

1. **RAG 不够用的信号是什么？**
   答：检索质量已经很好（gold chunk 都在 top3）但格式风格仍不稳定；或领域术语模型完全不理解导致指令遵从差——这是行为问题，RAG 治不了。
2. **微调能减少幻觉吗？**
   答：不能直接减少。幻觉根源是知识缺失或检索失败，微调不改知识供给；反而可能让模型更"像专家"连带更敢编。幻觉的直接防线在 RAG 的上下文约束和拒答机制。
3. **小模型 + RAG 能替代大模型吗？**
   答：封闭域知识问答经常可以——知识由 RAG 供给，模型只做阅读理解，7B 级够用且便宜；开放推理和复杂指令遵循仍有差距，按场景路由。
4. **上下文窗口都这么长了，为什么还要 RAG？**
   答：成本（每请求全量 token）、延迟（长上下文首字慢）、注意力稀释（lost in the middle）、知识更新粒度——四个都是硬伤，长窗口和 RAG 互补不替代。

## 5.4 失效模式与排查（背题级重要）

### 5.4.1 完整排查流程：八问八验

**是什么（通俗类比）：**

RAG 出问题像"快递没送到"——不能瞎猜，要沿物流链路逐站查：地址写对没（改写）→ 货打包完整没（切块）→ 仓库找到没（召回）→ 分拣排对没（融合排序）→ 质检做了没（rerank）→ 装箱完整没（上下文组装）→ 面单信息对没（Prompt 约束）→ 签收单对上没（引用对齐）。

**为什么：**
- RAG 是多模块串联系统，任何一环失效都会传导到最终答案——**不逐段归因就是瞎调参**
- 面试官问"效果不好怎么排查"，考的就是你有没有"分层归因"的工程素养

**怎么做（排查流程图，背下来）：**

```text
          RAG 答案质量差 / 答非所问 / 出现幻觉
                        │
                        ▼
     ┌──────────────────────────────────────┐
     │ Q1 Query 改写对吗？                   │
     │ · 多轮指代消解了吗？改写跑偏没？       │──错→ 修改写层 / 加相似度护栏
     └─────────────────┬────────────────────┘
                       ▼ 对
     ┌──────────────────────────────────────┐
     │ Q2 切块腰斩关键信息了吗？              │
     │ · 表格/代码/定义被切断？overlap 缺失？ │──是→ 调切块策略 / 结构感知切块
     │ · 检索粒度问题？→ Parent-Child 索引    │      / Parent-Child 索引(L4)
     │   （小块精准检索，大块供上下文）        │
     └─────────────────┬────────────────────┘
                       ▼ 否
     ┌──────────────────────────────────────┐
     │ Q3 向量召回了吗？                     │

                       ▼ 在
     ┌──────────────────────────────────────┐

     │ · RRF 参数？加权的分数归一化了吗？     │──错→ 修融合逻辑
     └─────────────────┬────────────────────┘
                       ▼ 对
     ┌──────────────────────────────────────┐
     │ Q5 Rerank 了吗？排得对吗？            │
     │ · 有精排吗？分数分布合理吗？           │──否→ 上 rerank / 换 reranker
     └─────────────────┬────────────────────┘

     └─────────────────┬────────────────────┘

```

**排查方法论（后端味儿拉满）：** 每一问都对应可观测指标（改写日志、recall@k、MRR、rerank 分数分布、组装快照、引用命中率）——**排查不是重放猜谜，是看每一层的指标仪表盘**。这也是 L7 评测体系反复强调的：先有分层评测，才有归因能力。

### 5.4.2 典型失效四类：归因与解法

| 失效类型 | 现象 | 根因 | 解法 |
|---------|------|------|------|
| **① 内容缺失** | 该有的知识没进上下文 | 文档没入库 / 切块腰斩 / 召回漏 / 元数据过滤误杀 | 补数据源、修切块、混合检索、查过滤器 |
| **② 排序错误** | 知识在库里但排 top100 开外 | 无 rerank / 融合参数错 / embedding 领域不适配 | 上 rerank、调融合、领域微调 embedding |
| **③ 上下文整合失败** | 材料都对，答案缝合错或只用一部分 | 上下文过长稀释注意力 / 块间矛盾 / 指令不清 | 压缩上下文、块去重排序、明确"综合所有材料" |
| **④ 幻觉兜底缺失** | 没依据也硬编 | 缺拒答约束 / 无引用校验 | 幻觉三板斧（见 5.5.4） |

**一句话记忆：** 缺失修上游（数据+召回），排序修中游（融合+精排），整合修组装，幻觉修兜底。

### 5.4.3 知识冲突：检索结果互相矛盾

**是什么（通俗类比）：**

两份文档说法打架——2023 版手册说"质保一年"，2024 版改成了"两年"，检索把两份都捞回来，模型随便挑一个答，用户投诉。

**为什么：**
- 知识库天然有版本演进、多源冗余、过期末清理——冲突是常态不是意外
- LLM 面对 contradict 上下文行为不可预测（倾向靠前的 / 倾向新的 / 或干脆混编）

**怎么做（四种策略，按场景选）：**

1. **权威源优先**：元数据标记权威级（官方文档 > 论坛帖 > 草稿），rerank/组装时加权——适合有权威体系的库
2. **时效优先**：按文档时间戳取最新版本，旧的降权或过滤——适合版本演进型知识（产品文档、政策）
3. **显式呈现分歧**：Prompt 指示"上下文存在分歧时分别说明各方说法及来源"——适合争议性/多视角问题（不能替用户拍板时）
4. **元数据过滤废弃文档**：源头治理——入库打有效期/废弃标记，检索 pre-filter 直接排除——**治本，前三者都是治标**

**组合拳：** 源头治理（4）为主，兜底策略（1/2/3）按业务语义选，并在答案中暴露依据版本（"依据 2024-06 版手册"）让用户可校验。

---

### 🎤 面试这样答：「你的 RAG 效果不好，怎么系统性排查？」

> "我有一套固定的八步归因链，从上游往下游逐段验，绝不拍脑袋调参。第一步查改写：把改写日志打出来，看多轮指代消解对不对、有没有跑偏。第二步查切块：把 bad case 的 gold 文档拉出来看表格代码有没有被腰斩。第三步查召回——最关键的一步：拿标注集算 recall@k，gold chunk 不在 top-K 就是召回问题，专有名词搜不中就补 BM25 混合检索，整体召回低就换或微调 embedding。第四步查融合：RRF 参数、加权的话分数有没有归一化。第五步查 rerank：有没有精排、MRR 够不够。第六步查上下文组装：关键块是不是被截断或去重误伤，我会 dump 组装快照肉眼对。第七步查 Prompt：'仅基于上下文、无依据说不知道'的约束在不在，噪声块是不是多到稀释注意力。第八步查引用对齐：答案里的引用编号是不是真指向那个块。每一步都有指标可看，修复完在回归评测集上验证，不靠'感觉变好了'。本质就是把后端'链路逐段排查+指标归因'的事故处理方法论搬到 RAG。"（约 340 字）

**追问：**

1. **八步里最常见的问题出在哪？**
   答：bad case 分布里切块腰斩和召回缺失占大头（数据问题），其次是无 rerank 的排序问题——优化优先级永远是先数据后算法、先召回后生成。
2. **怎么快速区分检索问题还是生成问题？**
   答：看 gold chunk 在不在最终上下文里：在 → 生成问题（约束/组装），不在 → 检索问题。一个二分砍掉一半搜索空间。
3. **没有标注集怎么排查？**
   答：从线上负反馈反向构造——把点"无帮助"的问题拉出来人工标 gold 文档，攒 50~100 条就能跑 recall，滚动扩充成回归集。
4. **排查出 embedding 领域不适配怎么办？**
   答：用领域语料微调开源模型（BGE 系）对比 recall；短期缓解可上查询改写把黑话翻译成通用表述。

---

### 🎤 面试这样答：「检索回来的结果互相矛盾，怎么处理？」

> "分'治本'和'治标'两层。治本是源头治理：入库时给文档打元数据——来源权威级、版本号、生效时间、废弃标记，检索时 pre-filter 把过期废弃的挡在外面，大部分冲突在进入上下文前就解决了。治标是兜底，按业务语义三选一：版本演进型知识如产品文档政策，时效优先按时间戳取最新，答案注明'依据 2024-06 版'；有权威体系的库，权威源优先，官方文档权重压过论坛帖；争议性多视角问题不让模型替用户拍板，Prompt 明确'存在分歧时分别陈述各方说法及来源'。另外我会监控冲突率指标——冲突突然升高通常意味着知识库治理出了问题，比如某部门旧文档没下线，这是数据治理的告警信号，不只是 RAG 层的事。"（约 280 字）

**追问：**

1. **模型倾向引用上下文里靠前的块怎么办？**
   答：组装时按 rerank 分数把高置信块放前面本来就是合理利用；但要防"位置决定论"，评测时做位置交换测试验证稳健性。
2. **两份都是官方且同时有效但说法不同（不同产品线）？**
   答：说明元数据维度不够——补产品线/适用范围维度，检索时按用户上下文过滤到正确产品线，这是元数据工程不足的信号。

## 5.5 工程化难点（高频追问）

### 5.5.1 规模扩展：10 万 → 1000 万文档

**是什么（通俗类比）：**

像电商从单库单表到分库分表的演进——先是"单机够用"，再"读写分离"，最后"分布式拆分"。RAG 的扩展路径同构，只是数据换成了"向量+索引"。

**为什么：**
- 量级每上一个台阶，瓶颈就换一处：内存 → 检索延迟 → 写入吞吐 → 运维复杂度
- 面试官考的不是"你知道 Milvus"，是"你知道每一步瓶颈在哪、什么时候该动"

**怎么做（分阶段路径表）：**

| 阶段 | 规模 | 瓶颈 | 动作 |
|------|------|------|------|
| 起步 | ~10 万 | 都不是瓶颈 | 单机 pgvector/Qdrant，HNSW 全内存，别过度设计 |
| 成长 | 10万~500万 | 内存、建索引时长 | 换专业向量库；HNSW 调参；入库流水线批量化；元数据 pre-filter 收缩搜索空间 |
| 上量 | 500万~1000万+ | 单机内存放不下 / 延迟 / QPS | **Milvus 分布式**：分片+副本；IVF-PQ 压缩换内存；冷热分层（热数据 HNSW、冷数据 IVF-PQ/磁盘） |

**三条工程主线（贯穿各阶段）：**
1. **数据组织**：按业务域拆 collection/分区（租户/时间/领域），检索只打目标分区——分区本身就是最大的性能优化
2. **索引选型随规模切换**：百万级 HNSW 舒适；千万级内存吃紧 → IVF-PQ 或 DiskANN，拿 recall 损失换资源可控（再靠 ef_search/nprobe 调回一部分）
3. **容量规划**：内存 ≈ 向量数 × 维度 × 4B × 1.5（HNSW 图开销）——先算账再选型，这是后端的老本行

### 5.5.2 多租户与权限隔离

**是什么（通俗类比）：**

SaaS 多租户的老问题在向量库的翻版——A 公司的知识绝不能被 B 公司的员工检索到。

**怎么做（三级方案，按隔离强度排序）：**

1. **collection 级隔离**：每租户独立 collection——隔离最彻底，但租户几百以上管理爆炸；适合大客户少而重
2. **分区/partition 级隔离**：一个 collection 内按 tenant_id 分区——主流方案，隔离与成本的平衡点
3. **元数据过滤级隔离**：全文档带 tenant_id + acl 字段，检索时 pre-filter——最省资源，但**过滤条件漏写就是越权事故**，必须框架层强制注入而非业务代码手拼

**权限细粒度（部门/角色级）：** 入库时把 ACL 写进元数据，检索时按用户身份动态生成过滤条件（呼应 L4 元数据工程）。**关键原则：权限过滤必须在检索层 pre-filter 做，不能检索完在应用层后筛**——否则 top-K 被无权文档占满，有权的相关文档被挤出去，结果又少又慢。

### 5.5.3 文档更新/删除的索引同步与入库补偿

**是什么（通俗类比）：**

"缓存与数据库一致性"在向量库的重演——源文档库是 truth，向量库是衍生物，套路全是后端熟悉的。

**怎么做（同步链路图）：**

```text
文档系统(源库, truth) ──变更事件──▶ MQ ──▶ 消费者：
                                      解析 → 切块 → embedding → 向量库 upsert/delete
        │
        ├─ 更新 = 按 doc_id upsert（同 id 覆盖）
        ├─ 删除 = 按 doc_id 批量删 chunk 向量
        │          （入库时必须存 doc_id → chunk_ids 映射外键）
        ├─ 幂等：以 (doc_id, version) 为幂等键，重复消费不产生脏数据
        ├─ 顺序：同 doc_id 按 version 大者胜，乱序到达不旧盖新
        └─ 补偿：定时对账任务比对源库与向量库的
                 (id, version, checksum) 集合，差异自动修复 + 告警
```

- **对账补偿是兜底底线**：MQ 丢消息、消费重试超限，最终靠定时对账拉回一致性——**接受最终一致，用对账保证收敛**
- **入库失败补偿**：重试队列（指数退避）→ 死信队列人工介入 → 监控"源库有、向量库无"的差集告警
- 全量重建不停服：新版本独立 collection 双跑验证后切别名，旧版保留可回滚（蓝绿式切流）

### 5.5.4 幻觉三板斧（背下来）

**是什么（通俗类比）：**

防幻觉像防洪——第一道堤坝约束水流（Prompt），第二道控制水源（检索质量），第三道泄洪区兜底（拒答+溯源）。

**怎么做（按防线顺序）：**

1. **第一斧 · Prompt 硬约束**：System 写死"仅基于提供的上下文回答；上下文无依据时明确说'知识库中未找到相关信息'"——零成本，但约束不是保证，模型仍可能违例
2. **第二斧 · Rerank 卡源头**：幻觉一大来源是"错误但看起来相关的块"混进上下文——rerank 把不相关块挡在门外；同时用 rerank 分数做置信度：最高分低于阈值 = 检索质量差 → 直接触发拒答或降级
3. **第三斧 · 强制引用溯源 + 低置信拒答**：答案逐条带 [n] 引用，出口做引用校验（被引的块确实支撑该陈述）；整体置信度低（检索分低/引用覆盖不足）→ 拒答话术 + 转人工/推荐相似问题——**宁可无答，不可错答**，企业场景铁律

### 5.5.5 降级与兜底：RAG-Fusion / 备用小模型

**是什么（通俗类比）：**

微服务降级链的 RAG 版：主链路挂了不能白屏，按故障程度逐级砍功能、换组件，保住"永远有回应"。

**怎么做（降级链）：**

```text
完整链路：改写 + 混合检索 + Rerank + 大模型生成（带引用）
   │ BM25 路异常 / rerank 超时
   ▼
降一级：单路向量检索 + 跳过 Rerank（精简模式）
   │ 向量库异常 / 超时
   ▼
降二级：跳过检索，备用小模型直答（声明"未挂知识库"）
   │ 主模型异常 / 熔断
   ▼
降三级：语义缓存找最相似历史优质答案 / 规则话术 + 转人工
```

- **备用小模型兜底**：主 LLM 熔断时切备用厂商/小模型，关键是**上下文交接**（对话历史 + 已生成半截内容打包重放）
- **语义缓存兼兜底**：检索+生成全挂时，拿 query 向量在历史优质问答里找最相似回复（相似度阈值从严）
- 所有降级流量打标，事后用 trace 复盘降级原因（呼应 L8 生产化）

---

### 🎤 面试这样答：「文档更新删除时，向量索引怎么同步？失败怎么补偿？」

> "我把向量库当衍生物，源文档库是唯一 truth，这就是经典的数据同步一致性问题。链路上，文档系统发变更事件到 MQ，消费者做解析、切块、embedding，然后按 doc_id upsert 或批量删 chunk——这里有个细节：入库时必须维护 doc_id 到 chunk_ids 的映射，否则删除时不知道该删哪些向量。三个可靠性设计：一是幂等，以 doc_id 加 version 做幂等键，MQ 重复投递不产生脏数据；二是顺序，同文档更新按 version 大者胜，乱序到达不会旧盖新；三是补偿，这是兜底底线——定时对账任务比对源库和向量库的 id、version、checksum 集合，'源库有向量库无'的差集自动补，删除失败的僵尸向量清掉，差异超阈值告警。中间态我接受最终一致——用户检索到几百毫秒前的旧版本文档业务可容忍，但对账保证最终收敛。入库失败走重试队列指数退避，超限进死信队列人工介入。本质就是把缓存一致性那套'事件驱动+幂等+对账'搬过来，多了 embedding 这个慢环节要异步批量化而已。"（约 330 字）

**追问：**

1. **为什么不用双写（写文档库同时写向量库）？**
   答：双写有一致性窗口和部分失败难题（一边成功一边失败），且 embedding 是慢操作会拖垮写路径。事件驱动异步解耦，失败可独立重试。
2. **文档高频小改（价格表每天改）怎么办？**
   答：按 chunk 级内容指纹做增量——只对变化的 chunk 重新 embedding 和 upsert，未变的复用，省算力。
3. **权限变更（文档从可见改不可见）也要同步吗？**
   答：不用动向量库——ACL 在元数据里，权限判断在检索 pre-filter 动态做，这正是"权限过滤放检索层"的设计红利。

## 进阶篇：高级岗深挖区（RAG 主战场的决胜局）

> 基础篇回答"是什么、怎么做"；进阶篇回答"数字是多少、为什么是这个值、翻过什么车"。RAG 是面试主战场，而主战场的决胜局在深挖链——**数字感是最快的试金石**，一问便知真调过还是背的。

### A. 二层追问链（面试官的深挖套路）

高级岗节奏：你答出概念（第一层）→ 面试官追问参数与数字（第二层）→ 再追边界与取舍（第三层）。以下五条链是 RAG 高频深挖路径，对话体演练。

#### A.1 二层追问链：RRF 的 k

> **追问：** "你说 RRF 用 k=60，这个 60 哪来的？"
>
> **答：** 经验值，来自 RRF 原论文（Cormack et al. 2009）在 TREC 融合任务上的实验——作者扫了一片 k 值，发现融合质量对 k 不敏感，60 附近表现稳定，就定成了默认。它不是理论推导的最优解，是"实验证明怎么调都不太坏"的鲁棒默认值。

> **再追问：** "那 k 调大调小分别意味着什么？"
>
> **答：** k 是排名差异的平滑器。k 大（比如 1000）：第 1 名和第 10 名的贡献几乎一样——融合接近"纯投票"，两路都收录的文档吃香；k 小（比如 1）：头部排名的差距被急剧放大——单路冠军几乎独裁。多数场景两路质量相当时取默认 60；想让"双方都认可"的文档更强就调大，想让"某一路非常靠前"的文档更强就调小。

> **再追问：** "什么时候你会放弃 RRF 换加权融合？"
>
> **答：** 两个前提同时满足才换：一是两路检索质量悬殊——比如向量路明显强、BM25 只兜底，RRF 的"平权投票"会强行抬升弱路噪声；二是有校准集能稳定估计归一化参数和权重——加权融合要解决分数归一化（余弦挤在高段、BM25 无上界），参数随数据分布漂移，没有标注集校准就是盲调。两者缺一，RRF 的鲁棒性都更值钱。

#### A.2 二层追问链：Rerank 的延迟账

> **追问：** "Cross-Encoder 为什么慢？Bi-Encoder 不是也要过模型吗？"
>
> **答：** 结构决定的。Bi-Encoder 的文档向量离线预计算好了，在线只算一次 query 向量然后比距离——O(1) 次模型调用；Cross-Encoder 把 query 和每个候选拼成一对**逐对现算**，50 个候选就是 50 次完整的前向传播，而且交叉注意力的序列长度是两段拼接之和，计算量不是加法是乘法级感受。慢的不是"过模型"，是"每个组合都要重新过模型"。

> **再追问：** "给个延迟数字感觉。"
>
> **答：** 中等大小的 rerank 模型（bge-reranker-base 级），单对 GPU 推理 5~10ms 量级。50 对串行就是 250~500ms——对话式产品 P95 直接爆。所以裸用 cross-encoder 是不可接受的，必须配优化。

> **再追问：** "四板斧各自能省多少？"
>
> **答：** 按性价比排序：① **top-k 截取**：50→20 对，延迟直接砍 60%，效果几乎无损（真相关的块很少排在 RRF 融合后 20 名开外）；② **batch 推理**：50 对拼一个 batch 一次 GPU 前向，均摊后单对成本降到 1~3ms，**这是最大头，通常 5~10 倍加速**；③ **GPU 常驻 + 算子优化**：模型驻内存免加载、FP16/INT8 量化，再拿 30~50%；④ **蒸馏小模型**：把大 reranker 蒸馏到 4 层小模型，单对降到 1~2ms，recall@3 掉 1~2 个点换延迟。组合拳下来：500ms → 60~80ms 级，才进得了生产。

#### A.3 二层追问链：多路召回的"路数"

> **追问：** "两路召回够吗？要不要再加？"
>
> **答：** 先问加路解决什么问题。向量管语义、BM25 管精确匹配，两路覆盖了绝大多数查询模式。值得考虑的第三路是**学习型稀疏向量**（SPLADE / BGE-M3 的稀疏头）——它是"模型学出来的加权词袋"，会激活同义词、压低停用词，本质是 BM25 的学习增强版。

> **再追问：** "什么时候第三路真的值得？"
>
> **答：** 两个信号：一是 bad case 分析发现"同义词改写型 miss"集中——用户说"退款"，文档写"售后返还"，BM25 搜不中、向量语义又偏了，稀疏路的词项扩展能救；二是本来就用 BGE-M3——稠密稀疏一套模型一次推理同时产出，第三路的**边际成本接近零**，白捡。反过来，如果要多部署一套 SPLADE 模型、多维护一条索引，收益撑不起成本。

> **再追问：** "为什么不加第四路第五路？"
>
> **答：** **边际收益递减**。前三路各自覆盖一类查询模式（语义/精确/词项扩展），第四路之后新增路和已有路高度重叠，每路召回的增量 bad case 修复个位数百分比，但延迟（串行路数）和运维面（每路一套索引+调参+监控）线性涨。数字感觉：两路→三路可能 +2~3 个点 recall，三路→四路通常 <1 个点。**3 路之后该投入的不是新召回路，是 rerank 和数据质量**。

```text
  召回收益                     多路召回的边际收益递减曲线
  ▲
  │            ● 向量+BM25+稀疏(三路)   ← +2~3pt，BGE-M3 下近零成本
  │          ╱    ─ ─ ─ ─ ─ ● 第四路    ← <+1pt，不值得
  │        ● 向量+BM25(两路)            ← 混合检索主力收益 +5~8pt
  │      ╱
  │    ● 纯向量(一路,baseline)
  │  ╱
  └───────────────────────────────────▶  召回路数
     1         2         3         4
  结论: 3 路之后, 边际成本 > 边际收益
        该砸的是 rerank 和数据质量, 不是新召回路
```

#### A.4 二层追问链：Embedding 维度

> **追问：** "768 / 1024 / 1536 / 3072 维怎么选？"
>
> **答：** 维度是表达力和成本的滑杆。768 是老一代基线（BERT 系），1024 是当前中文开源主力（BGE-large 级）的性价比点，1536/3072 是 OpenAI text-embedding-3 的档位。选型逻辑：先在标注集上对比几个维度档位的 recall@10——**很多业务语料 1024 和 3072 的差距在 1 个点以内**，而存储内存计算成本是 3 倍。我的默认起点：中文 1024，多语言或语义特别复杂的语料再试 1536+，用数据说话。

> **再追问：** "Matryoshka 嵌入为什么能截断？截完掉多少？"
>
> **答：** 概念级讲：训练时不止对全长向量算损失，**对 1/2、1/4、1/8 长度的前缀子段各算一份损失加权求和**——强迫模型把最重要的语义信息"前置"到前面的维度，后面的维度是精细化修正。所以截断后向量仍然语义有效，像俄罗斯套娃每层都是完整的娃。数字感觉：1024 截到 256（1/4），recall 通常只掉 1~3 个点——换来 4 倍的存储和检索成本下降。

> **再追问：** "这个截断特性生产里怎么用？"
>
> **答：** 经典玩法是**两阶段检索**：入库只存一份 1024 维，但建一个 256 维的粗排索引（前缀截断，扫描快 4 倍）粗筛 top200，再用全长 1024 维精排出 top50——粗排用套娃、精排用全长，一套向量两种用法，存储不翻倍。

#### A.5 二层追问链：HNSW 参数

> **追问：** "M 和 ef_construction 什么关系？调哪个疼？"
>
> **答：** 都是建索引期参数，疼法不同。M 是每个节点在图里的连接数——图的结构参数，调大意味着图更稠密、recall 上限更高，**内存按 M 线性涨**（每个连接要存邻居 id）；ef_construction 是建图时的搜索宽度——只影响建图质量，**不影响运行时内存**。调大 M：内存永久涨；调大 ef_construction：只让建库慢，一次性的。所以经验是 M 从默认起步别乱动，ef_construction 可以给狠一点（128~256）换图质量。

> **再追问：** "为什么 ef_search 是运行时旋钮，M 不是？"
>
> **答：** 因为**索引结构建完就凝固了**。M 决定图长什么样——节点、边、邻居表在建库那一刻写死，改 M 等于重建整个索引（全库重算图，小时级）；ef_search 只是查询时"在图上走多宽再停"的搜索半径，图没变、只是遍历策略变了——改个参数立即生效，毫秒级代价。这就是"结构参数 vs 策略参数"的区别，类比：表结构改起来要重建，SQL 的 limit 是免费的。

> **再追问：** "给我一套完整调参流程。"
>
> **答：** ① 从默认起步：M=16、ef_construction=128（或 64）、ef_search=64；② 建好标注集，测 baseline recall@10（比如 0.94）；③ 定业务目标线（如 recall@10 ≥ 0.97 且 P95 < 50ms）；④ 不达标先拧 ef_search——最便宜的旋钮，64→128→256 逐档测，通常 recall 能爬 1~3 个点，延迟涨 30~50%；⑤ 还不够才动 M（16→32）并接受**全量重建**，内存涨约一倍换 recall 上限抬高；⑥ 途中发现延迟爆了，回退 ef_search 或上 PQ 压缩。**方法论核心：先建 baseline，再按"改起来便宜的先动"排序——参数调整顺序本身就是工程经验的体现。**

### B. 生产 Case Study ×2（STAR-L，含数字）

> 高级岗的杀手锏不是"知道所有优化手段"，而是**"讲得出带数字的完整故事"**。以下两个 case 是叙事模板：每个都符合 STAR-L（情境-任务-行动-结果-复盘），数字是编好的合理量级，面试时替换成自己的真实数据。

#### B.1 Case：检索质量恶化之谜（上线三个月召回缓降）

**S（情境）**：企业知识库问答，上线时 recall@10 = 92%、答案采纳率 87%，运行平稳。第三个月，用户负反馈周环比连续上涨。

**T（任务）**：定位质量退化根因并修复，建立防回归机制。

**A（行动）**——排查走了弯路，弯路本身就是故事：
1. **先怀疑模型**（错误方向）：检查 embedding 服务版本、LLM 版本——都没变过，排除
2. **再怀疑参数**（错误方向）：HNSW 索引健康检查、ef_search 配置——正常
3. **回归评测集跑分**：固定评测集上 recall@10 = 91%，**几乎没掉**——关键矛盾出现：线上在掉、离线不掉，说明**问题在评测集没覆盖的部分**
4. **线上流量下钻**：拉线上 bad case 的 query 做聚类，发现两件事：
   - 知识库三个月来被业务部门灌了大量低质量文档（复制粘贴的会议纪要、重复草稿），占比升到 18%——**噪声文档挤占 top-K**，把好文档顶出去
   - 查询分布漂移：新产品上线后，用户开始问新领域问题（占比 23%），而新领域文档**入库了但元数据没打标**，被 pre-filter 误杀一部分
5. **修复三件套**：
   - 入库口加**文档质量分**（长度、重复度、来源等级综合打分），低于阈值拒入或降权
   - bad case 的 query 挖掘做成**每周例行**，评测集每月滚动扩充（分布漂移不再隐身）
   - 元数据打标流程固化：新领域文档入库必须带 domain 标签，漏标告警

**R（结果）**：修复后一个月，线上 recall@10 回到 91%（线上口径，采样标注），负反馈率回落到基线；知识库质量分纳入周报。

**L（复盘）**："这次事故最大的教训是**离线指标好≠线上没病**——评测集是静态的，流量是活的。此后我把'评测集滚动更新'和'查询分布监控'当成 RAG 系统的一等公民，而不是一次性交付物。如果重来，上线第一天就该配上线上采样标注 + 分布漂移告警。"

#### B.2 Case：一次 RAG 效果优化冲刺（两周 faithfulness 0.78 → 0.93）

**S（情境）**：内部文档助手，用户投诉"答非所问、编造参数"，基线 faithfulness = 0.78（RAGAS 口径）。

**T（任务）**：两周冲刺，目标 faithfulness ≥ 0.90，不改底层模型。

**A（行动）**——每轮只动一个变量，指标隔离归因：

```text
  faithfulness
  0.95 ┤                                        ● 0.93
       │                              ● 0.90 ──┘ 第4轮 +3pt
  0.90 ┤                    ● 0.87 ──┘ 第3轮 +3pt
       │          ● 0.83 ──┘ 第2轮 +5pt (最大单轮收益)
  0.80 ┤● 0.78 → ● 0.82 ──┘ 第1轮 +4pt
  0.78 ┤baseline
       └──┬────────┬────────┬────────┬────────┬──▶ 时间
        Day0     Day3      Day6      Day9     Day12
  第1轮查询改写  第2轮混合检索  第3轮Rerank  第4轮Prompt约束+引用校验
```

- **第 1 轮（+4pt）查询改写**：上线小模型指代消解 + 术语标准化（内部黑话→文档标准词）。工具：7B 微调小模型；成本：每 query +30ms、GPU 一张卡摊薄。归因：改写后召回的 query-doc 语义对齐度提升
- **第 2 轮（+5pt，单轮最大）混合检索**：BM25 双路 + RRF。工具：ES 8.x（团队已有）；成本：+15ms/查询。归因：错误码/型号类 miss 全部修复——**印证"数据侧和召回侧的收益天花板最高"**
- **第 3 轮（+3pt）Rerank**：融合后 top30 进 bge-reranker，取 top5。工具：自部署 + batch；成本：+70ms、一张 T4。归因：context precision@5 从 0.71 → 0.89，噪声块被挡在门外
- **第 4 轮（+3pt）Prompt 约束 + 引用校验**："仅基于上下文 + 无依据拒答"硬约束，出口做引用覆盖率校验，低置信触发拒答话术。成本：零边际成本。归因：幻觉兜底把"错误但自信"的回答变成"明确说不知道"

**R（结果）**：faithfulness 0.78 → 0.93，答案采纳率 +11pt；总延迟 P95 从 1.8s → 2.1s（rerank 和改写的代价，业务可接受）。

**L（复盘）**："优先级排序是这次最值钱的产出：**改写和召回端收益大（9pt）且便宜，精排和约束端收益稳（6pt）但有延迟代价**。如果预算只够做一轮，我选混合检索——单轮 +5pt、15ms、用现有 ES。这个'每轮只动一个变量、指标隔离归因'的打法，比任何单项技术都更值得写进团队 SOP。"

### C. 指标体系深算题（30 秒口算演示）

> 高级岗面试官爱出"现场算一笔账"——考的不是精确数字，是**量级感和单位换算的熟练度**。以下三题是典型题，答案给到口算路径。

#### C.1 深算题一：recall@10 从 0.85 → 0.92，对最终答案正确率影响多大？

**口算路径（链式衰减模型）：**

```text
端到端正确率 ≈ 召回率 × 排序命中率 × 生成忠实度   (链式乘积)

假设排序命中率 0.95、生成忠实度 0.90 固定:
  recall 0.85:  0.85 × 0.95 × 0.90 = 0.727
  recall 0.92:  0.92 × 0.95 × 0.90 = 0.787
                                     ────────
                                +6 个百分点

关键洞察:
· 检索是链路第一环, 它的天花板就是全链路天花板
· "漏检 ≈ 该题必答错" —— gold chunk 不在上下文,
  下游全链路再优秀也救不回来 (乘法链的残酷性)
· 反过来: 生成端从 0.90 提到 0.97, 收益上限只有 5.5pt
  —— 这就是"先修检索再修生成"的数学依据
```

**答**：约 +6 个百分点。核心逻辑是链式乘积——检索是第一环，漏检无法被下游弥补，所以召回率的提升几乎 1:1 传导到端到端上限。

#### C.2 深算题二：100 万 chunk × 1024 维 × float32，向量库占多少内存？

**口算路径：**

```text
第一步: 原始向量体积
  1,000,000 × 1024 维 × 4 字节 = 409.6 万字节/chunk × 100万
  = 4 GB                                (百万×千维×4B ≈ 4GB, 好记)

第二步: HNSW 图开销 (邻居表+索引结构, 经验系数 ~1.5)
  4 GB × 1.5 = 6 GB                     ← 全内存 HNSW 的真实账

第三步: 量级参照
  · 1000 万 chunk 同配置 → 60 GB    ← 单机内存开始吃紧
  · 换 IVF-PQ (压到 64B/向量): 100万 × 64B = 64MB (千分之一量级)
    代价: recall 掉 3~5pt, 可用 ef_search 找回一部分
```

**答**：裸向量 4GB，HNSW 全内存方案实际约 6GB。顺手给出延伸：千万级就到 60GB——这就是 5.5.1 说"上量阶段换 IVF-PQ/分布式"的数字依据。**内存 ≈ 向量数 × 维度 × 4B × 1.5 这个公式背下来，选型会上直接用。**

#### C.3 深算题三：日均 5 万 query × top-50 rerank，本地 GPU vs API 月成本？

**口算路径：**

```text
先算总量: 5万 query/日 × 50 对 = 250万 对/日 ≈ 7500万 对/月

方案A · API rerank (Cohere 级, 按 query 计费 ~$2/千次):
  150万 query/月 × $2/1000 = $3,000/月
  (按对计费的国产 API 折算量级相近, ¥1~2/万对)

方案B · 本地 GPU (bge-reranker, 一张推理卡):
  吞吐 ~2000 对/秒 (batch) → 250万对/日 ≈ 21 分钟纯算/日
  卡折旧+电+运维 ≈ $400~600/月 → 吞吐只用了 1.5%
  一张卡绰绰有余, 还能跑别的离线任务

结论: 本地方案约为 API 的 1/5~1/6 成本, 且数据不出域;
     但要自己背运维、扩容、故障切换
决策线: 日 query < 1万 且无 GPU 团队 → API 省心;
       日 query > 5万 或数据敏感 → 本地自部署
```

**答**：API 约 $3000/月，本地一张卡约 $400~600/月——量级差 5 倍。但要把"运维人力"算进去：没有 GPU 平台团队支撑时，API 的省心溢价是真实成本。**成本题的满分答案永远是"两边都算 + 给决策线"，只报一边数字是半分。**

### D. 高级视野：从"会用"到"有判断"

#### D.1 "背流程的人" vs "排过优先级的人"（答法差异对比）

同一道题，两种回答，高下立判：

| 面试题 | 背流程的人（B 档） | 排过优先级的人（A 档） |
|--------|------------------|----------------------|
| "RAG 效果差先改什么？" | "可以优化切块、加混合检索、上 rerank、改 prompt……"（罗列手段，无排序） | "先跑分层评测定位坏在哪层。**检索层坏了先看召回**——gold chunk 不在 top-K 就砸召回端（改写+混合检索，便宜且收益大）；召回没问题再治排序和生成。**只动一个变量，指标隔离归因**"（先归因、再排优先级、有方法论） |
| "怎么防幻觉？" | "prompt 里写不要编造"（单点手段） | "三板斧按防线排序：约束是下限不是保证，rerank 卡源头挡'看似相关的错误块'，引用校验+低置信拒答是兜底——**宁可无答不可错答**是我们的业务红线"（分层防御+业务判断） |
| "为什么这么设计管线？" | "业界都这么做"（从众） | "每一环补一类特定损失：改写补 query 质量、双路补召回盲区、rerank 补排序精度、约束补生成失控——**去掉哪一环，对应指标会掉多少，我测过**"（每环有存在理由+数字） |

**规律**：B 档回答的特征是"并列罗列"（把知道的都说一遍）；A 档的特征是"决策链"（先做什么后做什么、为什么、代价是什么）。**手段是查得到的，优先级判断才是你的。**

#### D.2 2025→2026 RAG 演进趋势判断

**趋势一：Agentic 化——检索从"流程"变成"决策"**
固定管线的边际优化已近天花板（混合检索+rerank 成标配后大家差距缩小），竞争点移到"动态决策"：要不要检索、检索哪个源、结果够不够、要不要换策略再来一轮。RAG 不再是系统本身，而是 Agent 工具箱里的一个工具（呼应 5.3.1）。**判断：Agentic RAG 会从"高级题"变成"标配题"，但成本纪律（路由分流、循环上限）决定它能不能进生产。**

**趋势二：评估左移——数据质量先于检索调优**
行业共识在向"RAG 上限由数据决定"收敛（呼应 L4）：与其在检索算法上内卷，不如在入库前把文档质量、切块质量、元数据完备性做好。评测也从"上线后看指标"左移到"入库前测数据"（文档质量分、切块抽检）。**判断：'用数据质量视角讲 RAG 优化'的候选人，比'用算法视角讲'的更显资深。**

**趋势三：长上下文没有杀死 RAG——四个理由**
窗口 128K~1M 后"全塞进去"依然输给 RAG，因为：① **成本**：每请求全量 token，知识库 MB 级时 token 费不可接受，RAG 只送 top-K；② **延迟**：长上下文首字延迟显著变慢，prefill 是用户能感知的等待；③ **权限**：全量塞入等于给模型看所有文档，多租户 ACL 无法执行——检索层 pre-filter 是权限的唯一执行点；④ **可解释**：RAG 能给出"答案依据这 3 块文档"的溯源，全塞进去无法定位出处。**判断：长上下文和 RAG 是互补——长窗口让"塞 top-20 而不是 top-5"成为可能，检索质量反而更重要了。**

#### D.3 面试官心理：RAG 深挖题在筛什么

RAG 是 AI 应用岗的"必考大题"，深挖链的设计意图非常明确：

```text
面试官的筛人漏斗:
"讲讲你的 RAG 架构"        ──▶ 筛掉没做过的 (连管线都画不顺)
"为什么加 BM25/rerank?"    ──▶ 筛掉只跑过 Demo 的 (说不出短板场景)
"recall 多少? 延迟多少?"   ──▶ 筛掉没管过线上的 (没有数字感)
"效果掉了怎么排查?"        ──▶ 筛掉没踩过坑的 (没有事故叙事)
"成本怎么控制? 何时不用?"  ──▶ 筛掉没做过取舍的 (没有决策权或没思考)
```

**数字感是最快的试金石**——"recall@10 大概多少、rerank 加多少毫秒、100 万 chunk 占多少内存"这类题，真调过的人 3 秒出量级，背题的人当场卡壳。所以进阶篇的所有数字不必精确，但**量级和换算路径必须形成肌肉记忆**。反过来说，面试中主动给出数字（"我们 rerank 后 MRR 从 0.62 到 0.81"）是最高效的 credibility 信号。

---

### 🎤 面试这样答：「你的 RAG 上线三个月后效果持续变差，怎么排查？」

> "这个我真踩过。核心方法论一句话：**离线评测集没掉、线上在掉，问题一定在评测集没覆盖的地方**。我的排查顺序：先排除静态因素——embedding 版本、LLM 版本、索引参数，这些有变更管理，一查便知；然后固定评测集跑分，如果掉了说明是回归（配置或数据变更），没掉就把矛头指向两处动态因素。第一是**知识库质量漂移**：业务部门持续灌文档，低质量的会议纪要、重复草稿占比悄悄升到快两成，噪声块挤占 top-K——我们拉线上 bad case 聚类实锤的，解法是入库口加质量分过滤。第二是**查询分布漂移**：新产品上线后用户开始问新领域，而新文档元数据没打标被误杀——解法是补标签+告警。事后复盘我加了两道防回归：线上采样标注做成每周例行（线上口径 recall），bad case 的 query 每月滚动扩充进评测集。教训就一条：**评测集是静态的、流量是活的，RAG 系统的数据面和流量面都要有监控，不然退化是隐形的**。"（约 320 字）

**追问：**

1. **为什么第一反应不是调 ef_search 这类参数？**
   答：参数是静态的、有变更管理的——三个月没人动过它就不可能是主因。先查"什么变了"（数据、流量），再查"什么可能一直坏但刚暴露"，最后才是参数调优。
2. **线上 recall 怎么测？没有 ground truth。**
   答：采样标注——每周抽几百条线上 query，人工标注 gold 文档算 recall；或用 LLM-as-Judge 辅助初筛 + 人工复核争议样本，成本和准确性折中。
3. **怎么区分"知识库变差"和"查询变难"？**
   答：分群对比——老 query 群的 recall 趋势 vs 新 query 群：只有新群掉 = 查询漂移，两群都掉 = 知识库劣化。控制变量做归因，跟 A/B 分析同一套思路。

---

### 🎤 面试这样答：「讲讲你做过的 RAG 优化，优先级怎么排的？」

> "我讲一个两周冲刺，faithfulness 从 0.78 做到 0.93。打法就一条纪律：**每轮只动一个变量，指标隔离归因**。优先级排序的逻辑是'收益天花板 × 实施成本'：第一轮上查询改写（小模型指代消解+术语标准化），+4 个点，成本每 query 30ms；第二轮上混合检索（BM25+RRF），单轮 +5 个点是最大收益，成本才 15ms——因为错误码型号类 miss 是我们 bad case 大头，**数据侧和召回侧的天花板最高，这是我排第一优先级的依据**；第三轮 rerank 精排 top30，+3 个点，代价 70ms 和一张卡；最后 prompt 约束加引用校验，+3 个点，零边际成本收尾。你看这个顺序：改写→召回→排序→生成，**恰好是从链路上游往下游修**——因为上游是乘法链的第一环，漏检无法被下游弥补，这也是我判断'先修检索再修生成'的数学依据。如果预算砍半只许做两轮，我保混合检索和 prompt 约束：一个收益最大，一个零成本，这是性价比的极值点。"（约 330 字）

**追问：**

1. **为什么每轮只动一个变量？同时上多个不更快吗？**
   答：快但归因就废了——两个手段一起上，+7 个点不知道谁的功劳，坏 case 也不知道该回滚谁。冲刺期两周一轮 A/B 的时间成本付得起，换来的是可复制的优先级经验。
2. **faithfulness 0.93 之后为什么停了？剩下的 0.07 是什么？**
   答：剩下的主要是标注口径分歧（judge 判严判松）和确实有歧义的文档——继续压要动数据治理，投入产出比拐点已过，性价比不如去修别的指标。
3. **这个优先级换一个业务还成立吗？**
   答：方法论成立、结论不一定。如果那个业务的 bad case 大头是"排序错"而不是"召不回"，第一优先级就换成 rerank。**优先级来自你自己的 bad case 分布，不是通用公式——这才是这道题真正考的。**
