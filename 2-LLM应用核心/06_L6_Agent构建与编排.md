# 第 6 层:Agent 构建与编排

## 本章导读

> **考察频率:★★★★★**
> 这是 AI 应用工程师面试的"架构师分水岭"。前面五层(RAG、Prompt、知识库)考的是"让 LLM 回答得对",
> 这一层考的是"让 LLM **干活干得对**"——会调工具、会规划、会停、出错会兜底。
> 对后端来说,这里是你的主场:Agent 本质上是一个**分布式系统问题**,
> 重试、幂等、超时、熔断、审计、权限——全是你熟悉的后端老三样,只是"调用方"从代码换成了一个不靠谱的 LLM。

**面试官想听什么:**

1. 不是"我会用 LangChain 搭 Agent",而是——**你怎么控制一个不靠谱的组件在业务流程里靠谱地工作**;
2. 选型判断力:什么时候 Workflow 就够了,什么时候才值得上 Agent(反模式:为了炫技上 Agent);
3. 容错设计:工具失败了怎么办、循环停不下来怎么办、重复扣款怎么办、越权了怎么办;
4. 工程闭环:幂等键、Dry-run、审计日志、人工审批、爆炸半径——这些词能不能自然地说出来。

**一句话心法:**

> Agent = LLM + Tools + State + Control Loop
> (大脑 + 双手 + 记忆 + 流程控制)

## 6.1 核心范式:Workflow vs Agent 与三种经典模式

### 6.1.1 先搞清楚:Agent 到底是什么

**是什么(通俗类比):**

- **LLM 裸调** 像一个"只会说话的顾问"——你问它答,答完就完,不碰任何真实系统;
- **Workflow(工作流)** 像一条**工厂流水线**——A→B→C→D 步骤写死,每一步干什么是代码规定的,LLM 只是流水线上的"智能工位";
- **Agent** 像一个**拿到了工具箱的实习生**——你给它一个目标,它自己看情况决定:先查什么、再调什么工具、拿到结果后下一步干什么,直到任务完成。

**为什么要有 Agent:**

有些任务的路径**事先无法穷举**。比如"帮我处理这封客诉邮件"——要先判断投诉类型,查订单还是查物流?
要不要补偿?补偿金额超没超权限?每一步都依赖上一步的结果。你没法用 if-else 写死,只能让 LLM 在运行时动态决策。

**怎么做(骨架):**

```
最简 Agent 循环(伪代码):

while not finished:
    thought  = LLM.think(目标, 历史, 工具列表)     # 推理:下一步干嘛
    action   = LLM.choose_tool(工具列表)            # 行动:选工具+参数
    obs      = runtime.execute(action)              # 执行:真正调 API
    state.append(thought, action, obs)              # 状态:记录到上下文
    finished = LLM.is_done() or 触发停止条件         # 控制:该停就停
```

四个要素:LLM(大脑)、Tools(手)、State(记事本)、Control Loop(刹车和方向盘)。

### 6.1.2 Workflow vs Agent 选型(必考中的必考)

**是什么(通俗类比):**

- Workflow 是**跟团游**:路线固定、成本可控、去哪都知道,但遇到突发情况不会变通;
- Agent 是**包车自由行**:司机(LLM)现场决定路线,灵活,但可能绕路、超预算、甚至开错地方。

**为什么必须先做这个选型:**

Agent 的灵活性是用**真金白银和稳定性**换来的:每一轮决策都是一次 LLM 调用(贵、慢),
而且决策是概率性的(不可复现、难测试)。Anthropic 的经典建议也是:**能 Workflow 就 Workflow,Agent 是最后手段**。

**对比表:**

| 维度 | Workflow(固定流程) | Agent(动态决策) |
|---|---|---|
| 流程 | 代码写死,LLM 只在节点内干活 | LLM 运行时决定下一步 |
| 可预测性 | 高,路径可枚举 | 低,同输入可能不同路径 |
| 可测试性 | 强(单测每个节点) | 弱(需要 trace 级评测) |
| 成本 | 低(固定次数调用) | 高(循环多轮,Token 不可控) |
| 延迟 | 低且稳定 | 高且波动大 |
| 调试难度 | 低(打日志看节点) | 高(需要全链路 trace) |
| 适用场景 | 步骤确定、输入结构化 | 路径依赖中间结果、无法穷举 |
| 典型例子 | "邮件→分类→模板回复" | "处理客诉:自主查单/判断/给方案" |

**怎么做(决策口诀):**

```
选型三问:
1. 流程能不能提前写死?  → 能:Workflow;不能(分支依赖中间结果):才考虑 Agent
2. 错误容忍度多高?      → 低(资金/生产环境):Workflow + 强校验;高(内部工具):可 Agent
3. 成本预算多少?        → 每请求几厘钱:Workflow;愿意为灵活性付 10 倍成本:Agent

实务做法:混合架构 —— 外层 Workflow(确定性骨架),个别"卡壳"节点内嵌 mini-Agent(局部自主)
```

**"什么问题不值得用 Agent?"——标准答法(三要点):**

1. **低复杂度**:一两步 LLM 调用或规则就能解决(如情感分类、格式转换)——上 Agent 纯属杀鸡用牛刀;
2. **高确定性**:输入输出映射稳定,没有"动态决策"空间(如固定字段抽取)——Workflow 又便宜又稳;
3. **成本/延迟敏感**:高频、大批量、对价格和响应时间敏感的场景——Agent 的循环调用会放大成本和延迟 10 倍以上。

再加一句体现认知深度:"**Agent 不是产品,是兜底**——我们把 80% 的请求走确定性流程,
只有流程处理不了的 20% 才路由给 Agent,这是成本和灵活性的帕累托最优。"

**反模式(面试官等你跳的坑):**

- "我们用了 AutoGPT/CrewAI 所以很厉害" —— 炫技式上 Agent,结果不可控、不可测、不可预算;
- 把 Agent 当"万能胶水":所有系统间调用都让 LLM 决策 → 纯属用概率系统干确定性中间件的活;
- 全链 Agent:从意图理解到落库全程自主 → 一旦 prompt injection,整条链全部暴露。

### 6.1.3 ReAct:推理-行动-观察循环

**是什么(通俗类比):** 像一个人在黑屋子里装家具——每拧一颗螺丝(行动),都眯眼看一下装得正不正(观察),
再琢磨下一步(推理)。走一步、看一步、想一步。

**ASCII 图:**

```
            ┌─────────────────────────────────────────┐
            │            ReAct 循环                     │
            │                                         │
   用户目标──►  Thought(推理)                          │
            │  "我需要先查订单状态"                      │
            │      │                                  │
            │      ▼                                  │
            │  Action(行动)                           │
            │  调用 tool: query_order(id=123)          │
            │      │                                  │
            │      ▼                                  │
            │  Observation(观察)                      │
            │  "订单已发货,物流滞留 3 天"               │
            │      │                                  │
            │      ▼                                  │
            │  Thought: "物流异常,查赔付规则" ──► 循环…  │
            │      │                                  │
            │      ▼  (满足条件时)                     │
            │  Final Answer(最终答案)                  │
            └─────────────────────────────────────────┘
```

**为什么:** 每一步都基于最新观察重新推理,天然适合"结果不可预测"的环境;且 Thought 显式写出,
**可解释、可调试**——出问题时能看到 LLM 当时"怎么想的"。

**怎么做:** 核心 system prompt 结构就是 `Thought/Action/Observation` 三段式循环(现代实现里
Action 由 Function Calling 结构化输出承载,不再是解析自由文本)。

### 6.1.4 Plan-and-Execute:先规划后执行

**是什么(通俗类比):** ReAct 是"走一步看一步",Plan-and-Execute 是"先做攻略再出发"——
出发前把整个行程列成清单,然后逐项执行,走偏了再改行程(Re-plan)。

**ASCII 图:**

```
  用户目标
     │
     ▼
┌─────────┐    1. 一次性生成任务清单
│ Planner │──────────────────────────┐
│ (强模型) │                          ▼
└─────────┘              ┌───────────────────────┐
     ▲                   │ Plan:                 │
     │                   │  1. 查订单             │
     │  5. 出错/偏离时    │  2. 查物流            │
     └──────────────────►│  3. 计算补偿 ──► ┐      │
        Re-plan(重规划)  │  4. 生成回复    │      │
                         └────────┬────────┘      │
                                  ▼               │
                         ┌─────────────┐          │
                         │  Executor   │  逐项执行 │
                         │ (可用弱模型) │◄─────────┘
                         └──────┬──────┘
                                ▼
                         ┌─────────────┐
                         │ Synthesizer │  汇总结果
                         └─────────────┘
```

**为什么:** ReAct 每一步都要"重新想全局",长任务容易**顾此失彼、原地绕圈**;先规划能保证方向感,
而且 Planner 用强模型、Executor 用弱模型,**成本结构更优**。

**怎么做:** Planner 一次调用产出结构化任务列表(JSON);Executor 循环执行,每项失败或偏差超阈值时
回传 Planner 触发 Re-plan;注意 Re-plan 本身也要设次数上限,否则"规划-失败-再规划"会变成新的死循环。

### 6.1.5 Reflection:自我修正

**是什么(通俗类比):** 写完作业自己检查一遍——让 LLM 生成答案后,再扮演"挑剔的审阅者"挑毛病,
然后根据批评意见重写。类似开发里的"写代码 → Code Review → 改代码"。

**怎么做:** 典型两段式:`生成器(答案) → 反思器(这个答案有什么问题?缺什么依据?) → 生成器(改进版)`。
可以迭代多轮,但每轮都是**双倍 Token**,一般 1-2 轮封顶。

**三种模式对比表(高频考题,背下来):**

| 维度 | ReAct | Plan-and-Execute | Reflection |
|---|---|---|---|
| 核心思路 | 走一步看一步 | 先全局规划再执行 | 生成后自我批评修正 |
| Token 消耗 | 中(每步都带全量历史) | 低(规划一次+分步执行) | 高(生成 N 倍:每轮双份) |
| 延迟 | 中,首响应快 | 低(并行执行子任务) | 高(串行多轮) |
| 长任务表现 | 易迷路、绕圈 | 方向稳定 | 提升单步质量 |
| 主要风险 | 死循环、上下文膨胀 | 规划错误全链皆错 | 反思空洞/越改越差 |
| 适用场景 | 步骤依赖中间结果 | 步骤可分解、可并行 | 高质量写作/代码生成 |
| 模型搭配 | 单模型即可 | Planner 强 + Executor 弱 | 生成器和反思器可异构 |

实务上**经常组合使用**:Plan-and-Execute 做骨架,每个子步骤内部用 ReAct,关键产出过一遍 Reflection。

### 6.1.6 循环控制:怎么让 Agent 停下来(面试官最爱追问)

**为什么:** Agent 最经典的线上事故就是**停不下来**——LLM 反复调用同一个工具、
反复"再确认一下"、上下文越滚越大、账单越滚越贵。没有刹车的 Agent 不能上生产。

**怎么做——五重刹车,层层兜底:**

```
┌──────────────────────────────────────────────────────┐
│ 1. 最大轮次   Max Iterations (如 10 轮,硬上限)         │
│ 2. Token 预算  累计 Token 超阈值 → 强制收敛             │
│ 3. 墙钟超时   整体 timeout(如 120s)+ 单工具 timeout    │
│ 4. 重复检测   连续 N 次相同(工具,参数) → 判定死循环     │
│              → 注入提示"你已重复此操作,请换思路或停止"  │
│ 5. 完成判定   每轮让 LLM 输出 FINISH 信号 + 置信度      │
└──────────────────────────────────────────────────────┘
        任一触发 → 收敛策略:让 LLM"总结已有信息直接作答"
                  而不是粗暴报错(尽量挽回部分价值)
```

追问"重复检测具体怎么做"时的细节:对每次 Action 计算 `(tool_name + 归一化参数)` 的哈希,
滑动窗口内出现 ≥3 次 → 死循环;处置顺序:**先注入纠偏提示(给它一次自救机会)→ 仍重复 → 强制收敛**。

### 🎤 面试这样答:"Workflow 和 Agent 怎么选?"

> "我先看流程的确定性。如果步骤能提前枚举、输入输出结构化,我一定用 Workflow——
> 可预测、可单测、成本固定,LLM 只在节点里当'智能函数'用。只有当路径强依赖中间结果、
> 没法穷举分支时,才上 Agent,让 LLM 在运行时决策。
> 我的核心判断是:Agent 的灵活性是用成本和稳定性换的——每一轮决策都是一次概率性调用,
> 不可复现、难测试。所以生产上我常用**混合架构**:外层是确定性 Workflow,
> 只在真正需要动态决策的节点内嵌一个受控的 mini-Agent(有轮次/Token/超时三重上限)。
> 80% 请求走流程,20% 复杂请求才路由给 Agent,这样灵活性和成本兼得。"

**追问:**

1. **"什么问题不值得用 Agent?"** → 低复杂度(一步调用能解决)、高确定性(映射稳定)、
   成本/延迟敏感(高频批量)——三占其一就别上;上 Agent 是炫技反模式。
2. **"你们线上 Agent 和 Workflow 的比例?"** → 说真实比例(如 8:2),并举例什么流量走哪条路、
   为什么——面试官在验证你是不是真上过生产。
3. **"混合架构里怎么决定一个请求走哪条路?"** → 前置分类器(小模型/规则)先识别复杂度,
   疑难杂症才升级到 Agent;Agent 处理不了还能降级回 Workflow 模板。

### 🎤 面试这样答:"Agent 什么时候该停?"

> "我把'停'分成**主动停**和**被动停**。主动停是完成判定:每轮循环让 LLM 明确输出
> FINISH 信号,并附上结论和置信度,低置信时转人工而不是硬答。
> 被动停是五重刹车:最大轮次、Token 预算、墙钟超时、重复检测、以及成本上限。
> 其中重复检测我最看重——对 (工具,参数) 做哈希,滑动窗口内连续重复就判定死循环,
> 先注入纠偏提示让它自救,不行就强制收敛。
> 还有一个容易忽略的点:**触发刹车后不要直接报错**,而是让 LLM 基于已有信息输出
> '部分结果 + 标注缺失',把已完成的 80% 价值还给用户。"

**追问:**

1. "强制收敛的输出用户看到一半结果,体验怎么保证?" → 明确标注"以下结论基于不完整信息",
   并给出补全路径(转人工/稍后重试)。
2. "Token 预算怎么定?" → 按任务类型历史 P95 定,分任务级配额 + 全局日配额双层。
3. "死循环的根因一般是什么?" → 工具返回的错误信息模型看不懂(反复重试)、
   目标定义模糊(永远觉得没完成)、上下文过长导致"忘了做过"(需要外部状态而非纯上下文记忆)。

## 6.2 工具调用:Function Calling 与 MCP

### 6.2.1 Function Calling 协议机制

**是什么(通俗类比):** Function Calling 就像给 LLM 一本**餐厅菜单**——每道菜(工具)有名字、
有介绍、有"配料要求"(参数)。顾客(LLM)不进厨房,只点菜;厨房(运行时)做好菜端上来,
顾客尝一口(观察结果)再决定下一道点啥。

**关键认知:模型从来不执行代码。** 它只输出"我想调哪个函数、参数是什么"的 JSON 意图,
**真正执行的是你的后端运行时**,执行完把结果拼回上下文,模型继续推理。

**ASCII 时序图(必会,白板能画):**

```
 用户        Agent 运行时(你的后端)        LLM API            业务系统
  │              │                        │                  │
  │──"查下我订单 │                        │                  │
  │   啥时候到"──►│                        │                  │
  │              │──1.发送 messages +     │                  │
  │              │   tools 列表(Schema)──►│                  │
  │              │                        │                  │
  │              │◄─2.返回调用意图 JSON────│                  │
  │              │  {name:"query_order",  │                  │
  │              │   args:{order_id:123}} │                  │
  │              │                        │                  │
  │              │──3.运行时校验参数(长度/  │                  │
  │              │   类型/权限)            │                  │
  │              │──4.真正执行:HTTP───────┼─────────────────►│
  │              │◄─5.订单数据─────────────┼──────────────────│
  │              │                        │                  │
  │              │──6.结果作为 tool 消息   │                  │
  │              │   回填上下文,再次请求──►│                  │
  │              │                        │                  │
  │              │◄─7.自然语言最终答案─────│                  │
  │              │  ("您的订单预计明天到") │                  │
  │◄─────────────│                        │                  │
```

**为什么这个设计聪明:** 把"决策"和"执行"分离——LLM 负责概率性的决策,
执行层保留全部工程控制权(校验、权限、审计、限流),这正是后端能施展拳脚的地方。

### 6.2.2 Tool Schema 设计哲学(描述质量决定调用成功率)

**是什么(通俗类比):** Schema 就是工具的"招聘启事"。写得含糊,来的 LLM 就瞎调;
写得精确(职责清晰、参数有约束、附示例),调用成功率天差地别。
**模型看不见你的代码,它只能看见 Schema**——Schema 即接口文档,即 Prompt 的一部分。

**怎么做(四条铁律):**

1. **描述写给模型看,不是写给人看**:说清楚"什么时候该用我、什么时候不该用、
   返回什么、有什么坑"(如"日期参数一律用 YYYY-MM-DD,相对时间请先换算")——
   这些"坑位说明"能显著减少参数错误;
2. **能用枚举就不要自由文本**:`enum: ["asc","desc"]` 直接消灭一类拼写错误;
3. **必填/可选/默认值显式声明**:required 列表精确,模型就不会瞎猜缺省参数;
4. **Few-shot 嵌入 Schema**:在 description 里放一两个典型调用示例(尤其参数格式复杂的),
   相当于给模型的"点单示范"。

**Tool Schema JSON 示例(以"创建工单"为例):**

```json
{
  "name": "create_ticket",
  "description": "创建客服工单。当用户问题需要人工跟进时使用。
    注意:priority 仅接受四个枚举值;调用前应已通过 query_order 获取 order_id。
    示例:用户说'我的订单三天没动、要投诉' → priority='high', 需先查单。",
  "input_schema": {
    "type": "object",
    "properties": {
      "order_id":   { "type": "string",  "description": "订单号,格式 ORD-XXXXXX" },
      "summary":    { "type": "string",  "maxLength": 200, "description": "问题摘要,≤200字" },
      "priority":   { "type": "string",  "enum": ["low", "medium", "high", "urgent"] }
    },
    "required": ["order_id", "summary", "priority"]
  }
}
```

**为什么这算"设计哲学"而不是"写文档":** 工具调不准,八成不是模型笨,是 Schema 烂。
面评案例:把 `date` 参数描述从"日期"改成"查询日期,格式 YYYY-MM-DD,不支持未来日期",
调用错误率能掉一个数量级。**改 Schema 比换模型便宜得多——先穷尽 Schema 优化再谈模型。**

### 6.2.3 REST API → Tool 封装规范(后端主场)

**怎么做(封装六原则):**

1. **面向意图命名,不面向 REST 动词**:`search_orders`、`get_refund_status` 优于 `GET /api/v1/orders`;
   工具粒度对齐"用户意图",不要把一个 REST 资源的 CRUD 全暴露;
2. **参数收敛**:REST 里的分页、鉴权、trace_id 由运行时注入,**不让模型填**它不该管的东西;
3. **返回值"瘦身"**:API 返回 50 个字段,Tool 只回模型需要的 5-8 个——
   每个多余字段都在浪费 Token、还会诱发幻觉;
4. **错误"翻译"**(见 6.2.4):HTTP 4xx/5xx 转成模型可读的描述;
5. **写操作三件套**:幂等键 + Dry-run 开关 + 审计日志(见 6.2.5);
6. **版本管理**:Schema 改名/改参数要向后兼容(新增可选字段可以,删字段不行),
   工具是"发给模型的接口",模型侧的"客户端"没法同步升级。

### 6.2.4 错误反馈与自愈(错误信息要"模型可读")

**是什么(通俗类比):** 工具报错时,把 Java 堆栈扔给 LLM,就像把心电图扔给病人——
它看不懂,只会原样复述或瞎猜。**错误信息要像医生对病人说话**:"哪里错了、怎么改、现在能做什么"。

**为什么:** Agent 的自愈能力 = 错误信息的可操作性。模型重试能不能成功,
几乎完全取决于错误反馈里有没有"下一步该怎么办"。

**错误反馈伪代码:**

```python
def tool_error_to_llm(error) -> str:
    # 目标:把系统错误翻译成"模型可读、可行动"的文本
    if error.type == "VALIDATION":
        return f"参数校验失败:字段 {error.field} 应为 {error.expected}," \
               f"你传的是 {error.got}。请修正后重试。"
    if error.type == "NOT_FOUND":
        return f"未找到记录:{error.query}。请确认标识符是否正确," \
               f"或先用 search 工具查询正确的 ID。"
    if error.type == "RATE_LIMIT":
        return f"调用过于频繁,请等待 {error.retry_after}s 后重试," \
               f"期间可先处理其他子任务。"
    if error.type == "PERMISSION":
        return "当前身份无权执行此操作。不要重试,请向用户说明," \
               "或改用 apply_for_approval 工具申请授权。"
    # 兜底:不暴露堆栈/内部细节(既没用又泄露信息)
    return "工具内部错误(已记录 trace_id: xxx)。请换一种方式," \
           "或基于已有信息继续完成任务。"
```

**怎么做(自愈闭环设计):**

```
执行失败 → 翻译成可读错误 → 回填上下文 → LLM 修正参数/换工具 → 重试
                │                                    │
                └── 重试 N 次仍失败 ──────────────────┘
                            │
                            ▼
              降级:fallback 工具(如实时查询挂了→查缓存)
                    或:返回部分结果 + 标注缺失
                    或:升级人工(HITL)
```

要点:**可重试错误**(超时/限流)与**不可重试错误**(参数错/无权限)要分类——
后者重试纯属浪费 Token,应该直接引导模型换路。

### 6.2.5 幂等性、超时、Dry-run、审计日志(Stripe 式追问)

**为什么(一句话):LLM 会重试、会重复调用、会在你以为结束后再调一次。**
所有写操作必须默认"它可能会被执行多次"。

**怎么做(四件套):**

1. **幂等性**:写操作一律带 `idempotency_key`(如订单号+操作类型+内容哈希),
   服务端对相同 key 的重复请求返回首次结果而不是重复执行。
   Stripe 式追问的标准答法见下方 🎤;
2. **超时**:每个工具独立 timeout(查询类 3-5s,写类按业务),超时返回"可读错误"而非异常中断;
   注意超时≠失败——请求可能已执行,**所以超时后的重试必须依赖幂等键**;
3. **Dry-run**:高危工具(发邮件/删除/支付)提供 `dry_run` 参数,先"彩排"返回
   "将执行什么操作、影响什么数据",确认无误再真执行——这也是 HITL 确认页的数据来源;
4. **审计日志**:记录每次工具调用的五元组 `谁(Agent身份/用户) + 何时 + 什么工具 + 什么参数 + 结果`,
   不可篡改、可回放——出事后的取证与回滚依据,也是合规刚需。

### 6.2.6 MCP(Model Context Protocol)专题——2025 高频新题

**是什么(通俗类比):**

- Function Calling 是**"模型会说'点菜'这句话"**——一种模型能力;
- MCP 是**"全国统一的餐厅点餐协议"**——任何餐厅(工具服务)按标准上架菜品,
  任何顾客(任何支持 FC 的模型/应用)都能直接点,即插即用。

在 MCP 出现前,每个应用接每个工具都要写一遍胶水代码(N×M 问题);MCP 把它收敛成
N+M:工具方实现一次 MCP Server,应用方实现一次 MCP Client,即可互通。

**ASCII 架构图:**

```
┌───────────────┐   ┌───────────────┐   ┌───────────────┐
│  MCP Host     │   │  MCP Host     │   │  MCP Host     │
│ (Claude桌面/  │   │ (你的Agent应用) │   │ (IDE 等)      │
│  你的Agent)   │   │               │   │               │
│┌─────────────┐│   │┌─────────────┐│   │┌─────────────┐│
││ MCP Client  ││   ││ MCP Client  ││   ││ MCP Client  ││
│└──────┬──────┘│   │└──────┬──────┘│   │└──────┬──────┘│
└───────┼───────┘   └───────┼───────┘   └───────┼───────┘
        │    标准协议(JSON-RPC):发现/调用/订阅     │
        └──────────────┬────────────────────────┘
                       │
     ┌─────────────────┼──────────────────┐
     ▼                 ▼                  ▼
┌──────────┐    ┌──────────────┐   ┌──────────────┐
│MCP Server│    │ MCP Server   │   │ MCP Server   │
│ (GitHub) │    │ (Postgres)   │   │ (你的内部系统) │
│ 工具:     │    │ 工具:         │   │ 资源+工具:     │
│ 建issue…  │    │ 查表/执行SQL… │   │ 订单/工单…     │
└──────────┘    └──────────────┘   └──────────────┘
```

**三类原语(Server 能暴露三种"货"):**

1. **Tools(工具)**:模型可主动调用的动作(查订单、建工单)——有副作用,走 Function Calling 通道;
2. **Resources(资源)**:可供读取的数据/文件(数据库 schema、文档)——类似只读数据源,可被引用进上下文;
3. **Prompts(提示)**:预置的提示词模板(如"代码审查模板")——把领域最佳实践随协议一起分发。

**FC vs MCP 对比表(高频,逐行背):**

| 维度 | Function Calling | MCP |
|---|---|---|
| 本质 | 模型的能力接口(会输出结构化调用意图) | 工具接入的传输/发现标准协议层 |
| 层次 | 模型 ↔ 应用 之间(模型怎么"点菜") | 应用 ↔ 工具 之间(菜怎么标准化上架) |
| 解决的问题 | 让 LLM 输出可执行的结构化意图 | 工具生态的即插即用、复用、分发 |
| 工具定义在哪 | 每个应用自己写一遍 Schema | Server 统一暴露,Client 动态发现 |
| 依赖关系 | 依赖具体模型的 FC 能力 | 模型无关,底层仍靠 FC 承载调用 |
| 类比 | 顾客会说"点菜"这门语言 | 全国的菜单格式与点餐流程标准化 |

**关系一句话:** MCP 不替代 FC,**MCP 是建立在 FC 之上的工具生态层**——
模型用 FC 的方式"说",用 MCP 的协议"拿"。

**优劣(体现辩证,面试加分):**

- 优点:工具一次实现处处可用;Server 集中管控权限与审计;生态复用(社区现成 Server);
- 代价/风险:多一跳网络与协议开销;**第三方 Server = 新的信任边界**(工具投毒、
  恶意描述诱导模型——Server 的 description 也是 Prompt,会被注入);
  企业内用需要私有 MCP 注册中心 + 准入审核。

### 🎤 面试这样答:"MCP 和 Function Calling 的区别?"

> "这俩不是竞争关系,是**不同层次**。Function Calling 是**模型侧的能力接口**——
> 模型能输出结构化的'我想调用哪个函数、参数是什么',它解决的是'模型怎么表达调用意图'。
> MCP 是**工具侧的标准协议**——定义了工具服务怎么被发现、怎么连接、怎么传输调用,
> 解决的是'工具怎么即插即用'。MCP 里 Server 暴露 Tools/Resources/Prompts 三类原语,
> Client 动态发现后转成本地工具再交给模型,底层承载调用的还是 FC。
> 打个比方:FC 是顾客会说'点菜'这门语言,MCP 是全国统一的菜单格式和点餐流程。
> 我们生产上用 MCP 的理由是工具复用和集中治理——工具实现一次,
> 多个 Agent 应用都能接,权限和审计收敛在 Server 侧统一做。"

**追问:**

1. "MCP 的安全风险?" → 第三方 Server 是新信任边界:工具描述可被注入(恶意 description
   诱导模型误用)、资源可投毒;对策:私有注册中心、Server 准入审核、工具描述也过 Guardrails。
2. "什么时候不值得用 MCP?" → 单应用、工具少且稳定——直接本地封装 FC 更简单,
   为协议而协议是过度设计。
3. "MCP 传输方式?" → 概念级:本地 stdio / 远程 HTTP(SSE、Streamable HTTP),
   远程场景注意鉴权与传输安全。

### 🎤 面试这样答:"工具调用失败怎么办?"

> "我分三层处理。**第一层,错误翻译**:把堆栈和 HTTP 状态码翻译成模型可读的信息——
   哪里错了、怎么改、下一步能做什么,回填上下文让模型自愈,比如参数错了它会自己修正重试。
   **第二层,分类重试**:超时/限流这类瞬态错误可以退避重试;参数错误/无权限这类确定性错误
   禁止重试,引导模型换路。**第三层,降级兜底**:重试耗尽后走 fallback 工具
   (实时接口挂了查缓存),再不行就返回部分结果并明确标注缺失,或升级人工。
   另外所有写操作从设计起就带幂等键,保证重试不会造成重复副作用。"

**追问:**

1. "怎么判断一个错误可重试?" → 瞬态(超时/限流/5xx)可重试;确定性(4xx 参数/权限)不可重试。
   超时要当'结果未知'处理,重试必须带幂等键。
2. "错误信息会不会泄露敏感细节?" → 会,所以翻译层同时做脱敏:不回传堆栈、内部主机名、SQL 细节,
   附 trace_id 供排查。
3. "模型反复用错误参数重试怎么办?" → 重复检测计数,≥3 次相同失败 → 注入强提示或直接熔断该工具、降级。

### 🎤 面试这样答:"LLM 重试怎么保证幂等?"(Stripe 式追问)

> "这和支付系统防重复扣款是同一个问题,只是调用方从'网络'换成了'更不可靠的 LLM'——
   LLM 会重试、会忘记自己调过、会在多轮里再次调用同一个写操作。
   我的标准做法:**每个写操作强制携带 idempotency_key**,key 由运行时生成
   (业务键 + 内容哈希,而不是让模型自己编),服务端用唯一索引/Redis SETNX 记录
   key→结果,相同 key 的重复请求直接返回首次结果。
   第二,执行前先查后写:Dry-run 返回'将要执行的操作',确认无重复再真执行。
   第三,超时特殊处理——超时≠失败,请求可能已落库,所以恢复后的重试必须携带同一个幂等键。
   第四,审计日志记录所有尝试,即使被幂等挡掉也留痕,方便对账。"

**追问:**

1. "幂等键谁生成?" → 运行时生成,不让模型生成(它可能每次编新的,等于没防护)。
2. "幂等结果保留多久?" → 按业务窗口(24h/7d),太短挡不住慢循环的 Agent。
3. "读操作要幂等吗?" → 读天然幂等,但要防"缓存击穿式"高频重复读——重复检测 + 结果缓存。

## 6.3 多 Agent 协作

### 6.3.1 三种拓扑(ASCII 图必会)

```
拓扑一:Supervisor(中心调度)——经理带团队
              ┌────────────┐
              │ Supervisor │  接收任务,拆解,分派
              └─────┬──────┘
        ┌───────────┼───────────┐
        ▼           ▼           ▼
   ┌────────┐  ┌────────┐  ┌────────┐
   │ Agent A │  │ Agent B│  │ Agent C│   执行者各自带
   │ 查订单  │  │ 查物流 │  │ 写回复  │   独立 prompt+工具
   └────┬───┘  └───┬────┘  └───┬────┘
        └───────────┼───────────┘
                    ▼
             汇总回 Supervisor → 输出
  特点:控制流集中,易观测易追责;Supervisor 是瓶颈和单点

拓扑二:Swarm(去中心化交接)——门诊分诊
   ┌────────┐  handshake   ┌────────┐  handshake  ┌────────┐
   │ 分诊Agent│────────────►│ 医生Agent│───────────►│ 药房Agent│
   └────────┘  连同上下文   └────────┘  连同上下文  └────────┘
              一并移交                 一并移交
  特点:无中心节点,谁擅长谁接手;链路灵活但全局视角弱、易跑偏

拓扑三:Hierarchical(分层)——公司组织架构
        ┌──────────────┐
        │  总调度 Agent  │
        └──────┬───────┘
       ┌───────┴───────┐
       ▼               ▼
  ┌─────────┐    ┌─────────┐
  │ 子调度 1 │    │ 子调度 2 │     每个子团队内部
  └──┬───┬──┘    └──┬───┬──┘     又是 Supervisor 结构
     ▼   ▼          ▼   ▼
    A1   A2         B1   B2
  特点:适合任务规模大到单层调度"管不过来"的场景;复杂度最高
```

**怎么选:** 默认 Supervisor(可控、可审计);任务链是"流水线式专业交接"用 Swarm;
任务量/角色多到单层调度撑不住才上分层。**拓扑越去中心化,可观测性成本越高。**

### 6.3.2 什么时候值得多 Agent(先泼冷水)

**为什么先泼冷水:** 多 Agent 不是"更多人干活 so 更强",协调开销是**真实成本**:
每多一个 Agent,就多一份上下文传递(翻译损耗)、多一类失败模式、多一跳延迟。
Anthropic 的经验:多 Agent 系统的 Token 消耗常是单 Agent 的 **5-15 倍**。

**值得上多 Agent 的两个硬条件(同时满足最好):**

1. **真并行**:子任务相互独立,可并发执行(如"同时查 10 个数据源"),多 Agent 能压延迟;
2. **角色差异大**:不同子任务需要**不同的 system prompt + 不同工具集 + 不同模型**
   (如"研究员 Agent 用搜索工具 + 强模型,写作 Agent 用长上下文模型")——
   单 Agent 塞所有工具反而稀释注意力、Schema 列表过长降低选工具准确率。

**反模式:** 为了"看起来高级"把线性流程拆给 5 个 Agent 串行传递——
除了贵和慢,还引入了 5 个"传话筒"的上下文损耗。

### 6.3.3 A2A(Agent-to-Agent)通信(概念级了解)

**是什么:** 跨组织/跨平台的多 Agent 互操作协议——解决"我的 Agent 怎么发现并安全地
和你的 Agent 协作"。核心三件事:**身份互信**(Agent Card 声明身份/能力,基于 OID 等既有信任体系)、
**能力发现**(类似服务注册)、**消息协议**(任务的全生命周期:创建/进行中/完成/失败)。

**和 MCP 的关系(易混,一句话记):** MCP 解决 **Agent ↔ 工具** 的接入;
A2A 解决 **Agent ↔ Agent** 的协作。MCP 是"手"的协议,A2A 是"同事"的协议。

### 6.3.4 部分失败处理(Senior 味最浓的小节)

多 Agent 系统里"某个子 Agent 挂了"是**常态**而非异常,设计时就要想好。

**怎么做(四板斧):**

```
1. Retry + Backoff     瞬态失败指数退避重试(带上限,防重试风暴)
2. Fallback 工具       主工具不可用 → 降级备选(实时→缓存→静态数据)
3. 断路器(Circuit     某子 Agent/工具连续失败率超阈值 → 熔断直接走降级,
   Breaker)           半开探测恢复——防止把故障组件打得更死
4. 优雅降级            返回已完成部分 + 明确标注缺失:
                       "已查到订单和物流信息;赔付计算暂不可用,
                        建议稍后重试或转人工"
```

再加两条工程细节体现深度:**死锁检测**(A 等 B、B 等 A,循环等待 → 全局超时兜底 +
依赖图分析)和**超时熔断分层**(子任务级/整体级两层超时,子任务超时不拖垮整体)。

### 🎤 面试这样答:"什么时候值得上多 Agent?"

> "我会先问两个问题:**任务能不能真并行?角色差异够不够大?**如果子任务独立可并发,
   或者不同子任务需要不同的 prompt、工具集甚至不同模型——比如研究员 Agent 要搜索工具加强模型,
   写作 Agent 要长上下文——那就值得拆,多 Agent 能压延迟也能让每个 Agent 的工具列表保持精简。
   反过来,如果是线性流程,拆成多个 Agent 只会带来传话损耗——每次交接都丢一次上下文,
   Token 成本能翻 5-15 倍,还多出 N 个失败点。所以我的默认选择是:
   **单 Agent + 好的工具组织**,确有并行/角色需求才上 Supervisor 拓扑的多 Agent,
   并为每个子 Agent 配好重试、断路器和优雅降级。"

**追问:**

1. "子 Agent 失败了整体怎么办?" → 分类处理:瞬态重试、连续失败熔断、
   非关键子任务跳过并标注缺失,关键子任务失败才整体失败或转人工。
2. "多 Agent 怎么共享记忆?" → 短期用共享黑板(任务状态存储),长期各自读写同一记忆库,
   注意写入的触发条件收敛(不是每轮都写,防记忆污染)。
3. "Supervisor 会不会成为瓶颈?" → 会,单点 + 串行分派;缓解:子任务批量分派、
   分层调度、Supervisor 只做路由不做内容处理。

## 6.4 记忆系统

### 6.4.1 短期记忆:上下文窗口管理

**是什么(通俗类比):** 就是 Agent 的"**工作台桌面**"——当前任务的所有便签都摊在桌上,
但桌面就那么大(上下文窗口有限),堆满了就得收拾。

**怎么做(两种收拾法):**

```
方法一:滑动窗口(简单粗暴)
  保留最近 K 轮对话 + 系统提示,更早的直接丢弃
  优点:实现简单、成本恒定  缺点:老信息硬丢失,长任务"失忆"

方法二:摘要压缩(温和)
  老对话 → LLM 压缩成摘要(保留:目标/关键决策/未决问题/关键数据)
  摘要 + 最近 K 轮 组成新上下文
  优点:保留长期脉络  缺点:压缩有损 + 额外一次 LLM 调用

实务:结构化状态外置(任务清单、已获数据存外部存储,每轮只注入"状态快照")
      ——比纯上下文记忆可靠得多,这是"State 模块"的正确打开方式
```

**为什么:** 上下文不是免费的——每轮循环都全量重发,Token 成本随轮数线性膨胀;
且超长上下文还有"中间遗忘"效应(lost in the middle)。**管理上下文 = 管理成本 + 管理注意力。**

### 6.4.2 长期记忆:向量库 / KV 持久化

**是什么(通俗类比):** 短期记忆是桌面,长期记忆是**笔记本 + 档案柜**——
跨会话沉淀下来的用户偏好、历史事实、经验教训。

**怎么做(三个关键设计点):**

1. **写入触发条件(不能什么都记)**:
   - 显式信号:用户说"记住我喜欢…"、用户纠正了 Agent 的错误(高价值!);
   - 隐式信号:某偏好连续 N 次出现;会话结束时重要性评分超阈值;
   - **防污染**:写入前过一道判断(是否稳定?是否与已有记忆矛盾?),低质记忆宁可不写;
2. **检索(相似度 + 时间 + 重要性三因子)**:
   向量相似度为主,叠加时间衰减(新记忆权重高)和重要性加权(纠正类/偏好类加成)——
   只按相似度检索会把五年前的过时偏好顶上来;
3. **遗忘与合并**:
   - 遗忘:TTL 过期、长期未被命中且低重要性 → 软删除;
   - 合并:同主题多条记忆 → 定期压缩合并成一条(用户偏好变了,新旧记忆冲突时**新的赢**,旧的标记失效)。

### 6.4.3 程序性记忆:SOP / Workflow 模板沉淀

**是什么(通俗类比):** 人类"骑车不会忘"就是程序性记忆。对 Agent 而言,
是**"这类任务上次成功走通的路径"**——把成功轨迹沉淀成 SOP/Workflow 模板,
下次同类任务直接复用,而不是每次从零探索。

**为什么:** 这是 Agent 的"**经验复利**":每成功一次,下次更快更稳更便宜——
直接绕过昂贵的试错循环,还规避了探索期的死循环风险。

**怎么做:** 任务完成后评估轨迹质量(成功 + 步数少 + 成本低)→ 抽象成参数化模板
(任务类型 → 推荐步骤序列 + 推荐工具)→ 下次同类任务作为"参考 SOP"注入 Planner 的上下文,
Planner 可遵循可偏离(保留灵活性)。

**三种记忆对比表:**

| 维度 | 短期记忆 | 长期记忆 | 程序性记忆 |
|---|---|---|---|
| 存哪 | 上下文窗口(+外置状态) | 向量库/KV 持久化 | SOP/Workflow 模板库 |
| 生命周期 | 单次任务/会话 | 跨会话长期 | 跨会话长期 |
| 记什么 | 当前对话、中间结果 | 用户偏好、事实、教训 | 成功路径、任务方法论 |
| 核心问题 | 窗口溢出怎么压缩 | 写入条件/检索/遗忘 | 何时沉淀、如何参数化复用 |
| 失效表现 | 长任务"失忆" | 记过时信息/记忆污染 | 模板过时(业务变了) |
| 类比 | 工作台桌面 | 笔记本+档案柜 | 骑车/打字的肌肉记忆 |

### 6.4.4 四概念辨析(面试常考,别混)

**对话记忆 vs 工作记忆 vs 长期记忆 vs 知识:**

| 概念 | 是什么 | 生命周期 | 例子 |
|---|---|---|---|
| 对话记忆 | 当前会话的对话历史 | 单次会话 | 这轮用户说了什么 |
| 工作记忆 | Agent 当前任务的执行状态 | 单次任务 | 任务清单、已调工具、中间结果 |
| 长期记忆 | 跨会话的用户/系统信息 | 长期持久 | 用户偏好、历史教训 |
| 知识 | 外部事实,与个体无关 | 独立维护 | 产品文档、公司规章(RAG 那一层) |

**一句话区分:** 对话记忆是"聊了什么",工作记忆是"干到哪了",长期记忆是"记住你是谁",
知识是"世界是什么样"。**知识通常不进记忆系统,走 RAG 检索通道**——这是最常被混的点。

### 🎤 面试这样答:"Agent 的记忆系统怎么设计?"

> "我按三层设计。**短期**就是上下文窗口管理:滑窗保底,老对话用摘要压缩,
   更关键的是把任务状态外置成结构化存储,每轮注入状态快照,而不是指望模型'记得'上下文里的一切。
   **长期**用向量库+KV 持久化,重点在设计三个环节:写入要设触发条件防止记忆污染、
   检索用相似度+时间衰减+重要性三因子、定期做遗忘和冲突合并。
   **程序性记忆**是把成功轨迹沉淀成 SOP 模板,同类任务直接复用路径,省 Token 也更稳。
   另外我会严格区分四个概念:对话记忆、工作记忆、长期记忆、知识——
   知识走 RAG 通道,不塞进记忆系统。"

**追问:**

1. "上下文快满了,滑窗还是摘要?" → 关键信息(目标/决策/数据)结构化外置 + 摘要压缩,
   纯滑窗会丢任务关键脉络。
2. "记忆污染怎么办?" → 写入门槛(显式信号/高重要性才写)+ 写前矛盾检测 +
   定期清理低质记忆;被污染的记忆比没有记忆更糟。
3. "检索到过时的用户偏好怎么处理?" → 时间衰减因子 + 新旧冲突时新记忆覆盖、旧记忆失效标记。

## 6.5 可靠性与人机协同(Senior 分水岭)

> 前四节讲"怎么干活",这一节讲"怎么不出事"。面试官在这一节区分 Demo 工程师和生产工程师。

### 6.5.1 失败模式清单(先背清单,再谈对策)

| 失败模式 | 典型表现 | 第一道防线 |
|---|---|---|
| 死循环 | 反复调用同一工具、永不收敛 | 循环控制五重刹车(6.1.6) |
| 幻觉工具调用 | 编造不存在的工具/参数/结果 | Schema 校验 + 工具白名单 + 结果回填验证 |
| 上下文漂移 | 长任务中途"忘了目标"、张冠李戴 | 状态外置 + 每轮重注入目标摘要 |
| 越权操作 | 调了不该调的工具、看了不该看的数据 | 专用身份 + RBAC 最小权限 |
| 成本失控 | 循环+长上下文导致账单爆炸 | Token 预算 + 成本告警 + 分层模型 |

其中**幻觉工具调用**值得展开:模型可能输出不存在的工具名、瞎编参数、甚至把
"想象中的结果"当真实结果继续推理。对策:运行时严格校验(工具名在白名单内、参数过 Schema)、
**观察结果只能来自真实执行回填**(prompt 里明确"不要假设工具结果")。

### 6.5.2 Human-in-the-Loop(HITL):不可逆操作必须人工确认

**是什么(通俗类比):** 银行柜员转账前要你输密码确认——**不可逆、有副作用的高危操作,
置信度再高也要人点头**。Agent 也一样:发邮件、删数据、支付退款,必须人工审批。

**为什么:** LLM 是概率系统,再高的准确率乘上大流量也会有错误——
而"发出去的邮件、扣掉的钱"没有 Ctrl+Z。**确定性的闸门必须由确定性组件(人/规则)把守。**

**ASCII 图(审批流中断与恢复,必会):**

```
 Agent 执行中
     │
     ▼
┌──────────────┐   高危操作识别(工具标记 dangerous)
│ 触发审批      │──► 生成审批单:操作内容+参数+Dry-run预览
└──────┬───────┘
       │
       ▼
┌──────────────────────────────┐
│ 中断:Checkpoint 状态保存       │
│ · 完整执行状态(上下文/中间结果) │
│ · 序列化落库(任务暂停态)       │
│ · Agent 进程释放,不占资源      │
└──────┬───────────────────────┘
       │ 异步通知(IM/工单/邮件)
       ▼
   ┌────────┐
   │ 人工审批 │
   └─┬────┬─┘
  批准│    │拒绝            ┌──────────────┐
     │    └───────────────►│ 终止+告知用户  │
     ▼                     └──────────────┘
┌──────────────────────────┐
│ 恢复:从 Checkpoint 反序列化 │
│ 继续执行该操作 → 后续流程    │
└──────────────────────────┘
       │
       ▼ 超时未审批
┌──────────────────────────┐
│ 超时策略(必须显式设计!):    │
│ 默认拒绝(fail-safe)或      │
│ 升级上级审批——绝不能默认通过 │
└──────────────────────────┘
```

**怎么做(四个设计要点):**

1. **哪些操作要审批**:按"可逆性 × 影响面"分级——不可逆+影响他人(支付/群发邮件/删除)必审批;
   可逆低危(读操作、写草稿)免审保流畅;
2. **异步中断而非阻塞等待**:Checkpoint 落库后 Agent 挂起,人批了再恢复——
   不是让循环干等(浪费资源且容易超时误判);
3. **超时策略**:默认拒绝(fail-safe)或逐级升级,**绝不默认通过**;
4. **审批信息设计**:给审批人看的是 Dry-run 预览(将执行什么、影响哪些数据),不是一堆参数 JSON。

### 6.5.3 确定性保障:用规则给概率系统上笼子

**是什么(通俗类比):** 飞行员自动驾驶再先进,起飞降落关键动作仍有检查单(checklist)硬约束。
Agent 的 LLM 负责"开",**规则引擎负责"卡"**。

**怎么做(四层笼子,层层过滤):**

```
输入侧   Guardrails:注入检测/PII 过滤/越权意图拦截
  ↓
过程侧   规则引擎嵌概率系统:关键分支用硬规则(金额>500 必须走审批,LLM 说了不算)
  ↓
输出侧   强校验:关键输出(金额/日期/ID/SQL)过 Schema/白名单/业务规则
  ↓
异常侧   不符合预期 → 自动重试(换 prompt/换模型)→ 仍失败 → 人工接管
```

举例:Agent 生成补偿方案,LLM 输出"赔偿 100 元"——**必须过规则引擎校验**(该用户等级上限、
该场景是否支持现金补偿),校验不过打回重试,重试两次不行上人工。**LLM 提议,规则裁决。**

### 6.5.4 Agent 权限:专用身份与爆炸半径

**为什么:"LLM 为什么不能直接拥有无限系统权限?"**(高频原题)

因为 LLM 是**概率组件 + 可被注入操纵的组件**:prompt injection 可能诱导它调用危险工具;
即使没有攻击,它自己也可能"幻觉出"一次不该有的写操作。**给概率系统无限权限 = 把生产环境交给掷骰子。**

**怎么做(三原则):**

1. **专用身份,非共享凭据**:每个 Agent 一个独立服务身份(独立 API Key/服务账号),
   绝不复用管理员凭据——出事能定位、能一键吊销、审计能区分"是谁干的";
2. **RBAC 最小权限**:只授任务所需的最小工具集与数据范围(订单 Agent 看不到用户手机号);
   工具层面收窄:给"退款查询"就不给"退款执行";
3. **爆炸半径控制**:按操作危害度分级——读 < 写 < 不可逆;高危操作叠加
   Dry-run + HITL + 金额上限;权限可随时回收,动作全部留审计日志。

### 6.5.5 沙箱隔离(执行不可信代码的标配)

**为什么:** 一旦 Agent 要**执行 LLM 生成的代码**(代码解释器/数据分析场景),
就等于运行"攻击者可控的输入"——必须假定这段代码是恶意的。

**怎么做(隔离四件套 + 冷启动优化):**

```
┌─────────────────────────────────────────────┐
│                宿主机                         │
│  ┌─────────────────────────────────────┐    │
│  │      沙箱(Docker/gVisor/E2B)        │    │
│  │  · 文件系统白名单:只挂载工作目录,只读  │    │
│  │    挂载必要数据                        │    │
│  │  · 网络白名单:默认断网,按域名放行      │    │
│  │    (防数据外传/反弹 shell)            │    │
│  │  · 资源配额:CPU/内存/执行时间硬上限    │    │
│  │    (防 fork 炸弹/挖矿/死循环)         │    │
│  │  · 行为审计:文件/网络/进程操作全记录   │    │
│  └─────────────────────────────────────┘    │
└─────────────────────────────────────────────┘
隔离强度:Docker(命名空间/cgroup,轻量) < gVisor(用户态内核,拦截系统调用,更强)
         < E2B/微 VM(独立内核,最强);按威胁模型选,不是越强越好(越强越重)
冷启动优化:预热池(提前起好一批沙箱待命)/ 快照恢复(内存快照秒级复原)
         ——否则"起容器 3s,执行代码 300ms",体验崩塌
```

### 🎤 面试这样答:"你们的 Agent 怎么保证不出事?"

> "我会从五个失败模式倒推防线:死循环用五重刹车(轮次/Token/超时/重复检测/完成判定);
   幻觉工具调用靠 Schema 严格校验加工具白名单,观察结果只认真实回填;
   上下文漂移靠任务状态外置加每轮重注入目标;越权靠专用身份加 RBAC 最小权限;
   成本靠 Token 预算加分层模型路由。
   对不可逆操作——发邮件、删除、支付——强制 Human-in-the-Loop:异步中断,
   Checkpoint 保存完整执行状态,审批通过后恢复;超时默认拒绝而不是默认通过。
   最后在输出侧上确定性笼子:LLM 提议、规则引擎裁决,关键输出强校验,
   不符合预期自动重试或换模型,再不行人工接管。核心思想就一句:
   **概率组件做决策,确定性组件守底线。**"

**追问:**

1. "审批打断用户体验,怎么平衡?" → 按可逆性×影响面分级,只卡不可逆高危操作;
   审批信息给 Dry-run 预览降低人的决策成本;高频低危操作用规则白名单免审。
2. "Checkpoint 里存什么?" → 完整执行状态:上下文、中间结果、待执行操作及其参数;
   序列化落库、可恢复可回放——顺便就是审计素材。
3. "为什么超时默认拒绝?" → fail-safe 原则:漏放行一次高危操作的代价远大于多拦一次;
   默认通过等于把超时当成"已同意"。
4. "沙箱里代码要访问内网 API 怎么办?" → 网络白名单按域名+方法精确放行,
   凭据由沙箱外的代理注入,代码本身永远摸不到密钥。

## 进阶篇：高级岗深挖区（Agent 生产化的决胜局）

> 基础篇回答"是什么、怎么做"；进阶篇回答"翻过什么车、赔过多少钱、为什么这么取舍"。Agent 是 2025-2026 最热的考察方向，基础篇的答案人人背得出，**深挖链上能不能站着走完三连问，才是高级岗的决胜局**——这一层的通行证不是知识点，是事故与账单。

### A. 二层追问链（对话体：追问→答→再追问→再答）

高级岗节奏：你给出标准答案（第一层）→ 面试官追问"然后呢"（第二层）→ 再追边界与数字（第三层）。以下五条链是 Agent 方向最高频的深挖路径，对话体演练。

#### A.1 二层追问链：ReAct 死循环的检测、干预与预防

> **追问：** "最大轮次是兜底——那死循环**正在发生**的时候，你怎么知道？"
>
> **答：** 靠运行时信号，不是等上限触发。两个检测器：一是**重复动作签名**——把每轮的（工具名+参数哈希）做成指纹，滑动窗口内重复出现即告警，抓显式重复；二是**状态熵不变化**——每轮结束后对中间结论做摘要向量化，连续 N 轮相似度超阈值，说明 Agent 在"原地踏步"而非"推进任务"，这个抓的是"换着参数空转"的隐性循环。

> **再追问：** "检测到了，直接杀掉？"
>
> **答：** 直接杀是最差的处理——用户拿到一个沉默的失败。要分级干预，像服务治理的降级预案：L1 **注入反思提示**——往上下文插一条系统消息"你已连续三次调用 search_order 且结果相同，请换一种方法或说明障碍"，给模型一次自救机会，实测约能救回一半；L2 **收窄工具集**——反思无效就强制只暴露未完成子任务相关的工具，逼它换路径；L3 **强制终止+升级人工**——带上下文快照转人工，附"卡在哪一步、试过什么"的摘要，而不是让用户重新描述一遍问题。

> **再追问：** "能不能让它根本不发生？"
>
> **答：** 预防性设计三件套：最大轮次+token 预算是硬刹车，但那是保险丝不是手段；真正有效的是**每轮进度断言**——设计上要求"每个动作必须产生新信息"（新的观察、新的中间产物），执行层校验本轮 observation 相对已有状态是否有增量，连续无增量直接触发干预；再配合把大目标拆成可判定的子目标清单，每轮明确"正在推进哪一项"，空转无处藏身。**把"每轮必须产生新信息"写进执行层代码而不是 prompt 里的恳求，这才叫工程手段。**

```text
              Agent 死循环：检测 → 分级干预全景

    每轮执行完成后 ──┬──▶ 检测器① 动作签名重复？
                     │     (工具名+参数哈希指纹，滑窗内重复≥2次)
                     ├──▶ 检测器② 状态熵不变化？
                     │     (中间结论向量相似度，连续N轮>阈值)
                     └──▶ 两个都没触发 ────────────▶ 正常继续
    任一触发 │
             ▼
    ┌──────────────────────────────────────────────────┐
    │ L1 注入反思提示："你已重复调用X且结果相同，请换方法"  │
    │     → 给模型一次自救机会，实测救回约 50%，成本≈0     │
    ├──────────────────────────────────────────────────┤
    │ L2 收窄工具集：只暴露未完成子任务的相关工具           │
    ├──────────────────────────────────────────────────┤
    │ L3 强制终止+升级人工：上下文快照+卡点摘要+已获信息     │
    └──────────────────────────────────────────────────┘
             ▲
             └ 最后的保险丝（不是手段）：最大轮次+Token预算+超时
```

#### A.2 二层追问链：MCP 解决了什么，没解决什么

> **追问：** "都说 MCP 统一了工具接入，它到底没解决什么？"
>
> **答：** MCP 解决的是"N 个应用 × M 个工具"的接入矩阵问题——以前每对组合都要写一遍胶水代码（M×N 份），统一协议后各自适配一次（M+N 份）。但它只管**接入协议**，不管生产化的三座山：**鉴权粒度**（协议能传 credential，但"这个用户此刻能调这个工具吗"的细粒度授权要自己做）；**版本兼容**（Server 升级改了工具签名，Client 何时感知、怎么灰度）；**审计**（谁在什么时候通过 Agent 调了什么工具、参数是什么——合规要的是这条链路，协议不管）。

> **再追问：** "公司里接了一堆 MCP Server 之后，会踩什么坑？"
>
> **答：** 两个大坑。一是**工具名冲突与语义混淆**——不同 Server 的命名和描述风格不一，撞名、近义工具增多，模型选错率上升；二是**上下文膨胀**——每个 Server 挂 10 个工具，5 个 Server 就是 50 个工具定义常驻上下文，活还没干先吃掉几千 token，而且工具越多选得越不准（A.3 展开）。本质是"接入标准化"与"使用治理"的错位：**接入越容易，垃圾工具泛滥越快。**

> **再追问：** "企业落地 MCP，治理方案怎么设计？"
>
> **答：** 三层：① **网关层统一鉴权**——Agent 不直连 Server，所有调用过 Agent 网关，统一做身份（用户身份透传，不是一个服务账号打天下）、授权（RBAC 到工具粒度）、限流与审计埋点；② **内部工具注册表**——工具像微服务一样注册，有 owner、SLA、版本、下线流程，同名工具强制命名空间隔离；③ **描述质量门禁**——工具描述过评审（按 A.3 的四要素标准），上架前跑"工具选择准确率"评测，不达标不准上。一句话：**MCP 给了你 USB 口，企业要的是带准入和监控的 USB Hub。**

#### A.3 二层追问链：工具数量与描述质量

> **追问：** "给 Agent 挂 50 个工具，它是不是就更全能？"
>
> **答：** 恰恰相反——**工具越多，调用越不准**。经验数字：**10-20 个是甜点区，超过 30 个选择准确率显著劣化**。机理是注意力稀释：几十个工具定义全占上下文，相似工具的描述互相竞争干扰，选错工具率和幻觉参数率都上升。和人翻 500 页手册找一条命令、不如 `ls --help` 是一个道理。

> **再追问：** "那工具描述怎么写，模型才'看得懂'？"
>
> **答：** 模型不是人，要按模型的理解方式写，四要素：**动词开头**（描述"这个动作干什么"，不是名词解释）；**前置条件**（什么时候该用/不该用——"仅当用户已提供订单号时调用，否则先用 search_user 查询"）；**返回结构示例**（贴一段真实返回 JSON——模型对输出格式的想象远不如给个例子）；**反例**（"不要用它查物流状态，那是 get_logistics 的职责"——负样本划清相邻工具的边界）。

> **再追问：** "业务确实需要 40 个工具，怎么办？"
>
> **答：** **工具分组+动态加载**——不把工具全量暴露给模型：意图识别后只挂载当前任务相关的子集（客服退款阶段挂 6 个退款工具，查单阶段挂 4 个）；或做两级结构——第一级一个 meta 工具"列出可用工具类别"，第二级按需展开。工程上这就是懒加载思想用在 prompt 上：上下文省了，选择准确率回来了。

#### A.4 二层追问链：Agent 状态管理

> **追问：** "Agent 的状态放在上下文里不行吗？"
>
> **答：** 短任务可以，生产级长任务必须外置。上下文是"工作内存"——贵、易失（进程重启就没了）、有上限；正解是**外部存储+checkpoint**：状态机当前节点、已完成步骤与产物、待执行队列、关键中间结论，序列化落库；上下文里只保留"足够下一步决策"的压缩视图。这和后端"无状态服务+外置 session"是同一个演进。

> **再追问：** "长任务跑到第 8 步机器挂了，怎么办？"
>
> **答：** 两件事配合：**每步后持久化状态机**——每个 action 执行完先落 checkpoint 再走下一步，重启后从最后一个 checkpoint 恢复；**幂等重放**——恢复时不能盲目重放最后一步，因为存在"执行了但没记下"的窗口（执行成功、写库前崩溃），所以每个外部副作用操作必须带幂等键，重放时服务端去重、已执行的跳过。这就是把分布式 saga 的 exactly-once 难题搬进来了——标准答案依然是**至少一次+幂等**，没有免费的 exactly-once。

> **再追问：** "Agent 逻辑升级了，线上还有跑了一半的旧会话怎么办？"
>
> **答：** 状态版本迁移问题，和数据库 schema 迁移同构：checkpoint 里带**版本号**，加载时按版本走迁移函数（旧状态结构升级到新结构）；升级期**双版本并行灰度**——新逻辑只接新会话，存量旧会话自然跑完；实在不兼容就分流："当前任务由旧版本继续、新任务走新版本"。原则：**在线任务的连续性优先，宁可双版本并行一段时间，不硬切。**

#### A.5 二层追问链：多 Agent 的真实成本

> **追问：** "5 个 Agent 的 token 成本是单 Agent 的 5 倍吗？"
>
> **答：** 不是，通常更糟——实际经验是 **2-3 倍的 N**。因为除了各自推理成本，还有两块隐性开销：**协调开销**——supervisor 每轮要理解各子 Agent 的状态和产出来做调度，这些"协调对话"本身全是 token；**上下文复制**——任务交接时 B 要干活，就得把任务背景和 A 的结论塞进 B 的上下文，同一份信息在 N 个上下文里被读 N 遍。和人开会一样：五个人的会，一半时间在"对齐信息"。

> **再追问：** "什么时候该把多 Agent 合并回单 Agent？"
>
> **答：** 核心判据：**角色差异是不是只有 prompt？**如果几个"Agent"用同一个模型、同一套工具，只是系统提示不同（"你是审查员""你是写手"），那它们是同一个 Agent 的不同模式——合并，用阶段化 prompt 切换，省掉全部协调开销和上下文复制。真正值得拆的是：**不同的模型**（便宜任务路由给小模型）、**不同的工具集与权限**（隔离爆炸半径）、**真并行**（独立子任务同时跑）。差异在基础设施层才值得拆，差异只在说话方式就不值得。

> **再追问：** "给一个'少即是多'的判断框架？"
>
> **答：** 三问：① 拆出来的每个 Agent 能否**独立测试与归因**？不能（永远要放一起看）就是假拆分；② **协调信息量占任务信息量的比例低于三成吗？**高于三成说明任务本身是一体的，拆开徒增搬运损耗；③ 有没有**真实的并行或隔离需求**？三问全过才拆，任何一问不过就用"单 Agent+好工具+分阶段 prompt"。**单 Agent + 设计良好的工具集 > 一堆 Agent 互相踢皮球**——这句话到 2026 年依然是行业共识。

### B. 生产 Case Study ×2（STAR-L，含数字）

> 高级岗的杀手锏不是"知道所有手段"，而是**讲得出带数字和时间的完整故事**。两个 case 都是叙事模板，数字为编好的合理量级，面试时替换成自己的真实数据。

#### B.1 Case：客服 Agent 上线之旅（Workflow → 半 Agent 的克制演进）

**S（情境）**：电商客服，日均 3 万会话，80 个人工坐席，首响 45 秒，旺季排队溢出严重。业务方要求"上 AI 客服"，红线：错误答案导致的资损与舆情必须可控。

**T（任务）**：分阶段建设自动客服，每一阶段有可量化的成败判据，并顶住"一步到位上全自主 Agent"的诉求。

**A（行动）**：

1. **第一阶段（纯 Workflow）**：历史工单聚类发现 80% 流量集中在 6 类固定诉求（查订单/查物流/退款进度/改地址/发票/FAQ）。意图分类 → 固定流程检索 → 模板生成，路径全确定、可单测。上线首月自动解决 55% 会话，准确率 96%（路径可枚举可测试）；再迭代两个月（FAQ 扩充+规则补齐）后稳定在 61%——**这就是纯 Workflow 的天花板**。
2. **卡壳点**：剩下 20% 长尾是跨系统复杂诉求（"上单退款了但运费没退，还要换绑手机号"），路径无法穷举，Workflow 写不过来，误转人工率居高不下。
3. **第二阶段（半 Agent）**：外层仍是 Workflow 骨架（鉴权、意图路由、出口合规检查全确定），只在"复杂诉求处理"这一个节点内嵌 mini-Agent——给它订单/物流/会员/退款 4 组共 13 个工具，最多 8 轮自主决策；**资金类动作（退款执行）不在它的工具箱里**，它只能"计算并申请"，审批走人工队列。
4. **第三阶段（度量驱动回收）**：半 Agent 稳定跑 4 个月、攒下 1.2 万条 trace 后，把高频成功路径固化回 Workflow 分支（程序性记忆），Agent 只处理真正的新长尾——**系统的"Agent 含量"随数据下降，而不是上升**。

```text
     自主性光谱：客服系统的克制演进（■ = 已覆盖流量）

  自主性低 ◀──────────────────────────────────────▶ 自主性高
  ────────────────────────────────────────────────────────────
  纯 Workflow            半 Agent                   全 Agent
  全流程代码写死          外层骨架确定               端到端自主规划
  LLM 只在节点内干活      复杂节点内嵌 mini-Agent
  ────────────────────────────────────────────────────────────
  ■■■■■■■■ 61%    ──▶   ■■■■■■■■■■■■■■ 78%      （刻意未到达）
  6 类高频固定诉求        +20% 长尾复杂诉求           边际收益 < 边际风险
  资损风险 ≈ 0           资损风险 ≈ 0                高危动作一进工具箱
  （路径可枚举可单测）    （资金动作不在 Agent 手里）   资损风险即不可控
                                │
                                ▼ 一年后
        高频成功路径固化回 Workflow（程序性记忆）
        —— Agent 含量随数据下降，只探索真正的长尾
```

**R（结果）**：三个阶段的指标对比——

| 指标 | 纯 Workflow（成熟期） | 半 Agent（一个季度后） | 变化与解读 |
|---|---|---|---|
| 自动解决率 | 61% | 78% | +17pt，全部来自长尾 |
| 单会话平均成本 | 基线 | 基线 +35% | 为长尾灵活性付的溢价，总人力成本仍大幅下降 |
| 人工转接量 | 基线 | 基线 -40% | 坐席排队压力显著缓解 |
| 资损事故 | 0 | 0 | 高危动作从设计上就不在 Agent 工具箱里 |

**L（复盘）**："两条经验：① **分界线不是技术是风险**——LLM 决策只放'信息收集与方案生成'节点，确定性代码守住'路由、合规、资金'节点；② **别爱上 Agent**——它的价值是探索长尾，探索完就该把发现固化回 Workflow。让 Agent 含量随时间下降的系统，才是健康的系统。"

#### B.2 Case：Agent 幻觉操作事故（资损 → 修复 → 制度化）

**S（情境）**：内部运营平台，Agent 可调用 20 个内部 API（含退款、发券）。上线 3 个月表现平稳，任务通过率 92%。

**T（任务）**：（事故后的）止血、根因分析、防复发机制。

**A（行动）**——先看时间线：

```text
T+0      Agent 处理客诉，调用 refund_order 时幻觉出不存在的参数值
         refund_reason_code="GOODWILL_V2"（API 枚举里根本没有）
T+2s     执行层 API 网关把未知参数原样透传给下游微服务
T+2s     下游对未知 code 走了默认分支——恰好是"全额退款+20 元补偿券"
T+40min  风控告警：当日 GOODWILL 类退款额异常 +370%
T+1h     拉出 Agent trace 确认参数幻觉；紧急下线 Agent 退款工具，切人工
T+3h     全量排查同类会话：17 单异常退款，资损合计 ¥4,200
         （单笔小，但方向危险——下次幻觉的可能是更大的动作）
```

**修复三件套（一周内上线）**：

1. **工具注册表白名单**：Agent 可调工具从"网关全量 API"收敛为注册表显式登记的子集；每个工具登记参数 Schema、危险等级、限流阈值——没有登记 = 对 Agent 不可见；
2. **参数 Schema 强校验**：执行层在调下游前按注册表 Schema 校验（含枚举值校验），**未知参数不透传、直接拒绝**——拒绝信息翻译成模型可读的错误，给 Agent 一次自愈重试的机会；
3. **高危操作 dry-run**：退款、发券类工具默认 dry-run 执行，返回"将要做什么"的预览，由审批流（规则引擎自动审+抽样人审）放行后才真正执行。

**制度化（一个月内）**：工具 Schema 变更走与代码同级的评审流程（Schema 变更 = 代码变更）；每月沙箱演练——注入"幻觉参数/prompt 注入/越权调用"攻击用例回归防御体系；执行层拒绝率、dry-run 拦截率纳入监控大盘。

**R（结果）**：此后再未发生参数幻觉穿透事故；执行层日均拒绝约 30 次无效调用（大半在模型自愈重试后通过）；dry-run 审批自动放行率 97%，人审压力可控。

**L（复盘）**："根因不是'模型幻觉了'——概率组件总会幻觉，这是本性；根因是**执行层把不可信输入当可信输入透传**。修复的核心思想一句话：**LLM 的输出要当作用户输入对待——校验、白名单、最小权限**。出事前我们觉得这是常识，出事后才知道常识必须长成代码。"

### C. 设计推演题（白板演示）

#### C.1 推演："内部 IT 运维助手"Agent 化六步走

> 白板题干："IT 部门 5 个人服务 800 员工，日均 120 张工单（密码重置/权限申请/VPN 故障/软件安装/账号回收）。设计 Agent 化方案，讲清每一步为什么。"

**第一步：业务拆解。** 把 120 张工单聚类成"频率×风险"矩阵：高频低危（密码重置 35%、权限申请 25%）、中频中危（VPN/软件安装 25%）、低频高危（账号回收、数据权限变更 15%）。**拆解的产出不是功能清单，是这张矩阵——它决定后面每一步的取舍。**

**第二步：Workflow/Agent 分界。** 密码重置：流程完全固定 → 纯 Workflow（LLM 最多做身份核验对话）；权限申请：路径固定但"批不批"需要判断 → Workflow 骨架+LLM 决策节点（半 Agent）；VPN 排障：路径依赖中间结果（ping 通不通、日志什么样）→ 真 Agent+诊断工具箱；账号回收：高危 → Workflow+全程人工确认，LLM 只做信息汇总。**白板上画出"每类工单落在光谱哪个位置"，比任何架构图都加分。**

**第三步：工具清单。** 每类任务 5-8 个工具，注册表总量控制在 25 个、单任务可见 ≤10 个：身份类（verify_employee/search_user）、工单类（create_ticket/update_status）、AD 类（reset_password/disable_account——危险等级标红）、知识类（search_runbook，RAG 工具）。描述按 A.3 四要素写，reset_password 的描述明确"仅当身份核验三要素齐全后调用"。

**第四步：记忆方案。** 短期：会话内滑窗+每 10 轮摘要压缩；长期：员工画像（常用设备、历史工单摘要）存 KV 按 employee_id 检索；程序性：**沉淀 runbook**——每次成功排障的路径人工确认后固化为 SOP 模板，同类故障优先走模板，模板失效才由 Agent 兜底（与 B.1"Agent 含量下降"同构）。

**第五步：失败兜底。** 分层：工具失败 → 重试+降级；Agent 迷路 → 轮次上限+反思注入；高危动作 → dry-run+人工审批；整体失败 → "已创建人工工单+附上已收集的诊断信息"——**用户永远不面对沉默的失败**。爆炸半径：Agent 用专用服务账号，只有工单系统和 AD 特定 OU 的权限——数据库它根本没有凭据，想越权都没有路径。

**第六步：评测方案。** 离线：200 条历史工单回放（自动解决率/平均轮次/token 成本/危险操作拦截率）；在线：每周抽样 50 条人工标注+满意度；回归：prompt 或工具任何变更跑全量离线集。**上线第一周设"自动处理率 ≤30%"的渐进放量熔断**——评测方案里主动讲"怎么放量"，是资深信号。

#### C.2 深算题：任务完成率评测的预算账

**题干**："评测 Agent 任务完成率：500 条任务 × 平均 8 轮 × 每轮 2K token，judge 用大模型复判。跑一次多少钱？怎么省？"

**口算路径**：

```text
第一步：被评测侧
  500 条 × 8 轮 × 2K token = 800 万 token / 全量一次
  混合均价 ~¥15/百万 token → ¥120/次
  （换旗舰模型 ¥60/M → ¥480/次，每日回归烧不起）

第二步：judge 侧
  每条喂完整 trace（~16K 输入）+ 判定输出（~0.5K）
  500 × 16.5K ≈ 825 万 token，量级与被评测侧相当
  → 总成本粗略 ×2：¥240 ~ ¥1000 / 全量一次

第三步：分层抽样替全量
  按 简单:中等:困难 = 5:3:2 分层（按任务长度/工具数/历史失败率分层）
  日常回归只跑 100 条分层样本 → 成本约 1/5
  全量 500 条留给发版前
  抽样比按"层内方差×信息量"定：困难层失败模式多、多抽；
  简单层结果稳定、少抽——这是统计常识，不是省钱技巧
```

**答**：全量一次约 ¥240~1000（看模型档位）；日常回归用 5:3:2 分层抽样跑 100 条（约 1/5 成本），发版前跑全量。**再补一句加分项：judge 要定期用人工标注对账——judge 和被测模型同源会系统性偏宽，这是被坑过的人才知道的坑。**

### D. 高级视野：搭过 Demo 的人 vs 上过生产的人

#### D.1 同一道题，两种回答

| 面试题 | 搭过 Demo 的人（B 档） | 上过生产的人（A 档） |
|--------|----------------------|----------------------|
| "Agent 失败了怎么办？" | "加 try-catch，失败重试几次"（把 LLM 当稳定服务） | "先给失败建分类学：模型侧（幻觉/迷路/死循环）、工具侧（超时/脏数据）、执行侧（越权/资损），每类有不同的检测信号和处置预案；兜底终点永远是'带上下文转人工'。**用户能接受'AI 没搞定'，不能接受'系统假装搞定了'**"（失败是分类学，不是异常） |
| "怎么保证 Agent 不做坏事？" | "prompt 里写'不要执行危险操作'"（约束靠恳求） | "prompt 约束是下限不是保证。我的防线：高危操作根本不在工具箱（最小权限）；在工具箱的走 dry-run+审批（分级）；执行层 Schema 校验拒绝一切未知参数（不信任 LLM 输出）。**让它做坏事的路径在设计时就不存在，而不是被劝阻**"（纵深防御） |
| "多 Agent 是不是更强大？" | "对，搞一个 Agent 团队协作"（把架构当时尚） | "先算账：协调开销+上下文复制，成本 2-3N，延迟和调试难度同步涨。拆分判据三条：异构模型/工具权限隔离/真并行——只差 prompt 的角色是假拆分。**多数业务单 Agent+好工具就够，多 Agent 是需求推出来的，不是愿景**"（架构是成本核算的结果） |

**规律**：B 档把 Agent 当"更聪明的 API"（功能视角），A 档把 Agent 当"不可靠的分布式组件"（风险视角）。**功能视角做出 Demo，风险视角才上得了生产。**

#### D.2 2025→2026 Agent 趋势判断

**趋势一：Workflow 与 Agent 融合——"确定性骨架+概率决策节点"成为主流形态。** 全 Workflow 太保守、全 Agent 太激进的争论被实践调和：生产系统普遍长成"外层状态机管流程、审计、恢复；内嵌 Agent 节点处理无法穷举的决策"（B.1 的半 Agent 正是此形态）。**判断：面试里主动讲"把 Agent 关进笼子里用"比"我搭了多自主的 Agent"更加分，这个风向已经确立。**

**趋势二：MCP 生态成熟后，竞争从"接入"转向"治理"。** 协议标准化让"接 100 个工具"变成配置问题，瓶颈从"能不能接"移到"接进来怎么管"：注册、描述质量、鉴权粒度、版本兼容、审计合规（对应 A.2 的三层治理）。**判断：2026 年 Agent 的差距不在框架（框架在趋同），在治理层——谁的工具生态更干净、更可审计，谁敢放生产。**

**趋势三：多 Agent 从噱头回归理性。** 2025 年上半年"Agent 团队"叙事满天飞，下半年行业集体踩过协调开销、调试地狱、成本失控三个坑后回归："单 Agent+好工具+分阶段任务"在多数业务上胜过"多 Agent 互相踢皮球"；真多 Agent 的存活场景收敛到真并行、异构模型路由、权限隔离。**判断：面试官会故意引导你吹多 Agent——冷静算账反而是加分项，"能证明不需要它"比"能搭出它"更稀缺。**

#### D.3 面试官心理：Agent 深挖题在筛什么

```text
面试官的筛人漏斗:
"搭过什么 Agent?"            ──▶ 筛掉没动手的（讲不出工具与轮次细节）
"死循环/幻觉操作怎么处理?"    ──▶ 筛掉只跑过 Demo 的（没见过系统失控）
"资损了怎么兜住?"            ──▶ 筛掉没上过生产的（没有爆炸半径概念）
"为什么不用更简单的方案?"     ──▶ 筛掉没有取舍能力的（炫技型候选人）
"成本多少?什么时候不该用?"   ──▶ 筛掉没有经营视角的（不背账单的高工不完整）
```

Agent 深挖题最终筛的是**敬畏心**：LLM 是概率组件，它会以你想象不到的方式失败，而且失败得自信满满。**真正理解概率本性的工程师才敢把它放进生产——因为他每一层设计都假设"它下一步就会出错"。**面试官宁可要"过度设防"的工程师，也不要觉得"模型这么强应该没问题"的乐观派。你六年后端的全部直觉——重试、幂等、熔断、最小权限、审计——本质上都是对不可靠组件的敬畏，这就是转型者在这一层的底牌。

### 🎤 面试这样答：「你的 Agent 死循环过吗？怎么处理的？」

> "死循环过，上线两周后——Agent 反复调用同一个查询工具，参数几乎一样，烧了三十多轮才被最大轮次兜住，用户侧表现是'转圈然后超时'。那次之后我搭了三层的东西。**检测层**：每轮把（工具名+参数哈希）做指纹，滑动窗口内重复即告警；再加状态熵检测——每轮中间结论做向量化，连续几轮相似度超阈值判'原地踏步'，这个能抓'换着参数空转'的隐性循环。**干预层**：分级——先注入反思提示，把'你已重复调用 X 次且结果相同，请换方法'写进上下文，给模型一次自救机会，实测救回约一半；无效就收窄工具集强制换路径；最后才是终止并带上下文快照转人工——用户看到的是'AI 遇到障碍已转接，附它已查到的信息'，不是沉默失败。**预防层**：每轮进度断言，执行层校验本轮是否产生了新信息，连续无增量直接干预。核心一句话：**死循环不能靠轮次上限兜底，那是最后的保险丝——检测要运行时做，干预要分级做，预防要工程化做。**"（约 340 字）

**追问：**

1. **为什么注入反思提示能救回一半？原理是什么？**
   答：多数死循环是上下文里缺少"我已经试过了"的显式信号——任务没变、工具结果没变，模型每轮都倾向重复同一推理路径。注入反思相当于把"重复"这个事实写进上下文，打破了信息不变的条件，模型才有依据切换策略。
2. **状态熵检测误报怎么办？**
   答：阈值放宽+连续 N 轮才触发+触发后先走成本最低的反思注入而非直接终止。误报的代价是多一次提醒，漏报的代价是烧 token——这个不对称决定了宁可偏松。

### 🎤 面试这样答：「什么业务不该上 Agent？」

> "我有一句口诀：**确定性、容错度、成本敏感——三占其一就别上。**流程能穷举的，Workflow 又便宜又可测试，Agent 的灵活性是负债；错误不可逆的（资金、生产变更、对外法律文本），概率决策放进关键路径等于埋雷——要么纯规则，要么 Agent 只出方案、人做决策；延迟和成本敏感的高并发场景，Agent 每请求多轮 LLM 调用，账算不平。我自己的例子：客服系统 80% 流量是六类固定诉求，纯 Workflow 就解决了；Agent 只上剩下的长尾，而且资金类动作不在它工具箱里——最终系统自动化率 78%，但 Agent 直接决策只占其中一小段。反过来说，该上的信号也明确：路径依赖中间结果、失败可恢复、单任务价值高到付得起十倍 token——内部运维排障、代码助手这类。**Agent 是最后手段——这句话我是当设计纪律讲的，不是当谦虚讲的。**"（约 320 字）

**追问：**

1. **老板坚持要"全自主 Agent"怎么办？**
   答：用风险和账说话：摆两条路的成本/延迟/可测试性对比，再给折中——半 Agent（骨架确定+局部自主），让"有 Agent"和"可控"同时成立。把政治问题翻译成工程方案。
2. **"路径能不能穷举"怎么实操判断？**
   答：拿历史数据：近几个月真实请求聚类，看头部模式覆盖多少流量、长尾占比与单量。长尾占比高且单条价值高才是 Agent 的地盘；长尾占比低，Workflow+规则兜底就完事。

- [ ] 能画 ReAct 循环图,说清 Thought/Action/Observation
- [ ] 能画 Plan-and-Execute 图,提到 Planner 强模型 + Executor 弱模型的成本结构
- [ ] 三模式对比表(Token/延迟/风险/场景)能脱口而出
- [ ] 循环控制五重刹车 + 重复检测的具体实现(哈希+滑动窗口)能展开
- [ ] "什么问题不值得用 Agent"三要点能秒答

**6.2 工具调用**
- [ ] 能画 Function Calling 完整时序图(意图→校验→执行→回填→继续)
- [ ] 理解"模型不执行代码,运行时执行",能讲出这个设计的意义
- [ ] Tool Schema 四条铁律能举例说明(枚举/必填/Few-shot/坑位说明)
- [ ] REST→Tool 封装六原则能说出至少四条(意图命名/参数收敛/返回瘦身…)
- [ ] 错误反馈伪代码能现场写:参数错/未找到/限流/权限 分类的"可行动"文案
- [ ] 幂等四件套(幂等键/Dry-run/超时当未知/审计)能按 Stripe 追问展开
- [ ] MCP 架构图能画,三类原语能解释,FC vs MCP 表能逐行说
- [ ] MCP 的安全风险(第三方 Server 是信任边界)能提到——加分项

**6.3 多 Agent**
- [ ] 三种拓扑图能画,默认选 Supervisor 且说得出理由
- [ ] 值得上多 Agent 的两个硬条件(真并行/角色差异)+ 成本认知(5-15 倍)
- [ ] A2A 与 MCP 的区别一句话:Agent↔Agent vs Agent↔工具
- [ ] 部分失败四板斧(Retry/Fallback/断路器/优雅降级)能串成完整回答

**6.4 记忆**
- [ ] 滑窗 vs 摘要压缩的取舍能讲,知道"状态外置"更可靠
- [ ] 长期记忆三环节:写入触发/三因子检索(相似度+时间+重要性)/遗忘合并
- [ ] 程序性记忆=SOP 模板沉淀,能讲"经验复利"
- [ ] 四概念辨析(对话/工作/长期/知识)不混淆,知识走 RAG

**6.5 可靠性与 HITL**
- [ ] 五大失败模式 + 各自第一道防线能对上号
- [ ] HITL 完整链路能画:高危识别→异步中断→Checkpoint→审批/拒绝/超时(默认拒绝)
- [ ] "概率组件做决策,确定性组件守底线"这句心法能自然说出
- [ ] Agent 权限三原则:专用身份/RBAC 最小权限/爆炸半径分级
- [ ] 沙箱四件套(文件白名单/网络白名单/资源配额/审计)+ 冷启动优化(预热池/快照)
- [ ] 能回答"LLM 为什么不能拥有无限系统权限"(概率组件+可被注入操纵)

---

> **本章一句话总结:** Agent 面试考的不是"会不会搭",而是"敢不敢让它上生产"——
> 选型上,默认 Workflow,Agent 是付费的灵活性;执行上,模型只出意图,运行时握住方向盘;
> 失败上,每一环都有翻译、重试、降级、人工四层网;权限上,概率系统永远不配拿到无限权力。
> 把这套"容错语言"说顺了,后端的系统设计功力就完整地迁移到了 AI 工程上。
