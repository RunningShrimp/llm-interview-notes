# 07 · L7 评测体系：最强区分度板块

## 本章导读

**考察频率：★★★★★**（后端转 AI 的优势区）

面试官心里有一句话，几乎每场 AI 应用面试都会问出口：

> **"你怎么证明它有效果？"**

大多数候选人的回答是："效果还不错，用户反馈挺好。"——这就是 Demo 工程师和生产工程师的分水岭。

- **Demo 工程师**：搭好系统 → 跑几条 case 看着挺对 → 上线 → 玄学迭代
- **生产工程师**：搭好系统 → **先建评测集和指标基线** → 上线 → 每次改动都有数据证明变好还是变坏

为什么是优势区？因为评测体系的本质是**测试工程 + 数据治理 + 监控治理**——这些东西后端天天在干（单元测试、回归测试、CI 门禁、监控告警、数据质量校验）。你缺的只是"翻译"：把后端的测试方法论映射到 AI 这种"输出不确定"的系统上。没做过生产系统的人答不出这套东西；你答得出，就是区分度。

## 7.1 RAG 评测：三层指标模型（本节核心）

### 是什么：把"效果好不好"拆成三层

**通俗类比**：RAG 系统就像一个开卷考试的学生——检索层是"翻书翻得对不对"，生成层是"抄得对不对、有没有自己瞎编"，系统层是"交卷快不快、学费贵不贵"。只看总分（最终答案）没法补课，分层才能知道该补哪科。

**为什么必须分层**：RAG 出错的根因可能在检索（没找到资料），也可能在生成（找到了但没用/瞎编）。不分层评测，你就只能"整体感觉变好了"，无法归因——归因能力是排查和迭代的前提（7.3 的实战 case 全靠它）。

```text
                        RAG 系统质量
                             │
        ┌────────────────────┼────────────────────┐
        ↓                    ↓                    ↓
     检索层                生成层                系统层
   Retrieval            Generation             System
        │                    │                    │
  · Hit Rate           · Faithfulness        · 延迟(P50/P95/P99)
  · MRR                · Answer Relevancy    · Token 成本
  · NDCG               · 正确性              · 错误率
  · Context Precision  · 幻觉率              · 吞吐(QPS)
  · Context Recall          │                    │
        │                    ↓                    ↓
  有标准答案时           依赖 Judge 或           纯工程监控
  可离线精确计算         人工评估                （后端老本行）
  （写代码就能算）       （主观性指标）
```

**怎么做**：先给检索层建可精确计算的指标（便宜、快、准），生成层用 LLM-as-a-Judge 自动化 + 人工抽检校准，系统层直接复用后端监控体系。三层分开看，出问题先定位层，再定位层内环节。

### 7.1.1 检索层指标（可离线精确计算）

前提：评测集里每条问题标注了"标准答案 + 支撑文档"（黄金 chunk）。有了它，检索指标就是**纯程序计算**——不用 LLM、不用人工、跑一万条也就几秒钟，可以放进每次 CI。

| 指标 | 通俗解释（一句话） | 离线可精确计算？ |
|---|---|---|
| **Hit Rate** (Hit@K) | 前 K 条检索结果里，有没有正确的文档——命中就是 1，没命中就是 0，求平均 | ✅ 程序算 |
| **MRR** | 正确文档排在第几位，取倒数——排第 1 得 1 分，排第 3 得 1/3，排不进前 K 得 0 | ✅ 程序算 |
| **NDCG** | 也是看排序质量，但给"多个正确文档 + 位置越靠前加权越高"的场景打分（比 MRR 更全面，理解成"排序质量的加权得分"即可） | ✅ 程序算 |
| **Context Precision** | 检索回来的上下文里，有多少是真正有用的——捞回来 10 块，8 块是金子，就是 0.8（噪音多不多） | ⚠️ 需判断"哪块有用"，通常借 LLM 标注，但可离线批量算 |
| **Context Recall** | 回答所需的信息，有多少被检索回来了——标准答案需要 5 个要点，召回 4 个，就是 0.8（漏没漏） | ⚠️ 同上（需对照标准答案判断要点覆盖） |

记忆口诀：
- **Hit Rate 管"有没有"**，MRR/NDCG 管"排得好不好"，Precision 管"捞了多少垃圾"，Recall 管"漏了多少金子"。
- **Context Recall 低 → 该 recall 的没 recall，去补召回**（加数据、改分块、换 embedding）；**Context Precision 低 → 捞回一堆噪音，去加 rerank**。

面试高频追问"MRR 和 NDCG 什么区别"：MRR 只看"第一个命中的正确文档排第几"，适合只有一个标准答案的场景；NDCG 能处理多个相关文档、按位置加权，适合"多个文档都算对但权重不同"的排序场景。**讲清适用场景即可，不要现场推公式。**

### 7.1.2 生成层指标（依赖 Judge 或人工）

检索对了不代表回答对了。生成层评的是"拿到正确上下文后，模型表现如何"。

| 指标 | 通俗解释（一句话） | 怎么算 |
|---|---|---|
| **Faithfulness 忠实度** | 回答里的每个说法，能不能在检索上下文里找到依据——找到的叫"有据"，找不到的就是"编的"。10 句话 9 句有据 = 0.9 | 拆句 → 逐句比对上下文（LLM 判） |
| **Answer Relevancy 答案相关性** | 回答有没有跑题——问物流它聊天气就是 0 分 | 用回答反推问题，和原问题比相似度（LLM 判） |
| **正确性 Correctness** | 和标准答案比，事实对不对——评测集里有 gold answer 时可判 | LLM 判 / 人工判 |
| **幻觉率 Hallucination Rate** | Faithfulness 的反面视角：回答中"无依据说法"的占比。投诉里说的"一本正经胡说八道"就是这个 | 同 Faithfulness，口径不同 |

**Faithfulness 和正确性的区别**（高频追问）：Faithfulness 只看"是否忠于检索到的上下文"，不管上下文本身对不对；Correctness 对标"客观标准答案"。上下文本身是错的，一个忠于错误上下文的回答 Faithfulness 高但 Correctness 低——所以**必须分层看，先修检索再修生成**。

### 7.1.3 系统层指标（后端老本行，直接复用）

| 指标 | 关键点 |
|---|---|
| 延迟 | 别只看平均值，看 P95/P99；RAG 要分解：检索耗时 / rerank 耗时 / LLM 首字延迟(TTFT) / 生成总时长 |
| Token 成本 | 输入+输出分开统计；上下文塞太满 → 检索质量没提升成本先爆炸 |
| 错误率 | 向量库超时、LLM 超时、结构化输出解析失败，分类统计 |
| 吞吐 | 峰值 QPS 下的表现，压测回归 |

### 7.1.4 三层指标总对比（背下来）

| 维度 | 检索层 | 生成层 | 系统层 |
|---|---|---|---|
| 代表指标 | Hit@K / MRR / NDCG / Context P&R | Faithfulness / Relevancy / 正确性 / 幻觉率 | 延迟 / 成本 / 错误率 / 吞吐 |
| 计算方式 | **程序精确计算**（有标准答案时） | **LLM-as-a-Judge 或人工**（主观判断） | 工程监控，精确 |
| 成本 | 几乎免费 | 贵（judge 也烧 token） | 免费 |
| 频率 | 每次 CI 都跑 | 抽样跑 | 实时 |
| 出问题修哪里 | 数据/分块/embedding/混合检索/rerank | Prompt/模型/温度/引用约束 | 架构/缓存/并发 |

**一句话总结（高级感拉满）**："检索指标可离线精确计算，生成指标依赖 judge——所以我的策略是检索层全量程序化回归，生成层抽样 + judge 校准，系统层进监控。这也是为什么修 RAG 先修检索：它便宜、可测、可归因。"

### 7.1.5 工具：RAGAS / TruLens / DeepEval

| 工具 | 定位 | 一句话 |
|---|---|---|
| **RAGAS** | RAG/Agent 指标库的事实标准 | 提供 Faithfulness、Context P/R、Tool Call Accuracy 等成套指标实现，嵌入你自己的流水线用 |
| **TruLens** | 带反馈交互的评测追踪 | 强项是"反馈函数 + 追踪链路"，边跑边收集指标，适合探索期 |
| **DeepEval** | 像 pytest 一样写评测 | 单测风格，`assert` 指标阈值，和 CI/pytest 生态无缝集成——对后端最亲切 |

面试说法定调：**工具是载体，指标体系是本体**。"我用 RAGAS 的指标定义 + DeepEval 的单测风格接入 CI"——表明你按指标选工具，不是按名气选工具。

### 7.1.6 LLM-as-a-Judge 专题（高级加分点，必背）

**是什么**：用一个 LLM 给另一个 LLM 的输出打分（判 Faithfulness、判相关性、判对错）。**为什么需要**：人工标注太贵太慢，无法支撑每次改动都回归；用 LLM 当裁判，评测才能自动化。

**代价：judge 本身不可靠。偏差清单（背全）：**

| 偏差 | 表现 | 典型案例 |
|---|---|---|
| **位置偏差** | 对比 A/B 两个答案时，偏向某个固定位置 | 把好的答案放后面 judge 就觉得"后面的更好" |
| **长度偏差** | 偏向更长的回答 | 啰嗦的答案得分更高，"言多必失"的幻觉被长文本掩盖 |
| **自我偏好** | 偏爱和自己风格相似的输出 | GPT-x 当 judge 更喜欢 GPT 系的答案 |
| **捧场偏差** | 不敢打低分 | 打分挤在 7-9 分之间，区分度差 |
| **rubric 漂移** | 评分标准随 prompt 措辞变化 | 同一答案换种问法分数就变 |

**校准方法（4 招，按顺序讲）：**

1. **与人工标注对齐**：先人工标 200~300 条，judge 和人工的一致率（如 kappa/一致比例）达 85%+ 才允许上线当裁判；不达标就修 judge prompt。
2. **Rubric 固化**：不给开放式问题，给结构化评分细则（每档 1-5 分的明确行为描述），judge 只做"对号入座"，不做自由发挥。
3. **多裁判投票**：换 2~3 个不同家族的模型分别当 judge，取多数/均值，单模型的自我偏好被抵消。
4. **交换位置 + 抽查复核**：对比类评测交换 A/B 顺序各判一次（治位置偏差）；线上持续随机抽 5% 人工复核，一致率掉了就告警（治漂移）。

| 对比项 | LLM-as-a-Judge | 人工标注 |
|---|---|---|
| 成本 | 低（token 费） | 高（人时费） |
| 速度 | 快，可全量/高频 | 慢，只能抽样 |
| 一致性 | 同一 judge 稳定，但有系统性偏差 | 人和人之间也会不一致（需一致性检验） |
| 上限 | ~85-90% 贴近人工 | 金标准 |
| 正确用法 | **日常回归的主力** | **校准 judge + 处理争议 case** |

伪代码：judge 上线前的校准流程（仅示意）：

```python
calib_set = load("人工标注_300条.pkl")          # 人工先标好
for judge_prompt in candidate_judge_prompts:     # 候选 rubric
    preds = [judge(q, a, ctx, judge_prompt) for q, a, ctx in calib_set]
    agreement = compute_agreement(preds, calib_set.labels)
    if agreement >= 0.85:
        freeze(judge_prompt)                     # rubric 固化 + 版本管理
        break
# 上线后：每天随机抽 5% 人工复核，一致率 < 0.80 触发告警
```

### 🎤 面试这样答："你怎么证明 RAG 有效果？"

> "我不会用'感觉变好了'来回答，我会先搭一套三层评测体系。**第一层检索**：评测集每条问题标注支撑文档，Hit@5、MRR、Context Precision/Recall 全部程序化计算，每次改动都能精确回归。**第二层生成**：Faithfulness 看回答有没有依据、Answer Relevancy 看跑没跑题、幻觉率盯无依据说法占比，用 LLM-as-a-Judge 自动化——judge 先和 300 条人工标注对齐到 85% 一致率才上岗。**第三层系统**：延迟分解、token 成本、错误率进监控。上线前在黄金集上跑基线，上线后每次优化都对比这套指标，比如我上个项目把 Faithfulness 从 0.65 提到 0.88，就是靠先发现 Context Recall 只有 0.7、定位到分块切断语义，改了 parent-child 索引后带起来的。"

**追问 1：Faithfulness 具体怎么算的？**
→ 把回答拆成一个个独立陈述，逐条判断"能否由检索上下文推出"，有依据条数 / 总条数。RAGAS 内置了这个实现，本质是 LLM 逐句判定。

**追问 2：检索指标都是程序算的，为什么 Context Precision 还要提 LLM？**
→ Hit/MRR/NDCG 依赖标注好的"正确文档"，纯程序算；但"捞回的 10 块里哪几块真的有用"（Precision）需要语义判断，通常离线批量让 LLM 标注，标完就是固定分数，不会漂。

**追问 3：为什么先修检索层再修生成层？**
→ 两个原因：一是因果，上下文都错了，生成层再强也是巧妇难为无米之炊；二是工程性，检索指标可精确计算、可归因、修复手段明确（补数据/改分块/加 rerank），ROI 远高于玄学调 prompt。

### 🎤 面试这样答："LLM-as-a-Judge 不可信怎么办？"

> "judge 不可信是共识，我不消灭偏差，我管理偏差。四个手段：**一，对齐**——judge 上线前和 300 条人工标注比对，一致率 85% 以上才启用，达不到就迭代 judge prompt；**二，固化 rubric**——把评分标准写成结构化的分档细则，版本化管理，prompt 变更走评审，防止评分尺度漂移；**三，多裁判**——关键评测用两个不同家族的模型投票，抵消自我偏好；对比类评测交换答案顺序判两次，治位置偏差。**四，持续抽查**——上线后每天随机抽 5% 人工复核，一致率跌破阈值就告警、必要时冻结评测结论。这套思路其实就是后端'监控数据可信度治理'的翻版：judge 是一个数据源，数据源本身也要有质量监控。"

**追问 1：为什么是 85% 一致率，不是 100%？**
→ 人和人之间的一致率本身也只有 80% 多（所以标注要做一致性检验）。judge 贴近"平均水平的人"就够了，追求 100% 成本上不成立。关键不是数字本身，而是"有阈值、有门槛、有告警"这个机制。

**追问 2：judge 和被评模型用同一个模型行不行？**
→ 不行，自我偏好会让分数虚高。裁判和选手必须分开——至少换不同版本，最好是不同家族的模型。

**追问 3：rubric 怎么设计才算好 rubric？**
→ 每一档描述"可观察的行为"而不是"好/较好/差"。比如 Faithfulness 的 1 分档写"存在与上下文直接矛盾的陈述"，5 分档写"全部陈述均有出处且可溯源"——judge 只做对号入座，不做主观发挥。

## 7.2 Agent 评测：trace 级过程评测

### 是什么：从"看结果"升级到"看过程"

**通俗类比**：结果指标是看考试成绩，过程指标（Trajectory，轨迹评测）是看草稿纸。RAG 是单步流水线，评输入输出就够了；Agent 是多步自主决策，**中间每一步怎么走的，比最后一步更重要**。

**为什么**：Agent 的执行链路长（选工具→传参→看结果→再决策），任何一步出错都可能被后续步骤"侥幸掩盖"，也可能当下没事、换个场景就爆炸（比如越权调用、裸 SQL）。不评过程，等于只验收成品不审代码。

### 关键认知：最终答案对 ≠ 过程对（本章最著名的反例）

```text
【反例：答案对了，过程全错】

用户任务：查一下订单 20250812 的物流状态

  理想轨迹                          实际轨迹（碰巧对了）
  ─────────                         ──────────────────
  Step1 调 logistics.query          Step1 调 user.search        ← ❌ 工具选错
        ↓                                 ↓
  Step2 参数 order_id=20250812      Step2 参数 uid="小米"        ← ❌ 参数瞎填
        ↓                                 ↓
  Step3 解析结果并回答              Step3 调 db.raw_sql          ← ❌ 绕过接口裸查库
        ↓                                 ↓
                                    Step4 调 logistics.query    ← 兜一大圈才调对
                                          ↓
                                    ✅ 最终答案正确

  只看结果指标：通过 ✅            看 trace 指标：工具选择 0 分 ❌
```

这个实际轨迹的危害：多花了 3 步（延迟×4、成本×4）、执行过裸 SQL（越权风险）、这次靠运气，下次同样的模式可能直接失败或造成事故。**所以 Agent 评测必须下沉到 trace 级，逐步骤核对"该调哪个工具、该传什么参数"。**

### 结果指标 vs 过程指标（对比表）

| 维度 | 结果指标 Outcome | 过程指标 Trajectory |
|---|---|---|
| 看什么 | 任务完成率、最终答案质量 | 工具选择准确率、参数正确率、步骤效率、错误恢复率 |
| 类比 | 考试成绩 | 草稿纸过程分 |
| 评测粒度 | 整个任务 | trace 里每一步 |
| 抓什么问题 | 能不能用 | 可靠不可靠、安全不安全、贵不贵 |
| 依赖 | 最终答案 + 标准答案 | 完整 trace + 标注的理想轨迹（或 judge 对齐） |
| 两者关系 | 结果对过程不一定对 | 过程对结果大概率对 |

**过程指标四个关键项**：

| 指标 | 通俗解释 |
|---|---|
| **工具选择准确率** | 该调工具 A 的步数里，实际调了 A 的比例——选错工具是 Agent 最常见错误 |
| **参数正确率** | 调对了工具，参数（订单号、日期格式、枚举值）填对的比例 |
| **步骤效率** | 实际步数 / 理想步数——兜圈子说明规划能力差，延迟成本翻倍 |
| **错误恢复率** | 中途出错（工具报错、结果为空）后，能自己纠正并完成任务的比例——高级 Agent 的核心能力 |

### 怎么做：工具与框架

- **RAGAS agent 指标**：Tool Call Accuracy / Tool Call F1（逐步比对实际调用与参考轨迹）、Agent Goal Accuracy（最终目标达成）。参考轨迹需在评测集里标注"理想工具调用序列"。
- **LangSmith evals**：Agent 每次运行产生带完整 span 的 trace（每步的工具、参数、返回），evaluator 直接挂在 trace 上逐步打分——trace 基础设施和评测是一体的。Langfuse 同理（开源替代）。
- 数据集形态：`任务描述 + 理想轨迹（工具序列+关键参数）+ 成功判据`，理想轨迹的标注成本高，常用"先跑一遍人工确认的轨迹再固化"来省成本。

### 端到端指标：延迟分解与每任务成本

- **延迟分解**：总延迟 = 规划耗时 + Σ(工具执行耗时 + LLM 推理耗时) + 重试耗时。多步 Agent 延迟天然是累加的，P95 必须按步骤分解看，才知道优化哪一步（并行工具调用？减少步数？换小模型做规划？）。
- **每任务成本**：不再按"每次请求"计费，按"每个任务"计——一个任务跑 8 步、每步都带上下文，token 消耗是 RAG 的好几倍。评测时输出"平均每任务 token/费用"，和完成率一起看（完成率 95% 但每任务成本翻了 3 倍，未必划算）。

### 🎤 面试这样答："Agent 最终答案对了，就是做得好吗？"

> "不一定，这正是 Agent 评测必须做 trace 级的原因。我见过一个 case：查订单物流，Agent 先调错用户查询接口、参数还是瞎填的、中途又绕去执行了裸 SQL，最后碰巧调对了物流接口，答案是对的。只看结果指标这个 case 是满分，但看轨迹：工具选择错、参数错、有越权行为、多花了三倍延迟和成本——这次是运气，换个场景就是事故。所以我的评测分两层：结果层看任务完成率和答案质量；过程层在 trace 上逐步评工具选择准确率、参数正确率、步骤效率、错误恢复率，用 RAGAS 的 Tool Call Accuracy 或 LangSmith 把 evaluator 挂到每一步 span 上。理想轨迹在评测集里标好，跑完自动对齐打分。"

**追问 1：理想轨迹怎么标注？成本会不会太高？**
→ 折中做法：不要求唯一轨迹，标注"必需的关键步骤"（必须调过某个工具、必须带某个参数）+ "禁止步骤"（如裸 SQL），评"关键步骤覆盖率 + 违禁步骤命中"。再配合先人工跑一遍确认的轨迹固化入库，成本可控。

**追问 2：错误恢复率怎么测？**
→ 主动注入故障：mock 某个工具返回 500 或空结果，看 Agent 是重试、换路径、还是直接崩。故障注入用例和正常用例分开维护——这就是后端混沌工程在 AI 上的翻版。

**追问 3：多 Agent 系统怎么评？**
→ trace 按 span 层级天然分层（coordinator → 子 agent → 工具），每个子 agent 单独评各自的目标达成率，再评整体。定位问题时看是哪个子 agent 的指标掉下来了。

## 7.3 数据集与反馈闭环

### 7.3.1 黄金数据集：评测的地基

**通俗类比**：评测集就是 AI 系统的"单元测试 + 回归测试集"。没有它的迭代 = 没有测试就重构线上代码，全凭胆量。

**三种构建来源对比（必背表）**：

| 维度 | 人工标注 | LLM 合成 | 线上日志挖掘（最优） |
|---|---|---|---|
| 质量 | 最高（金标准） | 中，需人工审核 | 高（真实分布） |
| 成本 | 最贵（人时） | 便宜（token 费） | 边际成本最低 |
| 覆盖 | 取决于标注者想象 | 易同质化、缺边界 case | 真实长尾、天然含边界 |
| 速度 | 慢 | 快 | 依赖上线后有流量 |
| 主要坑 | 标注不一致（要做一致性检验） | 分布偏移、答案错误 | 有偏（只覆盖被问过的问题）、含隐私需脱敏 |
| 定位 | 冷启动打底 + 校准 judge | 扩量填充 | **主力，持续进化** |

**线上日志挖掘怎么做（步骤，被追问就背这个）**：

1. **圈日志**：从 trace 里拉全量 query → 检索结果 → 回答（trace 完整是前提，这就是 L8 可观测性的价值）。
2. **按信号分层**：结合反馈信号初分"好/差/未知"（点赞点踩、复制、改写重问、追问澄清）。
3. **聚类去重**：query 向量化聚类，同类只留代表，避免 1000 条都在问"怎么退货"。
4. **人工定标**：差的 case（badcase）人工确认错在哪层（检索 or 生成），标上 gold answer / 支撑文档 → 直接入库；好的 case 抽样确认后入库。
5. **配额控制**：按 query 类型（事实型/推理型/闲聊/边界）和难度分层采样，保证分布合理、边界 case 有配额。

**边界 case 覆盖**：专门给"异常输入"留配额——query 拼写错误、指代不清（"它呢？"）、知识库没有答案的问题（考"拒答"）、恶意注入（考防御）、多问题混在一句里。**RAG 评测里最值钱的分数是"该说不知道时说了不知道"**。

**版本管理**：评测集用 DVC（数据版管理）或带 hash 的对象存储管理版本；每个模型的分数都绑定"评测集版本 + prompt 版本 + 模型版本"三元组——否则三个月后没人说得清 0.85 是在哪套数据上测的。新增 badcase 只增不删，删除需评审（防止"删测试保通过"）。

### 7.3.2 在线反馈闭环（完整图，必背）

**是什么**：离线评测集会过时，用户会用真实行为投票。反馈闭环 = 把线上信号持续变成评测数据，让系统越用越准。

```text
【在线反馈闭环】

  ┌────────────────────────────────────────────────────┐
  │                    线上服务                          │
  │          用户提问 → RAG / Agent → 回答               │
  └──────┬──────────────────────────────────┬──────────┘
         │ 显式信号                          │ 隐式信号
         │ · 点赞 / 点踩                     │ · 复制了答案（+）
         │ · "答错了"反馈入口                │ · 立刻改写重问（-）
         ▼                                  │ · 追问澄清（-）
  ┌──────────────┐                           │ · 只读了 2 秒（-）
  │ 反馈信号归集  │ ◄─────────────────────────┘
  └──────┬───────┘
         ↓
  ┌──────────────┐     ┌───────────────────────┐
  │ Badcase 判定  │ ──→ │ 自动入库（含完整 trace：│
  │ 信号→疑似坏例 │     │ query/检索结果/回答/反馈）│
  └──────────────┘     │ + 人工复核确认 + 定标    │
         └─────────────┴──────────┬────────────┘
                                    ↓
                       ┌─────────────────────┐
                       │ 回归测试集（黄金集）  │ ←→ 版本管理(DVC)
                       └──────────┬──────────┘
                                    ↓
                       ┌─────────────────────┐
                       │ 归因 → 分层修复      │
                       │（检索层 or 生成层）   │
                       └──────────┬──────────┘
                                    ↓
                        离线回归全通过 → 灰度放量
                                    ↓
                          发布新版本 ────────→ 回到线上（闭环）
```

**隐式信号怎么读（易错点）**：都是概率不是判决——复制大概率是满意，但也可能是"复制去骂它"；改写重问大概率是没答好，但也可能是用户自己没问清。所以隐式信号只做"疑似 badcase 的召回"，**入库前必须人工复核**，宁缺毋滥，否则闭环会污染回归集。

### 7.3.3 离线指标与在线 A/B 的关联、灰度发布

- **离线 → 在线的逻辑链**：离线指标（Faithfulness、完成率）是代理指标，业务指标（投诉率、采纳率、留存）才是终局。上线前在黄金集上证明"离线显著变好"，再用小流量 A/B 验证"在线也变好"，两跳都通过才全量。
- **灰度发布**：5% → 20% → 50% → 100% 逐级放量，每级观察核心在线指标（投诉率/采纳率/成本）至少一个波动周期；随时可回滚。AI 系统改动（换模型/改 prompt/改检索参数）一律走灰度，和后端发版纪律完全一致。
- **两者打架怎么办**（高级追问）：离线变好在线变差 → 大概率是评测集分布偏了（过期或被污染），优先修评测集而不是硬上功能。

### 7.3.4 实战 Case 全 Walkthrough："幻觉投诉 5%，一周降到 0.5%"

这是 L7 的压轴题，完整背下来。结构：**定位 → 分层修复 → 回归验证 → 监控告警**。

```text
Day1  投诉率 5% → 拉近一周投诉 case，逐条归因（看完整 trace）
        │
        ├─ 归因结论：60% 检索层（Context Recall 低：知识缺失/分块切碎）
        │            30% 生成层（上下文有答案但模型自由发挥）
        │            10% 数据层（文档本身过期/矛盾）
        ↓
Day2-3 分层修复（只动归因命中的层，每项独立可验证）
        · 检索层：补缺失文档 + 切断语义的分块改 parent-child + 加 rerank
        · 生成层：prompt 加"仅依据上下文回答，无依据明确说不知道" + 降温
        · 数据层：过期文档下线 + 矛盾文档标注生效时间
        ↓
Day4   回归验证：投诉 case 全部转入回归集 → 修复后逐条重跑
        + 黄金集全量：幻觉率 5%→0.8%，其余指标不回退
        ↓
Day5   灰度：10%→50%→100%，在线投诉率 5%→0.5%
        ↓
Day6-7 长效机制：
        · 每天随机抽 5% 线上回答，judge 打幻觉分，超阈值告警
        · 点踩/改写信号自动转疑似 badcase → 人工复核入库
        · 新 badcase 一律先进回归集再修复（防止复发）
```

三个拿分点：① **先归因再动手**（不做归因直接调 prompt 是 Demo 思维）；② **每项修复独立验证、其他指标不回退**（这是回归测试思维）；③ **留下长效机制**（监控 + 自动入库，而不是一次性救火）。

### 🎤 面试这样答："评测集怎么建？"

> "我按'三来源 + 一原则'来建。**冷启动**用人工标注 100~200 条打底，覆盖核心 query 类型和边界 case，这批同时用来校准 LLM-as-a-Judge；**扩量**用 LLM 合成（从知识库文档反向生成问答对），但必须人工抽审，防止分布偏移；**主力**是线上日志挖掘——从 trace 里拉真实 query，按反馈信号分层，聚类去重后人工定标，这样长尾和边界天然覆盖。一原则是：**所有线上 badcase 一律转成回归用例，只增不删**。数据集用 DVC 做版本管理，每份评测报告绑定'数据集版本 + prompt 版本 + 模型版本'三元组。规模上，我经验是 300~500 条分层抽样的黄金集，比 5000 条同质化的更有区分度。"

**追问 1：评测集规模多大合适？**
→ 看分层：核心类型各 50~100 条、边界 case 各 20~30 条，300~500 条通常够做统计显著的回归判断。盲目堆量只会堆出同质化样本，还拖慢 CI。质量 > 数量。

**追问 2：怎么防止评测集泄漏？**
→ 评测集绝不进 few-shot 示例、不进微调数据、不出现在任何 prompt 里；权限上和训练数据隔离存储；定期抽检"疑似背题"（分数异常高但线上表现差）。

**追问 3：query 分布变了，评测集跟不跟？**
→ 跟。每季度用线上日志重算 query 类型分布，评测集配额随之调整；旧 case 不删但可以降权重，保持和真实流量对齐。

### 🎤 面试这样答："线上幻觉投诉 5%，一周内降到 0.5%，你怎么做？"

> "四步：定位、分层修复、回归验证、长效机制。**定位**：拉近一周投诉的完整 trace，逐条归因到层——结论 60% 是检索层 Context Recall 低（该召回的没召回），30% 是生成层自由发挥，10% 是源文档过期。**分层修复**：检索层补文档、改分块、加 rerank；生成层 prompt 加'仅依据上下文、无依据说不知道'并降温；数据层下线过期文档。**回归验证**：所有投诉 case 先转成回归用例，修复后逐条重跑，黄金集全量指标幻觉率 5%→0.8% 且其他指标不回退，然后灰度 10%→50%→100%，在线投诉率落到 0.5%。**长效机制**：每天抽 5% 线上回答用校准过的 judge 打幻觉分、超阈值告警，点踩和改写信号自动转疑似 badcase、人工复核入库。这个 case 我最想强调的是归因——5% 的幻觉里只有 30% 是模型的问题，不做归因直接换模型，既贵也解决不了。"

**追问 1：为什么归因是 60/30/10，怎么算出来的？**
→ 逐条看 trace：投诉的 case 里，先看检索回来的上下文——上下文里根本没有正确依据的，记检索层；上下文有依据但回答没用甚至矛盾的，记生成层；文档本身错/过期的，记数据层。样本量一百多条，占比就是归因分布，误差范围内够指导投入分配。

**追问 2：修复期间线上还在产生幻觉怎么办？**
→ 先上兜底再修复：高风险域（价格、政策、医疗）临时收紧——检索相似度低于阈值直接拒答"知识库暂无该信息"，宁可少答不可错答，把投诉先压住，再从容修根因。

**追问 3：降到 0.5% 之后怎么证明不会回升？**
→ 三道保险：回归集（新 badcase 只增不删，每次改动全量跑）、线上抽检告警（幻觉率连续两天超阈值自动告警）、灰度纪律（任何涉及模型/prompt/检索的改动必须过离线门禁才能放量）。

## 7.4 评测自动化流水线与成本

### 是什么：把评测塞进 CI

**通俗类比**：指标门禁 = CI/CD 的卡点。后端改代码不过单测不许合并；AI 应用改 prompt/检索参数，也不过评测门禁不许合并——**prompt 就是代码，改 prompt 就是改逻辑**，凭什么不用走测试？

**为什么**：AI 应用的"代码"很大一部分是 prompt、分块参数、检索 top_k、rerank 阈值这些配置。没有门禁，一次"顺手优化"就能让幻觉率从 0.5% 回到 3%，而且没人知道是哪次改动干的。

```text
【评测 CI 流水线】

开发者改 Prompt / 检索参数 / 模型版本
        ↓
   git push / 提 MR
        ↓
┌─────────────────────────────────────────────────┐
│ CI 自动触发评测                                    │
│   1. 跑黄金集（500 条）                            │
│      · 检索指标：程序计算（秒级、免费、全量）        │
│      · 生成指标：LLM-as-a-Judge 抽样 20%           │
│      · 系统指标：延迟/成本随跑随采                  │
│   2. 与上一版本基线对比                             │
│   3. 指标门禁：                                    │
│      · Hit@5 ≥ 0.90 且不低于基线 -1%？             │
│      · Faithfulness ≥ 0.85？                      │
│      · P95 延迟 ≤ 2s？                            │
│      · 历史 badcase 零回归？                       │
└───────────────────┬─────────────────────────────┘
        ↓                            ↓
     全部门禁通过                  任一门禁挂
        ↓                            ↓
     允许合并                    拒绝合并 + 报告：
        ↓                         哪个指标掉、哪条 badcase 回归
   基线自动更新                          ↓
   （版本三元组留档）                开发者修复后重新提 MR
```

**怎么做（工程要点）**：评测脚本用 DeepEval 的 pytest 风格接入现有 CI；基线（上一版指标）存在版本库里，合并后自动滚动更新；**badcase 零回归是硬门禁**——平均分好看但任何一条历史 badcase 复发，直接 fail。

### 评测的成本问题：judge 也要花钱

一条生成层评测 = judge 模型一次完整调用。500 条黄金集、每条判 3 个指标、每天几十次 MR——评测费可能超过开发费。**抽样策略（背三个）**：

1. **分层抽样**：不是均匀抽 20%，而是给边界 case、历史 badcase、新增 case 100% 覆盖，稳定通过的简单 case 抽 5%~10%——钱花在刀刃上。
2. **级联评测**：先用便宜模型/规则过滤（格式校验、检索指标、关键词），只把"疑似有问题"的送大模型 judge——检索层全量程序算本身就是第一道免费过滤。
3. **便宜 judge 打分 + 昂贵 judge 仲裁**：日常回归用小模型 judge，分数接近门禁阈值或发生争议时升级到强模型复判（模型级联思想在评测上的复用）。

配套纪律：评测预算做成监控指标（每周 judge token 花费告警）；judge prompt 本身版本管理，避免"评测代码"被随意改动导致分数不可比。

### 🎤 面试这样答："评测这么贵，怎么在 CI 里天天跑？"

> "核心是把评测做成'分层、分级'的，而不是一把梭全量。第一层免费：检索指标全量程序计算，Hit/MRR 几秒出结果，每个 MR 都跑。第二层便宜：生成指标用小模型 judge，只对分层抽样的子集跑——边界 case 和历史 badcase 100% 覆盖，简单 case 抽 10%，钱花在高风险样本上。第三层按需：分数贴近门禁或有争议的，升级强模型复判。另外用规则做前置过滤，格式都不对的直接 fail，不劳 judge 大驾。我在上个项目这么拆完，单次评测成本降了一个数量级，门禁延迟从十几分钟压到 3 分钟，评测才真正能在 CI 里天天跑——评测体系不能自己先把自己跑破产。"

**追问 1：抽样会不会漏掉回归？**
→ 会漏随机回归，但我用"高风险样本 100% 覆盖"兜住主要风险，且线上还有抽检监控做第二道网。离线抽样 + 在线抽检，两层网加起来，漏网概率和成本达到平衡——本质又是后端'测试金字塔'的思路：便宜的跑得多，贵的跑得少。

**追问 2：门禁阈值怎么定，拍脑袋吗？**
→ 第一次定基线用当前版本实测值 + 小幅余量；之后阈值滚动跟随线上质量目标反推（如线上要求幻觉率 <1%，离线 Faithfulness 就得 ≥0.85），每次调整留变更记录。阈值本身也是配置，改它也要走评审。

**追问 3：模型/prompt 供应商更新导致指标全动了，怎么排查？**
→ 靠版本三元组留档：固定数据集版本，分别只换模型、只换 prompt 各跑一次，二分定位是谁引起的；所以每次评测我都记录完整环境快照——不可复现的评测等于没测。

## 进阶篇：高级岗深挖区（评测是资深经验的决胜区）

> 基础篇回答"是什么、怎么做"；进阶篇回答"数字是多少、怎么定的、翻过什么车"。多数人答得出 RAGAS 的指标名，答不出"judge 校准到多少才放上岗、A/B 跑几天才作数、500 条评测集够不够"——**这一层拼的不是 AI 知识，是测试工程与数据治理的年头，恰是后端的主场。**

### A. 二层追问链（面试官的深挖套路）

高级岗节奏：你答出概念（第一层）→ 面试官追问数字与标准（第二层）→ 再追边界与取舍（第三层）。以下五条链是评测高频深挖路径，对话体演练。

#### A.1 二层追问链：LLM-as-a-Judge 的偏差与校准线

> **追问：** "你说 judge 有偏差，具体有哪些？"
>
> **答：** 四大类必背：**位置偏差**——A/B 对比时偏向固定位置，好答案放后面就赢；**长度偏差**——偏爱更长的回答，啰嗦把幻觉藏住了；**自我偏好**——judge 偏爱同家族模型的输出，GPT 当裁判更认 GPT 系的答案；**锚定偏差**——rubric 措辞或先看过的评分示例把后续打分"锚"住，分数跟着示例走。本质上 judge 是个"有系统性倾向的标注员"——偏差不能消灭，只能管理。

> **再追问：** "怎么校准？校准到多少算合格？"
>
> **答：** 四招按顺序上：**一，与人工对齐**——先人工标 200~300 条，算 judge 与人工的 kappa / 一致率，**85% 是可用线**。依据：人与人之间的一致率本身只有 80% 多，judge 贴近"平均水平的人"就够用，追 100% 成本上不成立；**二，rubric 固化**——评分标准写成结构化分档、每档描述可观察的行为，版本管理、变更走评审；**三，多裁判投票**——两个不同家族的模型分别判、取多数，抵消自我偏好；对比类评测交换 A/B 顺序各判一次，治位置偏差；**四，抽样复核**——上线后每天随机抽 5% 人工复判，一致率跌破 80% 告警，必要时冻结评测结论。

> **再追问：** "什么时候必须人工，不能交给 judge？"
>
> **答：** 三种场景 judge 只做初筛、人做终审：**高风险域**（医疗/法律/金融，错判代价大）；**低频次场景**（一年几百条，judge 校准成本摊不平，直接人标更便宜）；**裁决性场景**（两个版本指标打架要定生死、badcase 归因有争议、门禁阈值要不要放行）。原则一句话：**judge 管日常回归的量，人管关键决策的准。**

#### A.2 二层追问链：指标体系怎么构建

> **追问：** "指标是不是越多越好？你们有几个？"
>
> **答：** 不是，核心 5~8 个足够。指标多了：看板没人看完、门禁互相打架、每个都有维护成本。我的配置 8 个：检索层 3（Hit@5、MRR、Context Recall）+ 生成层 2（Faithfulness、Answer Relevancy）+ 系统层 2（P95 延迟、单次成本）+ 业务层 1（投诉率）。**指标是决策工具，不是收藏品。**

> **再追问：** "这些指标怎么定出来的？从零开始怎么办？"
>
> **答：** 从用户投诉反推，三步：**投诉聚类**——拉历史投诉和点踩 case 聚类，得到失败模式分布（"编造参数"30%、"答非所问"15%、"引用过期文档"20%）；**失败模式翻译成可观测指标**——"编造"→ Faithfulness，"答非所问"→ Answer Relevancy + Context Precision，"过期文档"→ 数据新鲜度检查；**定门禁**——从线上质量目标反推（投诉率要 <2%，则 Faithfulness 门禁 ≥0.85）。指标不是抄别家清单，是**从自己的失败模式里长出来的**。

> **再追问：** "指标之间会打架吗？怎么取舍？"
>
> **答：** 两对经典冲突：**召回 vs 延迟**——top-K 调大、加 rerank，Context Recall 涨、P95 也涨；**成本 vs 准确率**——换大模型 Faithfulness 涨、单次成本翻倍。取舍原则是**红线优先**：先定业务硬约束（延迟 ≤2s、成本 ≤X、幻觉率 ≤1%），红线一票否决；红线之内做帕累托改进。面试关键不是说"要平衡"，而是**说出你的业务里哪个指标是硬约束、为什么**——这暴露你是否真做过取舍。

#### A.3 二层追问链：数据集泄漏

> **追问：** "评测集泄漏指什么？"
>
> **答：** 三类污染，一类比一类隐蔽：**训练集污染**——被评测的数据模型预训练时见过（公开 benchmark 被爬进语料是重灾区），测的是"背书能力"不是"泛化能力"；**测试集污染**——线上数据回流评测集后，又拿去调 prompt / 做 few-shot，等于拿考题教学；**时间穿越**——评测用了"未来"数据，比如评测集标注基于 2025 年 6 月的知识库状态，却评一个只学了 2024 年语料的模型，或"最新政策"类 query 没对齐评测时点。

> **再追问：** "怎么防？怎么证明防住了？"
>
> **答：** 防泄漏纪律四条：**隔离存储**——评测集和训练数据、few-shot 素材库物理分开、权限隔离；**绝不进 prompt**——不做示例、不做微调、不进任何调优环节；**时间戳对齐**——相对时间类 query 标注"在时点 T 是否有答案"；**定期审计**——抽检"分数异常高但线上表现差"的疑似背题 case，对评测集做 n-gram / 嵌入相似度扫描，和公开语料撞车超阈值就换题。证明手段：拿新出事件造一批"模型肯定没见过"的 case 冷测——老评测集 0.9、新 case 只有 0.6，泄漏实锤。

> **再追问：** "线上日志挖掘的 query 要进评测集，又怕测试集污染，不矛盾吗？"
>
> **答：** 关键在**用途隔离 + 时序纪律**：同一批 query 进了回归集，就再也不能被用来调 prompt 和做 few-shot（一次使用原则）；调优只用训练侧数据、验收只用评测集，两者永不交叉。这和后端"测试用例不能既当开发依据又当验收标准"一个道理——**考题泄露过一次就得换卷**。

#### A.4 二层追问链：显著性与 AB 周期

> **追问：** "500 条评测集，A 版 0.82、B 版 0.84，B 更好吗？"
>
> **答：** 先算标准误再说话：SE ≈ √(0.82×0.18/500) ≈ 0.017，2pt 差距连 2 倍标准误都不到，大概率是噪声。**规则：差距 < 2×SE，不下结论。** 要可信地检出 2pt 差距，每组得 4000 条起（口算见 C.2）。

> **再追问：** "A/B 测试跑几天怎么定？"
>
> **答：** 三个约束取最长：**样本量**——按效应量算所需流量；**行为周期**——至少 7 天覆盖工作日/周末差异，且新版本前 2~3 天是 novelty 噪声期（用户对新回答好奇，指标虚高），要看稳态段；**segment 饱和**——关键切片（query 类型 × 新老用户）每格样本要够。经验值：中小流量 2~3 周，大流量 1~2 周但**不少于 7 天**。太短是噪声，太长浪费流量拖慢迭代。

> **再追问：** "什么情况下离线指标和在线指标会打架？"
>
> **答：** 三个根因：**分布偏移**——评测集分布 ≠ 真实流量（评测集老了、建集时抽样有偏），离线测的是"旧世界的题"；**用户行为变化**——新功能改变了问法，离线集没覆盖新 query 模式；**样本偏差**——灰度桶流量不均、某类用户占比过高把在线指标带偏。排查顺序：先对照线上分布重分层评测集，再切 segment 看是否只利好头部，最后查实验设计（分桶均匀性、novelty 效应）。

#### A.5 二层追问链：badcase 归因

> **追问：** "拿到一个 badcase，你怎么归因？"
>
> **答：** 走分层归因树，从上往下问"这层有没有错"，先命中先修：

```text
【badcase 分层归因树：先定位层，再定位层内环节】

                badcase：回答错了 / 体验差
                        │
       Q1: 检索回来的上下文里有正确依据吗？
                        │
   ┌────────────────────┼─────────────────────┐
   ↓ 有依据，但答错      ↓ 没有依据             ↓ 有依据，但内容残缺
   │                    │                     │
【生成层】           Q2: 知识库里            【切块/解析层】
 · 自由发挥/编造       到底有没有？             · 切断语义
 · 答非所问             │                     · 粒度太粗/太细
 · 压缩过度漏要点        ├─ 根本没有            · 表格/图片解析丢内容
                       │   → 【数据层】        │
                       │    语料缺失/过期/矛盾   │
                       └─ 有，但没进 top-K     │
                            · 召回未命中        │
                            · 排序太后          │
   ↓                      ↓                    ↓
 修法：prompt 约束/    修法：补数据/下线       修法：改 embedding/   修法：parent-child/
 换模型/降温/引用校验   过期文档/修矛盾         混合检索/加 rerank    语义分块/修解析器
```

> **再追问：** "单个 badcase 修完就完了吗？"
>
> **答：** 不，要提炼成指标才算闭环。三问：**能否自动检测**——这个错误模式有没有可计算的信号（引用为空、答案与上下文矛盾、该拒答没拒答）；**能否度量**——能不能变成评测集上的检查项或指标（如"拒答准确率"）；**能否防回归**——能不能转成回归用例进门禁。三问全"否"，至少进人工抽检清单。**一个 badcase 的最高价值，是变成一个永不复发的前置检查。**

> **再追问：** "badcase 库怎么管理？"
>
> **答：** 当资产管理，四件套：**标签**——每条标归因层（生成/检索/切块/数据）、query 类型、严重级；**聚类**——定期聚类看失败模式分布，指导投入分配（60% 集中在检索层就先修检索）；**趋势**——按月看各类失败量，异动即预警；**季度复盘**——看哪些 case 反复复发、哪些根因反复出现，反推流程漏洞（切块问题反复出现 = 切块规则缺评审）。这就是后端"事故库 + postmortem 制度"的 AI 翻版。

### B. 生产 Case Study ×2（STAR-L，含数字）

> 高级岗的杀手锏不是"知道所有评测手段"，而是**讲得出带数字的完整故事**。两个 case 的数字是编好的合理量级，面试时替换成自己的真实数据。

#### B.1 Case：评测体系从 0 到 1（投诉率 8% → 1.5%）

**S（情境）**：企业知识库 RAG 问答，上线三个月，周投诉率 8%（"答错""编造""过期"混在一起）。迭代全靠"改了 → 上线 → 感觉好点"，没人说得清哪次改动真的有效。

**T（任务）**：建立评测体系，让每次迭代可度量、可归因、可回归；半年内投诉率降到 2% 以下。

**A（行动）**：
1. **建评测集**：人工标注 200 条金标（核心 query 类型 × 边界 case 配额，每条含 gold answer + 支撑文档）；同时从线上 trace 挖 500 条（点踩/改写重问信号召回 → 聚类去重 → 人工定标）——合计 700 条分层黄金集
2. **建三层指标**：检索层 Hit@5 / MRR / Context Recall 程序计算；生成层 Faithfulness / Answer Relevancy 走 judge——judge 先与 300 条人工标注对齐，kappa 一致率 87% 才上岗；系统层延迟/成本进监控
3. **建流程**：DeepEval 接 CI 做指标门禁卡合并；badcase 只增不删入回归集；judge 每天 5% 在线抽检
4. **跑出第一份归因分布**：基线 Faithfulness 0.71 / Context Recall 0.72；归因发现 65% badcase 在检索层——团队投入从"调 prompt"转向分块改造 + 混合检索

**R（结果）**：半年后稳态——**Faithfulness 0.93、Answer Relevancy 0.89、Context Recall 0.90、周投诉率 1.5%**。真实工时：约 1.5 个工程师 × 3 个月（标注外包另计约 2 万元）；judge token 月均 800 元（分层抽样 + 小 judge 日常、大 judge 仲裁之后）。

**L（复盘）**："最值钱的产出不是指标分数，是**第一份归因分布**——'65% 在检索层'这个数字，把团队三个月的精力从玄学调 prompt 扳到了数据与检索工程上。如果重来，第一个月就把线上挖掘自动化——人工标 200 条太慢，边际收益不如日志挖掘高。"

#### B.2 Case：一次糟糕的 A/B 测试（离线全涨、线上变差）

**S（情境）**：RAG 问答迭代：换更强 rerank 模型 + 重构分块。离线评测集全指标上涨（Faithfulness +3pt、Context Recall +4pt），A/B 两周后准备全量。

**T（任务）**：验证在线效果并放量。

**A（行动）**——教训本身：
1. A/B 两周，**离线全涨、在线变差**：投诉率 1.5% → 2.3%，采纳率 -4pt，被迫暂停放量
2. 复盘三个根因：
   - **评测集分布偏离真实流量**：评测集是三个月前建的；近一个月新上线两条产品线的 query 占真实流量 25%，评测集里几乎为 0——新策略在这 25% 上表现更差，离线完全看不见
   - **新策略只利好头部 query**：强 rerank 对标准常见问题提升明显；长尾模糊 query（表述混乱、多问题混合）上，激进排序反而把"勉强相关"的文档挤出去——头部拉高均值，长尾恶化被平均掩盖
   - **没看 segment 切片**：只盯大盘。事后回看，"长尾/模糊 query"segment 的投诉率第一周就涨了 60%——切片看板本来第一周就能报警
3. 修复：评测集按线上最新分布**分层重抽样**（定为季度例行）；A/B 看板加 **segment 切片监控**（query 类型 × 新老用户）；测试周期 2 周 → **3 周**（跨过 novelty 期看稳态）

**R（结果）**：重跑三周，全 segment 无回退后放量；此后再没出现"离线好线上差"的翻车。沉淀为团队 A/B 三纪律：**分布对齐、切片监控、足够周期**。

**L（复盘）**："一句话：**离线评测集测的是'你以为的世界'，A/B 测的是真实世界——分布不一致时，离线指标是幻觉**。花两周流量买这个教训，比任何文档都深刻：评测集不是建完即固定资产，是必须跟流量对齐的活物。"

### C. 指标手算/统计推演（30 秒口算演示）

> 面试官爱出"现场算一笔账"——考的不是精确数字，是量级感和手算路径的熟练度。

#### C.1 手算 MRR@10 与 NDCG@10（5 条 query 完整算例）

设 5 条 query，每条只有 1 个 gold 文档，top-10 检索结果中 gold 的位置如下：

```text
第一步 · MRR@10（倒数取平均）

  Query   gold 排名     MRR 贡献 = 1/rank
  ─────   ────────     ─────────────────
  Q1      第 1 位       1/1  = 1.00
  Q2      第 3 位       1/3 ≈ 0.33
  Q3      第 2 位       1/2  = 0.50
  Q4      不在 top-10   0
  Q5      第 5 位       1/5  = 0.20
                       ────────────────
                       合计 = 2.03
  MRR@10 = 2.03 / 5 ≈ 0.41

第二步 · NDCG@10（单 gold 场景：DCG = 1/log2(rank+1)；理想排第 1，IDCG = 1）

  Query   gold 排名     DCG = 1/log2(rank+1)    NDCG = DCG/IDCG
  ─────   ────────     ─────────────────────   ────────────────
  Q1      1            1/log2(2)  = 1.000       1.00
  Q2      3            1/log2(4)  = 0.500       0.50
  Q3      2            1/log2(3) ≈ 0.631        0.63
  Q4      —            0                        0.00
  Q5      5            1/log2(6) ≈ 0.387        0.39
                       ─────────────────────   ────────────────
                       NDCG@10 = 2.52 / 5 ≈ 0.50

直观读法：
· MRR 只问"第一个命中的排第几"——排第 3 就 1/3，简单粗暴
· NDCG 给排名打对数折扣——第 1 与第 3 的分差(1.00 vs 0.50)
  比 MRR(1.00 vs 0.33) 平缓，且天然支持多 gold 文档加权
· 两指标同向：NDCG 通常略高于 MRR（衰减更温和）
```

**答**：MRR@10 ≈ 0.41，NDCG@10 ≈ 0.50。口算锚点：MRR 是"倒数取平均"；NDCG 记三个数——第 1 名 1.0、第 2 名 0.63、第 3 名 0.5（即 1/log2(rank+1)），多 gold 时各 gold 的 DCG 求和、再除以理想排序的 IDCG。

#### C.2 样本量粗算：baseline 80%，要检出 5pt 提升，需要多少样本？

```text
经验公式（两比例检验，α=0.05、功效 80% 的口算版）：

  n ≈ 16 × p(1-p) / Δ²        p 取基线比例，Δ 是要检出的差距

代入 p=0.80、Δ=0.05：
  n ≈ 16 × 0.80 × 0.20 / 0.05²
    = 16 × 0.16 / 0.0025
    ≈ 1024（每组）

三个推论（面试脱口而出）：
· n ∝ 1/Δ²——效应量减半，样本翻 4 倍：检 2.5pt → 每组约 4100
· 检 10pt → 每组只要约 260——大改动小样本就能看清
· 这就是"500 条评测集上看 2pt 差距 = 看噪声"的数学根据
```

**答**：每组约 1000 条。核心直觉：**样本量随效应量平方反比**。给出这个反比关系 + "80% 基线附近，检 5pt 约千条/组"这个锚点就够了——没人要你现场查 t 表。

#### C.3 指标加权合成：5 个指标 → 1 个健康分，权重怎么定

```text
方法一 · AHP 层次分析法（把"拍脑袋"数学化）
  两两比较"Faithfulness 和延迟哪个重要、重要几倍"
  → 构造判断矩阵 → 最大特征值对应的特征向量归一化 = 权重
  → 一致性比率 CR < 0.1 才算数（自相矛盾的拍脑袋会被抓出来）
  适合：指标少于 10 个、有业务专家在场

方法二 · BTM（从业务指标回归，权重是"学"出来的）
  拿 3~6 个月历史数据回归：哪个指标变化对业务指标
  （投诉率/留存）解释力强，回归系数标准化后当权重
  适合：有线上数据积累的成熟期

方法三 · 业务反推（冷启动最常用）
  红线指标设为"一票否决"，不进加权
  其余按"离目标差距 × 可干预性"排序定权重
  适合：刚起步没数据，先用起来再迭代

合成公式：健康分 = Σ wi × min(指标值/目标值, 1)   ← 封顶防单项超额拉分
两个坑：① 高相关指标去重（Faithfulness 和幻觉率本质一个东西，只能进一个）
       ② 一票否决项不进加权（延迟破线，健康分再高也不许发版）
```

**答**：三法——AHP 两两比较出权重、BTM 从业务指标回归、业务反推从红线出发。坑两个：一票否决不进加权、高相关指标去重。**健康分是给老板看的驾驶舱，门禁永远看分项指标**——合成分会掩盖单项崩坏。

### D. 高级视野：从"会测"到"有判断"

#### D.1 "做过 Demo 评测" vs "建过生产评测"（答法对比表）

| 面试题 | Demo 评测（B 档） | 生产评测（A 档） |
|--------|------------------|------------------|
| "你怎么证明它有效？" | "跑了十几条 case，看着都挺对" | "三层指标 + 黄金集基线 + CI 门禁；judge 与人工一致率 87% 才上岗" |
| "指标怎么定的？" | "RAGAS 有什么我测什么" | "投诉聚类 → 失败模式 → 可观测指标，5~8 个核心项，每个绑定门禁" |
| "评测集多大合适？" | "越多越好，堆了几千条" | "分层 300~700 条比同质几千条强；报指标必绑版本三元组" |
| "A/B 结果怎么读？" | "B 组分数高就上 B" | "先显著性检验，再 segment 切片，跨 novelty 期看稳态" |
| "judge 可信吗？" | "用大模型当 judge 挺准的" | "四偏差清单 + 85% 校准线 + 多裁判换序 + 5% 抽检告警" |

**规律**：B 档的特征是"有工具没体系"——测了，但说不清为什么测这些、门禁为什么是这个数；A 档的特征是"每个数字背后有决策"。**工具是查得到的，判断才是你的。**

#### D.2 2025→2026 评测趋势判断

**趋势一：评测左移到数据侧**。"垃圾进垃圾出"成为共识后，评测从"模型输出之后"移到"数据入库之前"——文档质量分、切块质量抽检、元数据完备性检查先于任何检索指标上线，数据质量指标成为评测体系的第一块拼图。**判断：'数据质量先于模型指标'这套叙事，是 2026 年评测题的加分开场。**

**趋势二：在线实时评测**。离线评测集 + 定期回归跟不上 prompt/模型的高频迭代，方向是**每请求打标**：judge 随机抽样在线回答实时打分、指标按 segment（query 类型/用户群/场景）实时出看板、异常自动告警——评测从"发布前的关卡"变成"运行时的监控"。这本质是后端"拨测 + APM"的 AI 版，转型者的天然优势区。

**趋势三：human-in-the-loop 评测的工业化**。人工标注从"外包堆人天"进化为**众包 + 主动学习筛选**：模型先预标、人只校验"模型最不确定"的分歧样本，标注效率提升 3~5 倍；标注者间一致性检验（IAA）成为流程标配。人不再是标注流水线，而是校准与裁决的稀缺资源。

```text
【指标健康度看板示意：评测体系的一页纸】

┌─ RAG 质量驾驶舱（数据集 v3.2 · prompt/模型版本留档）──────────┐
│                                                            │
│  检索层  Hit@5  0.91 ✓   MRR 0.68 ✓   CtxRec 0.90 ✓        │
│  生成层  Faith 0.93 ✓   Relv 0.89 ⚠ 环比-1pt                │
│  系统层  P95  1.8s  ✓   单次成本 ¥0.021 ✓                   │
│  业务层  投诉率 1.5% ✓   采纳率 76%  ⚠ 环比-2pt              │
│                                                            │
│  门禁: 7/8 通过  红线: 0 违规  judge人工一致率 87% ✓         │
│  历史 badcase 回归: 0 复发   在线抽检幻觉率: 0.6% ✓          │
└────────────────────────────────────────────────────────────┘
  读法: ✓ 达标 │ ⚠ 环比恶化但未破线（连续两周恶化自动升级告警）
        ✗ 破线即阻断发布。看板一眼定位"哪层、哪个指标、什么趋势"
```

评测题的真实筛选意图：**筛"是不是工程师思维"——能不能用数据说话**。AI 团队最怕招到"感觉主义者"：效果靠玄学、迭代靠勇气、复盘靠故事。你说不出指标、基线、样本量、显著性，就是"没做过工程"的信号；你每个论断都带数字与归因路径，就是"能对结果负责"的信号。后端在这道题上是主场作战——单元测试、CI 门禁、监控告警、数据治理，全是你的旧地图；评测只是新大陆的名字。

### 🎤 面试这样答："你的评测体系怎么建的？"

> "分三步：先建数据地基，再建指标，最后建流程。**地基**：人工标 200 条金标覆盖核心类型和边界 case；同时从线上 trace 挖 500 条——点踩/改写信号召回、聚类去重、人工定标——合成 700 条分层黄金集，DVC 版本管理，每份评测报告绑定数据集/prompt/模型三元组。**指标**：三层——检索层 Hit@5、MRR、Context Recall 纯程序计算；生成层 Faithfulness 和 Relevancy 走 judge，judge 上岗前和 300 条人工标注对齐，kappa 一致率 87% 才启用，之后每天 5% 在线抽检；系统层延迟成本进监控。**流程**：DeepEval 接 CI 做指标门禁，badcase 零回归是硬门禁。效果：体系跑起来第一个月就发现 65% 的 badcase 集中在检索层，团队投入从调 prompt 转向分块和混合检索，半年后 Faithfulness 0.71 → 0.93、投诉率 8% → 1.5%。我的心得：评测体系最值钱的产出不是分数，是**归因分布**——它决定工程师的时间砸在哪。"

**追问 1：700 条会不会太少？**
→ 看用途：日常回归门禁够用（分层好、badcase 全覆盖）；做版本级决策要检出 2pt 差距，每组得 4000 条——所以重大决策我会临时扩集或跑 bootstrap 多次重采样。样本不够时靠分层质量和方差分析补，不是盲目堆量。

**追问 2：judge 校准是一轮就到 87% 的吗？**
→ 不是，第一版 rubric 只有 78%。主要坑是分档描述太主观（"基本准确"），judge 自由发挥。改成每档描述可观察行为（如 1 分档 = 存在与上下文直接矛盾的陈述）、补边界 few-shot 示例后才到 87%。**校准的本质是修 rubric，不是换更大的 judge。**

**追问 3：这套体系花了多久？值吗？**
→ 约 1.5 人 × 3 个月，一半时间在建数据集。值：以前每次迭代"感觉变好"要吵一架，现在 3 分钟跑门禁看数字；它还救过我们一次——一次"顺手升级"rerank 被门禁拦住，事后确认在新 query 上确实是回退。**没有评测的迭代是裸奔，出事只是时间问题。**

### 🎤 面试这样答："离线指标涨了、线上反而变差，你怎么排查？"

> "这个坑我真实踩过。结论先行：**先怀疑评测集，再怀疑实验设计，最后才怀疑功能本身**。我当时是离线 Faithfulness +3pt，A/B 两周在线投诉率反而 1.5% → 2.3%。复盘三步：第一步查评测集分布——拉线上最新 query 分布和评测集对比，发现评测集是三个月前建的，新上线产品线的 query 占真实流量 25% 而评测集里几乎为零，离线测的根本不是真实世界；第二步切 segment——按 query 类型切片，长尾模糊 query 的投诉率第一周就涨了 60%，新 rerank 只利好头部标准问题，大盘均值把这个恶化盖住了；第三步查实验设计——前 2~3 天是 novelty 噪声期，两周均值本身就不可靠。修复三个动作：评测集按线上分布分层重抽样并定为季度例行、A/B 看板强制 segment 切片监控、周期延到三周看稳态。重跑后全 segment 无回退才放量。这个教训一句话：**评测集是你以为的世界，流量是真实的世界——两者不对齐时，离线指标是幻觉。**"

**追问 1：为什么不先怀疑新功能有 bug？**
→ 也会查，但排第三。离线在线都是真实运行结果、两边数据都"对"，矛盾几乎必然出在**测量口径**——评测集的世界和线上世界不是同一分布。工程纪律是先修测量、再修被测对象，顺序反了会白改功能。

**追问 2：segment 怎么选，不怕切出假信号吗？**
→ 预先定义、不许事后翻找——事后切一百个 segment 总有几个"显著"，是多重比较陷阱。我们固定切 query 类型 × 新老用户：业务有意义、样本量有保证；新维度要加必须先登记评审，和后端"告警阈值变更走评审"一个纪律。

**追问 3：novelty 效应怎么量化？**
→ 看按天的时间曲线而不是均值：实验组指标若前 3~5 天高开低走再企稳，novelty 实锤，用企稳段算效果；没有明显拐点就按完整周期均值。这也是 AB 周期最少 7 天的原因——给用户行为留"退烧"时间。
