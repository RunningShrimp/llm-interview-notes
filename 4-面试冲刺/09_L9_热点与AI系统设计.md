# 第一部分 · 前沿热点（视野展示区）

> 每个知识点按"是什么 → 为什么火 → 面试怎么聊"三段式组织。
> 记住：热点题不需要你懂源码，需要你有**观点**。

## 1.1 MCP 生态与工具标准化

**是什么**：
MCP（Model Context Protocol），Anthropic 于 2024 年 11 月开源的协议，用来**标准化模型与外部工具/数据源的连接方式**。类比：MCP 之于 AI，相当于 USB-C 之于外设——以前每个工具都要为每个模型单独写适配，现在"一次实现，处处可用"。2025 年 OpenAI、Google 相继宣布支持后，MCP 成为事实标准，社区工具服务器（GitHub、数据库、浏览器、Slack……）爆发式增长。

**生态位**：它解决的是"**连接标准化**"这一件事——统一了工具发现（tools/list）、工具调用（tools/call）、资源读取的协议层。

**为什么火**：
- 工具生态从"N×M 适配地狱"变成"N+M 标准接口"，开发者接入成本骤降
- 大厂站队 + 社区服务器复利，形成生态飞轮
- 它让 Agent 的"能力扩展"变成配置问题而非开发问题

**面试怎么聊（一句话观点）**：
> "MCP 标准化了'连接'，但没解决'编排、权限、审计'——生产环境我会在 MCP 之上加一层网关：统一鉴权、工具调用审计、速率限制，并处理它目前的三个痛点：**调试难**（调用链黑盒，需要全链路 trace）、**安全边界模糊**（恶意服务器可以返回注入内容，信任不能外包给协议）、**版本管理缺失**（工具 schema 变更没有兼容性规范，升级即断）。"

这样答，比"我知道 MCP"高两个段位。

**MCP vs Function Calling**（大纲自测题 #7，高频）：

| 维度 | Function Calling | MCP |
|---|---|---|
| 本质 | 模型厂商的 API 能力（描述工具→模型产出调用参数） | 跨厂商的连接协议（客户端/服务器架构） |
| 范围 | 单次请求内，厂商私有 | 进程间通信，厂商无关 |
| 工具复用 | 换模型要重写接入 | 工具服务器跨模型复用 |
| 类比 | "手机支持充电" | "统一了充电口形状" |

一句话总结：Function Calling 是模型"会用工具"的能力，MCP 是工具"到处能插"的标准，两者互补而非竞争。

## 1.2 A2A 多 Agent 互信

**是什么**：
A2A（Agent2Agent）协议，Google 2025 年推出，解决**Agent 与 Agent 之间**的协作问题：互相发现能力（Agent Card，一张 JSON"名片"，声明我是谁、会什么、怎么联系我）、委托任务、交换消息。与 MCP 的关系一句话：**MCP 管 Agent↔工具，A2A 管 Agent↔Agent**，二者互补。

**核心概念（概念级即可）**：
- **身份**：每个 Agent 有可验证的身份（公钥/证书体系），就像微服务之间的 mTLS
- **消息协议**：任务委托、状态回传、长任务异步通知
- **能力发现**：类似"服务注册 + 能力描述"，甲方 Agent 看了乙方名片才知道能不能委托

**为什么火**：
- 跨企业 Agent 协作是公认的下一站（我的采购 Agent 和你的销售 Agent 谈判）
- 身份与互信是付费、签约、追责的前提——没有信任层，商业闭环不成立

**面试怎么聊（一句话观点）**：
> "A2A 我理解为核心解决两件事：能力发现（Agent Card）和身份互信。类比后端微服务：MCP 像 RPC 框架统一了调用格式，A2A 像服务网格 + 证书体系解决'我凭信你'。落地难点在**跨组织的身份体系**和**任务的可追责性**——这跟开放平台鉴权体系是同构问题。"

（最后一句是"后端转型"的加分动作：把新概念锚定到老经验。）

## 1.3 Agentic RAG / Self-RAG / 普通 RAG 一句话辨析

高频考题（大纲自测题 #4 原题："Agentic RAG 和普通 RAG 区别？"），用一张表 + 三句话记住：

| 方案 | 一句话定义 | 典型形态 |
|---|---|---|
| 普通 RAG | 固定管线：检索一次 → 生成一次，流程写死 | 查询 → 召回 → 拼 Prompt → 生成 |
| Agentic RAG | 把"检索"降级为 Agent 的**一个工具**，由模型自主决定：要不要检索、检索什么、结果好不好、要不要再检索 | Plan → 调检索工具 → 自评 → 不满意则改写再检索 → 生成 |
| Self-RAG | 训练模型**自我反思**：生成特殊反思标记，判断"这段要不要检索证据""生成内容是否被证据支持" | 模型内置反思能力的训练方法（学术味更重） |

**辨析要点**：
- Agentic RAG 是**架构层面**的演进（流程从写死变成模型自主），Self-RAG 是**模型层面**的训练技术（教会模型反思）
- 工程落地几乎都是 Agentic RAG（不改模型，改编排）；Self-RAG 多出现在论文和评测里
- 代价：Agentic RAG 延迟和成本翻倍（可能检索 2~3 次、多轮推理），**不是默认选项**——简单 FAQ 场景用它就是过度设计

**面试怎么聊**：
> "普通 RAG 是流水线，Agentic RAG 是把检索变成工具让模型自主编排，Self-RAG 是训练模型自带反思。我会按问题复杂度分层：80% 简单查询走普通 RAG 保延迟，复杂多跳问题才升级到 Agentic 流程——这也是成本工程的一部分。"

## 1.4 多模态 RAG（图文档问答）

**是什么**：
让 RAG 能回答"**这张图里是什么**"的问题。典型场景：企业知识库里大量 PDF 含图表、架构图、扫描件——纯文本管线处理不了。两条技术路线：

1. **多模态解析路线（工程主流）**：用 VLM/OCR 在**入库阶段**把图表转成文字描述（"这是一张 2024 年 Q3 营收柱状图，数值为……"），之后走纯文本 RAG。优点：检索便宜、可审计、跟现有管线兼容。
2. **统一嵌入路线（CLIP 类）**：用 CLIP/多模态 Embedding 模型把**图片和文本映射到同一向量空间**，检索时"文字 query 直接召回相关图片"，再把图+问题一起丢给 VLM 生成答案。优点：端到端、保留视觉细节；缺点：嵌入模型对密集图表（坐标轴、小字）效果差、VLM 调用贵。

**为什么火**：企业真实文档 30%+ 的信息在图里，纯文本 RAG 天生残缺；截图提问已成为客服/运维标配入口。

**面试怎么聊**：
> "图文档问答我会分两类：'图表转述型'（柱状图、流程图，问的是图里的事实）走**多模态解析入库**，一次性成本，检索仍是文本管线；'视觉定位型'（UI 截图找按钮、医学影像）才值得上 **CLIP 统一嵌入 + VLM 生成**。判断标准：图片信息能否被文字无损转述——能就走便宜路线。"

## 1.5 视频→文本多模态流水线（热点展示区）

> 与 1.4 的分工一句话：**图片（截图/PDF 图表）走 1.4 多模态 RAG；视频流走本节**——视频新增的核心维度是**时间轴**：音轨时间戳对齐、分段检索、带时间戳的可回放证据。

**为什么 2026 面试开始考（定位）**：
视频理解近两年完成了"能用 → 可用"的跨越：一边是 Qwen-VL、Video-LLaVA 这类开源视频语言模型成熟、视觉推理成本降了一个数量级；一边是场景同步落地——**客服质检**（通话与屏幕录像自动质检）、**会议纪要**（音轨+录制自动成稿）、**内容审核**（海量短视频机审初筛），三个场景的共同点是**视频量大到人看不完、业务要的是"可检索、可审计"的文本形态**。面试官爱考它，因为一道题能同时压出多模态、RAG、成本工程三个知识层，正是高级岗要看的交叉能力。

**典型任务四类（一句一任务）**：
- **视频摘要**：输入整段视频，输出"这片子讲了什么"的三五句总览，供速览与检索
- **章节划分**：按语义/场景切出带时间戳的章节目录，相当于给视频生成一份"视频版目录"
- **重点片段提取**：从一小时里捞出"出事的那 30 秒"——质检违规、故障现场、高光时刻
- **视频问答**：对视频内容自由提问，答案必须带时间戳证据、可回放定位

**六步处理流程（白板画这个）**：

```text
原视频（音轨 + 画面）
   │
   ▼
① ASR 提取音轨 ──→ 字幕文本 + 时间戳（t0, t1）
   │
   ▼
② 抽帧/分段 ──→ 场景切换检测 + 均匀采样 → 关键帧序列
   │
   ▼
③ 视觉编码 ──→ CLIP / Qwen-VL 类：帧 embedding + 帧 caption
   │
   ▼
④ 时间戳对齐 ──→ 字幕段 ↔ 帧 绑定为"分段级多模态单元"
   │
   ▼
⑤ 检索 + 重排 ──→ 向量召回相关分段 → 交叉编码器精排 top-k
   │
   ▼
⑥ 分层生成 ──→ 分段先答/先摘要 → 逐级层次汇总（带时间戳）
```

记忆口诀：**转写 → 切帧 → 编码 → 对齐 → 检索 → 汇总**，其中 **④ 时间戳对齐是视频独有的题眼**。

**① ASR：把音轨变成带时间戳的文本**
- Whisper/Paraformer 类模型转写，**必须保留时间戳（t0, t1）**——它是后续一切对齐的锚点
- 有现成字幕轨直接用（成本为零）；裸音轨才跑 ASR；质检/会议场景叠加说话人分离（谁在说、何时说）
- 多语种/重口音素材先小模型探测语言再路由转写模型，别指望一个模型通吃
- ASR 错误会向下游传播，字错率要单独评测；音轨是全管线**最便宜的信息源**——能从字幕回答的问题不要看画面

**② 抽帧/分段：帧率与分辨率是成本的总开关**
- 两条腿走路：场景切换检测（内容突变处切）+ 均匀采样兜底（防长镜头漏采）
- 帧率旋钮：1 fps 是常用起点，谈话类 0.2 fps 够用，监控/操作演示类才加密
- 分辨率旋钮：粗筛用低分辨率缩略图，命中片段细处理才上原生分辨率
- 抽帧时顺手去冗余：相邻帧 embedding 相似度超阈值即丢；静态画面（如 PPT 页）只留一张代表帧

**③ 视觉编码：帧变成可检索的表示**
- 路线继承 1.4 的两分法：**caption 路线**（VLM 把帧转文字描述，入库一次性成本，之后纯文本管线，便宜可审计）vs **统一嵌入路线**（CLIP 类图文同空间，保留纯视觉细节）
- Video-LLaVA / Qwen-VL 类原生视频模型直接吃片段，比逐帧独立编码省 token 且带时序感
- 输出物：每帧/每片段一个 embedding + 一段 caption，全部挂时间戳入库
- caption 质量要抽检：错描述会以"事实"身份进入知识库，比检索错更难排查

**④ 时间戳对齐：本节相对 1.4 的核心增量**
- 把前三步产物按统一时间轴拼成"分段级多模态单元"：[t0, t1] 内 = 字幕段文本 + 关键帧 + 帧 caption + 说话人
- 分段粒度：场景切换为主、说话人边界为辅，一般 30 秒~2 分钟一段——太大检索不准，太碎上下文断裂
- 时钟基准要统一：ASR 分段时间戳与帧采样时间戳常有秒级偏移，需对齐校正
- 这步做完，"视频"被抽象成"带时间戳的多模态文档集合"，下游全部复用标准 RAG

**⑤ 检索 + 重排：双路召回，证据优先**
- 问题同时走文本路（字幕段向量）与视觉路（帧 embedding），双路合并去重
- 两路向量空间不通用：要么各自检索后按分数融合（RRF 类），要么训练统一嵌入空间
- 交叉编码器重排取 top-k：粗召回看相似度，精排看"这段能否作为回答证据"
- 时间邻域扩展：命中 03:20 的段，把 03:10~03:30 一并纳入候选——视频语义常跨段；top-k 取 3~8 段，证据过多会撑爆生成上下文

**⑥ 分层生成：先分段，再汇总**
- 每个命中分段先生成"基于该段证据"的局部回答/摘要，再逐级归并（段 → 章节 → 全片）
- 摘要任务同构：段摘 → 章摘 → 全片摘要，每层结果可缓存复用，长视频不塞长上下文
- 输出必须带时间戳引用（如"见 12:34~12:51"）——可回放证据是视频系统可信度的来源
- 追问预案："为什么不让长上下文视频模型直接看全片？"——答：全片直灌的视觉 token 高出一个量级，且有大海捞针退化，分层管线还能用检索兜住精度

**成本优化三板斧（面试官必追："一小时视频多少钱？"）**：

| 手段 | 做法 | 省在哪 |
|---|---|---|
| 分层处理 | 低分辨率/低帧率粗筛全片 → 只对命中片段高帧率细处理 | 视觉 token 总量降到 1/5~1/10 |
| 分层摘要 | 段→章→全片逐级汇总，不整片塞长上下文 | 避开长上下文高单价与注意力平方开销 |
| embedding 去冗余 | 相邻帧/相似段聚类去重，只存代表帧与代表段 | 存储、索引规模、检索负担同比例下降 |

**小账本（1 小时视频，整数近似，量级估算）**：
- 全量暴力：1 fps 抽 3600 帧 × 约 1k token/帧 ≈ **360 万视觉输入 token**；帧 caption 再输出约 36 万 token；ASR 文本约 1~2 万 token——按主流 VLM 单价量级，**单条视频几美元**，批量化即不可接受
- 分层后：粗筛 0.2 fps × 720 帧 × 约 300 token/帧 ≈ 22 万 token；命中 10% 时长（6 分钟）细处理 360 帧 ≈ 36 万 token；合计约 **60 万视觉 token，压到 1/6**，叠加去冗余还能再降
- 结论话术：**能不能上线，取决于粗筛会不会漏掉关键片段**——所以覆盖率评测是分层方案的生死线

**评测四条线**：

| 维度 | 怎么测 | 红线/判据 |
|---|---|---|
| 事实性 | 生成内容对照字幕/脚本逐句核对："说的是不是视频里发生的" | 无时间戳证据支撑的断言按幻觉处理 |
| 覆盖率 | 拿人工标注的关键事件/场景清单，看摘要与检索是否命中 | 漏掉关键事件比答错更隐蔽，质检场景即事故 |
| 延迟与成本 | 端到端处理时长、单视频 token 账、索引与存储开销 | 离线管线看吞吐，在线问答看 P95 |
| 用户反馈 | 线上采纳率、纪要被人工改动的比例、投诉率 | 机器评不出的痛点在这里最先暴露 |

评测落地节奏：先拿 20~30 条人工标注视频跑通四线基线，再进回归门禁——视频标注贵，评测集要精不要多。

**🎤 口述模板（被问"设计一个视频问答系统"，直接背）**：

> "题眼是**时间轴对齐**：把视频变成可检索的带时间戳片段，之后就是标准 RAG。管线六步：① ASR 提音轨、留时间戳；② 场景切换检测加均匀抽帧；③ 视觉编码走双路——字幕走文本 embedding，帧走 CLIP 类嵌入或 VLM 转 caption；④ 按时间戳把字幕段和帧绑成'分段级多模态单元'，这是对齐核心；⑤ 问题双路召回分段、交叉编码器重排 top-k，再加时间邻域扩展；⑥ 先分段生成、再层次汇总，输出挂时间戳。成本三板斧：分层处理、分层摘要、embedding 去冗余——一小时视频视觉 token 能从三百多万压到六十万左右。可信度收一句：**每句输出都带时间戳、可回放验证——视频系统的可信来自可回放证据，不是模型的自信程度。**"

## 1.6 推理模型（o1/R1 类）对应用架构的影响

**是什么**：
以 OpenAI o1、DeepSeek R1 为代表的"推理模型"：回答前先进行长链条内部思考（测试时计算，test-time compute），用**更长的思考时间换更高的推理质量**，尤其擅长数学、代码、复杂规划。

**对应用架构的五个实际影响**（这是面试官想听的）：

| 影响维度 | 具体变化 | 架构应对 |
|---|---|---|
| 延迟 | 从秒级到 10 秒~几分钟 | 同步 API 变**异步任务**：提交→排队→回调/轮询；前端展示"思考中"的过程性 UI |
| 成本 | 思考 token 也计费，单次成本 3~10 倍 | **模型分层路由**：分类/抽取/简单问答坚决走小模型，只有复杂规划升级推理模型 |
| 规划能力 | 多步任务的成功率显著提升 | Agent 的 Planner 模块可以用推理模型，Executor 仍用快模型——"大脑贵、手脚便宜" |
| Prompt 方式 | Few-shot 示例反而干扰；不需要教它"一步步思考" | Prompt 变**短**：直接说清目标和约束，别写思维链示范；把省下的预算花在**上下文质量**上 |
| 可观测 | 思考过程是新变量 | 记录/分析思考链用于排查与评测 |

**何时值得用（一句话）**：
> "问题值不值 10 倍成本——多步规划、复杂代码、数学计算、疑难诊断值得；分类、抽取、格式转换、日常问答不值得。我的默认架构是**级联**：先小模型，置信度低或自评失败再升级推理模型，让贵模型只接 5%~10% 的难题。"

## 1.7 Fine-tuning 落地决策框架

**核心问题：什么时候 RAG 不够，必须上微调？**

RAG 和微调解决的是两类问题——**RAG 补知识，微调改行为**：

| 症状 | 属于 | 方案 |
|---|---|---|
| 答案必须引用最新/私有文档 | 知识问题 | RAG |
| 输出风格/语气始终不符合品牌要求 | 行为问题 | 微调 |
| 输出 JSON 格式不稳定、指令遵循差 | 行为问题 | 微调（或先试 Prompt 约束） |
| 领域术语/行话密度极高，通用模型读不懂 | 能力问题 | 领域语料微调（Continue Pretrain 或 SFT） |
| 简单任务也要塞几千 token 示例，成本高 | 成本问题 | 微调把示例"烤进"模型，推理变短 |

**决策框架（背这张顺序）**：
1. **先 Prompt**：约束不清楚就改 Prompt，成本最低
2. **再 RAG**：涉及事实/知识/时效，一律 RAG
3. **再考虑微调**：Prompt 和 RAG 都到位后，仍有稳定的"风格/格式/术语"问题，才微调
4. **通常组合拳**：微调管"怎么说"，RAG 管"说什么"——先 RAG 后微调，微调后保留 RAG

**LoRA 成本概念（不推导，只记量级）**：
- 全参微调：动辄几十/上百张 GPU，大多数企业不现实
- LoRA：**冻结原模型，只训练插入的低秩小矩阵**，可训参数约为全参的 1% 以下
- 效果：单张消费级/单张 A100 级显卡、几天内可完成 7B~14B 模型的领域 SFT，成本约为全参的 1%~10%
- 代价：容量上限低于全参（不适合"灌入海量知识"，**想灌知识请回去用 RAG**——这是最经典的坑）

**面试怎么聊**：
> "我的框架一句话：知识用 RAG，行为用微调，风格/格式/术语是微调的三大信号。落地用 LoRA 控成本，但要警惕'用微调灌知识'——容量不够、更新贵、还会灾难性遗忘。我会先做 RAG 三个月攒 badcase，攒出 5000 条高质量样本再评估微调，而不是上来就训。"

## 1.8 2025→2026 趋势判断（一段话，面试聊愿景用）

> 2025 年行业的关键转折是"从 Demo 到生产"：晒截图的时代结束，账单和 SLA 的时代开始。落到技术上，三件事从"加分项"变成"**常态考点**"：①**评测工程化**——评测集像测试集一样进 CI/CD，Prompt/模型每次变更自动跑回归，LLM-as-a-Judge 加人工抽检校准，没有评测的迭代等于裸奔；②**Context Engineering 取代 Prompt Engineering**——单条 Prompt 的措辞不再重要，重要的是系统性决定"什么信息、以什么顺序、多大预算进入上下文"，缓存、压缩、记忆治理都属此列；③**成本工程**——token 预算管控、语义缓存、模型级联路由成为标配组件。2026 年我会赌两个方向：Agent 的**可靠性工程**（沙箱、回滚、审计）和**多 Agent 协作标准**（A2A 类协议）走向生产。这个判断也决定我自己的学习投资顺序。

## 1.9 四方案选型对比（高级岗必考："同一业务问题，四方案怎么选"）

大纲自测题 #4 的完整版。**这是"🎤 面试这样答"示范 1**，见下表后。

| 维度 | RAG | 微调 | 长上下文 | Agent |
|---|---|---|---|---|
| 解决什么 | 知识时效/私有知识 | 风格/格式/领域能力 | 小规模资料一次性分析 | 多步骤任务编排 |
| 知识更新 | 随时（换索引） | 重新训练，周级 | 重新塞 Prompt，即时 | 取决于内部检索 |
| 单次成本 | 中（检索+生成） | 训练贵/推理便宜 | **最高**（长输入 token 贵） | 高（多轮调用） |
| 延迟 | 秒级 | 秒级（可更短） | 随长度线性变差 | 秒~分钟 |
| 可控性/可审计 | **高**（引用溯源） | 低（知识烤进权重） | 中（全文可查但难定位） | 中（依赖轨迹日志） |
| 典型陷阱 | 检索失败→幻觉 | 灌知识、灾难遗忘 | 大海捞针、成本爆炸 | 失控循环、延迟叠加 |
| 一句话适用 | "答事实要出处" | "改行为定型" | "资料少且一次性" | "要串多个动作" |

**🎤 面试这样答（示范 1）——"同一个业务问题，RAG/微调/长上下文/Agent 四个方案你怎么选？"**：

> "我先用一个问题切：**这个业务缺的是'知识'还是'能力'还是'流程'**。
> 缺知识、答案要出处——RAG，首选，因为可审计、可即时更新；
> 缺能力、行为要定型（风格、格式、术语）——微调，但要先确认 RAG 和 Prompt 已经到顶，且能攒出高质量训练集，用 LoRA 控成本；
> 资料规模小（几十篇以内）且一次性任务（如合同审阅）——长上下文直接塞，简单粗暴，但要算 token 账，超过几百万 token 或高频调用就不划算；
> 任务需要串联多个系统动作（查订单→改地址→发通知）——Agent，本质是流程自动化，可靠性靠工具幂等和轨迹审计兜底。
> 现实中几乎都是组合：我做过的话术是'**微调定行为，RAG 供事实，Agent 做编排，长上下文只做小场景兜底**'。判断顺序永远从便宜到贵：Prompt → RAG → 长上下文 → 微调，Agent 是正交维度随时叠加。"

## 2.0 万能答题框架：六步法

不管题目是知识库、客服还是 Agent 平台，**永远用同一套骨架**——练到肌肉记忆，考场上只是往骨架里填业务。

```text
┌─────────────────────────────────────────────────────────┐
│  ① 需求澄清 —— 先问再画！用户量/QPS/延迟/准确率/预算/合规  │
│  ② 能力拆解 —— Plan / Tools / Memory / Knowledge /       │
│                 Evaluator 五模块，对号入座               │
│  ③ 数据流 —— 白板画架构图 + 关键模块时序                  │
│  ④ 容量评估 —— 数字！→ 指出瓶颈 → 降级/熔断/灰度         │
│  ⑤ 成本-效果折衷 —— 模型选型/缓存/级联，每处给权衡        │
│  ⑥ 评测与监控 —— 没有评测的 AI 系统等于裸奔              │
└─────────────────────────────────────────────────────────┘
```

**一页速记图（考前 10 分钟看这个）**：

```text
考官抛题
   │
   ▼
①澄清 ── "我先确认几个数字" ──── 用户量? 峰值QPS? 延迟目标?
   │                            准确率目标? 月预算? 数据能否出域?
   ▼
②拆解 ── "这个系统本质是五种能力" ─┐
   │        Plan:      谁决定下一步做什么        │
   │        Tools:     需要哪些外部能力          │
   │        Memory:    会话记忆/长期记忆放哪     │
   │        Knowledge: 知识从哪来、怎么更新      │
   │        Evaluator: 怎么知道答对了            │
   ▼                                  │
③画图 ── 主数据流(实线) + 异步管线(虚线) + 失败路径(红色标记)
   ▼
④算账 ── 存储: 文档数×大小 / 向量: 块数×(维度×4B)
   │     流量: 日活×次数÷86400 ×峰值系数
   │     → "瓶颈在 X" → 降级链: A超时→B→C兜底 → 灰度发布
   ▼
⑤折衷 ── 模型分级(贵贱搭配) / 缓存(精确→语义) / 级联(先小后大)
   ▼
⑥闭环 ── 金标集→离线指标→线上反馈→回归门禁→告警看板
   │
   ▼
"以上是我的整体设计，您想深入哪个模块？"
```

**六步法的三条铁律**：
1. **不问不画**：需求澄清的问题本身就是得分点（面试官故意不给全数字，等你问）
2. **没有数字的设计是散文**：容量估算全部整数近似，够用就行（1000 万文档 × 50KB ≈ 500GB，别按计算器）
3. **每个亮点配一个权衡**：说"我用 Rerank"必须跟上"代价是延迟 +300ms，所以超时自动跳过"

## 2.1 设计题一：企业知识库问答系统

**题面**：为公司设计内部知识库问答，文档从 10 万增长到 1000 万，要求权限隔离、多租户、增量更新、可评测。

### 第①步 需求澄清（问答示例）

| 我问 | 面试官答（假设） | 对设计的影响 |
|---|---|---|
| 用户规模？ | 全员 5 万，日活 5000 | 流量不大，重点在数据侧 |
| 文档规模与增速？ | 起步 10 万，三年到 1000 万，日增 1% | 架构必须天生支持演进 |
| 延迟要求？ | 首字 P95 < 3 秒 | 流式输出 + 检索并行化 |
| 准确率要求？ | 宁可拒答不可答错 | 拒答机制 + 引用溯源是核心指标 |
| 权限模型？ | 按部门 + 密级，答案级过滤 | 权限过滤必须深入检索层 |
| 预算/合规？ | 数据不出域，私有化优先 | 模型选型受限，成本敏感 |

### 第②步 能力拆解（五模块对号入座）

- **Plan**：查询改写（多轮指代消解）、检索策略路由（单跳/多跳）
- **Tools**：向量检索、BM25 检索、元数据过滤（时间/部门）、SQL 统计查询
- **Memory**：会话级（近 3 轮改写用）；本场景无长期记忆需求
- **Knowledge**：离线索引管线（解析→切块→向量化→双写）+ 增量更新
- **Evaluator**：引用核验（答案里的出处必须真实存在）+ 拒答质量

### 第③步 架构图（白板画这个）

```text
【在线链路】
用户提问 ──→ 权限网关(身份/ACL) ──→ 查询理解(改写/指代消解)
                                        │
              ┌─────────────────────────┼──────────────┐
              ▼                         ▼              │
        向量检索(Milvus)          BM25检索(ES)          │
        [权限预过滤]              [权限预过滤]           │
              └───────────┬────────────┘              │
                          ▼                            │
                    Rerank(精排Top50→Top5)             │
                          ▼                            │
              LLM生成(引用+拒答判断) ←── 语义缓存命中?───┘
                          ▼
                  引用核验 ──→ 流式回答
                          └─→ 反馈埋点(点赞/点踩)

【离线管线】(虚线异步)
文档源(OA/Wiki/网盘) ─CDC变更─→ 解析器(PDF/Office/扫描件OCR)
      → 切块(标题层级+512token, Parent-Child)
      → 向量化(批处理) ──双写──→ 向量库 + 倒排索引
      → 旧版本软删除(版本号标记)
```

### 关键设计决策表

| 决策点 | 选项 | 选择及理由 |
|---|---|---|
| 权限过滤时机 | 检索后过滤 vs 检索前过滤 | **检索前**把 ACL 拼进过滤条件。后过滤会导致"召回 100 条过滤剩 3 条"，Top-K 不足质量骤降 |
| 切块策略 | 固定长度 vs 结构感知 | 结构感知（按标题层级）+ Parent-Child：检索命中子块，送入 LLM 的是父块，兼顾召回精度与上下文完整 |
| 向量库 | pgvector vs Milvus | 10 万文档 pgvector 够用（运维简单）；1000 万级选 Milvus 集群（分片+标量过滤强）。演进而非一步到位 |
| 多租户隔离 | 共享索引+租户ID过滤 vs 独立索引/实例 | 中小租户共享+过滤（省成本），金融类大租户独立索引（合规），**分级隔离** |
| 增量更新 | 定时全量 vs CDC 增量 | CDC 增量为主 + 每周全量对账（防漏）。删除用软删（版本标记），检索时过滤 |
| Embedding 更新 | 热切换 vs 双索引切换 | 双索引蓝绿切换：新索引建好→原子切流量→旧索引下线，避免边建边查的抖动 |

### 第④步 容量评估（整数近似）与瓶颈

```text
存储：
  原文:   1000万文档 × 50KB ≈ 500GB（对象存储）
  切块:   平均 20 块/文档 → 2亿块
  向量:   1024维 × 4字节 = 4KB/块 → 2亿 × 4KB ≈ 800GB 裸数据
          含索引副本 ×2.5 ≈ 2TB → Milvus 3节点集群(各1TB NVMe)
流量：
  日活 5000 × 10 问 = 5万问/日 ≈ 平均 0.6 QPS
  峰值系数 ×20 ≈ 12 QPS → 单集群轻松扛住(向量检索单机千级QPS)
  瓶颈不在在线，在离线：日增 1% = 10万文档 = 2000万... 不对，
  日增 1% = 10万文档 × 20块 = 200万块向量化
  批量嵌入 2000块/秒 → 约 17 分钟跑完，离线窗口充足
```

**瓶颈结论**：在线 QPS 压力小，真正瓶颈是**检索质量**（效果问题）和 **LLM 生成延迟**（首字 3 秒约束）。所以优化重心：Rerank 控制延迟预算（300ms 超时跳过）、生成走流式。

**降级链路**：Rerank 超时 → 跳过精排用召回序；向量库故障 → 降级纯 BM25；LLM 超时 → 语义缓存热门问答 → 模板答案+原文链接。**每级降级都保引用**。

### 第⑤步 成本-效果折衷

- **模型分级**：查询改写用小模型（7B 级，毫秒级）；生成用中标模型；只有多跳复杂问题升级大模型
- **语义缓存**：企业场景问题重复度高（制度、流程类问题），语义缓存命中率 20%~30%，直接省等比例生成成本
- **级联设计**：先检索 Top5 证据，若 Rerank 分数全部低于阈值 → 不进生成，直接拒答+转人工工单（省了最贵的生成调用，还减少幻觉）

### 第⑥步 评测与监控

- **金标集**：从真实查询抽 1000 条，业务专家标注标准答案 + 应引用文档，覆盖高频/长尾/无答案三类（无答案类专门考拒答）
- **离线指标**：召回率@K（检索）、引用正确率（证据链）、Faithfulness（答案忠实度）、拒答准确率
- **在线指标**：点赞率/点踩率、采纳率、无结果率、P95 延迟、缓存命中率
- **门禁**：任何切块/Prompt/模型变更，金标集回归通过才能发（灰度 5%→50%→100%）
- **监控告警**：点踩率环比涨 50% 告警；每周 badcase 评审回流金标集

### 面试官追问 Top5 及答法

1. **"文档更新了，旧答案还在缓存里怎么办？"** —— 语义缓存 key 携带相关文档的版本号指纹，文档变更使指纹失效；不能精确关联的，设 TTL 短（如 1 小时）+ 高敏文档（薪酬/制度）不走缓存。
2. **"权限过滤漏了导致越权泄露怎么防？"** —— 纵深防御：检索层预过滤（第一道）+ 生成后核验（答案引用的文档 ACL 再查一遍，第二道）+ 审计日志全链路留痕（事后可追责）+ 红队用"跨部门钓鱼问题"定期渗透测试。
3. **"1000 万文档混合检索慢怎么办？"** —— 先问慢在哪：向量侧→Milvus 分片+标量预过滤减少扫描量；BM25 侧→ES 分层存储热温冷；真正万能的是**先元数据粗过滤再检索**（部门/时间过滤能砍掉 90% 候选）。
4. **"怎么证明你的 RAG 比关键词搜索好？"** —— 不嘴炮，上评测：同一金标集跑两套管线对比召回率@K 和端到端正确率；再按 query 类型分层看——事实型查询两者接近，语义型（换个说法）RAG 明显胜出，这决定哪些场景值得付向量检索的成本。
5. **"拒答太多用户投诉怎么办？"** —— 拒答是特性不是缺陷，但要分级：无证据拒答（正确行为）、有证据但检索失败（bug，修检索）、模糊证据（给"可能相关"并附原文让用户判断）。同时拒答必须给下一步动作：转人工/提交工单/推荐相似已答问题。

## 2.2 设计题二：智能客服 Agent

**题面**：为电商平台设计智能客服，要处理订单/物流/退款查询，有工具链，需转人工，要控制幻觉投诉。

### 第①步 需求澄清（问答示例）

| 我问 | 假设答案 | 影响 |
|---|---|---|
| 日均会话量？ | 50 万 | 中大流量，成本敏感 |
| 峰值？大促呢？ | 平峰 200 QPS，大促 ×5 | 必须弹性+降级预案 |
| 转人工率目标？ | 从 40% 降到 10% | 核心北极星指标 |
| 首响/解决率？ | 首响 <2s，机器人解决率 >60% | 流式输出 + FAQ 分流 |
| 高危操作？ | 退款、改地址 | 需确认机制+额度控制 |
| 预算？ | 按 token 计费，季度考核成本 | 级联路由必须有 |

### 第②步 能力拆解（五模块）

- **Plan**：意图路由（一级分类）→ 对话策略（追问补槽 vs 直接执行）
- **Tools**：查订单、查物流、创建退款、修改地址、创建工单、转人工（工具全部幂等设计，携带请求 ID 去重）
- **Memory**：会话记忆（订单上下文、已确认信息）；用户长期画像（会员等级、历史投诉）只读注入
- **Knowledge**：FAQ 精确库 + 商品/政策知识库 RAG
- **Evaluator**：答案合规审查（承诺类话术检测）+ 满意度

### 第③步 架构图（白板画这个）

```text
用户消息 ──→ 接入网关(限流/会话粘性)
                │
                ▼
        意图路由(小模型分类器, 50ms)
        ├─① FAQ精确命中(30%) ──→ 模板直出(不调LLM, 零幻觉)
        ├─② 简单查询(40%) ──→ Agent工具链: LLM产调用参数
        │        ┌──────────────────────────┐
        │        │ LLM ─选工具─→ 工具执行 ──┤
        │        │  ↑______结果回填再决策___│ (最多3轮)
        │        └──────────────────────────┘
        ├─③ 复杂/政策类(20%) ──→ RAG检索+生成(带引用)
        └─④ 高危/低置信/投诉(10%) ──→ HITL转人工坐席
                                      (全量上下文移交, 不让用户重说)

        所有生成路径 ──→ 合规过滤器(禁承诺/禁赔偿话术)
                    ──→ 满意度评价(每轮可点踩)
                    ──→ 全链路Trace(审计+回流评测集)
```

### 关键设计决策表

| 决策点 | 选项 | 选择及理由 |
|---|---|---|
| 意图路由 | 规则 vs 小模型分类器 vs 大模型自路由 | 小模型分类器：比规则准、比大模型便宜快（50ms/近零成本）；长尾兜底走"未识别→澄清话术" |
| LLM 调用形态 | 单次大 Prompt vs ReAct 多轮 | 工具链用受控 ReAct（**最多 3 轮**防死循环）；政策问答单次生成。按意图分流，不全局 Agent 化 |
| 工具失败处理 | 静默重试 vs 反馈 LLM 重规划 vs 直接降级 | 反馈重规划 1 次 + 幂等重试，再失败→降级话术+工单。绝不静默重试（用户等不起，且易雪崩） |
| HITL 触发 | 用户主动 vs 系统主动 | 双通道：用户可随时转；系统在"低置信度/投诉关键词/高危操作确认失败/3轮未解决"时强制转 |
| 上下文移交 | 只传摘要 vs 全量轨迹 | 全量轨迹（结构化：已确认的订单号、已做的操作、用户情绪标记），坐席零冷启动 |

### 第④步 容量评估与瓶颈

```text
会话: 50万/日 × 平均5轮 = 250万轮/日 ≈ 平均 29 轮/秒
大促峰值 ×5 ≈ 150 轮/秒
分流估算: 30% FAQ(0次LLM) + 40%工具链(2次LLM)
         + 20% RAG(1次LLM) + 10%转人工(1次分类)
LLM调用 ≈ 150 × (0.4×2 + 0.2×1 + 0.1×1) ≈ 165 次/秒峰值
Token:   输入2K + 输出300 ≈ 2300 token/次
峰值吞吐 ≈ 165 × 2300 ≈ 38万 token/秒 —— 上游API多key+排队
转人工: 10% × 50万 = 5万/日, 峰值600/小时 ÷ 坐席并发3
        ≈ 需要 200 在线坐席(大促弹性排班)
瓶颈: ①上游 LLM API 吞吐(限流) ②坐席资源(成本大头)
```

**降级熔断**：LLM 错误率 >5% 熔断该模型 → 备用模型（上下文格式保持一致，用户无感）；上游全挂 → FAQ 库 + 规则话术兜底（覆盖 Top100 高频问题）；情绪升级（用户连发两条不满）→ 直接跳转人工优先队列。

### 第⑤步 成本-效果折衷

- **路由省钱**：30% 流量被 FAQ 精确拦下，零 LLM 成本——这是最大的单点优化
- **级联**：分类器(近零成本) → 小模型(1) → 中模型(5) → 大模型(20)，按问题难度上升，钱花在刀刃
- **会话缓存**：订单状态类查询 5 分钟内重复问，工具结果缓存直接复用

### 第⑥步 评测与监控

- **意图路由**：准确率/混淆矩阵（每周用线上抽样人工标注 500 条校准）
- **Agent 轨迹**：任务完成率、工具调用成功率、平均轮次；失败轨迹 100% 落库供复盘
- **生成质量**：合规话术违规率（零容忍）、点踩率、幻觉投诉率
- **业务北极星**：机器人解决率、转人工率、CSAT、首响 P95
- **门禁**：话术模板/Prompt/路由阈值变更 → 回放历史 badcase 集回归

### 🎤 面试这样答（示范 2）——"幻觉投诉从 5% 压到 0.5%，一周内怎么落地？"

> "一周干不完'根治幻觉'，但干得完'止血'。我按止血→加固→长效三步：
> **第 1~2 天止血**：先查投诉聚类——80% 的幻觉集中在退款政策和运费规则两类高敏问题。对这两类直接上**硬规则**：不走自由生成，改为'政策原文引用 + 固定模板'，模型只做填空不做发挥；同时话术层加合规过滤器，赔偿/承诺类词汇零容忍。
> **第 3~5 天加固**：这两类问题改走强约束 RAG——检索不到证据直接拒答转人工，绝不硬答；Prompt 层加'仅根据以下内容回答，没有就说不知道'；输出必须带政策文档链接，用户可自查。
> **第 6~7 天长效**：把本次投诉全部转成回归测试用例，进发布门禁；上线'点踩即审计'——每次点踩自动记录完整轨迹，每周评审回流。
> 一周后的数字：高敏问题幻觉率趋近于 0（因为根本不让自由发挥），整体投诉 5%→0.5%。**代价是这两类问题的回答变'笨'了，但客服场景，宁可笨不可错。**"

### 面试官追问 Top5 及答法

1. **"Agent 会不会死循环调工具？"** —— 三重保险：轮次硬上限（3 轮）+ 工具级冷却（同一工具同参数 2 次失败即禁）+ 总 token 预算熔断。触发任意一条→降级转人工，并记录轨迹供分析。
2. **"怎么保证工具调用幂等？"** —— 每个调用携带请求 ID，服务端按 ID 去重（跟支付防重是同一套后端逻辑）；LLM 重试由框架层拦截发起新 ID 的重复调用，只对**读操作**自动重试，**写操作**（退款）必须用户确认后执行且只执行一次。
3. **"转人工坐席不够怎么办？"** —— 排队优先级队列（情绪/高危/VIP 加权）+ 排队时机器人继续收集信息（结构化，坐席接手即有完整上下文）+ 大促前按历史流量弹性排班；极限情况 VIP 独享通道。
4. **"用户骂机器人，情绪升级怎么处理？"** —— 情绪分类器实时监测（负面词+连续否定+感叹密度），触发即转人工优先队列 + 话术安抚；情绪事件全量落库，是客服质量的领先指标。
5. **"大促流量 ×5，系统怎么扛？"** —— LLM 调用是瓶颈：提前压测上游配额、多供应商分流；FAQ 命中率战前优化（大促规则提前录入）拦截更多流量；非核心功能（主动推荐、满意度弹窗）降级关闭；全链路限流保坐席系统可用。

## 2.3 设计题三：万级并发 Agent 服务平台

**题面**：设计一个 ToB 的 Agent 服务平台：1000 家企业租户，峰值 1 万并发 Agent 会话，要求 Prompt 热更新、灰度发布、租户级成本核算。

### 第①步 需求澄清（问答示例）

| 我问 | 假设答案 | 影响 |
|---|---|---|
| 并发定义？ | 同时活跃会话 1 万，每会话 20 轮 | 长连接 + 状态管理是重点 |
| 单轮延迟？ | 工具调用 P99 <5s，生成首字 <3s | 流式 + 并行工具 |
| 租户差异？ | 各自 Prompt/工具集/模型偏好 | 配置化 + 隔离 |
| 热更新要求？ | 改 Prompt 5 分钟内全量生效 | 配置中心推送 |
| 成本核算粒度？ | 租户/会话/工具三级账单 | 全链路计量 |
| SLA？ | 99.9% 可用性，大租户独立配额 | 分级保障 |

### 第②步 能力拆解（五模块）

- **Plan**：Agent 编排引擎（DAG/ReAct 可配），租户自定义流程
- **Tools**：平台内置工具市场 + 租户私有工具注册（MCP 接入标准化）
- **Memory**：会话状态外置（Redis + 持久化存储）；长期记忆按租户隔离
- **Knowledge**：租户级向量空间（逻辑隔离，索引带 tenant_id）
- **Evaluator**：平台级评测服务（租户上线前跑基准 + 线上抽样巡检）

### 第③步 架构图（白板画这个）

```text
租户终端 ──→ 接入层(WebSocket长连接网关×N, 会话粘性)
               │  鉴权/限流/租户配额
               ▼
        编排层 Agent Runner (无状态, 水平扩展 ×50)
               │  ┌─ 会话状态 ←→ Redis集群(热) → 持久DB(冷)
               │  ├─ Prompt配置 ←→ 配置中心(版本化+推送)
               │  └─ 租户工具注册表
               │
        ┌──────┼───────────┐
        ▼      ▼           ▼
   模型网关   工具执行池    评测总线
   (多模型路由 (容器沙箱     (异步,
    /语义缓存  /网络白名单   全量轨迹
    /熔断分级  /超时隔离)    落仓)
    /计量)
        │
        ▼
   计费聚合(token/工具/租户三级账目 → 小时级出账)
```

### 关键设计决策表

| 决策点 | 选项 | 选择及理由 |
|---|---|---|
| Runner 状态 | 本地内存 vs 外置 Redis | **无状态 + 外置**：水平扩展、宕机秒级恢复、滚动发布不丢会话。代价是每轮多一次 Redis 读（<5ms，值得） |
| Prompt 热更新 | 重启生效 vs 配置中心推送 | 配置中心（版本化存储 + 推送），Runner 监听变更，**新轮次生效**（进行中会话不打断）；回滚=切回旧版本号，秒级 |
| 灰度发布 | 全量 vs 按租户分批 | 按"内部租户→5% 小租户→50%→全量"分批；每批观察错误率/满意度门禁，异常自动停批回滚 |
| 多租户隔离 | 共享池 vs 独立实例 | 默认共享（成本低）+ 大租户独立模型配额与限流域；工具沙箱按租户强隔离（一个租户的私有工具绝不能被别家看到） |
| 成本核算 | 事后抽样 vs 全链路计量 | 全链路计量：网关层记 token、工具池记调用次数、按 trace ID 聚合到租户账目。计量本身成本 <1% 流量，可接受 |
| 沙箱 | 进程隔离 vs 容器 vs microVM | 容器（Docker/gVisor）：租户自定义代码的执行环境，网络白名单+CPU/内存限额+只读文件系统 |

### 第④步 容量评估与瓶颈

```text
并发: 1万活跃会话, 平均每轮10秒 → 1000 QPS 模型调用
  工具调用: 每轮平均2次 → 2000 QPS 工具执行
长连接网关: 1万连接 × 10KB 会话内存 = 100MB
  单机10万连接无压力 → 网关4台(冗余+滚动发布)
Agent Runner: 单实例16核可处理 ~40 并发编排
  1万 ÷ 40 = 250... 保守按会话峰值3万 → 50~75台(弹性组)
模型网关: 1000 QPS × 平均5K token/轮 = 500万 token/秒
  多供应商分流 + 语义缓存(命中率25%) + 排队整形
瓶颈排序: ①上游模型吞吐 ②工具执行池资源 ③Redis带宽(次之)
```

**弹性设计**：Runner 无状态 + K8s HPA（按队列深度扩容）；上游模型配额用租户权重公平调度（防一家大促打爆全平台）；工具沙箱池预热（冷启动 2 秒不可接受）。

**降级熔断**：模型分级熔断（主→备→小模型简化应答）；工具超时快速失败（不阻塞主链，告知用户该能力暂不可用）；租户级限流兜底——**平台稳优先于单租户体验**。

### 第⑤步 成本-效果折衷

- **语义缓存平台化**：跨租户不共享（隔离），租户内命中率 20%~30%，直接是毛利
- **模型路由开放给租户**：默认性价比档，租户可付费升级——成本变成收入杠杆
- **级联默认开**：简单轮次小模型，复杂规划才升级；平台赚差价也降低租户门槛

### 第⑥步 评测与监控

- **平台监控**：并发/队列深度/首字延迟 P99/工具成功率/熔断触发次数/灰度批次指标
- **租户维度**：满意度、完成率、token 成本趋势（异常暴涨预警——可能是 Prompt 回归或攻击）
- **评测服务**：租户上线强制跑基准集；平台每周金标集巡检各租户（防止某家改坏还不知道）；Prompt 变更强制回归（这是热更新的安全网，**没有回归门禁的热更新等于裸奔**）

### 面试官追问 Top5 及答法

1. **"Prompt 热更新出 bug 影响所有租户怎么办？"** —— 三道闸：变更前强制回归评测（门禁）→ 变更后按租户分批灰度（爆炸半径可控）→ 版本秒级回滚。加上 Prompt 版本与轨迹绑定，出问题可精确追溯"哪批会话受影响"。
2. **"一个租户流量暴涨打爆平台？"** —— 租户级限流 + 配额（令牌桶），超配额排队或拒绝并明确告知；模型网关按租户权重公平调度；大租户引导独立资源池（加钱）。
3. **"Runner 发布时会话怎么办？"** —— 优雅下线：摘流量 → 等进行中轮次完成（上限 60 秒）→ 会话状态本就在外置 Redis，新 Runner 接管下一轮，用户无感。这是无状态化的直接红利。
4. **"工具沙箱被租户拿来跑恶意代码？"** —— 容器级隔离（gVisor 强化）+ 网络白名单（默认禁出网，白名单显式开）+ 资源限额（CPU/内存/执行时长）+ 只读文件系统 + 行为审计日志。跟公有云函数计算的防护模型一致。
5. **"成本核算怎么做得可信？"** —— 计量点选在模型网关（token 由 usage 返回值为准，不是自己估算）+ trace ID 全链路串联 + 小时级对账（网关计数 vs 供应商账单，差异告警）。审计可回放。

## 2.4 设计题四：多模态客服（截图 + 文本提问）

**题面**：客服场景，用户发一张 App 报错截图 + "这怎么回事？"，设计意图理解与处理链路。

### 第①步 需求澄清（问答示例）

| 我问 | 假设答案 | 影响 |
|---|---|---|
| 图片占比？ | 20% 会话带图 | 主链路仍文本，图片是增强分支 |
| 图片类型？ | 报错截图 70%/支付凭证 20%/其他 10% | 信息抽取路线可行 |
| VLM 成本约束？ | 单图预算 < 0.01 元 | 需要缓存+分级 |
| 准确率？ | 错误码识别 >95% | 传统 OCR 可兜底 |
| 无图用户？ | 需引导补图话术 | 多模态降级路径必须设计 |

### 第②步 能力拆解（五模块）

- **Plan**：意图链 = 图片理解 → 与文本意图融合 → 路由决策
- **Tools**：VLM 图片解析、OCR 兜底、订单/退款工具（同题 2）、图片合规检测
- **Memory**：会话内图片引用（图不重复解析，结果缓存）
- **Knowledge**：错误码知识库（结构化！错误码→原因→解决方案）
- **Evaluator**：图片解析质量抽检 + 端到端解决率

### 第③步 架构图（白板画这个）

```text
用户消息(截图+文本"这怎么回事?")
   │
   ▼
图片预处理(大小压缩/清晰度/合规鉴黄)
   │
   ▼
VLM结构化抽取(提示词: 提取错误码/UI页面/订单号/金额)
   │  输出: {页面:"支付页", 错误码:"E4023", ...}
   ▼
意图融合(VLM结果 + 用户文本 → 统一意图表示)
   │
   ├── 错误码命中知识库? ──→ 是 → RAG/模板直出解决方案
   │                       └─ 涉及订单? → Agent工具链(查单/退款)
   ├── 模糊(截图无关)? ──→ 追问话术:"请问您遇到的是支付问题吗?"
   └── VLM失败/超时 ──→ 降级: OCR抽错误码 + 引导用户文字描述

缓存: 同图片hash → 结构化结果缓存(命中率15%, 图片重发常见)
```

**意图链设计要点**（本题题眼）：**不要让 VLM 直接"回答问题"，让它做"信息抽取"**。抽取转结构化文本后，主链路（意图路由→FAQ/RAG/Agent 工具）与纯文本客服完全复用——多模态只是前端加了一个"翻译层"，架构侵入最小。

### 关键设计决策表

| 决策点 | 选项 | 选择及理由 |
|---|---|---|
| 图片理解路线 | VLM 端到端回答 vs VLM 抽取+文本主链 | **抽取路线**：复用已有文本链路（路由/工具/RAG 全不用改）、可审计、错误码类准确率更高；端到端回答贵且不可控 |
| VLM 部署 | 通用 API vs 自部署小模型 | 起步通用 API（迭代快）；量大后高频场景（错误码截图）蒸馏小模型自部署，长尾留 API |
| OCR 的角色 | 主力 vs 兜底 | 兜底+增强：错误码数字类 OCR 便宜且准，VLM 失败时 OCR 抽码 + 知识库直查，多数场景够用 |
| 图片缓存 | 不缓存 vs hash 缓存 | 图片 hash → 抽取结果缓存：用户重发同图（常见于追问）零成本；命中率 15% 就是 15% 的 VLM 费用 |
| 模糊图片处理 | 硬答 vs 追问 | 追问优先（"能重新截一张包含错误码的图吗"）；VLM 置信度低硬答是幻觉重灾区 |

### 第④步 容量评估与瓶颈

```text
图片量: 50万会话/日 × 20% = 10万图/日 ≈ 平均 1.2 图/秒
大促峰值 ×5 ≈ 6 图/秒
VLM成本: 每图输入1K token + 输出300 token
  10万 × 1.3K = 1.3亿 token/日
  按 0.003元/1K ≈ 400元/日, 缓存省15% ≈ 340元/日 —— 可接受
延迟: VLM解析 1~2秒 + 文本主链路 2秒 ≈ 首响 3~4秒
  优化: VLM流式抽取 + 预处理并行, 可压到 3秒内
瓶颈: VLM吞吐(与文本LLM共享网关, 需独立配额)
```

**降级链**：VLM 超时/故障 → OCR 抽错误码（覆盖 70% 场景）→ OCR 也失败 → 引导话术"请用文字描述您看到的内容"（**多模态系统的责任是优雅地退回文本模式**）。

### 第⑤步 成本-效果折衷

- 分级处理：先轻量分类（这图值不值得 VLM？表情包/无关图直接跳过）→ 只有业务相关截图进 VLM
- 缓存三层：图片 hash 精确缓存 → 错误码直查知识库（不进 VLM）→ 才是 VLM 全量解析
- 支付凭证类（低频高价值）保留 API 大模型；错误码类（高频模式固定）蒸馏小模型

### 第⑥步 评测与监控

- **抽取质量**：每周人工抽检 500 张（字段级准确率：错误码、金额、页面名）
- **端到端**：带图会话解决率 vs 纯文本会话（多模态必须证明"值得"，不能只加分不解决）
- **降级监控**：VLM 失败率、OCR 兜底命中率、追问转化率
- **专项**：模糊图追问后的补图率（追问话术本身也要迭代）

### 面试官追问 Top5 及答法

1. **"用户发无关图片/表情包怎么办？"** —— 入口轻量分类器先过滤（图片是否业务相关），无关图不进 VLM 直接按纯文本处理；这是成本保护，也是防"用户拿图片注入"的攻击面。
2. **"图片里藏 Prompt Injection？"** —— 多模态间接注入是真实威胁：VLM 只做结构化抽取（输出校验 JSON schema，非指令），抽取结果作为**数据**而非指令进入主链路；主链路 Prompt 明确"截图内容仅供参考数据"；高危字段（订单号）正则校验格式。
3. **"VLM 抽错了错误码导致答非所问？"** —— 抽取结果带置信度回显给用户确认（"您遇到的错误码是 E4023 吗？"）——一次确认换取准确率兜底；低置信直接追问补图。
4. **"为什么要复用文本主链路，直接 VLM 端到端不是效果更好？"** —— 三个理由：成本（抽取 300 token vs 端到端长输出）、可控（结构化可校验，自由文本不可审计）、架构（文本链路的路由/工具/评测全部复用，多模态只是一层适配）。端到端只在开放性视觉问题（"这个界面怎么找不到入口"）才局部启用。
5. **"语音/视频客服要不要预留？"** —— 架构上预留"模态适配层"：任何新模态都遵循"转结构化/文本表示 → 进统一意图链"的约定。语音 = ASR 转文本（已天然符合）；视频 = 关键帧抽取 + 走图片链。**考的是扩展性意识，不是真的实现。**

## 进阶篇：高级岗深挖区（定级之战）

> 基础篇教你"把题答完"，进阶篇教你"把级定高"。高级岗终面的真实剧本是：你按六步法流畅答完，面试官不动声色地改一个需求——"预算砍半""流量涨 10 倍"——看你是推倒重讲，还是**框架不变、参数重算**。前者像背过设计，后者像设计过系统。本篇四块：**变体题应对、二层追问链、白板节奏、高级视野**——系统设计定你的级，这一篇决定定在哪一级。

---

### A. 系统设计"变体题"应对（面试官改需求怎么办）

变体题的内核一句话：**需求变了，架构骨架大概率不变，变的是参数与取舍**。资深工程师的第一反应不是推翻重来，而是先定位"新需求冲击的是六步法的哪一步"——成本（⑤）、容量（④）、质量（⑥）还是范围（①②）？先定性，再重算。下面四个变体覆盖四类典型冲击：前两个对应基础篇的题 1/题 2，后两个（代码助手、AI 搜索）是面试官手里的高频姊妹题——应对套路完全同构。每个变体只给**重新推演的关键步骤**，架构图不重画——这就是答案本身。

#### A.1 变体一（企业知识库）："预算砍半，准确率要求不降"

**先定性**：成本冲击，主打第⑤步。架构不动，动的是"钱花在哪"——降本不是均匀压缩，是在成本-质量曲线上**从当前点移到拐点上方的最优点**，把"质量冗余"变现。

**重新推演的关键步骤**：

1. **先反问一句定基调**："预算砍半是暂时的还是长期的？砍的是模型调用费还是总拥有成本（含向量库、人力）？"——长期砍总成本才动索引架构，短期砍月账单先动级联和缓存。这一个问题就值半级。
2. **模型级联降本（大头）**：检索日志显示 ~80% 的提问是"单文档事实型"（查制度、查流程），这类走 7B 级小模型 + 强约束 RAG，质量几乎无损；多跳推理、开放式总结才上旗舰模型。典型分布 **80% 小 / 20% 大**，生成侧成本直接降 60%+。路由用"规则 + 小分类器"两层，冷启动没标注数据就用 embedding 近邻路由（历史流量天然是标注集）。
3. **缓存提效（第二大头）**：企业知识库提问分布长尾高度集中——制度类 top 高频。精确缓存 + 语义缓存（阈值 0.95 起、知识库版本号进过滤条件防污染）通常吃掉 20-35% 流量，命中部分成本趋近于零。
4. **索引精简（结构性省）**：三招——**切块去重**（simhash 合并近重复块，文档改版率 30%+ 意味着历史版本块占着死权重）、**低价值块淘汰**（检索日志 90 天零命中的块降冷归档，主索引瘦身 30-40%）、**精度降档**（向量 fp16→int8，存储减半，召回损失 <1%，用金标集实测说话）。
5. **报数字收尾**："三招叠加，月账单预计降 55-65%；质量用金标集回归验证，目标持平——如果回归掉点超 1 个点，我先回滚索引精简，因为它最难兜底。"

**成本-质量取舍曲线（白板现画，口算依据）**：

```text
 质量
  ▲                            ★ 当前点: 全走旗舰模型
  │                          ╱    花钱买"用不到的质量"= 冗余段
  │                        ╱
  │                      ╱  ● 级联+缓存后: 质量基本不变
  │                    ╱      成本降 60% (吃掉冗余段)
  │                  ╱
  │                ╱  ▲ 拐点: 再省 1 元钱, 质量明显掉
  │              ╱      (小模型接了超出能力的难题)
  │            ╱
  │          ╱   × 底部: 纯小模型+无缓存, 便宜但答非所问
  └───────────────────────────▶ 成本
  降本的本质: 从 ★ 沿曲线左移到拐点上方停下, 而不是滑过拐点
  金句: "我不是在省钱, 是在把质量冗余变现"
```

### 🎤 面试这样答（进阶示范 1）——"预算砍半，你的设计怎么改？"

> "先确认一句：砍的是短期月账单还是长期总拥有成本？假设是月账单。我的架构分层一行不动，动三个参数位：**第一，生成侧级联**——日志里八成提问是单文档事实型，切到小模型 + 强约束 RAG，两成难题保留旗舰，生成成本降 60%；**第二，缓存分层**——制度类高频问题用精确 + 语义缓存吃掉两三成流量，命中成本趋零；**第三，索引精简**——90 天零命中的块降冷归档 + 向量 int8 量化，存储和检索成本再砍三成。质量红线用金标集回归门禁守住，掉点超 1 个点先回滚索引精简。**整体月账单预计降 55-65%，准确率目标不动**——如果还不够，我会回来跟您砍需求：哪些场景可以接受模板化应答，那是第四个参数位。"
>
> （收尾那句"回来砍需求"是点睛：**资深工程师知道预算问题的最后一招是管理需求，不是压榨系统**。）

#### A.2 变体二（客服 Agent）："流量涨 10 倍"

**先定性**：流量冲击，主打第④步容量评估，顺带动第②步（状态要不要外置）。10 倍不是买 10 倍机器那么简单——先问清**涨在哪**：大促脉冲还是持续爬坡？两者解法完全不同（脉冲靠弹性+降级，爬坡靠扩容+架构）。

**重新推演的关键步骤**：

1. **容量重算（排队论视角）**：日均 50 万会话 → 500 万。单会话平均 6 轮、每轮输出 800 token、峰值系数 3：峰值生成吞吐 ≈ 500万 × 6 × 800 ÷ 86400 × 3 ≈ **8.3 万 token/s**。关键结论：**单 API 供应商的 TPM 配额大概率不够**——这就是多供应商分流的硬技术理由，不只是容灾理由。
2. **无状态化改造**：客服 Agent 最容易踩的坑是会话状态藏在进程内存。改造：上下文全量外置（Redis 存近 N 轮 + 历史摘要落库），Agent 服务变纯无状态函数，扩容才线性；同时补齐工具调用幂等（重试不重复建工单）——这是 10 倍流量下不炸的前提。
3. **多供应商分流**：网关按 TPM 配额 + 质量水位加权分流（如 60/25/15），上下文格式做统一抽象层。平时是成本与容灾工具，大促时是容量工具。
4. **降级预案按水位分级**（注意：按流量水位触发，不是按故障触发）：
   - 水位 70%：关非必要功能（多步诊断、花式澄清），单轮直答，token 消耗降 40%
   - 水位 85%：高频问题切 FAQ 精确匹配 + 语义缓存，Agent 只接长尾
   - 水位 95%：排队 + 等待预估 + 自助指引，保"不静默失败"
5. **收尾**："10 倍流量的设计核心不是买 10 倍资源，是把'哪些流量不配用满血 Agent'设计清楚——水位驱动的降级预案就是自动答案。"

**容量重算速查（口算过程）**：

```text
 日会话 50万 → 500万
 峰值生成吞吐 = 500万 × 6轮 × 800 token ÷ 86400 × 峰值系数3 ≈ 8.3万 token/s
 单供应商 TPM 配额通常按"万 token/分钟"级给 → 峰值分钟级需求 500万 token
 结论: 必须多供应商分摊 + 网关层配额调度, 单点必挂
```

> **追问：** "为什么不直接买 10 倍的卡、10 倍的 API 配额？"
>
> **答：** 三个理由：① **脉冲形态**——如果是大促型脉冲，10 倍资源 95% 时间在吃灰，成本模型不成立；② **供应商配额是谈判问题不是技术问题**——TPM 上调要商务流程，周期以周计，架构不能押在别人周末加班上；③ **质量分层本该做**——日志里四成流量是 FAQ 级问题，用满血 Agent 本来就是浪费。容量扩容是线性思维，分流 + 降级才是系统思维。

**和基础篇的关系**：Agent 循环、工具体系、评测闭环全部不变；变的是状态外置、供应商拓扑、容量数字三处。

#### A.3 变体三（代码助手）："要求 99% 建议可用率"

**先定性**：质量冲击，且是极端目标（多数 LLM 应用 95% 已是优秀线）。99% 靠生成端单点不可能达到——**必须把质量从"生成后统计"改为"交付前过滤"**，主打第⑥步：Evaluator 从监控位挪到门禁位。

**重新推演的关键步骤**：

1. **先拆指标定义**（高级动作）："99% 是谁判的？用户采纳率还是自动验证通过率？"——用户采纳到 99% 是产品问题，编译/测试通过到 99% 是工程问题。钉死定义再设计。
2. **评测门槛前置**：建议生成后、交付前过一道轻量验证闸——语法解析、静态检查、受影响测试集编译运行；模型自评低置信 + 校验失败的建议**宁可不出，不可出错**。此闸预计过滤 5-8% 的建议，直接抬高"错的下限"。
3. **双模型交叉验证**：高危操作（跨文件重构、删代码、依赖变更）用第二个模型独立复审，结论不一致就降级为"仅提示不自动改"。单模型 95% 正确、错误不相关的假设下，交叉通过率量级 ~99.7%——**这个"错误不相关"的假设要主动讲出来**，它是最脆的一环。
4. **人工审核位设计**：99% 的最后一公里注定有人。审核界面三要素：diff 视图 + 置信度 + 验证结果；高危建议默认进队列；审核结论回流成标注集反哺门槛校准——**人工不是成本，是数据飞轮**。
5. **口径诚实**："99% 我拆成'自动交付 92% + 人工审核 7% + 明确拒给 1%'——把不可达的目标翻译成可达的三段式，这是我对质量目标的工程化处理。"

> **追问：** "前置过滤掉 5-8% 的建议，用户会不会觉得'这助手动不动就说不知道'，体验反而变差？"
>
> **答：** 会，所以拒给体验要专门设计，三条：① **拒给要有信息量**——不是"我做不到"，而是"这个改动涉及跨文件依赖，我只有 80% 把握，建议重点看这两处"，把拒绝变成风险提示；② **拒给率本身设预算**——超 10% 说明门槛过紧，回头调置信度阈值，它和准确率是同一根滑杆的两端；③ **拒给的流量单独埋点**——每周复盘这 1% 里有多少事后证明"拒对了"，这是验证闸门价值的最直接证据。质量目标和体验目标不是二选一，是**两个都要显式管理**。

**和基础篇的关系**：五模块能力拆解不变，Evaluator 模块的位置从"上线后"升格为"交付链路上的强制节点"——模块没变，位置变了。

#### A.4 变体四（AI 搜索）："要多语言支持"

**先定性**：范围冲击，主打第①②步——新维度进来先问"支持到什么程度"：中英混合检索准确，还是小语种生成都地道？范围不同，方案差一个量级。

**重新推演的关键步骤**：

1. **语言检测路由**（入口分流）：轻量检测器（fastText 级，<1ms）打语言标签，进对应检索管线和生成模板。别指望"一个大模型包打一切"——prompt 模板、拒答话术、安全词表全部要分语言维护，**这是范围冲击的真实成本，主动摆出来**。
2. **多语言 embedding 选型**：检索质量的地基，选型三看——多语言榜单（MIRACL/C-MTEB 类）分数、覆盖语种与业务流量匹配度、推理成本。经验锚点：多语言通用模型单语性能比单语专属模型低 1-2 个点，换语种覆盖——典型的"用单语质量换覆盖面"trade-off。
3. **跨语言召回二选一**：**原生多语言模型**（共享语义空间，跨语言直接召回，延迟低）vs **翻译归一**（全部译成英语再检索，多一跳延迟但复用英文索引与配套）。文档侧稳定、查询侧多语言 → 翻译归一省；多轮对话混合语种 → 原生多语言顺。**给结论必须给条件**。
4. **跨语言评估集先行**：每语种至少 500 条"本地语料 + 本地问题 + 标准答案"金标集——**不能拿"英语测好的系统"直接宣布支持多语言**，语种间检索质量衰减必须实测。生成侧加语言一致性检查（用户问日语、回答蹦英语 = 质量事故）。
5. **收尾**："多语言不是加个参数，是检索、生成、评测三条链路都乘以语种数。我的优先级：流量 top3 语种实测做到达标，长尾语种翻译归一兜底——范围冲击同样分层解。"

> **追问：** "翻译归一这条路，翻译错了会不会污染检索？"
>
> **答：** 会，这是它最大的软肋，两道防线：① **翻译置信度进检索管线**——低置信翻译的 query 降级走"多语言向量直接召回 + 标注不可信"，宁可召回糙一点，不把错误放大；② **双语回译抽检**——评估集里专门放"翻译敏感型"问题（谚语、品牌名、领域黑话），上线前量化翻译引入的召回衰减。所以我的选型倾向其实是**能原生多语言就原生**，翻译归一是长尾语种的兜底手段而非主路径——这个优先级本身就是 trade-off。

**和基础篇的关系**：六步法骨架与检索管线不变，新增的是"语言维度"这个正交参数位——入口路由、embedding 选型、评估集三处跟着乘语种数。

**变体题总纲（背这句）**：面试官改需求时，先说"**框架不变**"，再说"**重算的是 X/Y/Z 三个参数位**"——这句话本身就是高级岗信号。四个变体的共同套路收进一张表：

| 变体 | 冲击类型 | 动的第几步 | 三个参数位 | 一句话内核 |
|---|---|---|---|---|
| 预算砍半 | 成本 | ⑤ | 级联分流比 / 缓存命中率 / 索引规模 | 把质量冗余变现，不滑过拐点 |
| 流量涨 10 倍 | 容量 | ④ | 状态外置 / 供应商拓扑 / 水位阈值 | 分流 + 降级，不是线性买资源 |
| 99% 可用率 | 质量 | ⑥ | 验证闸阈值 / 交叉验证范围 / 人工队列 | 评测从监控位挪到门禁位 |
| 多语言 | 范围 | ①② | 检测路由 / embedding 选型 / 评估集语种 | 新维度正交进来，三条链路同乘 |

### B. 二层追问链（对话体演练：追问→答→再追问→再答）

基础篇练"答得全"，进阶篇练"扛得住"。二层追问的规律：**第一问考做法，第二问考参数与 trade-off，第三问考边界与诚实**。以下四条链全部对话体，建议出声演练。

#### B.1 追问链：容量估算深挖——"你这个设计要几张卡？"

### 🎤 面试这样答（进阶示范 2）——"你这个设计要几张卡，怎么算的？"

> "现场口算，四步链：QPS → token 吞吐 → 单卡吞吐 → 卡数。
> ① 假设峰值 200 QPS，平均每请求输入 1500 + 输出 500 = 2000 token；
> ② 吞吐 = 200 × 2000 = **40 万 token/s**；
> ③ 单卡有效吞吐取保守锚点：80G 级单卡跑 70B 量化模型，大 batch 摊薄后约 2500 token/s；
> ④ 卡数 = 40万 ÷ 2500 ≈ **160 张**，再加 30% 冗余（故障转移、滚动发布、峰值毛刺）→ **约 200 张采购**。
> 如果走 API 就没卡的事了——所以我反问您一句：数据能不能出域？这决定自建还是 API。"

**容量口算链路图（白板 30 秒画完）**：

```text
 峰值QPS ──×── 每请求token(输入+输出) ──=── token吞吐(T/s)
    200              2000                      40万
                                               │
 单卡有效吞吐 ──÷──────────────────────────────┤
 (锚点: 7B≈8000 / 70B量化≈2500 /               ▼
  旗舰MoE≈5000+ T/s)                        裸卡数 ≈160
                                               │
                                    ×1.3 冗余(故障/发布/毛刺)
                                               ▼
                                          采购卡数 ≈200
 纪律: 只背"2500 T/s"一个主锚点, 其余现场乘除; 全整数近似, 不按计算器
```

> **追问：** "自建 vs API，成本平衡点在哪？"
>
> **答：** 按月 token 量估。自建 200 张 80G 卡：采购约 500 万、按 3 年折旧 + 电费托管运维，摊到约 **20 万/月**；同等吞吐（月 10-15 亿 token）走 API 均价也在这个量级。**经验数字：月均 5 亿 token 以下，API 几乎必胜**——零折旧、零运维团队、随用随停；5 亿到 20 亿是权衡区，看数据敏感性、峰值形态和团队运维能力；20 亿以上且流量稳定，自建 + 推理优化（量化/级联/缓存先压掉一半量）开始反超。但我会主动补一句：**纯成本很少是一票决定因素，"数据不出域"的合规要求经常直接否掉 API**——所以刚才我先反问您出域问题。

> **再追问：** "2500 T/s 这个锚点哪来的？万一不准呢？"
>
> **答：** 它是量级锚点不是精确值——模型大小、量化方案、batch 策略不同会在 1000-5000 浮动。口算的意义是**给数量级和给结构**：QPS 和输出长度是线性项（最敏感），模型规模是对数项。落地前必须真实压测校准。我背三个锚点覆盖九成场景：7B 约 8000、70B 量化约 2500、旗舰 MoE 5000+。"精确值我不装，量级和敏感度我有"——这个答法比编一个精确数可信十倍。

#### B.2 追问链：技术选型叙事——"为什么选 A 不选 B"

> **追问：** "检索为什么选混合检索（向量 + BM25），不用纯向量？"
>
> **答：** 实验数据推的：纯向量在语义题上强（"怎么退货"命中"退换货流程"），但专有名词、型号、错误码这类**字面精确匹配**题上，召回比 BM25 低 15 个点以上；混合两边都吃，代价是多一路检索 + 融合逻辑，延迟多 50-80ms。我们的问题分布里精确匹配占四成——混合是数据推出来的，不是追新追出来的。

> **再追问：** "混合检索的什么缺点你能接受？"（主动认缺口的时刻到了）
>
> **答：** 三个缺点明码接受：① 延迟多 50-80ms——两路并行检索压到 30ms 内，可接受；② 双索引双倍存储与同步复杂度——蓝绿切换要双写对齐，运维成本实打实增加；③ 融合权重（RRF 的 k 值）按业务调，没有普适值，换数据集要重调。我最警惕的是②——出现过双写不一致导致两路口径不一，靠对账任务兜住。接受的理由很朴素：**15 个点的召回差距是业务不可接受的，运维复杂度是我团队扛得住的——用可控的工程成本换不可控的质量损失**。

> **再追问：** "什么条件下你会迁回纯向量？"
>
> **答：** 给可量化的迁移扳机，三条任一成立就启动评估：① 检索日志里字面精确类 query 占比降到 15% 以下（业务形态变了）；② 向量侧模型升级后单路就能打平混合方案的召回（技术变了）；③ 双索引运维成本（对账告警频次、切换事故）连续两季度超预算（成本变了）。**选型不是终身制——留"重新选型"的量化扳机，而不是靠感觉反悔**。

（这条链的骨架背下来：**为什么选 → 缺点认哪条 → 何时迁移**。任何选型题都能套。）

#### B.3 追问链：热点深挖——MCP 往深打

> **追问：** "MCP 和我直接在代码里写函数调用，本质区别是什么？"
>
> **答：** 区别不在功能，在**标准化**。直接函数调用：工具定义、参数 schema、调用协议都是我工程里的私有约定，换模型换框架就重新粘合——N 个应用 × M 个工具的适配矩阵。MCP 把"发现-调用-返回"标准化成跨厂商协议：工具实现一次，任何 MCP 客户端即插即用。类比：**函数调用像各家私有 RPC，MCP 像把这一层变成了 HTTP**——HTTP 赢不是因为快，是因为所有人都说它。生态位标准化之后，调试、审计、权限网关这些外围设施才有处安放。

> **再追问：** "MCP 的安全模型有什么缺陷？"
>
> **答：** 核心缺陷：**对服务器的信任是全有全无的**。协议假设"客户端信任它连的服务器"，却没有服务器行为约束——恶意服务器可以在返回内容里夹带指令（间接注入的天然入口）、超范围读资源、用工具描述诱导模型误调用。相当于 HTTP 早期：有了协议，还没有 TLS 和同源策略。我的生产做法：MCP 之上加网关——服务器最小权限接入、返回内容过注入扫描、调用全量审计。**协议解决互操作，不解决可信；可信永远是工程层的责任**——和后端"别信任任何外部输入"是同一条纪律。

#### B.4 追问链：热点深挖——Reasoning 模型往深打

> **追问：** "什么任务不值得用推理模型？给判据。"
>
> **答：** 三判据，命中任一就不用：① **延迟敏感**——推理模型思考数秒到数十秒，客服首响 P95 < 3s 的场景直接出局；② **任务简单**——分类、抽取、格式转换、FAQ，链式思考零增益，小模型秒答质量持平；③ **成本约束**——推理 token 按输出计费、单价数倍于普通输出，简单任务上推理模型是"用金笔写便签"。经验比例：多数业务里值得上推理模型的流量**不足两成**——多步规划、复杂代码、数学、根因分析这类。

> **再追问：** "既然要用，怎么让推理模型省钱？"
>
> **答：** 四招组合：① **思考预算**——按任务档位限制最大推理 token（简单分析 2k、复杂规划 32k）；② **按需路由**——级联前置小模型判难度，难题才升级，80/20 分流；③ **缓存推理结论**——推理输出比普通输出贵，按问题模式缓存结论，同问不付二次思考费，缓存杠杆反而更大；④ **答案瘦身**——推理模型只在内部链路产出结构化结论，用户侧展示交给便宜模型渲染。综合压 50-70%，且第②招同时就是延迟优化。

### C. 白板表达与面试节奏（高级岗的"临场工程"）

系统设计面试是**表演型工程**——同样的设计，讲得好与讲得差，结论差一级。这一节把"怎么讲"工程化。

#### C.1 白板三图默画清单（每图 5 分钟内）

| 图 | 必含元素 | 5 分钟标准 | 常见失误 |
|---|---|---|---|
| 架构分层图 | 接入层→编排层→模型层→数据层，每层 2-3 个组件，权限/合规位置标出 | 先画四层框再填组件，边画边说每层职责一句话 | 一上来抠单个模块细节，10 分钟只画了五分之一 |
| 数据流图 | 离线管线（虚线）+ 在线链路（实线）+ 失败路径（红笔），线上标延迟预算 | 双线并行推进，每段标注预算（检索 200ms / 生成 2s / 总 P95 3s） | 只画在线不画离线——"数据从哪来"被一问就卡 |
| 降级矩阵图 | 行=故障点（模型超时/检索挂/工具失败/供应商限流），列=检测信号→降级动作→用户感知 | 三列五行表格画完，三级链路脱口而出 | 只背"熔断降级"四个字，给不出触发条件和用户感知 |

**练法**：计时默画 + 录音回放。标准不是"画得像"，是**每画一笔都有一句话跟着**——沉默画图超过一分钟，面试官就开始怀疑你是在回忆答案还是在现场思考。

#### C.2 "边画边说"话术模板

- **先框架后细节**："我先画整体分层，您看方向对不对，然后挑重点模块深入"——第一分钟交出地图，面试官从此在你的地图上提问，主动权在你手里。
- **主动抛 trade-off 的时机**：每个关键决策说完紧跟"代价是 X，我用 Y 对冲"——**别等面试官问"这方案缺点是什么"**：被动答缺点像狡辩，主动说缺点像掌控。频率约每 5 分钟一次，过密显得不自信。
- **被卡住时的自救话术**："这里我能想到两个方案，分别说说 trade-off，然后我倾向 A，理由是……"——把卡壳转成对比展示；或者"这个数我从 X 反推一下"——把沉默转成口算表演。**最差的选择是硬编**。

#### C.3 追问到知识边界时的应对

没实操过的领域被追问（多半是故意的），用公式：**诚实声明 + 原理推演 + 量级兜底**。

> "这个具体数字我没实操过，但按原理推演：它本质是 X 类问题，瓶颈应该在 Y，量级大概 Z——实际值我会用压测校准。方向上我有信心，精度上我不装。"

这个答法同时展示三样东西：诚实（高级岗最贵的品质）、推理能力（原理迁移）、工程习惯（压测校准）。反面教材是自信地报一个编造的精确值——面试官多追一层"怎么测的"就当场击穿。

#### C.4 面试官类型识别与策略

| 类型 | 识别信号 | 应对要点 | 别踩的坑 |
|---|---|---|---|
| 技术深挖型 | 每个答案都追"为什么 / 多少 / 怎么验证" | 主动给数字和 trade-off，欢迎深挖——这是你的主场 | 答得泛而全，没有一处够深 |
| 业务导向型 | 频繁问"用户价值 / ROI / 落地周期" | 设计节点绑定业务指标（"这层是为了拒答率控在 1% 以内"），成本和优先级主动提 | 纯讲技术优雅，不接业务地气 |
| 压力测试型 | 打断、质疑、连续否定（"这不行吧"） | 不慌不怼：先复述对方质疑点，再条件化回应——"在 X 条件下您说得对，我的假设是 Y" | 立刻全盘改方案，或防御性争辩 |

压力测试型特别说明：质疑的往往不是方案本身，是在测**你被挑战时的稳定度**——后端老兵开架构评审被 challenge 过无数次，把面试官当成评审会上的同事就好。

#### C.5 45 分钟白板题的节奏表（掐表练）

| 时间段 | 动作 | 产出 | 危险信号 |
|---|---|---|---|
| 0-5 min | 需求澄清（①） | 数字清单：QPS/延迟/准确率/预算/合规 | 面试官替你给出数字——说明你没问 |
| 5-10 min | 能力拆解（②）+ 框架图 | 五模块对号入座，四层分层框 | 直接开画细节，没有地图 |
| 10-20 min | 数据流 + 关键模块深入（③） | 双管线图，延迟预算标注 | 每个模块都讲，没有深浅层次 |
| 20-25 min | 容量口算（④） | 卡数/token 吞吐/存储三个数 | 跳过算账直接谈优化 |
| 25-35 min | 成本与 trade-off（⑤） | 级联/缓存/降级链 + 主动抛代价 | 只讲优点不讲代价 |
| 35-42 min | 评测闭环（⑥）+ 变体预演 | 金标集→门禁；"预算砍半我会…" | 评测一句话带过 |
| 42-45 min | 总结收口 | "以上是整体设计，您想深入哪块？" | 被问到哪算哪，没有收口 |

这张表的价值在"危险信号"列——**每一格失分动作，都是面试官在心里默默扣级的时刻**。

### D. 高级视野：定级之后的表达层次

#### D.1 "背过设计的人" vs "设计过系统的人"：同一问的两种答法

| 追问 | 背过的人答 | 设计过的人答 |
|---|---|---|
| "为什么用 Rerank？" | "Rerank 提升相关性，业界都在用" | "召回 hit@50 实测 78%，瓶颈在排序不在召回，所以加 cross-encoder 重排；代价 300ms，设了超时跳过——命中率和延迟按 P95 预算倒推的" |
| "为什么拒答机制重要？" | "防幻觉，提升可信度" | "我们场景是宁拒答不答错：拒答率从 2% 调到 5%，换引用错误率 3%→0.5%——滑杆位置是和业务方一起定的，不是技术拍的" |
| "多租户怎么隔离？" | "查询里加租户 ID 过滤" | "过滤下沉到检索层做预过滤——后过滤在高密租户下会把 top_k 全滤光、召回为空；这个坑是 500 并发压测时发现的" |
| "这个设计的风险？" | "可能会慢、会贵" | "最大单点是向量库主从切换的秒级抖动；预案降级 BM25 单路，质量掉 2 个点保可用——上季度演练过，RTO 40 秒" |

规律：设计过的人每个答案里都有**数字、代价、出处**——数字来自度量，代价来自权衡，出处来自踩坑。这三样背答案背不出来，这也是为什么进阶篇反复要求"报数字收尾"。

#### D.2 2025→2026：系统设计考察趋势

- **从"能不能搭"到"能不能省"**：成本约束直接进题面（"预算砍半""月成本控在 X 以内"），不再是加分项而是必答项。每 token 成本、级联分流比例、缓存命中率——这些数进不了嘴，就还是"搭 demo"水平。
- **Agentic 系统设计题兴起**：题面从"设计一个 RAG"变成"设计一个能自主完成 X 的 Agent"——新考点是**状态管理**（长任务断点续跑、检查点与恢复）和**失败恢复**（工具失败重规划、部分完成对账、幂等）。这恰是后端分布式内功的直译区：消息队列、事务、重试幂等那套平移过来就是最优解。
- **评估体系成为必答环节**：没有评测方案的设计题答案，2025 年起直接判"不完整"。金标集规模、离线指标、线上反馈闭环、发布门禁——六步法第⑥步的权重在涨。

#### D.3 反问环节：3 个高质量反问

1. **"团队的 AI 功能效果怎么评？有金标集和回归门禁吗？"**——探工程成熟度：有门禁说明团队较真；没有说明你去了就是建体系的人（机会与坑并存，问清再选）。
2. **"现在最大的技术债是什么？在模型层还是数据层？"**——探真实状态，同时展示你懂"AI 系统的债不只躺在代码里，还在数据管线和 prompt 资产里"。
3. **"AI 功能上线后的运维归属？平台组统一 oncall 还是业务团队自理？"**——探组织形态，直接影响入职后的生活质量；也展示你从交付思维到运维思维的完整视角。

（反问的隐藏功能：这是你**唯一主动定义对话层次的环节**——问执行细节显得像执行者，问体系与债显得像 owner。）

#### D.4 一段"面试官心理"：系统设计题到底在筛什么

45 分钟里，面试官脑子里只有三把尺子：

**结构化思维**——面对模糊需求，你是先澄清再动手，还是抓住第一个念头就冲？量的是组织复杂度的能力，决定你能不能带一块业务。**Trade-off 诚实度**——每个方案说得出代价吗？被质疑时是条件化回应还是全盘动摇？量的是判断可信不可信——高级岗最贵的不是聪明，是可信。**数字感**——设计里有没有量级正确的数字（QPS、token 吞吐、成本占比、错误率）？量的是你跟真实系统打过交道没有——数字感无法速成，它是运营过系统的年轮。

三把尺子都过，题答得糙也能给高级——因为尺子量的从来不是这道题，是**你处理复杂问题的默认方式**。
