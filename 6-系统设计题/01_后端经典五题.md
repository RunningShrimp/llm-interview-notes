# 01 | 后端经典设计五题（高并发 · 存储 · 一致性 · 流量治理 · 异步）

> **定位**：后端系统设计的主战场。2026 的考察方式已「穿插化 + 深度化」——面试官通常在一面、二面穿插一到两道设计题，答法从「堆方案名」转向「瓶颈定位 → 取舍分析」。
> 本章五题覆盖高并发、海量存储、分布式一致性、流量治理、异步任务五大母题，全部按六步法骨架展开（需求澄清 → 架构 → 决策 → 容量 → 追问 → 口述），但追问链比入门题更深，目标是把每题练成可迁移的母题模板。

## 本章导读

**考察定位**：秒杀与短链仍是中文后端面试两大代表场景题；分布式锁、分布式 ID、分布式事务作为衍生追问高频出现；限流、MQ、分库分表以链路分析形式考。另外，多维度限流（RPM/TPM/并发/租户预算）、语义缓存、智能客服流量激增降级等 AI 变体已进入主流题库——后端题的追问链里要**主动埋 AI 延伸**，这是 2026 的显著增量。

**三条答题心法**：

1. **2026 答法要点是瓶颈定位与取舍，而非方案堆砌**：报方案名不得分，「瓶颈在 X → 原因 Y → 所以选 Z → 代价是 W」才得分；每个亮点必须紧跟一个代价。
2. **主动把后端题延伸到 AI 场景变体是加分项**：答完传统链路后补一句「如果换成 AI 配额 / 推理资源，差异点是……」——展示迁移能力，这是当前面试的显著增量方向。
3. **没有数字的设计是散文**（对齐六步法）：容量估算整数近似、够用就行；每个方案给出量级依据（QPS / 存储 / 延迟），取舍才有说服力。

## 题 1｜秒杀系统：10 万 QPS 抢 1000 件库存

> **一句话考察点**：怎么在 10 秒内扛住平时上千倍的流量，同时把 1000 件库存**不多不少**地卖出去——热点治理、库存一致性、削峰填谷、防刷四件事的合奏。
>
> **考频**：⭐⭐⭐⭐⭐（考频校准：高并发场景题出现率第一梯队，一面考主干架构，二面考追问链深度）

### 需求澄清

不问不画。数字不同，设计天差地别：

| 我问 | 面试官答（假设） | 对设计的影响 |
|---|---|---|
| 主推单品还是多品？各多少库存？ | 大促 100 个商品，主推 1 款 1000 件 | 单品热点极端集中 → 热点 key 治理是主战场 |
| 10 万 QPS 峰值持续多久？ | 开抢后约 10 秒退潮 | 短时洪水 → 削峰（排队）比扩容便宜百倍 |
| 一致性要求？ | 绝不超卖；少卖万分之五内可回补 | 「Redis 强校验 + DB 最终一致 + 对账兜底」够用，不必上强一致 |
| 黄牛占比与拦截要求？ | 机刷约 30%，要网关层实时拦 | 风控前置：答题 + 账号/设备画像双层 |
| 未支付多久释放库存？ | 15 分钟 | 需要延迟任务回补库存（联动题 5） |

澄清话术示范（开场 30 秒定调）：

```text
"我先确认三个数字：峰值 QPS 与持续时长、库存量级、超卖少卖容忍度。
整体思路八个字：分层拦截、异步落库——在离数据库越远的地方拦掉越多流量，
DB 最终只看到几百 TPS 的平稳写入；库存一致性由 Redis Lua 原子扣减保证，
DB 只做异步记账和兜底对账。"
```

三个数字对设计的推演：

- **峰值÷库存 = 放大倍数**：10 万 QPS ÷ 1000 件 = 100 倍流量集中在 10 秒，决定了「拦」优先于「扛」
- **持续时间 10 秒**：决定了不需要为常态扩容，临时资源（弹性扩容 + 排队）即可
- **少卖容忍度**：决定了敢不敢用「库存分 key + 本地标记」这类牺牲少量精确度换吞吐的手段

### 架构图

```text
                    【秒杀链路：分层拦截 + 异步落库】
 100万用户点击
    │
    ▼
 CDN（商品页静态化/售罄图，扛掉 90% 读流量）
    ▼
 网关层：令牌桶限流 + 答题验证码 + 风控画像     ←─ 拦掉约 95%
    ▼
 秒杀服务（无状态集群，独立部署，故障隔离）
    │  ① 查本地售罄标记 ──已售罄──→ 直接返回，不再下沉
    ▼
 Redis 集群：Lua 原子「查库存-扣减-一人一单去重」←─ 只剩有效请求
    │ 扣减成功 = 获得抢购资格（非下单成功）
    ▼
 MQ（削峰，消费端按 DB 水位限速）
    ▼
 订单服务：落库（订单号唯一索引幂等）+ DB 库存扣减（最终一致）
    ▼
 支付 ──15分钟未支付──→ 延迟任务关单 + Redis/DB 库存回补
    │
    └→ 对账服务（小时级）：Redis剩余 vs 已购SET vs DB订单 三方核对
```

链路走读（面试时边画边讲，每层一句「为什么放这里」）：

1. **读请求全走 CDN**：商品详情静态化，库存数字前端定时拉，读流量不进服务
2. **网关是第一道闸**：限流保证进入系统的量在服务水位内；答题既拦机器人又把瞬时 QPS 摊到 2~3 秒
3. **秒杀服务独立部署**：即使全挂，主站交易不受影响——故障隔离是隐形考点
4. **本地售罄标记是性价比之王**：1000 件抢完后，99% 以上流量根本到不了 Redis
5. **Redis 是库存唯一裁判**：单线程串行执行 Lua，天然没有并发扣减问题
6. **MQ 把尖峰变平原**：DB 永远只看到约 500 TPS 的平稳写入，连接池无压力
7. **延迟任务闭环**：15 分钟未支付关单回补，防止库存被「占着不付款」耗尽
8. **对账兜底一切异常**：消息丢、回补漏、Redis 主从切换丢数据，最终都能被对账修正

### 关键设计决策表

| 决策点 | 方案 A | 方案 B | 方案 C | 选择与理由 |
|---|---|---|---|---|
| 库存扣在哪 | DB 行锁 `stock=stock-1` | Redis Lua 预扣，异步落库 | 前端随机放行+Redis 兜底 | 选 B：A 在 10 万 QPS 下连接池先爆；C 超卖风险不可控。B 把「裁判权」收归 Redis，DB 只管记账 |
| 售罄怎么感知 | 每次请求实时查 Redis | 本地售罄标记（version 控制） | 配置中心全量推送 | 选 B：售罄后 99% 流量在应用本地就被拒绝；几秒的不一致无业务影响，换来 Redis 压力数量级下降 |
| 下单链路形态 | 同步落库后返回结果 | 异步：资格→MQ→落库→通知 | 纯前端摇号事后通知 | 选 B：DB 削峰 + 用户可接受「排队确认中」；A 有毛刺传导风险；C 无法保证真实发货顺序公平 |

补充「为什么不选」（主动交代代价，面试官最爱问）：

- 不选 A（同步扣 DB）：正确性没问题，**性能上必死**——这正是本题的起点认知
- 不选 C（前端摇号）：省了后端但公平性缺失、库存与资格对不齐，客诉风险高
- 选 B 的代价：**用户体验从同步变异步**，需要轮询/推送机制 + 明确的「排队中」状态文案

### 容量估算

整数近似，够用就行：

```text
流量账：
  峰值 10 万 QPS × 10 秒 ≈ 100 万请求，抢 1000 件
  有效请求比例 = 1000 / 100万 = 0.1% → 99.9% 是要被拦掉的无效流量
  → 核心结论：重点不是"扛住 10 万 QPS"，是"尽早拦掉 99.9%"

分层拦截账（每层幸存量）：
  CDN/静态化      读流量全拦（读:写 ≈ 10:1）
  网关限流+答题    10万 → 约 1万 QPS 进应用（答题摊 3 秒 + 令牌桶）
  本地售罄标记     开抢约 3 秒后库存清零 → 1万 → 数百 QPS 到 Redis
  Redis           单分片上限约 10 万 QPS，实际承压 < 1 万，安全
  MQ              资格消息峰值千级，消费限速 500 TPS，堆积无压力
  DB              平稳 500 TPS 落库，单实例绰绰有余

存储账：
  订单 1000 行 × 1KB ≈ 1MB，可忽略
  Redis：库存 key 100 个 + 去重 SET（100 万成员 × 8B ≈ 8MB）→ 数十 MB 级

延迟账：
  CDN+网关 10ms → Redis Lua 1ms → MQ 异步 ≈ 同步链路 P99 < 50ms
  异步落库完成：P99 < 3 秒（对用户呈现为"排队确认"）
```

**瓶颈结论**：瓶颈不在计算在**热点**——单 key 有把 Redis 单分片打满的风险，靠「本地售罄标记 + 库存分 key」化解；DB 是假想敌，实际只剩对账和回补的量级。

**降级链**：Redis 主从切换中 → 网关限流压到 DB 水位（500 QPS）→ 仍扛不住 → CDN 静态售罄页全量拒绝。原则一句话：**秒杀可以失败，主站不能陪葬**。

### 追问链

**追问1**：为什么不能直接扣数据库？——分层拦截思想

- DB 行锁串行：上千并发更新同一行，InnoDB 行锁排队，TPS 上限几千
- 更早死的是连接池：10 万 QPS × 平均 5ms = 500 并发连接，池子瞬间打满 → **秒杀拖垮主站**才是最大事故
- 正确姿势是分层拦截，每层都有明确的「拦掉什么」：

```text
CDN（拦读） → 网关（拦 95%） → 本地售罄标记（拦 99%）
→ Redis（拦到只剩有效请求） → MQ（削到 500 TPS） → DB
```

- 判断标准：流量每下一层，数量级掉一个，DB 看到的应该是「平稳的常态流量」
- ❌踩坑：只答「加 Redis 缓存」——缓存解决的是**读**，库存扣减是**写热点**，这才是本题核心

**追问2**：热点 key——10 万 QPS 全打到 Redis 一个分片怎么办？

- 集群水平扩展对单 key 无效：key 按 hash slot 落在固定分片，加机器不分流
- 三层解法，按性价比排序：
  1. **本地售罄标记**：库存清零后各节点本地置 flag，后续请求本地拒绝（拦大头，几行代码）
  2. **库存分 key**：`stock:{sku}` 拆成 `stock:{sku}:0..9` 十个子库存，请求取模路由，单 key QPS ÷10
  3. **读写分离**：库存余量这类展示型读请求走从库或客户端缓存
- 分 key 的副作用：各子 key 扣减不均 → 部分已空、部分有剩 → **少卖**
- 处理：子 key 全空触发「跨片借用」逻辑；实在借不到就等对账回补二次放卖，把少卖压进容忍度
- ❌踩坑：只说「分 key」不讲少卖副作用——面试官等的就是这句，**主动讲清代价反而是加分项**

**追问3**：Redis 预扣怎么做才不超卖？

- `GET` 判断再 `DECR` 是两步操作，并发下必然超卖；`DECR` 后判负回滚则可能多扣（中间态已被别人读到）
- **Lua 脚本原子执行**——Redis 单线程，脚本内多命令天然串行：

```lua
-- KEYS[1]=库存key  KEYS[2]=已购用户SET   ARGV[1]=用户ID
local stock = tonumber(redis.call('GET', KEYS[1]) or '-1')
if stock <= 0 then return -1 end                     -- 售罄
if redis.call('SISMEMBER', KEYS[2], ARGV[1]) == 1 then
  return -2                                          -- 一人一单，重复抢
end
redis.call('DECR', KEYS[1])
redis.call('SADD', KEYS[2], ARGV[1])
return stock - 1                                     -- 返回剩余库存
```

- 关键点：**扣减与去重必须在同一个 Lua 里**，拆成两条命令就有并发窗口
- Redis 主从是异步复制：主宕机切换瞬间可能丢最后一次扣减 → 不追求绝对，靠对账兜底（见追问5）
- ❌踩坑：用 `WATCH/MULTI/EXEC` 乐观锁——高并发下冲突重试风暴，吞吐远低于 Lua；另一个坑是脚本里写业务逻辑太长，会阻塞 Redis（脚本要短小）

**追问4**：为什么还要 MQ？Redis 扣完同步写 DB 不行吗？

- 有效请求虽只剩千级，但同步落库 = 多表事务 + 扣减 + 联动，DB 毛刺会沿调用链传导成用户超时
- **削峰本质：把「抢购成功」拆成两段**——Redis 扣减成功即返回「排队确认中」，落库异步完成
- 消费端按 DB 水位限速（500 TPS），用户侧轮询或长连接拿最终结果，P99 控制在 3 秒内
- 附加收益：秒杀服务短暂不可用时**消息堆积不丢**，恢复后继续消费，天然具备「暂停-恢复」能力
- ❌踩坑：不做结果通知机制，用户一直转圈 → 大量重复点击 → 流量二次放大——异步化必须配套「状态可见」

**追问5**：消息丢了、消费失败了怎么办？——最终裁判是对账

- 生产端可靠化：**本地消息表**（预扣成功先落「待发送」流水，发送后更新状态，定时任务补偿扫描重发）
- 消费端三件套：订单号唯一索引幂等 + 指数退避重试 + 超 N 次进**死信队列**
- 死信三步走：实时告警 → 人工或自动补偿（补单 / 回补库存）→ 复盘归因
- **对账兜底**（小时级或 T+1）：`Redis 剩余 + 已购 SET 数 + DB 订单数 + DB 库存` 四方核对：
  - Redis 少、DB 多 → 消息重复消费，查幂等是否失效
  - Redis 多、DB 少 → 消息丢失，补单或回补库存
- 少卖处理：对账发现差异后二次放卖，业务上万分之几完全可接受
- ❌踩坑：宣称「MQ 配置成持久化就万无一失」——所有可靠性最终都要落到**自己的消息表 + 对账**，中间件只保证尽力而为

**追问6**：怎么防黄牛？

- **网关层——答题/滑块验证码**，两个作用：抬高脚本成本；更关键的是把开抢瞬间的尖峰摊到 2~3 秒（流量治理视角）
- **风控层——实时画像打分**：账号维度（注册时长、历史行为）、设备指纹、IP 聚集度、黑名单，低分直接拒
- **业务层**：一人一单（Redis SADD 去重，见追问3）、限购数、同收货地址/同支付账号聚合检测
- **事后层**：异常订单聚类冻结、人工复核、黑名单回流
- ❌踩坑：以为验证码的答案是「安全」——面试官想听的是「**摊薄流量 + 抬高成本**」双重作用，这是把安全手段讲成流量治理的视角切换

**追问7**：Redis 挂了怎么办？

- 先表态：**秒杀可以失败，主站不能陪葬**——独立部署、独立 Redis 集群是前提
- 常规：主从 + 哨兵/集群秒级切换；切换窗口内网关把限流阈值压到 DB 水位（约 500 QPS），超出直接拒绝
- 切换丢数据：异步复制可能丢最后若干次扣减 → 业务上接受（最多少卖几件）+ 对账修正
- 极端兜底：CDN 静态「已售罄/活动太火爆」页全量拦截，活动顺延
- ❌踩坑：答「Redis 天然高可用所以没事」——没讲切换瞬间的一致性损失，会被顺势追问到分布式锁正确性（自然桥接题 3）

**追问8**（AI 延伸）：把「抢库存」换成「抢大模型推理配额」，设计变吗？

- 同构本质：GPU 推理并发槽位 = 库存；用户请求 = 抢购；「超卖」= 过量请求打爆推理集群
- 三个差异点，答出來就是迁移能力：
  1. **库存会「还」**：推理完成要释放槽位 → 从一次性计数器变成**信号量**（INCR/DECR 动态 + 任务结束释放；泄漏用定时对账清理僵死占用）
  2. **抢不到不是售罄而是排队**：优先级队列（付费租户、核心场景高优先），返回预计等待时间而非直接失败
  3. **降级链更长**：满载 → 排队 → 切小模型 → 返回语义缓存的历史答案 → 明确提示稍后再试（对齐题 4 的 AI 限流）
- 收尾话术：「本质都是**资源远小于需求**的分配问题——秒杀求快（先到先得），推理求稳（分级服务）」
- ❌踩坑：直接平移秒杀方案不讲差异——这个追问考的就是迁移与变通，而不是背诵

### 🎤 口述模板

> 这道题我先澄清三个数字：峰值 QPS 与持续时长、库存量级、超卖少卖容忍度。核心判断是——100 万请求抢 1000 件，99.9% 是无效流量，所以设计重点不是「扛」而是「拦」，做分层拦截。
>
> 读流量全走 CDN 静态化；网关层用令牌桶限流加答题验证码，把 10 万 QPS 摊薄到万级，同时风控画像拦机刷；库存清零后各节点打本地售罄标记，拦掉 99% 残余流量；最后由 Redis 用 Lua 原子完成「查库存、扣减、一人一单去重」，它是库存的唯一裁判，不超卖靠这一层。热点单品再做库存分 key，接受可控少卖，靠对账回补。
>
> 扣减成功只代表资格，我马上发 MQ 削峰，订单服务按 500 TPS 限速落库，订单号唯一索引保证幂等；15 分钟未支付走延迟任务关单回补。所有异常最终由对账兜底：Redis 剩余、已购集合、DB 订单三方核对，差异回补或二次放卖。整体上 DB 只看到平稳流量，秒杀集群即使全挂也不影响主站。如果换成抢 AI 推理配额，我会把计数器改成信号量，加优先级排队与模型降级，骨架完全复用。

### 一句话总结

秒杀的魂不是「快」而是「拦」：分层把 99.9% 的无效流量拦在离数据库越来越远的地方，Redis Lua 当裁判，MQ 当缓冲池，对账当最终兜底——超卖零容忍，少卖用对账换吞吐。

## 题 2｜短链服务：10 亿条短码，读多写少

> **一句话考察点**：海量数据下的「读路径设计」——发号、编码、多级缓存、防穿透四件事串成一条读多写少的极致链路，考的是存储选型与缓存体系的功底。
>
> **考频**：⭐⭐⭐⭐⭐（考频校准：与秒杀并列的场景题双雄，读路径设计类题目的标准载体）

### 需求澄清

| 我问 | 面试官答（假设） | 对设计的影响 |
|---|---|---|
| 读写比和数据总量？ | 10 亿条存量，读写比约 100:1 | 读路径是主战场，写路径保正确即可 |
| 短码长度有约束吗？ | 越短越好，7 字符内 | 62^7 ≈ 35 亿，7 位 Base62 刚好覆盖 10 亿量级 |
| 跳转延迟目标？ | P99 < 50ms | 必须缓存扛住 95% 以上读，DB 只接长尾 |
| 短码能被预测吗？ | 不能被遍历爬取 | 自增 ID 直接暴露不行，要加混淆或随机因子 |
| 支持自定义后缀/过期吗？ | 支持自定义，默认永久有效 | 需要冲突检测与软删除机制 |

澄清后的核心判断：**这是一道读路径题**。写一天百万级没有技术难度，难度全在「10 亿条数据怎么存、6 万 QPS 怎么读、不存在的短码怎么防打穿」。

### 架构图

```text
                【短链服务：写路径发号，读路径多级缓存】
 ── 写路径（日增百万，低频）──
 长链入库请求 → 去重(MD5查长链索引) → 发号器(号段模式)
    → Base62 编码 → MySQL(分库分表) → 返回 t.cn/xAb3fK9
    └→ 异步：布隆过滤器登记 + 热点预热(可选)

 ── 读路径（约 6 万峰值 QPS，高频）──
 用户点击 t.cn/xAb3fK9
    ▼
 本地缓存 LRU（Top 10 万热点，命中率约 60%）
    ▼ 未命中
 Redis 集群（Top 千万热点，命中率约 35%）
    ▼ 未命中
 布隆过滤器 ──判定不存在──→ 直接 404（不进 DB，防穿透）
    ▼ 判定存在（含极小误判率）
 MySQL 16 库 × 64 表（短码 hash 分片）→ 回填缓存 → 302 跳转
    └→ 异步埋点：点击统计（UV/PV/来源）
```

读路径设计原则一句话：**每一层只承接上一层的未命中，DB 是最后一道而不是第一道**。

### 关键设计决策表

| 决策点 | 方案 A | 方案 B | 方案 C | 选择与理由 |
|---|---|---|---|---|
| 短码怎么生成 | 长链哈希后截断 | 发号器取号 + Base62 | 随机生成+查重 | 选 B：A 截断必然碰撞且可被彩虹表逆推；C 要多次查库。B 单调有序、无碰撞，配合号段模式 DB 压力极小 |
| 主存储选型 | MySQL 分库分表 | 全量 Redis | SSD KV（RocksDB 系） | 选 A（+缓存）：B 内存成本约 150GB 起太贵；C 运维栈冷门。MySQL 分表后单表 100 万行内，配合缓存完全够 |
| 跳转方式 | 301 永久重定向 | 302 临时重定向 | 服务端直接代理转发 | 选 B：301 被浏览器缓存后不再经过服务，**丢统计**；302 每次回源可统计可改跳。纯无统计场景才用 301 |

发号器细节补充（追问高频点，先埋在这）：

- **号段模式**：DB 表 `biz_tag, max_id, step`，应用一次取一个号段（如 1~1000）在内存分配，用到 10% 时异步双 buffer 预载下一段——DB 更新 QPS = 写 QPS ÷ step
- **雪花算法**：64 bit = 1 符号 + 41 时间戳 + 10 机器 ID + 12 序列；无 DB 依赖，但有**时钟回拨**问题（回拨小于阈值等待，超过则报错切换备用机器 ID）

### 容量估算

整数近似：

```text
存储账：
  10 亿条 × (短码 8B + 长链均值 80B + 状态/时间等 60B) ≈ 150B/条
  150B × 10 亿 ≈ 150GB 裸数据，含索引 ×2 ≈ 300GB
  → MySQL 16 库 × 64 表 = 1024 表，单表约 100 万行 / 300MB，健康水位

写账：
  日增 100 万条 ≈ 平均 12 QPS，峰值 ×20 ≈ 240 QPS
  号段 step=1000 时，发号 DB 更新仅 100 万 ÷ 1000 = 1000 次/日，可忽略

读账：
  日跳转 10 亿次 ≈ 平均 1.2 万 QPS，峰值 ×5 ≈ 6 万 QPS
  二八定律：20% 热短码扛 80% 流量
  本地缓存（10 万条）命中 60% + Redis（千万条）命中 35% ≈ 95%
  → DB 只接 6万 × 5% = 3000 QPS，摊到 16 库 = 单库 190 QPS，轻松

布隆过滤器账：
  10 亿元素 × 15 bit ≈ 1.9GB，误判率约 0.5%
  拆 8 个分片部署，单实例 240MB

内存账：
  本地缓存 10 万 × 200B = 20MB/节点
  Redis 千万 × 150B ≈ 1.5GB，单实例或一主一从
```

**瓶颈结论**：写路径完全无压力；读瓶颈被三级缓存消化后，真正的风险点是**缓存穿透**（恶意扫不存在的短码）与**缓存击穿**（顶级热 key 过期瞬间）——这就是布隆过滤器和逻辑过期存在的原因。

### 追问链

**追问1**：短码为什么用发号器 + Base62，而不是对长链做哈希？

- 哈希截断（如 MD5 前 7 位）：**必然碰撞**，冲突处理要查库重哈希，写路径复杂化；且短码与长程可被彩虹表批量逆推，安全差
- 发号器 + Base62：号是自增的，**天然无碰撞**；62 字符（0-9a-zA-Z）都是 URL 安全字符
- 为什么不是 Base64：`+` 和 `/` 在 URL 里有特殊含义，还要转义，得不偿失
- 防遍历：自增号可被猜测 → 发号后加**可逆混淆**（如乘大质数取模映射）或直接从大随机数起步
- ❌踩坑：说「Base62 编码能压缩长度」——它不是压缩，是**进位制表示**，7 位只是把号空间编码得更短

**追问2**：号段模式和雪花算法怎么选？

- 号段模式优点：号码趋势有序（对 B+ 树索引友好）、无时钟依赖；缺点：**依赖 DB**、宕机时未用完号段作废（浪费但不重复）
- 双 buffer 是号段模式的灵魂：当前号段用到 10% 就异步加载下一段，消除取号段的同步等待毛刺
- 雪花优点：本地生成零网络依赖、吞吐百万级；缺点：**时钟回拨**会产生重复 ID，机器 ID 分配要额外协调（ZK/DB）
- 选型口径：短链有 DB 落库，号段模式够用且简单；无 DB 依赖、超高并发的场景（如日志追踪 ID）用雪花
- ❌踩坑：被追问「号段模式的号段用完了但 DB 挂了取不到下一段怎么办」答不上——答案是本地双 buffer 就是干这个的，能顶住取号段窗口期的故障

**追问3**：为什么不全放 Redis？10 亿条怎么存？

- 算账拒绝：10 亿 × 150B ≈ 150GB 全内存，成本是 SSD 的十倍以上，而读热点极度集中（二八甚至一九定律）
- 正确姿势：**MySQL 分库分表做主存储（真相源），Redis 只放头部千万级热点**
- 分片键：短码本身做 hash 分 16 库——跳转查询天然带短码，无需二次路由
- 单表控制在 100 万行内：`t_code` 短码唯一索引 + `t_long_hash` 长链哈希索引（用于「同一长链返回同一短码」去重）
- 数据增长到百亿：分片数不够就**翻倍扩容 + 一致性 hash 迁移**，短链场景读有缓存挡着，迁移窗口影响可控
- ❌踩坑：分片键选了自增 ID——查询不带 ID，还得先查映射层，等于白分

**追问4**：多级缓存的一致性和击穿怎么处理？

- 更新策略：**旁路缓存 + 先更新 DB 再删缓存**（短链几乎不可变，实际冲突极少）
- 击穿（单点热 key 过期瞬间大量请求直奔 DB）：
  1. **互斥重建**：只有一个请求拿锁查库回填，其余等待或返回旧值
  2. **逻辑过期**：value 里存过期时间，过期后返回旧值 + 异步异步刷新——热点永不穿透
- 雪崩（大批 key 同时到期）：TTL 加随机抖动（基准 ±20%），错峰过期
- 一致性容忍度：短链跳转场景读旧一秒无业务损失，逻辑过期这种「最终一致换永不穿透」完全划算
- ❌踩坑：给所有 key 都上互斥重建——普通冷 key 没必要，锁竞争反而拖高延迟；**分层处理**才是考点

**追问5**：布隆过滤器怎么防穿透？误判怎么办？

- 原理：k 个独立哈希函数把元素映射到 m 位数组的 k 个位，全 1 才「可能存在」，有 0 则「必然不存在」
- 防穿透逻辑：**「必然不存在」直接 404，不进 DB**——恶意扫描随机短码的流量全部被挡在布隆层
- 误判方向：只会**误判存在**（位数组被污染），误判率 0.5% 时，穿透到 DB 的量 = 攻击量 × 0.5%，DB 可承接
- 参数估算：10 亿元素、误判率 0.5% → 每元素约 15 bit ≈ 1.9GB 内存，分片部署
- 两大短板与对策：
  1. **不能删除** → 计数布隆（4 倍空间）或定期全量重建（新表切换，秒级）
  2. 新写入要登记 → 写路径同步 setbit 或近实时同步（分钟级窗口内新短码可能被 404，业务可接受）
- ❌踩坑：说「布隆过滤器误判会导致穿透打挂 DB」——误判率是**可控参数**，量级算给面试官听才是得分点

**追问6**：301 和 302 到底选哪个？

- 301 永久重定向：浏览器会缓存，后续点击**不再经过短链服务**——快、省服务器，但丢统计、无法改跳
- 302 临时重定向：每次回源——多一跳延迟，但可统计点击（UV/PV/来源/地域）、可随时改跳目标、可做过期与风控拦截
- 短链的商业价值就在**跳转那一刻的埋点**，所以主流选择 302；纯静态无统计场景（如内部资源链接）才 301
- 延迟优化：302 的回源链路被多级缓存挡住后，增加的一跳是 CDN→服务的一次轻量请求，P99 可控在几十毫秒
- ❌踩坑：只背「301 永久 302 临时」的定义——面试官要的是**统计与可控性**这个业务视角

**追问7**：自定义短码和过期短码怎么支持？

- 自定义短码：`t_custom` 唯一索引兜底，冲突时返回「已被占用」让用户换；不占用发号器号码段，两套命名空间隔离
- 过期：**懒删除**——跳转时检查 `expire_time`，过期则 302 到过期页并异步下线；**定期任务**批量清理回收
- 下线同步：删除 MySQL 记录后，**缓存和布隆都不用急着清**——布隆不能删，误判「存在」会查库拿到空再兜底 404，逻辑闭环
- 安全合规：违规长链黑名单拦截、举报下线走同一套过期机制
- ❌踩坑：想着「布隆过滤器里的过期短码怎么删」删不出来——正确答案是靠 DB 查空兜底，不硬删

**追问8**（AI 延伸）：分享链接要带 AI 摘要预渲染，怎么设计？

- 场景：用户分享文章/商品链接到社交平台，平台爬虫抓 OG 标签生成卡片——要展示 AI 一句话摘要
- 关键认知：**爬虫抓取是 bursty 高并发读**（一条链接被分享后瞬间上百次抓取），恰好复用短链读路径
- 设计三步：
  1. 生成短链时投 MQ，异步跑摘要管线（抓正文 → 清洗 → 小模型摘要 → 生成 OG 标签/分享图）→ 写入短链元数据 + CDN
  2. 预渲染未完成时，爬虫先拿到**默认卡片**（标题 + 原图），摘要就绪后自然更新——不阻塞分享动作
  3. 摘要结果按内容哈希缓存（同篇文章多处分享只算一次），失败降级为截取首段
- 量级账：日增 100 万短链 × 摘要 500 token，小模型批量推理，成本可控在个位数百分比增量
- ❌踩坑：把摘要生成放进短链创建的同步链路——用户等 2 秒才能拿到链接，体验崩塌；**分享动作和摘要渲染必须解耦**

### 🎤 口述模板

> 我先澄清读写比和总量级：10 亿条、读写比 100 比 1，所以这是一道读路径题，写路径保正确就行。
>
> 写路径：长链先按内容哈希去重，发号器用号段模式取号——双 buffer 预载下一段，DB 压力只有写量除以号段长度；号码做可逆混淆防遍历，再 Base62 编码成 7 位短码，落 MySQL 按 16 库 64 表分片，短码做分片键。
>
> 读路径是重点：本地 LRU 缓存十万热点，Redis 缓存千万热点，两层合计命中率约 95%，DB 只接 3000 QPS 左右的长尾；不存在的短码靠布隆过滤器挡在 DB 之前，误判率调到 0.5%，内存约 2GB 分片部署。顶级热 key 用逻辑过期防击穿，TTL 加随机抖动防雪崩。跳转用 302，因为点击统计和可控改跳是短链的商业价值所在。
>
> 一致性上短链几乎不可变，先更新 DB 再删缓存足够。如果延伸到分享链接带 AI 摘要预渲染，我会把摘要生成放 MQ 异步管线，爬虫先拿默认卡片，摘要按内容哈希复用，失败降级截首段——分享动作绝不等待模型推理。

### 一句话总结

短链是读路径设计的教科书：发号器管无碰撞生成，多级缓存管 95% 的读，布隆过滤器管住不存在，302 保住统计权——10 亿条数据，DB 只见长尾。

## 题 3｜分布式锁与幂等：订单重复提交的防线

> **一句话考察点**：你能不能把「一把锁的正确性边界」讲清楚——SETNX 的续期与误删、RedLock 的争议与 fencing token、以及认识到**锁永远会破，幂等与对账才是最后防线**。
>
> **考频**：⭐⭐⭐⭐⭐（考频校准：秒杀/下单场景的一线衍生追问，从命令细节一路追到架构哲学，链路极长）

### 需求澄清

场景对齐：用户快速双击「提交订单」、App 弱网重试、MQ 至少一次投递导致的重复消费、支付回调重发——四种重复，对应的防线不同。

| 我问 | 面试官答（假设） | 对设计的影响 |
|---|---|---|
| 重复的下单 QPS 峰值？ | 大促 5000 QPS | 锁操作的量级决定选型（Redis 轻松 / ZK 吃力） |
| 锁粒度按什么维度？ | 用户级（一人一单） | 粒度越细冲突越少，user_id 维度即可 |
| 业务能容忍锁失效的极端情况吗？ | 极小概率可容忍，但要有兜底 | 不追求锁绝对正确，**幂等 + 对账兜底**才是完整答案 |
| 对账实时性要求？ | T+1 全量 + 小时级增量 | 决定对账系统的复杂度 |
| 涉及资金扣减吗？ | 余额支付，涉及 | 幂等必须做三层，且补偿要有审核位 |

核心判断先亮出来：**锁是性能优化（挡住 99% 的并发重复），幂等是正确性保证（守住最后 1%），对账是兜底闭环**——三者是互补关系，不是替代关系。

### 架构图

```text
          【下单防重：锁拦并发，幂等守正确，对账兜底】
 用户提交订单（带前端生成的幂等 token）
    ▼
 网关/应用层：前端防抖 + token 快速去重（Redis SETNX）
    ▼
 订单服务 ── 获取分布式锁 lock:user:{uid} ────┐
    │        SET NX PX 30s + 看门狗续期        │ 挡并发重复
    ▼                                        ▼
 幂等第一层：幂等表（token 唯一索引）──冲突──→ 返回"请勿重复提交"
    ▼
 幂等第二层：订单表唯一索引（uid+sku+activity）
    ▼
 业务落库：状态机流转 PENDING → PAID / CLOSED
    │  update ... set status=2 where id=? and status=1  ← 幂等第三层
    ▼
 MQ / 支付回调（重复投递）──→ 状态机 CAS 天然幂等
    ▼
 对账任务：订单流水 vs 库存 vs 支付流水 三方核对 → 补偿队列
```

一句话讲透分层：**锁解决「同时」，幂等解决「重复」，对账解决「漏网」**。

### 关键设计决策表

| 决策点 | 方案 A | 方案 B | 方案 C | 选择与理由 |
|---|---|---|---|---|
| 锁实现 | Redis（SETNX+续期） | ZK（临时顺序节点） | etcd（lease+revision） | 选 A 做一线：性能万级 QPS、生态成熟；正确性敏感（资金）场景用 B/C 或 A+幂等兜底 |
| 解锁方式 | 直接 DEL | Lua 校验 value 再 DEL | 不设过期靠崩溃自愈 | 选 B：直接 DEL 可能删掉别人的锁；A 的 Lua 是唯一正确姿势；C 会永久死锁 |
| 防重复主线 | 只靠分布式锁 | 只靠唯一索引 | 锁 + 幂等三层 + 对账 | 选 C：锁会破（GC 停顿、主从切换），唯一索引是数据库的最后防线，对账闭环一切 |

三种锁实现的硬指标对比（这张表值得背）：

| 维度 | Redis | ZooKeeper | etcd |
|---|---|---|---|
| 一致性 | 主从异步，AP 倾向 | ZAB，CP | Raft，CP |
| 性能 | 上万 QPS | 千级 QPS | 数千 QPS |
| 崩溃自愈 | 靠过期时间 | 临时节点随会话删除 | lease 到期自动释放 |
| 惊群 | 无 | 顺序节点 watch 前一个，无惊群 | 版本号排队，无惊群 |
| 典型坑 | 主从切换瞬间双持 | 会话超时误判、运维重 | 需要自己封 watchdog 语义 |

### 容量估算

```text
锁流量账：
  下单峰值 5000 QPS，每单加锁+解锁 = 2 次Redis操作 → 1 万 QPS
  锁持有时间（幂等检查+落库）约 50ms
  并发持锁数 = 5000 × 0.05 = 250 把锁同时在飞 → 单 Redis 毫无压力

续期账：
  过期 30s，看门狗每 10s（1/3）续期一次
  250 把活跃锁 → 续期 QPS = 250 ÷ 10 ≈ 25，可忽略

幂等表账：
  日订单 2000 万 × 幂等记录 50B ≈ 1GB/日
  保留 7 天滚动清理 → 常驻 7GB，分表后单表健康

对账账：
  日 2000 万订单 × 三方流水 ≈ 6000 万行核对
  分 100 并发片，单片 60 万行约 2 分钟 → 全量 30 分钟内跑完
```

**瓶颈结论**：锁本身不是瓶颈（万级 QPS 内 Redis 闭环），瓶颈是**正确性推理**——面试官真正考的是你知不知道每种实现会在哪种故障下破防。

### 追问链

**追问1**：手写一把正确的 Redis 锁——完整说说每一步为什么。

- 加锁一条命令搞定（原子性关键）：

```text
SET lock:order:1001 <uuid> NX PX 30000
-- NX：不存在才设置（互斥）；PX 30000：30秒过期（防死锁）
-- value 用 uuid：标识「这把锁是我的」，解锁时校验
```

- 解锁必须 Lua（查 + 删两步要原子）：

```lua
if redis.call('GET', KEYS[1]) == ARGV[1] then
  return redis.call('DEL', KEYS[1])
else
  return 0   -- 锁已被别人持有或已过期，绝不能删
end
```

- 错误示范拆解：`SETNX` + `EXPIRE` 两条命令——中间崩溃就死锁；先 `GET` 判断再 `DEL`——判断完锁恰好过期被别人拿到，删掉的就是别人的锁
- ❌踩坑：只写 `SETNX key value` 就收工——没有过期时间是死锁，没有 uuid 是「删别人锁」，这两点是被追问的固定起手式

**追问2**：过期时间到了业务还没执行完怎么办？

- 后果：锁自动释放 → 别人拿到锁 → **两个客户端同时执行** → 互斥被破坏
- 解法：**看门狗（watchdog）续期**——后台线程每 过期/3（如 10s）检查业务是否还在执行，是则把过期重置回 30s
- Redisson 的实现：默认 30s 锁，`lockWatchdogTimeout` 周期续期；业务线程结束/崩溃后看门狗停止，锁自然过期
- 续期也失败怎么办（Redis 抖动）：业务侧要能感知（续期结果检查），拿不稳就**放弃执行并回滚**，把机会让给幂等层
- ❌踩坑：把过期时间设成 10 分钟来「保险」——崩溃后其他节点要等 10 分钟才能拿锁，可用性崩塌；正确思路是**短过期 + 勤续期**

**追问3**：就算有看门狗，为什么还可能出现两个客户端同时持锁？

- 经典场景（GC/调度停顿版）：
  1. 客户端 A 拿到锁，开始执行业务
  2. A 发生长达 40s 的 GC 停顿（或 VM 冻结），看门狗也一起停了
  3. 锁 30s 过期，客户端 B 拿到锁开始执行
  4. A 恢复，**自我感觉还持锁**，继续写数据 → 双写
- 解药：**fencing token**——锁服务每次发锁附带单调递增令牌（33、34、35…），存储层（DB/Redis）记录见过的最大令牌，**拒绝旧令牌的写入**
- 效果：A 持 token=33 恢复后写库，库已见过 34，直接拒绝——正确性由存储层守门，不再依赖「持有者自觉」
- ❌踩坑：以为续期机制能 100% 防住——续期本身也是网络请求，停顿期间什么都可能发生；** fencing token 是把正确性从「锁的承诺」转移到「存储的校验」**，这是本题的分水岭认知

**追问4**：RedLock 是什么？为什么有争议？你怎么站队？

- RedLock 流程：向 5 个**独立**（无主从）的 Redis 实例依次加锁，多数派（≥3）成功且总耗时小于锁有效期 → 持锁成功
- 质疑方（Martin Kleppmann）核心论点：
  1. 依赖各节点时钟大致同步——时钟跳跃一次，锁提前失效，双持
  2. GC 停顿/网络延迟后，持有者可能拿着「已失效的锁」继续操作——RedLock 没有 fencing token 就挡不住
- 反驳方（antirez）：时钟可以单调化处理；性能与工程可用性足够
- 务实站队（面试推荐口径）：
  - 效率型锁（防重复计算/防并发覆盖）：单 Redis + 看门狗足够，破了的代价是重算一次
  - 正确型锁（防资金双扣）：要么 ZK/etcd（CP，天然 fencing：zxid/revision 单调递增），要么 Redis 锁 + **幂等唯一索引兜底**——生产系统里后者更常见
- ❌踩坑：无脑吹 RedLock「多数派所以一定安全」——没讲时钟依赖和 fencing 缺失两大批评，等于没读过这场争论

**追问5**：ZK 和 etcd 的锁原理？什么时候值得为它们多付成本？

- ZK：创建 `/lock/seq-` **临时顺序节点**，最小序号者持锁；其他人只 watch **前一个**节点（避免惊群）；会话断开节点自动删除（崩溃自愈）
- etcd：`CreateRevision` 排队 + **lease（租约）** 到期自动删除 + `KeepAlive` 续租；revision 全局单调，天然可当 fencing token 用
- 代价：写都要过多数派共识，吞吐千级 vs Redis 万级；运维复杂度高
- 值得付的场景：锁保护的资源本身是强一致存储、错误代价是资金/合规级别、QPS 不高（如定时任务互斥、主备切换）
- ❌踩坑：只说「ZK 是 CP 所以选它」——不看量级，5000 QPS 的锁打到 ZK 上会把它打挂；**正确性要求和性能要求一起摆出来再选**

**追问6**：幂等三层防线，每一层各挡什么？

- **第一层——幂等表/token 去重**（挡「并发重复提交」）：
  - 前端进页面先领 token，提交带上；服务端 `INSERT` 幂等表（token 唯一索引），冲突即拒绝
  - 快速失败，业务逻辑都没进；缺点：token 本身要管理（过期、防伪造）
- **第二层——业务唯一索引**（挡「漏网的重复落库」）：
  - `uk(uid, sku, activity)` 直接建在订单表上，数据库层物理兜底，任何上游失误到这里终止
  - 报错转「返回已有订单」，对用户表现为幂等成功
- **第三层——状态机 CAS**（挡「重复消息/回调」）：

```sql
UPDATE orders SET status = 'PAID' WHERE order_id = ? AND status = 'PENDING';
-- affected = 0：已被处理（支付过/已关单），直接 ACK 消息，不重试
```

- MQ 重复消费、支付回调重发都在第三层被天然吸收——**状态单向流转是分布式系统里最便宜的幂等**
- ❌踩坑：三层只讲一层还自称「做了幂等」；或者用 `SELECT 再 UPDATE` 两步实现——不是原子的，等于没防

**追问7**：为什么锁和幂等都做了，还要对账？

- 认知起点：**每一层都可能破**——Redis 主从切换锁丢失、唯一索引建漏了字段、状态机分支写错、代码 bug——工程上没有绝对
- 对账是**不信任任何中间层的最终防线**：订单流水 vs 支付流水 vs 库存变动三方核对，差异进补偿队列
- 补偿分级：可自动（重复扣减 → 退回）、需审核（金额异常）、需人工（流程缺失）
- 节奏：小时级增量对账（快发现）+ T+1 全量对账（兜底闭环），对账结果本身要有监控（差异数突增告警）
- 话术点睛：「锁和幂等决定系统**平时不出错**，对账决定系统**错了能发现、能恢复**——资金链路两者缺一不可」
- ❌踩坑：把对账说成「DBA 手工核对」——要对齐到自动核对 + 补偿队列 + 告警的工程体系

**追问8**：主从切换导致锁丢失，具体是怎么发生的？

- 时间线拆解（背下来，高频）：
  1. 客户端 A 在**主**上拿到锁
  2. 主宕机，锁还没同步到从（**异步复制**）
  3. 哨兵提升从为新主——锁「凭空消失」
  4. 客户端 B 在新主上拿到锁 → A、B 双持
- 缓解手段排序：
  1. 等 O_DOWN/故障转移窗口过了再放锁请求（治标）
  2. `WAIT` 命令强制同步 N 个副本（降性能换概率）
  3. RedLock / etcd（结构性解决，见追问4/5）
  4. **接受它，靠唯一索引兜底**（生产最常见的务实选择）
- ❌踩坑：答「Redis 集群不会丢数据」——异步复制这个词必须主动说出口，面试官在等它

### 🎤 口述模板

> 这个问题我分三层回答：锁挡「同时」，幂等挡「重复」，对账兜「漏网」。
>
> 锁用 Redis：`SET key uuid NX PX 30000` 一条命令原子加锁，解锁用 Lua 先校验 value 再删，防止误删别人的锁；业务执行期由看门狗每十秒续期，避免过期后双持。但我清楚 Redis 锁的正确性边界：主从异步复制下切换瞬间可能丢锁，GC 停顿后持有者也可能拿着失效锁继续写——所以资金场景要么上 etcd 用 lease 加 revision 当 fencing token，要么就用幂等兜底，生产上后者更常见。
>
> 幂等做三层：前端领 token，幂等表唯一索引挡并发重复提交，快速失败；订单表业务唯一索引做数据库级物理兜底；状态机 CAS `update where status=PENDING` 天然吸收 MQ 重复消费和回调重发。最后是 T+1 全量加小时级增量的三方对账，差异进补偿队列——锁和幂等保证平时不出错，对账保证错了能发现、能恢复。

### 一句话总结

分布式锁是一道「诚实题」：能写对 SETNX 和 Lua 只是入场券，讲清锁会怎么破（GC、时钟、主从切换）、拿 fencing token 和幂等三层接住、最后用对账闭环——才是完整答案。

> **一句话考察点**：限流四算法的边界、单机到集群的演进、熔断三状态机，以及 2026 的真题方向——大模型调用的 RPM/TPM/并发/租户预算四维限流与供应商限流时的排队降级。
>

### 需求澄清

### 关键设计决策表

|---|---|---|---|---|
| 限流算法 | 固定窗口计数 | 滑动窗口 | 令牌桶 | 选 C（漏桶做对照）：允许可控突发贴合真实流量；滑动窗口内存高；固定窗口有 2 倍突刺 |

### 容量估算

```text
网关吞吐账：
  入口峰值 5 万 QPS，网关单节点 2 万 QPS（纯 IO 转发）
  → 3 节点 + 1 冗余 = 4 节点，CPU 目标 < 50%

限流账：
  Redis Lua 令牌桶：每次请求 1 次往返 ≈ 1ms
  5 万 QPS 全走 Redis → Redis 单实例 10 万 QPS 内可行但延迟抖动
  → 混合模式：本地预扣 80%（每秒领一批），远程精确 20%
  Redis 实际承压 ≈ 1 万 QPS，安全

熔断账（按下游维度统计）：
  滑动窗口 10s，最少 20 个请求才统计错误率（防小样本误判）
  错误率 > 50% 持续 2 个窗口 → OPEN；冷却 30s → HALF-OPEN 放 5 个探测

AI 调用账（2026 变体）：
  日 50 万次 LLM 调用，平均输入 2000 token + 输出 500 token
  TPM 峰值 = 50万 × 2500 ÷ 86400 × 峰值系数5 ≈ 72 万 token/分钟
  → 需要按供应商配额拆分 + 排队削峰（见追问6/7）
```

**瓶颈结论**：网关本身不是瓶颈（无状态水平扩展），瓶颈在**限流的精确性与性能互斥**（集群精确 → Redis 集中 → 往返延迟）以及 **AI 场景下 token 维度的计量成本**。

### 追问链

**追问1**：四类限流算法各自的坑？

- **固定窗口**：窗口边界突刺——第 1 秒后半 + 第 2 秒前半可打出 **2 倍阈值**；实现最简单，只适合粗粒度
- **滑动窗口**：把窗口切小格子（如 6 格 × 200ms）滚动统计，消除边界突刺；代价是内存和统计复杂度
- **漏桶**：恒定速率流出，**绝对平滑**；缺点是无法应对合理突发——早高峰的脉冲流量全部被拒
- **令牌桶**：匀速产令牌、桶缓存令牌，**允许累积的突发**（最多一桶），主流选择（Guava RateLimiter 就是它）
- 选型口径：要平滑（调用第三方支付）用漏桶；要弹性（网站入口）用令牌桶；要简单统计（运营位）固定窗口也行
- ❌踩坑：只背算法名不讲「2 倍突刺」这个具体数字场景——突刺例子是固定窗口的经典失分点反杀点

**追问2**：集群限流怎么做？Redis 令牌桶的 Lua 怎么写？

- 集中式的本质：把「计数状态」收敛到 Redis，用 Lua 保证「读-算-写」原子：

```lua
-- KEYS[1]=令牌桶key  ARGV: 速率/容量/当前时间/申请数
local rate, capacity = tonumber(ARGV[1]), tonumber(ARGV[2])
local now = tonumber(ARGV[3])
local b = redis.call('HMGET', KEYS[1], 'tokens', 'ts')
local tokens = math.min(capacity,
    (b[1] or capacity) + (now - (b[2] or now)) * rate)  -- 按时间补令牌
if tokens >= tonumber(ARGV[4]) then
  redis.call('HMSET', KEYS[1], 'tokens', tokens - ARGV[4], 'ts', now)
  return 1  -- 放行
end
return 0      -- 拒绝
```

- 性能矛盾：每请求一次 Redis 往返，5 万 QPS 时 Redis 成新瓶颈
- 混合模式：每个网关节点每秒**预领一批令牌**（如 1000 个）本地发，远程只做余量校准——牺牲千分之一精度换十倍吞吐
- ❌踩坑：写成了先 GET 再 SET 两步——原子性没了，超发；或没讲 Redis 故障时的降级（回退单机限流，保命要紧）

**追问3**：熔断器三状态机完整走一遍？

- **CLOSED（正常）**：请求放行，滑动窗口统计错误率/慢调用比例
- **OPEN（熔断）**：错误率 > 50%（窗口 ≥ 20 请求）且持续 2 窗口 → 快速失败（fail fast），**一个请求都不发**，给下游喘息
- **HALF-OPEN（半开探测）**：OPEN 冷却 30s 后放 5 个探测请求——全成功 → CLOSED 恢复；任一失败 → 回 OPEN 再冷却
- 关键细节：
  1. 最小样本数：低流量时 3 个请求错 2 个 ≠ 66% 错误率，要设门槛
  2. 慢调用熔断：错误不多但 P99 飙到秒级，按「慢调用比例」触发同样有效
  3. 熔断维度：按下游服务 × 接口分组，不能全局一把闸
- ❌踩坑：恢复策略说「到期直接全量放开」——瞬时流量全灌入刚缓过来的下游，二次雪崩；**half-open 渐进探测**是必答点

**追问4**：限流和熔断什么区别？各自保护谁？

- 限流是**主动预防**：在入口按配额放行，保护「自己不被打爆」，触发条件是**量**
- 熔断是**被动止损**：下游已经病了，快速失败防止调用方线程池被拖死（级联雪崩的根因是**超时堆积**不是流量本身），触发条件是**健康度**
- 一句话：限流防「我打爆别人」，熔断防「别人拖死我」；两者在网关上组合成流量防线
- 顺带提降级：熔断后返回兜底数据（缓存旧值/默认值），是「止损后的体验补偿」
- ❌踩坑：把熔断说成「特殊的限流」——触发信号、保护对象、恢复机制三者都不同，混答直接暴露没理解

**追问5**：灰度路由在网关层怎么实现？

- 路由维度：uid 尾号（1% → 5% → 50%）、用户标签（白名单/内部员工/某地域）、流量权重（随机百分比）
- 实现：规则存配置中心，网关 watch 秒级生效；路由表 `规则 → 服务分组（stable/canary）`
- **灰度必须配自动回滚**：灰度组的核心指标（错误率/P99/转化率）与基线组实时对比，超阈值自动切回——没有自动回滚的灰度是「定时炸弹」
- 发布姿势：金丝雀 1% 观察 30 分钟 → 5% → 50% → 100%，每步有检查清单
- ❌踩坑：只讲路由不讲回滚——面试官考的是「敢不敢灰度」的工程完备性，回滚机制才是成熟度标志

**追问6**（AI 延伸）：大模型调用为什么要同时看 RPM、TPM、并发数、租户预算四个维度？

- 四个维度各保护一个不同的东西，缺一不可：
  1. **RPM（每分钟请求数）**：保护调度层与供应商计费单位——请求再小也有固定开销（建连、排队、鉴权）
  2. **TPM（每分钟 token 数）**：保护真实吞吐与成本——推理耗时和显存占用与 token 数正相关，**只限 RPM 会被一个 10 万 token 的长 prompt 打爆**
  3. **并发数**：保护连接池与队列长度——并发 100 × 平均 30 秒 = 3000 个在飞请求，队列一旦无限增长，延迟雪崩且超时全军覆没
  4. **租户预算**：保护商业上的钱——技术限流防故障，预算限流防超支；月度配额到 80% 告警、100% 降级到便宜模型或停服
- 计量实现：网关在请求前预扣输入 token 估算值，流式返回后按实际值修正（多退少补），并发用 INCR/DECR 信号量
- ❌踩坑：只答「多加几个计数器」——要讲出**每个维度对应的故障模式**，这是 2026 真题方向的采分点

**追问7**（AI 延伸）：模型供应商限流（429）时，怎么排队降级保护核心请求？

- 第一步**分级**：请求打优先级标签——核心（交易客服、生产链路）> 交互（用户对话）> 批量（离线报表、评测跑批）
- 第二步**排队**：429 或并发满时进**优先级队列**而非直接拒绝——核心请求插队，批量任务自动让路延后执行；队列返回预计等待时间，超时主动放弃
- 第三步**failover**：多供应商配置（主 + 备 + 降级位），429/超时自动切换，注意**配额分池**别把备用打爆
- 第四步**降级链**：大模型 → 小模型（答 70% 的问题够用）→ 语义缓存命中（高频问题直接回历史答案）→ 模板回复 +「稍后再试」
- 第五步**预算联动**：租户预算耗尽的请求走最便宜的降级路径，而不是硬切供应商烧钱
- ❌踩坑：降级只答「换小模型」一条——排队、failover、缓存、模板是完整链条；另外**批量任务必须可暂停**（让路核心），这点说出来是明显加分项

**追问8**：限流阈值到底怎么定？

- 压测找拐点：逐步加压，P99 延迟开始飙升的 QPS 就是系统真实容量（比如 8000）
- 阈值 = 拐点 × 0.8（留 20% 余量），按核心接口单独定，不搞全局一刀切
- 动态调整：大促前扩容 → 配置中心同步上调；依赖节假日历的「容量预案」提前演练
- 进阶：自适应限流（按 CPU/负载自动收缩阈值），适合长尾服务，核心链路仍用静态阈值保确定性
- ❌踩坑：拍脑袋定「10 万 QPS」——没提压测和拐点，阈值就是玄学；也要防「压测环境与线上不对称」的坑（数据量、连接数、依赖桩）

### 🎤 口述模板

> 网关我定位成流量守门人：限流管入口的量，熔断管出口的伤，灰度管发布的险。
>
> 限流算法我选令牌桶，允许可控突发；但四个算法的边界我会讲清楚——固定窗口有边界突刺、漏桶太刚性。集群限流用 Redis Lua 令牌桶保证原子性，高 QPS 下改成本地预领配额加远程校准的混合模式，牺牲少量精度换吞吐，Redis 故障就回退单机限流保命。熔断是三状态机：关闭态统计错误率，超阈值进入打开态快速失败，冷却后半开态放五个探测请求渐进恢复，绝不直接全量放开。灰度路由配置中心动态下发，配自动指标对比回滚。
>
> 如果接大模型调用，限流要升到四个维度：RPM 保护调度、TPM 保护真实吞吐和成本、并发保护连接池、租户预算保护钱——只看 RPM 会被长 prompt 打爆。供应商 429 时走五步：请求分级进优先级队列、多供应商 failover、大模型降小模型、语义缓存兜底、模板回复保底，批量任务主动让路核心请求。阈值全部来自压测拐点打八折，不拍脑袋。

### 一句话总结

传统限流考「算法边界 + 集群原子性 + 熔断状态机」，2026 增量考「AI 四维计量 + 排队降级链」——四个维度各防一种死法，降级是一条链不是一个开关。

## 题 5｜延迟任务系统：订单 30 分钟自动取消

> **一句话考察点**：时间维度上的架构——四种延迟方案的精度/量级/可靠性三角权衡，关单的幂等与竞态处理，死信联动兜底——考的是「到期这件事交给谁」的全局判断。
>
> **考频**：⭐⭐⭐⭐⭐（考频校准：订单/支付场景的标配追问，与 MQ、幂等、分布式锁天然联动）

### 需求澄清

| 我问 | 面试官答（假设） | 对设计的影响 |
|---|---|---|
| 精度要求？30 分钟误差容忍多少？ | ±1 分钟内 | 不需要秒级精度 → 方案空间大幅放宽 |
| 日订单量级？ | 常态 500 万，大促 5000 万 | 量级决定单机时间轮够不够、要不要分片 |
| 任务丢了能接受吗？ | 不能，宁可晚关不能不关 | 可靠性优先 → 必须有对账/扫描兜底 |
| 关单时要做什么？ | 释放库存 + 退优惠券 + 通知 | 关单是编排动作，失败要分解重试 |
| 大促后的到期分布？ | 集中在整点后 30 分钟 | 有到期洪水问题，消费端要能水平扩展 |

开场定调：延迟任务的本质是「**把未来的某个时间点变成一次触发**」——四个候选方案（DB 轮询 / Redis ZSet / 时间轮 / MQ 延迟队列）在精度、量级、可靠性上各有甜点区，选型 + 兜底才是完整答案。

### 架构图

```text
        【延迟关单链路：投递 → 延迟 → 触发 → 幂等关单 → 兜底】
 创建订单（status=PENDING, expire_at=now+30min）
    │
    ├─→ 主延迟通道：MQ 延迟消息（30min 后投递）
    │        │消费：关单服务
    │        ▼
    │   幂等关单（状态机 CAS）：
    │   UPDATE orders SET status='CLOSED'
    │    WHERE order_id=? AND status='PENDING';   ← affected=0 说明已支付/已关
    │        │成功
    │        ▼
    │   编排补偿：回补库存 → 退优惠券 → 通知用户（失败进重试）
    │        │重试超限
    │        ▼
    │   死信队列 → 告警 → 人工/自动补偿
    │
    └─→ 兜底通道（不信任任何单点）：DB 定时扫描
         expire_at < now AND status='PENDING' 每分钟扫一批补关
              └→ 与支付回调的竞态：统一走状态机 CAS 裁决
```

两条通道的关系一句话：**MQ 是主通道（准时、解耦），DB 扫描是兜底通道（漏网必抓）**——互为保险，幂等让它们可以重复执行。

### 关键设计决策表

| 方案 | 原理 | 精度 | 量级 | 可靠性 | 适用 |
|---|---|---|---|---|---|
| DB 轮询 | `WHERE expire_at<now AND status=1` 定时扫 | 分钟级 | 百万内好使（要索引） | 高（数据就在 DB） | 中小系统 / 兜底通道 |
| Redis ZSet | score=到期时间戳，`ZRANGEBYSCORE` 轮询取 | 秒级 | 内存受限（亿级要分片） | 中（持久化弱、挂了要重建） | 高精度中小量级 |
| 时间轮 | 环形数组+槽，指针走到即触发；层级化覆盖长延迟 | 毫秒级 | 单机千万任务 O(1) | 低（纯内存，重启丢） | 网关超时/连接管理（Netty、Kafka 内部用它） |
| MQ 延迟队列 | RocketMQ 延迟 level / 死信重投 | 秒~分钟级 | 分布式海量 | **最高**（持久化+重试+死信生态） | 订单类业务首选 |

（对比表是必背项：四个维度各记一个「最」，选型时按业务对号入座）

补充两个高频细节：

- RabbitMQ 的 TTL + 死信实现有**队头阻塞**：队列头的 10 分钟消息会挡住后面的 1 分钟消息（TTL 按队头判定）→ 必须按延迟时长分队列（如 1min/5min/30min 各一条）
- RocketMQ 5.x 前只支持 18 个固定延迟 level（1s~2h），30 分钟正好有档位；任意精度要 5.x 的定时消息或自己实现

### 容量估算

```text
任务量账：
  常态日 500 万单，未支付率 20% → 100 万延迟任务/日
  大促日 5000 万单 → 1000 万任务/日，且集中在整点后 30 分钟到期

到期洪水账（大促 20:00 开抢）：
  20:00~20:10 下单 300 万，20:30~20:40 集中到期
  → 峰值到期速率 = 300 万 ÷ 600s ≈ 5000 任务/秒
  → 关单服务按 1 万 TPS 水平扩展（关单本身很轻，一次 CAS + 编排）

存储账：
  MQ：1000 万条消息/日，单条 1KB ≈ 10GB，堆积能力绰绰有余
  Redis ZSet 若做主通道：1000 万 × (member 20B + score 8B + 跳表开销)
    ≈ 2~3GB，单实例可扛但持久化窗口有丢失风险 → 兜底必须有

DB 扫描账：
  expire_at + status 联合索引，每分钟扫一批（LIMIT 500）
  5000 万订单表上，命中索引的 range 扫描毫秒级
  扫描节流：只扫 30~90 分钟区间，超龄的直接进人工对账表
```

**瓶颈结论**：常态毫无压力；**大促到期洪水**是唯一峰值——解法是关单服务无状态水平扩展 + 幂等让重复触发无害 + 扫描分片并行。

### 追问链

**追问1**：四个方案怎么选？给个决策顺序。

- 决策三问：精度要多高？量级多大？丢了行不行？
- 决策树口径：
  - 分钟级精度 + 中小量级 → **DB 轮询**（最简单，别过度设计）
  - 秒级精度 + 内存量级可控 → **Redis ZSet**
  - 毫秒级 + 海量 + 进程内 → **时间轮**（中间件内部用）
  - 业务可靠第一 + 分布式 → **MQ 延迟队列**（订单场景 90% 的答案）
- 本题口径：±1 分钟精度 + 大促千万级 + 不能丢 → MQ 主通道 + DB 扫描兜底
- ❌踩坑：秒杀式地答「上时间轮」——时间轮纯内存单机，重启丢任务，订单场景裸奔；**先问精度和可靠性再选**才是考点

**追问2**：Redis ZSet 方案详细说说，坑在哪？

- 核心：`ZADD delay:orders <到期时间戳> <order_id>`；消费线程循环 `ZRANGEBYSCORE delay:orders 0 <now> LIMIT 100` 取到期任务，`ZREM` 删除成功后执行
- **ZREM 是并发关键**：多消费者同时取到同一批任务，谁 ZREM 成功谁执行（返回值=删除数），天然抢占去重
- 坑一：**big key**——千万成员挂在一个 key 上，单分片热点 → 按 order_id hash 拆 16 个 zset，消费端并行扫
- 坑二：**持久化窗口丢任务**——AOF 每秒刷盘，宕机丢 1 秒任务 → 兜底扫描必须配
- 坑三：**取了没删、删了没执行**——ZREM 后进程崩溃任务消失 → 先写「执行表」再删，或接受兜底扫描补
- ❌踩坑：只说 ZSet「天然有序所以适合」不讲 ZREM 抢占和三大坑——追问两层就露底

**追问3**：时间轮原理讲一下，为什么它是 O(1)？

- 单层时间轮：长度 60 的环形数组（槽），指针每秒走一格；任务按 `到期时间 % 60` 挂到槽的链表上；指针走到就触发——**插入 O(1)，触发无排序**
- 覆盖范围只有一轮（60 秒）→ **层级时间轮**：秒轮、分轮、小时轮，像时钟进位——任务先挂小时轮，时间临近降级到分轮、秒轮（Kafka 的延迟操作就这么实现）
- 对比堆：优先级队列取最近到期是 O(log n)，时间轮是 O(1)——千万级任务时差距显著
- 适用边界：**进程内、可丢、超大量**——连接超时、请求重试调度；订单这种要持久化的业务不合适
- ❌踩坑：说「时间轮支持任意延迟所以万能」——单层轮只覆盖一轮时长，长延迟必须层级化，这个细节最能区分背没背过

**追问4**：RabbitMQ 和 RocketMQ 的延迟消息差异？

- RabbitMQ：原生无延迟队列，靠 **TTL + 死信交换机**模拟——消息到期变成死信，路由到消费队列
- 致命坑：**队头阻塞**——队列按队头消息 TTL 判定过期，队头 10 分钟 + 队尾 1 分钟 = 队尾要等 10 分钟 → 必须按延迟档位拆多条队列（1min/5min/30min）
- RocketMQ 4.x：**18 个固定 level**（1s/5s/30s/1m/…2h），30 分钟正好命中；实现是消息先存 SCHEDULE_TOPIC_XXXX，定时线程到点投回原队列
- RocketMQ 5.x：任意精度的定时消息（timestamp 直接指定）；
- 选型口径：延迟档位固定的业务（关单/提醒）4.x 够用；任意延迟需求上 5.x 或自建
- ❌踩坑：不知道队头阻塞——这是 RabbitMQ 延迟方案最经典的坑，被问到必须秒答「按档位拆队列」

**追问5**：关单怎么保证幂等？

- 核心一招：**状态机 CAS**——

```sql
UPDATE orders SET status = 'CLOSED'
 WHERE order_id = ? AND status = 'PENDING';
-- affected = 0：订单已支付或已关单 → 直接 ACK 消息，不重试不报错
```

- 重复触发无害化：MQ 重复投递、扫描兜底与 MQ 主通道**同时触发**同一单——两次 CAS 只有一次成功，败者安静退出
- 编排动作的幂等：回补库存用「补偿流水表」唯一索引防重复回补；退优惠券同理（补偿 id = order_id + action）
- 消费侧 ACK 纪律：**先执行后 ACK**，失败不 ACK 走重试；绝不能先 ACK 后执行（丢任务）
- ❌踩坑：用 `SELECT status` 判断再 `UPDATE`——两步非原子，并发下双关；另一个坑是关单失败立即重试无退避——把下游打挂

**追问6**：用户在第 29 分 59 秒支付成功，关单任务同时触发，怎么办？

- 竞态本质：支付回调和延迟关单**并发修改同一订单状态**
- 裁决机制：两者都走**状态机 CAS**，DB 行锁串行化——先到先得：
  - 支付先 CAS 成功（PENDING→PAID）→ 关单 CAS affected=0，安静退出 ✓
  - 关单先成功（PENDING→CLOSED）→ 支付回调发现订单已关 → 走**退款/补单流程**
- 补单分支是业务重点：钱收了单关了 → 自动发起退款 + 通知；或高价值场景走人工审核
- 加强版：支付回调处理前先拿 order 级分布式锁（联动题 3），把并发窗口物理消除——但**状态机兜底依然不能省**（锁可能破）
- ❌踩坑：只答「加分布式锁」——锁会破（主从切换/GC 停顿），**最终裁决必须在数据库状态机上**；或漏了「已关单+已支付」的退款分支——业务完备性丢分

**追问7**：死信队列怎么和延迟任务联动？

- 触达死信的三条路：消费重试超限（默认 16 次指数退避后）、队列满/过期、消费端 reject 不重回队列
- 联动设计：
  1. 关单消息消费失败（DB 抖动）→ 重试 3 次指数退避（10s/30s/90s）
  2. 仍失败 → 进死信 → **实时告警**（值班群/电话）
  3. 死信消费程序：隔离排查后**自动重放**（低峰期）+ 无法自动处理的转人工工单
- 死信监控指标：死信产生速率突增 = 系统性故障的前兆（比业务告警更早发现问题）
- 兜底闭环：即使死信重放也失败 → 每日对账扫描 `expire_at < now AND status='PENDING'` 全量补关——**三层保险（MQ→死信→扫描）**
- ❌踩坑：死信配了不监控——死信队列变成「黑洞队列」，任务无声消失；或重试次数配很大（如无限重试）——毒药消息堵塞正常消费

**追问8**：大促后的到期洪水怎么扛？

- 现象：20:00 开抢的 300 万单在 20:30 集中到期 → 5000 任务/秒的瞬时峰值
- 四板斧：
  1. **消费端水平扩展**：关单服务无状态，按队列分区数扩消费者（RocketMQ 并发消费）
  2. **关单动作瘦身**：关单只做状态 CAS，回补库存/退券再发一条普通消息异步做——把「到期触发」和「编排执行」解耦
  3. **扫描分片并行**：兜底扫描按 order_id 取模分 16 片并行扫
  4. **削峰错位**：下单时间戳 + 随机抖动 0~5 分钟作为过期时间——用户无感，到期洪峰被抹平（30±2.5 分钟业务可接受时才用）
- 监控三件套：到期速率、关单延迟（到期→实际关闭的时间差）、死信速率
- ❌踩坑：只答「加机器」——编排动作瘦身和随机抖动这两个「省」的思路才是区分度；另外忘了**幂等让重复触发无害**，扩并发后会大量重复关单报错

### 🎤 口述模板

> 先澄清三个数：精度 ±1 分钟、大促日千万级、任务不能丢。方案对比我背四个：DB 轮询分钟级但简单；Redis ZSet 秒级但要处理 big key 和持久化丢失；时间轮毫秒级 O(1) 但纯内存进程序用的；MQ 延迟队列可靠性和分布式能力最强。所以我的答案是 **MQ 延迟消息做主通道，DB 定时扫描做兜底**，两条通道可以重复触发同一单，幂等让重复无害。
>
> 关单幂等用状态机 CAS：update status=CLOSED where status=PENDING，affected 为零说明已支付或已关，直接确认消息。这同时解决了和支付回调的竞态——两边都走 CAS，DB 行锁裁决先后；关单先成功而支付后到的，走自动退款补单分支。关单动作本身只做 CAS，回补库存和退优惠券拆成后续异步消息，失败重试三次进死信，死信有告警和重放，最后还有每日扫描对账兜底——三层保险。
>
> 大促到期洪水四个手段：消费者水平扩容、关单与编排解耦、扫描分片并行、过期时间加随机抖动抹平洪峰。如果被问到 RabbitMQ 方案，我会主动提队头阻塞要按延迟档位拆队列，RocketMQ 4.x 是固定 level、5.x 才支持任意定时。

### 一句话总结

延迟任务的完整答案是「选型 + 双通道 + 幂等」：按精度/量级/可靠性三问选主方案，DB 扫描永远兜底，状态机 CAS 让重复触发无害——到期洪水靠解耦与抖动消化，死信联动守住最后一环。
