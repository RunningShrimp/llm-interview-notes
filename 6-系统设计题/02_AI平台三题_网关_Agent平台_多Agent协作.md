# 02 | AI 平台设计三题（LLM 网关 · Agent 平台 · 多 Agent 协作编排）

> **定位**：AI 平台基建三母题。业务方问「为什么我们的 Agent 上不了线」，答案几乎都落在这三层基建——模型怎么统一进出、单个 Agent 怎么被治理与隔离、多个 Agent 怎么协作与恢复。
> 三题自底向上：网关管「模型入口」，平台管「单 Agent 生产化」，编排管「多 Agent 协作容错」；与 01 章后端五题共享同一套六步法骨架，但每个决策点都是 AI 特有的取舍——计量单位从 QPS 变 token、故障域从自家服务变别家 API、错误代价从「重试一次」变「幻觉一次」。

## 本章导读

**考察定位**：AI 系统设计的考察正在从「单应用怎么搭」升级为「平台基建怎么建」。一线高频问法已经非常具体：「从零设计一个 Agent 平台需要哪些模块」「多模型动态路由按什么选、全故障时怎么兑底」「多 Agent 协作的通信机制与状态共享怎么做」——这三问分别对应本章三题，全是平台/基建视角，不再是「一个应用怎么写 Prompt」。

**三题知识地图**：

```text
AI 平台三题（基建层级 → 核心链路 → 高频追问 → 与 L9 单应用题的差异）
│
├─ 题6 LLM 网关与多模型动态路由 ··· 模型入口层
│    ├─ 核心链：统一协议接入 / 动态路由分级 / 级联升级 / 池化 failover
│    ├─ 治理面：四维限流 / 虚拟 key / 成本归因（租户·用户·Prompt 版本）
│    └─ 差异：L9 答「这个应用选什么模型」，本题管全公司模型的进出与账单
│
├─ 题7 企业 Agent 平台 ············ 单 Agent 生产化层
│    ├─ 核心链：工具注册与 MCP 治理 / 沙箱隔离 / HITL 审批流
│    ├─ 治理面：工作区越权防护 / 日志脱敏 / 记忆基建 / 多租户配额审计
│    └─ 差异：L9 答「一个 Agent 怎么设计」，本题是「平台怎么让一百个 Agent 安全上线」
│

     ├─ 核心链：拆分三问 / 协作拓扑 / 通信与状态共享 / 冲突仲裁
     ├─ 容错面：DAG Checkpoint / 幂等重放 / 人审挂起 / 版本兼容
```

**与 L9 单应用题的三条差异线**（考前想清楚，避免答串）：

1. **视角差异**：L9 的智能客服题站在「一个应用」视角——我怎么把这个应用做好；本章站在「平台」视角——几十个业务方接进来，模型、工具、记忆、编排都要被统一治理。开场第一句就该是「我先按多租户平台澄清需求」，而不是急着画单个应用的数据流。
2. **主要矛盾差异**：单应用的主要矛盾是效果（准确率、解决率）；平台的主要矛盾是治理与隔离（权限边界、成本归因、故障域、审计合规）。答本章题目时，每个设计都要能回答「多租户怎么隔离、出了事怎么定责」。
3. **答法差异**：单应用题答「一条链路」；平台题答「分层 + 治理面 + 故障域」——先分清每层管什么，再讲治理面（鉴权/限流/审计/版本）长在哪层，最后说清一个业务出事时怎么不让全平台陪葬。

## 题 6｜LLM 网关与多模型动态路由（公司级统一入口）

> **一句话考察点**：几十个业务、多家供应商、上百个模型，怎么设计一个统一入口，让「选模型」从每个团队的私事变成平台的公事——协议适配、动态路由、级联升级、failover 熔断、多维限流、密钥治理、成本归因七件事的合奏。
>
> **考频**：⭐⭐⭐⭐⭐（考频校准：AI 平台类题目的第一梯队，「多模型按什么选、全供应商故障怎么兑底」是真实高频追问，常作为公司级 AI 基建的开工题）

### 需求澄清

不问不画，先问四个数字：

| 我问 | 面试官答（假设） | 对设计的影响 |
|---|---|---|
| 接入规模？业务方/供应商/日调用量 | 30+ 业务线，5 家供应商 20+ 模型，日均 2000 万次调用 | 各业务自接必然失控，统一入口是前提 |
| 延迟与成本约束？ | 在线场景 P95 < 3s；月度推理预算有硬顶 | 路由器要同时吃延迟与成本两个约束 |
| 可用性目标？全供应商挂了呢 | 在线核心链路 99.9% | failover + 兜底链是必答题，不能只答「切备用」 |
| 计费与合规要求？ | 成本归因到租户/用户/Prompt 版本；真实密钥不许出平台 | 虚拟 key + 全链路计量打标是地基 |

澄清后的核心判断：这是一道「供应商治理 + 流量治理」的合体题——把 01 章网关限流的骨架平移过来，但计量单位从 QPS 换成 token，故障域从「自家服务」变成「别家 API」，而且别家 API 的账单要月底才见真章。

四个数字对设计的推演：

- **日调用 2000 万**：决定了网关必须无状态水平扩展，治理动作（限流判断、路由决策）只能依赖本地缓存 + Redis 两级——一次请求查三次库就把自己查死了
- **20+ 模型、5 家供应商**：决定了「档位」抽象必须存在——业务方面向档位（小/中/大）编程，不面向具体模型编程，否则供应商一调整产品线，全公司改代码
- **P95 < 3s**：决定了网关自身预算必须压在 100ms 内，也决定了级联只能开给离线流量——延迟预算的大头永远要留给模型推理
- **预算硬顶 + 归因到 Prompt 版本**：决定了计量必须两段式（入口预扣/出口校正），归因标签从虚拟 key 一路透传到出账，断一环归因就失真
- **在线:离线 7:3**：决定了治理链要分快慢路径——在线走全量检查，离线批量可放宽部分检查换吞吐，两类流量不能一碗水端平
- **5 家供应商**：决定了商务与技术是耦合的——配额、单价、稳定性都是变量，路由权重要把三者当实时输入，而不是写死的常数
- **可用性 99.9%**：决定了网关自身双活是硬要求——它比任何一家供应商都关键，自己先不能成为短板

澄清话术示范（开场 30 秒定调）：

```text
"我先确认四个数字：接入业务数与日调用量、延迟与月预算约束、
可用性目标、成本归因粒度。整体思路：网关做『模型进出公司的唯一闸口』——
协议归一让业务零改造，路由分级让钱花在刀刃上，池化熔断吸收供应商抖动，
计量归因让每一分钱能落到租户和 Prompt 版本头上。"
```

### 架构图

```text
业务A ─┐
业务B ┼─→ 统一接入层（OpenAI 兼容格式，业务 SDK 零改造）
业务C ─┘      │ 虚拟 key 鉴权 → 解出 租户/用户/场景/Prompt版本
               ▼ 治理链（顺序执行，网关自身预算 P99 < 100ms）
     ① 四维限流：RPM / TPM / 并发 / 租户月度预算
     ② 安全检查：入参注入检测 / 出参敏感信息拦截
     ③ 三级缓存：精确缓存 → prompt caching 亲和 → 语义缓存
               ▼ 动态路由器（特征 + 策略 + 分级模型池）
     ├─ 成本优先（摘要/分类）──→ 小模型池 1x
     ├─ 延迟优先（实时代码补全）→ 低延迟池 TTFT 优先
     ├─ 质量优先（复杂推理/代码）→ 大模型池 10~20x
     └─ 级联：小模型低置信/结构失败 → 升级大模型带 hint 重答
               ▼ 供应商适配层（协议转换 / 参数映射 / 流式对齐）
     ├─ 同档池化：2~3 家互备，健康×余量×成本 加权轮询
     ├─ 熔断三态：错误率>50% 打开 → 半开 1% 试探 → 恢复闭合
     └─ 全故障兜底链：语义缓存回放 → 排队 → 诚实拒答
               ▼ 计量出账层
     ├─ 两段式计量：入口预扣（输入+预估输出）→ 出口按真实用量校正
     └─ 归因：租户/用户/Prompt版本 → 明细仓 → OTel GenAI span 导出
```

链路走读（面试时边画边讲，每层一句「为什么放这里」）：

1. **接入层只做协议归一**：OpenAI 兼容格式已是事实标准，业务侧零改造才推得动——迁移成本是平台类产品的第一死因
2. **治理链在路由之前**：限流与安全检查必须在选模型之前完成，否则每换一家供应商就漏一次审计
3. **缓存放路由前是钱**：精确与语义缓存命中的请求根本不该进模型池；prompt caching 亲和则反过来影响路由——同前缀请求固定打到同一家，吃供应商的前缀缓存折扣
4. **路由器是大脑**：它手里有健康度、配额余量、成本三张牌，业务方只声明「我要什么」，不指定「用谁」
5. **适配层是翻译官**：每家供应商的参数、流式分片、错误码都不同，脏活全挡在这一层，往上的所有组件面对同构接口
6. **计量是闭环**：没有归因出账，前面的治理全部白做——预算限流的前提是知道每个租户现在花了多少
7. **兜底链是最后防线**：语义缓存回放 → 排队 → 诚实拒答，顺序体现「能兜多低兜多低，兜不动就说实话」
8. **网关自身要双活**：它成了全公司 AI 流量的单点，可用性目标必须高于任何一家供应商
9. **计量在最后但不次要**：出口校正是预算准确性的生命线——预估偏差不回流，月底一定对不上账
10. **所有治理点无状态**：网关任意实例可替换——状态全在 Redis 与配置中心，这是水平扩展的前提
11. **熔断在适配层不在路由层**：健康度是「这一家」的属性，路由只消费结果不维护状态——职责分清，两边才能独立测试与演进
12. **兜底链的出口要可观测**：每一级兜底的触发量单独计数——缓存回放多少、排队多少、拒答多少，次日晨会一眼看清

每层挂的治理能力（面试可口头报这张表，10 秒讲完全景）：

| 层 | 挂什么能力 | 失效会怎样 |
|---|---|---|
| 接入层 | 协议归一、虚拟 key 鉴权 | 业务与供应商锁死，密钥满天飞 |
| 治理链 | 限流、安全检查、三级缓存 | 一家被打穿全公司陪葬，成本失控 |
| 路由器 | 分级、级联、caching 亲和 | 成本翻倍，长尾质量崩 |
| 适配层 | 池化、熔断、协议转换 | 供应商抖动直接传导给业务 |
| 计量层 | 两段式计量、归因、对账 | 预算与账单互相不信任 |
| 兜底链 | 缓存回放、排队、诚实拒答 | 故障期间用户拿到幻觉答案 |

### 关键设计决策表

| 决策点 | 方案 A | 方案 B | 方案 C | 选择与理由 |
|---|---|---|---|---|
| 路由决策放哪 | 业务方自选模型，网关透传 | 网关静态规则表 | 网关动态策略引擎 | 选 C：A 把复杂度甩给业务且无法全局优化成本；B 维护不动（模型周级在更新）；C 用「场景标签 + 实时指标」决策，策略可热更可灰度。代价：网关复杂度上升，路由器自身要双活 |
| 成本优化主路线 | 全量级联（先小后大） | 难度预分类直达 + 级联兜底 | 全大模型保质量 | 选 B：A 延迟翻倍只适合离线；C 成本爆炸。预分类让 80% 请求一步到位，级联只接住预分类漏判的长尾——两个杠杆各管一段 |
| 供应商部署形态 | 每档单供应商独占 | 每档主备两家 | 同档池化 + 熔断摘除 | 选 C：B 故障切换慢且备家平时空转；C 平时加权分摊配额与成本，故障自动摘除无缝接管。代价：同档两家输出分布有差异，结构化解析失败率要双跑监控 |

补充「为什么不选」（主动交代代价，面试官最爱问）：

- 不选 A（业务自选）：每个团队都要养一套模型评测能力，重复建设且永远选不准——平台的价值就是把这件事做一次给所有人用
- 选 C（动态引擎）的代价：路由器成为关键组件，它故障 = 全公司 AI 流量故障，必须双活部署 + 路由决策全留痕
- 级联的代价再强调一次：小模型白跑的 token 也是钱——级联触发率要监控，长期高于 30% 说明预分类器该重训了
- 池化（选 C）的隐藏代价：平时两家分摊意味着两套配额、两份商务关系都要维护——用运营成本换可用性，这笔账要摆在明面上
- 三个决策的共同逻辑：都不是「技术上谁更强」，是「复杂度放哪一侧」——放业务侧则重复建设，放平台侧则平台要背可用性
- 灰度是三个决策共同的落地方式：路由策略、级联开关、池化权重全部支持按租户按比例灰度——平台自身组件的变更管理要比业务更严
- 决策表的隐藏前提是评测基建：三档映射、级联阈值、池化权重全靠历史数据校准——没有评测管道，平台只是个转发器

### 容量估算

整数近似，够用就行：

```text
流量账：
  日均 2000 万次调用，在线:离线 ≈ 7:3
  在线平峰 ≈ 2000万×0.7 ÷ 86400 ≈ 160 QPS，晚高峰 ×5 ≈ 800 QPS
  单次调用 输入2K + 输出0.5K ≈ 2.5K token
  峰值吞吐 ≈ 800 × 2.5K = 200万 token/分钟
  → 单供应商 TPM 限额通常几十万~百万级
  → 需要 3~5 个 key 聚合，且跨 2 家分摊才扛得住峰值

成本账（单价按相对倍数，小模型 = 1x）：
  全走大模型（20x）：2000万 × 2.5K token × 20x —— 预算直接爆
  路由分级后：60%小(1x) + 30%中(5x) + 10%大(20x)
  混合倍数 ≈ 0.6×1 + 0.3×5 + 0.1×20 = 4.1x → 比全大模型省约 80%
  再叠缓存：精确+语义命中 15%、prompt caching 折扣再省一成 → 综合省 80%+

延迟账：
  网关自身开销：鉴权+限流 5ms / 安全检查 20ms / 语义缓存查询 50ms / 路由 5ms
  治理链合计 P99 < 100ms，占 3s 预算的 3% —— 网关不该是延迟瓶颈
  真正的大头是模型推理 1~3s，所以「低延迟池」选型看 TTFT 与吐字速率
  级联流量延迟翻倍（小模型白跑 + 大模型重答）→ 只开给离线/半在线

缓存账：
  精确缓存命中 8%（归一化后 KV 指纹）+ 语义缓存命中 7%（阈值 0.95）
  语义缓存的误命中率（答非所问）必须 < 0.1%，否则宁可整体关闭

可用性账：
  网关双活 + 无状态 → 自身 99.99%，高于任何一家供应商（约 99.5%）
  两家池化互备：同时故障概率 ≈ 0.005 × 0.005 ≈ 十万分级 → 全故障约十年一遇
  MTTR：熔断判定 1 分钟窗口 + 半开探测 30 秒 → 单家故障切换 < 90 秒

弹性账：
  在线晚高峰 ×5 → 网关无状态扩容 4 → 16 实例（分钟级）
  上游 TPM 不随你扩容 → 峰值靠排队 + 缓存消化——扩自己没用时要认命

演练账：
  每季度全供应商故障注入一次，验收四件事：
  拒答 100% 触达用户 / 零幻觉输出 / 恢复后排队 5 分钟内清空 / 计量零丢失
  单家故障演练每月一次（轮流摘除一家），MTTR 实测 < 90 秒
  熔断误开率（把忙当挂）< 1%/月，超标即重校窗口与阈值
  缓存一致性抽检：每日 500 条语义缓存命中 vs 重新生成对比
```

**瓶颈结论**：瓶颈不在网关计算，在**上游配额**——TPM 是硬约束，靠多 key 聚合、跨供应商分摊、排队消化；其次是成本，主战场在路由分级的准确率与缓存命中率。

**降级链**：某档池全熔断 → 降一档模型顶上（仅白名单场景）→ 语义缓存回放 → 排队 + 延迟承诺 → 诚实拒答。合规红线类任务只允许走最后两级，绝不静默换模型。

追加一句第二瓶颈：语义缓存的误命中——它直接产出错误答案，0.1% 的红线要靠人工抽检 + 自动金标 Canary 双通道守住，超线宁可整层关闭。

### 追问链

**追问1**：为什么必须是统一网关？各业务自己接模型不行吗？

- 先算分散接入的账：30 个业务 × 5 家供应商 = 150 条私有集成——密钥散落 30 个仓库、计量口径 30 套、供应商调价没人第一时间知道、想做全公司统一安全检查无从下手
- 平台四收益，一条条报：
  1. **协议归一**：对外统一 OpenAI 兼容格式，业务切换模型零改造——「可替换性」是平台的第一价值
  2. **治理集中**：限流、审计、安全检查、合规拦截在一处做一次，全公司生效
  3. **成本可视**：统一计量才谈得拢量价、做得成预算、出得了账单
  4. **故障域收窄**：供应商抖动由网关的池化与熔断吸收，业务方无感
- 一句面试官爱听的总结：网关的本质是把「选模型」从每个团队的私事变成平台的公事——模型是可替换组件，业务不该和任何一家供应商锁死
- 类比传统基建：这就是数据库中间件 / 统一出入口在 AI 时代的复刻——「多上游、计量计费、按租户治理」的后端经验全部可平移

```text
分散接入 vs 统一网关（一页对比）：

  维度        各业务自接             统一网关
  密钥管理    30 个仓库各存一份      密钥保险仓 1 处 + 虚拟 key
  供应商调价  无人第一时间知道       网关改一处，全公司生效
  限流配额    各自为战互不知晓       四维统一，全局可调
  故障切换    每个团队自己写         池化熔断自动
  成本账单    月底供应商账单才知道   实时归因到租户/Prompt 版本
```

- 反方观点也要接得住（面试官会故意唱反调）：小团队就一个业务，要不要先建网关？——网关可以晚建，但「密钥不出业务服务」「计量统一口径」两条规范从第一天就要守，否则欠的账后面连本带利还
- 演进路径补充：裸 SDK 直连 → 统一 SDK + 轻代理 → 完整网关（路由/熔断/计量逐步长出来）——一步到位的网关是过度设计，但协议规范必须一步到位
- 网关的边界也要说清：它管「模型流量」，不管「业务语义」——prompt 内容审核这类跟场景强绑定的策略，以插件形式挂在治理链上，由业务方按租户启用
- 组织维度补充：平台团队管网关、业务团队管场景策略——权限分离本身就是安全设计，网关管理员改不了业务路由策略，反之亦然
- **收束一句**：统一网关不是「多一层转发」，是把选型、治理、计量三件事从 30 个团队收归一处——省的是全公司的重复建设
- ❌踩坑：把网关答成「转发代理」——没有路由、熔断、计量、治理，就只是个反向代理；另一个极端是堆产品名，面试官要的是能力维度拆解，不是采购清单

**追问2**：动态路由具体怎么做？「按任务特征/成本/延迟」落到实现是什么？

- 路由三要素：**特征**（这次调用是什么）→ **策略**（该进哪个池）→ **目标**（池内选哪家）
- 特征从哪来（在「不额外加延迟」的前提下）：
  - 调用方显式声明：场景标签（摘要/分类/代码/客服）+ 质量档位要求——最可靠，写进入接入规范强制要求
  - 网关侧轻量推断兜底：输入长度分桶、语言检测、50ms 意图小分类器处理未打标流量
- 策略分层执行：准入（租户配额 / 场景白名单）→ 选档（难度标签映射模型档）→ 池内选择（健康度 × 剩余配额 × 成本加权轮询）
- 三个典型映射举例：摘要与分类 → 小模型池（成本优先）；实时代码补全 → 低延迟池（TTFT 优先）；复杂推理与长代码生成 → 大模型池（质量优先）
- 高级技巧——**prompt caching 亲和路由**：同系统提示前缀的请求固定路由到同一家供应商，命中供应商侧前缀缓存，成本能再降一截
- 档位边界不是永久的：小模型用上 GQA 后长上下文推理成本明显下降，档位映射要按季度重评——「路由策略是活的」这句话本身就是加分项
- 路由决策必须留痕：每次决策落一条日志（特征、命中规则、目标、事后指标），线上效果退化才能归因到具体策略

```text
一次路由决策的完整流水线（路由器自身只花 5ms）：

  请求 → 取虚拟 key 策略(本地缓存) → 场景标签(声明/推断兜底)
       → 准入校验(配额/白名单) → 档位映射(标签 → 模型池)
       → 池内打分(健康 × 余量 × 成本) → caching 亲和修正
       → 选定目标 + 决策日志落盘 → 放行到适配层
```

- 路由的冷启动：新业务没历史数据时按「保守档」起步（宁可贵不可错），跑一周有分布数据后再降档——「先对再省」是顺序，反过来省出来的都是事故
- 路由策略的灰度方法：新策略先对 5% 流量生效，对比完成率/成本/延迟三项指标，无回归再全量——路由策略本身也要当「发布」来对待
- 失败兜底路由：特征缺失或策略引擎超时（>50ms）时走「保守默认路由」（中档池）——路由器自己不能成为单点故障
- **收束一句**：路由器的价值 = 让业务方只声明意图、由平台代替它做最优选择——意图与策略分离，才是多模型时代的接入姿势
- ❌踩坑：路由逻辑写成散落各处的 if-else——策略要抽成规则/配置引擎，能热更新、能按租户灰度；只报「按成本路由」不讲特征怎么来，一句追问就哑口

**追问3**：级联升级（escalate）——小模型答不好，什么时候升大模型？

- 先讲为什么值得级联：大模型单价是小模型的 10~20 倍，但真实只有 10~20% 的请求需要它——让简单请求先走小模型，整体成本立降一个数量级
- **升级判定点四类信号**（这才是面试官真正想听的）：
  1. **自评置信低**：小模型输出附带自评分或对数概率，低于阈值触发升级
  2. **结构化失败**：要求 JSON 或工具调用参数，解析/校验失败，原地重试一次仍失败即升级
  3. **特征逃逸**：生成中途长度爆表、任务标签与实际内容明显不符（预分类器误判的长尾）
  4. **下游反馈**：用户点踩、下游校验器打回——异步升级重答并回流 badcase
- 升级要带 hint：把小模型的失败原因（低置信 / 格式错误点）作为提示传给大模型，比盲目重问收敛快、token 也省
- 关键取舍：级联 = 延迟翻倍（小模型白跑一趟 + 大模型从头答）——只对延迟不敏感、成本敏感的离线/半在线流量开启；实时链路靠预分类一步到位
- 监控指标：级联触发率，且按信号拆开看——置信类占比升高说明阈值该调，结构类占比升高说明小模型的 JSON 能力跟不上了

```text
升级判定阶梯（按判定成本从低到高依次过，命中即升级）：

  L1 结构校验失败(JSON/schema) ──原地重试1次仍败──→ 升级
  L2 自评置信 < 阈值(如 0.6) ─────────────────────→ 升级
  L3 长度逃逸(输出超预算 2 倍) ────────────────────→ 升级
  L4 下游打回/点踩(异步) ──────────────→ 重答 + 回流 badcase
```

- 阈值不是拍脑袋：拿历史标注集跑 ROC，选「误升级率 <10% 且漏升级率 <5%」的工作点，每季度用新分布重校一次
- 级联标记要进 trace：升级过的请求在轨迹里可见——评测时分开算「直达质量」与「级联后质量」，否则小模型的真实能力被大模型救场掩盖
- 级联与缓存的顺序：先查缓存再进模型——命中语义缓存的请求连第一次小模型调用都省了，优化叠加的顺序决定成本上限
- 级联的评测口径：升级后答案单独抽检——如果大模型救场后仍差，说明问题不在模型档位，在 prompt 或任务拆分，级联救不了设计缺陷
- **收束一句**：级联的本质是「用延迟换成本的保险」——保险费（小模型白跑）要算清，理赔条件（四类升级信号）要钉准
- ❌踩坑：只说「先小后大」不讲判定信号——「你怎么知道小模型不行」就是这道题的题眼；对实时流量也开级联，P95 直接翻倍，得不偿失

**追问4**：failover 与熔断——供应商挂了怎么切？

- 健康度三层探测：被动（滑动窗口错误率/超时率）+ 主动（周期心跳探针，防低流量时探不出问题）+ 慢启动（恢复节点逐步放量，防二次打挂）
- 熔断三态照搬后端：错误率 1 分钟窗口 >50% → 打开（该家流量全走池内其他家）；半开每 30 秒放 1% 试探；成功率回升 → 闭合
- 同档池化是前提：同能力档 2~3 家组成池，池内加权轮询，单家被熔断自动摘除——没有池化，「切换」就是一次手工事故
- **流式请求的特殊性**（做过才答得出）：SSE 已经吐出一半的请求无法无损重投——只能对「尚未输出首 token」的请求切换；已开流的要么硬着头皮收完，要么按业务语义中断重发
- 切换的静默代价：同档不同家的输出分布有差异——切换后下游结构化解析失败率会抖一下，要盯 15 分钟下游指标，必要时双跑对比
- 供应商限速（429）不算故障：这是配额管理问题，走 key 轮换与配额分摊，不要触发熔断——把「忙」误判成「挂」会让熔断器频繁误开

```text
熔断状态流转（单家供应商视角）：

  闭合 ──错误率>50%(1min窗口)──→ 打开(流量全切池内他家)
  打开 ──30s 后──→ 半开(放 1% 试探流量)
  半开 ──成功率>95%──→ 闭合(慢启动放量 10%→50%→100%)
  半开 ──试探仍失败──→ 打开(计时重置，等待下一轮探测)
```

- 熔断粒度选择：按「供应商」还是按「供应商 × 模型」？——选后者：一家的小模型挂了大模型未必挂；但粒度再细（再乘场景）会导致窗口样本不足频繁误判，两级刚好
- 预热连接池：切换目标后新建连接有冷启开销——适配层对每家保持最小连接池「常温」，切换才是真的快
- 熔断恢复的「黄金一分钟」：半开放量的节奏比阈值更重要——放量太快二次打挂、太慢白白损失流量，10%→50%→100% 三段式是实践出来的
- 跨家切换的计费陷阱：切换期间的半途请求两家都计费（一边已收了输入 token 的钱）——对账时单列这类双计费损耗，月度占比应压在 0.1% 以下
- 半开探测的流量真实度：探测要用真实小任务而不是 ping——只生成一个 token 的探活，探不出长文本能力劣化
- **收束一句**：failover 的目标不是「永不故障」而是「故障对业务无感」——池化让切换变成常态操作，而不是事故响应
- ❌踩坑：答「自动切备用」就停——熔断阈值、半开探测、流式中断语义三个硬细节少一个，都会被判定没做过生产

**追问5**：全部供应商都故障，怎么兑底？哪些任务**不能**自动降级？

- 兜底链按业务可接受度排序：
  1. **语义缓存回放**：高度相似的历史优质答案顶上（页面上标注「参考历史回答」）
  2. **排队 + 延迟承诺**：非实时任务进队列，供应商恢复后消费，告知预计时间
  3. **诚实拒答**：明确「暂时无法处理，请稍后重试」——宁可诚实，不可幻觉
- 但比兜底链更重要的是**降级边界清单**（高频追问点，主动说）：
  1. **合规红线类**：法务/医疗/金融决策建议——错误答案的代价不可逆，只能拒答，不能换小模型硬答
  2. **签约 SLA 的核心链路**：降档等于质量违约，切换决策要走人工流程，不自动
  3. **结构化关键输出**：代码生成、工具调用参数——小模型格式失败率高一截，降级可能引发下游连锁故障
- 边界的落地机制：场景标签 + **降级白名单**——「默认不降级、显式登记可降级」。反过来做（默认都降级），总有一天在合规场景翻车
- 故障演练：定期故障注入「全供应商不可用」，验证兜底链真的接得住、拒答话术真的触达用户——没演练过的预案等于没有

```text
降级白名单样例（配置即文档）：

  scene: legal_advice      allow_downgrade: false   # 合规红线，只许拒答
  scene: internal_summary  allow_downgrade: small    # 可降小模型
  scene: code_gen          allow_downgrade: none     # 结构化关键输出，不降
  scene: casual_chat       allow_downgrade: any + cache + queue
```

- 「兑底」的用户体验设计：拒答话术带「预计恢复时间」与「已排队位置」（如果有）——诚实但不冷冰冰，这既是产品细节也是工程指标
- 兜底期间的自愈探测：全故障时网关持续低频探活（每秒 1 个探测请求），恢复即放量——「什么时候敢切回来」和「什么时候切出去」同样重要
- 兜底期间的产品姿态：核心场景显示「降级中」状态标记，让下游知道自己拿到的是缓存或降档结果——静默降级会把质量问题变成信任问题
- **收束一句**：全故障兑底的三层（缓存回放/排队/诚实拒答）按「错误的可挽回性」排序——越不可挽回的场景，越早走到诚实拒答
- ❌踩坑：只答「切小模型兜底」——小模型一本正经答错比不答贵得多；「所有任务都能降级」是没出过事故的说法

**追问6**：多维限流——RPM/TPM/并发/租户预算四把尺子怎么同时生效？

- 四维各管一件事：**RPM** 稳调用频次（防刷）、**TPM** 稳 token 吞吐（供应商按这个限额）、**并发** 稳长连接（流式请求占坑不放）、**租户预算** 稳钱（月度硬顶）
- 实现：网关侧 Redis 滑动窗口/令牌桶，四维并行校验、任一超限即拒（429 + Retry-After + 告知命中的是哪把尺子）
- **token 计数的特殊难点**（QPS 限流没有这个问题）：请求进来只知道输入 token，输出 token 要生成完才知道——两段式计量：

```text
入口：预扣 = 输入token + 预估输出（按场景历史均值，如 0.4×输入）
出口：实扣 = 预扣 - 预估值 + 真实用量（回流校正差额）
夜间对账：累计偏差 > 5% → 重校该场景的预估系数
```

- 预算三级粒度：租户 → 项目 → 虚拟 key，逐级限额向上传导；水位 80% 告警、95% 拒新请求只放存量、100% 只放核心场景白名单
- 超限不是一刀切 429：高优先级排队、低优先级直接拒——优先级由业务方在虚拟 key 上声明，平台不替业务做价值判断
- 为什么并发要单独一把尺：流式请求时长 30 秒以上，RPM 低不代表连接少——RPM 100 但并发能打到 100，长连接把供应商出口占死
- 限流的返回设计：429 带上 Retry-After 与「命中的是哪个维度」，业务方才能做定向退避——是等一秒还是换档，答案完全不同
- 四把尺子的校准节奏：RPM/并发限额随供应商配额周级同步；TPM 预估系数夜间重校；预算按小时聚合滚动——尺子本身也要维护
- 限流键的设计：四维限流的 key = 租户 + 场景（不是用户）——按用户限会把大客户的内部并发放大成限流风暴
- 排队的设计细节：队列深度上限 + 预计等待时间估算（按当前吞吐）+ 超队剔除——排队不是无限等，是「有承诺的等」
- **收束一句**：四维限流的本质是把「钱、连接、频次、吞吐」四种资源分开管——一把尺子量四种资源，必然顾此失彼
- ❌踩坑：只按 QPS 限流——token 才是计费与配额的真实货币，一个长上下文请求顶一百个短请求；只做入口预扣不做出口校正，预算会被预估偏差腐蚀成摆设

**追问7**：虚拟 key 与密钥治理怎么做？

- 铁律：**供应商真实密钥只在网关的密钥保险仓里出现**（加密存储 + 定期轮换 + 最小可见范围），业务方永远拿不到——密钥泄漏面从 30 个仓库收窄到 1 个
- 虚拟 key 是发给业务方的凭证，它携带策略而不只是身份：租户/项目/场景、可用模型档位白名单、RPM/TPM/预算限额、调用来源限制
- 治理动作四件套：
  1. 定期轮换：虚拟 key 90 天，真实密钥跟随供应商策略
  2. 异常检测：某 key 流量形态突变（量级、时段、prompt 分布）→ 自动冻结 + 通知负责人
  3. 即时吊销：项目下线、人员变动，吊销一把 key 即断，不动供应商配置
  4. 权限审计：key 的创建/修改/使用全量留痕
- 附带收益：按 key 出账天然成立——成本归因的第一块积木就是虚拟 key

```text
一把虚拟 key 的字段清单（策略随身份走）：

  身份：租户 / 项目 / 场景 / 负责人
  能力：模型档位白名单、工具白名单
  限额：RPM / TPM / 并发 / 月度预算
  约束：来源 IP 段、生效期、环境(prod/test)
  审计：创建人、最近使用时间、最近轮换时间
```

- key 的分级治理：生产 key 与测试 key 物理隔离（不同网关集群或不同路由空间）——测试流量打挂生产配额是经典事故
- key 与人的映射：每把 key 必须有唯一负责人（离职即触发吊销流程）——孤儿 key 是成本泄漏和安全事故的头号来源
- key 的轮换仪式感：批量轮换选在业务低峰，新旧 key 双活 24 小时过渡——轮换本身不该造成可用性抖动
- **收束一句**：密钥治理一句话——真实密钥锁保险仓，虚拟 key 走天下；key 上绑的不是密码，是策略
- ❌踩坑：虚拟 key 只做鉴权不做策略——key 上不绑限额与模型白名单，治理就退化成「换了个地方放密码」；真实密钥进配置中心明文，是合规一票否决项

**追问8**：成本归因怎么做？怎么落到 Prompt 版本？

- 归因链路：虚拟 key（租户/用户/场景）+ 请求元数据（模型、真实 token、缓存命中、级联标记）→ 实时计量管道 → 明细落仓 + 聚合出账
- **Prompt 版本归因**是亮点：业务方调用时带 prompt 版本号，或网关对系统提示前缀做指纹哈希自动识别版本——「v2 砍掉了系统提示里的冗余示例，单次成本降 18%」这种结论，只有版本级归因才得出来
- 可观测：按 OTel GenAI 语义约定导出 span（请求/生成各一段，统一字段：token 数、模型、缓存命中、拒绝原因）——成本和 trace 拼在一张图上，「又慢又贵」的请求一查一个准
- 对账闭环：网关计量 vs 供应商账单 T+1 对账，差异 >1% 告警——供应商计费口径的坑很多（缓存折扣怎么算、失败请求计不计费），不对账的成本报表都是估算
- 数据要回流：归因明细反哺路由策略（哪个场景贵了 → 重评档位）、反哺缓存策略（哪类 prompt 重复率高 → 加语义缓存）

```text
成本归因的维度（一条计量明细行的字段）：

  时间 ─ 租户 ─ 用户 ─ 场景 ─ Prompt 版本
   └ 模型 ─ 输入/输出 token ─ 缓存命中 ─ 级联标记 ─ 当时单价快照
  → 聚合视图：租户月账单 / 场景成本排行 / 版本 AB 成本对比 / 异常探测
```

- 单价快照很关键：供应商调价频繁，明细行存「当时单价」——否则历史账单会被重算得面目全非，版本对比也就失真了
- 计量管道的技术形态：网关本地聚合（1 分钟窗口）→ 异步批量写明细仓——别为每个请求同步写库，计量本身不能拖慢数据路径
- 成本异常检测：租户/场景维度的日成本环比突增超 50% 即告警——多数根因是「prompt 改长了一大截」或「缓存集体失效」这类可修的问题
- **收束一句**：成本归因的终点不是账单是优化——每个归因维度都要能指向一个可执行的杠杆（档位/缓存/prompt 长度）
- ❌踩坑：只在网关记总账——归因到不了 Prompt 版本，成本优化就找不到抓手；完全信任供应商账单，自己的计量形同虚设

### 🎤 口述模板

> 我先澄清四个数字：接入业务数与日调用量、延迟与月预算约束、可用性目标、成本归因粒度。核心判断：这是「供应商治理 + 流量治理」的合体题——网关骨架可以平移后端经验，但计量单位从 QPS 变 token，故障域从自家服务变别家 API。
> 架构五层：接入层统一 OpenAI 兼容格式，业务零改造；治理链做虚拟 key 鉴权、四维限流（RPM/TPM/并发/租户预算）、入出参安全检查、三级缓存；动态路由器按场景标签与实时健康度分级到小/中/大模型池，离线流量开级联，小模型低置信升级大模型并带失败 hint；适配层同档池化、熔断三态、半开试探，流式请求只在首 token 前无损切换；计量层入口预扣出口校正，归因到租户、用户、Prompt 版本，按 OTel GenAI 语义约定导出。
> 两个边界主动交代：全供应商故障走「语义缓存回放 → 排队 → 诚实拒答」，合规红线类任务默认不自动降级；级联只开给延迟不敏感流量，代价是延迟翻倍。瓶颈通常在上游 TPM 配额，用多 key 聚合加跨供应商分摊消化。

### 一句话总结

LLM 网关的魂是「把模型变成可替换的组件」：协议归一让接入零成本，动态路由让钱花在刀刃上，池化熔断让供应商故障对业务无感，虚拟 key 与四维限流让治理有抓手——而全故障时的诚实拒答，永远比错误答案便宜。

## 题 7｜企业 Agent 平台（工具治理 + 沙箱 + HITL + 记忆基建）

> **一句话考察点**：怎么让「一个 Agent demo」变成「一百个 Agent 安全跑在生产」——工具注册与 MCP 治理、沙箱隔离、人工审批流、工作区越权防护、记忆基建、多租户隔离六件事，考的是把 AI 能力驯化成企业基建的工程判断。
>
> **考频**：⭐⭐⭐⭐（考频校准：「Agent 平台需要哪些模块」「Coding Agent 怎么防越权」高频出现，MCP 治理与审批流是二面深挖点）

### 需求澄清

不问不画，先问四组边界：

| 我问 | 面试官答（假设） | 对设计的影响 |
|---|---|---|
| 接入规模？业务方/Agent/工具数 | 15 个业务方，60+ Agent，200+ 工具，其中 20 个高危 | 平台化治理是主线，工具注册中心是地基 |
| Agent 能做哪些危险操作？ | 写代码并执行、改配置、对外发消息、动测试环境；日志里不许出现密钥与敏感信息 | 沙箱 + 审批流 + 边界校验三件套必须齐，脱敏进发布门禁 |
| 审批时效要求？ | 高危操作人审 SLA 30 分钟，超时有默认策略 | 审批不能成为吞吐瓶颈，必须异步挂起 |
| 记忆需求与红线？ | 跨会话记忆要，跨租户共享绝对禁止 | 短期/长期分层，过期与去重是深挖点 |

澄清后的核心判断：Agent 平台的主要矛盾不是「效果」而是「治理」——demo 到生产的距离，就是工具、沙箱、审批、记忆四道闸门的宽度。答这题每个模块都要挂一句「没有它会出什么事」。

四个边界对设计的推演：

- **200+ 工具、20 个高危**：决定了工具治理必须自动化——靠人审每一个工具注册不现实，描述质量门禁与兼容矩阵必须是机器跑的流水线
- **Agent 能写代码并执行**：决定了沙箱不是可选项而是地基，且网络外发控制比文件系统隔离更关键——数据偷走的通道是网络
- **审批 SLA 30 分钟**：决定了审批必须异步挂起，审批人路由与超时升级是吞吐瓶颈的解法——瓶颈在人的吞吐，不在算力
- **跨会话要、跨租户禁**：决定了记忆服务的隔离边界画在租户——读写都过租户上下文校验，这条红线硬编码，不开放配置
- **审批 SLA 30 分钟 + 高危 20 个**：决定了审批要去重合并与分组路由——审批额度是稀缺资源，运营思维与技术设计各占一半
- **日志合规（密钥与敏感信息不许出现）**：决定了脱敏必须在平台层统一做——业务方自行脱敏一定有漏网，这是合规一票否决项
- **15 个业务方、60+ Agent**：决定了接入面必须薄——注册到上线的路径越短，业务绕过平台的动机越小
- **20 个高危工具对 20 名审批人**：决定了审批要合并去重与白名单预授权并用——纯人审的天花板就是人的吞吐

澄清话术示范（开场 30 秒定调）：

```text
"我先按多租户平台澄清四组边界：接入规模、危险操作清单、审批时效、
记忆合规红线。整体思路：平台做『四道闸门』——工具治理管入口、
沙箱管执行、审批管高危动作、记忆管数据沉淀。demo 到生产的距离，
就是这四道闸门的宽度。"
```

### 架构图

```text
              【Agent 平台：注册 → 隔离 → 审批 → 记忆】
 业务方 ─→ 接入 SDK/DSL ─→ 编排执行引擎（Agent 循环）
                               │
        ┌──────────────────────┼──────────────────────┐
        ▼                      ▼                      ▼
   工具调用请求           代码/命令执行            上下文装配
        │                      │                      │
        ▼                      ▼                      ▼
  工具注册中心            沙箱集群（按需选型）      记忆服务
   ├ 描述质量门禁          ├ 容器/微VM：生态完整   ├ 短期：会话窗口
   │ （选对工具率>90%）    ├ gVisor：拦截系统调用  │  + prompt caching
   ├ 鉴权粒度              ├ WASM：毫秒级启动      ├ 长期：向量+KV
   │ （工具/参数/数据三级）├ 网络：默认拒绝+白名单 │  过期/去重/检索回忆
   └ 版本兼容矩阵          └ 配额：CPU/内存/墙钟   └ 跨租户绝对隔离
        │                      │
        ▼                      ▼
  策略引擎（危险分级）──→ 高危 → 审批服务（状态机）
   ├ 低危：直执行                挂起→通知→人审→放行/驳回
   ├ 中危：按租户策略            超时：默认驳回 + 升级提醒
   └ 边界校验：工作区/路径逃逸   审批内容：意图+影响面+diff
  全链路：审计日志（脱敏）→ OTel 轨迹 → 租户配额 → 账单
```

链路走读（边画边讲）：

1. **工具注册中心是唯一入口**：所有外部能力（含 MCP Server）必须注册才能被调用——旁路直连工具的 Agent 一律不准上线
2. **策略引擎在执行前**：每次工具调用先分级，低危直执行、高危进审批——分级规则集中管理，不散在各 Agent 里
3. **沙箱只管执行不管决策**：代码类动作全部进沙箱，网络白名单与文件挂载最小化是比沙箱技术本身更重要的防线
4. **审批服务独立部署**：它挂了高危任务全停（可接受），但不能让它拖垮执行引擎——故障域隔离
5. **记忆与执行分离**：记忆服务独立，Agent 重启不丢记忆；跨租户隔离在记忆服务里硬编码，不靠业务自觉
6. **审计贯穿全链**：谁（Agent/用户）、在什么任务里、调了什么工具、结果如何——四元组全留痕，出事能定责
7. **策略与执行分离**：分级规则在策略引擎集中管理，执行引擎只管跑——规则改了不用动引擎，审计时也有唯一规则源
8. **记忆的写入有门槛**：不是所有对话都值得记——「值得记」判定挡掉噪声，比事后清洗便宜十倍
9. **审批是资源不是功能**：人的吞吐有限，审批流设计本质是「怎么花最少的审批额度保最大的安全」
10. **注册中心是工具的唯一事实源**：Agent 运行时拿到的工具列表、鉴权策略、版本全部来自注册中心快照——本地缓存带 TTL，防止「已下线的工具还在被调用」
11. **预热池是代码类任务的延迟关键**：沙箱冷启秒级会拖垮体验——预热常驻 + 用完销毁，是隔离性与速度的折中
12. **审批服务与执行引擎解耦**：审批挂了高危任务全停、普通任务照跑——按危险等级划分故障域，不全线陪葬
13. **记忆服务不是强依赖**：记忆不可用时降级为「无记忆执行」——不让记忆成为整个平台的单点

四道闸门一句话总结（每道都能独立展开 5 分钟）：

| 闸门 | 管什么 | 核心机制 | 没有它会怎样 |
|---|---|---|---|
| 工具治理 | 能调用什么 | 注册中心三层门禁 | 工具越挂越多，Agent 越来越笨 |
| 沙箱 | 怎么执行代码 | 隔离 + 网络白名单 + 配额 | 一段恶意代码拖走全部数据 |
| 审批 | 高危动作 | 状态机挂起 + 超时默认驳回 | Agent 一时兴起删了库 |
| 记忆 | 数据沉淀 | 分层存储 + 过期去重 + 租户隔离 | 满脑子过时事实，还串了租户 |

### 关键设计决策表

| 决策点 | 方案 A | 方案 B | 方案 C | 选择与理由 |
|---|---|---|---|---|
| 沙箱技术 | 共享内核容器 | gVisor/微VM 系统级沙箱 | WASM 运行时 | 选 B 为主、C 为辅：B 拦截系统调用、生态完整，跑任意第三方代码；C 毫秒启动、能力裁剪，适合受控 DSL 与数据变换。A 只留给受信内部脚本 + 严配额。代价：B 冷启秒级，要预热池 |
| 审批模式 | 同步阻塞等人审 | 异步挂起 + 事件唤醒恢复 | 事前批量预授权 | 选 B：A 挂着连接等人，吞吐崩盘；C 批额一旦泄漏等于免检。B 的前提是执行引擎支持断点挂起（思路联动题 8）。C 可作为低频固定动作的白名单补充 |
| 长期记忆存储 | 纯向量库 | KV + 全文索引 | 分层混合：热 KV/向量 + 原文对象存储 | 选 C：向量管「想起相关的」，KV 管「取出完整的」，原文归档管审计回放——三个需求一种存储满足不了。代价：三套存储的生命周期管理 |

补充「为什么不选」（主动交代代价）：

- 不选「容器裸跑」：共享内核的容器逃逸案例一抓一把，跑模型生成的代码等于把攻击面交给概率
- 选 B（异步挂起）的代价：任务延迟受人的响应时间支配，所以审批超时策略和升级通道不是可选项是必选项
- 记忆选 C 的代价：一致性维护成本——原文删了向量还在，要有生命周期联动清理
- 沙箱选 B 的隐藏代价：gVisor 类运行时拦截系统调用有性能损耗（IO 密集任务可能慢两成以上）——CPU 密集的测试执行要实测再定，不能纸上选型
- 三个决策的共同点：都在「安全性 vs 吞吐」之间找工作点，且都配了一条逃生通道（预热池 / 白名单预授权 / 分层存储）对冲代价
- 三个决策共同回答一个问题：「安全边界画在哪，吞吐代价谁来付」——每个选择都显式给出对冲手段，比单说「选 X 更安全」高一个层次
- 一条暗线：三个决策都依赖「评测数据」做依据（工具选择率、逃逸测试、记忆效果 AB）——没有评测基建，平台决策全靠拍脑袋
- 最后一条工程直觉：任何「安全组件」本身也要高可用——沙箱池、审批服务、注册中心都按「挂了会怎样」设计降级路径

### 容量估算

整数近似，够用就行：

```text
执行账：
  60 个 Agent × 平均 500 任务/日 = 3 万任务/日，平均 8 步
  工具调用 ≈ 3万 × 8 × 0.6 ≈ 14 万次/日 ≈ 2 次/秒，峰值 ×10 = 20 次/秒
  代码执行类占 15% ≈ 峰值 3 次/秒
  沙箱：单次执行中位 20s → 并发占用 ≈ 3 × 20 = 60 个
  冷启动：容器/微VM 秒级 → 预热池常驻 80 个（60 + 余量），WASM 毫秒级免预热

审批账：
  高危操作占工具调用 5% ≈ 7000 次/日
  审批人 20 名 → 人均 350 单/日，平均响应 8 分钟 < SLA 30 分钟 ✓
  超时（30 分钟）默认驳回率预估 3% ≈ 200 次/日 → 需要升级提醒通道兜住

记忆账：
  短期会话：3 万任务 × 6 轮 × 4K token ≈ 7 亿 token/日
  　热存只留 24h 活跃会话 ≈ 100GB 级（正文 + 索引）
  长期记忆：100 万用户 × 50 条 × 500 字 ≈ 250 亿字
  　向量（1.5K 维 × 4B ≈ 6KB/条）+ 原文 ≈ 1TB 级
  过期策略：会话 7 天归档冷存 / 事实类 90 天复核 / 偏好类 180 天衰减

沙箱资源账：
  单沙箱 1C/512M，80 常驻 ≈ 80C/40G —— 两台高配物理机绰绰有余

审计与轨迹账：
  工具调用 14 万次/日 × 平均 2KB（脱敏后）≈ 280MB/日
  留 180 天 ≈ 50GB → 对象存储 + 按租户分区，检索走索引
  任务轨迹：3 万任务/日 × 30KB ≈ 900MB/日，留 90 天 ≈ 80GB

评测账：
  工具注册门禁：每工具 20 个任务 × 200 工具 = 4000 次评测（一次性）
  线上抽检：1% 任务全轨迹复核 ≈ 300 次/日（自动 + 人工抽查）
  发布门禁：平台升级跑 500 条金标轨迹 ≈ 每次发布 2 小时机器时间

演练账：
  越权攻防：每次发版跑「跨租户仿冒」自动化用例 200 条
  沙箱逃逸：季度红蓝对抗一次（靶机环境，不影响生产池）
  审批断供：月度演练「审批人全不在线」，验证默认驳回与升级链路
  记忆合规：季度演练「用户要求删除记忆」，验证三处联动清除
  降级演练：月度切断记忆服务，验证无记忆降级执行
```

**瓶颈结论**：瓶颈不在算力在**人的吞吐**——审批人均 350 单/日已接近上限，高危操作再涨一倍就要加审批人或收紧分级；其次是长期记忆的检索延迟，亿级向量必须走 ANN 索引。

**策略链**：审批排队超 SLA → 高危操作自动升级通知审批主管 → 长期无人审 → 默认驳回并通知发起方改走人工工单；沙箱池耗尽 → 排队 + 溢出降级到 WASM 受控执行（仅白名单任务）。

### 追问链

**追问1**：从零设计一个 Agent 平台，需要哪些模块？

- 先给总-分结构再展开：模块按「运行面 / 治理面 / 数据面」三组报，别一口气背十个名词——结构感本身就是得分点
- 运行面四件：
  1. **编排执行引擎**：Agent 循环（规划 → 工具调用 → 观察 → 再规划），支持挂起恢复
  2. **工具调用代理**：所有工具流量过注册中心与策略引擎，无旁路
  3. **沙箱执行集群**：代码类动作的隔离执行环境
  4. **上下文/记忆服务**：短期窗口管理与长期记忆的读写检索
- 治理面四件：工具注册中心（唯一入口）、策略引擎（危险分级）、审批服务（HITL 状态机）、审计与配额（多租户出账定责）
- 数据面三件：会话与轨迹存储（全量留痕、可回放）、记忆库（短期+长期）、评测集仓库（上线门禁与回归）
- 一句话收束：平台的价值不是「提供 Agent 框架」（开源一堆），而是「让业务方的 Agent 安全地跑在生产」——「安全上线」四个字，每个模块都为它服务

```text
模块清单速记（按三面报，每面一句职责）：

  运行面：执行引擎(Agent循环) / 工具代理(无旁路) / 沙箱集群 / 记忆服务
  治理面：工具注册中心 / 策略引擎(危险分级) / 审批服务(HITL) / 审计配额
  数据面：轨迹存储(可回放) / 记忆库(短长分层) / 评测仓库(上线门禁)
```

- 平台与框架的边界：框架解决「一个 Agent 怎么跑」，平台解决「一百个 Agent 怎么管」——接入面越薄越好，治理面越厚越好
- 上线流程把模块串起来讲：业务方注册工具（过门禁）→ 定义 Agent（绑工具与权限）→ 评测通过 → 灰度上线 → 全链路审计——串成流程比报清单高一个层次
- 数据面容易被漏掉的模块：版本与配置中心（Agent 定义、工具绑定、策略版本的集中管理与发布）——没有它，「哪个 Agent 用哪个工具版本」说不清
- 平台的接入成本是隐形指标：业务方从注册到上线超过一周，就会想绕过平台自己直连——接入体验是治理的护城河
- 多环境贯穿所有模块：test/staging/prod 三套隔离，且 prod 变更必须走审批——平台自己是被治理得最严的系统，这句话本身就是加分项
- 模块清单的变体问法：「缺了 X 还能不能跑」——用反证法检验模块必要性，也是答这类题的自检手段
- **收束一句**：报模块时带上「三面」（运行/治理/数据），每个模块一句话职责——结构化表达本身就是平台思维的证明
- ❌踩坑：按开源框架的功能清单背模块——面试官想听的是你按职责分层，且每个模块能说清「没有它会出什么事」

**追问2**：工具注册中心怎么治理 MCP 接入？——三层门禁

- 先一句话定位 MCP：把工具与数据源做成标准化 Server，Agent 作为 Client 统一发现与调用——**协议解决连通性，治理解决敢不敢接**，两件事分开说
- 第一层 **描述质量门禁**：工具名、描述、参数 schema 是模型看的「API 文档」——描述模糊 = 选错工具。上线前两道门：
  - 静态检查：命名规范、描述完整度、参数必填性与默认值
  - 动态评测：20 个典型任务跑一遍，工具选择正确率 >90% 才放行
- 第二层 **鉴权粒度**：工具级（能不能调）→ 参数级（能查订单但不能查手机号字段）→ 数据级（行级过滤，只看得见自己租户的）——MCP Server 侧不落地租户上下文，越权只是时间问题
- 第三层 **版本兼容**：schema 变更走语义化版本；平台维护「Agent 声明版本 ↔ 工具当前版本」兼容矩阵，破坏性变更强制新旧并行 + 旧版 sunset 时间表
- 附加一层：MCP 流量也过统一网关——鉴权/限流/审计在网关做，不信任 Server 自觉

```text
三层门禁速记：

  层          门禁问题              机器可查的部分
  描述质量    模型能不能选对工具    静态规范 + 20任务选择率>90%
  鉴权粒度    选对了能不能调用      工具/参数/数据三级 + 租户上下文
  版本兼容    改了会不会弄崩在用者  语义版本 + 兼容矩阵 + sunset
```

- MCP 的鉴权细节：Server 收到的每个调用必须带「调用主体链」（Agent → 任务 → 租户/用户）——三层上下文缺一层，事后审计就断链
- 私有 MCP Server 的额外要求：出网走代理、依赖白名单、资源限额——Server 本身也是要被治理的 workload
- 描述质量的持续运营：上线后每周跑「工具选择 badcase 回流评测」——描述漂移（业务语义变了描述没跟上）是注册中心的慢性病
- 工具下线流程：先标 deprecated（新 Agent 不可绑定）→ 通知存量使用者迁移 → 到期下线——直接删工具等于制造在线事故
- 第三方 MCP Server 的准入：安全评估（出网行为、依赖、数据驻留）+ 试用隔离区（只读工具先上）——外部组件一律按「不可信」对待
- 描述质量的度量口径：工具选择准确率要在「同类工具组内」算——全局平均会被简单工具拉高，掩盖真问题
- **收束一句**：MCP 三层门禁的共同逻辑，是把「人审接口」的老经验搬来管「模型调工具」——文档、权限、版本，一个都不能少
- ❌踩坑：只答「接上就能用」——没有描述门禁，工具越多 Agent 越笨；没有参数级鉴权，MCP 等于把内网接口裸奔给模型

**追问3**：代码执行沙箱怎么选型？容器 / gVisor / WASM 对比

- 先说选型维度再报结论：隔离强度、启动速度、生态兼容、资源开销四个维度权衡：

| 方案 | 隔离机制 | 启动 | 生态 | 适合 |
|---|---|---|---|---|
| 共享内核容器 | namespace/cgroup（共享内核） | 秒级 | 完整 | 受信内部脚本 |
| gVisor/微VM | 拦截系统调用 / 独立内核 | 秒级 | 完整 | 任意第三方代码 |
| WASM | 能力裁剪 + 线性内存 | 毫秒级 | 受限（需适配） | 受控 DSL、数据变换 |

- 选型逻辑落到场景：Coding Agent 执行仓库测试 → gVisor/微VM 级；报表 DSL、JSON 变换 → WASM；平台自家运维脚本 → 普通容器 + 严配额
- **三道附加防线不依赖沙箱技术**（漏答必扣分）：网络默认拒绝 + 域名白名单；文件系统挂载最小化（仓库只读 + 输出目录可写）；资源配额（CPU/内存/墙钟时间，防死循环烧钱）
- 冷启动优化：预热池——空闲沙箱常驻，任务来了秒级接管；用完销毁不复用（防状态泄漏攻击）
- 深度防御的排序逻辑：先网络（堵外带）、再文件系统（堵读取）、再配额（堵耗尽）、最后才是沙箱技术升级——越靠前的防线越便宜越通用
- 沙箱逃逸的应急剧本：发现逃逸迹象 → 立即熔断该沙箱池 → 快照留证 → 全量回扫受影响任务 → 复盘补防线——「逃逸响应」比「永不逃逸」是更现实的承诺
- WASM 生态受限的实情：不是所有语言与库都能跑，需要适配层——所以按「任务能不能改造进受控 DSL」倒推选型，而不是硬塞
- 沙箱镜像供应链：基础镜像统一构建、定期更新、签名校验——镜像被投毒比运行时逃逸更难发现，防线要前移到构建环节
- 执行结果的可信回传：沙箱内产出文件经哈希校验 + 病毒扫描再落工作区——不是跑完就算完成
- 沙箱池的隔离边界：不同租户的任务不共享沙箱实例（用完销毁），池只共享空闲容量、不共享运行态
- 沙箱日志也要治理：沙箱内执行的命令与产出摘要进审计——沙箱不是审计盲区，事后要能回答「它到底跑了什么」
- **收束一句**：沙箱题答「对比表 + 三道防线 + 选型逻辑」三层就够——面试官要的是判断框架，不是安全术语堆砌
- ❌踩坑：只说「用容器隔离」——共享内核逃逸历史一抓一把；「上了沙箱就万事大吉」——网络、挂载、配额三道防线不做，沙箱里发个外带请求照样能把数据带出去

**追问4**：危险操作人工审批流怎么设计？——状态机 + 超时策略

- 危险分级先行：低危（只读查询）直执行；中危（写操作、对外消息）按租户策略；高危（删数据、生产变更、资金操作）必须人审——分级规则集中在策略引擎，可按租户配置
- 审批状态机：

```text
执行中 ──遇高危动作──→ 待审批（实例挂起，上下文持久化）
                          │ 审批人路由：按资源 owner 找人，不是按发起 Agent
                          ├─ 放行 ──→ 恢复执行
                          ├─ 驳回 ──→ Agent 收到驳回原因，走替代策略
                          └─ 超时 ──→ 默认驳回 + 升级提醒审批主管
```

- 超时策略三选一：**默认驳回**（安全优先，推荐）/ 默认放行（绝对禁止）/ 升级审批人 + 延长等待——默认驳回必须配「Agent 的善后」：它得知道被拒了，且不能无限重试同一操作
- 防滥用两件套：同一操作的审批合并去重（批量场景一轮审批覆盖一批）；Agent 重复发起被拒操作 → 自动熔断该 Agent 的高危权限并告警
- 审批内容设计：给人看的卡片——操作意图、影响面、diff 预览、可回滚性，不是一坨原始 JSON——审批体验决定审批质量
- 审批人与受益人分离：审批人不能是发起任务的用户本人——自审自批等于没审，路由按资源 owner 而非发起者
- 可回滚性标注：每个高危动作注册时声明「可回滚 / 可补偿 / 不可逆」三档——不可逆动作（删库、对外打款）加一道双人复核
- 审批积压的运营指标：队列深度、平均响应、超时率三件套上看板——人的吞吐是瓶颈，要提前扩人或收窄高危范围，等爆了再说就晚了
- 审批分组路由：按工具类别路由到不同审批组（数据操作归 DBA、基础设施归运维）——通用审批池必然成为瓶颈
- Agent 侧的「审批前置」：规划阶段就标注高危步骤，任务提交时一次性预告——审批人有上下文，通过率高、反复少
- 审批数据回流：驳回原因结构化落库，月度分析 Top 驳回原因——多数是 Agent 的规划缺陷，修一次少一类
- 驳回后的替代路径要预设计：高危被驳回时给 Agent「合法 Plan B」（如改为生成草稿待人工执行）——没有替代路径，Agent 会反复撞墙
- **收束一句**：HITL 的目标不是「拦住所有危险」，是「用最少的审批额度拦住最贵的错误」——额度要花在刀刃上
- ❌踩坑：同步阻塞等人审——Agent 挂着几百个连接等人，吞吐崩盘；超时默认放行——等于没有审批，只是把责任推给了时间

**追问5**：工作区越权防护与日志脱敏怎么做？

- 越权分两类，分别拆解：
  - **纵向越权**（Agent 拿到不该有的权限）：最小权限 + 权限随任务发放、用完即收——不是给 Agent 一个长期高权限账号
  - **横向越权**（A 租户看到 B 租户数据）：任务启动时分配独立工作区；路径校验拦截 `../` 逃逸与符号链接逃逸；网络命名空间隔离
- Coding Agent 特有三条：仓库白名单（只能 clone 列表内的库）；分支保护（只能推 feature 分支，主干合并走平台）；命令黑白名单双轨（`rm -rf`、向外部发数据类命令直接拦）
- 日志脱敏：密钥、token、手机号、身份证号——入参与出参双端脱敏；trace 里的 prompt 含敏感信息时落「脱敏副本 + 密封原件」，解密原件要走审批
- 事故剧本推演：日志里出现供应商密钥 → 日志已被采集到三四个系统、删除追不回 → 所以**必须事前脱敏，不能事后擦**——把这个因果链说出来，面试官知道你真踩过坑

```text
Coding Agent 命令拦截双轨示例：

  黑名单（直接拦）：rm -rf /  curl/wget 外发数据  chmod 777  kill 系统进程
  白名单（默认拒其余）：git status/diff/commit  跑测试  ls/cat（限工作区内）
  灰区（转人工）：git push  安装新依赖  访问平台白名单域名
```

- 脱敏的实现位置：统一在日志/trace 的 SDK 出口做，规则中心化下发——每个业务自己写脱敏一定有漏网
- 「密封原件」的访问控制：解密要审批 + 留痕 + 有期限——安全需要看原文排障，但每次查看都是一次审计事件
- 工作区的生命周期：任务级创建、任务结束归档销毁——长期存在的共享工作区是越权与数据残留的温床
- 网络隔离的颗粒度：egress 代理按域名白名单放行，请求体过外发内容检查（含密钥特征即拦）——网络层做最后一道数据闸门
- 密钥的运行时分发：Agent 需要第三方凭证时发短时效临时凭证，不落配置文件——泄漏窗口从「永久」压到「分钟」
- 越权演练的攻击面清单化：路径逃逸、符号链接、环境变量注入、依赖混淆——列成清单才能回归，不然每次演练都在重复
- **收束一句**：越权防护一句话——纵向靠最小权限，横向靠工作区与网络双隔离，日志脱敏是最后的安全网
- ❌踩坑：只防路径逃逸不防网络外发——数据偷走的通道是网络不是文件系统；脱敏只在应用层做，中间件与网关的访问日志原样落盘

**追问6**：Agent 记忆系统怎么设计？——短期/长期/过期/去重/检索

- 短期 = 会话上下文：窗口管理（超出截断或摘要压缩），配 prompt caching 把重复前缀的成本打下来；存热存储，TTL 24 小时
- 长期 = 跨会话记忆：写入要过「值得记」的门槛——任务结果、用户偏好、明确的事实断言才存，不是每轮对话都往里塞
- **过期管理**三类时钟：事实类 TTL 90 天到期复核（「用户在 A 部门」半年后可能失效）；偏好类 180 天衰减（读取时降权，长期不读归档）；会话类 7 天转冷存归档
- **去重**两级：写入前向量近似查重（相似度 >0.92 判重，合并而非新插）；事实冲突检测——新旧矛盾以新为准，但保留变更链可回溯
- **检索式回忆**：不把全量记忆塞 prompt——按当前任务向量检索 Top-K（3~5 条）注入，每条带来源与时间戳；记忆量大之后，检索比全量塞又准又省
- 隔离红线：跨租户记忆绝对禁止共享；同一用户不同业务的记忆默认隔离、显式授权才可打通

```text
记忆分层与生命周期：

  层              存储                 生命周期
  会话短期        热缓存(24h TTL)      滚动窗口 + 超长摘要压缩
  任务中期        KV(7 天)             任务结束归档
  长期事实/偏好   向量+KV(90/180 天)   到期复核 / 衰减降权
  归档            对象存储(1 年)       只读，审计与回放
```

- 「值得记」的判定交给谁：小分类器 + 规则（任务结论 / 用户明确纠正 / 偏好表述），阈值宁紧勿松——存错比漏存危害大，污染的是后续所有回忆
- 记忆的权限随数据走：记住了用户手机号，取出时也要过参数级鉴权——记忆不是鉴权盲区，这条最容易被忽略
- 记忆与知识库的边界：记忆是「写回的个性化事实」，知识库是「只读的共享知识」——检索方式像，治理方式完全不同（前者按用户隔离，后者按租户共享）
- 记忆污染的防御：用户输入写入记忆前过校验（事实断言分类 + 敏感信息检测）——刻意污染记忆是新型攻击面
- 记忆的效果度量：A/B 对比有/无长期记忆的任务完成率与轮次——记忆系统也要有效果指标，不是存了就算
- 记忆的合规动作：用户请求删除时，向量、原文、备份三处联动清除——「可被遗忘」是记忆系统的合规底线
- **收束一句**：记忆系统三问——什么值得记、记多久、怎么取——三问答完，分层设计与生命周期自然浮出来
- ❌踩坑：把长期记忆当「聊天记录全集」——存储爆炸且检索噪声大；记忆只写不删不过期——半年后 Agent 满脑子过时事实，比没有记忆更糟

**追问7**：多租户隔离怎么做？——配额/限流/审计/故障域

- 四层各管一件事：**配额**（token/QPS/存储按租户硬顶）、**限流**（公平调度防大租户挤占）、**审计**（租户维度全操作留痕，出事定责）、**故障域**（某租户的失控 Agent 不能拖垮平台——按租户熔断）
- 数据隔离选型：共享库 + 租户 ID 行级过滤（省成本，中小租户默认）vs 独立 schema vs 独立库（大客户合规要求数据物理隔离）——按租户分级给，不是一刀切
- 嘈杂邻居治理：单租户并发上限 + 全局队列加权轮转；某租户重试风暴自动降级为串行执行——「一个租户的 bug 不让全平台陪葬」是平台题的收尾金句
- 审计日志独立存储、防篡改（追加写 + 定期校验和）——与业务日志分开放，出事时拿得出不可抵赖的操作链

```text
租户隔离四层速记：

  配额层：token/QPS/存储 三级硬顶，水位告警
  限流层：公平调度(加权轮转)，防大租户挤占
  审计层：全操作留痕，追加写防篡改
  故障域：按租户熔断，重试风暴自动降级串行
```

- 大客户物理隔离的成本线：独立库 / 独立集群只给「付费 + 合规」双要求的租户——隔离是分级商品，不是普惠设施
- 隔离要靠测试兜底：跨租户访问的自动化渗透用例进回归——每次发版跑一遍「A 租户仿冒 B 租户上下文」的攻击路径
- 配额的商品化视角：基础配额随套餐、弹性配额按需购买、突发额度短时借用——配额系统本质是资源计价系统
- 租户维度的成本可见性：每个租户能看到自己的用量与配额水位——透明是减少纠纷的最好手段
- 合规审计的「重放」能力：按租户导出任意时段的完整操作链（含审批与轨迹）——等级保护与行业合规检查都会要
- 租户生命周期联动：注销租户时配额释放、数据清理、审计归档三级动作——隔离设计要覆盖「退出」这个最后环节
- **收束一句**：多租户四层（配额/限流/审计/故障域）——前三层管「公平」，最后一层管「安全」，缺任何一层都会出大事
- ❌踩坑：只做逻辑隔离不做故障域隔离；审计日志与业务日志混存——定责时才发现关键操作被滚动日志冲掉了

**追问8**：Agent 可观测性与稳定性怎么落地？

- 三层看板：基础设施层（网关/沙箱/注册中心的常规指标）、Agent 行为层（任务完成率、工具调用成功率、审批通过率、重试率、空转率）、输出质量层（抽检违规率、用户点踩率）
- **轨迹回放**是 Agent 特有的观测手段：每次任务完整轨迹（每步输入输出与工具调用）落库，badcase 一键回放调试——Agent 的「日志」就是轨迹
- 埋点标准：按 OTel GenAI 语义约定组织 span（Agent span / 工具 span / 模型调用 span，统一 token 与模型字段）——平台与业务的观测数据能拼在一张图上查
- 稳定性三板斧：超时分级（模型调用 30s / 工具 10s / 审批挂起不计入执行超时）；重试预算（每任务最多 N 次，防重试风暴）；上游异常时的降级链（换工具实现 → 换模型档 → 任务挂起转人工）

```text
三层看板速记：

  基础设施：网关延迟/错误率、沙箱池占用、注册中心可用性
  Agent 行为：任务完成率、工具成功率、审批通过率、空转率
  输出质量：抽检违规率、点踩率、幻觉投诉率
```

- 空转率是 Agent 特有的金指标：工具循环转了很多轮没产出——烧钱且往往在死循环边缘，超阈值直接告警介入
- 回放调试的工程化：轨迹按 span 组织后，可以从任意一步「分叉重跑」（改 prompt / 换模型）做对照实验——轨迹不只是日志，是实验台
- 告警的分层路由：基础设施告警给平台值班、Agent 行为异常给业务负责人、质量劣化进评测看板——告警发错人就是噪声
- 上游升级的兼容验证：模型/工具升级先跑金标轨迹回归，通过率不降才放量——「上游一升级、下游全崩」是最常见的生产事故
- 成本可观测：每租户每场景的实时成本曲线 + 预算外推预测——月底才发现超预算，是成本管理的失败而非成功
- 观测数据的分级保留：实时指标 7 天、轨迹 90 天、审计 180 天——全量永久保留是成本灾难，分级才可持续
- **收束一句**：Agent 可观测一句话——基础设施看存活、行为看空转、质量看点踩，轨迹回放是终极手段
- ❌踩坑：只监控基础设施不监控 Agent 行为——服务全绿但 Agent 全在空转烧钱；轨迹不落库，badcase 无法归因只能靠猜

### 🎤 口述模板

> 我先按多租户平台澄清四组边界：接入规模、危险操作清单、审批时效、记忆合规红线。核心判断：Agent 平台的主要矛盾不是效果是治理——demo 到生产的距离，就是工具、沙箱、审批、记忆四道闸门的宽度。
> 运行面一个引擎：Agent 循环里每次工具调用先过工具注册中心——MCP 接入过三层门禁：描述质量（选对工具率大于 90% 才放行）、参数与数据级鉴权、版本兼容矩阵。代码类动作进沙箱：gVisor 类系统级沙箱跑任意第三方代码，WASM 跑受控任务，再叠网络白名单、文件只读、资源配额三道防线。危险分级后，高危操作进审批服务：状态机挂起实例、上下文持久化、按资源 owner 路由审批人，超时默认驳回并升级提醒。记忆分短期会话窗口配 prompt caching，长期记忆写入过「值得记」门槛，带过期时钟、向量去重和检索式回忆，跨租户绝对隔离。
> 全链路审计日志双端脱敏、轨迹按 OTel GenAI 语义约定落库、租户配额与按租户熔断防嘈杂邻居。容量上，沙箱预热池八十个常驻，审批人均三百五十单在 SLA 之内——瓶颈在人的吞吐，不在算力。

### 一句话总结

Agent 平台的魂是「安全上线」：工具治理管得住入口，沙箱管得住执行，审批流管得住高危动作，记忆基建管得住数据——四道闸门的宽度，就是 demo 到生产的距离。

## 题 8｜多 Agent 协作与 Workflow 编排（DAG + 状态持久化 + 断点恢复）

> **一句话考察点**：一个任务拆给多个 Agent，怎么让它们「分得开、聊得通、合得拢、断得起」——拆分判断、协作拓扑、通信与状态共享、冲突仲裁、Checkpoint 断点恢复、版本兼容六件事，考的是分布式思维在 AI 编排上的平移。
>
> **考频**：⭐⭐⭐⭐（考频校准：「多 Agent 协作：通信机制与状态共享」是协作类题的标准问法，LangGraph 式 State/Checkpoint 机制被多家直接追问）

### 需求澄清

不问不画，先问四组边界：

| 我问 | 面试官答（假设） | 对设计的影响 |
|---|---|---|
| 什么任务要拆？为什么拆 | 深度调研报告：检索+分析+写作+审校，单 Agent 上下文撑不住 | 拆分三问是第一决策点，拓扑选择第二 |
| 多少个 Agent？什么协作关系 | 4~6 个，允许试主从与辩论 | 拓扑与通信机制是主干问答 |
| 哪些节点必须人审？等多久 | 终稿发布前、外部发送类动作；SLA 15 分钟 | 人审节点的挂起语义必答 |
| 任务多长？失败语义是什么 | 30 分钟级长任务；不能整体重跑，中间态要能补偿 | Checkpoint + 幂等重放是核心考点 |

澄清后的核心判断：多 Agent 的价值在**隔离失败域与切片上下文**，代价是通信与状态复杂度——所以先用「拆分三问」过滤要不要拆，再谈怎么拆；长任务 + 不能重跑这两个约束，直接把「状态持久化与断点恢复」顶成全题重心。

四组边界对设计的推演：

- **「单 Agent 撑不住」是拆分理由**：检索、分析、写作、审校四类步骤的工具集与系统提示完全不同——拆分三问的第一问直接命中
- **4~6 个 Agent**：主从拓扑的 orchestrator 是标配；辩论只在终稿评审点开一轮，不会全图乱吵——拓扑数量级决定了复杂度还可控
- **人审 SLA 15 分钟**：挂起实例的定时器与升级通道要精确到分钟级；「修改后放行」要支持写回 State 并留痕
- **30 分钟长任务 + 不可整体重跑**：Checkpoint 粒度、幂等设计、补偿分支从「加分项」升格为「及格线」——这三个词必须出现在架构图里
- **允许试主从与辩论**：说明拓扑不是拍死的——设计里要留「节点类型」（含辩论节点）这类扩展位，而不是把拓扑焊死在代码里
- **中间态要能补偿**：说明外部副作用存在——补偿分支与可回滚性标注从第一天就要进流程定义
- **人审 SLA 15 分钟**：决定了挂起唤醒链路的延迟预算——审批动作到实例恢复要压在秒级，等待本身占大头

澄清话术示范（开场 30 秒定调）：

```text
"我先澄清四组边界：什么任务、为什么拆、哪些节点人审、失败语义。
整体思路：先用拆分三问过滤要不要拆；要拆就上 DAG——共享 State 做
唯一事实源，消息只传引用；每节点边界写 Checkpoint，配幂等重放，
挂了从断点爬起来；流程定义版本化，在途实例绑旧快照跑完。"
```

### 架构图

```text
        【多 Agent 编排：定义态 → 运行态 → 恢复态】
 流程定义（DAG，语义化版本 + 不可变快照）
   ├ 节点：规划器/检索/分析/写作/审校（各绑模型档与工具集）
   ├ 边：依赖 + 条件分支 + 补偿分支
   └ 人审节点：挂起语义（上下文+执行位置持久化）
        │ 发布：新版本只接新实例，在途实例绑旧快照
        ▼
 调度器 ─→ 执行实例（长任务 30min 级）
   ├ 共享 State（带 schema 的黑板，字段级 owner + 版本号）
   │   └ Checkpoint：每节点边界快照 → 状态存储
   ├ 消息总线：节点间只传引用与通知，不传全文
   └ 冲突仲裁：评审打分 → 主从裁决 → 平票升级人审
        │
        ▼ 节点执行（幂等：节点ID + 输入指纹 查重跳过）
   ├ 成功 → 写 Checkpoint → 调度下游
   ├ 失败 → 重试（指数退避 ≤3）→ 耗尽：跳过/换档/补偿分支
   └ 崩溃 → 恢复：加载最近 Checkpoint → 幂等重放
 人审节点：实例挂起（释放资源 + 定时器）→ 审批事件唤醒
   ├ 放行 / 驳回 / 修改后放行（修改写回 State 留痕）
   └ 超时：提醒 → 备选审批人 → 默认驳回归档
```

链路走读（边画边讲）：

1. **定义态与运行态分离**：流程是代码、实例是数据——这一分离是版本化与断点恢复的前提
2. **共享 State 是唯一事实源**：所有中间产物进 State，消息只做通知——恢复时只依赖 State，不依赖消息流
3. **Checkpoint 卡在节点边界**：节点内部（LLM 调用中途）不快照——不可中断续传，重跑即可，配合幂等不伤副作用
4. **幂等是重放的安全带**：节点执行前查「节点 ID + 输入指纹」是否已有成功产出，有则跳过
5. **人审是特殊的挂起节点**：实例进 suspended 态、资源释放、定时器计时——不是驻留内存干等
6. **补偿分支画在图里**：哪些动作可逆、怎么逆，在流程定义时声明，不是出事后现想
7. **版本快照不可变**：在途实例绑启动时的版本跑到底，新版本灰度只接新实例
8. **补偿分支是设计时产物**：哪些动作可逆、怎么逆，在流程定义时声明——出事后现想的补偿都不靠谱
9. **消息总线只传轻通知**：引用 + 事件类型，单条消息一 KB 以内——重了说明数据搬运走错了路
10. **调度器刻意保持「薄」**：只做图遍历与分发，不做业务逻辑——它越薄，挂掉重选的代价越小
11. **执行位置也存在 Checkpoint 里**：恢复的不只是数据还有「图上走到哪」——只恢复数据不恢复位置，等于白走一遍
12. **死信是运营入口**：每个 failed 实例都能从任意 Checkpoint 手动重放——兜底操作的工程化，而不是在日志里翻错误
13. **条件分支在图上不在代码里**：分支条件是声明式的（基于 State 字段判断）——改分支 = 改定义发版本，不偷偷改运行时
14. **补偿分支与主流程同图**：补偿不是隐藏逻辑，画在同一张 DAG 上——审图的人一眼看到「失败会怎么收场」

一个实例的状态生命周期（面试时可口头背，10 秒讲完）：

| 状态 | 含义 | 占用资源 |
|---|---|---|
| running | 节点执行中 | 计算 + 内存 |
| suspended | 人审 / 上游等待中 | 仅存储（状态 + 定时器） |
| failed | 策略耗尽进死信 | 仅存储（待人工重放） |
| done | 完成，轨迹归档 | 仅存储（只读） |

### 关键设计决策表

| 决策点 | 方案 A | 方案 B | 方案 C | 选择与理由 |
|---|---|---|---|---|
| 任务形态 | 单 Agent + 强工具 | 固定 Workflow（DAG） | 自由多 Agent 协商 | 选 B 为主：生产确定性第一，DAG 可视、可测、可恢复；C 只给探索型任务小范围开（不确定性与成本都高）。A 适合短链路——由拆分三问判定，不先入为主 |
| 通信机制 | 纯共享 State 黑板 | 纯消息传递 | State 为事实源 + 消息做通知 | 选 C：A 并发写冲突但易恢复；B 松耦合但状态碎片化、恢复要重放全事件。C 的关键是「消息只带引用不带全文」，两头的好处都拿到 |
| 状态持久化 | 全量快照（每步存全部） | 节点级 Checkpoint | 事件溯源（只存事件） | 选 B：A 状态大时写入放大严重；C 恢复要重放整条事件链，长任务太慢。B 在节点边界快照 + 幂等重放，RTO < 1 分钟、RPO = 0 |

补充「为什么不选」（主动交代代价）：

- 不选 C（自由协商）做默认：Agent 间对话轮次不可预测，成本与延迟都无法给业务方承诺——探索期用，稳定后固化成 DAG
- 选 C（混合通信）的代价：引用化要求所有中间产物有稳定 ID 与存储位置——「对象化」这一步省不掉
- 选 B（节点级 Checkpoint）的代价：节点内失败只能整节点重跑，LLM 的非确定性要用低温度 + 版本钉住来压漂移
- 不选事件溯源（C）的深层原因：LLM 节点的重放成本不对称——普通事件重放是毫秒级，这里的「事件」是一次模型调用就是几秒几毛钱，快照比重放便宜
- 混合通信（C）的代价量化：所有中间产物要走对象存储拿稳定 ID——多一次写入约 10ms，换恢复语义的大幅简化，这笔账算得过来
- 三个决策的共同约束是「可恢复性优先」：任务形态、通信、持久化怎么选，都以「挂了能不能从断点爬起来」为第一判据——这是长任务编排区别于普通系统的根本点
- 一条容易忽略的约束是「可解释」：三个决策都要能对着架构图讲清为什么——出故障时讲不清选择依据的平台，是不可运维的平台

### 容量估算

整数近似，够用就行：

```text
任务账：
  日均 5000 个编排任务 × 平均 12 节点 = 6 万节点执行/日
  单节点平均 40s（含 LLM 调用与工具执行）
  节点并发 ≈ 6万 × 40 ÷ 86400 ≈ 28，峰值 ×5 ≈ 140

Checkpoint 账：
  写入：每节点边界 1 次 ≈ 峰值 140 次/秒，单次状态 10~100KB
  → KV 存储（热）+ 对象存储（历史）分层，写入对 KV 是小菜
  恢复目标：RTO < 1 分钟（加载快照 + 重放未完成节点），RPO = 0（节点边界持久化）

状态账：
  单任务共享 State 平均 50KB（中间产物引用化，原文放对象存储）
  在途任务 2000 个 × 50KB = 100MB 热态 → 内存缓存 + KV 双写可行
  历史轨迹：5000 任务/日 × 50KB × 留 90 天 ≈ 22GB → 对象存储 + 索引

人审账：
  人审节点占比 10% ≈ 500 次/日，平均响应 15 分钟
  挂起实例并发 ≈ 500 × 15min ÷ 86400 ≈ 每时刻 5 个挂起
  → 量小，但状态必须持久化：发布重启不能丢任何一个挂起实例

LLM 成本账：
  单任务 12 节点 × 平均 3 次调用 × 3K token ≈ 10 万 token/任务
  5000 任务/日 ≈ 5 亿 token/日 → 分档路由（联动题 6）控成本

消息账：
  节点间通知：6 万节点/日 × 平均 2 条 ≈ 12 万条/日，单条 <1KB（只带引用）
  峰值 ≈ 30 条/秒 —— 普通 MQ 毫无压力，可靠性「至少一次 + 幂等消费」即可

调度器账：
  活跃实例 2000，挂起约 5，节点并发峰值 140
  调度决策 <1ms（内存图 + 状态缓存）→ 单调度器绰绰有余
  高可用：调度器主备 + 实例锁在 KV，切换 <10s —— 不是瓶颈，别过度设计

演练账：
  每月一次「杀掉调度器」：验证主备切换 <10s、实例零丢失
  每季度一次「Checkpoint 存储故障」：验证降级写入与恢复一致性
  版本发布例行：金标任务集跑通 + 5% 灰度 24 小时无回归才放量
  人审演练：季度验证「审批人失联」的升级与默认驳回链路
  补偿演练：对有副作用的任务注入失败，验证补偿分支真能回滚
```

**瓶颈结论**：瓶颈不在调度在 **LLM 调用的时长与成本**——节点并发 140 对调度器毫无压力，Checkpoint 写入 140 次/秒对 KV 也是小菜；钱和时间都烧在模型上，所以分档路由与失败策略（少重跑）就是成本策略。

**降级链**：上游模型限流 → 节点换低一档模型重试 → 仍失败 → 非关键支路跳过（标记降质）→ 关键路径挂起等待 → 长期不恢复进死信，人工从任意 Checkpoint 重放。

### 追问链

**追问1**：什么时候才真的需要多 Agent？——拆分三问

- **第一问：子步骤是否需要不同的系统提示/工具集/模型档？**——写代码和查资料的最佳配置完全不同，混在一个 Agent 里互相拖累、工具列表越挂越长
- **第二问：上下文会不会被撑爆？**——单 Agent 干全程，中间产物全堆在上下文里，注意力稀释 + 成本线性涨；拆开后各 Agent 只看自己需要的切片
- **第三问：失败域要不要隔离？**——检索挂了不该拖死写作；拆开才能对单点重试、降级、换档
- 三问都答「否」就老实单 Agent + 好工具——一个强 Agent 配一套好工具，多数场景比多 Agent 又便宜又稳
- 反向清单（不该拆）：线性短链路、强一致的小步骤、需要全局直觉的创意任务——拆了反而丢上下文
- 经验数字：步骤 >8、上下文 >50K token、工具 >15 个，才值得认真评估拆分

```text
拆分三问自查表（拿真实任务过一遍）：

  问题                       否               是
  需要不同提示/工具/模型档？   单 Agent         记 1 分
  上下文会超 50K token？       压缩/摘要能兜住   记 1 分
  失败域需要隔离？             一起挂能接受      记 1 分
  → 0 分单 Agent；1 分观察；2 分以上认真设计拆分
```

- 拆分的成本清单要主动报：通信开销（消息 + 状态同步）、调试复杂度（轨迹跨多个 Agent）、延迟（串行段叠加）、token 成本（角色提示重复注入）——四项起步都是翻倍
- 「工具数量」作为拆分信号的原理：工具列表本身占上下文，15 个以上时模型的选择准确率肉眼可见地下滑——这是实测经验不是理论推导
- 拆分的「粒度」陷阱：拆太细（每步一个 Agent）通信开销吞掉全部收益——经验值是 4~8 个 Agent 封顶，再细就该合并
- 单 Agent 的强化手段先穷尽：好工具（减少试错）、结构化规划（先列步骤再执行）、上下文压缩——这些都做了还不行，拆分才真正成立
- 混合形态最常见：一个主 Agent 带若干「工具型子 Agent」（检索/代码执行），对用户呈现单 Agent 体验——拆分是内部实现，不是产品形态
- **收束一句**：拆分三问的底层逻辑——多 Agent 是为「隔离与并行」付费，没有隔离与并行的需求，就不该付这笔钱
- ❌踩坑：为了「多 Agent」而拆——通信开销、状态同步、成本全部翻倍，效果反而降；面试官想听的恰恰是「默认单 Agent，三问通过才拆」的克制

**追问2**：协作拓扑怎么选？——主从/流水线/辩论/黑板

- 四种拓扑一张表说清：

| 拓扑 | 结构 | 强项 | 代价 | 适用 |
|---|---|---|---|---|
| 主从 | orchestrator 拆解分派，worker 汇总 | 可控、可审计 | 单点规划瓶颈 | 通用默认 |
| 流水线 | 上一步输出 = 下一步输入 | 延迟可预测、易并行 | 不易处理回环 | 翻译→审校→排版 |
| 辩论 | 多 Agent 独立作答再互批 | 降低单点幻觉 | 成本 ×N、轮次难控 | 高价值决策评审 |
| 黑板 | 共享状态区各取所需 | 结构灵活 | 并发协调复杂 | 多专业协作 |

- 生产推荐混合形态：主从做骨架，局部嵌流水线（并行检索多个源），关键决策点加一轮辩论（两个评审 Agent 互批后裁决）
- 辩论要设收敛控制：最多 2 轮互批，超轮次或超时强制进裁决——否则两个 Agent 能吵到预算烧完
- 拓扑与可观测性挂钩：主从天然有汇总点便于审计；辩论的每轮互批都要进轨迹——拓扑选择直接影响「出事后能不能查」
- 动态拓扑的诱惑要顶住：让 Agent 自己商量谁干什么（自由组队）演示很酷、生产是灾难——结构不确定 = 延迟不确定 = 无法给业务方承诺
- 流水线的并行变体：同层多 Agent 并行（三个检索 Agent 查不同源）再汇合——「宽流水线」是检索增强场景的常用形态
- 拓扑选择的决策顺序：先看任务结构（线性→流水线、可分解→主从、要质询→辩论），再看延迟预算，最后看成本——顺序反了会被酷炫拓扑带偏
- 拓扑写进流程定义而不是运行时涌现：图结构是声明式的，运行时只做调度——「动态选拓扑」只存在于规划节点内部，不存在于图层面
- 拓扑与成本的速算：辩论 = 该节点成本 ×(2N-1)（N 个独立作答 + 互批）——所以辩论永远只放在少数关键节点
- 拓扑的演进路径：先单线跑通 → 主从拆分 → 局部并行 → 关键点加辩论——一步画满拓扑图是纸上谈兵
- **收束一句**：拓扑四选一口诀——线性走流水线、可拆走主从、高价值加辩论、不确定上黑板
- ❌踩坑：上来选「平等自由协商」——不确定性爆炸，token 烧不起也没法调试；只报拓扑名不讲适用场景，等于没答

**追问3**：通信机制与状态共享怎么做？——共享 State vs 消息传递

- 两条路线先对比：**共享 State**（黑板模式，所有 Agent 读写同一份带 schema 的状态）——全局一致、易持久化恢复、易审计；缺点是并发写冲突与 schema 演进。**消息传递**（点对点/订阅）——松耦合、易跨服务；缺点是状态碎片化，恢复要重放消息流
- 生产推荐混合，一句话原则：**State 是唯一事实源（SSOT），消息只做通知、不做数据搬运**
- 落地三件套：
  1. 消息里带引用（state 路径 / 对象 ID）不带全文——避免同一份中间产物五六个副本对不上账
  2. State 字段级所有权：每个字段一个 owner Agent，别人只读
  3. 乐观锁版本号：并发写同字段冲突时后写者重读重试
- 消息可靠性：通知丢失的后果 = 下游晚启动，不是数据丢（数据在 State）——所以消息层用「至少一次 + 幂等消费」就够，不必上事务消息

```text
SSOT 落地三规则（缺一条就退化成消息传递）：

  ① 中间产物只写 State（带 owner 字段与版本号）
  ② 消息体 ≤1KB，只含引用（state 路径/对象ID）与事件类型
  ③ Agent 本地不留跨节点状态——重启后从 State 重建
```

- schema 演进管理：State 字段带版本注释，破坏性变更走迁移函数——与 API 版本化同构，后端经验直接平移
- 通信与拓扑的耦合关系：主从天然适合 SSOT（都经过 orchestrator）；对等协商才更依赖消息——先定拓扑再定通信，顺序反了会来回改
- State 的 schema 设计原则：字段少而稳（任务、产物引用、审校意见、状态标志）——「经常变的」放对象存储用引用指，State 本身要像数据库表一样被设计
- 引用的解析与失效：消息里的引用带版本号，读取时校验——防止「读到已被下游覆盖的中间态」
- 通信的追溯性：所有消息与 State 变更进同一条时间线（轨迹）——复盘时能还原「谁在何时基于什么做了什么」，审计与调试共用这一条线
- **收束一句**：通信机制一句话——State 管事实、消息管通知、引用管指向；三者各司其职，恢复与审计才有唯一依据
- ❌踩坑：消息里传全文——副本不一致是必然的；「通信机制」只答用哪个 MQ——考的是语义设计（谁拥有数据、怎么防冲突），不是中间件选型

**追问4**：多个 Agent 结论冲突，怎么仲裁？

- 先分类再给机制：**事实冲突**（数字、结论不一致）与**方案冲突**（两条路线之争）——前者靠证据裁决，后者靠目标裁决
- 仲裁阶梯（逐级升级）：
  1. **检测**：结构化输出对齐到可比字段，diff 出分歧点——冲突检测本身要自动化
  2. **轻量裁决**：第三方评审 Agent 打分并给理由
  3. **主从裁决**：orchestrator 按任务目标拍板——冲突最终要有一个人格化责任者
  4. **平票/高危升级人审**：裁决不了或影响大的，进人审节点
- 辩论模式的收敛控制再强调：最多 2 轮互批 + 超时强制裁决——「让它们再聊聊」不是策略是祈祷
- 裁决留痕：为什么采信 A 不采信 B，写进任务轨迹——人审复盘与仲裁策略优化都靠它

```text
仲裁阶梯（成本递增，逐级升级）：

  L0 自动检测：结构化对齐 + diff 分歧点（机器，毫秒级）
  L1 评审 Agent：第三方打分 + 给理由（一次模型调用）
  L2 主从裁决：orchestrator 按任务目标拍板
  L3 人审：平票 / 高影响 / 不可逆决策
```

- 事实冲突的快速通道：两边都给了来源引用时，先比「证据有效性」（时效、权威度）——很多冲突在证据层就解了，不必上升到裁决
- 冲突是信号：高频冲突的任务说明拆分边界画错了（两个 Agent 职责重叠）——复盘时把冲突率当拆分质量的反向指标
- 证据优先原则：能靠检索证据裁决的（两结论各自带来源）不靠模型打分——证据比对是确定性操作，比评审 Agent 便宜且可解释
- 仲裁者的独立性：评审 Agent 不能与被评审者共享上下文（防立场污染）——独立实例、只看两份结论与任务目标
- 冲突率的健康线：长期低于 2%；突增通常是上游检索质量劣化（两边拿到了不同证据）——冲突的根因有时不在 Agent 在数据
- 仲裁结果的置信标注：裁决后的结论带置信与分歧摘要——下游（和人）要知道这是「一致通过」还是「勉强裁决」
- **收束一句**：仲裁阶梯的本质是把「分歧」逐级升级为「更贵的确定性」——机器 diff 最便宜，人审最贵也最确定
- ❌踩坑：仲裁无留痕，出了错无法归因；让两个 Agent 无限互批——成本指数级上涨还未必收敛

**追问5**：DAG 节点状态怎么持久化？怎么断点恢复？——Checkpoint + 幂等重放

- 为什么必须持久化：30 分钟级长任务，进程重启 / 发版 / 机器故障不能让任务从头再来——LLM 调用是真金白银，重跑一次就是钱打水漂
- **Checkpoint 设计**：每个**节点边界**把「共享 State + 执行位置（图上走到哪）」快照落 KV/对象存储；节点内部不快照——LLM 调用中途不可续传，整个节点重跑即可
- 可以提 LangGraph 的思路对齐概念：State 是带合并函数（reducer）的类型化结构——写入是「合并」不是「覆盖」；Checkpoint 按步持久化，恢复 = 加载最近检查点继续执行图——它把「断点恢复」做成了框架能力，自研时照这个语义设计即可
- **幂等重放**：节点执行前先查「（节点 ID + 输入指纹）是否已有成功产出」，有则跳过——重放不会重复外部副作用；对外工具调用带请求 ID 去重（联动题 7 工具幂等）
- LLM 节点的非确定性：同样输入重跑结果可能不同——接受它，但钉住模型版本与低温度，把漂移压到最小；对「结果必须可复现」的节点，存产出而不是依赖重跑
- 恢复流程：调度器发现实例失联/宕机 → 抢占锁 → 加载最近 Checkpoint → 从断点继续调度（未完成节点重跑，幂等保副作用）

```text
一条 Checkpoint 记录的字段：

  实例ID / 版本快照ID / 节点ID / 输入指纹
  共享 State(全量或增量) / 执行位置(图上走到哪条边)
  重试计数 / 开始时间 / 累计耗时 / 结果状态
  → 恢复 = 按实例ID取最新一条 → 校验版本兼容 → 继续调度
```

- 增量 vs 全量：State 小（百 KB 内）全量快照最省心；大了改增量（记 diff），恢复时重放 diff 链——本题规模全量够用，别过早优化
- 存储选型跟着读写模式走：热 Checkpoint 进 KV（按实例 ID 读写），完成实例的归档轨迹转对象存储——不是反过来为了用某个存储去改设计
- 节点开始前也写「执行意图」（含输入指纹）：崩溃时能区分「没开始」与「开始了没完成」——两种状态的重放策略不同
- 幂等键的稳定性：输入指纹要对「语义输入」哈希（排除时间戳类噪声字段）——否则重试一次指纹就变，幂等直接失效
- 轨迹与 Checkpoint 的关系：轨迹是「追加的执行日志」给人看，Checkpoint 是「可恢复的状态快照」给机器用——两种模型别混用一个存储
- Checkpoint 的安全边界：含敏感信息的中间结果加密存储、解密走权限——断点恢复不能变成数据泄漏的后门
- **收束一句**：断点恢复一句话——节点边界快照 + 幂等重放，RTO 一分钟、RPO 零；这两个数字说出来，这题就稳了
- ❌踩坑：只持久化最终结果不持久化中间态——恢复等于全量重跑；节点不做幂等，重放时发消息、下单这类副作用重复执行——这是本题最重的那个坑

**追问6**：人审节点怎么设计？——状态挂起 vs 事件唤醒

- **状态挂起**：实例进入 suspended 状态——全部上下文与 Checkpoint 持久化、调度器释放计算资源、定时器开始计时；不是把实例驻留内存干等（发版重启全丢）
- **事件唤醒**：审批动作产生事件（放行/驳回/修改后放行）→ 调度器加载 Checkpoint 恢复执行；事件本身要持久化——审批发生在平台宕机窗口时，恢复后事件不丢
- 超时策略阶梯：SLA 过半提醒 → 超时转交备选审批人 → 长期挂起（>24h）任务归档并通知发起方——「默认驳回」是安全兜底，但要给人留足梯度
- 审批粒度两档：批节点（这一步过不过）vs 批内容（人改完再放行）——后者要把修改写回 State 并记录修改人，否则轨迹断链
- 挂起实例的资源模型：挂起不占算力只占存储——所以「每时刻挂起 5 个」这种量级毫无压力，压力全在人的吞吐

```text
人审挂起-唤醒时序：

  节点触发人审 → 写 Checkpoint → 实例置 suspended
    → 释放计算资源 → 注册定时器(SLA 提醒/超时升级)
    → 审批事件(先持久化) → 调度器加载 Checkpoint
    → 校验审批与实例匹配 → 修改写回 State(留痕) → 继续执行
```

- 事件与实例的匹配校验：审批事件带实例 ID 与节点 ID，防止「批了 A 任务却唤醒了 B」——审批并发时的张冠李戴是真实事故模式
- 挂起期间的上下游状态：上游节点已完成（结果安全躺在 State 里），下游全部未启动——挂起的代价是尾部延迟，不是数据风险
- 挂起的超预算保护：人审等待计入任务总时长预算，超总预算自动终止——防「僵尸任务」无限挂起占存储
- 审批通道的多入口：网页审批台 + 即时消息卡片审批——审批人在哪审批就推到哪，响应时间差三倍
- 批量审批：同类动作（同一任务的十个文件修改）合并为一张卡片，一次批一批——审批额度是稀缺资源，省着用
- **收束一句**：人审节点一句话——挂起要持久化、唤醒靠事件、超时有阶梯；把「等人」做成可恢复的资源调度问题
- ❌踩坑：挂起实例驻留内存——一次发布重启全部丢失；审批事件走内存回调不持久化——审批完了任务却找不到，两头对不上账

**追问7**：节点失败怎么办？——重试/跳过/补偿分支

- 三板斧各有适用条件，**在流程定义里按节点声明**，不运行时拍脑袋：
  1. **重试**：瞬时故障（超时/限流）——指数退避 + 抖动，上限 3 次；对外部写操作重试前必须确认幂等
  2. **跳过**：非关键支路（可选增强项）失败——标记降质继续，最终结果注明「少了什么」
  3. **补偿分支**：已产生副作用的失败——消息撤回、资源清理、状态回滚；可逆性在节点注册时就要标注
- DAG 级失败传播：单节点重试耗尽 → 看下游依赖——无依赖支路继续跑（部分完成也有价值），关键路径失败 → 整体进失败处理（人工介入 / 补偿 / 重新调度）
- 死信与告警：进死信的任务带完整轨迹与最近 Checkpoint，支持一键从任意断点手动重放——人工兜底的操作台要现成
- 成本视角：失败策略就是成本策略——少整体重跑、多断点续跑，30 分钟任务的「重跑」与「续跑」差的是真金白银

```text
节点失败策略声明（流程定义里每个节点都要填）：

  节点        重试    失败后              副作用
  检索        3 次    跳过(标记降质)      无
  分析        3 次    换模型档重跑         无
  写作        2 次    挂起转人工           无
  外部发送    2 次    补偿分支(撤回)       有(不可逆部分双人审)
```

- 重试必须加抖动：多实例同时失败同时重试 = 对上游的定向脉冲——指数退避 + 随机抖动，是礼貌也是自保
- 「跳过」的用户可见性：最终产物注明缺了哪块（「数据源 B 不可用，本报告未含…」）——静默降质是信任杀手
- 失败根因分类先行：瞬时（超时/限流）重试、逻辑（参数错）不重试直接降级、系统性（上游故障）熔断——不分类的重试是把头埋进沙子
- 部分完成的交付语义：跳过支路后的「降质交付」显式标注——下游拿到的永远是「带质量标记的完整结构」，不是缺字段的惊喜
- 死信的运营化：死信有看板、有认领、有 SLA，堆积超 50 单自动升级——死信不是垃圾桶，是待办清单
- **收束一句**：失败策略一句话——瞬时重试、逻辑降级、系统熔断；每节点的策略在定义时声明，运行时只执行
- ❌踩坑：全局统一「失败重试 3 次」——对外部写操作重试等于重复副作用；「失败就整体重跑」——烧钱且把已完成的正确工作全部作废

**追问8**：流程定义要迭代怎么办？——版本化与在途实例兼容

- 为什么这是必答题：流程定义就是代码，一定会改——加了审校节点、换了模型档、改了 State 字段，在途任务怎么办？
- 版本化机制：流程定义带语义化版本 + **不可变快照**（每次发布物化一个版本）；**在途实例绑定启动时的版本快照跑到结束**，新版本只接新实例——一条铁规避免「改着改着把跑着的任务改崩了」
- 兼容性难点在 Checkpoint 结构变化：State 加了字段——旧实例恢复时跑 schema 迁移（默认值/迁移函数）；工具接口变更走工具注册中心的兼容矩阵（联动题 7）
- 灰度发布：新版本按实例比例放量（5% → 50% → 100%），对比完成率、成本、耗时三指标——流程定义的灰度和服务发布的灰度是同一套思路
- 存量收敛：旧版本设 sunset（在途跑完 + 不再接新），超期强制迁移并人工复核

```text
版本兼容矩阵（注册中心维护，发布前必查）：

  流程版本     State schema    工具版本       在途实例处理
  v1.2 → 1.3   加可选字段      兼容           在途绑 v1.2 跑完
  v1.3 → 2.0   删改字段        破坏性(v2)     新旧并行 + sunset 30 天
                                              超期未收敛 → 人工迁移
```

- 在途实例的观察窗口：发布后盯「旧版本实例完成率」——长期跑不完的旧实例往往是被新版本的工具变更暗伤，别等用户投诉才发现
- 流程回滚也是版本操作：出问题回滚 = 把旧快照重新发布为新版本号，在途实例不动——「回滚」与「热更」走同一套机制，不搞特权通道
- 版本化的测试基线：每个版本带一组「金标任务」，发布前在新版本上跑通——版本不是换个标签，是带证据的变更
- 在途实例的迁移判断：sunset 到期时按进度分流——进度超八成的加速跑完、不足八成的评估迁移，一刀切浪费已投入的计算
- 回滚的数据兼容：回滚版本要能读新版本写的 State（前向兼容字段）——回滚比升级更容易踩 schema 坑，因为没人提前设计「倒退」
- 版本发布的检查单：兼容矩阵已查 / 金标已跑 / 灰度计划已定 / 回滚预案已备——四项全绿才准发布
- **收束一句**：版本化一句话——定义不可变、在途绑快照、变更走灰度、回滚同机制；四条守住，流程迭代就不怕在途任务
- ❌踩坑：流程定义原地热更——在途实例的 Checkpoint 与新定义对不上，恢复即崩溃；只留 latest 不留历史版本——出问题想回滚时无门

### 🎤 口述模板

> 我先澄清四组边界：什么任务、为什么拆、哪些节点必须人审、失败语义是补偿还是重跑。核心判断：多 Agent 的价值在隔离失败域与切片上下文，代价是通信与状态复杂度——所以先用拆分三问过滤：子步骤是否需要不同配置、上下文会不会撑爆、失败域要不要隔离；三问不过就老实单 Agent 加好工具。
> 要拆就上 DAG 编排：拓扑以主从为骨架、局部嵌流水线、关键决策点加辩论；通信的原则是「共享 State 为唯一事实源，消息只带引用做通知」，字段级 owner 加乐观锁防写冲突；结论冲突走「检测→评审打分→主从裁决→平票升级人审」的仲裁阶梯，裁决全程留痕。
> 韧性三件套：每节点边界写 Checkpoint，节点幂等靠「节点 ID 加输入指纹」查重，恢复就是加载最近检查点再幂等重放，RTO 一分钟、RPO 为零；人审节点状态挂起、事件唤醒，审批事件持久化防丢；失败按节点声明策略走重试、跳过或补偿分支。流程定义语义化版本加不可变快照，在途实例绑启动版本跑完，新版本灰度只接新实例。

### 一句话总结

多 Agent 编排的魂是「断得起」：拆分三问决定要不要拆，拓扑与通信决定怎么协作，Checkpoint 与幂等决定挂了能不能从断点爬起来——能从任意断点恢复的编排，才敢把半小时的长任务交给它。
