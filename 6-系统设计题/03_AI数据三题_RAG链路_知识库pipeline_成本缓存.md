# 03 | AI 数据与成本设计三题（RAG 全链路 · 知识库流水线 · 成本与缓存）

> **定位**：AI 数据侧 + 成本侧的系统设计三连题。「完整介绍 RAG 链路 + 延迟/成本优化」是当前出现率最高的 AI 设计大题；知识库入库流水线是 ETL 老经验直接迁移的主场；Token 成本与缓存体系是「业务跑起来之后」的必答题——三题串起来正好覆盖「建知识库 → 喂数据 → 控账单」的完整生命周期。
> 三题共用同一骨架（需求澄清 → 架构 → 决策表 → 容量 → 追问链 → 口述），每题都带整数容量账与踩坑标记。

## 本章导读

**考察定位**：RAG 全链路 + 延迟/成本优化是最高频设计题；chunk size/重叠度、混合检索、rerank 特征权重、embedding 选型是稳定追问；幻觉缓解的分层答法（提示词 → 工具 → RAG → 微调）全站最高频；KV Cache 为什么能降成本、Prompt 静态/动态排列、语义缓存适合哪些请求、Token 消耗过快怎么排查，均已被真实考到。答好这三题，AI 数据与成本维度的系统设计基本闭环。

**三题知识地图**：

```text
AI 数据与成本三题（母题 → 核心链路 → 衍生追问）
│
├─ 题9 RAG 全链路设计 ····· 检索侧母题（百万 → 千万文档）
│    ├─ 核心链：chunking → 混合召回 → RRF 融合 → rerank → 生成
│    ├─ 权衡点：延迟预算分配 / 质量vs成本 / 分片副本 / 热温冷
│    └─ 追问延伸：幻觉分层缓解 / 软删除墓碑 / 多租户隔离 ★

│    ├─ 核心链：多格式解析 → 切块 → 质量门禁 → 向量化 → 入库
│    ├─ 权衡点：增量 vs 全量（蓝绿双索引）/ 幂等 / 死信重试
│    └─ 老经验迁移：这就是一条标准 ETL 管道，套路全复用
│
└─ 题11 Token 成本与缓存 ·· 成本侧母题（月账单 50万 → 10万）

     ├─ 权衡点：命中率 vs 幻觉风险 / 时效与权限隔离

```

**与 L9 知识库题的定位差异**：L9 的知识库 walkthrough 是入门六步法，场景停在百万级、单租户、理想数据；本题组是**规模化工程化升级**——千万 chunk 的分片分层与增量更新、月级入库吞吐的流水线治理、真实账单的归因与熔断，全部带数字、带代价、带踩坑。面试只给 15 分钟按 L9 六步法走；给足 40 分钟或有追问压力，用本题组的深度打。

**三条答题心法**：

1. **链路题先给全景再谈优化**：最忌一上来抠 chunk 细节——先 30 秒画完「切块 → 召回 → 重排 → 生成」骨架并报出各段延迟预算，再等面试官挑段深挖。
2. **每个优化必须报数字**：延迟从多少 ms 降到多少 ms、月账单从多少降到多少、命中率多少——没有数字的优化叙述等于没答。
3. **数据侧经验是转型者的主场**：入库流水线本质是 ETL，幂等、死信、对账、蓝绿切换全在老工具箱里，主动点破「这就是我熟悉的大数据管道模式」，把转型劣势打成主场优势。

## 题 9｜RAG 全链路设计：百万 → 千万级文档，含延迟与成本优化

> **一句话考察点**：文档量从百万涨到千万，检索质量、P95 延迟、推理成本三件事如何同时保住——切块、混合检索、重排、向量库分片、热温冷分层、增量更新的合奏，外加一道必考的幻觉缓解分层答法。
>
> **考频**：⭐⭐⭐⭐⭐（考频校准：AI 系统设计出现率第一的母题，「完整介绍 RAG 链路 + 延迟/成本优化」是最高频形态；一面考链路骨架与延迟分配，二面考 chunk 权衡与向量库容量，三面考多租户隔离与幻觉治理）

### 需求澄清

不问不画。规模与延迟不同，链路完全不同：

| 我问 | 面试官答（假设） | 对设计的影响 |
|---|---|---|
| 文档量级与增速？ | 现有 300 万文档，年内到 1000 万；短文档为主（公告/FAQ/工单），均篇约 2 页 | 千万文档 ≈ 千万级 chunk，向量单机内存放不下 → 必须分片 + 副本 + 分层，容量账先算 |
| 在线还是离线？P95 红线？ | 在线问答，P95 ≤ 2s | 召回/融合/精排/生成逐段切预算，rerank 是最贵一段 |
| 查询形态？ | 混合：型号/错误码等精确词多，故障描述类语义多 | 纯向量顶不住精确词 → BM25 + 向量双路召回 + 融合层 |
| 多租户吗？隔离要求？ | SaaS 多租户，大客户要求物理隔离 | 索引隔离 vs 共享要给决策表，过滤必须 pre-filtering |
| 检索质量怎么验收？ | 有 500 条标注问答对，季度更新 | chunk/权重/top-k 一切调参必须评测集回归，不拍脑袋 |
| P95 2s 里生成占多少？ | 生成 1.2s 是大头 | 优化重心在生成而非检索——为题 11 埋线 |

> **本题主线**：四段链路（切块 → 召回 → 重排 → 生成）× 三条约束（质量 / 延迟 / 成本）× 一个底座（千万级容量账）。
> 后面所有决策都是这条主线的展开——答任何追问，先回到主线定位再展开细节，就不会乱。

### 架构图

30 秒画全景，报出延迟预算，再等面试官挑段深挖：

```text
┌───────────────── 离线链路（题 10 展开）─────────────────┐
│ 文档源 → 解析切块 → 批量向量化 → 向量库 8 分片 × 双副本  │
│                        （热/温/冷分层 + 软删除墓碑）     │
└───────────────────────────────────────────────────────┘
┌──────────────────────── 在线链路 ──────────────────────┐
│ Query → 查询改写 ─┬→ BM25 召回 top50 ─┐                │
│                   └→ 向量召回 top50 ─┴→ RRF 融合去重    │
│                        → rerank 精排 top5               │
│                        → LLM 生成（强制引用出处）        │
└───────────────────────────────────────────────────────┘
延迟预算：改写100 + 召回100 + 融合20 + 精排500 + 生成1200 ≈ 2s
```

（图注：双路召回并行执行，两段各 100ms 取 max 不相加；精排 + 生成合计占预算 85%，是优化主战场。）

**链路降级预案**（先说设计，别等事故）：

1. 一级降级：砍 rerank，RRF 序直出——立省 500ms，精度小损；
2. 二级降级：top5 → top3，精排候选与生成输入同砍；
3. 三级降级：检索失联时兜底 FAQ 库 +「暂无法检索」话术，绝不让模型脱离资料自由发挥；
4. 兜底顺序不能反：先降质量再降可用——宁可答案糙一点，不能让用户收到报错。

**关键模块一句话职责**：改写（把口语变规范查询）/ 召回（宽进，top50 宁多勿漏）/ 融合（两路名次合一）/ 精排（严出，top5 宁缺毋滥）/ 生成（有据可依，句句带引用）——宽进严出，是整条链路的灵魂。

**宽进严出的量化及格线**：召回段召回率@50 ≥ 95%，精排段精度@5 ≥ 85%——两段各有各的指标，混在一起谈质量是外行。

**为什么先画全景**：链路题的评分点是「结构完整 + 预算合理」，全景图 30 秒拿到这两个基础分，再等深挖逐段加分——比一上来抠细节的答法稳得多。

### 关键设计决策表

**决策 1｜chunk size 与重叠度**（稳定追问第一名，必须给权衡表而非拍脑袋数字）：

| 方案 | size / 重叠 | 召回精度 | 上下文完整性 | Token 成本 | 适用 |
|---|---|---|---|---|---|
| 小块 | 256 / 50 | 高（向量语义集中） | 差（答案易被切断） | 低 | FAQ 式短问答 |
| 中块 | 512 / 64 | 中高 | 中 | 中 | 通用知识库推荐起点 |
| 大块 | 1024 / 128 | 低（多主题稀释向量） | 好 | 高 | 长报告整体理解 |
| 语义切块 | 动态 / 句界对齐 | 最高 | 好 | 解析开销大 | 质量敏感场景，复杂度高 |

- 取舍本质：**检索粒度 vs 上下文完整性**。块小 → 向量语义集中、命中准，但答案跨块被切断；块大 → 上下文完整，但一个向量编码多个主题、召回变糊。
- 重叠度唯一目的：防止命中点恰好落在切块边界，把答案拦腰斩断；经验值 10%-15%，重叠换召回不换语义。
- 方法论：不拍数字，用**评测集网格搜索**——{256, 512, 1024} × {0, 64, 128} 九组配置离线跑「召回率@10 + 答案忠实度」，选帕累托最优。
- 别忘了术语归一化：内部缩写、产品代号要做词表归一化预处理，否则切块再好，向量也学不到「黑话 ↔ 标准词」的等价性。
- 细节加分：标题与层级路径拼进 chunk 文本再 embedding，否则向量丢失「这段话属于哪篇哪章」的归属信息；表格内容转 Markdown 保结构。
- 重建代价提醒：改 chunk 策略 = 全量重新切块向量化 → 必须走题 10 的蓝绿切换，所以 chunk 策略变更要克制、要评测背书。

❌ 踩坑：说「我们调了很久 chunk size」却讲不出取舍维度和评测数字——暴露没有工程方法论。

**决策 2｜检索方案：为什么必须混合**：

| 方案 | 强项 | 弱项 | 结论 |
|---|---|---|---|
| 纯 BM25 | 精确词稳（型号/错误码）、可解释、零幻觉 | 不懂同义改述，「蓝屏」搜不到「花屏死机」 | 单独不够 |
| 纯向量 | 语义泛化、跨表述召回 | 专有名词匹配弱、新词冷启动 | 单独不够 |
| 混合 + RRF 融合 | 双路互补，对查询分布鲁棒 | 双索引存储、链路复杂 | 生产标配 |

- RRF（Reciprocal Rank Fusion）：`score = Σ 1/(k + rank_i)`，k 取 60——只用到名次不用原始分，天然规避两路分数量纲不一致，融合层的默认答案。
- 加权融合也可，但 BM25 分数与余弦相似度量纲不同，权重必须靠评测集离线调；没有评测集就别碰加权。
- 向量召回两级化：HNSW 粗召回（efSearch=64）取 top50 送精排，召回率与延迟两头兼顾。
- 混合检索的代价清单：双索引存储（倒排 + 图）、双路算力、融合逻辑维护——收益是鲁棒性，代价要主动报。
- 检索调试顺序：先单路各自调优（BM25 分词与词典 / 向量 top-k），再调融合，最后上 rerank——顺序反了会互相掩盖问题。

**决策 3｜rerank：链路里最贵的瓶颈段，延迟预算死线**：

先给延迟预算分配表（本题的「分库分表怎么分」，面试官最爱）：

| 阶段 | 预算 | 占比 | 说明 |
|---|---|---|---|
| 查询改写 | 100ms | 5% | 意图识别 + 关键词抽取，可旁路降级 |
| 双路召回 | 100ms | 5% | BM25 与向量并行，取 max 不取 sum |
| RRF 融合去重 | 20ms | 1% | 纯 CPU 名次计算 |
| rerank 精排 | 500ms | 25% | 交叉编码器逐对打分，最大瓶颈 |
| LLM 生成 | 1200ms | 60% | 首 token 延迟 + 流式输出 |
| 合计 | ≈ 2s | 100% | P95 达标 |
| 缓冲 | 80ms | 4% | 吸收长尾抖动，别把预算排满 |

| 方案 | 延迟（50 条） | 效果 | 成本 | 结论 |
|---|---|---|---|---|
| LLM 当 rerank | 1-3s | 最好 | 最高 | 预算放不下，只能离线用 |
| 交叉编码器小模型 | 300-500ms | 好 | 中 | 在线标配 |
| 粗排打分函数 | <10ms | 中下 | 低 | 适合做精排前的截断层 |
| 不 rerank | 0ms | 差 | 0 | 精度顶不住追问 |

- rerank 模型看三样特征：query-chunk 交叉注意力分（主特征）、BM25 分数（辅助）、来源权重与时效权重（业务特征融合排序）——被问「rerank 特征权重」按此作答。
- 压延迟四板斧：粗排先截断到 top50 再进精排；批内并行推理；模型 INT8 量化；蒸馏小模型替换。
- 降级预案：高峰期把 rerank 降级为纯 RRF 序，立省 500ms，精度换可用性——降级链要提前设计而不是现场拍。
- 精排候选数是旋钮：top50 是「精度 vs 延迟」的平衡点，候选越多精度越高但延迟线性上涨——50 条 × 10ms/条 = 500ms 就是这道算术。
- GPU 攒批策略：精排请求进批队列，攒满 32 条或等 20ms 即推理——吞吐与延迟的折中，和消息队列攒批同构。

❌ 踩坑：报不出各段延迟预算占比；或用 LLM 做在线 rerank 还声称「没什么延迟问题」。

**决策 4｜千万 chunk 向量库分片与副本**：

| 维度 | 方案 | 理由 |
|---|---|---|
| 分片键 | tenant_id + doc_id 哈希，8 片起步 | 租户内查询不跨片；扩容翻倍到 16 片，一致性哈希路由 |
| 副本 | 每片 1 主 1 从 | 读扩展 + 主挂提升从；写入只有离线链路，压力小 |
| 索引 | HNSW（M=16，efSearch=64） | 千万级 + 低延迟场景的默认解 |
| 路由层 | 查询带 tenant_id 路由到分片组 | 避免全分片广播聚合 |

- 为什么 8 片：每片约 125 万 chunk ≈ 10GB 内存（由下面容量账反推），单机 64GB 可放 4-6 片，4 台物理机起步并留扩容余量。
- 副本数怎么定：读 QPS ÷ 单副本可承载 QPS，向上取整再 +1 冗余；本题 50 QPS，双副本绰绰有余。
- 分片间负载均衡：按租户体量预分片，避免超大租户独占单片成为热点——热点治理思路从 Redis 迁移过来。
- 扩容路径：片内饱和 → 翻倍分片 → 一致性哈希最小迁移；不要一步分 64 片。

❌ 踩坑：「分 1000 片」——片不是越多越好，每片 HNSW 图结构有固定内存开销，小片浪费内存且跨片聚合延迟反升。

**决策 5｜热温冷分层**（存储成本的三级火箭）：

| 层 | 数据范围 | 存储形态 | 预估占比 |
|---|---|---|---|
| 热 | 近 3 个月被访问过的 chunk | 内存 + 全精度 HNSW | 20% |
| 温 | 3-12 个月 | SSD + PQ 量化索引 | 50% |
| 冷 | 1 年以上未访问 | 磁盘归档，可选下线 | 30% |

- 迁移由访问统计驱动：命中计数 + 时间衰减（复用 Redis LFU 淘汰思路），后台任务低峰搬移。
- PQ 量化省 4-8 倍内存，代价是召回率掉 1-3 个点——主动报「省多少、亏多少」，取舍才算讲完。
- 分层不能拍脑袋：先全热跑一个月攒真实访问分布，再按分布切层——想象的热温冷比例往往是错的。
- 冷层按需回热：冷 chunk 被命中时异步搬回热层，该查询首轮延迟上升；用访问统计证明冷层命中率 <5%，代价可忽略。

**决策 6｜多租户：索引隔离 vs 共享**：

| 方案 | 隔离性 | 成本 | 适用 |
|---|---|---|---|
| 每租户独立索引 | 最强，可物理隔离 | 小租户索引碎片化浪费 | 大客户/合规要求 |
| 共享索引 + tenant_id 过滤 | 逻辑隔离 | 最省 | 中小长尾租户 |
| 分组共享：大客户独享 + 长尾共享 | 折中 | 折中 | SaaS 主流（推荐） |

- 分片键用 tenant_id 前缀哈希：同租户 chunk 落在同组分片，pre-filtering 直接裁剪整片，把过滤下推到存储层。
- 权限变更的隐藏优势：权限过滤在查询时做而非入库时做，权限体系变化不需要重建索引——架构对变更友好。

❌ 踩坑：共享索引只做 post-filtering——租户数据量悬殊时 top-k 先取满再过滤，小租户可能拿到 0 条结果；必须 pre-filtering（向量库带过滤检索，或按租户分区裁剪）。

**决策 7｜增量更新与软删除墓碑**：

| 操作 | 做法 | 原因 |
|---|---|---|
| 新增文档 | 解析切块后按分片键双写主从 | 增量写不影响在线查询 |
| 文档更新 | 新 chunk 全量写入 + 旧 chunk 打墓碑，版本号 +1 | 避免删旧写新之间的检索空窗 |
| 文档删除 | 软删除：元数据库置 deleted + 墓碑表记录 chunk_id | HNSW 图结构硬删代价高，触发图修补 |
| 物理清除 | 低峰期后台 compaction 合并墓碑 | 查询时 post-check 墓碑有损耗，定期真删回收 |
| 定向重刷 | 按 doc_id/标签过滤受影响 chunk 重嵌入 | 元数据修正、切块 bug 修复不必全量重建 |

❌ 踩坑：「调向量库删除接口直接删」——大批量硬删长时间占写锁、图结构退化；先软删后合并才是生产做法。

**决策 8｜embedding 选型**：

| 维度 | 选项 | 权衡 |
|---|---|---|
| 维度 | 768 / 1024 / 1536 | 内存与延迟线性放大；1024 是质量与成本平衡点 |
| 语言 | 通用多语 vs 中文优化 | 中文知识库优先选中文效果更好的模型 |
| 评测 | 公开榜单初筛 | 必须用自建评测集跑召回率终审；换模型 = 语义空间改变 = 全量重建索引（走题 10 蓝绿） |

**决策 9｜查询改写与多轮对话**（在线链路第一段，最容易被漏）：

| 问题形态 | 方案 | 代价 |
|---|---|---|
| 口语化/错别字 | 小模型改写成规范查询 | +100ms，可旁路降级 |
| 多轮指代（「它贵吗」） | 拼接历史做指代消解，改写成独立查询 | 依赖会话存储 |
| 一问多意长问题 | 拆子查询分别召回再合并 | 召回次数 ×N |
| 中英混杂/术语缩写 | 术语表归一化（内部黑话→标准词） | 维护词表成本 |

- 改写模块放最前且可降级：改写服务挂了直接用原始查询，链路不断。
- 改写结果也要缓存：高频 query 的改写结果缓存复用，命中率 40%+，改写延迟均值砍半。
- ❌ 踩坑：把整段聊天历史塞进检索查询——检索器被无关上下文污染，召回漂移。

**决策 10｜在线可观测与 badcase 回流**：

| 指标 | 采集点 | 用途 |
|---|---|---|
| 召回率@10（抽样标注） | 线上日志 | 检索质量趋势 |
| 引用点击率 | 前端埋点 | 答案可信度的代理指标 |
| 拒答率 | 生成日志 | 检索覆盖缺口地图 |
| badcase 队列 | 用户点踩 + 客服标记 | 回流评测集，季度回归 |

- 闭环：badcase → 标注进评测集 → 调参（chunk/权重/top-k）→ 评测回归 → 上线——没有回流的调参都是玄学。
- 告警阈值示例：召回率@10 周环比跌 2 个点、拒答率涨 1 个点即告警——阈值提前定好，不靠肉眼盯盘。
- ❌ 踩坑：只看离线指标不看线上回流——坏版本上线两周才发现，损失已经造成。

### 容量估算

整数近似，现场口算展示（**1024 维 float32 = 4KB/chunk** 是本题的口算锚点）：

**向量存储账（千万 chunk）**：

- 单 chunk 向量：1024 维 × 4B（float32）= 4096B ≈ **4KB**
- 原始向量总量：1000 万 chunk × 4KB = **40GB**
- HNSW 索引膨胀（图邻接表 + 元数据）：经验系数 ×2 → **80GB**
- 双副本：80GB × 2 = **160GB 总内存需求**
- 分 8 片 → 每片 20GB，单机 64GB 内存承载 2 片 + 30% 余量 → **4-6 台起**

**热温冷分层后的实际内存**（决策 5 收益量化）：

- 热层 20%（200 万 chunk）：全精度进内存 ≈ 200 万 × 8KB（含索引膨胀）≈ **16GB**
- 温层 50%（500 万 chunk）：PQ 量化（÷8）+ SSD，内存仅 **2.5GB** 量级的码本与索引
- 冷层 30%（300 万 chunk）：磁盘归档，内存占用 ≈ 0
- 对比：全内存 160GB → 分层后 **20GB 级**，机器从 6 台降到 2 台——这就是分层答法的数字底气

**生成 Token 成本账（为题 11 埋线）**：

- 单次问答输入：top5 × 512 token + 系统提示 500 + 问题 100 ≈ **3K token**；输出 500 token
- 单价整数化假设：输入 ¥15/百万、输出 ¥60/百万（主流强模型量级）
- 月 100 万次问答：输入 30 亿 token × ¥15/M = **¥4.5 万**；输出 5 亿 × ¥60/M = **¥3 万** → **月生成账单 ≈ ¥7.5 万**
- 结论：检索链路的机器成本是小头，**生成 Token 才是大头**——优化重心交给缓存与级联（题 11 展开）

**embedding 离线吞吐账**：

- 全量 1000 万 chunk，批量向量化 5K chunk/s → 1000 万 ÷ 5K = 2000s ≈ **33 分钟**
- 结论：全量重建是小时级工程，完全可行——这是题 10「蓝绿双索引切换」的容量底气

**QPS 与召回算力账**：

- 在线 50 QPS × 双路召回：单分片 HNSW 查询 <10ms，8 分片分摊后单机轻松扛住
- rerank：50 QPS × 500ms = 25 并发 × GPU 批推理，1-2 张卡做精排池；高峰降级砍 rerank 保命

**数字速答卡**（现场直接背，每题口算不超过 10 秒）：

| 口算题 | 答案 |
|---|---|
| 1024 维 float32 向量多大 | 1024 × 4B = 4KB |
| 千万 chunk 原始向量 | 1000 万 × 4KB = 40GB |
| 含 HNSW 膨胀 | ×2 ≈ 80GB |
| 双副本总量 | 160GB，分 8 片每片 20GB |
| 热温冷分层后内存 | 20GB 级（热 16GB + 温 2.5GB） |
| 全量重建耗时（5K chunk/s） | 1000 万 ÷ 5K ≈ 33 分钟 |
| 单次问答输入 | top5 × 512 + 600 ≈ 3K token |
| 月 100 万次问答生成账单 | 输入 4.5 万 + 输出 3 万 ≈ ¥7.5 万 |

**与后两题的接口**：入库吞吐与质量门禁看题 10；生成 Token 账单怎么砍看题 11——三题共用同一套容量口算方法，练一题等于练三题。

### 追问链

模拟面试官深挖顺序，每层先给要点再标踩坑；这八层覆盖本题八成的二面战场：

```text
追问链地图：chunk怎么定 → 为什么混合 → rerank怎么压 → 索引怎么选
→ 增删改怎么同步 → 幻觉怎么治(分层) → embedding怎么换 → 洪峰怎么扛
```

**追问 1**：chunk size 你们线上到底多少？怎么定的？

- 要点一：先给权衡表（决策 1），取舍本质是「检索粒度 vs 上下文完整性」——这句话说出来，面试官就知道你懂行。
- 要点二：再报结论——「评测网格搜索后定 512/64，召回率@10 比默认 256 提升约 8 个点」；先方法论后数字。
- 要点三：适用条件要挂上——「我们是短文档为主的知识库」；如果是长手册场景，答案会不一样。
- 加分：文档异构时（短公告 + 长手册），按文档类型分层配置 chunk 策略，比全局一刀切更优。
- 反问兜底：被追问「为什么不用语义切块」时答「解析质量不稳、坏块率难控，先用固定块 + 评测兜底，语义切块在 roadmap」——有边界的克制比激进加分。

❌ 踩坑：直接报一个数字且无任何条件限定，被追问「为什么不是 1024」当场卡住。

**追问 2**：都 2026 了，BM25 为什么还没被向量检索取代？融合层具体怎么做？

- 要点一：精确词场景 BM25 完胜——产品型号、错误码、法条编号这类 token，向量检索反而模糊，关键词检索零幻觉。
- 要点二：RRF 公式 `score = Σ 1/(60 + rank_i)`——只用名次不用原始分，天然规避 BM25 分数与余弦相似度的量纲差异，这是融合层的默认答案。
- 要点三：两路并行召回，延迟取 max 不相加；融合后按 chunk_id 去重，双路命中的取更优名次。
- 要点四：如果非要加权融合，权重要评测集离线调；没有评测集就别碰加权，RRF 是无参稳解。
- 延伸：融合不止两路——知识图谱路、标签路都可以 RRF 进来，名次融合天然支持多路扩展，这是选 RRF 的架构级理由。

❌ 踩坑：说「向量检索全面优于关键词」——一句话暴露没碰过真实语料。

**追问 3**：rerank 为什么慢？延迟怎么压？

- 要点一：慢的根源——交叉编码器要对 query × chunk 逐对做交叉注意力，50 条候选就是 50 次前向传播，天然比双塔模型（一次编码、万次比对）贵一个量级。
- 要点二：压延迟四板斧——粗排截断到 top50 再进精排、批内并行推理、模型 INT8 量化、蒸馏小模型替换。
- 要点三：预算死线 500ms 說在前面；高峰降级直接砍 rerank 用 RRF 序，立省 25% 延迟预算，精度换可用。
- 要点四：rerank 的特征权重——交叉注意力分为主，BM25 分数与来源/时效权重为辅，业务特征融合排序。
- 数字心算：50 条候选 × 10ms/条 = 500ms，截断到 30 条 = 300ms——延迟随候选数线性，这就是截断有效的原因。
- 成本视角：精排 GPU 是固定投入，QPS 越高摊薄越狠——延迟账和成本账要一起算。

❌ 踩坑：用 LLM 做在线 rerank 还声称「没什么延迟」；或报不出自己方案里 rerank 段占多少预算。

**追问 4**：向量库为什么选 HNSW？IVF、暴力检索不行吗？

| 索引 | 召回率 | 延迟 | 内存 | 适用规模 |
|---|---|---|---|---|
| 暴力检索 | 100% | 千万级不可接受 | 无额外开销 | 百万 chunk 以下 |
| IVF（倒排文件） | 中，nprobe 敏感 | 中 | 省 | 更大规模/成本敏感 |
| HNSW（层图） | 高且稳 | 低且稳 | 大（图结构膨胀 ×2） | 千万级 + 低延迟（本题） |

- 要点一：按「召回率 / 延迟 / 内存」三维说取舍，别只报名字。
- 要点二：参数张口就来——M=16 控制图连接密度，efSearch=64 是召回率与延迟之间的旋钮，调大召回升延迟也升。
- 要点三：索引形态也分层——热层全精度 HNSW，温冷层换 PQ 量化索引，索引跟着存储一起降级。
- 参数敏感度：efSearch 64 → 256，召回率 +2%、延迟 ×3——参数调优的边际收益要报数字，不是「调大点」。

❌ 踩坑：只背索引名字，说不出三维护型差异；或者不知道 HNSW 内存膨胀约 2 倍这个容量常识。

**追问 5**：文档每天增删改，索引怎么跟着变？删掉的文档还能被搜到吗？

- 要点一：新增走题 10 的入库流水线，按分片键双写主从，增量写不影响在线查询。
- 要点二：更新防空窗——先把新版本 chunk 全量写入，再给旧版本打墓碑，元数据版本号 +1；绝不能先删后插。
- 要点三：删除用**软删除墓碑**：元数据库置 deleted 标记 + 墓碑表记录待删 chunk_id 列表，检索结果后置过滤墓碑。
- 要点四：物理清除靠低峰期后台 compaction——墓碑攒到阈值批量合并真删，回收图空间。
- 要点五：为什么不全量硬删——HNSW 删除要修补图邻接，大批量删除长时间占写锁、索引退化，代价远高于「标记 + 后台合并」。
- 一致性窗口：墓碑写入到检索生效有秒级延迟，「删除后 1 分钟内仍可能被搜到」要提前和业务对齐预期。

❌ 踩坑：「调 delete 接口直接删」——没考虑图索引的删除代价与批量写锁，生产会出事故。

**追问 6**：模型一本正经地胡说八道（幻觉），怎么治？（全站最高频，必须分层答）

| 层 | 手段 | 成本 | 见效速度 |
|---|---|---|---|
| L1 提示词层 | 强约束「仅依据参考资料回答，没有就明确说不知道」+ 强制引用标注 | 极低 | 立竿见影 |
| L2 检索层 | 幻觉大半源于检索没命中——查询改写、混合检索、rerank、top-k 回炉 | 低-中 | 迭代可见 |
| L3 工具层 | 事实校验器、外部搜索兜底、低置信度拒答转人工 | 中 | 中 |
| L4 微调层 | 领域语料微调 | 高、更新慢 | 慢 |

- 核心句式：**顺序就是答案——提示词 → 检索/工具 → 微调，成本递增、迭代速度递减，永远先便宜后昂贵**。
- 补充：引用标注是双保险——答案每句话挂 chunk 出处，用户可校验，模型也因「要给出处」而更克制。
- 补充：拒答是特性不是缺陷——「资料中没有」配合转人工/转搜索，比硬编强一万倍。
- 评测配套：幻觉要单独评「忠实度」（答案是否被资料支持），不能只看总体满意度——两个指标会打架。
- 量化分层效果：提示词约束通常砍掉三成明显幻觉，检索优化再砍三成，剩下是长尾——这组数字说明为什么微调不是必需品。
- 场景分级：客服场景容忍度低 → 严格拒答；创意场景容忍度高 → 放宽约束——治理强度跟着场景走。

❌ 踩坑：开口就「微调一个领域模型」——顺序反了，直接扣分；微调是最后手段不是第一反应。

**追问 7**：embedding 模型怎么选型？要换模型怎么办？

- 要点一：维度即成本——1536 比 1024 内存贵 50%，容量账（4KB/chunk 锚点）随维度线性变。
- 要点二：榜单初筛、自建评测集终审——公开榜单与自己的语料分布差异很大，召回率必须自己跑。
- 要点三：切换成本要主动点破——换模型 = 语义空间改变 = 全量向量失效 = 走题 10 的蓝绿全量重建流程，不是改个配置。
- 要点四：部署形态——月增量千万级以下用 API 按量更省；亿级存量 + 数据隐私要求才考虑自部署开源模型。
- 维度边际递减：768 → 1024 提升明显，1024 → 1536 边际递减——容量账的另一半。

❌ 踩坑：只背榜单排名；或以为换 embedding 是热更新的小事。

**追问 8**：某个大租户查询洪峰把共享检索集群打挂，怎么办？

- 要点一：租户级限流先行——RPM/TPM/并发多维预算，单个租户的洪峰不能外溢到别人。
- 要点二：架构级隔离——大客户独享分片组（决策 6 的分组共享方案），物理上打不穿别人。
- 要点三：读副本弹性扩容——检索是无状态读，扩副本线性分摊。
- 要点四：降级链依次触发——先砍 rerank（省 500ms 算力）、再减 top-k（省精排与生成输入）、最后排队限流。
- 要点五：限流维度选 TPM 而非全局 QPS——AI 资源的成本单位是 token，不是请求数。
- 公平性度量：P95 按租户分桶看，不看全局 P95——大户达标、小户被挤时，全局指标会撒谎。

❌ 踩坑：只答「加机器」——没有租户维度的隔离与公平性设计，加多少机器都会被下一个大户打挂。

### 🎤 口述模板

先背熟再自由发挥——下面这段话就是本题的 90 秒开场：

> 我把 RAG 链路分四段讲。离线侧：文档解析切块后批量向量化，写入按租户哈希的 8 分片向量库，热温冷三层存储加双副本，删除走软删除墓碑加后台合并。在线侧：查询先改写，BM25 与向量双路并行召回各取 top50，RRF 融合去重后送交叉编码器精排取 top5，最后带强制引用生成。延迟预算是改写 100、召回 100、融合 20、精排 500、生成 1200，P95 卡 2 秒。容量上千万 chunk 按 1024 维 float32 每条 4KB 口算：原始 40GB、索引膨胀翻倍 80GB、双副本 160GB，分 8 片 4 到 6 台机器；热温冷分层后内存压到 20GB 级。多租户用大客户独享加长尾共享的分组方案，过滤必须 pre-filtering。幻觉缓解我按提示词、检索、工具、微调四层从轻到重治理，顺序不能反。如果聊优化，第一刀砍 rerank 截断与分层存储，第二刀是生成侧缓存——那才是成本大头。

- 口述节奏：先骨架后血肉——四段链路 30 秒、延迟预算 15 秒、容量口算 30 秒，剩下时间留给面试官挑段深挖。
- 数字锚点：4KB/chunk、40GB→80GB→160GB、P95 2s 的五段分配——这三个数字组合是本题的记忆钩子。
- 主动埋钩子：讲完补一句「生成侧成本是大头，怎么优化可以在成本题里展开」——把面试官引向自己熟悉的领域。
- 万能回退：任何细节答不上，回到「质量-延迟-成本」三角给取舍框架——框架分永远拿得到。

### 一句话总结

> RAG 全链路的满分答案 = 四段骨架 + 逐段延迟预算 + 千万级容量口算（4KB/chunk 锚点）+ 幻觉分层治理——先全景后细节，每个取舍都带数字与代价。

> 延伸记忆：宽进严出（召回宁多、精排宁少）、软删墓碑（图索引别硬删）、pre-filtering（过滤必须下推）——三个关键词顶三段论述。

## 题 10｜知识库异步入库流水线：百万文档/月的解析-切块-向量化管道

> **一句话考察点**：每月百万份多格式文档（PDF/扫描件/表格/HTML）如何稳定变成可检索的高质量向量——解析选型、质量门禁、MQ 驱动的幂等异步、增量 vs 全量蓝绿切换、失败补偿；本质是一条标准 ETL 管道，后端数据侧老经验全量迁移。
>
> **考频**：⭐⭐⭐⭐⭐（考频校准：作为独立大题出现率仅次于 RAG 链路，但作为题 9 的「离线侧深挖」追问出现率极高；数据工程背景候选人二面常被直接出题，考察重点从「画链路」转向「可靠性设计」）

### 需求澄清

| 我问 | 面试官答（假设） | 对设计的影响 |
|---|---|---|
| 月入库量与格式分布？ | 100 万份/月：PDF 60%、扫描件 15%、Office 15%、HTML 10% | 解析器按格式路由，OCR 是吞吐瓶颈，独立队列隔离 |
| 时效 SLA？ | 上传到可检索 P95 ≤ 30 分钟 | 同步链路不可能 → MQ 驱动异步 + 优先级队列 |
| 允许多大失败率？ | 解析成功率 ≥ 99%，失败进人工修复 | 重试 + 死信 + 人工修复台 + 对账兜底 |
| 全量重建频率？ | embedding 每半年升级一次 | 增量为主 + 蓝绿全量切换双轨制 |
| 文档会被修改吗？ | 20% 文档月内有版本更新 | 版本化幂等键 + 旧版墓碑（呼应题 9 决策 7） |
| 重复上传多吗？ | 常见，约 15% 是重复件 | 内容哈希前置去重，直接省掉整条管道成本 |
| 上传高峰有规律吗？ | 工作日晚间集中，白天零散 | 峰值系数 ×10 设计，夜间窗口跑批处理 |

> **本题主线**：一条 ETL 管道 = 抽取（解析）→ 转换（切块 + 门禁 + 向量化）→ 加载（写索引）——每个阶段都要回答三件事：吞吐多大、质量怎么保、失败了怎么办。
> 答题顺序也按这个主线走：先管道全景，再逐阶段给「吞吐 + 质量 + 失败」三件套，最后用容量账收尾。

### 架构图

```text
上传 API ─→ 对象存储(原始件) ─→ 发 MQ(doc_id + version)
                                        │
       ┌────────────────────────────────▼───────────────────────────┐
       │ 解析 Worker（按格式路由，分队列隔离）                          │
       │  PDF文本层→直提 │ 扫描件→OCR(GPU池) │ 表格→结构化 │ HTML→清洗 │
       └──────┬─────────────────────────────────────────────────────┘
              ▼
       切块 + 质量门禁（质量分 < 阈值 → 降级重切 / 转人工）
              ▼
       批量向量化（GPU 池错峰共享，batch 256）
              ▼
       写向量库(8 分片双写) + 元数据库(MySQL) → 状态回写 + 通知
 失败：重试 3 次(1m/5m/25m 退避) → 死信队列 → 人工修复台 → 补偿重放
 全量重建：索引 B 灌满 → 抽样校验 → 别名原子切换 → 灰度观察 → 下线 A
```

（图注：每阶段消费成功才 ack，幂等键 = doc_id + version + stage；对账 job 每小时核对对象存储文件数与索引 chunk 数，差异自动补投。）

**画图顺序**：先画主干（上传 → MQ → 解析 → 切块 → 向量化 → 入库），再补三条旁路（重试/死信/修复台、优先级队列、蓝绿重建）——主干答结构分，旁路答可靠性分。

**这就是一条标准 ETL**：解析 = 抽取、切块向量化 = 转换、写索引 = 加载——幂等、死信、对账、蓝绿全是老工具箱里的东西，开口先点破这层映射，面试官立刻知道你带着数据侧功底来的。

**管道与题 9 的接口**：本题为在线检索供数——chunk 策略、元数据 schema、墓碑机制三处必须与题 9 对齐；「数据侧定质量、检索侧定体验」是两题的分工线。

### 关键设计决策表

**决策 1｜多格式解析选型矩阵**：

| 格式 | 难点 | 方案 | 质量要点 |
|---|---|---|---|
| 文本层 PDF | 版面还原、阅读顺序 | 开源解析库抽文本层 + 版面分析 | 段落顺序、页眉页脚水印剔除 |
| 扫描件 PDF | 无文本层，纯图片 | OCR 引擎（GPU 加速）+ 版面恢复 | 乱码率是核心指标，慢是吞吐瓶颈 |
| Word/PPT | 嵌入对象多、图表文字 | 统一转 PDF 走下游，原生解析双通道兜底 | 图表内文字丢失要有检测 |
| Excel 表格 | 结构语义强 | 转 Markdown/HTML 保表格结构 | 列头拼进每行 chunk，否则数值无主语 |
| HTML | 噪声大 | 正文抽取算法 + 清洗管道 | 广告/导航/脚注剔除，正文识别准确率 |

- 原则一：**先按格式路由再进统一切块**——不同格式不同队列，慢的 OCR 独立队列 + GPU 池，不拖垮快格式。
- 原则二：解析器版本化管理——解析逻辑变更 = 新版本号，出问题按版本回滚，坏批次按版本定位定向重刷。
- 原则三：扫描件识别前置探测（有无文本层），别让 OCR 白跑——探测毫秒级，OCR 秒级，省下的是 GPU 钱。
- 原则四：原始件永远留在对象存储——解析可以重跑，原件丢了就没了；这也是全量重建和定向重刷的底气。
- 扩展性：路由表设计成可插拔——音视频附件走 ASR 转写再进文本管道，新格式只加一行路由，不动主干。
- 多语言文档：语言检测进元数据，检索侧按语言分索引或混排——策略入库时就定死，不留给检索侧猜。

❌ 踩坑：所有格式一个队列——15% 的扫描件把 60% 的普通 PDF 全堵死（队头阻塞），这是本题最经典的容量事故。

**决策 2｜切块质量门禁**（垃圾进垃圾出的最后防线）：

| 门禁项 | 阈值示例 | 不达标动作 |
|---|---|---|
| 乱码率（非常规字符占比） | > 5% 拦截 | 转 OCR 重解析 / 转人工 |
| chunk 长度分布 | 均值偏离 512 ± 50% 告警 | 回炉重切 |
| 空 chunk / 截断率 | > 1% 拦截 | 解析器版本回滚排查 |
| 句边界截断比例 | > 20% 告警 | 切块参数回炉 |
| 抽检（采样 1% 人审） | 批次不合格率 > 5% | 批次冻结 + 告警升级 |
| 语言检测置信度 | < 90% 转人工标注语言 | 防多语言误切 |

- 质量分 = 乱码率 + 长度分布偏离度 + 句边界截断比例加权合成——入库前硬拦截，不是软提醒。
- 在线回流闭环：检索点击率、引用命中率、拒答率的异常下跌反推某批次质量问题——离线门禁 + 在线回流双向验证，缺一不可。
- 抽检的采样设计：按 parse_version + 格式 + 租户分层采样，比纯随机更能暴露系统性问题。
- 阈值不是拍出来的：用历史数据分布定基线（P99 之外才拦），上线后按误杀率微调——门禁本身也要迭代。
- 误杀的出口：被拦截文档可人工强制入库并打「豁免」标记——门禁是默认策略不是铁律，给业务留逃生门。

❌ 踩坑：只有离线指标没有在线回流——坏批次入库两周才被发现，用户早已投诉到客服。

**决策 3｜MQ 驱动异步 + 幂等消费 + 死信重试**：

| 机制 | 设计 | 说明 |
|---|---|---|
| 队列拓扑 | 按阶段分段：解析→切块→向量化→入库 | 每段独立扩缩容，慢段单独加机器 |
| 幂等键 | doc_id + version + stage | 消费前查状态表，已成功直接 ack |
| 投递语义 | MQ 至少一次 + 业务幂等 = 恰好一次效果 | 别指望 MQ 层给你恰好一次 |
| 重试 | 3 次指数退避（1m/5m/25m） | 只救瞬时故障（抖动/限流） |
| 死信 | 3 次失败进 DLQ + 告警 | 人工修复台认领，修复后重放原始消息 |
| 对账 | 每小时核对文件数 vs 入库数 | 漏单自动补投，双保险 |
| 优先级 | VIP 租户独立队列 | 大客户文档 5 分钟可见 |

- 幂等实现细节：状态表 (doc_id, version, stage, status)，消费事务里「检查 → 执行 → 标记」三步走，重复消息靠唯一索引挡掉。
- 队列分段的价值：向量化段 GPU 扩容不影响解析段 CPU 扩容——资源类型不同的阶段必须拆队列。
- 消息体只放引用（doc_id + version），不放内容——大 payload 拖垮 MQ，内容按需从对象存储拉。
- 消费并发设计：单 stage 内多 worker 并行，分区键 = doc_id——同文档保序、跨文档并行，两不耽误。
- ack 时机：业务落库成功才 ack；处理中崩溃靠消息重投 + 幂等兜底，不靠小心翼翼。

❌ 踩坑：把「MQ 至少一次」当「恰好一次」用，不做业务幂等——重复消费产生重复 chunk，用户看到答案成对出现。

**文档状态机**（幂等与对账的公共底座）：

```text
UPLOADED → PARSING → PARSED → CHUNKING → CHUNKED → EMBEDDING
        → INDEXED（终态成功）
任意态 → FAILED（终态失败，进死信）→ REPAIRED → 重放回 PARSING
DELETED（软删除终态，墓碑）
```

- 状态机落在 MySQL 状态表，每条迁移记录时间戳与 parse_version——幂等检查、对账、坏批次定位、重放全部依赖它。
- 状态迁移与业务操作同事务——「先改状态后干活」或「先干活后改状态」都行，但必须原子，否则状态表会撒谎。

**决策 4｜增量 vs 全量：双索引蓝绿切换**：

| 方案 | 触发场景 | 做法 | 风险与代价 |
|---|---|---|---|
| 增量更新 | 日常新增/修改（绝大多数流量） | 新文档走流水线直写线上索引 | 长期碎片化、旧策略残留 |
| 混合模式 | 常态运营 | 日常增量 + 季度合并重建 | 双轨并行，碎片定期治理 |
| 全量重建 | embedding 升级 / 切块策略改版 | 索引 B 全量灌入 → 抽样校验 → 别名原子切换 → 灰度观察 → 下线 A | 机器双倍、切换期一致性问题 |

- 切换原子性：路由层索引别名翻面，秒级生效；灰度按租户分批 5% → 50% → 100%，出问题秒级回切。
- 全量重建的容量底气：题 9 算过 1000 万 chunk ÷ 5K/s ≈ 33 分钟——小时级工程，蓝绿完全可行，不是天级冒险。
- 观察期指标：新旧索引双跑对比召回率@10 与 badcase 率，达标才全量切、才下线旧索引。
- 增量期的碎片治理：定期（如季度）做一次「合并重建」抵消碎片化——增量是日常，全量是体检。
- 资源隔离：全量重建走影子资源池，不与日常增量抢配额——重建任务把增量堵死是经典事故。

❌ 踩坑：边删边建原地升级——中途失败回不去，也没有对照校验；蓝绿双倍资源买的就是「可回退」。

**决策 5｜元数据设计与 pre-filtering**：

| 字段 | 用途 | 过滤方式 |
|---|---|---|
| tenant_id / acl | 权限隔离 | pre-filter 必备，进分片路由 |
| doc_id / version / chunk_id | 幂等、版本更新、墓碑定位 | 精确定位 |
| source_type / 原始格式 | 结果溯源展示 | 展示 + 统计 |
| created_at / updated_at | 时效过滤（只搜近一年） | pre-filter |
| 标签（产品线/部门） | 业务维度裁剪 | pre-filter |
| parse_version / 质量分 | 坏批次定位与定向重刷 | 运维维度 |

- 元数据双写：向量库侧存过滤字段（支持下推），MySQL 存全量明细——两边职责不同，不要只存一边。
- 权限字段冗余两份：向量库侧做粗过滤（pre-filtering），展示前由权限服务二次校验——快慢两条路各取所需。
- 时间字段的坑：统一存 UTC + 毫秒时间戳，字符串日期格式混用是脏数据的头号来源。
- 字段设计原则：**入库时是信息最全的时刻**（来源、格式、权限、时效全部在手），此时不存，事后补的成本是全量回刷。

❌ 踩坑：元数据只存 MySQL——检索时先查库再查向量，两跳且无法下推过滤，延迟翻倍（题 9 决策 6 的镜像错误）。

**决策 6｜失败补偿与人工修复队列**：

| 层 | 机制 | 覆盖场景 |
|---|---|---|
| 自动 | 重试 3 次（指数退避） | 瞬时抖动、限流 |
| 半自动 | 修复台按失败原因模板化一键处理（密码 PDF 解密 / 损坏件修复 / OCR 加固）后重放 | 可修复的确定性失败 |
| 兜底 | 对账 job 漏单补投；连续失败批次回滚 parse_version | 系统性故障 |
| 度量 | 解析成功率、平均入库延迟、死信积压量三大看板指标 | 运营视角 |

- 修复台设计要点：按失败原因聚类展示，TOP 原因做成模板——目标是把人工量压到总量的 1% 以内。
- 死信 SLA：积压超 24 小时告警升级——死信队列只进不出等于静默丢数据。
- 修复台与工单系统打通：不可修复的文档（损坏件）走业务流程通知上传方重传——技术兜底之外要有业务兜底。
- 复盘机制：每次死信风暴后出一份「根因 + 防复发」短文档进团队 wiki——同样的坑不踩第二次。

❌ 踩坑：死信队列没有修复台和 SLA——积压成灾，月底对账发现 5% 文档静默丢失。

**决策 7｜与经典 ETL 的映射表**（转型者的高光时刻）：

| ETL 概念 | 本题对应 | 老经验复用度 |
|---|---|---|
| 抽取 Extract | 多格式解析 | 多源适配器模式，直接迁移 |
| 转换 Transform | 切块 + 质量门禁 + 向量化 | 数据质量规则引擎，思路同构 |
| 加载 Load | 写向量库 + 元数据库 | 幂等写、批量写，直接迁移 |
| 调度 | MQ 驱动的阶段流水线 | 完全同构 |
| 数据治理 | 死信 / 对账 / 血缘追溯（doc→chunk） | 完全同构 |
| 重复文档与解析缓存 | 决策 9 | 去重/缓存/灰度 | 直接迁移 |
| 安全与合规 | 决策 10 | 脱敏/审计/防注入 | 新增但思路同构 |

- 差异点也要主动讲：解析结果是概率性的（OCR 会错），质量门禁比传统 ETL 更重；向量语义无法肉眼校验，要靠评测集；GPU 资源要错峰调度——这三处是新增学习成本，其余全在舒适区。
- 面试价值：这题答好 = 直接证明「后端数据经验可迁移」，比背十个 AI 名词更有说服力。

**决策 8｜流水线可观测与运营水位**：

| 指标 | 采集点 | 告警阈值示例 |
|---|---|---|
| 各阶段积压量 | 队列深度 | 追平时间 > 20 分钟告警 |
| 解析成功率 | 状态表统计 | < 99% 告警 |
| 端到端入库延迟 | 入库时间 - 上传时间 | P95 > 25 分钟预警（SLA 30 分钟） |
| 死信积压 | DLQ 深度 | 非零持续 1 小时告警，超 24 小时升级 |
| 门禁拦截率 | 门禁日志 | 环比突增 2 倍 = 上游格式异常 |
| 对账差异数 | 对账 job | 非零即告警，自动补投 |

- 运营视角三问（每个阶段的灵魂拷问）：**积压了怎么办（扩容 + 优先级）、失败了怎么办（重试 + 死信 + 修复台）、错了怎么办（对账 + 定向重刷）**——任何阶段答不全三问，设计就没闭环。
- 水位分级：绿色（追平 < 10 分钟）/ 黄色（10-20 分钟，冻结变更发布）/ 红色（> 20 分钟，触发扩容预案）。
- 发布约束：队列黄色水位时冻结流水线变更——防止「变更 + 积压」双重故障叠加，这是从传统发布纪律里搬来的规矩。
- 水位数据的第二个用途：容量规划——连续四周黄色即启动扩容评估，不等红色告警才动手。

❌ 踩坑：只监控服务存活不监控业务水位——进程全绿但积压爆表，SLA 默默破掉一周才发现。

**决策 9｜重复文档与解析缓存**（省的都是真金白银）：

| 场景 | 方案 | 收益 |
|---|---|---|
| 同文件重复上传 | 文件内容哈希先行去重 | 跳过全管道，秒级返回已有 doc_id |
| 近重复文档 | 文档级 SimHash/MinHash 聚类 | 提示「已有相似文档」，减少噪音入库 |
| 相同内容批量重刷 | 解析结果缓存（内容哈希 → 解析产物） | 解析器小版本升级不重刷全库 |
| 相似问题不同格式 | 格式归一化后再哈希 | 同内容 PDF/Word 只入一份 |
| 解析器升级灰度 | 新旧版本并行跑、对比抽检 | 升级不翻车的唯一安全路径 |

- 内容哈希去重的位置：上传 API 同步做——哈希计算毫秒级，挡掉的是后面整条管道的算力。
- 解析缓存与 parse_version 绑定：解析器大版本升级缓存全失效，小版本参数修补则定向失效——「按版本重刷」的实现基础。
- 收益量化：企业知识库重复率常见 10%-20%，前置去重直接砍掉同比例管道成本——数字要主动报。
- ❌ 踩坑：用文件名/URL 当唯一键——改名重传、多源同名全部穿透；内容哈希才是文档的身份。

**决策 10｜安全与合规：敏感文档的管道内治理**：

| 环节 | 风险 | 方案 |
|---|---|---|
| 上传 | 恶意文件（伪装成 PDF 的可执行件） | 类型嗅探 + 病毒扫描，先隔离区后管道 |
| 解析 | 文档内藏注入指令（间接提示词注入） | 文档内容只当数据不当指令，输出侧过滤指令样模式 |
| 入库 | 敏感信息（证件号/卡号）进索引被检索 | 切块前脱敏（正则 + NER），原文加密单独存 |
| 检索 | 越权访问他人文档 | tenant_id + acl 进 pre-filtering（接题 9 决策 6） |
| 审计 | 合规追溯 | doc_id 全链路血缘 + 操作日志留痕 |

- 脱敏的位置在解析之后、切块之前——对 chunk 逐块脱敏会切断上下文一致性，整篇处理再切。
- ❌ 踩坑：只防外网入口不防文档内容——知识库是被投毒的重灾区，管道内安全是 2026 的新必答题。

### 容量估算

整数近似，口算展示：

**吞吐账**：

- 100 万份/月 ÷ 30 天 ≈ 3.3 万份/天 ≈ 平均 0.4 份/秒，峰值 ×10 ≈ **4 份/秒**
- 平均每份 2 页（60% 单页短文 + 40% 长文档）→ 峰值 8 页/秒；扫描件 15% 均 10 页 → 峰值 OCR 约 6 页/秒
- OCR 单卡吞吐 ≈ 2 页/秒 → **OCR GPU 池 3 卡起步，配 5 卡留余量**
- 普通解析 CPU 单机 10 份/秒 → 1 台够，配 2 台冗余——瓶颈永远在 OCR，不在文本解析
- 队列容量：峰值 4 份/秒 × 30 分钟 SLA = 积压上限约 7200 份——MQ 与状态表按 10 万级消息设计，毫无压力

**chunk 产出账**：

- 短文档为主：均篇约 1.2 chunk → **月产约 120 万 chunk**
- 向量化 5K chunk/s → 120 万 ÷ 5K = 240s/月——纯计算每月不到 5 分钟，GPU 利用率极低
- 结论：**向量化与在线推理共享 GPU 池，错峰调度**（白天保在线、夜里跑批量），单独买卡是浪费

**存量与增长账**：

- 存量 1000 万 chunk（与题 9 口径一致），月增 120 万 → 年增约 1400 万
- 印证题 9 热温冷分层的必要性：两年后逼近 4000 万 chunk，全内存方案彻底不可行——离线侧的入库节奏决定在线侧的架构演进
- 反向印证去重的价值：若不做前置去重，年增量还要多 15%——管道省钱就是在线侧省机器

**SLA 账**：

- 单文档端到端计算：解析 5s + 切块 1s + 向量化（批）2s + 入库 1s ≈ 10s，其余全是排队
- 30 分钟 SLA 的隐含约束：队列积压文档数的追平时间必须 < 20 分钟——容量按峰值 2 倍配，排队 P95 才有保障
- 优先级队列的价值：VIP 文档插队，普通文档让路——SLA 分级用队列隔离实现，最便宜
- 反压设计：下游（向量库）过载时，上游 worker 主动限流消费——整条管道的背压传导，别让压力在末端爆掉

**数字速答卡**：

| 口算题 | 答案 |

| 百万文档/月的平均速率 | 0.4 份/秒，峰值按 4 份/秒设计 |

### 追问链

按二面深挖顺序模拟，每层先给要点再标踩坑；答法结构：先定位问题域（容量/可靠性/质量），再给机制，最后报数字：

```text
追问链地图：OCR积压怎么办 → 怎么不重复入库 → 何时必须全量 → 表格图片怎么办
→ 怎么发现坏数据 → 和传统ETL区别 → 元数据为什么不能事后补
```

**追问 1**：OCR 队列积压，SLA 眼看要破，怎么办？

- 要点一：先定位再动手——积压量 ÷ 消费速率 = 追平时间，判断还剩多少余量；瓶颈在 GPU 不在 CPU，加 CPU worker 没用。
- 要点二：短期三板斧——GPU 水平扩容（3 卡 → 6 卡）；低优先级文档延后处理；VIP 队列保大客户 SLA。
- 要点三：极限降级——先入文本层可解析部分，OCR 结果异步补录（部分可检索优于完全不可见）。
- 要点四：长期解——扫描件占比上升超过 30% 时，评估独立 OCR 集群，不再与解析共享资源池。
- 要点五：预防性设计——容量水位看板提前一周预警趋势，别等 SLA 破了再救火。

❌ 踩坑：只答「加机器」——说不清瓶颈在 GPU、说不清优先级隔离，等于没做过容量管理。

**追问 2**：怎么保证不重复入库？消息重放了怎么办？

- 要点一：幂等键三元组 doc_id + version + stage，状态表 + 唯一索引，重复消息在「检查」一步就被挡掉。
- 要点二：死信修复后重放的是原始消息——幂等保证修复重跑不产生第二份数据，这是设计修复台的前提。
- 要点三：终极兜底是对账——就算幂等全失效，对账 job 也能发现并修正数量级异常。
- 要点四：重复的另一种形态——同文档高频更新（一分钟改五版），版本号幂等保证只入最新版，旧版消息直接丢弃。

❌ 踩坑：说「MQ 是 exactly-once 所以不会重复」——投递语义和业务语义是两层，面试官等的就是这句话。

**追问 3**：为什么要蓝绿？什么时候必须全量重建？

- 要点一：必须全量的两种情况——embedding 模型升级（语义空间变）与切块策略改版（chunk 边界变）；元数据补充用定向重刷不用全量。
- 要点二：蓝绿五步——索引 B 灌满 → 抽样校验 → 别名原子切换 → 灰度观察（双跑对比召回率）→ 下线 A。
- 要点三：代价明说——双倍存储与算力，买的是「秒级回退」；全量 33 分钟的容量账让这一切可行。
- 要点四：回切演练——蓝绿上线前必须实际演练一次回切路径；没演练过的回退等于不存在。
- 要点五：双跑期间的写策略——增量写 A 同步镜像到 B，保证切换瞬间数据不落后——双跑不是只读复刻。

❌ 踩坑：原地升级（边删边建）——中途失败既回不去也没有对照校验，是本题最危险的操作。

**追问 4**：表格和图片里的信息丢了怎么办？

- 要点一：表格转 Markdown 保结构，列头必须拼进每行 chunk——否则「42%」这种数值没有主语，命中了也是废 chunk。
- 要点二：跨页表格先合并再切块；超大表按行组切，表头重复携带。
- 要点三补充：表头识别用「合并单元格 + 字体特征」启发式，识别错的表头比没有表头更糟——宁可不切也不切碎语义。
- 要点三：图片两条路——关键图表走 OCR + 图注描述；进阶用多模态 embedding 直接索引图像语义（成本高，按需启用）。
- 要点四：取舍报数字——多模态索引成本约为纯文本 3-5 倍，只对图表密度高的文档子集启用，不做全库。

❌ 踩坑：「表格转纯文本」——两列表格变一行字符串，列对应关系全毁，检索质量塌方。

**追问 5**：怎么发现「入库了但质量差」的坏数据？

- 要点一：离线侧——质量门禁分拦截 + 1% 分层抽检人审，批次不合格率超 5% 冻结。
- 要点二：在线侧——点击率、引用命中率、拒答率的异常下跌按批次回溯定位坏数据（在线回流是最后防线）。
- 要点三：定位链——坏 chunk → parse_version + 批次号 → 受影响 doc 列表 → 定向重刷，不全量买单。
- 要点四：抽检人审自身要校准——标注规范 + 10% 交叉复核，否则门禁本身质量失控。
- 要点五：门禁指标的月度复盘——拦截率漂移往往早于线上故障，是最灵敏的前置信号。

❌ 踩坑：只靠离线指标——坏数据静默污染检索两周才被用户投诉发现，回溯成本翻十倍。

**追问 6**：这条流水线和你做过的传统 ETL 有什么区别？

- 要点一：同构部分——抽取/转换/加载骨架、幂等、死信、对账、调度、血缘治理，全是老经验直接复用。
- 要点二：差异一：解析是概率性的（OCR 会错、版面会还原错），质量门禁比传统 ETL 更重。
- 要点三：差异二：向量语义无法肉眼校验，质量验收要靠评测集；GPU 资源要错峰调度——这是新增的两块学习成本。
- 要点四：一句话总结迁移性——「骨架是 ETL，血肉是概率性数据处理」，既有老经验兜底，又有新认知加分。
- 要点五：被追问「AI 数据工程和传统最大的思维差异」——答「从确定性校验转向概率性质量经营」，一句话立住认知高度。

❌ 踩坑：只说「差不多一样」——显得没理解 AI 侧的新问题；只说差异不说同构——丢掉迁移性加分。

**追问 7**：元数据为什么不能入库后再补？

- 要点一：pre-filtering 依赖入库时的字段——事后补等于检索侧能力空窗期 + 全量回刷成本。
- 要点二：入库时是信息最全的时刻（来源、格式、权限、时效都在手），过了这个村，很多信息要重新抽取。
- 要点三：新增元数据字段的正确姿势——先加字段默认值，流水线双写，新老数据分区渐进补齐，检索侧渐进启用过滤。
- 要点四：元数据 schema 的变更管理——字段演进走评审，一个字段的误删等于一类过滤能力下线。

❌ 踩坑：上线后再补元数据——权限过滤和时效过滤直接失效，等于裸奔运营。

**追问 8**：GPU 资源在线离线共享，怎么错峰不打架？

- 要点一：资源池统一调度——白天在线推理优先级高，批量向量化任务夜间窗口跑；配额硬隔离防止批量任务饿死在线。
- 要点二：削峰填谷的量化：向量化月需求仅约 5 分钟纯计算，哪怕全部塞进夜间 6 小时窗口，占用率不到 1%——共享毫无压力，数据要报出来。
- 要点三：兜底——在线洪峰时批量任务可暂停（消息回队列），幂等消费保证暂停恢复后无损续跑。
- 要点四：调度颗粒度——按 chunk 批（如 256 条）拆任务，单任务失败重跑的代价被压到秒级。
- 要点五：成本核对——共享池按 token/卡时计费分摊到在线与离线两个成本中心，账目清才能持续共享。

❌ 踩坑：为离线向量化单独采购 GPU 集群——账算不过来，容量思维缺位的典型表现。

### 🎤 口述模板

> 我把入库流水线当一条 ETL 管道设计：上传后原件进对象存储，发 MQ 触发异步处理；解析层按格式路由——普通 PDF 直提文本、扫描件进 GPU OCR 独立队列、表格转 Markdown、HTML 清洗，慢格式不拖快格式；然后统一切块过质量门禁，乱码率、长度分布、截断率不达标就拦截重切或转人工；再批量向量化，与在线推理共享 GPU 池错峰；最后双写向量库八分片和 MySQL 元数据。可靠性三件套：幂等键 doc_id 加 version 加 stage 挡重复消费，三次退避重试加死信队列加人工修复台，每小时对账兜底漏单。更新走增量加墓碑；embedding 升级走蓝绿——新索引灌满、抽样校验、别名原子切换，双倍资源买可回退。容量上百万文档每月折合峰值每秒 4 份，OCR 三卡起步，全量重建千万 chunk 约半小时。这条管道的幂等、死信、对账、蓝绿都是我做大数据管道时的老套路——AI 侧新增的只有解析概率性带来的质量门禁和 GPU 错峰两块。

- 口述节奏：先「这就是 ETL」定调，再按管道顺序展开，最后用可靠性三件套和容量账收尾——90 秒版本。
- 高光点：主动说「幂等、死信、对账、蓝绿是我做过的大数据管道套路」——把转型焦虑打成主场优势。
- 常见误答警示：只画链路不讲可靠性——面试官会判定「没上过生产」；这题的分数一半在失败处理。
- 数字锚点补充：SLA 30 分钟里计算只占 10 秒——其余全是排队与治理，这题的本质是调度题不是算力题。
- 数字锚点：峰值 4 份/秒、OCR 3 卡、全量重建 33 分钟、重复率 15%——四个数字撑起全场。

### 一句话总结

> 入库流水线的满分答案 = ETL 映射定调 + 格式路由防队头阻塞 + 质量门禁双向闭环 + 幂等/死信/对账三件套 + 蓝绿切换可回退——数据侧老经验全量迁移，AI 味只在解析概率性与 GPU 错峰两处。

> 延伸记忆：状态机是底座（幂等/对账/重放全靠它）、内容哈希是身份（去重/缓存全靠它）、水位是纪律（积压超阈值禁发布）——三个关键词顶三段论述。

## 题 11｜Token 成本工程与缓存体系：月账单 50 万 → 10 万

> **一句话考察点**：业务跑起来后月账单 50 万，怎么系统性地砍到 10 万——KV Cache/前缀缓存的原理与 Prompt 静态/动态排列、prompt caching 计费差异、语义缓存（时效与权限隔离）、模型级联、成本归因、预算熔断，外加 Token 消耗异常排查链。
>
> **考频**：⭐⭐⭐⭐⭐（考频校准：成本题是增速最快的题型——业务上线后必然出现；「KV Cache 为什么能降成本」「Prompt 静态/动态怎么排列」「Token 消耗过快怎么排查」「语义缓存适合哪些请求」均被真实考到；一面考缓存原理，二面考失效与隔离设计，三面考归因与熔断体系）

| 我问 | 面试官答（假设） | 对设计的影响 |
|---|---|---|

### 架构图


### 关键设计决策表

**决策 1｜KV Cache / 前缀缓存原理 + Prompt 排列**（被问「为什么能降成本」的标准答案）：

- 原理一：Transformer 自回归推理分两阶段——prefill（处理全部输入，算力密集）+ decode（逐 token 生成）。
- 原理二：注意力计算需要每个输入 token 的 Key/Value 投影；**相同前缀的 K/V 矩阵可以跨请求复用**，跳过重复的 prefill 计算。
- 原理三：省的是 GPU 算力（FLOPs）而不只是带宽——推理成本主要在 prefill，命中前缀缓存等于这段白送。
- 原理四：推理服务因此按「cached input token 大幅打折」计费（约原价 1/10），折扣来自真实算力节省，不是促销。

一张图记住 prefill 与 decode 的成本差异：

```text
请求A：[系统提示 2K][检索 0.5K][问题 0.1K] → prefill 2.6K → 生成 0.4K
请求B：[系统提示 2K][检索 0.7K][问题 0.2K] → 前缀 2K 命中 KV Cache（1/10 价）
                                    只 prefill 后缀 0.9K → 生成 0.4K
```

Prompt 排列规则（真题：静态/动态如何排列利用缓存）：

| 排列 | 结构 | 缓存效果 |
|---|---|---|
| ❌ 动态在前 | 时间戳 + 用户名 + 系统提示 + 问题 | 每次前缀都不同，命中率趋近于零 |
| ✅ 静态在前 | 系统提示 + few-shot + 工具定义（稳定不变）→ 检索片段 + 用户问题（变化） | 最长公共前缀稳定，命中率高 |

- 细则一：缓存按**最长公共前缀**逐 token 命中——中间插一个变化的 token，其后全部失效。
- 细则二：few-shot 示例固定顺序；系统提示版本化，升级 = 前缀全体失效一次，挑低峰发版。
- 细则三：检索片段这种「半动态」内容排静态区之后、用户问题之前——能蹭到的公共前缀尽量蹭。
- 细则四：多轮对话的历史消息放中段并做摘要截断——全量历史既爆 token 又打断前缀，两头亏；历史每多带一轮约多 1K token，摘要截断到 2K 是标配。

❌ 踩坑：把「当前时间」放在系统提示第一行——每秒前缀都在变，前缀缓存全废。

**决策 2｜prompt caching 计费差异**：

| 计费项 | 常规定价 | 缓存命中定价（量级） | 说明 |
|---|---|---|---|
| 输入 token | 1×（如 ¥15/百万） | ≈ 1/10（如 ¥1.5/百万） | 命中越多省越多 |
| 缓存写入 | 1× 或略高 | — | 首次请求多付一点，换后续十倍折扣 |
| 输出 token | 4×（如 ¥60/百万） | 不缓存 | 生成内容每次不同，无从缓存 |

- 结论一：**能进静态前缀的全进前缀**——这是零质量损失的省钱，优先级最高。
- 结论一的推论：系统提示越稳定越长，前缀缓存的收益越大——「精简提示词」在这套计费下反而是反直觉的误操作。
- 结论二：输出比输入贵 4 倍——压输出长度（max_tokens、结构化精简）比抠输入更划算。
- 结论三：不同模型的缓存折扣率不同（1/5 到 1/10 不等）——选型时把「缓存单价」当一等公民比较，不只看原价。
- ❌ 踩坑：只盯输入 token 总数，不看「其中多少命中缓存」——同样 3K 输入，全价与 1/10 价差十倍。

**决策 3｜语义缓存设计**（真题密集区：适合哪些请求？时效与权限怎么处理？）：

| 设计点 | 方案 |
|---|---|
| 原理 | 问题向量化 → 与缓存 key 近邻检索 → 相似度 ≥ 0.95 直接返回缓存答案 |
| 相似度阈值 | 0.90-0.98 权衡：低→命中率高但答非所问；高→安全但命中率跌；从 0.95 起用 badcase 集调 |
| 分层 | L1 精确缓存（问题归一化后 hash 完全相等）+ L2 语义缓存（向量近邻）——先 L1 后 L2 |
| key 设计 | 问题向量 + 模型版本 + Prompt 版本 + 知识库版本 + 权限域 |
| 失效·数据时效 | 依赖的源数据更新 → 知识库版本号 bump → 整代失效；TTL 兜底（如 24h） |
| 失效·权限隔离 | tenant_id + 权限位进缓存 key（或按租户分缓存命名空间）——绝不跨租户命中 |
| 适配请求 | 高频、事实稳定、弱个性化（FAQ/政策/产品说明类） |
| 不适配请求 | 强时效（行情/库存）、强个性化（个人数据）、创作类（每次都要新意） |
| 冷启动策略 | 新场景先只开 L1 精确缓存，观察两周错答率再开 L2 |

- 命中答案附来源引用与「来自缓存」标记——用户可校验，出问题可追溯。
- 缓存容量治理：按「问题频次 × 答案稳定性」打分淘汰，高频稳定的长留，长尾的定期清——缓存本身也有成本。
- 观测指标三件套：命中率、命中后负反馈率、平均节省金额——只看命中率会把缓存做成事故源。
- 缓存的缓存：语义缓存的 key 向量索引本身也做热点驻留——高频问题的近邻检索走内存，长尾走磁盘。
- ❌ 踩坑一：缓存 key 不含权限维度——A 租户命中 B 租户的答案，安全事故级错误。
- ❌ 踩坑二：强时效问题也缓存——「今天有什么公告」返回昨天的答案，时效事故。

**决策 4｜模型级联省钱路由**：

| 层 | 模型 | 分流 | 单价 | 职责 |
|---|---|---|---|---|
| L1 | 规则 + 蒸馏小模型 | 50% 简单请求 | ≈1/10 | FAQ 直答、意图分类 |
| L2 | 中档模型 | 35% 中等请求 | ≈1/3 | 常规问答、摘要 |
| L3 | 旗舰模型 | 15% 复杂请求 | 1× | 推理、长文、多约束 |
| 兜底 | 置信度低自动升级重试 | — | 多一次小模型钱 | 质量保底 |
| 观测 | 升级率 / 负反馈率双指标 | 100% | 路由健康度 |

- 分流信号：分类器难度打分、输出格式异常检测、用户负反馈率——三个信号联合判定。
- 路由本身要便宜：分类器用蒸馏小模型或规则，路由成本超过节省额就是负优化——这笔账要算。
- 场景白名单：核心场景（付费用户、法务合规）强制旗舰模型，级联只作用于长尾——商业风险隔离。
- 级联的极限：三档足够——档位越多路由越容易错，维护成本吃掉省钱收益。
- ❌ 踩坑：级联无兜底——简单请求答崩了没人管；路由分类器本身也要用蒸馏小模型，别用旗舰模型做分流。

**决策 5｜成本归因体系**（不知道钱花在哪，一切优化都是盲剪）：

| 维度 | 示例 | 动作 |
|---|---|---|
| 按租户 | A 租户占 40% 账单 | 配额、计费、限流谈判 |
| 按场景 | 客服 60%、摘要 25%、其余 15% | 优化优先级排序 |
| 按阶段 | prefill / decode / 缓存命中占比 | 判定前缀缓存效果 |
| 按版本 | Prompt v8 上线后单次成本涨 2 倍 | 定位变更、回滚或重构 |

- 落地：每次请求记 trace 日志（input/output/cached token 数、模型、场景、租户、Prompt 版本、各层缓存命中标记），日聚合进看板。
- 看板设计原则：一屏三层——总账单、四维拆解、单请求构成——从「多少钱」一路下钻到「哪次请求哪个字段多了」。
- 周报机制：每周固定出「环比异动 top5」——成本治理常态化的抓手。
- ❌ 踩坑：只有总账单没有归因——50 万花在哪都不知道，优化无从下手。

**决策 6｜预算管控与超额熔断**：

| 层级 | 机制 | 触发动作 |
|---|---|---|
| 租户月度预算 | token 配额 + 用量预警 | 超限降级到小模型/限流，不是硬拒 |
| 分钟级 TPM 熔断 | 突增防护（重试风暴/爬虫） | 保护后端与钱包 |
| 全局日预算 | 80% 告警 / 100% 降级链 | 先降非核心场景 |
| 熔断恢复 | 半开探测（同熔断三态） | 流量正常后自动恢复 |

- 降级顺序：级联换小模型 → 砍 top-k 上下文 → 关闭非核心场景 → 排队——每一步都是「降质可用」而非「停服」。
- 熔断粒度：按租户 + 场景双维度熔断——一个场景异常不拖全局下水，爆炸半径可控。
- 演练常态化：每季度人为触发一次超额，验证熔断与降级链真的能动——没演练过的预案是装饰品。
- 熔断与降级的区别要讲清：熔断挡的是异常流量（保护系统），降级服务的是预算目标（保护钱包）——两个开关两件事。
- ❌ 踩坑：超额直接拒绝所有请求——商业事故；正确姿势是永远给用户留一个降级可用的出口。

**决策 7｜输出治理**（输出比输入贵 4 倍，最容易被忽略的一刀）：

| 手段 | 做法 | 收益 |
|---|---|---|
| max_tokens 硬顶 | 按场景设上限（客服 500 / 摘要 800） | 杜绝长篇失控 |
| 结构化输出 | 强制 JSON/模板字段，砍废话 | 输出长度平均砍 30% |
| 约束风格 | 提示词明确「简洁、要点式」 | 与结构化双管齐下 |
| 响应式截断 | 超长输出分段续写而非一次性放开 | 保体验同时保上限 |

**决策 8｜缓存体系总览**（四层缓存一张表收口）：

| 层 | 缓存什么 | 命中收益 | 失效复杂度 |
|---|---|---|---|
| L1 精确缓存 | 归一化问题的 hash | 整次请求免费 | 低（版本号） |
| L2 语义缓存 | 问题向量近邻 | 整次请求免费 | 高（时效+权限） |
| L3 前缀缓存 | Prompt 静态前缀的 KV | 输入 1/10 价 | 低（改前缀才失效） |
| L4 结果复用 | 相同任务批处理合并 | 摊薄请求 | 中（任务去重） |
| L5 会话级复用 | 同会话共享检索结果 | 省重复检索 | 低 |

- 判断顺序 L1 → L2 → L3：便宜的先查，贵的后查——缓存层级本身也是成本。
- ❌ 踩坑：四层缓存各自为政没有总览——出一次「答案错乱」事故，排查不知道从哪层下手。

**决策 9｜省钱与质量的守门体系**（每一刀都要有质量护栏）：

| 优化刀 | 质量护栏 | 指标红线 |
|---|---|---|
| 语义缓存 | 命中后负反馈率监控 + badcase 集 | 负反馈率 > 基线 1.5 倍即回滚阈值 |
| 前缀缓存 | 无质量风险，只验行为等价 | 输出 diff 抽检一致率 > 99% |
| 模型级联 | 离线评测集通过率 + 线上升级率 | 升级率 > 20% 说明分流失效 |
| 输出治理 | 结构化输出校验 + 长度分布监控 | 截断率 > 0.5% 即放宽上限 |

- 核心思想：**每省一笔钱都要回答「质量代价谁签字」**——没有护栏的优化是埋雷，不是工程。
- 双门机制：上线前离线评测门 + 上线后线上指标门，两道门都过才算落袋。
- 护栏的成本意识：护栏本身也花钱（评测集维护 + 监控算力），通常占节省额 3-5%——要报，但别省。

**决策 10｜FinOps 组织与流程**（技术之外的半个答案）：

| 机制 | 做法 |
|---|---|
| 成本看板周会 | 按租户/场景的周账单 review，异常环比即时解释 |
| Prompt 变更评审 | 改 Prompt 如改代码——token 影响估算进评审单 |
| 预算进目标 | 各场景负责人背单次请求成本指标 |
| 告警责任制 | 谁的场景谁响应，超预算 24 小时内出归因报告 |
| 上线前估费 | 新场景上线必须附 token 预估，无预估不上线 |

- 为什么讲组织：成本问题的根因常是「没人对账单负责」——技术体系再好，没有流程闭环照样复发。
- 半步之遥的提醒：只答技术不答流程，本题最多拿 80 分——最后 20 分在「谁负责、多久看一次」。
- ❌ 踩坑：只建技术体系不建流程——三个月后账单悄悄涨回去，因为没有人持续看护。

### 容量估算

**基线账单拆解（月 50 万怎么花掉的）**：

- 单价整数化假设：输入 ¥15/百万 token、输出 ¥60/百万、cached 输入 ¥1.5/百万（主流旗舰模型量级）
- 月 600 万次主力请求，均次输入 3K、输出 400 token
- 口径提醒：单价取整数便于口算，量级与结构和真实账单对得上才算过关——面试官会核你的口径自洽性
- 输入：600 万 × 3K = 180 亿 token ≈ 200 亿口径 → 20000M × ¥15/M = **¥30 万（占 60%）**
- 输出：600 万 × 400 = 24 亿 token = 2400M × ¥60/M ≈ **¥15 万（占 30%）**
- 其他（embedding / rerank / 小模型）：≈ **¥5 万（占 10%）**
- 合计 **¥50 万**——输入六成、输出三成、杂项一成的结构先钉死

**逐刀推演（50 万 → 10 万）**：

- 第一刀·语义缓存：高频 FAQ 命中 25% 请求 → 剩 450 万次，账单整体 ×0.75 ≈ **37.5 万**
- 第二刀·前缀缓存：剩余请求输入中 60% 是静态前缀且命中 → 输入成本 = 30 × 0.75 × (0.6×0.1 + 0.4×1) ≈ **10 万**（原 22.5 万砍半再砍半）
- 第三刀·模型级联：50% 请求路由到 1/10 价小模型 → 剩余成本 ×(0.5×0.1 + 0.5×1) = ×0.55 ≈ **14 万**
- 第四刀·输出治理：max_tokens + 结构化，输出 token 减三成 ≈ 再省 2-3 万 → **≈11 万**
- 第五刀·杂项治理：embedding 批处理、非核心场景错峰 → **≈10 万，达标**
- 结论：**没有单点银弹，四层各砍一刀**；顺序是先缓存（零质量损失）再级联（可控质量损失）最后动输出
- 推演的展示技巧：每一刀报「乘子」（×0.75 / ×0.46 / ×0.55）——乘子连乘就是答案，面试官跟着算跟着信

**数字速答卡**：

| 口算题 | 答案 |
|---|---|
| 输入/输出单价口径 | ¥15/百万 与 ¥60/百万（4 倍差） |
| cached 输入单价 | ≈ ¥1.5/百万（1/10） |
| 月 600 万次 × 3K 输入 | ≈ 200 亿 token = ¥30 万 |
| 语义缓存命中 25% | 账单 ×0.75 |
| 前缀覆盖 60% 输入 | 输入成本 ×0.46 |
| 级联 50% 走小模型 | 成本 ×0.55 |
| 四刀合计 | 50 万 → 约 10 万 |
| 缓存系统自身成本 | < 节省额 5%（ROI 为正但要报） |

**命中率与收益的敏感性**（为什么 0.95 阈值不能乱降）：

- 语义缓存阈值 0.95 → 0.90，命中率可能从 25% 涨到 35%，但错答率翻倍——省的钱不够赔一次客诉。
- 前缀缓存覆盖率每提升 10 个点，输入成本再降约 6%——把系统提示做长做稳反而是省钱（与直觉相反）。

**缓存基础设施自身的成本**（别忘了省钱的工具也要钱）：

- 语义缓存的向量检索：百万级 key 的近邻索引，一台中等机器搞定——相对节省额九牛一毛，这笔账要报。
- 缓存存储与失效计算：知识库版本 bump 引发的整代重建，低峰执行——失效风暴本身就是一次小型「流量洪峰」。
- 结论：缓存系统成本通常小于节省额的 5%——ROI 为正但要说出来，体现算账习惯。

**四刀的 ROI 排序**（先做哪个的决策依据）：

| 优化刀 | 月节省（本题口径） | 质量风险 | 实施周期 | ROI |
|---|---|---|---|---|
| 前缀缓存（改排列） | ≈12 万 | 零 | 一周 | 最高 |
| 语义缓存 | ≈12 万 | 中 | 两周 | 高 |
| 模型级联 | ≈13 万 | 中 | 三周 | 高 |
| 输出治理 | ≈3 万 | 低 | 一周 | 中 |

**与题 9/10 的联动**（三题数字口径自洽）：

- 题 9 的生成账单（月 100 万次 ≈ ¥7.5 万）就是本题的输入之一——流量与单价假设前后一致。
- 题 10 的知识库版本号是本题语义缓存失效的触发器——数据侧 bump，成本侧整代淘汰，两题共用一个事件源。
- 检索 top-k 的削减（题 9 降级链）同时是本题的成本手段——砍 top-k 既省延迟也省输入 token，一石二鸟。

### 追问链

八层追问覆盖本题九成战场，每层先给要点再标踩坑；追问的顺序就是面试官注意力的顺序，前两问答稳，后面才有深挖价值：

```text
追问链地图：KV Cache原理 → Prompt排列 → 语义缓存适配 → 时效权限隔离
→ 命中率vs幻觉 → Token暴涨排查 → 级联质量兜底 → 再砍一半怎么办
```

**追问 1**：KV Cache 为什么能降成本？（原理题，一字不差地准备）

- 要点一：prefill/decode 两阶段——prefill 处理全部输入是算力大头，decode 逐 token 生成。
- 要点二：注意力的 K/V 投影只依赖已见前缀——相同前缀的 K/V 跨请求复用，跳过重复 prefill。
- 要点三：省的是真实 GPU 算力，推理服务因此给 cached token 打约 1 折——折扣有物理基础，不是营销。
- 补充：prefix cache 的容量有限（按 token 量淘汰），静态前缀要控制长度——前缀越长命中率越高但占缓存越多，存在平衡点。
- 反问加分：被问「为什么输出不能缓存」——生成依赖完整上下文的随机性，相同输入也可能要不同表达（创意场景），所以只缓存「事实型答案」不缓存「生成过程」。
- ❌ 踩坑：答「因为缓存了结果」——KV Cache 缓存的是中间计算状态，不是最终答案，一字之差暴露不懂推理。

**追问 2**：Prompt 静态/动态怎么排列？为什么顺序影响命中？

- 要点一：静态在前（系统提示 + few-shot + 工具定义）、动态在后（检索片段 + 用户问题）。
- 要点二：按最长公共前缀逐 token 命中——前缀里任何一个位置变了，其后全部失效，所以顺序就是命中率。
- 要点三：系统提示版本化 + 低峰发版——升级提示词等于主动放弃一次全量缓存，要挑时段。
- 要点四：工具定义（function calling schema）也进静态前缀——工具列表稳定且动辄上千 token，是常被忽略的缓存大户。
- ❌ 踩坑：时间戳、用户名放在头部——每秒都在变的前缀，缓存形同虚设。

**追问 3**：语义缓存适合哪些请求？哪些绝对不能上？（真题）

- 要点一：适合三条件——高频、事实稳定、与用户上下文弱相关（FAQ / 政策 / 产品说明）。
- 要点二：不适合三类型——强时效（行情库存）、强个性化（个人数据）、创作类（要求每次不同）。
- 边界案例答题法：「退货政策是什么」适合缓存；「我的订单能退吗」不适合——前者事实稳定，后者绑定个人状态，边界讲清即满分。
- 要点三：灰度策略——新场景先只开 L1 精确缓存，观察两周错答率再加 L2 语义层。
- 要点四：上线后的「缓存命中率 × 错答率」双曲线要一起看——命中率涨错答率也涨等于白干。
- ❌ 踩坑：答「所有查询类请求都适合」——绝对化的答案在这题必错。

**追问 4**：语义缓存的数据时效和权限隔离怎么处理？（真题，安全红线）

- 要点一·时效：知识库版本号进 key，源数据更新版本号 bump、整代失效；TTL 兜底防漏网；时效敏感类型走白名单直接跳过缓存。
- 要点二·权限：tenant_id + 权限位进 key（或租户独立命名空间），物理上杜绝跨租户命中。
- 要点三：缓存答案带「来自缓存 + 生成时间 + 引用来源」标记——出了时效问题可追溯可回收。
- 要点四：失效风暴的量化——知识库日更触发整代失效，缓存命中率每天有一个低谷窗口，选在低峰 bump 版本把冲击降到最小。
- ❌ 踩坑：只答 TTL——版本化失效粒度粗但正确性优先；TTL 是兜底不是主机制。

**追问 5**：命中率调高，错答（幻觉）风险怎么权衡？

- 要点一：阈值 0.95 起步，用 badcase 集离线调——每降 0.01 都要有错答率数据背书，不拍脑袋。
- 要点二：场景分级——FAQ 低风险场景高命中；医疗法务高风险场景关闭语义缓存只留精确缓存。
- 要点三：线上反哺——监控「命中后用户重问率 / 负反馈率」，异常升高即回滚阈值。
- 要点五：给「错答」留逃生门——命中返回时附带「重新生成」入口，用户一次点击即绕过缓存——信任的最后一道保险。
- 要点四：命中答案附引用可校验——用户能点开出处，错答的伤害半径被引用机制截断。
- 要点六：阈值的场景化——同一系统里 FAQ 场景 0.92、高风险场景 0.97——一个全局阈值管所有场景是偷懒设计。
- ❌ 踩坑：为冲命中率把阈值降到 0.85——省的是小钱，赔的是信任。

**追问 6**：Token 消耗突然暴涨，怎么排查？（真题，排查链要背熟）

- 要点一·排查链：日账单看板异常 → 按场景/租户/Prompt 版本归因下钻 → trace 抽样看单次请求 token 构成 → 定位变更 → 回滚或修复 → 看板验证闭环。
- 要点二·构成四问：系统提示膨胀了？检索 top-k 变多了？输出变长了？重试放大了？——单次请求的 token 构成图一拉，元凶现形。
- 要点二补充：区分「流量性暴涨」与「单次性暴涨」——前者看租户/场景维度，后者看 Prompt 版本维度，两条排查线不要混。
- 要点三·常见元凶排行：Prompt 版本变更（few-shot 从 3 例加到 10 例）、top-k 调大、重试风暴、爬虫刷量、输出模板变长。
- 排查提速技巧：把「单次请求 token 构成」（系统提示/历史/检索/输出四段占比）做成 trace 默认字段——暴涨时一眼定位是哪段膨胀。
- ❌ 踩坑：第一反应「加预算」——治理症状不治理病因，下个月账单再翻倍。

**追问 7**：级联省钱会不会把质量砍了？

- 要点一：置信度兜底——小模型输出低置信自动升级旗舰重试，质量下限由兜底守住。
- 要点二：离线评测集守门——小模型在评测集通过率达标才放量；灰度 5% → 50% → 100%。
- 要点三补：分级不是一次定终身——每月用最新 badcase 重标难度分布，路由边界要跟着漂移。
- 要点三：线上监控——负反馈率、升级率两个指标盯死，升级率异常升高说明路由分类器退化了。
- 要点四：路由规则的透明度——分档规则要可解释（什么问题进哪档），黑盒路由出问题没法排查。
- ❌ 踩坑：无兜底全量切小模型——省了 40% 成本，掉了一半满意度，得不偿失。

**追问 8**：老板说 10 万还是太贵，再砍到 5 万呢？

- 要点一：报边际成本递增——缓存与级联的红利已吃满，剩下的都是架构级动作。
- 要点二：架构级选项——蒸馏自有小模型（前期投入大）、非实时场景转批处理、长尾场景下线、请求合并。
- 要点三：管理预期——给出「每砍 1 万损失什么」的对照表，让决策方在知情下选择。
- 要点四：最后一张牌是产品策略——降级体验（延迟换价格）、功能分层（付费用户优先）——成本工程的终点是产品决策，不是技术执念。
- ❌ 踩坑：拍胸脯说随便砍——成本工程的可信度来自量化的边界，不是无限的承诺。

**追问链收束**：八层追问的三条红线——原理题不许错（KV Cache）、安全题不许糊（权限与时效）、数字题不许空（账单推演）；任何一条失守，本题从亮点变扣分。

### 🎤 口述模板

先拆账再动刀，最后上锁——这段话就是本题的 90 秒开场：

> 月账单 50 万我会先拆账：按租户、场景、阶段、Prompt 版本四个维度归因，假设输入占 60%、客服场景占一半。然后四层递进优化：第一层语义缓存，高频 FAQ 相似度 0.95 以上直接返回，权限和知识库版本进缓存 key，命中 25% 请求；第二层前缀缓存，把系统提示、few-shot 等静态内容排前、检索片段和用户问题排后，让 KV Cache 命中最长公共前缀，cached token 按 1/10 计费——它的原理是相同前缀的 K/V 矩阵跨请求复用，省掉重复的 prefill 算力；第三层模型级联，小模型接 50% 简单请求，置信度低自动升级旗舰兜底；第四层输出治理，max_tokens 硬顶加结构化输出。数字上：30 万输入经前缀缓存降到约 10 万，级联再乘 0.55，输出再砍三成，账单从 50 万落到 10 万左右。最后是防复发：分钟级 TPM 熔断、租户月度预算、日预算 80% 告警；Token 暴涨走「看板 → 归因下钻 → trace 抽样 → 定位 Prompt 版本」的排查链。核心原则：先缓存后级联——先动质量安全的刀，再动质量有损的刀。

- 口述节奏：拆账 15 秒、四层各 10 秒、数字推演 20 秒、防复发 15 秒——全程 90 秒内说完。
- 数字锚点：输入 ¥30 万 / 输出 ¥15 万 / 杂项 ¥5 万；×0.75、×0.46、×0.55——三个乘子就是三条优化。
- 常见误答警示：只会说「上缓存」三个字说不清哪层缓存挡什么——四层分工表是本题的骨架。
- 主动埋钩子：讲完补一句「语义缓存的失效设计其实和知识库更新联动，可以在数据题里展开」——把面试引向题 10 的主场。
- 万能回退：被问没做过的细节，答「我的优先级排序是 X，因为 ROI 表里 Y」——排序逻辑永远比细节值钱。
- 收尾金句：成本工程的本质不是抠门，是把每一分钱花在用户体验的刀刃上——价值导向收尾，格局立住。

### 一句话总结

> Token 成本工程的满分答案 = 先归因拆账 + 四层递进优化（语义缓存 → 前缀缓存 → 模型级联 → 输出治理）+ 逐刀数字推演 + 熔断与排查链防复发——每一刀都报「省多少、代价什么」。

> 延伸记忆：排列定生死（静态前缀在前）、key 定安全（权限进 key）、归因定优先级（钱花在哪刀往哪）——三个关键词顶三段论述。
> 与题 9 的接口：检索 top-k 和上下文长度既是延迟问题也是成本问题——两题共用同一个旋钮，答任一题都可互相引用。
