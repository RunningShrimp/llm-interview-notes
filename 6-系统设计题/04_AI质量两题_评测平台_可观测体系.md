# 04 | AI 质量设计两题（评测平台 · 可观测 Trace 体系）

> **本章定位**：AI 全栈工程化的「质量侧」。上线只是及格线，「持续又准、又稳、又便宜」才是长期仗。两道题一左一右：评测平台管**上线前**（变更验不验收），可观测体系管**上线后**（线上看得见、坏得知道、错得回流）。这也是后端工程师转型 AI 的优势区——测试工程、CI 门禁、全链路追踪、告警治理，这些后端老本事几乎可以逐字翻译，只是被测对象从确定性代码换成了概率性模型。

## 本章导读

**为什么质量侧是后端转 AI 的主场？**

写业务代码时你早就习惯了：改一行跑一遍单测、合码前 CI 挡一道、线上有 APM 全链路追踪、指标越界就告警。AI 应用把「确定性」换成了「概率性」——同一个输入可能出不同答案，对不对没有 assert 可写——但方法论没变，变的只是打分函数和数据形状。

**两题地图：**

| | 题 12：评测平台 | 题 13：可观测体系 |
|---|---|---|
| 时间轴 | 上线前（离线验收） | 上线后（在线监控） |
| 核心资产 | 评测集 + judge | trace 数据 + 指标三条线 |
| 闭环出口 | 回归门禁接 CI/CD | badcase 回流评测集 |
| 后端原型 | 测试平台 + CI | APM + 监控告警 |
| 一句话 | 「改了之后到底变好没」 | 「线上现在还好吗」 |

**后端老经验 → AI 质量侧翻译表（本章主线）：**

| 后端老经验 | AI 侧对应物 | 翻译要点 | 哪里不一样 |
|---|---|---|---|
| 单元测试 | 评测集（黄金集 + badcase 集） | 用例即资产，版本化、有 owner | 没有 assert 只有分数；用例会过期，要回流换血 |
| CI 门禁 | 回归门禁 | 变更触发 + 阈值卡点 | 通过/失败变成分数区间，要定阈值与放行策略 |
| 全链路追踪 | AI trace（span 树） | 请求→检索→工具→生成逐段埋 span | span 多带 token/成本/模型版本/prompt 版本 |
| 告警 | badcase / 质量告警 | 阈值 + 分级 + 值班响应 | 「错」不是抛异常，是分数下跌或模式漂移 |
| 线上日志排查 | badcase 自动挖掘 | 低分聚类→模式归纳→回流评测集 | badcase 只增不删，是回归资产不是垃圾 |
| 灰度发布 | AI A/B 实验 | 流量分割、样本量、显著性判断 | 主指标是采纳率/满意度这类代理指标 |

一句话主线：**把「测试左移、监控右移」这套双金字塔搬到 AI 上，中间垫一层「概率世界的打分函数」。**

## 题 12｜AI 评测平台（公司级）

> **一句话考察点**：能不能把「prompt/模型/检索改一改，效果到底变好还是变坏」从人工拍脑袋，工程化成有指标体系、有评测集资产、有 judge 治理、有 CI 门禁闭环的公司级平台。
>
> **考察频率**：⭐⭐⭐⭐（AI 平台/中台方向高频题；应用团队也常考缩水版「你们上线前怎么评效果」）

### 需求澄清

拿到题先别急着画图，把边界问清——澄清本身就是得分点：

**Q1：平台服务谁？多大规模？**

A：按业务方数量分三档，答案完全不一样：

| 规模 | 形态 | 平台怎么做 |
|---|---|---|
| 少于 5 个业务 | 共享评测库 + 定时跑批脚本 | 别急着上平台，先攒评测集 |
| 5~30 个业务 | 公司级平台：多租户、评测集隔离、统一 judge 服务 | 本题主战场 |
| 30 个以上 | 评测即服务：自助接入、OpenAPI、SLA | 加配额与优先级调度 |

默认按中间档答：约 10 个业务方，每家 1~3 个核心场景（RAG 问答、摘要、Agent 工具调用）。

追问一句接入形态也很关键：是业务方把评测集交上来平台托管跑批，还是平台只给 SDK 和流水线、业务方在自己 CI 里跑？前者管控强、后者侵入低——生产上一般是「评测集托管 + 执行流水线以 SDK 形式嵌进业务 CI」：资产统一管，跑批贴近业务真实环境。

**Q2：离线评还是在线评？**

A：两层都要，但主角是离线：

- **离线评测**：变更前在评测集上跑分，结果接 CI 门禁——平台的主体
- **在线评测**：A/B 实验看真实行为指标（采纳率、点踩率、留存）——平台只做「对接」，复用公司实验平台，不自建

资深做法是把两层连起来：离线分数是「上岗证」，在线指标是「体检报告」。离线涨、在线跌的变更要被打回复盘——通常是评测集没覆盖线上分布，这本身就是评测集要补血的信号。

> 误区提醒：只做在线不做离线，是常见初级答案——在线指标反馈周期以周计，根本挡不住 prompt 变更；反过来只做离线也会漂——评测集和线上分布脱节。所以要两条腿，且互相校准。

**Q3：谁打分？**

A：三层指标天然对应三种打分方式，这是本题第一个核心结构：

| 指标层 | 打分方式 | 为什么 |
|---|---|---|
| 检索层（recall@k、MRR、引用命中） | 规则计算 | 有标注答案，可精确算，不需要人 |
| 生成层（相关性、事实性、安全） | LLM-as-a-Judge + 人工抽检 | 开放文本没有唯一解，只能语义打分 |
| 系统层（延迟、成本、报错率） | 直接读监控埋点 | 纯工程指标，埋点就有 |

注意采集位和打分方式是一一绑定的：检索层在评测执行器里算、生成层走统一 judge 服务、系统层读监控——后面架构图里的「数据采集位」表，就是把这张表落到组件级。

**Q4：评测结果用来干嘛？出报告还是卡发版？**

A：必须落到门禁。只出报告的评测平台是个「图表工具」，没人看；能阻塞发版才是质量关卡。这个答案直接决定了架构里必须有 CI/CD 集成、通知链路和放行审批流——没有牙齿的质量体系都是装饰品。

补一句时机设计：门禁不是一开始就硬卡——头两周「影子模式」（只记录不阻塞），先攒误拦数据、调阈值，再切换成硬门禁。冷启动就硬卡，第一次误拦就能把业务方的信任耗光。

### 架构图

```
 变更触发: prompt │ 模型 │ 检索配置 │ SDK 发版
     │ webhook / CI 入口                 线上日志
     ▼                                      │
 ┌────────────┐   ┌───────────────────┐     │
 │ 评测编排引擎 │──►│ 评测集仓库(版本化)  │     │
 │ 队列+并行跑批│◄──│ 黄金集 + badcase   │◄────┘
 └──────┬─────┘   │ (badcase只增不删)  │ 挖掘回流:
        ▼         └───────────────────┘ 聚类→人审→入库
 ┌─────────────────────────────┐
 │ 评测执行层: 三层指标+过程评测   │
 │ ①检索 recall/MRR    ②生成judge│
 │ ③系统 延迟/成本/错率 ④过程评测 │
 │   工具调用对不对·引用对不对    │
 └──────┬──────────────┬──────┘
        ▼              ▼
 ┌──────────┐    ┌──────────┐
 │ 报告/看板  │    │ 回归门禁   │──► CI/CD 卡点
 │ 趋势+下钻  │    │ 阈值+放行  │    (阻塞合并/发版)
 └──────────┘    └──────────┘
  在线侧: 对接 A/B 实验平台(不自建), 离在线联动复盘
```

图读法（口述时按编号走）：

1. **左上进**：四类变更源通过 webhook 触发评测——覆盖「任何可能改变输出」的东西，prompt、模型、检索配置、依赖 SDK，漏一类就是回归盲区
2. **中段**：编排引擎从评测集仓库拉数据，任务队列并行跑三层指标 + 过程评测
3. **右上闭环**：线上日志挖掘出的 badcase 经人审回流进评测集——平台「越用越准」的核心机制
4. **两个出口**：报告给人看趋势，门禁卡发版；在线 A/B 走实验平台对接，不做重复建设

**平台内部模块职责（对应后端老物件）：**

| 模块 | 职责 | 后端对应物 |
|---|---|---|
| 触发接入层 | 收 webhook、识别变更类型、路由评测任务 | CI 事件网关 |
| 评测集仓库 | 黄金集/badcase 管理、版本、PR 评审流 | 代码仓库 |
| 编排引擎 | 任务拆分、队列调度、并发控制、失败重试 | 任务调度系统 |
| judge 服务 | rubric 管理、打分、缓存、多裁判路由 | 内部 RPC 服务 |
| 结果聚合 | run 级指标计算、基线 diff、趋势存储 | 报表数仓 |
| 门禁服务 | 阈值判定、放行审批流、CI 状态回写 | 发布卡点服务 |

**一次评测任务的生命周期（10 步走一遍）：**

1. prompt 仓库合并 PR → webhook 打到平台，附带变更 diff
2. 触发接入层识别「影响 RAG 问答业务」→ 拉起评测任务，锁定当前评测集版本
3. 编排引擎拆任务：检索/生成/系统三路并行，worker 池按业务配额调度
4. 被测系统逐 case 推理，过程 trace 全量落档（供过程评测与失败复现）
5. 检索指标即时算；生成答案进 judge 服务——先查缓存，未命中再调模型
6. 三层指标 + 过程指标按 run_id 聚合，与基线 diff
7. 门禁判定：核心指标跌超 2pp → 红，回写 CI 阻塞合并
8. 红了走放行：owner 审批 → 限时白名单 → 标记「带病放行，48 小时内补测」
9. 结果进趋势看板，badcase 明细自动推送业务 owner
10. 月底：日志挖掘管道产出候选 badcase → 人审 → 入库，评测集版本 +1

**数据采集位**（三层指标各自在哪采，这是「落地成平台」的关键）：

| 指标 | 采集位 | 备注 |
|---|---|---|
| recall@k / MRR | 评测执行时，检索结果对比标注引用集 | 检索配置变更必跑 |
| judge 分数 | 评测执行时调统一 judge 服务 | 带缓存，见容量估算 |
| 延迟/成本/报错率 | 沙箱跑批埋点 + 线上监控双份 | 离线压测 + 在线巡检互证 |
| 工具调用/引用命中 | 过程 trace 的结构化字段 | 过程评测的原料，见追问链第 8 层 |

**三层指标字典（平台内置的第一批指标，业务方开箱即用）：**

| 层 | 指标 | 定义 | 计算方式 |
|---|---|---|---|
| 检索 | recall@k | 前 k 条结果命中标注文档的比例 | 规则 |
| 检索 | MRR | 首个命中文档排名倒数的均值 | 规则 |
| 检索 | NDCG | 按标注相关性加权的位置折损排序质量 | 规则（依赖分级标注） |
| 检索 | 引用命中率 | 回答实际引用的文档在标注集内的比例 | 规则 |
| 生成 | 相关性 | 是否回答了用户真正问的 | judge |
| 生成 | 事实性 | 陈述与检索文档是否一致 | judge |
| 生成 | 安全性 | 有无违规、越界内容 | judge + 规则兜底 |
| 系统 | P95 延迟 | 评测沙箱内端到端 | 埋点 |
| 系统 | 单次成本 | token 数 × 单价 | 埋点 |
| 系统 | 报错率 | ERROR / total | 埋点 |

**为什么是这个形状（分层逻辑）：**

- **评测集和执行分离**：集是资产、执行是算力，各自独立演进——集变了不用动引擎，引擎扩容不用动集
- **三层指标在执行层内聚**：检索/生成/系统三类指标采集位不同，但聚合到同一次回归报告里，避免「三个工具三张表」
- **门禁和报告同源**：都吃执行层输出，报告展示全量，门禁只看核心集——一个数据源，两种消费
- **回流是单向阀门**：线上日志→挖掘→人审→入库，人审这道闸不能省，否则线上噪声会把评测集冲烂

### 关键设计决策表

**决策 1：生成质量用什么方案评？**

| 方案 | 怎么做 | 优点 | 缺点 | 适用 |
|---|---|---|---|---|
| 规则/精确匹配 | 正则、指标计算 | 免费、确定、可回归 | 覆盖不了开放生成 | 检索指标、分类任务 |
| 小模型打分器 | 交叉编码器回归打分 | 便宜、毫秒级 | 泛化差，rubric 表达不了 | 单一维度（如相似度） |
| LLM-as-a-Judge | 大模型按 rubric 逐项打分 | 贴近语义、能给出理由 | 贵、会漂、有系统性偏见 | 开放生成主力 |
| 人工全量 | 人审 | 金标准 | 贵、慢、不可回归 | 只做抽检校准 |
| 线上行为指标 | 点赞点踩、采纳率 | 最真实 | 反馈慢、有噪声 | 在线最终验证 |

> 结论：**能规则算的绝不 judge，judge 为主、人工抽检校准、线上指标做终审**。RAGAS 这类开源方案可以参考它的指标设计思路（忠实度、答案相关性），但生产平台一般自建 judge 管道——开源指标嵌不进自家 rubric 和业务语义。对指标名也要去魅：recall@k、MRR、NDCG 谁都会背，真门槛在「标注从哪来」——NDCG 要相关性分级标注，谁标、标注一致性多少、成本几何才是检索评测的真问题，答得出这一层才算没停留在背名字。

一个常被忽略的排序问题：**先建评测集，再挑 judge 方案**——没有 300 条以上的标注样本，任何 judge 方案都无法校准，选型就是空谈。顺序错了，平台会卡在「有打分器但没有尺子」的尴尬里。

**决策 2：judge 怎么治理（本题最容易出彩的地方）？**

| 治理项 | 做法 | 量化标准 |
|---|---|---|
| 上岗校准 | 抽 300~500 条人工标注，算 judge 与人的一致率 | 一致率 ≥ 85% 才准上岗 |
| 校准频率 | 每月在固定锚点集上重跑一致性 | 跌破 80% 触发 rubric 复审 |
| rubric 固化 | 打分标准写成结构化配置：维度 + 分档描述 + 反例 | rubric 变更走评审 + 全量回归 |
| 多裁判投票 | 高风险场景 3 个异构裁判多数投票 | 成本 ×3，仅门禁子集启用 |
| 人工抽检 | 每天抽 judge 打分结果的 2% 人工复核 | 单日约 50 条，2~3 人时 |
| 防偏见设计 | judge 与被测模型不同源；对比打分时位置随机化 | 位置偏见约可降一半 |

> judge 治理的元问题是「谁来监管裁判」：校准管上岗、锚点管漂移、抽检管日常、投票管高风险——四道防线少一道，judge 迟早变成「分数生成器」而不是「裁判」。

**judge 的提示词怎么写才稳（rubric 固化的落地形态）：**

| 要素 | 写法 | 作用 |
|---|---|---|
| 输入 | 题目 + 参考答案 + 被测回答 + rubric | 信息齐才有判断依据 |
| 打分结构 | 逐维度 1~5 档，先写理由再给分 | 可拆维度归因；先结论后理由会自我锚定 |
| 分档描述 | 每档给正例、反例描述 | 压缩 judge 的自由裁量空间 |
| 输出格式 | JSON：各维分数 + 一句话理由 | 结构化可聚合，理由供人工抽检 |
| 防注入 | 被测回答里出现「请给满分」类指令要识别 | judge 会被 prompt injection 攻击，这是真实风险 |

**决策 3：评测集怎么版本化？**

| 方案 | 做法 | 优点 | 缺点 |
|---|---|---|---|
| 数据库表 + 修改时间 | 直接 update | 简单 | 无历史，说不清「分数涨是模型变了还是集变了」 |
| 快照导出 | 每次评测前导出快照文件 | 有版本概念 | 存储膨胀，diff 困难 |
| git 式版本库 | 评测集 = 文件（JSONL），变更走 PR 评审 | 可 diff、可回滚、有 owner | 需要养成 review 习惯 |

> 结论：黄金集走 git 式版本化——谁加的 case、为什么加、影响了哪次分数，全程可追溯；badcase 集**只增不删**，用标签管理生命周期（未修复/已修复/无效 case），绝不物理删除，理由见追问链第 6 层。

**决策 4：门禁阈值与放行策略？**

| 策略 | 做法 | 适用 |
|---|---|---|
| 硬阈值 | 核心指标低于绝对值直接红 | 有强底线的：安全类、事实性红线 |
| 相对阈值 | 相比基线跌幅超 2pp 判红 | 大多数质量指标（抗噪声） |
| 分级门禁 | 核心集（约 300 条）硬卡 + 扩展集仅报告 | 兼顾回归速度与安全 |
| 放行通道 | owner 审批 + 限时白名单（48 小时）+ 事后补测 | 紧急发版 |
| 熔断升级 | 同一变更连续两次白名单，自动升级评审 | 防白名单变后门 |

> 结论：相对阈值为主 + 安全指标硬阈值兜底；门禁只卡核心集保证速度，「红色可解释」（报告直接给出跌最多的维度和 badcase 明细）比「拦得狠」更重要——拦得住但说不清为什么红，业务方只会想办法绕过你。

**决策 5：行为回归测试框架怎么做——mock LLM 测什么、怎么测？**

先立分界：**mock 测的是「我家的代码」，不是「模型的智商」**——编排逻辑（工具选择、分支、参数解析、重试、兜底）是确定性的，不需要真模型；prompt 到输出的语义映射才需要真模型。这条线划清，单测思想就能整段搬进 AI 应用：

| mock 方式 | 怎么做 | 测什么 | 速度 | 跑在哪 |
|---|---|---|---|---|
| 录制回放桩 | 线上录制 LLM 真实响应，按（prompt 版本 + 输入指纹）回放注入 | 工具选择、调用顺序、参数解析、分支流转 | 毫秒级 | 每次 CI 必跑 |
| 规则桩 | 按输入特征返回预设响应：超时、畸形 JSON、拒答、空输出 | 重试、降级、兜底链路真的能走到 | 毫秒级 | 每次 CI 必跑 |
| 快照断言 | 最终结构化输出与基线 diff，变化即 fail | 输出 schema 与契约稳定性 | 毫秒级 | 每次 CI 必跑 |
| 真实模型冒烟 | 小集真调用（50~100 条） | 端到端真实性、模型漂移早期信号 | 分钟级 | 每日定时 + 发布前 |

落地三要点：①**录制库版本化**——模型升级后重新录制，录制 diff 本身就是一份回归信号；②**桩带指纹校验**——prompt 版本变了 mock 自动失效并告警，防止「测的是旧响应还全绿」；③**mock 桩顺带做故障注入**——超时、限流、截断都注入一遍，把稳定性代码路径也纳入行为回归。价值一句话：把「AI 应用没法写单测」的偏见打掉——概率部分交给评测集，确定性部分照样单测覆盖，分层各管一段。

**决策 6：A/B 实验平台化怎么做？**

| 关注点 | 做法 | 量化参考 |
|---|---|---|
| 流量分割 | 按用户哈希分桶，同一用户稳定进同组 | 5%~50%，按预期效应定 |
| 样本量 | 双比例检验：基线采纳率 40%，预期 +3pp，α=0.05，power=0.8 | 单组约 3800~4000 样本 |
| 显著性判断 | p 值 + 置信区间一起看 | p<0.05 且方向一致才算赢 |
| 护栏指标 | 延迟、成本、点踩率做护栏 | 护栏破线立即止损 |
| 持续时长 | 覆盖 1~2 个完整周期波动 | 7~14 天 |

> 结论：A/B 的平台价值不在「能做实验」，而在「实验不翻车」——样本量、护栏、周期这三件套是防止「看见显著就全量」的工程保险。

**决策 7：平台技术底座怎么选？**

| 组件 | 选型思路 | 备注 |
|---|---|---|
| 评测集存储 | git 仓库（JSONL）+ 对象存储放附件 | 版本化天然解决 |
| 执行引擎 | 任务队列 + 容器化 worker 池 | 按业务方配额调度 |
| judge 服务 | 独立微服务 + 模型路由（便宜档/旗舰档） | 缓存层必配 |
| 报告存储 | 列式库，按回归 run_id 组织 | 支撑趋势看板与下钻 |
| 门禁接入 | webhook + 状态回写公司 CI | 有门禁 API 就直接复用 |

> 原则：**能复用公司基建就复用**（CI、队列、看板、权限），平台真正自研的只有「评测语义」这一层——评测编排、judge 管道、集管理。资深和初级的差距常在这里：初级画一堆新组件，资深先列哪些不用建。

**决策 8：离线分数和在线指标怎么联动？**

| 环节 | 做法 | 目的 |
|---|---|---|
| 上线前 | 离线门禁绿 → 允许进实验 | 上岗证 |
| 实验期 | 在线 A/B 主指标 + 护栏指标 | 体检报告 |
| 全量后 | 在线指标巡检，异常自动触发 badcase 挖掘 | 事后追踪 |
| 复盘 | 离在线不一致的变更，强制标注原因（评测集缺覆盖/分布漂移/指标失真） | 反哺评测集 |

> 离在线不一致不是麻烦，是评测集最宝贵的补课清单。

**决策 9：模型或 Prompt 升级后线上质量下降，怎么定位、怎么回滚？**

这是评测平台的「售后场景」，也是被反复问到的原题。定位三板斧，按顺序走：

1. **先查门禁历史**：这次变更离线分到底跌没跌？跌了但被白名单放行 → 流程问题；没跌 → 离线评测集没覆盖线上分布，是评测集失真——两种结论的整改动作完全不同
2. **按版本 pivot 线上指标**：质量三线指标按「模型版本 × prompt 版本 × 检索配置版本」切分，锁定跌幅集中在哪个版本、哪个场景桶，再拉该桶 badcase 聚类看共性
3. **trace 回放双跑对比**：取跌幅最大场景桶的采样 trace，用记录的完整现场（渲染后 prompt、检索快照、采样参数）在新旧版本上各跑一遍，确认归因

回滚手段按粒度备好三档，别出事才想：

| 手段 | 粒度 | 耗时 | 事前前提 |
|---|---|---|---|
| prompt 版本回退 | prompt 库双版本热切换 | 秒级 | prompt 已入库版本化 |
| 模型别名切换 | 网关路由切回旧版本 | 分钟级 | 新旧并行期保留旧实例 |
| 灰度暂停 / 全量回退 | 关分流、回退发布 | 分钟级 | 变更可逆性设计 |

> 核心是两个「事前」：**升级前基线留档**（没有对比物，跌了也不知道跌多少）、**trace 记全可回放**（没有证据链，归因全靠猜）。这两个没做，出事只能干瞪眼；做了，回滚就是按按钮的事。回滚权限也要事前定义好——质量红灯谁拍板，别等出事再吵。

### 容量估算

先拍数：10 个业务方 × 平均 1000 条/家 = **全公司 1 万条评测集**。

**热身算例（面试现场怎么快算 judge 成本）：**

「1 万条 × 2500 token = 25M token；按 ¥12/M 一除，约 300 元；增量只跑两成、缓存再砍四成，日常一天几十块。」——先乘后除、量级优先，数字取整不报小数点：面试官要的是量级判断力，不是计算器。

**单次全量回归的调用成本：**

- 被测系统调用：1 万次 × 平均 3k token（RAG 场景上下文大）≈ 30M token
- judge 调用：1 万次 × 2.5k token（题目 + 参考答案 + rubric + 被测回答）≈ 25M token
- 按主流模型价位量级（输入约 ¥10~15/M token）：单次全量 ≈ **几十到几百元**
- 三裁判投票只给门禁子集约 1000 条：额外 ×2 成本，可控

**频次与缓存：**

- 变更触发每天约 30 次，多为**增量回归**：只跑受影响业务 + 变更相关子集（约全量的 20%）
- judge 结果缓存：键 = `hash(题目版本, 被测输出, rubric 版本, judge 模型版本)`，命中即免调
- prompt 没改到的 case 输出不变，缓存命中约 60%，**日成本压到百元级**

**存储：**

- 单次回归结果（含过程 trace 数据）：1 万条 × 2KB ≈ 20MB
- 每天 30 次增量 + 2 次全量 ≈ 100MB/天，保留 12 个月 ≈ **36GB**——一个对象存储桶的事
- mock 录制库：每业务线 500 条录制 × 3KB ≈ 1.5MB/线，模型升级重录一次——存储忽略不计，护住的是 CI 秒级行为回归

**人力：**

- 人工抽检每天 50 条 × 3 分钟 ≈ 2.5 人时，一个 QA 兼职可扛
- 日志挖掘回流：每月一次集中清洗约 2 人日

**成本敏感度（哪个参数最伤钱）：**

| 变量 | 摇一下 | judge 费用变化 | 结论 |
|---|---|---|---|
| 业务方数量 | 10 → 20 家 | ×2 | 线性涨，可控 |
| 单家评测集 | 1000 → 3000 条 | ×3 | 有边际递减，黄金集不必贪大 |
| 触发频次 | 30 → 100 次/天 | 近 ×3 | 靠增量子集选择压住 |
| judge 模型档位 | 便宜档 → 旗舰档 | ×5~10 | 非门禁场景一律便宜档 |

**单个业务方接入成本（平台推广的隐性指标）：**

- 首次接入：整理 300 条种子集约 2 人日 + 配置 rubric 约 1 人日
- 日常维护：每周看一次报告 30 分钟，每月回流清洗半天
- 接入成本高于这个数业务方就会用脚投票——平台要把「接入摩擦」当核心体验指标来打

**冷启动路线（平台从 0 到 1）：**

| 阶段 | 动作 | 里程碑 |
|---|---|---|
| 第 1 个月 | 2 个业务方试点，各 300 条种子集（从线上日志人工挑） | judge 校准 85% 跑通 |
| 第 2~3 个月 | 接入 5 个业务方，黄金集扩到 1000 条/家 | 门禁挂非核心链路试运行 |
| 第 4 个月起 | 全量推广，badcase 回流管道上线 | 进入「越用越准」循环 |

**平台自身建设成本（面试官常问「要几个人」）：**

- 最小团队：2 后端（编排引擎 + judge 服务）+ 1 数据（评测集与回流管道），复用公司 CI/看板
- 第一版工期约 6~8 周：先跑通「触发→跑批→报告」，门禁第 2 个月再上——先有可信分数，再谈卡点
- 运维常态：每天巡检门禁结果 + 抽检复核约 0.5 人力，其余自动

> 冷启动最容易死在「没人愿意先喂评测集」——所以第 1 个月平台团队要自己下场帮业务方标数据，先把第一份回归报告做出来，用结果换信任。

> 这组数字的意义：证明评测平台不是「太贵玩不起」的奢侈品——**一天一杯咖啡钱，换每次变更都有回归兜底**。算得出成本，才说得清平台值不值得建。

### 追问链

**第 1 层：「judge 校准 85%」这个数怎么定出来的？**

抽 300~500 条人工标注样本（高/中/低分分段抽样，不能只抽好认的），judge 与人工结论的一致率 ≥ 85% 才上岗。两个坑要主动说：一是**分段看一致率**——judge 往往高分段准、低分段差，总分 85% 可能掩盖低分段只有 60%；二是 85% 是工程约定不是物理常数，本质是「错判代价 × 频率」可接受的人机共识，高风险业务要抬到 90%。

另外口径本身也要说清：严格一致（完全同判）还是宽松一致（相邻档位算对）——严格口径下 85% 相当高，宽松口径下 85% 只是及格线。**口径比数字重要**，这一句能体现你真做过标注对齐。

**第 2 层：judge 自己会漂移吗？怎么发现？**

会。judge 模型升级、输出风格变化都会漂。对策：**每月在固定锚点集上重跑**（锚点集 = 人工结论稳定不变的几百条），锚点一致率跌破 80% 触发 rubric 复审；同时监控 judge 分数分布的整体漂移（KS 检验），分布突然变形说明 judge 或被测方必有一方变了。

**第 3 层：judge 用什么模型？跟被测模型同款行不行？**

不行，**同源有自恋偏置**——裁判会偏向「自家写法」的输出风格。原则：judge 档位 ≥ 被测模型档位（弱裁判评不了强选手），且不同源；门禁等高风险场景上 3 个异构裁判多数投票，成本 ×3 换可信度。

裁判的「档位」还有个隐含前提：judge 模型自己也要过能力线——拿便宜档小模型当裁判，它在事实性维度上会频繁「看不懂就给中分」，分数分布挤在中间段，一致率再高也没有区分度。判断标准看区分度（分数方差）而不只看一致率。

**第 4 层：三个裁判投成一比一怎么办？**

一比一说明样本落在边界区，恰恰是最有价值的样本——**不要机器硬裁，回流人工仲裁**，仲裁结论沉淀进黄金集。边界样本是评测集最好的养料，比刷一千条简单题有用。

**第 5 层：评测集会过期吗？**

会，这是和单测最大的不同——代码行为不变，用例长期有效；但**线上 query 分布会漂**，老评测集越来越「不考真题」。对策：日志挖掘回流每月增量（线上低分、新意图、长尾模式进 badcase 集）；黄金集每季度人工复审，标注「过时」的 case 移入归档区但保留——历史分数要能对齐解释，不能删了装没发生过。

过期还分层：**表层过期**（问法变了，考察意图没变）改写即可；**意图层过期**（用户开始问新东西了）必须补新 case；**标注层过期**（标准答案本身要更新，比如政策类知识）要触发重新标注并记录版本原因——三种过期的处理动作完全不同，报告里要分开标识。

**第 6 层：badcase 为什么只增不删？删几条怎么了？**

badcase 是回归资产：今天修好的 case 删掉，下个月 prompt 一改，同类错误悄悄回来没人知道。正确姿势是**标签化管理生命周期**（未修复→已修复→无效 case）：「已修复」的 case 留着继续站岗，从「考题」变成「回归哨兵」。删除仅限法务/隐私强制要求，且走审批留痕。

**第 7 层：门禁红了，但业务就是急着发版，怎么办？**

放行不是后门，是流程：owner 审批 + 限时白名单（48 小时）+ 事后补测闭环；**同一变更连续两次白名单自动升级**到更高层级评审，防止白名单常态化把门禁掏空。底线：安全类指标（违规内容误出）不接受白名单。

再往深一层说，门禁的本质是和研发效率做博弈：卡得太狠，业务方会想办法绕过平台（私下改、不声明变更）；卡得太松，门禁形同虚设。所以阈值要和业务方一起定、每季度复盘一次误拦率——**误拦（变更其实没坏却被拦）占比超过两成，就该调阈值**，否则平台就是在消耗自己的信用。

**第 8 层：分数全绿上线，用户还是说答错了，评测漏了什么？**

漏了**过程**。答案对 ≠ 过程对：模型可能引用了错误文档碰巧答对、可能调错工具绕一圈自愈、可能幻觉拼出正确结论。过程评测在 trace 层做：工具调用序列是否命中预期、检索引用是否指向标注的支撑文档、有没有编造引用——这些从过程 trace 的结构化字段直接判，不需要 judge。这也是评测平台要和可观测体系（题 13）打通的原因。

**资深 vs 初级：这道题的答法差在哪**

| 维度 | 初级答法 | 资深答法 |
|---|---|---|
| 切入点 | 罗列工具和指标名 | 先问规模与接入形态，再定平台边界 |
| 指标体系 | 「用 LLM 打个分就行」 | 三层各有采集位，指标字典开箱即用 |
| judge | 拿来就用 | 校准口径 + 锚点防漂 + 抽检 + 多裁判 |
| 评测集 | 一个 JSON 文件 | 资产化：版本化、只增不删、回流管道 |
| 门禁 | 「分数低就报警」 | 阈值分级 + 放行流程 + 熔断升级 |
| 成本 | 没算过 | 现场：集规模 × token × 单价 × 频次 × 缓存 |
| 闭环 | 出报告结束 | 线上 badcase → 评测集 → 门禁，越用越准 |

**面试常见坑（自查清单）：**

- 坑 1：只讲 judge 不讲治理——judge 一漂门禁全红，平台信用破产
- 坑 2：评测集一次建完永不更新——三个月后和线上分布脱节，分数再绿也不可信
- 坑 3：门禁阈值拍绝对值（「低于 90 分就红」）——业务间不可比，相对阈值才稳
- 坑 4：忘了过程评测——答案对过程错的 case 全部漏网
- 坑 5：白名单没有熔断——门禁被业务方「借道」借空，形同虚设
- 坑 6：A/B 只看主指标不设护栏——赢了采纳率、输了延迟和成本，白忙一场

### 🎤 口述模板

> 这题我先立观点：评测平台的本质，是把效果验收从人工拍脑袋变成工程资产，后端测试平台的经验可以整段翻译。指标分三层各有采集位：检索层规则算 recall 和 NDCG，生成层 LLM-as-a-Judge 按 rubric 打分，系统层读延迟成本。评测集当资产：黄金集 git 式版本化，badcase 只增不删，线上日志每月挖掘回流。judge 要治理不是拿来就用：上岗校准到与人一致率 85%，rubric 固化成配置，门禁场景三裁判投票，每天抽检盯漂移。结果必须接 CI 门禁：任何变更自动触发，核心指标跌破相对阈值卡合并，配审批放行防后门；编排逻辑用 mock LLM 做秒级行为回归，答案对不等于过程对，过程在 trace 层单独验。售后也归平台管：升级后质量下降，靠基线留档加 trace 回放双跑定位到版本，prompt 秒级回退、模型切别名回滚。规模上一万条评测集、单次回归几十块，就能在公司跑起来。

（约 330 字；骨架是「三层指标→评测集资产→judge 治理→CI 门禁与 mock 回归→升级定位回滚→成本」六段，数字可按面试官给的业务规模现场重算）

### 一句话总结

> 评测平台 = 测试工程的概率版：**评测集是资产、judge 是打分函数、门禁是闭环出口**——不卡发版的评测平台只是图表工具。

## 题 13｜AI 全链路可观测体系（Trace+监控+badcase 闭环）

> **一句话考察点**：能不能给概率性的 AI 系统搭一套「看得见」的体系——span 树记录每一步、指标三条线盯着质量/成本/延迟、badcase 自动挖出来回流评测集，并且复用 OpenTelemetry 生态、落库前把 PII 脱干净。
>
> **考察频率**：⭐⭐⭐⭐⭐（AI 应用上线后的第一件事就是可观测；平台/稳定性方向必问，应用岗高频出现缩水版「线上怎么监控」）

### 需求澄清

**Q1：可观测到底为了什么？排障、降本还是质量？**

A：三合一，但要分清主次——这决定架构重心：

| 目标 | 用的东西 | 优先级 |
|---|---|---|
| 快速排障（「用户说答错了，为什么」） | trace 全链路下钻 | P0，上线第一天就要 |
| 质量监控（「今天整体变差了吗」） | 指标三条线 + 分级告警 | P0 |
| 成本治理（「钱花哪了、能不能省」） | token/成本指标 + 版本维度拆解 | P1，流量上来后 |
| badcase 挖掘（「错都错在哪几类上」） | 低分聚类 + 模式归纳 | P1，持续改进的输入 |

> 排障为什么是 P0：AI 系统的「错」不会抛异常——不崩溃、不返回 500，就是安安静静地答错。没有 trace，用户投诉进来你连「错在哪一步」都无从看起，只能干瞪眼。

**Q2：流量多大？trace 全采存得起吗？**

A：先拍数再谈方案（详细见容量估算）：日请求 100 万、每请求约 6 个 span、每 span 约 2KB——**全采 12GB/天**。结论：全采不现实也不必要，用尾部组合采样：错误全采 + 慢查询全采 + 正常抽 10% + 随机兜底，落到约 2GB/天。面试时先报这组数，方案自然立住。

这里有个答题技巧：**先给量级再给方案**。很多同学上来就讲「我会做采样」，但说不出采多少、为什么是这个比例——量级感是资深和初级最直观的分水岭。

**Q3：公司已有后端 APM，AI 这套是另起炉灶还是复用？**

A：**复用，而且这是后端工程师的主场**。方案是 OpenTelemetry 统一埋点：AI 的 span 属性对齐 OTel 的 GenAI 语义约定（semantic conventions），Collector、存储、看板、告警链路全部沿用后端已有的，AI 侧只新增三块：GenAI 属性、质量指标线、badcase 挖掘管道。另起炉灶是初级答案——两套体系排障时对不上 request_id，等于白干。

> 误区提醒：自建一套「AI 监控」听着高大上，实际是给自己挖坑——排障时两套系统「对表」就要十分钟，AI 的 span 和 HTTP/SQL 的 span 长不在一棵树上，端到端延迟算不出来。复用不是偷懒，是让后端 APM 的老骨架直接承重。

**Q4：trace 里全是用户 prompt 和模型回答，隐私怎么办？**

A：落库前必须脱敏，两道防线：SDK/应用端先裁剪（密钥、系统提示词里的机密不进 span）；Collector 端过双通道脱敏（正则规则 + NER 模型识别 PII）。原则：**结构化属性全保留、自由文本脱敏后保留**——排障要的是「形状」不是原文。

**边界确认清单**（面试官没说、但你要主动问的）：

| 要确认的 | 为什么关键 | 默认假设 |
|---|---|---|
| 流量规模 | 直接决定采样和存储设计 | 日 100 万请求 |
| 已有 APM 什么栈 | 决定复用边界 | OTel 生态，可复用 |
| 隐私合规等级 | 决定脱敏强度和留存周期 | 高：PII 落库前必须处理 |
| 值班体系有没有 | 告警发出去得有人接 | 复用后端值班 |
| 多少业务方接入 | SDK 推广成本和属性治理 | 5~10 个业务方 |

### 架构图

```
       AI 应用层(网关/编排/Agent)
        │ OTel SDK 埋点, span 树: 请求→检索→工具→生成
        ▼
 ┌─────────────────────────────┐
 │ OTel Collector 采集层        │
 │ ①尾部采样: 错误/慢查询全采    │
 │   + 正常流量抽 10%           │
 │ ②脱敏: 正则+NER 双通道 PII   │
 │ ③富化: 补模型/prompt 版本标签 │
 └──────┬────────┬───────┬────┘
        ▼        ▼       ▼
    ┌──────┐ ┌──────┐ ┌────────┐
    │trace │ │指标   │ │badcase  │
    │列式   │ │三条线 │ │挖掘管道  │
    │存储   │ │质量/  │ │低分聚类→ │
    │      │ │成本/  │ │模式归纳  │
    │      │ │延迟   │ │  ↓回流   │
    └──────┘ └──────┘ └───┬────┘
        ▼        ▼         └──► 评测集(题12)
  消费层: 统一看板 │ 分级告警 │ request_id 排障下钻
```

图读法（口述时按编号走）：

1. **顶上埋点**：SDK 层把一次 AI 请求拆成 span 树，检索/工具/生成各占一段——trace 从出生就带 AI 语义，不是事后拼日志
2. **中段 Collector 三件事**：尾部采样（看完整体结果再决定去留）、双通道脱敏（PII 落库前拦住）、富化（补版本标签，指标异常时能按版本归因）
3. **右路闭环**：低分样本进挖掘管道，聚类归纳后回流评测集——和题 12 接成「线上发现问题 → 变成离线用例」的大闭环
4. **底下消费**：统一看板 + 分级告警 + request_id 反查排障，全套复用后端 APM 的面板和值班机制

**埋点三原则（写进 SDK 接入规范）：**

- **属性结构化**：token、成本、版本号一律进 span attributes，不藏在日志文本里——结构化才能聚合，聚合才有指标
- **树形完整**：检索、工具、生成任何一步都挂到请求的 trace 树上，禁止「旁路日志」——旁路的日志算不进端到端延迟
- **语义对齐**：字段名对齐 OTel GenAI 语义约定，不自造轮子——自造字段接不进 APM 生态，看板和告警全要重做
- **上下文随树传**：AgentContext（会话 id、实验分组、注入的记忆与变量）在根 span 生成、随上下文自动传到每个子 span——业务无感；回放时缺了它，一模一样的 query 也复现不了当时的答案

**与后端 APM 的复用/新增对照（复用是本题的隐形考点）：**

| 组件 | 后端已有 | AI 侧动作 |
|---|---|---|
| OTel SDK | HTTP/RPC/DB 埋点 | 新增 GenAI span 类型与属性 |
| Collector | 采集、路由、处理 | 新增尾部采样规则 + 脱敏处理器 |
| 存储 | trace/指标/日志三件套 | 直接复用，加 TTL 分层策略 |
| 看板 | 服务大盘 | 加 AI 三线指标面板 |
| 告警 | 分级告警、值班排班 | 加质量/成本线告警规则 |
| 排障入口 | request_id 反查 | 完全一致，无学习成本 |

**拿着这套体系排障是什么体验（走读一遍）：**

用户投诉「答错了」。拿 request_id 查 trace：根 span 显示 judge 低分标记；展开检索 span——recall_hit=false，本该引用的文档没进前 k；再看生成 span——模型版本没变，但检索配置昨天从 top_k=5 改成了 3。定位：配置变更压缩了召回。全程没看一行代码，两分钟出结论——这就是可观测的投资回报。

**span 树长什么样（AI trace 数据模型的核心）**：一次请求一棵树，每个 span 带结构化属性：

```
 request (root span)
  ├─ attrs: request_id, scene, user_tier, 出口状态
  ├─ AgentContext: 会话id, 实验分组, 注入记忆/变量摘要
 ├─ retrieval.span · 向量检索
 │   ├─ attrs: top_k, latency_ms, recall_hit?
 │   └─ events: 引用文档 id 列表
 ├─ tool.call · 外部 API/函数
 │   ├─ attrs: tool_name, args_hash, latency_ms
 │   └─ status: OK / ERROR(错误码)
 ├─ generation.span · 生成
 │   ├─ attrs: model_version, prompt_version
 │   ├─ metrics: input/output_tokens, cost, TTFT
 │   └─ quality: judge_score(抽样), 点踩标记
 └─ 全树 rollup: 总延迟=关键路径和, 总成本=Σ各span
```

**OTel GenAI 语义属性示例（命名对齐社区约定，别自造）：**

```
gen_ai.request.model          = "chat-7b-2025q2"   # 模型版本
app.prompt.version            = "v137"             # prompt 版本
gen_ai.usage.input_tokens     = 1820               # 输入 token
gen_ai.usage.output_tokens    = 356                # 输出 token
gen_ai.response.finish_reason = "stop"             # 正常结束/截断
app.cost.cny                  = 0.021              # 单价表富化后回填
app.retrieval.hit_annotated   = true               # 引用是否命中标注
```

**span 属性速查表**（面试可白板默写）：

| span 类型 | 关键属性 | 用途 |
|---|---|---|
| request（根） | request_id、scene、user_tier、AgentContext（会话/实验分组/注入摘要）、最终状态 | 排障入口、按场景下钻、回放上下文 |
| retrieval | top_k、检索延迟、命中标注文档与否、引用文档 id | 检索质量、引用溯源 |
| tool.call | tool_name、参数哈希、延迟、错误码 | 工具成功率、慢工具定位 |
| generation | 模型版本、prompt 版本、输入/输出 token、成本、首字延迟 | 成本归因、版本对比 |
| judge（异步） | 维度分、理由摘要、裁判模型版本、rubric 版本 | 质量线数据源、judge 漂移监控 |
| 整树 | 总延迟（关键路径）、总成本（求和）、judge 分（抽样） | 请求级三线指标 |

**属性治理（防止 span 越埋越乱）：**

- 新增属性走命名空间评审（genai.\* / retrieval.\* / tool.\*），杜绝同义不同名
- 属性集带 schema 版本，消费端按版本兼容解析，避免一次改名打挂所有看板
- 每季度清点低频属性（90 天没被任何查询引用的），下线或降级进日志——基数失控是时序存储的第一杀手

**真题直击：「为了问题回放，一次请求至少要记录哪些数据？」（完整清单答案）**

| 组 | 必记字段 | 少了会怎样 |
|---|---|---|
| 输入 | 原始 query、会话 id、用户 id（哈希）、时间戳、场景/入口标签 | 复现不了「谁在什么语境下问了什么」 |
| 上下文 | AgentContext：系统 prompt 版本、历史轮次摘要、注入的工具清单/记忆/变量 | 同一 query 答案不同，缺它必然无法复现 |
| 模型侧 | 模型版本、prompt 版本、温度/top_p 等采样参数 | 概率系统的「编译器版本」，不锁死就对不上 |
| 检索 | 改写后 query、召回 doc_id + 分数列表、rerank 后顺序、chunk 定位 | 分不清「检索错了」还是「生成错了」 |
| 工具 | 工具名、入参、返回摘要、耗时、重试次数 | Agent 行为无法复盘 |
| 生成 | 完整输出、finish_reason、输入/输出 token、分片延迟 | 有内容没性能，或有性能没内容 |
| 环境 | 服务版本、检索配置/索引版本、实验分组标记 | 「当时是什么配置」说不清，回放无意义 |
| 结果 | 用户反馈（点踩/采纳/追问）、异步 judge 分 | 事后判断好坏缺地面真相 |

回放三要素：**输入可复现、版本可锁定、随机可控**（温度设 0 或记录 seed）。最容易被漏的两件：**渲染后 prompt 全文**（只记模板不记渲染结果，检索一变就对不上）和 **AgentContext**（上下文不记，query 一模一样也复现不了）。一句话版：**输入 + 上下文 + 全部版本号 + 中间产物 + 反馈**——少任何一组，回放就退化成猜。

### 关键设计决策表

**决策 1：trace 数据模型怎么定？**

| 方案 | 做法 | 优点 | 缺点 |
|---|---|---|---|
| 纯文本日志 | 每步打一行日志 | 改造快、门槛低 | 无树状关系，算不了「关键路径延迟」 |
| 结构化 span 树 | OTel span + GenAI 语义属性 | 树状聚合、生态复用、直连 APM | 埋点有侵入，属性要治理 |
| 事件流 + 事后拼装 | 各组件发事件，落库后拼 trace | 组件解耦 | 拼装复杂、乱序难处理 |

> 结论：结构化 span 树，属性对齐 OTel GenAI 语义约定——这是「复用后端 APM」的前提；自由文本（prompt/回答原文）作为 span 附件单独存、单独管 TTL 和脱敏。

**决策 2：采样策略怎么选？**

| 方案 | 怎么做 | 优点 | 缺点 | AI 场景评价 |
|---|---|---|---|---|
| 头部采样 | SDK 入口按比例决定，选中才埋 | 实现简单、内存省 | 错误请求可能在门口就被丢 | 不合格：错误只有跑完才知道 |
| 尾部采样 | Collector 等整条 trace 走完，按结果决定留不留 | 能做到「错误全采、正常抽样」 | 要缓存整条 trace，内存压力大 | 主方案 |
| 尾部组合规则 | 错误全采 + 慢查询全采 + 正常抽 10% + 随机兜底 1% | 兼顾成本、覆盖率、代表性 | 规则要持续维护 | 生产标配 |
| 业务分级采样 | 核心场景 50%、边缘场景 5% | 钱花在刀刃上 | 配置复杂 | 进阶 |

> 尾部采样实现要点：Collector 内存缓存等整树完成（span completion）；高吞吐下可用「先直写、事后按规则清理」的变体，拿存储换内存。

> 另一个容易被追问的点：**采样规则要有兜底**——所有规则都没命中时（既不是错误、不算慢、又没被随机抽中），按 1% 保底随机保留，防止规则配置错误导致某类请求全军覆没；采样决策本身也要打指标（各规则命中率），否则「采样把问题采没了」你都不会知道。

**决策 3：指标三条线，每条线盯什么、阈值怎么定？**

| 线 | 核心指标（3~5 个） | 告警阈值思路 |
|---|---|---|
| 质量线 | 用户满意率（赞/总反馈）、judge 抽检分（1% 在线抽样）、引用命中率、幻觉/拒答异常率、工具调用成功率 | 滚动 7 天基线的 -2σ，或周环比跌 5pp |
| 成本线 | 单请求平均成本、日总成本、token 利用率（有效输出/上下文）、缓存命中率 | 预算制：日预算 80% 黄、100% 红 |
| 延迟线 | 端到端 P95、首字延迟 TTFT P95、检索 P95、生成 P95 | SLO 制：P95 目标 + 错误预算烧完告警 |

> 阈值方法论：**不拍静态绝对值**。先跑 2~4 周建基线；质量用统计量（分位数/环比），成本用预算，延迟用 SLO；分级 P0 电话拉人、P1 即时消息、P2 日报汇总。冷启动没有用户反馈时，用人工标注小样本 + judge 抽样把质量线先立起来。

**三线之间的关系（联动分析才有价值）：**

- 质量跌 + 成本涨：大概率模型或检索变更引入问题——先按版本维度切分
- 质量平 + 成本涨：上下文膨胀（检索塞太多无用文档）——查 token 利用率
- 质量跌 + 延迟涨：下游依赖劣化或重试风暴——查工具 span 的错误码
- 三线齐跌：流量结构变了（新场景涌入）——查 scene 维度的分布漂移

**告警分级与响应（复用后端值班体系）：**

| 级别 | 触发示例 | 通道 | 响应要求 |
|---|---|---|---|
| P0 | 满意率崩塌 + 报错率飙升同时发生 | 电话 + 即时消息 | 15 分钟响应，值班 oncall |
| P1 | 质量线跌破 -2σ 或成本预算击穿 100% | 即时消息 | 当天定位到维度 |
| P2 | 单指标抖动、新 badcase 簇出现 | 日报汇总 | 周会排期处理 |

> 分级的本质是**保护告警的信噪比**：全发 P0 等于没有 P0。上线头一个月建议所有告警先跑「影子模式」（只记录不通知），用历史数据校准阈值和分级，再正式接入值班——和题 12 门禁的影子模式是同一个思想。

**决策 4：badcase 自动挖掘怎么做？**

| 步骤 | 方案 | 备注 |
|---|---|---|
| 候选筛选 | 规则先滤：点踩、judge 低分、空/超长输出、报错重试 | 把 100 万/天缩到几千条 |
| 向量化 | embedding 模型统一编码 | 成本可忽略 |
| 聚类 | HDBSCAN 密度聚类，不用预设簇数 | 新错误模式会自动冒出来 |
| 模式归纳 | 每簇取代表样本让 LLM 总结错误模式并命名 | 「引用错文档类」「日期计算类」 |
| 回流 | 人审通过→入 badcase 评测集，挂模式标签 | 只增不删，接题 12 的门禁 |

> 结论：挖掘管道的输出不是「一堆 badcase」，是「有名字、有状态、有责任人的错误模式」；人审这道闸不能省——自动入库等于让线上噪声直接改写回归标准。

**采样率敏感性（采样不是定死的）：**

| 采样率 | 日体量 | 12 个月留存（压缩后） | 判断 |
|---|---|---|---|
| 100% | 12GB | ~1.5TB | 治理成本失控，不采纳 |
| 18%（组合规则） | ~2GB | ~250GB | 生产标配 |
| 5%（激进） | ~600MB | ~75GB | 正常流量画像失真，统计不稳 |

**决策 5：LLM API 超时/异常，稳定性链路怎么建？**

可观测负责「发现」，这一层负责「兜住」——超时、重试、熔断、降级四件套组合用：

| 机制 | 做法 | 数字锚点 |
|---|---|---|
| 超时预算 | 总预算分段：检索 3s / 工具 5s / 生成 20s + 缓冲；连接超时 2s | 流式只卡「首 token」5s，不卡整包 |
| 重试 | 指数退避加抖动（1s/2s/4s），最多 2 次；只重试幂等与可重试错误（429/5xx/超时），4xx 不重试 | 无抖动的重试在对端恢复瞬间二次雪崩 |
| 熔断 | 滑动窗口错误率 >50%（窗口 ≥20 请求）打开，直接快速失败；30s 后半开放探活 | 打开期间必须配降级，不是让用户硬等 |
| 降级链 | 主模型 → 备用模型 → 语义缓存/热门问答 → 规则兜底话术 + 转人工 | 每级降级在 span 上打标记，降级占比本身是指标 |

> 口诀：**重试保抖动、熔断保自己、降级保用户、观测保真相**。两个 AI 特有细节：流式请求已吐出一半内容时不能重试（会重复输出），只有首 token 前失败才安全重试；备用模型也要过评测门禁校准——没评过的降级是把故障换成事故。超时/熔断/降级每次触发都产生一条全采 trace + 事件，这本身就是可观测体系的质量样本。

**决策 6：脱敏在哪一层做？**

| 位置 | 做法 | 优劣 |
|---|---|---|
| SDK/应用端 | 密钥、系统提示词、敏感字段不进 span | 最源头，但每个业务方都要改，容易漏 |
| Collector 端 | 正则（手机号/身份证/卡号）+ NER（人名/地址）双通道，替换为槽位占位符 | 统一收口、漏网少；NER 有算力成本 |
| 查询端 | 落原文，查询时再脱 | 不推荐：落库即有合规风险 |

> 结论：Collector 端统一收口为主 + SDK 端「结构化属性不带你明文」的纪律；原文确需保留时走加密存储 + 授权重放。

> 补充「授权重放」怎么落地：原文单独加密存（密钥在 KMS，按业务方分 key），trace 里只留密文指针；排障确需看原文时走审批（owner + 安全双确认），解密访问全打审计日志，默认 24 小时后权限自动回收——把「看原文」变成一个显式动作，而不是默认能力。

**决策 7：存储怎么选？**

| 方案 | 优 | 劣 | 用法 |
|---|---|---|---|
| 复用现有 APM 存储 | 与现有链路零摩擦 | 高基数属性查询慢 | 起步首选 |
| 列式数仓（按天分区） | 大规模聚合强、压缩好 | 写入链路要自建 | 量大后 trace 主体迁入 |
| 搜索型存储（倒排） | request_id/属性秒查 | 成本高 | 只给热层排障用 |
| 对象存储 + 列式文件 | 最便宜、无限容量 | 查询要引擎层 | 冷层归档 |

> 结论：起步复用 APM 存储；量级上来后 trace 主体进列式（按天分区 + TTL）、热层留搜索型、冷层沉对象存储——和后端日志平台的存储分层一模一样，能共栈就共栈。

### 容量估算

接着需求澄清的数往下算（整数近似）：

**基本盘：**

- 日请求 100 万（均值约 12 QPS，峰值 50）
- 每请求 span 数：1 根 + 2 检索 + 1~2 工具 + 1~2 生成（含重试）≈ **6 个**
- 每 span 约 2KB（属性 + 事件 + 附件引用）→ 每请求约 12KB

**全采 vs 采样：**

| 项 | 计算 | 结果 |
|---|---|---|
| 全采体量 | 100 万 × 12KB | 12GB/天，12 个月约 4.4TB |
| 采样构成 | 错误 5%（5 万）+ 慢查询 3%（3 万）+ 正常 10%（9.2 万）+ 兜底 1%（1 万） | 约 18 万请求/天，综合采样率 18% |
| 采后体量 | 18 万 × 12KB | 约 2GB/天，压缩后 12 个月约 250GB |
| 在线 judge 抽样 | 1% × 2k token | 20M token/天，便宜档 judge 约 ¥40/天 |
| 聚类挖掘 | 每周约 5000 条低分样本 | embedding 成本可忽略 |

**回放成本（新增的排障能力，要用得起）：**

- 每周回放约 1000 条排查样本 × 每条重放一次完整链路 ≈ 3K token——周成本几十元，忽略不计
- 真正贵的是「没记全导致不能回放」：一次线上事故排查平均消耗数人时，远超全年回放 token 费——记全字段的存储开销，比事故便宜两个量级

**在线 judge 的账单展开（质量线的成本大头）：**

- 抽样 1% = 1 万次/天 × 平均 2k token（题目 + 回答 + rubric）= 20M token/天
- 便宜档 judge 按约 ¥2/M token：**约 ¥40/天、¥1200/月**
- 想再省：白天抽 1%、凌晨抽 0.5%；或先用规则粗筛（空回答/超长/重试），只对可疑样本 judge——再砍一半
- 反向提醒：抽样率压到 0.5% 以下，日样本量进不了几百条，日级波动就会淹没真实信号——**质量线的灵敏度是用钱买的**

**存储分层（TTL 三档）：**

- 热（7 天）：全字段，排障主力区
- 温（30 天）：剥离自由文本，只留结构化属性 + 摘要
- 冷（365 天）：只留聚合指标，存储再降一个量级

**查询与增长（容量不只是写入）：**

- 排障查询：request_id 精确查，毫秒级，量小忽略
- 看板聚合：全部走预聚合 rollup（5 分钟粒度），查询压力转嫁给聚合层
- 增长敏感度：流量翻倍 → 正常抽样从 10% 降到 5%（错误和慢查询永不降），存储近线性可控
- 最坏情况：模型故障错误率飙到 50% → 错误全采会把写入放大近 3 倍，Collector 要预留突发余量，降级预案是「错误也限额采样 + 保留首个错误」

**冷启动最小集（上线第一周就要有的）：**

- request + generation 两个 span（检索/工具可以后补）
- 尾部规则最简版：错误全采 + 正常抽 5%
- 延迟线和成本线（埋点即有）；质量线用 judge 每日抽样 1% 先顶着
- 一条 P0 告警：报错率 + 空输出率
- 先能回答「用户说答错了，当时发生了什么」，再谈 badcase 闭环——排障是这套体系的第一性价值

> 这组数字的意义：**采样不是省小钱，是把「存不起也用不上」变成「存得起且查得动」**；18% 的采样率保住了全部错误和慢查询，正常流量的统计画像也不失真。

### 追问链

**第 1 层：为什么不干脆全采？硬盘又不贵。**

贵的不只是硬盘：全采 12GB/天意味着索引、查询、TTL 管理全部翻几倍；正常流量对排障价值极低（99% 的排障都从错误和慢查询进来）；隐私暴露面也翻倍——每一条 trace 都是一份潜在 PII。存储便宜了，**读吞吐和治理成本没便宜**。

再加一层判断：全采的 trace 里 95% 是「正常且平庸」的请求，找问题时的信噪比极低——采样不仅是省钱，更是**给排障降噪**。错误全采保证不漏案，正常抽样保证统计画像，这才是组合采样的完整逻辑。

**第 2 层：头部采样和尾部采样的本质区别？AI 为什么必须尾部？**

头部在 SDK 入口就决定埋不埋，尾部在 Collector 看完整条 trace 的结果再决定留不留。AI 请求「错没错」只有生成完才知道——幻觉、点踩、超时都是尾部信息，头部采样会把这些宝贝按比例丢掉。代价是 Collector 要缓存整树，用内存换「错误全采」的能力。

顺带一个实现细节：尾部采样的决策延迟等于最慢 span 的到达时间，重试链路长的请求可能拖几秒——所以生产上「先直写、后清理」的变体更稳：全部先落缓冲区，超时窗口内没凑齐整树的按规则处理，别让采样逻辑反压业务链路。

**第 3 层：span 里为什么要带 prompt 版本和模型版本？**

为了**归因**。质量指标跌了，第一反应不是查代码，是把指标按「模型版本 × prompt 版本 × 检索配置版本」三个维度 pivot——十有八九是某次变更引入的。版本不进 span，归因就要靠「时间点对齐」猜，线上混部多版本时根本猜不准。这是把后端「发布标签打进日志」的老规矩翻译过来。

版本属性还有个衍生用法：**灰度归因**。新版本只放 10% 流量时，按版本维度切分指标就能实时对比新旧表现，不用等 A/B 平台排期——trace 里的版本标签是自带实验能力的最低成本方案。

**第 4 层：质量告警的阈值怎么定？AI 又没有「正确率」这个直指标。**

对，所以用**代理指标组**：用户满意率（真实但稀疏）、judge 抽检分（密但间接）、引用命中率、工具成功率。阈值不拍静态值：先跑 2~4 周基线，质量线用滚动分位数（-2σ）或周环比（-5pp），成本线用预算制，延迟线用 SLO 错误预算。多指标交叉验证，单指标抖不动整条告警。

还有一个冷启动细节：满意率这类指标**分母太小的时候会乱跳**（一天只有 50 条反馈，三条点踩就能触发告警）——所以新业务上线头两周，质量线只挂 judge 抽检分和工具成功率这类分母可控的指标，等反馈量上来再挂满意率。

**第 5 层：badcase 聚类具体怎么做？为什么用 HDBSCAN 不用 KMeans？**

流程：规则筛选候选 → embedding 向量化 → 聚类 → 每簇 LLM 归纳命名 → 人审回流。选 HDBSCAN 因为**不用预设簇数**——线上错误模式有多少类事先不知道，KMeans 强行切 k 等会把新模式切碎或并没；HDBSCAN 按密度找簇，新错误模式会自己冒成一个簇，还能把噪声点标出来（长尾单例，单独人审）。

簇的运营也有讲究：**簇大小骤增**本身就是信号（某类错误今天突然翻倍，比单指标告警更早发现问题）；簇要防退化——连续几周不更新的簇标记「已修复候选」，修复后加回归用例关簇。坏case 挖掘的产出不是「一堆簇」，是「有状态、有生命周期的错误模式库」。

**第 6 层：脱敏会不会破坏排障能力？**

会削弱，所以设计上补偿：结构化属性（token 数、版本、延迟、错误码）不脱，排障 80% 靠这些；自由文本脱敏保留「形状」——长度、语言、槽位类型（手机号→[PHONE]）；确需看原文的疑难 case，走加密原文的授权重放流程，审批后解密查看。**可观测性和合规不是二选一，是分层设计**。

**第 7 层：成本怎么精确到「每次请求、每个场景、每个用户」？**

span 里记 token 数（输入/输出分开），乘以按模型版本维护的单价表，得到 span 级成本；trace 树天然支持 rollup——请求成本 = 各 span 求和，场景成本 = 按 request 的 scene 标签聚合，用户成本 = 按 user_id 聚合。单价表版本化，历史账单可复算。这就是后端「计量计费」的翻版。

注意一个归一化陷阱：**成本和延迟的 rollup 规则不一样**——成本可加（各 span 求和），延迟不可加（并行 span 取关键路径）。新手常把两者都写成求和，端到端延迟就会虚高一截，SLO 形同虚设。

**第 8 层：这套和后端 APM 已有体系冲突吗？**

不冲突，是增强：同一套 OTel Collector、同一套存储和看板；AI 新增的是 GenAI 语义属性、质量/成本指标线、badcase 挖掘管道。排障时一个 request_id 能从 HTTP 入口一路串到 SQL 查询和 LLM 生成——**后端同学 debug AI 系统的体验，和 debug 老服务一模一样**，这正是复用生态的最大价值。

**资深 vs 初级：这道题的答法差在哪**

| 维度 | 初级答法 | 资深答法 |
|---|---|---|
| 数据模型 | 打日志记 token | span 树 + 版本属性，可归因可 rollup |
| 采样 | 「全存着以后用」 | 尾部组合：错误全采、正常抽样，报得出采样率 |
| 阈值 | 拍一个绝对值 | 基线 + 分位数 + 预算制 + SLO |
| 隐私 | 「加个脱敏开关」 | 分层脱敏 + 属性/文本区别对待 + 授权重放 |
| 生态 | 自建一套监控 | OTel 对齐，复用 Collector、存储、看板 |
| 闭环 | 挖出 badcase 给人看 | 聚类→归纳→人审→回流评测集 |

**两题怎么接（面试收尾金句）：**

题 13 挖出的 badcase 回流题 12 的评测集，题 12 的门禁守住题 13 的线上质量——线下验收 + 线上监控合成一个质量飞轮。面试里把两题串起来讲，就是「质量侧架构师」的完整视野。

**面试常见坑（自查清单）：**

- 坑 1：只讲采集不讲采样——面试官必追「全采存得起吗」，现场算不出 12GB/天就露怯
- 坑 2：指标没有版本维度——质量跌了无法归因到「哪次变更」，监控变成事后诸葛亮
- 坑 3：脱敏一刀切全抹掉——排障能力被自己废了，合规和可观测不是二选一
- 坑 4：另起炉灶自建采集——和后端 APM 对不上 request_id，两边排障两头苦
- 坑 5：badcase 挖掘直接自动入库——线上噪声冲垮评测集，人审闸门不能省
- 坑 6：只报质量线不报成本线——老板第一个问题就是「这个月模型账单为什么涨了三成」

### 🎤 口述模板

> 这题我的总纲是：AI 是概率系统，「看得见」比「测得准」还急，后端 APM 的老骨架直接能穿。第一层数据模型：用 OpenTelemetry 把请求拆成 span 树——请求、检索、工具、生成各占一段，每个 span 带 token、延迟、成本、模型版本、prompt 版本和 AgentContext；要能回放，至少记五组：输入、上下文、全部版本号、中间产物、用户反馈。第二层采样：尾部组合——错误和慢查询全采、正常抽一成，一天 12GB 压到 2GB。第三层指标三条线：质量、成本、延迟，阈值先跑两周基线，再上分位数、预算制和 SLO。第四层稳定性：LLM API 超时分段预算，重试带退避抖动，错误率过半熔断，配主模型到备模型到缓存到兜底话术的降级链，降级本身也打标可观测。第五层闭环：低分聚类、模式归纳、人审回流评测集，和离线评测平台接成质量飞轮。最后落库前正则加 NER 双通道脱敏，整套复用后端 APM，一个 request_id 串到底。

（约 290 字；骨架是「数据模型与回放清单→采样→三线指标→稳定性降级→badcase 闭环→脱敏与生态复用」六段，数字现场可按面试官给的流量重算）

### 一句话总结

> AI 可观测 = 给 APM 的老骨架装上概率系统的新器官：**span 记过程、三线盯全局、badcase 回流闭环**——看得见，才修得快。
