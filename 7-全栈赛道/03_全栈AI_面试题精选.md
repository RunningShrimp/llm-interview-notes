## 1. 全栈候选人的差异化考察逻辑

**面试官面对全栈候选人时，考察重心从「单层深度」移向「链路完整度」。** 纯后端候选人会被追问存储、限流、推理池怎么扩；全栈候选人则被追问「这条链路的两端你怎么接」——流式响应到浏览器之后谁负责关代理缓冲、取消要不要一路传到 GPU 释放 KV cache、模型降级了 UI 上给用户看什么。这类问题的本质是：你能不能把「体验指标（TTFT、流式渲染、失败态）」和「系统指标（吞吐、成本、KV cache）」在同一个架构叙事里讲通。

**第二个差异点：安全与成本的「交叉地带」只考全栈。** LLM 输出的 markdown 怎么防 XSS（prompt injection 直接打到渲染层）、免费用户用小模型的质量落差怎么在 UI 上做预期管理——这些题目后端候选人不会被问到，前端候选人又缺系统侧的上下文，只有全栈候选人被期待两端都答。把本篇 8 道设计题的「考察点」背熟，本质上是提前拿到这份「差异化追问清单」。

## 2. 八道系统设计题

### 题 1：设计 ChatGPT 式聊天应用（1M DAU）

> Design a ChatGPT-style conversational app serving 1M DAU. Cover frontend token streaming (SSE), request queues under GPU pressure, and per-token cost control.

**考察点：**
- 是否理解 TTFT/TPOT 是「产品指标」而非纯后端指标（缓冲一整段再渲染 = 产品失败）
- SSE vs WebSocket 的选型理由（单向、CDN/代理友好、`Last-Event-ID` 自动重连）
- 取消传播链路：用户关标签页 → 网关 → 推理层释放 KV cache
- 分层模型路由（免费/付费）对单位经济性的影响（~7x 成本差）
- 前端在代理缓冲（Nginx/Cloudflare 默认 buffer）下的「坑」意识

**答题骨架：**
- 需求量化：1M DAU ≈ 数千~数万 turn/s；先算 token 吞吐再算 GPU/连接数（瓶颈在 6M 级并发 SSE 长连接而非带宽）
- 链路：浏览器 SSE → CDN → 网关（鉴权/限流 RPM+TPM）→ 会话状态（Redis 热缓存 + PostgreSQL append-only）→ 模型路由 → 推理池
- 流式管线：`res.flushHeaders()` 提前刷头；关掉 `proxy_buffering`；`res.write()` 返回 false 时 await `drain` 做背压；连接关闭 → abort 上游释放 KV cache
- 成本：免费层路由到小模型、prompt caching（缓存读≈10% 价格、TTFT 最多降 85%）、GPU 压力下先 shed 免费流量
- 前端体验：`submitted → streaming → ready/error` 状态机、Stop 按钮、断线自动重连

来源：[engineering-handbook · 30-chatgpt-conversational-ai](https://github.com/handbook-academy/engineering-handbook/blob/main/content/hld/part-8-case-studies/30-chatgpt-conversational-ai.md) · [OpenAI · Scaling PostgreSQL](https://openai.com/index/scaling-postgresql/) · [Exponent · Design ChatGPT 模拟面试](https://www.youtube.com/watch?v=I9-PUPYZyiw)

### 题 2：设计 RAG 客服知识门户

> Design a RAG-powered customer support portal end to end: document ingest pipeline, retrieval, streaming answer UI with citations, and production monitoring/evaluation.

**考察点：**
- 全栈视角：能否把 ingest 管线、检索、LLM、UI、监控串成一条链，而不是只讲向量库
- ACL 预过滤 vs 后过滤（后过滤崩 Recall@K 且有 timing 侧信道泄露）
- 引用（citation）在 UI 上如何渲染与校验，「幻觉引用 URL」如何杜绝
- 生产 RAG 评估：RAGAS（faithfulness / context precision / answer relevance）+ 用户反馈信号
- 监控与失败路径：检索空结果、模型不可用时如何优雅降级

**答题骨架：**
- Ingest：SaaS 连接器 → 对象存储 → 解析（PDF/OCR）→ chunk（1024 token / 128 overlap + Contextual Retrieval 前缀）→ 嵌入 → 向量库 + BM25 双写，chunk 级 hash 做 CDC 增量重嵌
- 查询路径：BM25 + ANN 并行（都带 ACL 预过滤）→ RRF 融合 → cross-encoder rerank → 组装上下文 → SSE 流式回答 + 引用后处理
- 1.5s 延迟预算拆分：检索 250ms + rerank 150ms + 组装 100ms + LLM TTFT 800ms + 引用处理 100ms + 网络 100ms
- UI/全栈侧：流式渲染带内联引用、无 grounding 来源时拒答、admin 控制台（连接器健康、重索引、评估看板、成本）
- 监控：RAGAS 进 CI 卡回归；thumbs 反馈 + 「错误引用」信号回流；语义缓存覆盖 FAQ 头部查询

来源：[engineering-handbook · 31-enterprise-rag](https://github.com/handbook-academy/engineering-handbook/blob/main/content/hld/part-8-case-studies/31-enterprise-rag.md) · [Anthropic · Contextual Retrieval](https://www.anthropic.com/engineering/contextual-retrieval) · [RAGAS 文档](https://docs.ragas.io/) · [ai-engineering-interview-questions](https://github.com/amitshekhariitbhu/ai-engineering-interview-questions)

### 题 3：设计 AI 编码助手（Cursor / Copilot）

> Design an AI coding assistant with three modes (autocomplete <200ms, chat, autonomous agent loop), covering agent UI streaming, sandboxed execution, and latency engineering.

**考察点：**
- 「三个产品一个入口」的拆解能力：三种模式各有独立的延迟 SLO、模型档位、安全边界
- 取消即常态：45–50% 的补全请求被用户「打字穿过」取消，HTTP/2 stream-reset 而非断 TCP
- 沙箱：为什么 Firecracker microVM 而非 Docker（内核 CVE 逃逸面）、网络白名单、用完即毁
- Diff 即界面：为什么全文重写优于 unified diff（模型数不对行号）、apply 原子性 + 一键回滚
- Agent UI：多分钟任务的持续进度可见性、审批门（destructive 动作 human-in-the-loop）

**答题骨架：**
- 分模式：补全（小模型 + 热池 + 200ms 预算）、chat（前沿模型 + 仓库检索）、autonomous loop（ReAct + 沙箱），共享检索索引与 eval 体系
- 上下文：嵌入 + tree-sitter 符号图（PageRank）+ git 新近度三路混合，token 预算内 rerank
- 前端：debounce 键击、ghost text、`RST_STREAM` 取消、diff 按 hunk 接受/拒绝、rollback token
- 成本：模型分层让补全单价差 ~100x；prompt caching 是 chat/agent 模式最大成本杠杆
- 治理：step/token/wall-clock 三重上限 + 重复工具调用检测打断死循环（引用 Anthropic Claude Code 事故复盘）

来源：[engineering-handbook · 32-coding-agent](https://github.com/handbook-academy/engineering-handbook/blob/main/content/hld/part-8-case-studies/32-coding-agent.md) · [ZenML · 低延迟代码补全服务](https://www.zenml.io/llmops-database/building-a-low-latency-global-code-completion-service) · [Cursor · Instant Apply](https://cursor.com/blog/instant-apply) · [Quant-Developers-Resources · AI System Design](https://github.com/cybergeekgyan/Quant-Developers-Resources/blob/main/Artificial%20Intelligence/AI%20System%20Design/README.md)

### 题 4：设计 Perplexity 式 AI 搜索（带引用）

> Design an AI answer engine (Perplexity-like): web-scale retrieval, streaming answers with inline citations, and a fast, trustworthy UI.

**考察点：**
- 搜索级延迟与 LLM 级延迟的混合预算；「answer-first」体验如何不牺牲可信度
- 引用与去重：爬取/索引 → 检索 → 生成时逐 claim 绑定来源；UI 上悬停高亮
- 查询理解与改写（HyDE、query decomposition）作为前端可见的「计划」展示
- 全栈候选人的加分点：SSR/流式 HTML、SEO 与 AI 摘要页的张力、移动端首屏

**答题骨架：**
- 管线：query → 改写/分解 → 混合检索（web index + 向量）→ rerank → 生成（system prompt 强制引用）→ SSE 流式 + citation post-process
- 双轨输出：流式 token 与最终 sources 列表分离；无来源 claim 直接抑制
- 缓存：语义缓存覆盖高频问句（命中率 30–70%），缓存击穿时降级到传统搜索结果
- UI：答案卡片 + 来源侧栏 + 逐句引用锚点；生成中显示「正在阅读 N 个来源」的进度

来源：[engineering-handbook · 33-perplexity-ai-search](https://github.com/handbook-academy/engineering-handbook/blob/main/content/hld/part-8-case-studies/33-perplexity-ai-search.md) · [Quant-Developers-Resources · AI System Design](https://github.com/cybergeekgyan/Quant-Developers-Resources/blob/main/Artificial%20Intelligence/AI%20System%20Design/README.md)

### 题 5：设计多 Agent 客服系统（人机协同）

> Design a multi-agent customer support system where agents call tools (refund, order lookup); the UI must support streaming status, tool-call approval, and escalation to humans.

**考察点：**
- Agent 事件流的 UI 化：thought / tool_call / tool_result / diff / done 各自如何渲染
- 危险操作的审批 UI（human-in-the-loop）、预算熔断后如何「暂停等审批」而不是崩溃
- 会话状态原子性：崩溃在 tool call 与 tool result 之间时如何恢复
- 转人工（escalation）的体验设计：上下文交接、用户可见状态

**答题骨架：**
- 编排：orchestrator + 专职 agent（检索/订单/退款），工具白名单 + 参数 schema 校验
- 事件流协议：SSE 推送结构化事件（非纯文本），前端按 part 类型渲染（工具卡片、加载态、错误态）
- 审批与熔断：破坏性工具 → `waiting_approval` 状态 + 审批 UI；per-task token/步数/时长上限 + 重复调用检测
- 持久化：assistant 消息与 tool results 单事务原子写入，重连后从事件日志回放恢复会话
- 可观测：按 `stream_id` 关联全链路日志，TTFT / 完成率（区分 abort/server-error）单独打点

来源：[ai-engineering-interview-questions · Multi-Agent Customer Support](https://github.com/amitshekhariitbhu/ai-engineering-interview-questions) · [Anthropic · Building Effective Agents](https://www.anthropic.com/engineering/building-effective-agents) · [Streaming Real-Time Agent UIs](https://tianpan.co/blog/2026-04-10-streaming-real-time-agent-uis-sse-backpressure-reconnection)

### 题 6：设计模型路由 / LLM 网关（OpenRouter / LiteLLM 式）

> Design an LLM gateway that routes across providers/models with failover, rate limiting, cost accounting, and client-facing streaming semantics.

**考察点：**
- 边缘/网关层全栈知识：CDN、代理缓冲、HTTP/2、限流（TPM 是 LLM 的真正约束）
- failover 与流式的冲突：中途切换 provider 时已流出的 token 怎么办
- 多租户隔离与成本记账（按 token 计费的计量管线）
- 前端契约：统一 SSE 事件格式、`stop_reason` 透传、部分响应语义

**答题骨架：**
- 统一 API 面：OpenAI 兼容协议 + 网关侧改写；路由维度 = (租户、tier、feature flag、实验臂)
- 可靠性：provider 健康探测、自动 failover、429/5xx 退避；流中断时「已完成部分 + 错误事件」的明确契约
- 计量与限流：Redis token bucket，RPM 与 TPM 双限，超限即时 429 不占 GPU
- 语义缓存层：相似 query 直接命中（FAQ 场景 30–70%）
- 交付形态：边缘部署（低 TTFT、数据驻留）与集中部署的取舍

来源：[engineering-handbook · 37-model-router-gateway](https://github.com/handbook-academy/engineering-handbook/blob/main/content/hld/part-8-case-studies/37-model-router-gateway.md) · [engineering-handbook · 36-semantic-cache](https://github.com/handbook-academy/engineering-handbook/blob/main/content/hld/part-8-case-studies/36-semantic-cache.md) · [ai-engineering-interview-questions（AI gateway/proxy、fallback 相关题）](https://github.com/amitshekhariitbhu/ai-engineering-interview-questions)

### 题 7：设计端侧 / 浏览器内 AI 助手（WebLLM）

> Design an AI assistant that runs inference in the browser (WebGPU/WebLLM) vs edge vs server-side. When do you choose each, and how do you handle model download UX and fallback?

**考察点：**
- 部署谱系判断力：端侧（隐私/零推理成本/弱算力）vs 边缘（低 TTFT）vs 专用推理服务（质量/工具调用）
- 端侧工程细节：模型下载缓存（Cache API/OPFS）、Web Worker 卸载避免卡 UI、加载进度 UX
- 混合架构：端侧小模型兜底 + 云端大模型升级的降级路径
- 全栈候选人的差异化：能同时谈浏览器 API 与 GPU serving

**答题骨架：**
- 默认服务端（质量 + 工具调用），满足隐私/离线/成本场景才上端侧（WebLLM：OpenAI 兼容 API、WebGPU 加速、Web Worker/Service Worker 隔离）
- 端侧 UX：`initProgressCallback` 做下载/加载进度条、模型首次加载秒级~分钟级的预期管理、失败回退云端
- 能力差异明示：端侧限制（上下文窗口、无重工具链）要在产品上可见
- 混合路由：按任务类型分流（打字建议→端侧、深度问答→云端）
- 权衡表：延迟、成本、隐私、质量、可更新性五轴

来源：[mlc-ai/web-llm](https://github.com/mlc-ai/web-llm) · [ai-engineering-interview-questions · On-Device AI Assistant](https://github.com/amitshekhariitbhu/ai-engineering-interview-questions) · [Outcome School · Cloud vs On-Device](https://outcomeschool.com/blog/cloud-vs-on-device-model-deployment)

### 题 8：设计实时语音 Agent

> Design a real-time voice agent (Alexa/Siri-class): sub-500ms round-trip latency, streaming ASR→LLM→TTS, and client-side audio pipeline UX.

**考察点：**
- 延迟预算收紧到 <500ms 时每个环节的取舍（speculative decoding、prompt caching 变刚需）
- 传输选型：语音为何常走 WebRTC/WS 而文本 token 走 SSE；打断（barge-in）如何实现
- 全栈视角：浏览器麦克风权限、音频采集/回声消除、VAD 在端上的角色
- 失败 UX：识别错误时的纠正回路

**答题骨架：**
- 管线：客户端 VAD/ASR 流式上传 → LLM（短 prompt、强缓存）→ 流式 TTS 分块回传
- 传输：音频用 WebRTC/WS（真双向），信令与状态用 HTTP；打断 = 客户端立即静音 + 上游 abort
- 延迟账：TTFT 预算再砍半，靠小模型路由 + KV 复用 + 端侧回声消除
- UX：说话指示器、转写上屏（可编辑=高效纠正）、失败时自动降级到文本输入
- 部署：区域化推理池（语音对跨区 RTT 极敏感）

来源：[engineering-handbook · 34-voice-agent](https://github.com/handbook-academy/engineering-handbook/blob/main/content/hld/part-8-case-studies/34-voice-agent.md) · [engineering-handbook（AI 案例索引 30–37）](https://github.com/handbook-academy/engineering-handbook) · [30-chatgpt-conversational-ai（语音扩展 follow-up）](https://github.com/handbook-academy/engineering-handbook/blob/main/content/hld/part-8-case-studies/30-chatgpt-conversational-ai.md)

## 3. 六道前端编码题（AI 方向）

### 编码题 1：用 fetch + SSE 实现流式聊天 UI（含取消与状态机）

- **题目**：实现一个 React 聊天组件：POST 发起 SSE 流、逐 token 追加渲染、Stop 按钮中断、错误时显示重试。为什么用 `fetch` + `ReadableStream` 而不是原生 `EventSource`（后者不支持 POST/自定义头）？
- **关键技术点**：`AbortController` 取消；`status` 状态机（submitted/streaming/ready/error → 决定 spinner、Stop、禁用输入）；服务端 `req.on('close')` 传播取消并释放推理资源；`res.flushHeaders()` 与关闭代理缓冲。
- **来源**：[AI SDK · Chatbot 文档](https://ai-sdk.dev/docs/ai-sdk-ui/chatbot) · [Streaming Real-Time Agent UIs](https://tianpan.co/blog/2026-04-10-streaming-real-time-agent-uis-sse-backpressure-reconnection)

### 编码题 2：Token 级打字机效果（节流渲染 + 可中断）

- **题目**：实现打字机效果：流式 delta 高频到达时不能每个 token 触发一次 React 重渲/重排；要求节流批量 flush、流中断后光标态正确清理、`regenerate` 可重跑。
- **关键技术点**：rAF/`setInterval` 合帧批量 flush；`useChat({ throttle: 50 })` 的原理；中断时清理 pending timer 防止「幽灵续写」；markdown 半开语法（未闭合代码块）的降级渲染。
- **来源**：[AI SDK · Chatbot 文档](https://ai-sdk.dev/docs/ai-sdk-ui/chatbot) · [Outcome School · Token Streaming](https://outcomeschool.com/blog/how-does-token-streaming-work)

### 编码题 3：安全渲染 LLM 输出的 Markdown 与代码块（XSS）

- **题目**：LLM 输出含任意 markdown/HTML（可能被 prompt injection 注入 `<script>` 或 `javascript:` 链接）。实现安全的渲染管线：代码高亮、链接净化、公式/表格支持。
- **关键技术点**：`react-markdown` 默认安全（不使用 `dangerouslySetInnerHTML`，默认转义 HTML）；`rehype-raw` 仅在「信任内容」时使用且必须配 `rehype-sanitize` schema；`urlTransform`/`defaultUrlTransform` 白名单协议（http/https/mailto 等）；覆盖 `urlTransform` 为不安全实现是常见 XSS 引入点。
- **来源**：[react-markdown · Security 一节](https://github.com/remarkjs/react-markdown)

### 编码题 4：AI 工具调用的乐观 UI / Generative UI

- **题目**：Agent 流式返回 tool call（部分 JSON delta 累积，`content_block_stop` 才可解析）。实现 UI：`input-available` → 工具卡片 loading 态；`output-available` → 用返回数据渲染真实组件（如天气卡）；`output-error` → 错误态。
- **关键技术点**：流式部分 JSON 的累积与「解析前必须检查 `stop_reason`」（`max_tokens` 截断会让 `JSON.parse` 抛错，需要恢复路径而非崩溃）；`message.parts` 按 `tool-${toolName}` 分派组件；乐观渲染 + 失败回滚；工具失败作为 `is_error` 结果回传让 LLM 重试而非杀死会话。
- **来源**：[AI SDK · Generative User Interfaces](https://ai-sdk.dev/docs/ai-sdk-ui/generative-user-interfaces) · [Streaming Real-Time Agent UIs](https://tianpan.co/blog/2026-04-10-streaming-real-time-agent-uis-sse-backpressure-reconnection)

### 编码题 5：刷新页面后恢复进行中的生成（可恢复流）

- **题目**：一个 3 分钟的 agent 任务流式中途用户刷新页面。实现：重连后从头回放事件、区分「未开始/进行中/已完成」、处理 `complete` 事件先于尾部 chunk 到达的竞态。
- **关键技术点**：原生 `Last-Event-ID` 只能覆盖短流，长任务需要三层架构（KV 存 `task_id→active_stream_id`；独立 stream buffer 如 Redis Streams；SSE 端点纯 relay）；流 ID 在任务开始时生成 UUID（不能用生成结束才分配的框架消息 ID）；reconnect 前先查 `active_stream_id`。
- **来源**：[Streaming Real-Time Agent UIs](https://tianpan.co/blog/2026-04-10-streaming-real-time-agent-uis-sse-backpressure-reconnection)

### 编码题 6：在浏览器里集成端侧推理（WebLLM + Web Worker）

- **题目**：用 WebLLM 在浏览器跑 Llama-3.1-8B：把推理移入 Web Worker 避免卡 UI、实现模型首次下载的进度 UX、流式输出循环、GPU 不可用时优雅回退到服务端 API。
- **关键技术点**：`CreateWebWorkerMLCEngine` / `ServiceWorkerMLCEngine`；`initProgressCallback` 驱动加载进度条；Cache API/IndexedDB/OPFS 模型缓存；OpenAI 兼容接口的 `stream: true` AsyncGenerator 消费；端云切换的产品级 fallback。
- **来源**：[mlc-ai/web-llm](https://github.com/mlc-ai/web-llm) · [Outcome School · Cloud vs On-Device](https://outcomeschool.com/blog/cloud-vs-on-device-model-deployment)

|---|---|---|---|
| **UX 敏感度** | 「模型超时怎么重试」「限流怎么做」 | 「用户怎么知道 AI 在思考？失败了看到什么？幻觉了怎么纠正？」 | 引用 HAX 18 条指南的语言：能力/置信度明示（G01–02）、高效纠正（G09）、不确定时降级（G10）、可解释（G11）。来源：[Microsoft HAI Interaction Guidelines](https://www.microsoft.com/en-us/research/blog/guidelines-for-human-ai-interaction-design/) |
| **流式前端工程** | SSE/WS 传输层实现 | 「代理缓冲谁负责关？背压在前端怎么体现？取消要不要传到 GPU？」 | 知道 `proxy_buffering off`、`res.write()`/drain 背压、AbortController→网关→KV cache 释放的全链路。来源：[Streaming Real-Time Agent UIs](https://tianpan.co/blog/2026-04-10-streaming-real-time-agent-uis-sse-backpressure-reconnection) |
| **边缘 / 端侧部署** | Cloud vs 自建推理 | 「什么时候放浏览器（WebLLM）？模型下载 2GB 的 UX 怎么做？端云如何 fallback？」 | 按五轴（延迟/成本/隐私/质量/可更新性）选型；Worker 隔离、缓存后端、进度反馈。来源：[mlc-ai/web-llm](https://github.com/mlc-ai/web-llm) |
| **可观测性** | QPS/错误率/延迟看板 | 「TTFT 在前端如何打点？完成率为何要区分 abort vs server error？重连成功率怎么算？」 | 用同一 `stream_id` 串联前后端生命周期日志；知道 P99 连接时长决定 `proxy_read_timeout`。来源同上 |
| **DX / 迭代速度** | CI/CD、灰度发布 | 「prompt/模型怎么版本化？eval 怎么进 CI？前端如何快速试验新模型？」 | 评估驱动开发：RAGAS/LLM-as-judge 进 CI、feature flag 切模型、canary + 回归集（引用 Anthropic Claude Code 事故说明 eval 缺失的代价）。来源：[RAGAS](https://docs.ragas.io/) · [interviewing.io · OpenAI](https://interviewing.io/openai-interview-questions) |
| **Agent UI / 人机协同** | agent loop 编排、工具定义 | 「审批按钮放哪？进度事件怎么渲染？中途刷新怎么恢复？」 | 事件分区渲染（thought/tool/diff/done）、`waiting_approval` 状态机、三层可恢复流。来源：[Anthropic · Building Effective Agents](https://www.anthropic.com/engineering/building-effective-agents) · [AI SDK · Generative UI](https://ai-sdk.dev/docs/ai-sdk-ui/generative-user-interfaces) |
| **安全（前端 × 注入交叉）** | prompt injection、guardrails | 「LLM 输出的 markdown 怎么防 XSS？被注入的链接/图片如何净化？」 | 知道 `react-markdown` 默认安全、`rehype-raw`+`rehype-sanitize` 配对、URL 协议白名单；把「不可信模型输出=不可信用户输入」。来源：[react-markdown](https://github.com/remarkjs/react-markdown) |
| **成本 × 产品权衡** | 单位推理成本优化 | 「免费用户用小模型，质量落差在 UI 上怎么处理？排队时给用户看什么？」 | 分层路由 + 前端预期管理（tier 感知提示、busy 降级话术），把 7x 成本差讲成产品决策。来源：[engineering-handbook · 30-chatgpt](https://github.com/handbook-academy/engineering-handbook/blob/main/content/hld/part-8-case-studies/30-chatgpt-conversational-ai.md) |

## 5. 真实大厂信号

- **OpenAI** 已在 onsite 试点 **agentic coding round**（给现成代码库，用 AI 编码代理完成手工无法完成的大改造），且编码题「比 LeetCode 实际」（如 KL divergence 实现、信息论/概率题）——全栈候选人应展示「用 agent 干活 + 判断其产出」的能力。来源：[interviewing.io · OpenAI 面试题库](https://interviewing.io/openai-interview-questions)
- **GitHub Copilot** 公开架构把「45–50% 请求被取消」作为一等设计约束（HTTP/2 stream-reset），说明**取消传播**已是顶级团队的面试考察实质内容。来源：[ZenML · 低延迟全球代码补全服务](https://www.zenml.io/llmops-database/building-a-low-latency-global-code-completion-service)
- **Cursor** 公开 fast-apply 模型（~1000 token/s 全文重写、解决模型数不对行号），可衍生成「实现流式 diff 应用与按 hunk 回滚」的编码题。来源：[Cursor · Instant Apply](https://cursor.com/blog/instant-apply)
- 常见 AI 系统设计题库（Design ChatGPT / Perplexity / Copilot / Cursor / On-Device Assistant / Multi-Agent Support）已收录在：[amitshekhariitbhu/ai-engineering-interview-questions](https://github.com/amitshekhariitbhu/ai-engineering-interview-questions) · [Quant-Developers-Resources · AI System Design](https://github.com/cybergeekgyan/Quant-Developers-Resources/blob/main/Artificial%20Intelligence/AI%20System%20Design/README.md)
